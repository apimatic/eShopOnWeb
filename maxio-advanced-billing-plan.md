Steps (in order):

1. **Config + client wiring** (no SDK op). `MaxioOptions` bound from `Maxio:` with keys `ApiKey`, `Subdomain`, `ProductFamilyHandle`, `BaseUrl`; validated at startup; `MaxioAdvancedBillingClient` registered as singleton with `HttpClient`. Reference the SDK project from `PublicApi.csproj` (see Client facts).
2. **Persistence**: entities `SubscriptionClaim` (composite PK `UserKey`+`PlanHandle`) and `MaxioCustomerLink` (PK `UserKey`) in ApplicationCore/Entities, configurations in Infrastructure/Data/Config, `DbSet`s on `CatalogContext`. No migration is applied (in-memory only).
3. **GET /api/subscription-plans**: `ProductFamilies.ListProductsForProductFamily` with `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`, paged manually -> plan list DTO (handle, name, price, interval).
4. **POST /api/subscriptions** (body: plan handle). Order: validate plan handle against step-3 list -> take SubscriptionClaim -> ensure customer (take MaxioCustomerLink claim; `Customers.ReadCustomerByReference`, else `Customers.CreateCustomer`) -> `Subscriptions.CreateSubscription` -> record result on claim -> return plan/price/state/next billing date.
5. **GET /api/my-subscriptions**: read the caller's claim rows from the store, `Subscriptions.ReadSubscription` for each settled one (live state), settle `Unknown` ones via `Subscriptions.FindSubscription`.
6. Error mapping (Maxio -> HTTP) in the endpoint/service boundary; tests.

## 6. Assumptions & Blockers

Blockers: none.

Assumptions (all decided, headless):

1. **Caller identity**: the JWT carries only `ClaimTypes.Name` (the Identity user name) and roles. `userKey` = that name, trimmed and upper-invariant, read from the authenticated principal (`ClaimsPrincipal`/`HttpContext.User`), never from the request body. Missing/blank -> 401. Source: `IdentityTokenClaimService.cs`.
2. **Customer fields**: `CreateCustomer` requires first name, last name, email, none of which is in the token. Email is read via `UserManager<ApplicationUser>.FindByNameAsync` (already registered in PublicApi `Program.cs`). Identity has no first/last name, so `FirstName` = the local part of the email/user name and `LastName` = the placeholder `"Shopper"` (YOUR CALL; the user can change it). A user with no email -> 422 to the caller.
3. **"Default target" plan `eshop-pro`**: configuration has exactly four keys and handles must not be hard-coded, so the POST body requires a plan handle (`planHandle`); there is no server-side default plan. The client picks from GET /api/subscription-plans. If the user wants an omitted `planHandle` to default to the highest-priced plan this can be added (YOUR CALL).
4. **Plans = products** of `Maxio:ProductFamilyHandle` (not archived). The default price point of the product is used (`ProductPricePointHandle` unset); UNVERIFIED that the SDK/API picks the default price point on omission, so the response `ProductPriceInCents` is echoed back and compared in the integration check to the listed price.
5. **Next billing date** = `Subscription.NextAssessmentAt`, falling back to `CurrentPeriodEndsAt` when null. UNVERIFIED which one Maxio populates for a no-trial, payment-method-less plan; return whichever is non-null and name the field in the DTO doc.
6. **Payment method not required**: no payment profile fields are sent. If the sandbox product nevertheless demands payment info, `CreateSubscription` returns 422 and we map it; that would then be a live finding, not a design change.
7. **Persistence is in-memory**: the userId<->subscription mapping lives in `CatalogContext` tables and is lost on restart. GET /api/my-subscriptions therefore only lists subscriptions created in this run; on an empty store it returns an empty list (no `ListCustomerSubscriptions` fallback, by design, since the task defines the table as the mapping).
8. **Same user + same plan twice** returns the existing subscription (200), not a second one; same user + a different plan is allowed (claim key is user + plan).
9. **Metered component `api-call`** is out of scope for Subscribe (no component allocation is made); its handle is therefore not referenced in code.
10. **EU-hosted sandbox**: config has no environment key; `Us` is used. If the sandbox site is EU-hosted, set `Maxio:BaseUrl` to its URL.
11. The SDK project reference path is machine-local (plugin install dir); report it at hand-over.

## 7. Implementation deviations (recorded after live verification)

- `CreateSubscription` sets `PaymentCollectionMethod = Remittance` (`Models/CreateSubscription.cs`, enum `Models/Enums/CollectionMethod.cs`). With the default (automatic) the sandbox answered 422 "No payment method was on file for the $299.00 balance" even though the plans are payment-method-not-required; remittance collection lets a subscription start without card capture.
- Before `CreateSubscription` the service also calls `FindSubscription` by reference and adopts a match, so a restart of the in-memory store never creates a second Maxio subscription. `CreateCustomer` is likewise preceded by `ReadCustomerByReference`.
- The `IEndpoint<...>` generics in MinimalApi.Endpoint take at most two request arguments, so the three endpoints implement the non-generic `IEndpoint`.
