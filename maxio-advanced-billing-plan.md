## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the SDK project from the project that will own the Maxio gateway (Infrastructure or PublicApi — YOUR CALL — not in the map). Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`; fail fast on missing; register one `MaxioAdvancedBillingClient`. | none (client construction) |
| 2 | Add two claim entities to `CatalogContext` (`MaxioCustomerClaim`, `MaxioSubscriptionClaim`), each with a primary key that refuses a second claim (see DUPLICATE CLAIMS). | none |
| 3 | `GET /api/subscription-plans` — list the configured family's plans (name, handle, price, interval). | `client.ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure-customer (internal, idempotent): claim → adopt existing provider customer by reference → else create → record id. | `client.Customers.ReadCustomerByReference`, `client.Customers.CreateCustomer` |
| 5 | `POST /api/subscriptions` — validate the plan handle against step 3's list, ensure customer, claim, create subscription, record, return plan/price/state/next-billing-date. | `ListProductsForProductFamily` (validation), step 4 ops, `client.Subscriptions.CreateSubscription`, `client.Subscriptions.FindSubscription` (reconciliation) |
| 6 | `GET /api/my-subscriptions` — resolve the caller's Maxio customer (stored id, else by reference), list their subscriptions. A caller with no Maxio customer gets an empty list, not an error. | `client.Customers.ReadCustomerByReference`, `client.Customers.ListCustomerSubscriptions` |
| 7 | Tests: stubbed-HttpClient tests for each endpoint incl. double-submit and connection-failure-after-send. | — |

No capability gap: every step maps to an operation in the map. The metered component `api-call` is out of the task's three endpoints and is not used.

## 5. PRODUCTION READINESS

| # | Concern | Decision |

| 1 | Credential fail-fast | Bind the `Maxio` section to an options class at startup in `src/PublicApi/Program.cs`; validate with `ValidateOnStart()` (or an explicit check before `builder.Build()`): `Maxio:ApiKey`, `Maxio:Subdomain` and `Maxio:ProductFamilyHandle` must each be non-null **and** non-whitespace, else the host refuses to start with a message naming the key (never its value). `Maxio:BaseUrl` is optional; when set it must parse as an absolute `https` URI. ## 6. Assumptions & Blockers

**Blockers**

- **B1 — Build toolchain.** The SDK project declares `LangVersion 14` with `TreatWarningsAsErrors` (SDK `Directory.Build.props`), and its DI helper is a C# 14 `extension(...)` block (`ServiceCollectionExtensions.cs`); C# 14 needs a .NET 10 SDK. The repo's `global.json` pins `8.0.x` with `rollForward: latestFeature`. The machine has SDKs 9.0.317 and 10.0.400 (no 8.0.x). The main agent must confirm the baseline build resolves an SDK at all and decide (with the user) whether `global.json` may be changed to allow the 10.0 SDK — the SDK project cannot compile under an 8.0 compiler. Not a Maxio API gap; it blocks building, not planning.

**Assumptions**

- **A1 — Customer identity (revised at implementation).** Maxio customer `reference` = the eShop Identity **user name** (the JWT `ClaimTypes.Name`), and the claim tables are keyed by it; `Email` = `ApplicationUser.Email`. Reason: Web and PublicApi each seed their own in-memory Identity store with random GUID ids, so the id is not stable across hosts or restarts, while the user name is unique in Identity and stable. YOUR CALL — not in the map.
- **A2 — One subscription per user.** "A double-click never creates two subscriptions" is implemented as one `MaxioSubscriptionClaim` per user (PK = user id). A user who already holds a subscription gets 409 even for the other plan; switching plans/cancel-and-resubscribe is out of scope. If the user wants one per (user, plan), the PK becomes composite (user id, plan handle). YOUR CALL — not in the map.
- **A3 — Required names.** `CreateCustomer.FirstName`/`LastName` are `required` strings, but `ApplicationUser` stores no names. The plan derives non-blank values from the user record (e.g. e-mail local part / a fixed last name) rather than sending empty strings (whether the provider accepts blanks is `UNVERIFIED`). YOUR CALL — not in the map.
- **A4 — `MAXIO_ENVIRONMENT`.** The task lists env var `MAXIO_ENVIRONMENT` but mandates only the keys `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`. The SDK's only environments are `Us`/`Eu` — there is no "sandbox" member; the sandbox is a separate site selected by subdomain. The plan leaves `Environment` at the SDK default `Us` and adds no fifth key. If the user's environment value must pick `Eu`, a binding key is needed — ask.
- **A5 — Env var names vs binding keys.** `MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_DEFAULT_PRODUCT_FAMILY` do not bind to `Maxio:*` keys by .NET's default env-var convention (`Maxio__ApiKey`). Whether to add an explicit mapping from those names into the `Maxio:*` keys is YOUR CALL — not in the map; the code reads only the `Maxio:*` keys.
- **A6 — Claims are process-lifetime in this run.** With `UseOnlyInMemoryDatabase=true` the claim tables vanish on restart. The codebase does have a durable path (SQL Server when the flag is false — would need an EF migration for the two new tables, YOUR CALL). After a restart, ensure-customer adopts the existing provider customer via `ReadCustomerByReference` before creating, and subscribe checks `ListCustomerSubscriptions` for an existing live subscription before claiming a new one (supplementary read, not the refusal).
- **A7 — Plan price display.** Plan price = `Product.PriceInCents` with `Interval`/`IntervalUnit`; the subscription's price = `Subscription.ProductPriceInCents`. No product-level currency field exists in `Product.cs`; show `Subscription.Currency` where present and do not hard-code a currency for plans. Price points (`ProductPricePoints`) are not needed.
- **A8 — "Next billing date".** Returned as `Subscription.NextAssessmentAt` ("when capture of payment will be tried or retried"), with `CurrentPeriodEndsAt` ("when the next regularly scheduled attempted charge will occur") also returned; which one the UI labels "next billing date" is YOUR CALL — not in the map.
- **A10 — Collection method (added at implementation).** Live sandbox traffic refused `CreateSubscription` for `eshop-pro` with 422 "No payment method was on file for the $299.00 balance" under the default (`automatic`) collection. This flow captures no card, so `CreateSubscription.PaymentCollectionMethod` is sent from setting `Maxio:PaymentCollectionMethod` (default `remittance`; validated against `MaxioAdvancedBilling.Models.Enums.CollectionMethod` at startup). Source: `src/MaxioAdvancedBilling/Models/CreateSubscription.cs` (member docs: `remittance`/`automatic`/`prepaid` for Relationship Invoicing, `invoice`/`automatic` for legacy Statements). YOUR CALL — not in the map.
- **B1 resolved.** The .NET 10 SDK builds the C# 14 SDK project; `global.json` now pins `8.0.100` with `rollForward: latestMajor`.
- **A9 — Default plan.** `eshop-pro` is described as the default subscribe target; the plan treats `planHandle` as optional in `POST /api/subscriptions` only if the user wants a default — otherwise required. No numeric IDs are used anywhere (handles only), per the task.
