# Maxio Advanced Billing — subscription billing for eShopOnWeb (plan + contract sheet)

SDK root (plugin-relative): `sdk/dotnet/` — every **source** cell below is relative to it.
Project file to reference: `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` (root namespace `MaxioAdvancedBilling`, `netstandard2.0`, C# 14).

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the SDK project from the layer that will hold the Maxio adapter (Infrastructure, behind an ApplicationCore interface — `YOUR CALL — not in the map`); bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`; fail fast on blanks; register the client via `services.AddMaxioAdvancedBillingClient(...)` in PublicApi `Program.cs` | none (construction) |
| 2 | Add the claim entities to `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`), one config class each beside `src/Infrastructure/Data/Config/BasketConfiguration.cs`: **customer link** (PK = customer reference) and **subscription claim** (PK = subscription reference) — see DUPLICATE CLAIMS | none |
| 3 | Plans read: `GET /api/subscription-plans` — list the products of family `handle:{Maxio:ProductFamilyHandle}`, page-walked with a cap; map name/handle/description/`PriceInCents`/`Interval`/`IntervalUnit`; drop archived | `client.ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure customer (idempotent): claim link row → `ReadCustomerByReference` (survives in-memory restarts) → `CreateCustomer` only on not-found → record Maxio customer id | `client.Customers.ReadCustomerByReference`, `client.Customers.CreateCustomer` |
| 5 | Subscribe: `POST /api/subscriptions` — validate plan handle against step 3's set → ensure customer (step 4) → claim subscription row → `FindSubscription` by the deterministic reference (pre-check after restarts) → `CreateSubscription` with `ProductHandle` + `CustomerId` + `Reference` → record subscription id; return plan/price/state/next billing date. | 6 | My subscriptions: `GET /api/my-subscriptions` — resolve customer id (link row, else `ReadCustomerByReference`; not found → empty list, no customer creation on a GET) → list that customer's subscriptions | `client.Customers.ReadCustomerByReference`, `client.Customers.ListCustomerSubscriptions` |
| 7 | Unknown-outcome settlement in each write's own `catch` (UNKNOWN OUTCOMES) + tests with a failing `HttpClient` stub | `ReadCustomerByReference`, `FindSubscription`, `ListCustomerSubscriptions` |

Endpoints follow the PublicApi convention: one `IEndpoint<...>` class per route, `MapGet/MapPost` in `AddRoute`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<...>().WithTags(...)`, request/response classes deriving `BaseRequest`/`BaseResponse` in nested-file style. Exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. Caller identity: the token carries only `ClaimTypes.Name` = the user's username (read in `src/Infrastructure/Identity/IdentityTokenClaimService.cs`; seeded usernames are emails). Duplicate → 409 already exists via `DuplicateException` in `src/PublicApi/Middleware/ExceptionMiddleware.cs`.

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter, built with an object initializer whose property names are the record's own — never flat arguments. (An operation with no inputs takes none.)
> ⚠ **Every SDK type is written fully-qualified with the namespace its source path implies**, taken from the path the map gives for THAT type — never from where a neighbouring type sits (`Requests/<Controller>/` → `MaxioAdvancedBilling.Requests.<Controller>`; `Models/` → `.Models`; `Models/Enums/` → `.Models.Enums`; `Models/AnyOf/` → `.Models.AnyOf`; `Errors/` → `.Errors`).

All operations: `options.BasicAuth`; server group `Production`; throw-only; no SDK `Pageable` anywhere in scope; trailing params `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a caller sends to `POST /api/subscriptions` (sent as `CreateSubscription.ProductHandle`) must be the `Product.Handle` of a non-archived product returned for family `handle:{Maxio:ProductFamilyHandle}` | `CreateSubscription` ← `ListProductsForProductFamily` | In the subscription service, before the subscription claim and `CreateSubscription`: read the family's product set (same reader as `GET /api/subscription-plans`) and reject (400) a handle not in it. If that read was cut short by the page cap and the handle is absent, fail the request (do not pass an unverified handle) |
| The `CustomerId` passed to `CreateSubscription` and `ListCustomerSubscriptions` must be the `Customer.Id` this application stored (link row) or read back by the caller's own reference — never a caller-supplied id | `CreateSubscription`, `ListCustomerSubscriptions` ← `CreateCustomer` / `ReadCustomerByReference` | In the customer-ensure member, which is the only producer of the id; the endpoints accept no customer id |
| The `SubscriptionId` passed to `ReadSubscription` must be one this application stored on the caller's subscription claim row | `ReadSubscription` ← `CreateSubscription` / `FindSubscription` | In the subscription service's replay path; the endpoints accept no subscription id |

### DUPLICATE CLAIMS

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. **Customer reference = the JWT `ClaimTypes.Name` username** (the only identity claim the token carries; eShop usernames are emails). Using `ApplicationUser.Id` instead would need a `UserManager` lookup per request — `YOUR CALL — not in the map`.
2. **`CreateCustomer` requires `first_name`, `last_name`, `email`**; `ApplicationUser` has no name fields. Plan: `Email` = username; `FirstName`/`LastName` derived placeholders (e.g. email local part / `"eShop"`) — `YOUR CALL — not in the map`. Maxio may reject a username that is not a valid email — `UNVERIFIED`; surface 422 errors.
3. **Subscription-reference uniqueness is `UNVERIFIED`** (the map says only "The reference value (provided by your app) for the subscription itself" and `FindSubscription` returns one subscription). Directive: never rely on Maxio to reject a duplicate subscription reference — the PK claim is the guard; the `FindSubscription` pre-check before `CreateSubscription` covers claims lost to an in-memory restart; settlement falls back to `ListCustomerSubscriptions` matched on `Reference`.
4. **Customer-reference uniqueness is provider-enforced** (`Api/Customers.cs` remarks). A `CreateCustomer` 422 whose errors indicate the reference is taken → re-read via `ReadCustomerByReference` and adopt that customer (exact 422 text `UNVERIFIED`; detect by a follow-up read, not by string matching).
5. **`ReadCustomerByReference` not-found status is undocumented (Case B)** — 404 assumed `UNVERIFIED`; only `HttpStatusCode.NotFound` is treated as "absent", any other status propagates.
6. **In-memory store loses claims on restart** (`UseOnlyInMemoryDatabase=true`). Claim rows therefore stop concurrent duplicates within a process; across restarts the Maxio-side lookups by reference (customer: provider-unique; subscription: `FindSubscription` pre-check) prevent re-creation. On SQL Server the claims are durable. Not a blocker — the task designates `CatalogContext`.
7. **One subscription per (user, plan)**: the subscription claim key is (customer reference, plan handle), so a user can hold Pro and Basic concurrently and re-POSTing the same plan replays the existing one. A canceled subscription cannot be re-created for the same plan under this key — no cancel flow is in scope (`YOUR CALL — not in the map`).
8. **Plan handle in `POST /api/subscriptions`**: request body field (e.g. `planHandle`); if omitted, defaulting to `eshop-pro` (the task's "default subscribe target") is `YOUR CALL — not in the map` — a default handle is not one of the four `Maxio:` keys.
9. **Environment**: `MAXIO_ENVIRONMENT` has no binding key in the task's four-key list; plan uses `ServerEnvironment.Us` (SDK default), whose `Production` template is `https://{site}.chargify.com`, for site `cp-exp-3` — `UNVERIFIED` that the site is US-hosted. Env vars map to keys by deployment convention: `MAXIO_API_KEY`→`Maxio:ApiKey`, `MAXIO_SITE_SUBDOMAIN`→`Maxio:Subdomain`, `MAXIO_DEFAULT_PRODUCT_FAMILY`→`Maxio:ProductFamilyHandle` (mapping mechanism `YOUR CALL — not in the map`; user-secrets in dev).
10. **Price data for listing** comes from `Product.PriceInCents`/`Interval`/`IntervalUnit` (the product's default price point) — no `ProductPricePoints` call. Currency is not on `Product`; site currency assumed (USD per task).
11. **Next billing date** returned to the user = `Subscription.CurrentPeriodEndsAt` ("when the next regularly scheduled attempted charge will occur"); `NextAssessmentAt` may diverge after a failed renewal.
12. **SDK reference is machine-local**: the `<ProjectReference>` points into this plugin's install directory (`sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`); CI/teammates need the plugin at the same path. The SDK uses C# 14 `extension` blocks — builds only with the .NET 10 SDK; repo `global.json` pins `8.0.x` with `rollForward: latestFeature`, so running under the .NET 10-only SDK needs roll-forward handling (task says "run with roll-forward").
