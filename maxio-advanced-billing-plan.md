| Invariant | Operations | Enforced where |

| A plan handle accepted by subscribe must be one of the plans `GET /api/plans` offers (non-archived product inside a product family this app created for a catalog brand) — `ReadProductByHandle` succeeding only proves the product exists in Maxio, not that this app offers it | `Subscriptions.CreateSubscription` (`ProductHandle`) <- `ProductFamilies.ListProductFamilies` + `ProductFamilies.ListProductsForProductFamily` (the same helper that serves F1) | plan-catalog helper, called before `CreateSubscription`; 400/422 with reason when the handle is not offered |

| A subscription id in any shopper path is acted on only if its `Customer.Reference` equals the JWT `ClaimTypes.Name`; the Maxio customer exists only because this app created it with that reference | `ReadSubscription` / every status, migrate, update, usage op <- `Customers.CreateCustomer` (reference set from JWT name) | ownership helper run before every shopper write/read; mismatch -> 404 (no existence leak) |

### DUPLICATE CLAIMS

Store: `OperationClaims` table on `CatalogContext` (`ApplicationCore/Entities/OperationClaim.cs`, string primary key; migration `20261112120000_AddOperationClaims`). Order: claim -> SDK call -> release in `finally`. Decision: claims are held only while the write is in flight (stale after 5 min) — they stop concurrent duplicates without blocking a legitimate later write (e.g. re-subscribing after cancelling).

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| Subscribe | `OperationClaims`, key `subscribe:{user}:{handle}` | primary-key violation | `OperationClaimStore.TryClaimAsync` catches `DbUpdateException` -> endpoint answers 409 | `SubscribeEndpoint.HandleAsync`: `claims.TryClaimAsync` then `billing.SubscribeAsync` |
| Create plan | key `create-plan:{plan handle}` | primary-key violation | same -> 409 | `CreatePlanEndpoint.HandleAsync`: `claims.TryClaimAsync` then `billing.CreatePlanAsync` |
| Currency price | key `currency-price:{planId}:{currency}` | primary-key violation | same -> 409 | `CreateCurrencyPriceEndpoint.HandleAsync`: `claims.TryClaimAsync` then `billing.AddCurrencyPriceAsync` |

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**

1. `planId` in `/api/admin/plans/{planId}/currency-prices` and the plan's `id` in plan responses is the Maxio product id (int); `plan handle` is the Maxio product `Handle`. Maxio is the system of record; there is no local plan table.
2. The create-plan body is `{ "name", "price" (monthly, decimal), "brand" }`, where `brand` is the catalog brand NAME (case-insensitive match to `CatalogBrand.Brand`); an unknown brand is 400. Plan billing interval is 1 month. decided, see §7 (shape of the app's own request).
3. Maxio product family per brand is created on first use (handle = app prefix + `CatalogBrand.Id`); "offered plans" are products in such families.
4. Shopper identity = JWT `ClaimTypes.Name`; customer `reference` is that value; any signed-in user (including an administrator) may subscribe for themselves; the administrator role (`Administrators`) gates all `/api/admin/*` endpoints.
5. `MAXIO_ENVIRONMENT` value: `US`/`EU` (case-insensitive) map to `ServerEnvironment`; `sandbox`, `production`, `live` and blank are treated as `US` (the SDK has no sandbox member and the sandbox host is selected by subdomain). Any other value fails startup.
6. Card-less subscribe uses `PaymentCollectionMethod.Remittance` and a product with `RequireCreditCard = false`; acceptance by the sandbox site is `UNVERIFIED` (see 2.4). If the sandbox site rejects it, the endpoint returns 422 with the provider reason — no fabricated card data.
7. `paid` = `balance_in_cents <= 0`, with the invoice-based fallback of 2.4 if the sandbox shows the balance ignores open invoices (`UNVERIFIED`).
8. Switch on a canceled subscription = product change via `UpdateSubscription` (stays canceled, on the new plan), not reactivation; acceptance by the provider is `UNVERIFIED`.
9. New persistence (three claim tables) requires an EF migration for the SQL Server path; the in-memory path needs none.
10. The four `Maxio:` values are loaded into `dotnet user-secrets` of `src/PublicApi` from the sandbox env vars by the main agent; the fail-fast check means existing PublicApi integration tests also need those values present in their environment.
11. Date format for usage and next-billing-date is `YYYY-MM-DD` (strict); next billing date is applied at 00:00:00 UTC of that date.

## 7. Decisions settled during implementation (former decided, see §7)

- Customer reference = JWT `ClaimTypes.Name`; names derived from the e-mail local part (`FindOrCreateCustomerAsync`). Ownership mismatch and unknown id both answer 404 (`ReadOwnedAsync`).
- Offered plans = non-archived products in product families whose handle starts with `eshop-brand-` (`MaxioBillingService.FAMILY_HANDLE_PREFIX`, `ListPlansAsync`); one family per catalog brand id (`FindOrCreateFamilyAsync`).
- Plan creation: interval 1 month, description = name, `RequireCreditCard=false`, handle `{slug}-b{brandId}` (`CreatePlanAsync`); request accepts `name`, `price`/`monthlyPrice`, `brand` (name) or `brandId`; unknown brand -> 400.
- Subscribe: `PaymentCollectionMethod.Remittance`; verified against the sandbox: accepted without card details. Several plans at once are allowed; duplicates only blocked while one is in flight (see claims). No per-(shopper, plan) permanent rule (changed from the first draft).
- `paid` = balance_in_cents <= 0 AND no open-invoice amount due (`ToInfoAsync`, `OpenInvoiceDueAsync`). Sandbox check: a remittance subscription on a priced plan reports a positive balance (paid=false).
- Pause only from active/trialing; resume only from on_hold/paused; cancel immediate, not when already canceled; restart only from canceled with `ReactivateSubscription` (no `Resume`), (`RequireState`).
- Switch: live -> `MigrateSubscriptionProduct`; canceled/trial_ended -> `UpdateSubscription{ProductHandle}` (stays canceled on the new plan). Verified in the sandbox: accepted, handle changed, state stays canceled; restart then reactivates on the new plan.
- Usage: one day = since D, until D+1 at UTC-midnight dates, then filtered to the requested calendar date in the offset the provider returns (`GetUsageAsync`). Sandbox plans had no metered components, so the usage path was only verified to answer 200 with an empty list (`UNVERIFIED` with data: time zone).
- Currency price: baseline role on the plan's default price point; whole-number price only. Sandbox site has no extra currency defined, so only the 422 relay was exercised (`UNVERIFIED`: unit of `price`).
- Next billing date: UTC midnight of the date, future dates only, live states only, verified by re-reading `CurrentPeriodEndsAt` (sandbox: verified).
- Status mapping (`MapStatus`): provider 404 -> 404; 400/409/422 -> 422 with the provider's text; 401/403 -> 502; 429 -> 503; timeout -> 504; other -> 502.
- Overall budget: 45 s per request (`BillingEndpointHelper.RunAsync`), per-attempt 15 s, retries GET/HEAD only (`MaxioServiceCollectionExtensions`).
- Fail-fast: the host throws at startup when `Maxio:ApiKey` is blank, or both `Maxio:Subdomain` and `Maxio:BaseUrl` are blank, or `Maxio:Environment` is not US/EU (sandbox/production/blank treated as US).
