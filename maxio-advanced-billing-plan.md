## 3. Trap notes

- Step 1 — what `options.Retry.Timeout` vs `HttpClient.Timeout` vs a `CancellationToken` each bound, and which verbs are resent; a wrong pick holds the request thread for minutes. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- Step 1 — an unset/blank credential is not an error to the SDK; the call simply goes out unauthenticated. **MUST load `maxio-advanced-billing:dotnet-authentication`**
- Step 1 — client/`HttpClient` lifetime, DNS staleness of a singleton, and the shared default factory client. **MUST load `maxio-advanced-billing:dotnet-client-initialization`**
- Step 1 — built-in SDK logger is on/off depending on how the client is built; env var can turn body logging on (customer email/name in the create body). **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- Step 3 — list endpoint has page params but no SDK pagination; an unbounded manual loop / silent truncation. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- Steps 3–6 — Case A vs Case B catch types differ per operation; a wrong `TError` compiles and never matches. **MUST load `maxio-advanced-billing:dotnet-error-handling`**
- Step 4 — a 404 on read-by-reference vs an unreadable body are different facts; conflating them causes a spurious create. **MUST load `maxio-advanced-billing:dotnet-error-handling`**
- Steps 4–5 — POST outcome after a transport failure is unknown, and the injected `Idempotency-Key` header is not a key. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- Steps 3–6 — open enums: `ToString()`/interpolation is not the wire value; unknown values still deserialize. **MUST load `maxio-advanced-billing:dotnet-models`**
- Steps 3–6 — request record vs body model naming (`…OperationRequest`), positional `requestOptions`. **MUST load `maxio-advanced-billing:dotnet-calling-endpoints`**
- Step 8 — request body is disposed after the call; counting resends; constructing SDK exceptions. **MUST load `maxio-advanced-billing:dotnet-testing`**

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | `MaxioOptions` bound from `Maxio:` with `ValidateOnStart()` + custom validator: `ApiKey` non-blank, and either `BaseUrl` (absolute http/https URI) or `Subdomain` non-blank, `ProductFamilyHandle` non-blank, `Environment` ∈ {US, EU}. Basic password is the fixed `x` (map), so the one secret part is checked. Message names the key, never the value. |
| 2 | Secret sourcing & rotation | `Maxio:ApiKey` comes from config: .NET user-secrets in Development (PublicApi `UserSecretsId`), env vars (`Maxio__ApiKey`) / secret store elsewhere. Options built once when the singleton client is first resolved — rotation requires a restart (acceptable; documented). |
| 3 | Total timeout budget | Per-attempt `Retry.Timeout` = 10 s, `HttpClient.Timeout` = 15 s backstop, `MaxRetries` = 2; every SDK call runs under one `Bounded()` helper: linked CTS with a 25 s per-call ceiling (`MaxioSubscriptionService.CallBudget`). Every public operation runs its reads under one 60 s deadline linked to `HttpContext.RequestAborted` (`WithinOperationBudget`, `OperationBudget`). Writes (`CreateCustomer`, `CreateSubscription`) and their settlement lookups run outside that deadline under their own 25 s budget (never under the caller's token), so a deadline never cuts a create off after Maxio may have acted. Worst case for subscribe ≈ 60 s of reads + 2 × (25 s create + 25 s lookup). A deadline that fires surfaces as 503 + `Retry-After`. |
| 4 | Write-retry ownership | SDK default `HttpMethodsToRetry` (GET/HEAD/PUT/OPTIONS) kept → `CreateCustomer`/`CreateSubscription` (POST) are never resent by the SDK; reads may be retried. The app never auto-resends writes; it reconciles instead. |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: real key = `CreateCustomer.Reference` (provider-unique per remarks) → reconcile via `ReadCustomerByReference`. `CreateSubscription`: no provider-enforced key in the map; `CreateSubscription.Reference` is an app-supplied reference (uniqueness `UNVERIFIED`) used for lookup via `FindSubscription`. Injected `Idempotency-Key` header is not a key. |
| 6 | Observability | SDK built-in logger with `LoggerFactory` from DI (Information request/response lines, Warning retries, Error terminal); service logs Information on create/settle, Warning on provider rejection (status + provider messages), Error on unknown outcome. Correlation: Maxio error bodies in scope carry no correlation id (map: `ErrorListResponse1.errors`, `CustomerErrorResponse1.errors` only) → we log our own claim id / subscription reference + HTTP status. |
| 7 | Sensitive data | Create-customer body carries email + name (PII) → `LogRequestBody = false`, `LoggerFactory` assigned explicitly (disables `MAXIOADVANCEDBILLINGCLIENT_LOG`), no request bodies in our logs; `reference` query param is masked by the SDK's allow-list. No card data in scope. |
| 8 | Environment selection | One server group in scope: `Production` (`Ebb` unused). `Maxio:Environment` (US default / EU) picks `ServerEnvironment`; `Maxio:Subdomain` → `options.Server.Production.{Us,Eu}.Site`; `Maxio:BaseUrl`, when set, → `options.Server.Production.{Us,Eu}.BaseUrl` verbatim. The SDK declares no sandbox environment: test traffic is kept off live by the site — dev user-secrets point at the sandbox site; tests use a stub handler / unroutable `BaseUrl`. |
| 9 | Duplicate prevention under concurrency | See DUPLICATE CLAIMS. |
| 10 | Partial results | See PAGED READS. |
| 11 | Unknown outcomes | See UNKNOWN OUTCOMES. |

## 6. Assumptions & Blockers

- Assumption: the eShop identity key for billing is the JWT `Name` claim (username = email); the token carries no user-id claim, and the in-memory identity store regenerates user ids each run, so the username is the only stable key. Billing reference = `eshop-` + lower-cased username.
- Assumption: Maxio customer first/last name (required) — ApplicationUser has no name fields; first name = email local part, last name = `"eShop customer"`. YOUR CALL — not in the map.
- Assumption: one live subscription per user per plan; re-subscribing to an ended plan creates a new one.
- Assumption: `ReadCustomerByReference` signals "no such customer" with 404 (`UNVERIFIED` — Case B carries no typed 404); any other status/unreadable body is treated as an error, never as absence.
- `UNVERIFIED`: whether Maxio rejects a duplicate subscription `reference` — not relied on; the local claim is the guard.
- Found in live sandbox testing (2026-10-19): a create without `payment_collection_method` is rejected with 422 "No payment method was on file for the $299.00 balance" even though the plans do not require a payment method (the default collection charges a card). Resolved with the SDK-documented non-card collection method chosen per site (`ReadSite.relationship_invoicing_enabled`: `remittance`, else `invoice`). A missing flag is treated as Relationship Invoicing (`UNVERIFIED` on a legacy site).
- Verified live (sandbox, 2026-10-19): plans list; double-click → one 201 + one 409 with exactly one `POST /customers.json` and one `POST /subscriptions.json`; sequential repeat → 200 `already_subscribed`; after a process restart (in-memory store wiped) → 200 `already_subscribed` with zero Maxio writes; `ReadCustomerByReference` signals absence with 404 (assumption confirmed).
- Blockers: none.
