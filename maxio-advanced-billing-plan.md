### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |

| 11 | Unknown outcomes | See UNKNOWN OUTCOMES: on `SdkConnectionException`/`SdkTimeoutException`/budget expiry on a POST, the same `catch` re-reads by reference; if still unsettled the claim row is set `Unknown` and the hosted sweeper settles it | below |

### DUPLICATE CLAIMS

Order for every row: claim (insert) -> SDK call -> record the result; the claim is released (row deleted) only when Maxio definitively refused the call (422/4xx `ApiException`) or the plan was never sent. Store = `CatalogContext` (the store the codebase already keeps its records in). Entities have a natural string primary key (`HasKey` on the claim key; NOT `BaseEntity`), because a primary key is refused by the in-memory provider and by SQL Server; no unique index is relied on. Claim states: `Pending` (claimed, SDK call not yet resolved) -> `Completed` (Maxio ids stored) | `Unknown` (outcome not settled). A caller who loses the claim reads the row: `Completed` -> returns the stored result (HTTP 200, same body); `Pending`/`Unknown` -> reconcile once (re-read by reference) and, if still unsettled, HTTP 409 "in progress" (no second provider write). A `Pending` row older than a lease (5 min > the 45s budget) is treated as `Unknown`.

## 6. Assumptions & Blockers

**Blockers:** none. Every needed capability (list products of a family by handle, read customer by reference, create customer, create/find/list subscriptions, read site) is on the map.

**Assumptions:**
1. **No sandbox environment in the SDK.** `ServerEnvironment` has only `Us`/`Eu`; sandbox and production are distinguished by site and API key, not by host. `MAXIO_ENVIRONMENT` therefore maps to no SDK member and no fifth `Maxio:` key is added (the four keys are exact). Sandbox-only is enforced at startup by `Sites.ReadSite` -> `Site.Test == true`, failing closed. (`Site.Test` semantics are inferred from the field name — UNVERIFIED against live traffic.)
2. **Caller identity** = the `ClaimTypes.Name` claim of the JWT (the only identity claim the token service issues). The user key is that name, trimmed and lower-cased. It is never sent to Maxio or logged raw as the reference — only its SHA-256 hash. No `NameIdentifier` claim exists.
3. **Customer PII:** `CreateCustomer` requires first name, last name and email; the Identity user has none of the names. Email is taken from `UserManager<ApplicationUser>` for that user name (falling back to the JWT name only if it is email-shaped, else 400). First/last name: YOUR CALL — not in the map: derive first name from the email local part and use a fixed last name placeholder; flagged as a product decision.
4. **Plans have no card requirement** (task statement; `Product.RequireCreditCard` is surfaced). `PaymentCollectionMethod` is left unset so the site/product default applies; whether Maxio accepts a payment-less create for these plans is **UNVERIFIED** (not a Blocker: the task states it works). A 422 here is mapped to a 422/502 for the caller with the error strings, no retry.
5. **One subscription per user per plan handle** (the claim key). Re-subscribing the same plan returns the existing result (HTTP 200) rather than creating a second; cancel/resubscribe is out of scope — YOUR CALL.
6. **Maxio-side uniqueness** of customer `reference` and subscription `reference` is **UNVERIFIED**; the design does not depend on it (local claim is the guard; references are only lookup keys). The "not found" HTTP status of `ReadCustomerByReference` (Case B) is **UNVERIFIED** (404 assumed; other statuses are errors).
7. **"Next billing date"** is returned from `Subscription.NextAssessmentAt`, falling back to `CurrentPeriodEndsAt` when null (both nullable).
8. **Claim persistence** lives in `CatalogContext` (in-memory when `UseOnlyInMemoryDatabase=true`): claims, like the existing data, are lost on restart; recovery after restart is by `ReadCustomerByReference` / `FindSubscription` by deterministic reference (this is why those reads precede each create). No EF migration is generated for the in-memory run; a migration is a YOUR CALL for the SQL Server path.
9. **Duplicate-key exception type** raised by the EF in-memory provider (`DbUpdateException` vs `InvalidOperationException`) is UNVERIFIED; a test pins it, and the catch covers both.
10. Repo note: `global.json` shows as modified in the working tree at plan time (environment roll-forward, not touched by the planner).

## 7. As-built deviations (recorded after implementation)

1. **One claim table** (`MaxioClaims`, natural string PK = reference) instead of two; customer vs subscription is the `Kind` column.
2. **No hosted sweeper.** Unknown claims are settled lazily: the next request for the same (user, plan) hits the adopt-read by deterministic reference, which completes the claim. No new infra.
3. **Sandbox guard is a warning, not a startup refusal.** `MaxioStartupCheck` reads the site, logs whether it reports `test`, and refuses to start only on 401/403 (bad credentials). Refusing on `Site.Test == false` would stop the same build running against another site.
4. **Payment collection method.** A payment-less create with the default (automatic) collection returned HTTP 422 "No payment method was on file" in the sandbox (observed live). The service now sends `PaymentCollectionMethod` = `remittance` on Relationship Invoicing sites and `invoice` on legacy sites, chosen from `Site.RelationshipInvoicingEnabled` (`MaxioSiteInfo`). Verified live: subscription created `active`.
5. **Endpoint-level tests** were not kept: the in-process `TestServer` (Mvc.Testing 8.0.2) fails on this machine's .NET 10 runtime with `PipeWriter ... UnflushedBytes` — the pre-existing PublicApi integration tests fail identically without my changes (12 of 15). Service-level tests (`MaxioSubscriptionServiceTest`) cover the logic; the endpoints were verified live over HTTPS.
