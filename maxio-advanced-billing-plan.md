### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The `planHandle` a caller POSTs must be a `Product.Handle` returned for the configured family (non-archived) | `CreateSubscription.Body.Subscription.ProductHandle` ← `ProductFamilies.ListProductsForProductFamily` (`ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`) | the subscribe service, before the subscription claim, `CreateCustomer` and `CreateSubscription` — it calls the step-4 plan reader and rejects (400) a handle not in the set; if the set was `Truncated` and the handle is absent, reject with a distinct "catalog incomplete" error instead of "unknown plan" |
| The `customer_id` sent to create a subscription must be the `Customer.Id` Maxio returned for *this* caller's deterministic reference | `CreateSubscription.Body.Subscription.CustomerId` ← `CreateCustomer` / `ReadCustomerByReference` (result stored in the customer link row) | the ensure-customer step, which returns only the id stored on (or just recorded to) the caller's own link row; never a caller-supplied id |
| The `CustomerId` listed for "my subscriptions" must be the caller's own stored/looked-up id | `ListCustomerSubscriptions.CustomerId` ← `CreateCustomer` / `ReadCustomerByReference` | the my-subscriptions handler resolves it from the caller's `ClaimTypes.Name` only (link row, else `ReadCustomerByReference`); no id is accepted from the request |
| The reference re-read after an unknown outcome must be the one this app stored on the claim before the write | `FindSubscription.Reference` ← the subscription claim row written before `CreateSubscription`; `ReadCustomerByReference.Reference` ← the customer link row written before `CreateCustomer` | the reconciliation code in each write's `catch`, which reads the reference from the claim row, never recomputes or accepts it from the request |

## 3. Trap notes

| Step | Hazard (what it costs) |

| 2 | HttpClient ownership/lifetime and singleton registration choices decide socket exhaustion and whether options can ever change. **MUST load `maxio-advanced-billing:dotnet-client-initialization`** |

| 2 | Pointing the client at `Maxio:BaseUrl` / the subdomain: which override point wins, and which server group each operation resolves through — a wrong pick sends sandbox traffic to the placeholder `subdomain` site or a live site. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`** |
| 2 | Logging posture: request bodies carry customer PII; the env-var log switch can turn body logging on with no deploy. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`** |

| 7 | Existing `ExceptionMiddleware` echoes `exception.Message` on 500 — an SDK exception message reaching it may expose provider/request details. **MUST load `maxio-advanced-billing:dotnet-error-handling`** |

Hazard row (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

(In scope here: `ProductResponse.Product`, `CustomerResponse.Customer` and `ErrorListResponse1.Errors` are `required` — a 2xx/422 missing them throws `ResponseDeserializationException`; on `CreateCustomer`/`CreateSubscription` a 2xx that fails deserialization means the provider **acted** → treat as unknown outcome and reconcile, never release the claim.)

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. **Identity = `ClaimTypes.Name`** (the only stable identity in the JWT; seeded users have user name = email). `ApplicationUser.Id` is not used: the in-memory identity store is re-seeded every run, so the GUID changes; the Maxio customer reference is derived deterministically from the normalized user name (exact format `YOUR CALL`, e.g. `eshop-` + lowercase user name or its hash), so a restart re-finds the same Maxio customer via `ReadCustomerByReference`.
2. **Customer fields:** `CreateCustomer` requires `first_name`, `last_name`, `email`; eShopOnWeb has no names. Email = user name (reject 400 if it is not an email); first/last name derived (e.g. email local-part / a fixed "eShop customer" label) — `YOUR CALL`.
3. **Duplicate scope:** one subscription claim per (user, plan). A double-click on the same plan never creates two; subscribing to a *different* plan creates a second subscription. Re-subscribing to the same plan after a cancellation is blocked within a run by the completed claim (no cancel flow is in scope). Across restarts (in-memory store lost) duplicates are prevented by the post-claim `ListCustomerSubscriptions` pre-check for a live subscription on the same product.
4. **`POST /api/subscriptions` body requires `planHandle`.** The task names `eshop-pro` as the "default subscribe target" but mandates no config key for a default plan and forbids hard-coding catalog values; the endpoint therefore does not default the plan (UI may preselect it). If a default is wanted, a new config key would be needed — confirm with the user.
5. **Price/period display:** plans show `Product.PriceInCents` with `Interval`/`IntervalUnit`; `Product` has no currency field (subscriptions expose `Currency`). "Next billing date" = `Subscription.NextAssessmentAt`, falling back to `CurrentPeriodEndsAt` — `YOUR CALL`.
6. **`MAXIO_ENVIRONMENT`** — decided at implementation: bound as the *optional* `Maxio:Environment` (`US` default / `EU`), selecting `ServerEnvironment.Us`/`.Eu` and the matching `options.Server.Production.{Us|Eu}` override point; the four mandated keys are unchanged.
7. **Payment collection (revised after live traffic):** the sandbox rejected `CreateSubscription` without a collection method (422 "No payment method was on file for the $299.00 balance" via `TryGetErrorListResponse1`). The app never captures a card, so it now sends the SDK-documented `payment_collection_method` = `remittance` (invoice-based; Relationship Invoicing) by default, overridable via optional `Maxio:PaymentCollectionMethod`. Verified live: Pro and Basic subscriptions created `active`.
8. **Persistence:** new entities are added to `CatalogContext` (in-memory in this environment). For the SQL Server path an EF migration would be required (`src/Infrastructure/Data/Migrations`); whether to add one is `YOUR CALL` (no LocalDB here to generate/verify against).
9. **SDK reference is machine-local** (ProjectReference into the plugin directory) — CI or another machine needs the plugin installed and the reference re-pointed.
10. Out of scope: metered component `api-call`, cancellation/plan change, webhooks, Web/Blazor UI.
