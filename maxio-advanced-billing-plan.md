## 1. Scope & sequence

Repo conventions (pattern → ONE exemplar to imitate):
- Admin endpoint: `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `IEndpoint<IResult, TRequest, ...>`, `app.MapPost("api/...")`, `.Produces<T>().WithTags(...)` → `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`.
- Anonymous-style list endpoint + AutoMapper/repository use → `src/PublicApi/CatalogBrandEndpoints/CatalogBrandListEndpoint.cs` (brands come from `IRepository<CatalogBrand>`, `CatalogBrand.Brand` is the name).
- Request/response base types `BaseRequest`/`BaseResponse` (correlation id) → `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.CreateCatalogItemRequest.cs`.
- Errors: `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps only `DuplicateException` → 409 and everything else → 500. Every "app cannot carry out the request" case here must therefore return an explicit 4xx `Results.*` with a reason (never let it reach the middleware as 500).
- DB: `src/Infrastructure/Data/CatalogContext.cs` + `Data/Config/CatalogBrandConfiguration.cs` (EF Core; SQL Server, or in-memory when `UseOnlyInMemoryDatabase`); migrations in `Infrastructure/Data/Migrations`.
- JWT facts read from `src/Infrastructure/Identity/IdentityTokenClaimService.cs`: token carries ONLY `ClaimTypes.Name` (= the Identity user name) and one `ClaimTypes.Role` per role. No user id / email claim. Admin role constant: `BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS` ("Administrators"). Signed-in shopper = `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`; identity read from the principal's `ClaimTypes.Name`, never from request body/query.

Steps (operation names are SDK controller.method):
1. **Settings + client** (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:Environment`, `Maxio:BaseUrl`): bind, validate on start, register singleton client. No SDK operation.
2. **Claim store** (app DB): new `MaxioOperationClaim` entity (PK `Key` string, `ClaimedAtUtc`, optional `Result`), EF config, migration. No SDK operation. Used by steps 4, 7, 9, 10 (see DUPLICATE CLAIMS).
3. **Plan catalog service** (shared by features 1, 2, 6, 8, 9): `ProductFamilies.ListProductFamilies`, `ProductFamilies.ListProductsForProductFamily`, `Products.ReadProductByHandle`, `Products.ReadProduct`. Defines "offered plan" (§2 invariants).
4. **Customer mapping** (feature 2): `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`.
5. **Feature 1** GET /api/plans (signed-in shopper): list offered plans.
6. **Feature 2** POST /api/subscriptions `{planHandle}`: `Components.ListComponentsForProductFamily`, `Customers.ListCustomerSubscriptions`, `Subscriptions.CreateSubscription`.
7. **Feature 3** GET /api/subscriptions/{subscriptionId}: `Subscriptions.ReadSubscription` (+ ownership check).
8. **Features 4–6** pause/resume/cancel/restart/switch: `SubscriptionStatus.PauseSubscription`, `ResumeSubscription`, `CancelSubscription`, `ReactivateSubscription`; `Subscriptions.UpdateSubscription` (switch); each preceded by `Subscriptions.ReadSubscription` (ownership + state).
9. **Feature 7** GET /api/subscriptions/{id}/usage?date=: `SubscriptionComponents.ListSubscriptionComponents`, `SubscriptionComponents.ListUsages`.
10. **Feature 8** POST /api/admin/plans: `ProductFamilies.CreateProductFamily` (first use per brand), `Products.CreateProduct`.
11. **Feature 9** POST /api/admin/plans/{planId}/currency-prices: `Sites.ReadSite`, `Products.ReadProduct`, `ProductPricePoints.CreateProductCurrencyPrices`.
12. **Feature 10** PUT /api/admin/subscriptions/{id}/next-billing-date: `Subscriptions.ReadSubscription`, `Subscriptions.UpdateSubscription`.
13. Tests against the Maxio sandbox (no stubbing of Maxio): real calls from `tests/PublicApiIntegrationTests` style; secrets from user-secrets only.

Key design decisions (these are the task's cross-operation rules; the reasoning is in §2 and §6):
- **Plan = Maxio product; brand = Maxio product family.** One product family per catalog brand, handle `eshop-brand-{CatalogBrand.Id}`, name = `CatalogBrand.Brand`. The plan's brand is stored by the product family it sits in (the Maxio product model has no brand field — read `Models/CreateOrUpdateProduct.cs`). "Offered plans" = non-archived products in product families whose handle matches `eshop-brand-{id}` AND whose id is still a `CatalogBrand` in the shop's catalog. Plan id in routes = Maxio product id (`Product.Id`, int); plan handle = `Product.Handle`.
- **Ownership = Maxio customer `reference`.** Each shopper maps 1:1 to a Maxio customer whose `reference` is `eshop:{ClaimTypes.Name lower-cased}`. A subscription belongs to the caller iff `Subscription.Customer.Reference` equals that reference (re-read from Maxio on every shopper call; Maxio stays the record). Not owned or not found → **404** (do not leak existence).
- **"paid"** = `Subscription.BalanceInCents <= 0` (null balance → treated as not determinable → 502 with reason, not guessed). `balance_in_cents` is "the current outstanding subscription balance" (`Models/Subscription.cs`); positive = owes money; zero/negative = owes nothing (credit).
- **Subscribe without card**: `PaymentCollectionMethod = CollectionMethod.Remittance` (invoice, no card, no `payment_profile`), with `Reference` = deterministic reference derived from the claim key (see DUPLICATE CLAIMS). Fallback if the sandbox site is on the legacy statements architecture and rejects `remittance` (422): retry the single call once with `CollectionMethod.Invoice` (UNVERIFIED which architecture the sandbox site uses).
- **Switch** uses `Subscriptions.UpdateSubscription` with `ProductHandle` (immediate product change; `ProductChangeDelayed` NOT set) for every state, including canceled. `MigrateSubscriptionProduct` is rejected: its remarks only allow `active`/`trialing` and say a `trial_ended`/ended subscription "should be canceled, the product changed, and then … reactivated" (`Api/SubscriptionProducts.cs` remarks) — the update path is the one that works on a canceled subscription. After the call, the response's `Subscription.Product.Handle` MUST equal the requested handle, else report failure (a delayed change or silent no-op must not be reported as "switched").
- **Next billing date** sets `UpdateSubscription.NextBillingAt` only; see invariants for why a call alone is not "billed on that date".

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a shopper subscribes with (`POST /api/subscriptions`) must be an *offered plan*: a non-archived product in a brand family `eshop-brand-{id}` whose `{id}` is still a catalog brand — not merely a product that exists on the Maxio site | `Subscriptions.CreateSubscription` ← `ProductFamilies.ListProductFamilies` + `ProductFamilies.ListProductsForProductFamily` (the same read that backs GET /api/plans) | plan catalog service, before `CreateSubscription` (not `ReadProductByHandle`, which only proves existence) |

Other plan facts:
- Plan creation: `Handle` = slug of the plan name (lower-case, `[a-z0-9-]`), unique per site; a name that slugs to an existing product handle → 409 (app checks with the plan list before writing). `PriceInCents` = `round(monthlyPrice × 100)` from a decimal request price > 0; `Interval = 1`, `IntervalUnit.Month`. Description required by the SDK → plan name unless the request supplies one.
- Currency prices: `CreateProductCurrencyPrice.Price` is an `int` (whole currency units) while the response `CurrencyPrice.Price` is a `double`; unit semantics are UNVERIFIED in the map (a request with a fractional price cannot be expressed) → reject non-whole prices with 400 stating that. One entry, `Role = Baseline`. The product has no trial or setup fee, so no further roles are needed ("must mirror the structure of your primary pricing").
- Usage per day: day semantics from remarks: `since_date`/`until_date` "default to midnight on the date specified" and `until_date` is inclusive of midnight (`≤`), so a one-day window `[D, D+1)` is NOT expressible exactly. Query `SinceDate = D−1 day`, `UntilDate = D+2 days` (midnight, offset 0) and keep only usages whose `CreatedAt` local date (in the offset the API returns, i.e. the site time zone) equals D; total per component = sum of `Quantity` (`Quantity1` int or numeric string; non-numeric → reported as an error, not 0). UNVERIFIED: how `DateTimeOffset` is rendered in the query string, and the site time zone behind `created_at`.

## 3. Trap notes

- Request construction: every operation takes one request record with a nested body wrapper (`CreateSubscriptionRequest { Subscription = … }`, `UpdateSubscriptionRequest`, `CancellationRequest`, `CreateOrUpdateProductRequest`, `CreateCustomerRequest`, `CreateProductFamilyRequest`) — a flat body does not compile and an omitted wrapper sends nothing useful. **MUST load maxio:dotnet-calling-endpoints**
- Enums are open string records, not C# enums; an unrecognised server state is a real possibility for a default-deny state machine. **MUST load maxio:dotnet-models**
- `Quantity1` is a union with an int and a string arm and an unknown arm; reading it wrongly silently yields zero usage. **MUST load maxio:dotnet-models**
- Cancel/Pause/Resume/Reactivate/Update/Create all have per-operation typed 422 payloads, while Read*/List* are `RawError` (Case B): one catch ladder will not cover both shapes, and a body that fails to deserialize is a third type. **MUST load maxio:dotnet-error-handling**
- Client lifetime: the options (including `Server.Production.*.BaseUrl` and the environment) are captured at construction; what a late edit does is not what it looks like. **MUST load maxio:dotnet-client-initialization**
- Credential wiring: which source fills `BasicAuth`, and what "fail on start" must check when the credential comes from `IConfiguration` rather than the SDK's variables. **MUST load maxio:dotnet-authentication**
- Timeouts and retries: what `Retry.Timeout` and `HttpClient.Timeout` bound, which verbs are resent by default (two of this plan's reactivate/update writes are among them), and where a whole-call budget lives. **MUST load maxio:dotnet-configuration-resilience**
- Paged reads: plain list operations here return a plain list, not a `Pageable`; the stop condition and what a truncated result must say to the caller. **MUST load maxio:dotnet-configuration-resilience**
- The same write arriving twice and a write whose connection fails mid-flight need code in this app, not SDK settings. **MUST load maxio:dotnet-configuration-resilience**
- Tests: Maxio must not be stubbed (task), but connection-failure and 422 paths still need to be provoked; the seam and what can be asserted. **MUST load maxio:dotnet-testing**

Hazard row (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 6. Assumptions & Blockers

Blockers: none that stop planning. No operation the task needs is missing from the map (checked: Customers, Products, ProductFamilies, ProductPricePoints, Subscriptions, SubscriptionStatus, SubscriptionComponents, Components, Sites).

Assumptions (major first; the first four deserve a glance):
1. **Brand storage.** Maxio products have no brand attribute in the SDK (`Models/CreateOrUpdateProduct.cs`), so brand = product family per catalog brand (`eshop-brand-{CatalogBrand.Id}`), created on demand by plan creation. Plans in other families (e.g. products pre-existing on the sandbox site) are intentionally NOT offered. Renaming/deleting a catalog brand makes its plans un-offered (they stay in Maxio).
2. **No-card subscribe** uses `CollectionMethod.Remittance` (fallback `Invoice` once on a 422 that rejects it); the resulting open invoice makes `paid = false` until Maxio shows a zero balance. **Verified live: the sandbox accepted `Remittance` (the `Invoice` fallback in `Subscribe.Create` was not needed); a new subscription reports `paid = false`.** With `Automatic` and no card Maxio would reject creation. If the sandbox rejects both, that is a runtime blocker to report, not to stub.
3. **Switch on a canceled subscription** relies on `UpdateSubscription` + `ProductHandle` working on canceled subscriptions (supported by the SubscriptionProducts remark's "canceled, the product changed, then reactivated" flow). The code verifies the returned `Product.Handle`; the subscription stays canceled (switch changes the plan, not the state) — "puts them on the new plan" is interpreted as the plan on the subscription. **Verified live: a canceled subscription switched to the new plan (it stays canceled, on the new plan).**
4. **Currency price units**: SDK sends `price` as an `int`; interpreted as whole currency units; fractional → 400. UNVERIFIED whether Maxio reads it as units or cents. **The sandbox site has no non-primary currency enabled (`site.non_primary_currencies` is empty; Maxio itself answers 422 "Currency must be defined on the site level"), so the success path of feature 9 could not be exercised live; only its refusals are tested.**
5. **Next billing date**: set as noon UTC of the requested date (so the calendar date holds across site time zones UTC−11…UTC+11). **Decided as written; `MaxioBillingService.SetNextBillingDate`. Verified live: the sandbox site (UTC+5) returned `next_billing_at` on the requested date.** Because the response omits `next_billing_at`, success is verified by re-read of the period end. The call itself does not bill: billing happens when Maxio processes the subscription after that moment, only for renewing states (`Active`/`Trialing`); canceled/on-hold subscriptions would not be billed and are refused. No product price point or product family is needed for this call (only `next_billing_at`); calendar-billing `snap_day` is not used.
6. **Usage day**: the "day" is the site-time-zone calendar date of the usage's `created_at`; the app widens the query by a day each side (the API's `until_date` is inclusive of midnight) and filters locally. Metered components attached at subscribe time are all non-archived `metered_component`s of the plan's family (the plan "includes" them); the other system records usage against those components. UNVERIFIED that `CreateSubscriptionComponent` with only `ComponentId` is accepted (no member is marked required in `Models/CreateSubscriptionComponent.cs`); the sandbox plans created for the tests have no metered components, so the usage endpoint was verified only for the empty case.
7. **Customer fields**: Maxio customer needs first/last name and email; the JWT has only the user name. Email = the Identity user's email (looked up via `UserManager<ApplicationUser>.FindByNameAsync`), else the user name when it is an address, else 400; first name = local part, last name = `eShop`. **Decided as written; `MaxioBillingService.EnsureCustomer`.**
8. **Same plan twice**: a shopper may hold several plans at once but not two live subscriptions to the same plan (409). A "live" subscription = state not `Canceled`/`Expired`/`FailedToCreate`.
9. **Cancel** is immediate (no schedule parameters); problem states allowed per the table. **Decided as written; `MaxioBillingService.Cancel`.**
10. **Pause** is indefinite (no `automatically_resume_at`); body-less hold is accepted. **Verified live.**
11. `ListProductFamilies` and `ListCustomerSubscriptions` show no paging in the map; if the sandbox site is large, results may be cut by the API without the SDK saying so (not detectable — noted, not mitigated).
12. A new EF migration (`MaxioOperationClaims`) is needed for SQL Server; the in-memory provider (tests) needs none. The ProjectReference to the plugin's SDK is machine-local.
