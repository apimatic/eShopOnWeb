# Maxio Advanced Billing plan: eShopOnWeb subscriptions (PublicApi)

SDK root (plugin-relative): `sdk/dotnet/`. Every `Source` cell below is relative to that root. The map index is `sdk-map.md`, and the operations pages are `map/operations/*.md`.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Add a `ProjectReference` from `src/PublicApi` (or `src/Infrastructure`, YOUR CALL) to `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`. Bind a `Maxio` options class from the `Maxio:` section (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`), validate it at start, then register the client in DI. | none |
| 2 | Persistence: add two EF entities to `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`): a customer link and a subscription enrollment. Both are keyed by the eShop user id (`ApplicationUser.Id`). Each gets an `IEntityTypeConfiguration` modelled on `src/Infrastructure/Data/Config/CatalogBrandConfiguration.cs`, but with a string PK and no HiLo. | none |
| 3 | Plan catalog: build `GET /api/subscription-plans` by walking pages of the products in the family `handle:{Maxio:ProductFamilyHandle}`. Drop archived products. Map name/handle/price/interval. | `ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure customer (idempotent): claim the link row, then reconcile (`ReadCustomerByReference`, reference = eShop user id). Call `CreateCustomer` only if the lookup finds nothing. Record the customer id. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5 | Subscribe: check the requested plan handle against step 3's set. Ensure the customer (step 4). Claim the enrollment row, which holds a generated subscription reference. Call `CreateSubscription` (product handle + customer id + reference). Record the result. If the outcome is unknown, settle it with `FindSubscription`. Serves `POST /api/subscriptions`. | `Subscriptions.CreateSubscription`, `Subscriptions.FindSubscription`, `Customers.ListCustomerSubscriptions` (fallback settle) |
| 6 | My subscriptions: resolve the customer (local link, else `ReadCustomerByReference`), list that customer's subscriptions, and settle any `Pending` enrollment along the way. Serves `GET /api/my-subscriptions`. | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions`, `Subscriptions.FindSubscription` |
| 7 | Error boundary: turn SDK exceptions into HTTP results inside the endpoints/services, before they reach `src/PublicApi/Middleware/ExceptionMiddleware.cs`. That middleware writes `exception.Message` into the 500 body. | all of the above |
| 8 | Tests: stubbed-`HttpClient` unit tests (unknown outcomes, 404/422 paths, truncation). Existing `tests/PublicApiIntegrationTests` must still boot `Program`, so they need non-secret dummy `Maxio:` settings. | none |

Endpoint convention: `MinimalApi.Endpoint` `IEndpoint<IResult, …>` classes with `AddRoute` + `HandleAsync`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<…>().WithTags(…)`, and request/response classes deriving from `BaseRequest`/`BaseResponse` (correlation id). The exemplar is `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. Caller identity: the JWT carries only `ClaimTypes.Name` = user name, plus roles (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`). Resolve `ApplicationUser` with `UserManager<ApplicationUser>.FindByNameAsync` to get `Id` and `Email`.

Hazard row (verbatim): a body that does not match its declared type surfaces as `ResponseDeserializationException`. That covers a drifted or malformed **2xx** response (a missing `required` member) and a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape. That exception is an `ApiException` that keeps the HTTP status and names the target type, but it is **not** an `ApiException<TError>`. A catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

Specific to this scope: `ListProductsForProductFamilyError` decodes the 404 body as a JSON **string** (`src/MaxioAdvancedBilling/Errors/ListProductsForProductFamilyError.cs`), and `ProductResponse.Product` / `CustomerResponse.Customer` / `ErrorListResponse1.Errors` are `required`. A non-string 404 body, or a missing envelope, lands in the `ResponseDeserializationException` arm.

## 6. Assumptions & Blockers

**Blockers:** none. All in-scope capabilities exist in the map: list family products by handle, look up a customer by reference, create a customer with a reference, create a subscription by product handle + customer id with a subscription reference, find a subscription by reference, and list a customer's subscriptions.

**Assumptions:**
1. **Store and restart.** The claim store is the existing `CatalogContext` (SQL Server in production, EF in-memory here). PK inserts are refused by both providers. Unique indexes are not enforced in-memory, so none are relied on. In-memory loses every link and enrollment on restart. After a restart, state is settled from Maxio: `ReadCustomerByReference(eShop user id)` finds the customer, and `ListCustomerSubscriptions` shows its subscriptions. A `Pending` row lost in a restart cannot be settled by `FindSubscription`, because its reference is gone. The fallback is `ListCustomerSubscriptions`.
2. **User ids are not stable on the in-memory store.** In this environment the Identity store is in-memory too (`src/Infrastructure/Dependencies.cs`), and `AppIdentityDbContextSeed` re-creates `demouser@microsoft.com` / `admin@microsoft.com` on each start without a fixed `Id`. So `ApplicationUser.Id`, and with it the customer reference, changes on every restart. After a restart the same shopper gets a **new** Maxio customer (the old one is orphaned; Maxio refuses nothing, since the reference differs). On SQL Server the Id is stable, and that is the production design. The alternative is reference = user name/email: stable here, but mutable in production. Decision: user id (production-correct). The main agent may revisit (YOUR CALL — not in the map).
3. **Identity source.** The JWT carries only `ClaimTypes.Name` (user name) and roles. The user id and email come from `UserManager<ApplicationUser>.FindByNameAsync(name)`. An unknown user → 401.
4. **Customer names.** `CreateCustomer` requires `FirstName`, `LastName` and `Email`, but `ApplicationUser` has no name fields. Decision: `POST /api/subscriptions` accepts optional `firstName`/`lastName`. The fallback is the email local part for first name and a fixed non-empty placeholder for last name. YOUR CALL — not in the map.
5. **Plan selection.** `POST /api/subscriptions` body requires `planHandle`. It is validated against the live family listing. No plan handle is hard-coded, so a different catalog works. The task's "default target `eshop-pro`" is a demo value, not a code default. Re-subscribing while an `Active` enrollment exists → 409. Plan changes and cancellation are out of scope.
6. **Metered component `api-call`.** It is not attached at signup, and usage recording is out of scope.
7. **Next billing date and price.** "Next billing date" = `Subscription.CurrentPeriodEndsAt` (doc: "when the next regularly scheduled attempted charge will occur"). `NextAssessmentAt` is also returned, because it diverges on payment retries. Price = `Subscription.ProductPriceInCents` (`long?`, cents) + `Subscription.Currency`. Plan prices come from `Product.PriceInCents`/`Interval`/`IntervalUnit`. `Product` has no currency field, so the plans list shows cents without a currency code. YOUR CALL — not in the map.
8. **Payment method.** The plans are configured "payment method not required" (task). If a product does require a card, `CreateSubscription` is expected to refuse with a 422 (remarks: payment information "may be required … depending on the options for the Product"). That 422 is surfaced to the caller and the claim is released. No card capture or 3DS is planned.
9. **Archived products.** Server-side filtering of archived products when `IncludeArchived` is unset is **UNVERIFIED**, so the mapper also drops products with `ArchivedAt != null`.
10. **SQL Server migrations.** New entities need an EF migration for the SQL Server path. The in-memory provider ignores migrations. Adding one is the main agent's call. The run here does not need it.
11. **Toolchain.** The SDK project targets `netstandard2.0` with C# `LangVersion 14` (its DI helper uses an `extension` block), so it needs the installed .NET 10 SDK. `global.json` pins `8.0.x` with `rollForward: latestFeature`, which does not roll to a new major. The main agent must select the .NET 10 SDK (the task says roll forward). The `ProjectReference` into the plugin's `sdk/dotnet/` is machine-local: CI or another machine needs the plugin at the same path or a re-pointed reference.
13. **Collection method (found in live traffic).** The sandbox plans need no payment method, but the site still tried to charge the first period automatically and refused the create (422, no payment method on file). The flow captures no card, so subscriptions are created with `payment_collection_method = remittance` (invoiced). A legacy Statements-architecture site would need `invoice` instead (the enum documents both). That would be a one-line change, and it is not exposed as configuration.
12. **Wire defaults sent.** `CreateSubscription` always sends `defer_signup: false` and `dunning_communication_delay_enabled: false` (non-null model defaults). These are assumed to be benign defaults.
