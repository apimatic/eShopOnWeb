# Maxio Advanced Billing integration plan — eShopOnWeb subscriptions (PublicApi)

SDK root (plugin-relative): `sdk/dotnet/` · project to reference: `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` · map: `sdk/dotnet/sdk-map.md` + `sdk/dotnet/map/operations/`. All `src/...` paths below are relative to that SDK root.

## 1. Scope & sequence

| # | Step | Operations used |

Endpoint convention (read, not invented): one class per endpoint implementing `MinimalApi.Endpoint.IEndpoint<...>`, `AddRoute` mapping `api/...` with `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<T>()`, `.WithTags(...)`, request/response classes deriving from `BaseRequest`/`BaseResponse` with `CorrelationId()` — exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. Exceptions → `src/PublicApi/Middleware/ExceptionMiddleware.cs` (maps `DuplicateException` → 409, everything else → 500). Caller identity: the PublicApi JWT carries only `ClaimTypes.Name` (= the Identity user name) and roles — read in `src/Infrastructure/Identity/IdentityTokenClaimService.cs`. `UserManager<ApplicationUser>` and `IMemoryCache` are registered in `src/PublicApi/Program.cs`.

## 2. CONTRACT SHEET

> ⚠ Signatures are generated code, verbatim. Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer using that record's own property names — never flat arguments.
> ⚠ Every SDK type is written fully-qualified with the namespace its own source path implies (taken from the path the map gives for THAT type, never from a neighbouring type): `Models/` → `MaxioAdvancedBilling.Models`, `Models/Enums/` → `MaxioAdvancedBilling.Models.Enums`, `Models/AnyOf/` → `MaxioAdvancedBilling.Models.AnyOf`, `Errors/` → `MaxioAdvancedBilling.Errors`, `Requests/<Controller>/` → `MaxioAdvancedBilling.Requests.<Controller>`, `ApiException<T>`/`ResponseDeserializationException`/`SdkConnectionException`/`SdkTimeoutException` → `MaxioAdvancedBilling.Core.Exceptions`, `RawError` → `MaxioAdvancedBilling.Core.ErrorResponse`, `RequestOptions` → `MaxioAdvancedBilling.Core`.

All operations: throw-only (no `…Result` variants), Auth `options.BasicAuth`, server group `Production`, no SDK pagination (map defaults table).

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Settings class bound from `Maxio:` section; validated at startup (options validation with `ValidateOnStart`, or an explicit check before `builder.Build()` in `src/PublicApi/Program.cs`): `Maxio:ApiKey` non-blank, `Maxio:ProductFamilyHandle` non-blank, and `Maxio:Subdomain` non-blank unless `Maxio:BaseUrl` is set (then `BaseUrl` must be an absolute URI). BasicAuth's second part is the constant `"x"` (map), so the API key is the only variable part — checked for blank, not just null. The host refuses to start otherwise. The existing `tests/PublicApiIntegrationTests` host must supply non-secret placeholder `Maxio:*` values in test code (e.g. `WebApplicationFactory.WithWebHostBuilder(...UseSetting...)`), never real values. `YOUR CALL — not in the map` for mechanism. |
| 2 | Secret sourcing & rotation | Source: env `MAXIO_API_KEY`/`MAXIO_SITE_SUBDOMAIN`/`MAXIO_DEFAULT_PRODUCT_FAMILY` → `dotnet user-secrets set Maxio:ApiKey ...` etc. on `src/PublicApi` (existing `UserSecretsId`); env vars `Maxio__ApiKey` also bind (Program calls `AddEnvironmentVariables()`). The DI client is a singleton whose options (incl. `BasicAuth`) are built once on first resolution and captured — a rotated key takes effect only after a process restart; accepted (no hot rotation requirement in the task). |
| 3 | Total timeout budget | Per attempt: `options.Retry = RetryOptions.Default() with { Timeout = 10s }`. Total: one budget per inbound HTTP request — **30 s** — enforced in the gateway's single `Bounded(...)` wrapper via a `CancellationTokenSource` linked to `HttpContext.RequestAborted` with `CancelAfter(30s)`, one token shared by every SDK call in that handler. Subscribe makes ≤ ~6 calls (list plans pages, read customer, create customer, find subscription, create subscription) — GET retries make the worst case exceed 30 s, so the token, not the knobs, is the caller's ceiling. Reconciliation reads inside a write's `catch` run on their own fresh 10 s token (the budget token may be the thing that fired). |
| 4 | Write-retry ownership | `HttpMethodsToRetry` stays at the SDK default (it excludes POST) — `CreateCustomer` and `CreateSubscription` (both POST) are sent at most once per call by the SDK; GETs (`ListProductsForProductFamily`, `ReadCustomerByReference`, `FindSubscription`, `ListCustomerSubscriptions`) may be retried by the SDK. Nobody may widen the verb list; the application never re-sends a write before reconciling. |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: no key member on `CreateCustomerOperationRequest`; the body's `reference` is provider-unique per remarks ("you can only create one customer for a given reference value") → send deterministic customer reference; reconcile with `ReadCustomerByReference`. `CreateSubscription`: no key member on `CreateSubscriptionOperationRequest`; body `reference` set deterministically but provider uniqueness `UNVERIFIED` → reconcile with `FindSubscription(reference)` (fallback: `ListCustomerSubscriptions` matched on `Product.Handle` + `CreatedAt` after the claim's timestamp). ## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. **Caller identity → Maxio customer reference.** The PublicApi JWT carries only `ClaimTypes.Name` (the Identity user name, an email for seeded users) — no user-id claim (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`). `ApplicationUser.Id` is regenerated on every in-memory run (the seed creates users without a fixed id, `src/Infrastructure/Identity/AppIdentityDbContextSeed.cs`), so the customer reference is derived deterministically from the normalized user name (prefixed, e.g. `eshop-user:<name>`; hashing optional), which stays stable across restarts and keeps one Maxio customer per eShop user. `YOUR CALL — not in the map`.
2. **Customer names.** `CreateCustomer` requires `first_name`, `last_name`, `email`; `ApplicationUser` has no name fields. Email = Identity email/user name; first/last name derived (e.g. local part of the email / a fixed fallback such as "eShop" "Customer") — never empty strings. `YOUR CALL — not in the map`.
3. **One subscription per user per plan.** The deterministic subscription reference is f(customer reference, plan handle); a repeated POST for the same plan returns the existing subscription (200) instead of creating another. Re-subscribing after cancellation is out of scope. `YOUR CALL — not in the map`.
4. **Claims only survive one run here.** With `UseOnlyInMemoryDatabase=true` the claim tables are lost on restart (user-acknowledged). Cross-restart duplicates are then caught by the pre-create reads (`ReadCustomerByReference`, `FindSubscription`) and, for customers, the provider's documented reference uniqueness; for subscriptions provider-side reference uniqueness is `UNVERIFIED`. Under SQL Server the claims are durable once an EF migration for the two new entities is added (migrations are ignored by the in-memory provider; generating one does not need LocalDB).
5. **`MAXIO_ENVIRONMENT` is not bound.** The task mandates exactly `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`; the SDK's `ServerEnvironment` is a hosting region (`Us`/`Eu`), not sandbox/production, so the client uses the SDK default `Us` and the sandbox is selected by the site subdomain.
6. **No payment method.** Subscriptions are created without `payment_profile_id`/card attributes. *Live finding (fix round 1, falsifies the original UNVERIFIED assumption):* with the default (automatic) collection method the sandbox refused `CreateSubscription` with 422 "No payment method was on file for the $299.00 balance", even though the products do not require a payment method at signup. Resolution: `CreateSubscription.PaymentCollectionMethod = CollectionMethod.Remittance` (invoice-billed), a named constant in the gateway, no configuration key. Whether the site accepts `remittance` (Relationship Invoicing) is to be confirmed on the next live run; any 422 is still surfaced as a refusal with the provider's messages and releases the claim.
7. **`ListCustomerSubscriptions` completeness.** The record has no paging inputs; whether the provider caps the list is `UNVERIFIED`. My-subscriptions returns what the call returns; acceptable for a per-user list.
8. **Plan list contents.** Plans = non-archived products of the configured family; the metered `api-call` component is not a product and is neither listed nor attached at subscribe time (not requested).
9. **Machine-local SDK reference.** The `<ProjectReference>` points into this plugin's install directory; the solution builds only where the plugin is installed at that path (teammates/CI need it re-pointed), and `src/PublicApi/Dockerfile` builds will not see it.
10. **Existing duplicate-check pattern is not reused as the guard.** `CreateCatalogItemEndpoint` does a count-then-insert (`DuplicateException` → 409); only its 409 mapping via `ExceptionMiddleware` is reused, the guard itself is the primary-key claim.
