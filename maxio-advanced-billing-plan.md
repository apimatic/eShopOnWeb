# Maxio Advanced Billing — subscription billing for eShopOnWeb (plan + contract sheet)

SDK root (plugin-relative): `sdk/dotnet/` — all `Source` paths below are relative to it. Map: `sdk-map.md`, `map/operations/*.md`.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the plugin's SDK project from `src/PublicApi` (and Infrastructure if the service lives there); bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`; fail-fast validation; DI-register the client | none (client construction) |

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer whose property names are the record's own — never flat arguments.
> ⚠ **Every SDK type is written fully-qualified with the namespace its source path implies**, taken from the path the map gives for THAT type, never from where a neighbouring type sits (e.g. `MaxioAdvancedBilling.Requests.Customers.ReadCustomerByReferenceRequest`, `MaxioAdvancedBilling.Models.CustomerResponse`, `MaxioAdvancedBilling.Models.AnyOf.Errors1`, `MaxioAdvancedBilling.Models.Enums.SubscriptionState`, `MaxioAdvancedBilling.Errors.CreateSubscriptionError`, `MaxioAdvancedBilling.Core.Exceptions.ApiException<T>`, `MaxioAdvancedBilling.Core.ErrorResponse.RawError`).

All operations: auth `options.BasicAuth`; throw-only; server group `Production`; every non-GET sends a fresh `Guid.NewGuid()` `Idempotency-Key` header (NOT a key). Common trailing params on every signature: `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.

**Idempotency facts (resolved):** none of the request records in scope carries a key-shaped member (no idempotency key / request id / `If-Match`). `CreateCustomer`: the body's `reference` is **provider-enforced unique** (remarks of `Api/Customers.cs` `CreateCustomer`) — a second create with the same reference is rejected; the rejection's status/shape is **UNVERIFIED** (expected the declared 422 `CustomerErrorResponse1`; directive: on any `ApiException<CreateCustomerError>` during ensure-customer, re-read with `ReadCustomerByReference` before reporting failure). `CreateSubscription`: the subscription `reference` is app-provided and findable (`FindSubscription`), but the map does **not** state that the provider enforces its uniqueness → **UNVERIFIED**; it is a reconciliation handle only, never the dedupe mechanism.

### DUPLICATE CLAIMS

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. Caller identity is the JWT `ClaimTypes.Name` claim — the only identity claim `src/Infrastructure/Identity/IdentityTokenClaimService.cs` puts in the token (the user name, which is the e-mail in this app). The token's name is resolved to an existing user via `UserManager.FindByNameAsync` (`BillingUserResolver`). Decided: the Maxio customer `reference` is `"eshop-"` + the first 16 bytes (hex) of SHA-256 over the upper-cased user name (`MaxioSubscriptionBillingService.CustomerReference`) — deterministic (it survives in-memory restarts, where seeded Identity ids are regenerated), unique per user, and free of the e-mail address.
2. `CreateCustomer` requires `first_name`, `last_name`, `email`; eShop users have only user name/e-mail. Decided: `first_name` = e-mail local part, `last_name` = `"eShopOnWeb"`, `email` = the user's e-mail (`MaxioSubscriptionBillingService.NamesFor`).
3. `MAXIO_ENVIRONMENT` is not one of the four mandated `Maxio:` keys and the SDK has no sandbox environment member (`Us`/`Eu` are hosting regions). Plan keeps `ServerEnvironment.Us` (default) and treats sandbox vs. live as a matter of site subdomain/key. Decided: optional `Maxio:Environment` (`US` default / `EU`; loaded into user-secrets from `MAXIO_ENVIRONMENT`) selects `ServerEnvironment.Us/Eu`, and `Maxio:Subdomain` / `Maxio:BaseUrl` are written to the matching node (`MaxioSettings.IsEu`, `MaxioBillingServiceCollectionExtensions.BuildClientOptions`).
4. Env vars `MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_DEFAULT_PRODUCT_FAMILY` do not bind to `Maxio:*` automatically (.NET maps `Maxio__ApiKey`); they are copied into PublicApi user-secrets under `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle` (and `Maxio:BaseUrl` only when overriding).
5. "Next billing date" shown to the user: `Subscription.CurrentPeriodEndsAt` (next regularly scheduled charge) vs. `NextAssessmentAt` (next payment attempt; diverges after a failed renewal). Decided: `nextBillingAt` = `NextAssessmentAt ?? CurrentPeriodEndsAt`, with `currentPeriodEndsAt` returned alongside (`MaxioSubscriptionBillingService.ToSummary`).
6. Price shown for a plan: `Product.PriceInCents` with `Interval`/`IntervalUnit`; for a subscription: `Subscription.ProductPriceInCents`. Currency is not on `Product`; `Subscription.Currency` exists. Displaying USD for plans is an assumption.
7. `GET /api/my-subscriptions` returns all of the customer's subscriptions from Maxio (no product-family filter) — Decided: no filter — the customer is created by and for this app, so all of its subscriptions are the user's eShop subscriptions; sorted newest first (`MaxioSubscriptionBillingService.ListSubscriptionsCoreAsync`).
8. Both formerly UNVERIFIED provider behaviours were confirmed live on 2026-11-13: `handle%3A…` in the family path is accepted (200) and `ReadCustomerByReference` answers 404 for an unknown reference.
9. EF migration `20261113000549_AddBillingClaims` (Infrastructure) creates `BillingClaims` for SQL Server. It is scoped to that table only: pre-existing, unrelated nullability drift on `Orders`/`OrderItems`/`Catalog` was left out of it and of the snapshot. The in-memory provider ignores migrations.
