# Maxio Advanced Billing integration plan: eShopOnWeb subscriptions (PublicApi)

SDK: NuGet `sohail-ab-sdk` (install version-less into `src/PublicApi`), root namespace `MaxioAdvancedBilling`. All contract facts below come from the SDK map (`sdk-map.md`, `map/operations/*.md`) and the source files those pages name, from branch `main` of the SDK source repo.

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none). Build it with an object initializer whose property names are the record's own, never flat arguments. Every operation also takes `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.
>
> ⚠ **Every SDK type is written fully-qualified with the namespace its source path implies**, taken from the path the map gives for THAT type, never from where a neighbouring type sits. Request records are in `MaxioAdvancedBilling.Requests.<Controller>`, models in `MaxioAdvancedBilling.Models`, enums in `MaxioAdvancedBilling.Models.Enums`, AnyOf unions in `MaxioAdvancedBilling.Models.AnyOf`, errors in `MaxioAdvancedBilling.Errors`, `ApiException<T>` in `MaxioAdvancedBilling.Core.Exceptions`, `RawError` in `MaxioAdvancedBilling.Core.ErrorResponse`.

All operations: Auth `options.BasicAuth`; server group `Production`; throw-only (no `…Result` variants); no SDK `Pageable`.

**Hazard (verbatim):** a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

Note for this scope: `ProductResponse.Product`, `CustomerResponse.Customer` and `ErrorListResponse1.Errors` are `required`, so a body missing them takes that path.

## 6. Assumptions & Blockers

**Blockers**

- **B1. Claim store does not outlive the process under the mandated configuration.** The codebase's record store is `CatalogContext`; with `UseOnlyInMemoryDatabase=true` (required by the task) it is EF Core InMemory and is lost on restart. Within one process the primary-key claims fully stop double-clicks. After a restart: customers stay safe, because Maxio enforces one customer per `reference` (method remarks) and the 422 path adopts the existing customer via `ReadCustomerByReference`. Subscriptions are not safe: the claim and its stored reference are gone, and the provider does not document unique subscription references. A user who subscribed before a restart can subscribe again afterwards. Proposed mitigation (YOUR CALL, needs user acceptance): when a new subscription claim is made, first call `ListCustomerSubscriptions` for the (re-adopted) customer and refuse if a live subscription already exists. That is a read, not a refusal, so it does not close concurrent races; the PK claim does that. With the SQL Server configuration the claims persist and B1 does not apply. Needs the user to accept this limitation as inherent to the in-memory requirement.

**Assumptions**

- A1. Env-var to config mapping: `MAXIO_API_KEY` -> `Maxio:ApiKey`, `MAXIO_SITE_SUBDOMAIN` -> `Maxio:Subdomain`, `MAXIO_DEFAULT_PRODUCT_FAMILY` -> `Maxio:ProductFamilyHandle`, all loaded into PublicApi user-secrets. `MAXIO_ENVIRONMENT` has no binding key in the task's list and the SDK has no sandbox environment (only `Us`/`Eu`); sandbox targeting is by subdomain, so `Environment` stays `Us`. If the sandbox site is EU-hosted, a `Maxio:BaseUrl` override is the way to point at it.
- A2. Caller identity: the JWT has only `ClaimTypes.Name` (user name). The endpoint resolves `ApplicationUser` by name and keys claims on `ApplicationUser.Id`. That id is stable for the life of the Identity store, but the Identity store is also in-memory and re-seeded on restart, so seeded users get new ids after a restart. That makes B1 worse for customers too: a new user id means a new reference, so a second Maxio customer is created for the same person. Alternative (YOUR CALL): use the normalized user name (email) as the customer reference, which survives re-seeding. **Recommended: reference = `eshop:` + normalized user name**, claim PK still the user id.
- A3. `CreateCustomer` requires `first_name`, `last_name`, `email`; `ApplicationUser` has no name fields. First name = email local part, last name = "eShopOnWeb" placeholder (YOUR CALL).
- A4. One subscription per user (claim PK = user id). A POST for a different plan while one exists returns 409, not a plan change. A POST body with no handle defaults to `eshop-pro`.
- A5. Plans are taken from the family's non-archived products (`IncludeArchived` unset; `ArchivedAt == null` filter applied too); the metered component `api-call` is not listed or attached (out of scope for Subscribe).
- A6. No payment profile and no collection method are sent; the plans are configured "payment method NOT required" (task statement). If Maxio returns 422 for a missing payment method, that would be a configuration blocker; the planner does not expect it given the stated plan config.
- A7. "Next billing date" = `Subscription.CurrentPeriodEndsAt`, also returning `NextAssessmentAt` (doc: diverges only on failed renewal). Price = `Subscription.ProductPriceInCents` / 100 with `Currency`.
- A8. Maxio errors map to HTTP: invariant failure 400; 422 from Maxio 422 with the provider's error strings; claim conflict 409; unknown outcome that cannot be settled 503 (claim kept Pending); connection/timeout/5xx/deserialization 502. Mapping is YOUR CALL.

## 7. Implementation decisions (recorded after coding)

- **B1 accepted** (headless run, decided by the implementing agent): the in-memory claim store cannot outlive a restart. Mitigation implemented: before any new create, `EnsureSubscriptionAsync` lists the customer's Maxio subscriptions and adopts a live one (no second create), and `EnsureCustomerAsync` looks the customer up by reference before creating. Verified live across a restart: the same subscription was returned with `created:false`, and no duplicate was created. With SQL Server the claims persist; migration `AddBillingClaims` creates both tables (billing-only: pre-existing model drift on Orders/OrderItems/Catalog was deliberately left out).
- **A2 adopted**: the claim primary key and the customer reference both derive from `ApplicationUser.NormalizedUserName` (`eshop:<lower-cased name>`), which survives identity re-seeding.
- **A4 changed**: no hard-coded default plan. `planHandle` is required in the POST body, because the build must run against other catalogs.
- **A6 superseded by live evidence**: with no collection method, the sandbox refused `CreateSubscription` with 422 "No payment method was on file for the $299.00 balance". The request now sets `CreateSubscription.PaymentCollectionMethod = MaxioAdvancedBilling.Models.Enums.CollectionMethod.Remittance` (source: `src/MaxioAdvancedBilling/Models/CreateSubscription.cs`, `Models/Enums/CollectionMethod.cs`: "Relationship Invoicing Architecture valid options are remittance, automatic, prepaid"). Maxio invoices the customer instead of charging a card. Verified live: state `active`.
- **Endpoint signature**: `MinimalApi.Endpoint`'s `IEndpoint` takes at most two inputs, so the user-scoped endpoints take `HttpContext` and resolve `UserManager`/`SubscriptionBillingService` from `RequestServices`.
- **Test runtime**: `Microsoft.AspNetCore.TestHost` 8.0.2 cannot write JSON responses on the .NET 10 runtime ("PipeWriter … UnflushedBytes"); this is the cause of the 12 pre-existing PublicApi test failures. On the ASP.NET Core 8.0 runtime all 89 tests pass.
