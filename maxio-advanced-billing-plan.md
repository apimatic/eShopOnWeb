# Maxio Advanced Billing integration plan: eShopOnWeb subscriptions (PublicApi)

Workflow: `maxio-advanced-billing:dotnet-integrate-maxio-advanced-billing`. SDK source and map (plugin-relative): `sdk/dotnet/` (`sdk-map.md`, `map/operations/*.md`, `src/MaxioAdvancedBilling/...`). All **source** cells are relative to that SDK root unless they say `repo:`.

Configuration keys (the only ones bound): `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional). No credential value appears in this file.

---

## 1. Scope & sequence

| # | Step | Maxio operations used |
| --- | --- | --- |
| 1 | Reference the plugin's SDK project from the project(s) that call Maxio (local `<ProjectReference>`; see §6). | none |
| 2 | Bind `Maxio:` options, fail fast on missing/blank values, register the SDK client once as a singleton (Basic auth, Production server group, optional `Maxio:BaseUrl` override). | none (construction) |
| 3 | Add the duplicate-claim / user-to-Maxio mapping row in the app's EF Core `CatalogContext` (primary key = the user id). | none |
| 4 | `GET /api/subscription-plans`: list the plans of the family named by `Maxio:ProductFamilyHandle`, walking pages, dropping archived products; return handle, name, description, price (cents), interval, interval unit. | `ProductFamilies.ListProductsForProductFamily` |
| 5 | `POST /api/subscriptions` (body: plan handle): read the site profile once (`Sites.ReadSite`, revision) for the invoice-style collection method → validate the handle against step 4's set → write the claim row → ensure the Maxio customer by reference (read, else create) → record customer id on the claim → create the subscription with a claim-generated subscription reference → record subscription id; return plan/price/state/next-billing-date. Unknown outcomes reconcile by reference. | `ProductFamilies.ListProductsForProductFamily`, `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`, `Subscriptions.CreateSubscription`, `Subscriptions.FindSubscription` |
| 6 | `GET /api/my-subscriptions`: settle any claim left in an unknown state, then list the caller's Maxio subscriptions (by the customer id stored on the claim row; fall back to `ReadCustomerByReference` when the row has none) and return plan/price/state/next-billing-date per subscription. | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions`, `Subscriptions.ReadSubscription` (optional, to refresh the stored subscription), `Subscriptions.FindSubscription` (settling) |
| 7 | Error boundary: map SDK exceptions to HTTP results; tests with the HttpClient stub seam (duplicate claim, provider 422, connection failure after create). | all of the above |

Out of scope: payment profiles, price-point management, components/metered usage (`api-call` is not enrolled), cancellation, webhooks, Ebb events. Price points are **not needed** for price display: `Product` carries `PriceInCents`, `Interval`, `IntervalUnit` (source: `src/MaxioAdvancedBilling/Models/Product.cs`).

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter, built with an object initializer whose property names are the record's own — never flat arguments. Then `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.
>
> ⚠ **Every SDK type is written fully-qualified with the namespace its own source path implies** (path `Models/` → `MaxioAdvancedBilling.Models`, `Models/Enums/` → `.Models.Enums`, `Models/AnyOf/` → `.Models.AnyOf`, `Errors/` → `.Errors`, `Requests/<Controller>/` → `.Requests.<Controller>`, `Core/Exceptions/` → `.Core.Exceptions`, `Core/ErrorResponse/` → `.Core.ErrorResponse`), taken from the path the map gives for THAT type, never from a neighbour.

All in-scope operations: Auth `options.BasicAuth`; server group `Production` (default); throw-only; no SDK pagination (no `Pageable`) — `page`/`per_page` are plain request members you drive yourself.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a caller sends to `POST /api/subscriptions` (→ `CreateSubscription.ProductHandle`) must be the `Handle` of a non-archived product that `ListProductsForProductFamily("handle:" + Maxio:ProductFamilyHandle)` returned — i.e. a plan this app offers, not merely any product on the site | `CreateSubscription` ← `ListProductsForProductFamily` | In the new subscribe service method that handles `POST /api/subscriptions`, **before the claim write and before `CreateSubscription`**: it calls the same plan-listing member that backs `GET /api/subscription-plans` and rejects (400) a handle not in that set. (`ReadProductByHandle` must NOT be used for this check — it proves existence on the site, not membership in the offered family.) |
| The `CustomerId` passed to `CreateSubscription` (and `ListCustomerSubscriptions`) must be the `Customer.Id` that `ReadCustomerByReference`/`CreateCustomer` returned **for this caller's reference** and that the app stored on the caller's claim row | `CreateSubscription`, `ListCustomerSubscriptions` ← `ReadCustomerByReference` / `CreateCustomer` | In the subscribe service (and the my-subscriptions query), the customer id is read only from the caller's own claim row (keyed by the authenticated user id) or from a fresh `ReadCustomerByReference` with the caller's reference — never from request input. |
| The `SubscriptionId` passed to `ReadSubscription` must be one `CreateSubscription`/`FindSubscription` returned and the app stored on the caller's claim row | `ReadSubscription` ← `CreateSubscription` / `FindSubscription` | In the my-subscriptions query member: subscription id comes only from the caller's claim row; no subscription id is accepted from the request. |

Hazard (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

Map-visible trust points: `ListProductsForProductFamilyError` declares its 404 body as a JSON string (`src/MaxioAdvancedBilling/Errors/ListProductsForProductFamilyError.cs`) — a misconfigured family handle may therefore surface as `ResponseDeserializationException` with status 404 instead of `TryGetString`; `ProductResponse.Product` and `CustomerResponse.Customer` are `required`, so a 2xx without them also surfaces as `ResponseDeserializationException`.

## 6. Assumptions & Blockers

**Blockers:** none. Every capability the task needs (list family plans by handle, customer lookup/create by reference, create subscription by product handle + customer id, list a customer's subscriptions, read/find a subscription) is on the map.

**Assumptions:**

1. **User id / Maxio reference** — PublicApi tokens carry only the user name (`ClaimTypes.Name`), no id claim (repo:`IdentityTokenClaimService.cs`). The claim-table key and the Maxio customer `reference` are derived from the authenticated identity — either the user name directly or the `IdentityUser.Id` looked up by name. `YOUR CALL — not in the map`. Either way the reference must be stable per user and app-namespaced (e.g. prefixed) so other apps on the same Maxio site cannot collide.
2. **Required customer fields** — `CreateCustomer` requires `FirstName`, `LastName`, `Email`; `ApplicationUser` has no names. Email = the user's email (= user name for seeded users); names derived from the email local part / a fixed placeholder. `YOUR CALL — not in the map`.
3. **Plan selection** — `POST /api/subscriptions` takes the plan handle in the body; the task's "default subscribe target `eshop-pro`" is not hard-coded (the build must run against another catalog) — a missing handle is a 400, or defaults to the first listed plan. `YOUR CALL — not in the map`.
4. **One subscription per user** — the claim is keyed by user id alone, so a user holds at most one eShop subscription; a second `POST` returns the existing one (or 409). Plan changes are out of scope.
5. **`MAXIO_ENVIRONMENT`** — not bound: the task fixes the four `Maxio:` keys, and the SDK's only environments are `Us`/`Eu` (no sandbox member). `ServerEnvironment.Us` is used; the sandbox is selected by the site (`Maxio:Subdomain`) and API key. If the sandbox site were EU-hosted, `Maxio:BaseUrl` is the override.
6. **Next billing date** shown = `Subscription.CurrentPeriodEndsAt` (next scheduled charge), with `NextAssessmentAt` also returned; they diverge only after a failed renewal (Subscription.cs docs).
7. **Currency** — `Product` has no currency field; plan prices are returned in cents with interval/unit; currency is shown only from `Subscription.Currency` after subscribe. `YOUR CALL — not in the map` whether the plans DTO labels a currency.
8. **UNVERIFIED (defensive directives recorded above):** `ReadCustomerByReference` not-found status (treat 404 only); duplicate-customer-reference status (expect 422; reconcile by reference); subscription-reference uniqueness at Maxio (claim row is the guard); server-side cap on `ListCustomerSubscriptions`; provider request-id header name.
9. **Portability** — the SDK is referenced as a local `<ProjectReference>` into the plugin install directory; the solution builds only where the plugin is installed at that path (hand-over note).

**Decisions taken at implementation (the `YOUR CALL` rows):**

- Buyer id = the account's canonical `UserName` (looked up from the token's name claim), matching the codebase's `Basket.BuyerId`/`Order.BuyerId` convention. Maxio customer reference = `eshop-user-` + first 16 bytes of SHA-256(upper-cased buyer id) in hex: stable across restarts and free of personal data (it travels in the lookup URL and logs).
- `POST /api/subscriptions` body: `planHandle` (required; 400 when missing or not offered), optional `firstName`/`lastName` (default: email local part / `Customer`). No default plan is hard-coded.
- One live subscription per shopper. Same plan again → 200 `AlreadySubscribed`; another plan → 409 `SubscribedToDifferentPlan`; a subscription that ended (canceled/expired/failed_to_create) re-opens the enrollment for a new subscribe.
- Before creating, the customer's Maxio subscriptions are checked and a live one on an offered plan is adopted, so losing the local enrollment (in-memory restart) never produces a second subscription.
- `Maxio:Environment` (optional, `US` default / `EU`) is bound from `MAXIO_ENVIRONMENT` via user-secrets; it selects `ServerEnvironment` and which `Server.Production.{Us|Eu}` members receive the site/base URL.
- HTTP mapping of `BillingProviderException`: Rejected → 422 (with Maxio's `errors`), Timeout → 504, Unavailable (5xx, 401/403, 404 on our own configuration, 429, unreadable bodies, connection failures) → 502. Messages are caller-safe.
