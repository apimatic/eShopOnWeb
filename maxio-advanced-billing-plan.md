### Business semantics fixed by the sheet (each with its source)

- **paid** (GET subscription): `paid = true` only when ALL hold: `Subscription.BalanceInCents` is 0 (null treated as unknown => not trusted, see UNVERIFIED), `AccountBalances.OpenInvoices.BalanceInCents` is 0 (covers Relationship Invoicing, where invoices rather than statements hold what is owed), and `State` is not past_due / unpaid / soft_failure / suspended. A negative balance (credit) counts as owing nothing. Source: Models/Subscription.cs (`balance_in_cents` doc), Models/AccountBalances.cs; subscription-status.retrySubscription.1 (past due = balance due). Rule on null booleans/values: every-request.11. Label: `YOUR CALL — not in the map` for the exact predicate; `UNVERIFIED` that `balance_in_cents` is populated on this site.
- **cancel** = immediate cancel (no body) — subscription-status.cancelSubscription.1; "already canceled" is 422 (cancelSubscription.6). Precondition in app: state must not already be canceled/expired => 409 with reason.
- **restart** = `ReactivateSubscription`; Maxio accepts only canceled/unpaid/trial_ended (reactivateSubscription.1). Precondition: state == canceled (and cancelled by this shopper — see Assumptions) else 409. Reactivation may charge; no payment profile on file + balance => 422 "No payment method was on file" (reactivateSubscription.12): surface as 4xx with that reason. Send `resume` per YOUR CALL.
- **pause**: only active (or trialing — UNVERIFIED) ; Maxio refuses within 24h of next_billing_at (pauseSubscription.1) and non-eligible (pauseSubscription.2): translate 422 to 409 with Maxio's message. **resume**: only `on_hold` (resumeSubscription.1); resuming after the renewal date charges immediately and resets the billing date (resumeSubscription.3).
- **switch**: migration accepts only active/trialing (migrateSubscriptionProduct.1). For on_hold/paused/canceled the app uses `UpdateSubscription` with `ProductHandle` (product change, no proration; new amount from next period — updateSubscription.3) and must verify the response `Product.Handle` == target (`switching puts them on the new plan`). `migrate` default resets the period and charges full price (migrateSubscriptionProduct.8): `PreservePeriod` is `YOUR CALL — not in the map`. Cross-family switch drops components/coupons (migrateSubscriptionProduct.5-6): record in response? `YOUR CALL`. Check after the call: Read the subscription again and compare `Product.Handle`; mismatch => report failure, not success. Canceled-subscription switch via Update is `UNVERIFIED` (the map documents no state rule for it) — verify against the sandbox first and, if Maxio refuses, that is a Blocker to raise (do not silently reactivate).
- **next billing date**: `UpdateSubscription` with `NextBillingAt`. Response has no next_billing_at — verify via re-read `CurrentPeriodEndsAt` (updateSubscription.12) and compare date. New date becomes the anchor of later dates (updateSubscription.11); impossible dates roll over (updateSubscription.10 => validate the YYYY-MM-DD with `DateOnly.TryParseExact`); `billing_date_change` webhook is only for explicit edits (.13). A subscription that is on_hold/canceled/expired does not renew (pauseSubscription.3/pause rule background renewal), so "billed on that date" cannot hold: refuse 409 unless state in {active, trialing, past_due?}. Date must be in the future (>= tomorrow site-local). Timestamp: `DateTimeOffset` of 12:00 at the UTC offset of the subscription's own returned timestamps (`NextAssessmentAt`/`CurrentPeriodEndsAt` carry the site-tz offset — every-request.12/.14), never `DateTimeOffset` built in server-local tz. Label: `YOUR CALL` for the eligible-state list; `UNVERIFIED` whether Maxio refuses past/near dates.
- **usage for a day D**: components = `ListSubscriptionComponents` with `Kind == MeteredComponent` and `ArchivedAt == null`. Per component `ListUsages` with `SinceDate` = D 00:00 and `UntilDate` = (D+1) 00:00 at the site-tz offset (listUsages.2: until_date is midnight-exclusive-of-later-that-day, so ask for the day after), `PerPage = 200`, `Page` from 1 until a page is empty or shorter than 200 (every-request.23/.24), then filter `Usage.CreatedAt` to `D 00:00 <= t < D+1 00:00` (site-tz offset) client-side because bounds are inclusive. Sum `Quantity` per component (union: int or string — parse string with `decimal`, `TryGetUnknown` => report unparseable). Page cap `MaxPages = 25` per component; on cap hit the response carries `truncated: true` and the component name(s) (PAGED READS). Metered only: usages for a quantity-based component is an error (listUsages.1). Offset source = the subscription's returned timestamps (no site-tz field exists on `Site`).
- **subscribe without card**: product created with `RequireCreditCard = false`, and `CreateSubscription` sends `PaymentCollectionMethod` = `Remittance` when `Site.RelationshipInvoicingEnabled` else `Invoice` (valid sets: createSubscription.41/.44). Paid product + no payment method is otherwise refused (createSubscription.7). Initial charge is billed immediately when `next_billing_at` omitted (createSubscription.10): on a remittance/invoice sub that yields an open invoice => `paid:false` until paid. Label: `YOUR CALL` for method mapping; `UNVERIFIED` that the sandbox site accepts that method without a payment profile (Blocker candidate §6).

- **Preconditions:** pause needs active/trialing; resume needs on_hold/paused; cancel refuses canceled/expired; restart needs canceled; next billing date needs active/trialing/past_due/soft_failure, a real `YYYY-MM-DD`, at least 24h ahead, sent as 12:00 at the subscription's own offset and re-read to confirm.
