# Maxio Advanced Billing integration plan — eShopOnWeb subscriptions (PublicApi)

SDK root (plugin-relative): `sdk/dotnet/` — every `Source` below is relative to it. Map index: `sdk-map.md`.
Skill: `dotnet-integrate-maxio-advanced-billing`. The SDK is project-referenced from the plugin (`sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`), not NuGet.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the SDK project from the project(s) that call Maxio; bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional) with startup validation; register the client once in DI | none (client construction — §2 *Client construction*) |
| 2 | One application service fronting the SDK (owns the call budget, the error translation, the reconciliation) — placement/layering YOUR CALL | all below |
| 3 | `GET /api/subscription-plans` — list plans of the family `handle:{Maxio:ProductFamilyHandle}`, page-walked, archived excluded; display name/handle/price/interval | `ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure customer (idempotent): claim → look up by reference → create if absent → record | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5 | `POST /api/subscriptions` — validate plan handle against step 3's set, ensure customer (step 4), claim → create subscription with `product_handle` + `customer_id` + deterministic `reference` → record; reconcile on unknown outcome | `ProductFamilies.ListProductsForProductFamily`, `Subscriptions.CreateSubscription`, `Subscriptions.FindSubscription`, `Customers.ListCustomerSubscriptions` |
| 6 | `GET /api/my-subscriptions` — caller's customer by reference → that customer's subscriptions; plan/price/state/next billing date | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` (optionally `Subscriptions.ReadSubscription` for a single refresh) |
| 7 | Tests: HttpClient-stub tests for each SDK path incl. connection failure on both writes; endpoint tests | — |

Routes are the task's: `GET /api/subscription-plans`, `POST /api/subscriptions`, `GET /api/my-subscriptions`, JWT-authenticated, following the exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (`IEndpoint<…>` + `AddRoute`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.WithTags(...)`). Duplicate-to-409 convention: `DuplicateException` → `src/PublicApi/Middleware/ExceptionMiddleware.cs`. App store: `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`, entity configs applied from assembly in `src/Infrastructure/Data/Config/`).

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a caller sends to `POST /api/subscriptions` (→ `CreateSubscription.ProductHandle`) must be the `Product.Handle` of a non-archived product returned for family `handle:{Maxio:ProductFamilyHandle}` | `Subscriptions.CreateSubscription` ← `ProductFamilies.ListProductsForProductFamily` | In the subscribe service method, before the claim and before `CreateSubscription`: it reads the family's product list (same page-walk as `GET /api/subscription-plans`) and rejects a handle not in it (400). `Products.ReadProductByHandle` is NOT an acceptable substitute — it proves the product exists on the site, not that it is in this family |
| The `CustomerId` passed to `CreateSubscription` and `ListCustomerSubscriptions` must be the `Customer.Id` of the caller's own customer — the one `ReadCustomerByReference`/`CreateCustomer` returned for the reference derived from the caller's token identity (never a client-supplied id) | `Subscriptions.CreateSubscription`, `Customers.ListCustomerSubscriptions` ← `Customers.ReadCustomerByReference` / `Customers.CreateCustomer` | In the ensure-customer step of the subscribe service and at the start of the my-subscriptions handler: the id is taken only from that call's result (or the app's recorded mapping written from it); `GET /api/my-subscriptions` and `POST /api/subscriptions` accept no customer id input |

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind the `Maxio:` section to an options class; validate at startup (`ValidateOnStart`) that `Maxio:ApiKey` is non-blank, `Maxio:ProductFamilyHandle` is non-blank, and `Maxio:Subdomain` is non-blank unless `Maxio:BaseUrl` is set (when set, it must be an absolute http(s) URI). The Basic password is the constant `"x"` (map), so the API key is the only secret part; a blank key or subdomain refuses to start the host |
| 2 | Secret sourcing & rotation | `Maxio:ApiKey` comes only from user-secrets in Development (PublicApi already has a `UserSecretsId`) / the host's secret store in other environments; never in `appsettings*.json` or the repo. Options are built once inside the `AddMaxioAdvancedBillingClient` configure callback and captured by the singleton client — a rotated key takes effect only on process restart; restart-on-rotate is accepted (no live rotation required by the task) |
| 3 | Total timeout budget | Per attempt: `options.Retry = RetryOptions.Default() with { Timeout = 10s }`; `HttpClient.Timeout = 15s` backstop. Whole inbound request: one linked `CancellationTokenSource` (linked to `HttpContext.RequestAborted`, `CancelAfter` 30s from `Maxio:CallBudgetSeconds`; `Maxio:AttemptTimeoutSeconds` = 10 feeds `Retry.Timeout`, `HttpClient.Timeout` = attempt + 5s; re-reads that settle an unknown write get their own `Maxio:ReconcileBudgetSeconds` = 10 budget) created in the single Maxio-fronting service and passed to every SDK call the handler makes (plans page walk + customer lookup/create + create subscription + reconciliation). Caller-visible ceiling ≈ 30s |
| 4 | Write-retry ownership | `CreateCustomer` and `CreateSubscription` are POST → never resent by the SDK under the default `HttpMethodsToRetry` (GET/HEAD/PUT/OPTIONS). GET reads (`ListProductsForProductFamily`, `ReadCustomerByReference`, `ListCustomerSubscriptions`, `FindSubscription`, `ReadSubscription`) may be retried by the SDK — safe |

The provider error models in scope (`ErrorListResponse1`, `CustomerErrorResponse1`, `RawError`) carry no correlation/request id field — none reaches the logs from Maxio; log the `errors` messages instead |

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. `MAXIO_ENVIRONMENT` has no binding key among the four mandated `Maxio:` keys and no SDK counterpart for "sandbox". Resolved: an optional `Maxio:Environment` (`US` default / `EU`) selects `ServerEnvironment`; Subdomain/BaseUrl are applied to the selected environment's server options.
2. The env vars (`MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_DEFAULT_PRODUCT_FAMILY`) do not map onto `Maxio:ApiKey`/`Maxio:Subdomain`/`Maxio:ProductFamilyHandle` by themselves (.NET maps `Maxio__ApiKey`); the plan assumes their values are copied into PublicApi user-secrets under those keys (`dotnet user-secrets set`), per "user-secrets only".
3. The JWT carries only `ClaimTypes.Name` (userName) and roles; the customer reference and the `CreateCustomer` required `first_name`/`last_name`/`email` are derived from that (userName is the email for seeded users) — derivation YOUR CALL. `last_name`/`first_name` placeholders may be needed because Identity stores no names.
4. Customer reference uniqueness at Maxio is documented (remarks); subscription `reference` uniqueness is not — duplicate prevention for subscriptions rests on the app-side claim only.
5. `UseOnlyInMemoryDatabase=true`: claims survive only within a process run. After a restart, a duplicate customer is still refused by Maxio's reference uniqueness and reconciled by `ReadCustomerByReference`; a duplicate subscription is not provider-refused, so the subscribe path should check `FindSubscription` by the deterministic reference when no local row exists (a read, not a guard — accepted only for the cross-restart gap; the in-run guard is the PK claim). With SQL Server (`UseOnlyInMemoryDatabase=false`) the claim is durable and an EF migration is needed for the new entities.
6. `ReadCustomerByReference` "not found" is assumed to be HTTP 404 (Case B; not stated in the source) — confirmed by live sandbox traffic; only 404 is treated as absent. `FindSubscription` not-found = 404 also confirmed live.
7. The plans need no payment method (task), so `CreateSubscription` is sent without payment fields. **Corrected by live traffic:** with the default (automatic) collection Maxio refused the $299 signup with 422 "No payment method was on file". Plans whose `RequireCreditCard` is not true are therefore subscribed with invoice-style collection (`remittance` on Relationship Invoicing sites, `invoice` on legacy Statements sites, read once per process via `Sites.ReadSite`). A plan that requires a card keeps automatic collection and gets Maxio's 422 (claim released).
8. Plan price display uses `Product.PriceInCents` + `Interval`/`IntervalUnit` from the list call (no price-point calls needed); the subscription's price uses `Subscription.ProductPriceInCents`. Currency is read from `Subscription.Currency`; the product list exposes no currency field — plans are assumed to be in the site's default currency (USD per the task).
9. The SDK is referenced as a `ProjectReference` into this plugin's install path — builds only where the plugin is installed at that path (teammates/CI must re-point it).
