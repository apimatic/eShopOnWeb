- `SubscriptionResponse.Subscription` is **not** `required` (nullable), while `CustomerResponse.Customer` and `ProductResponse.Product` are `required`. - `ListCustomerSubscriptions` in `src/MaxioAdvancedBilling/Api/Customers.cs` does **not** forward `requestOptions` to `Execute` (it passes only the auth list and `cancellationToken`). Per-call `requestOptions` (log level, hooks) are silently ignored on that operation. Rely on client-level options and the `cancellationToken`.
- Subscription `reference` uniqueness at Maxio is not stated anywhere in the source. **UNVERIFIED.** Directive: always generate a fresh `eshop-sub-{Guid}` per claim, so uniqueness is never relied on for correctness. If `FindSubscription` returns a subscription whose `Reference` differs from the one sent, treat it as not found.

## 3. Trap notes

- Step 1: building the options inside a singleton factory fixes when the API key is read, and a missing key fails late as a 401 instead of at boot. MUST load maxio-advanced-billing:dotnet-client-initialization
- Step 1: the Basic credential has two parts, and the source of the password differs from the API key. Getting either wrong costs a 401 that looks like a bad key. MUST load maxio-advanced-billing:dotnet-authentication
- Step 1: the base-URL override, site template variable and environment interact. A wrong pick sends sandbox traffic to the wrong host. MUST load maxio-advanced-billing:dotnet-configuration-resilience
- Step 1: what `Retry.Timeout` actually bounds, versus the whole call including retries and backoff, decides whether the caller's request can hang past the endpoint budget. MUST load maxio-advanced-billing:dotnet-configuration-resilience
- Step 1: logging configuration can echo customer PII (email and names in the CreateCustomer body) into logs, and an env var can switch that on without a deploy. MUST load maxio-advanced-billing:dotnet-configuration-resilience
- Step 3: the page walk has a cap, and nothing in the SDK signals that more pages exist. A silent cut makes a valid plan "not offered". MUST load maxio-advanced-billing:dotnet-configuration-resilience
- Steps 3–6: each operation takes one request record plus `requestOptions` and `cancellationToken`. Passing the wrong token or forgetting the `Body` wrapper compiles but misbehaves. MUST load maxio-advanced-billing:dotnet-calling-endpoints
- Steps 3–6: the nullable response members, the `SubscriptionState` open enum and the `Errors1` AnyOf union each have read rules that a plain property access gets wrong. MUST load maxio-advanced-billing:dotnet-models
- Step 4: telling "customer not found" apart from other failures on a Case B `RawError` decides whether a duplicate customer is created. MUST load maxio-advanced-billing:dotnet-error-handling
- Step 4/5: a catch ladder that handles only the typed `ApiException<TError>` lets other SDK failures escape into `ExceptionMiddleware`'s 500 branch with their message. MUST load maxio-advanced-billing:dotnet-error-handling
- Step 5: whether a failed `CreateSubscription` POST can be resent by the SDK, and how a connection drop or timeout after send surfaces, decides between a duplicate subscription and a lost one. MUST load maxio-advanced-billing:dotnet-configuration-resilience
- Step 5: which exception types mean "the provider may have acted" and which mean "it refused". Reconcile versus release-the-claim hinges on it. MUST load maxio-advanced-billing:dotnet-error-handling
- Step 7: faking connection failures, 422 bodies and timeouts without the network, and asserting the outgoing body (`reference`, `product_handle`, `customer_id`). MUST load maxio-advanced-billing:dotnet-testing

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind the `Maxio` section to a `MaxioSettings` options class with `ValidateOnStart()`. Validation requires a non-blank `ApiKey`, a non-blank `ProductFamilyHandle`, and **either** a non-blank `Subdomain` **or** a non-blank `BaseUrl`, which must parse as an absolute http(s) URI. The Basic password is the constant `x` from the map, so there is nothing to bind or check for it. The host refuses to start on a missing or blank part. Tests: `PublicApiIntegrationTests` supplies non-secret placeholder `Maxio:*` values through the factory's in-memory configuration and a stub base URL, so the existing tests keep booting. (YOUR CALL, not in the map) |
| 2 | Secret sourcing & rotation | `Maxio:*` values live in .NET user-secrets of `src/PublicApi` (existing `UserSecretsId` in `PublicApi.csproj`) for development and in host configuration for deployments. Nothing goes in `appsettings*.json`. The DI factory builds the options **once** and the singleton client captures them, so a rotated key needs a process restart. Rotation without restart is not required; accepted. |
| 3 | Total timeout budget | **25 s** per inbound request (implemented as `MaxioSubscriptionBillingService.RequestBudget`; per attempt `Retry.Timeout` = 8 s, `MaxRetries` = 2, `HttpClient.Timeout` = 10 s backstop; reconcile re-reads get their own 10 s `ReconcileBudget`) for each Maxio-backed endpoint. The relation between the knobs is per the configuration-resilience skill, checked at implementation. On budget expiry for a write, go to the Unknown-outcome path; for a read, return 503. |
| 4 | Write-retry ownership | The writes in scope are `CreateCustomer` (POST) and `CreateSubscription` (POST). POST is **not** in `RetryOptions.Default().HttpMethodsToRetry`, so the SDK never resends them; keep it that way (never add POST). The app also never blindly retries them. Reads (GET) keep SDK retries. |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: the real key is the body field `customer.reference` (= eShop user id; remarks: only one customer per reference value), so a resend is refused by Maxio with 422. Reconciliation uses the app-generated `subscription.reference` through `FindSubscription`, plus the adopt-check via `ListCustomerSubscriptions`. The auto-generated `Idempotency-Key` header is a fresh GUID per call and is **not** a key. |
| 6 | Observability | Information: subscribe started/completed with userId, plan handle, Maxio customer id, subscription id and state. Settle rules (applied in each write's `catch`, before returning): the triggers are `SdkConnectionException`, `SdkTimeoutException`, the budget `OperationCanceledException`, 5xx `ApiException<…>` / `RawError`, `ResponseDeserializationException` on a 2xx, and a 2xx with a null `Subscription`/`Customer.Id`. On these, re-read with a fresh short token (not the expired budget token). Found → record it on the claim as `Completed` and return success. Definitively not found (404 via `TryGetNoContent` / `RawError.StatusCode == 404`) → release the claim and return 503 "try again". The re-read itself fails → leave the claim `Pending` with `OutcomeUnknown = true` and return 202 "subscription pending confirmation". The next subscribe or `GET /api/my-subscriptions` for that user re-runs the same reconcile helper on any `OutcomeUnknown` claim before anything else (YOUR CALL, not in the map).

## 6. Assumptions & Blockers

**Assumptions**
- A1. Config keys: the env vars named in the task are mapped into the bound keys. Each value is set once into PublicApi user-secrets (`dotnet user-secrets set`) under the binding key: `Maxio:ApiKey` (API key), `Maxio:Subdomain` (site, sandbox `<sandbox site from MAXIO_SITE_SUBDOMAIN>`) and `Maxio:ProductFamilyHandle` (`<family from MAXIO_DEFAULT_PRODUCT_FAMILY>`). `Maxio:BaseUrl` is left unset in dev. The raw `MAXIO_*` names do not bind to `Maxio:*` keys by themselves (.NET binds `Maxio__ApiKey`), so the app reads only the `Maxio:` section. User-secrets load only when `ASPNETCORE_ENVIRONMENT=Development`.
- A2. The task's environment selector ("target the sandbox") maps to no SDK setting: the SDK has only `Us`/`Eu` and no sandbox environment. The sandbox is selected purely by the site subdomain; `ServerEnvironment.Us` is assumed (US-hosted site).
- A3. Customer identity (**revised at implementation**): Maxio `customer.reference` = `"eshop-" + lower-cased NormalizedUserName` (`BillingUser.CustomerReference`), because the in-memory identity store regenerates `ApplicationUser.Id` on every restart, which would create a duplicate Maxio customer per run. Local claim rows are still keyed by `ApplicationUser.Id`. `email` = `ApplicationUser.Email` (falls back to `UserName`). Because `ApplicationUser` has no names and `first_name`/`last_name` are `required`, the plan uses `FirstName` = email local part and `LastName` = `"eShop"` placeholder (YOUR CALL).
- A4. "Idempotent subscribe" means one subscription per (user, plan). Subscribing to the other plan creates a second subscription; plan change/upgrade is out of scope.
- A5. `POST /api/subscriptions` body: `{ "planHandle": string? }`. **Revised**: the default comes from the optional `Maxio:DefaultPlanHandle` setting (user-secrets: `eshop-pro`) so no catalog value is hard-coded; with no default configured and no `planHandle`, the call is a 400. Responses return plan handle, name, price (`product_price_in_cents`/100, currency), state wire value and next billing date (`current_period_ends_at`).
- A6. The metered component `api-call` is not attached at subscribe and no usage is recorded. It is out of the hero flow.
- A7. `GET /api/my-subscriptions` treats Maxio as the system of record (live `ListCustomerSubscriptions`). The local claim table is only a dedupe/claim store. The in-memory store is wiped on restart; the customer lookup by reference and the adopt-check in step 5 keep restarts from creating duplicates at Maxio.
- A8. Plans with `RequireCreditCard == true` are not offered, because there is no card capture in scope. Per the task, both seeded plans have it false.
- A9. The not-found status for `ReadCustomerByReference` (Case B) is UNVERIFIED as 404. Only 404 is treated as "absent"; any other status aborts the flow and releases nothing that was confirmed.

**Blockers**
- None. The map covers every capability needed (list plans by family handle, customer by reference, create customer, create subscription by product handle + customer id, find subscription by reference, list customer subscriptions).
