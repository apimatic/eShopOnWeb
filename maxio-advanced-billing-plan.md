# Maxio Advanced Billing integration plan — eShopOnWeb subscriptions

SDK root (plugin-relative): `sdk/dotnet/` · project to reference: `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` (netstandard2.0, built with C# 14; reference it from the project that calls Maxio, never copy the source). Map: `sdk/dotnet/sdk-map.md` + `sdk/dotnet/map/operations/`. All `source` cells below are relative to `sdk/dotnet/`.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the SDK project; bind `Maxio:` settings (`ApiKey`, `Subdomain`, `ProductFamilyHandle`, `BaseUrl`); validate at startup; DI-register the client in `src/PublicApi/Program.cs` | none (client construction) |
| 2 | Plan catalogue reader: list the configured family's products by handle, walk pages, drop archived | `ProductFamilies.ListProductsForProductFamily` |
| 3 | `GET /api/subscription-plans` endpoint (JWT) returning handle/name/price/interval + truncated flag | step 2 |
| 4 | Customer resolver ("ensure customer"): claim row → look up by reference → create if absent → record Maxio customer id | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5 | Subscribe service: validate plan handle against step 2's set → claim row → check existing live subscription → create → record subscription id | step 2, step 4, `Customers.ListCustomerSubscriptions`, `Subscriptions.CreateSubscription`, `Subscriptions.FindSubscription` (unknown outcome) |
| 6 | `POST /api/subscriptions` endpoint (JWT) returning plan/price/state/next-billing-date | step 5 |
| 7 | `GET /api/my-subscriptions` endpoint (JWT): resolve this user's customer (lookup only, never create) → list its subscriptions | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` |
| 8 | Tests (unit with stubbed HttpClient + PublicApiIntegrationTests), then live sandbox verification | all of the above |

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a caller POSTs to `/api/subscriptions` must be the `Product.Handle` of a non-archived product returned by listing the configured family (`handle:` + `Maxio:ProductFamilyHandle`) | `Subscriptions.CreateSubscription` (`ProductHandle`) ← `ProductFamilies.ListProductsForProductFamily` | In the subscribe service, before the claim row and before `CreateSubscription`: call the step-2 catalogue reader and reject (400) a handle not in its set; a truncated catalogue that lacks the handle is also a reject (503), never a pass |
| The `CustomerId` sent to `CreateSubscription` / `ListCustomerSubscriptions` must be the id this application resolved for the calling user (from `ReadCustomerByReference` or `CreateCustomer` with this user's reference) — never a client-supplied id | `Subscriptions.CreateSubscription`, `Customers.ListCustomerSubscriptions` ← `Customers.ReadCustomerByReference` / `Customers.CreateCustomer` | In the customer resolver: the request DTOs carry no customer id; the services take the id only from the resolver's result for the JWT user |
| Subscriptions shown/returned as "this app's plans" must belong to the configured family | `Customers.ListCustomerSubscriptions` ← `ProductFamilies.ListProductsForProductFamily` | In the my-subscriptions handler and the "existing live subscription" check: keep only entries whose `Product.ProductFamily.Handle` equals `Maxio:ProductFamilyHandle`, or (if that is null) whose `Product.Handle` is in the step-2 set |

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind `Maxio:` to an options class in PublicApi with `ValidateOnStart`: `ApiKey` non-blank; `ProductFamilyHandle` non-blank; `Subdomain` non-blank **unless** `BaseUrl` is set; `BaseUrl`, when set, an absolute https URI. The BasicAuth password is the constant `x` (map), so the only secret part to check is the key. Host refuses to start on failure; the client's `configure` delegate also throws if reached with a blank key (it runs lazily, so startup validation is the real gate). |
| 2 | Secret sourcing & rotation | Dev/sandbox: `dotnet user-secrets` on `src/PublicApi` (existing `UserSecretsId`) under exactly `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle` (and `Maxio:BaseUrl` only if overriding), set from the `MAXIO_*` env vars without echoing values; deployed: the same keys from environment (`Maxio__ApiKey` …) or a vault provider. Options are built once into the singleton client → **rotation requires a process restart**; accepted (no hot rotation requirement in the task). |
| 3 | Total timeout budget | Each Maxio call runs under a linked `CancellationTokenSource` with an **8 s** total budget covering every attempt; each endpoint request is bounded at **45 s** overall by a request-level token the per-call ones link to (subscribe = up to list pages + lookup + create customer + list subscriptions + create + re-read), whichever expires first. A budget expiring on a POST is an unknown outcome (§UNKNOWN OUTCOMES), not a failure. ## 6. Assumptions & Blockers

**Blockers:** none. Every capability in scope is in the map: list products by family handle (`ListProductsForProductFamily` with `handle:` prefix), customer lookup by reference (`ReadCustomerByReference`), create customer, create subscription by product handle, list a customer's subscriptions (`ListCustomerSubscriptions`), find a subscription by reference (`FindSubscription`).

**Assumptions:**

1. **Customer reference = derived from the JWT user name, not the Identity user id.** The JWT carries only `ClaimTypes.Name`; with `UseOnlyInMemoryDatabase=true` the Identity store re-seeds users with new GUID ids on every restart, so an id-based reference would create a new Maxio customer per run. Reference = a fixed prefix + the normalized user name (e.g. `eshop:demouser@microsoft.com`). YOUR CALL — not in the map; trade-off: a user-name change orphans the Maxio customer.
2. **Customer names:** `CreateCustomer` requires `FirstName`, `LastName`, `Email`; eShop users have only user name/email. Email = the Identity user's `Email` (looked up via `UserManager` by name); first/last name derived from the email local part with a fixed fallback last name. YOUR CALL — not in the map.
3. **One live subscription per user** (any plan in the family): a second `POST /api/subscriptions` returns the existing subscription if it is for the same plan, 409 otherwise. Plan changes/cancellation are out of scope.
4. **After a restart** the in-memory claim tables are empty; idempotency then rests on (a) Maxio's one-customer-per-reference rule + `ReadCustomerByReference` and (b) the subscribe service checking `ListCustomerSubscriptions` for a live subscription in the family before creating. That check runs after the claim insert, so it does not replace the claim.
5. **`MAXIO_ENVIRONMENT`** is not one of the four mandated binding keys and the SDK has no sandbox environment member (only `US`/`EU`); the sandbox is selected by `Maxio:Subdomain`. The client uses `ServerEnvironment.Us`. Binding an optional region key is YOUR CALL — not in the map.
6. **Env-var → key mapping:** `MAXIO_API_KEY` etc. do not bind to `Maxio:ApiKey` by themselves (.NET maps `Maxio__ApiKey`). The values go into user-secrets under the `Maxio:` keys (per the task's secrets rule); user-secrets load only when `ASPNETCORE_ENVIRONMENT=Development` (the PublicApi launch profile sets it).
7. **Next billing date** shown = `NextAssessmentAt`, falling back to `CurrentPeriodEndsAt`; price shown = `Subscription.ProductPriceInCents` (falling back to `Product.PriceInCents`), formatted from cents with `Subscription.Currency` when present.
8. **Persistence placement:** the claim tables go in `CatalogContext` (where the app keeps orders). The SQL Server path needs an EF migration for them; the in-memory path ignores migrations.
9. **Existing integration tests** (`tests/PublicApiIntegrationTests`) boot `Program`; Maxio startup validation requires placeholder, non-secret `Maxio:` values in the test configuration (`appsettings.test.json` is already loaded by `Program`) and no live Maxio calls from those tests.
10. Payment collection method is left unset (site default); the seeded plans require no payment method, so `CreateSubscription` is expected to succeed without payment attributes. If Maxio still demands one, that is a 422 surfaced to the caller, not something to work around.
