## 1. Scope & sequence

1. **Config + client** — bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional) to an options class; register ONE `MaxioAdvancedBilling.MaxioAdvancedBillingClient` singleton (project reference to the SDK csproj, only from the project that hosts the client — Infrastructure). No op.
2. **Claim store** — two EF entities in `CatalogContext` (+ configurations, + SQL Server migration): `MaxioCustomerLink` (PK `UserName`) and `MaxioSubscriptionLink` (composite PK `UserName`+`PlanHandle`). No op.
3. **List plans** (`GET /api/subscription-plans`) — `client.ProductFamilies.ListProductsForProductFamily` with `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`, paged manually (page/per_page).
4. **Subscribe** (`POST /api/subscriptions`) — order: validate plan handle against step-3 list -> claim subscription link -> ensure customer (claim customer link -> `client.Customers.CreateCustomer`, reconcile with `client.Customers.ReadCustomerByReference`) -> `client.Subscriptions.CreateSubscription` -> record ids on claim -> return plan/price/state/next billing date from the `SubscriptionResponse`. Reconcile unknown outcomes with `client.Subscriptions.FindSubscription`.
5. **My subscriptions** (`GET /api/my-subscriptions`) — customer link for the token's user -> `client.Customers.ListCustomerSubscriptions` -> keep subscriptions whose `Product.ProductFamily.Handle` equals the configured handle.
6. **Error mapping** — new branches in `ExceptionMiddleware` (400 invalid plan, 404 none, 409 duplicate, 502/504 provider unavailable) without leaking provider messages.
7. **Tests** — unit (service with stubbed `HttpClient`), PublicApi integration (in-memory DB, stubbed Maxio base address via `Maxio:BaseUrl`).

## 2. CONTRACT SHEET

> Signatures are generated code, verbatim: each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer whose property names are the record's own — never flat arguments.
>
> Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits.

All operations also take `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`. Settle in the failing write's own `catch` for `SdkConnectionException`/`SdkTimeoutException`/`ResponseDeserializationException` (from `MaxioAdvancedBilling.Core.Exceptions`): re-read by reference; found -> record the id on the claim and continue as success; 404 -> release the claim and return 502/504; re-read itself failing -> leave the claim row with null id (state "unknown", second caller gets 409) and return 504/502.

## 6. Assumptions & Blockers

**Blockers: none.**

**Assumptions (decisions to settle at implementation, marked per §7):**

1. **Identity** — the JWT carries only `ClaimTypes.Name` (the user name, an email in this app) and roles. Identity = `ClaimTypes.Name`; absent -> 401. The "userId" in the claim store is that user name (it is the stable identifier tokens are minted from, see `IdentityTokenClaimService`). Source: repo code read. If the token should gain a `NameIdentifier`, that touches `IdentityTokenClaimService` — DECIDED: identity is `ClaimTypes.Name`, normalized to upper-case invariant as the claim key (`MaxioSubscriptionService.NormalizeUser`); token unchanged.
2. **Customer first/last name and email** — `CreateCustomer` requires `FirstName`, `LastName`, `Email` and the token supplies none of them. Plan: `Email` = the user name when it contains `@`, `FirstName` = local part of the email, `LastName` = the same local part or the constant `"Customer"` (Maxio requires non-blank). Alternative is `UserManager<ApplicationUser>` lookup of the account email (`AppIdentityDbContext` is in the same Infrastructure layer). DECIDED in `MaxioSubscriptionService.ResolveIdentityAsync`: `UserManager` email, falling back to the user name; first name = local part, last name = `Customer`.
3. **Claim granularity** — one claim per (user, plan): a double-click on the same plan never produces two customers or subscriptions; subscribing the same user to a second distinct plan is allowed (one shared Maxio customer). A user who cancels and wants to resubscribe the same plan is out of scope (no cancel endpoint in the request). DECIDED: one claim per (user, plan) via the composite key, as planned.
4. **Default plan** — the task calls `eshop-pro` the default, but `Product` carries no "default" flag the integration can read and no config key for it exists (only the four named keys are allowed). `planHandle` is REQUIRED in `POST /api/subscriptions`; no defaulting, no extra config. If an implicit default is wanted the user must say how it is identified.
5. **Request/response DTOs** — `GET /api/subscription-plans` returns `Plans[]` {handle, name, description, priceInCents, interval, intervalUnit} + `IsTruncated`; `POST` returns {subscriptionId, planHandle, planName, priceInCents, state, nextBillingAt (= `Subscription.NextAssessmentAt`, falling back to `CurrentPeriodEndsAt`)}; `GET /api/my-subscriptions` returns the same shape per item. All derive `BaseResponse` per repo convention. Status codes: POST 201 on first create, 200 when idempotently returning the existing one.
6. **Payment not required / no trial / no setup fee** — the request sets no payment profile, trial or component. The plans are seeded so; if a plan had `RequireCreditCard`, Maxio will answer 422 and the service returns 422/400 with the provider error text mapped, not retried. Not expected for the seeded plans (UNVERIFIED — only live sandbox traffic confirms).
7. **Maxio write success with `Subscription` null** — `SubscriptionResponse.Subscription` is nullable; treat a null as a malformed response (unknown outcome, reconcile via `FindSubscription`).
8. **SQL Server path** — a migration for the two new tables is added under `src/Infrastructure/Data/Migrations`, otherwise only the in-memory dev path works.
9. **Customer link vs. subscription link reuse** — the metered component `api-call` is not touched by this scope (subscribe flow only).

## 7. Decisions made during implementation

- **Collection method (UNVERIFIED in plan, settled live):** with the default (automatic) collection Maxio answered 422 "No payment method was on file for the $299.00 balance" even though the plan does not require a card. `CreateSubscription.PaymentCollectionMethod = CollectionMethod.Remittance` (documented on `Models/CreateSubscription.cs`) is set in `MaxioSubscriptionService.SubscribeAsync`; subscriptions are then invoiced, no card/3-DS. Verified live: state `active`.
- **Default plan:** `planHandle` stays required (no config key for a default exists).
- **Error mapping:** `SubscriptionException` -> `ExceptionMiddleware` (400 invalid plan, 422 rejected, 503 unconfirmed, 504 timeout, 502 other); duplicate in flight -> existing `DuplicateException` 409.
- **Stale claims:** a claim with no id older than 2 minutes whose reference Maxio does not know is released and re-claimed (`StaleClaimAge`).
- **SQL Server migration:** `AddMaxioSubscriptionLinks` creates only the two link tables (unrelated model drift the EF tool also scaffolded was removed by hand).
