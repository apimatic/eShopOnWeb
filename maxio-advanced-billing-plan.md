## 1. Scope & sequence

Repo facts read (not Maxio facts): endpoints are `MinimalApi.Endpoint` classes (`IEndpoint<IResult, ...>`) in `src/PublicApi/<Group>Endpoints/`, exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (route `api/...`, `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<T>().WithTags(...)`). Errors: `src/PublicApi/Middleware/ExceptionMiddleware.cs` turns `DuplicateException` into 409 and every other exception into 500, so 4xx-with-reason must be returned as `Results.*` with a reason body by the endpoint itself. The JWT (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`) carries ONLY `ClaimTypes.Name` (the username) and `ClaimTypes.Role` claims — no NameIdentifier/email claim. Brands: `CatalogBrand` (`Id`, `Brand`) via `IRepository<CatalogBrand>` (exemplar `CatalogBrandEndpoints/CatalogBrandListEndpoint.cs`). Persistence: `CatalogContext` (EF, SQL Server or in-memory when `UseOnlyInMemoryDatabase`), migrations in `src/Infrastructure/Data/Migrations`. Tests: `tests/PublicApiIntegrationTests` (`ProgramTest.cs`, `ApiTokenHelper.cs`).

### Semantics the sheet pins down

- **`paid`** (F3): `paid = true` iff ALL of: `Subscription.BalanceInCents` is `0` or null-equivalent-zero (field doc: "current outstanding subscription balance"); `State` not in {`PastDue`, `Unpaid`, `SoftFailure`}; and no invoice returned by `Invoices.ListInvoices { SubscriptionId = id, Status = InvoiceStatus.Open }` has a `DueAmount` parsing (invariant culture) to `> 0`. Remittance subscriptions bill by invoice, so an open invoice with a due amount is money owed even when `State` is `Active`. Short-circuit to `false` on the first due invoice. `Draft`/`Pending` invoices are not owed yet; `Voided`/`Canceled` never owed. Whether `BalanceInCents` reflects invoice dues on a Relationship-Invoicing site is UNVERIFIED — hence the invoice check is mandatory, not optional.
- **Usage for a day** (F7): the date param is parsed as `yyyy-MM-dd` (else 400). For each metered component of the subscription call `ListUsages` with `SinceDate = D 00:00 +00:00` and `UntilDate = (D+1) 00:00 +00:00` (documented recipe; the SDK sends the offset's own calendar date, so the offset MUST be zero-offset midnight of the intended date). Doc says `until_date` is "less than or equal to midnight", so a usage stamped exactly at midnight of D+1 can leak in: post-filter `CreatedAt` to the day in the site's time zone — the site time zone is UNVERIFIED (no field read) and `created_at` is the recording time, not a separate usage date. Page `Page=1..` with `PerPage=200` until a page returns fewer than 200 rows. Response lists per component: handle, name, unit, total quantity (sum of `Quantity` int arm; string arm parsed as decimal) and the individual records; add `truncated: true` if the page cap hit.
- **Next billing date** (F10): `UpdateSubscription` with `NextBillingAt` is a REAL billing change ("Send the `next_billing_at` to set the next billing date for the subscription. After that date passes and the subscription is processed, the following billing date will be set according to the subscription's product period"), not a note (`SubscriptionNotes` is not used). The response does NOT carry `next_billing_at`; verify via `Subscription.CurrentPeriodEndsAt` (remark) on the response or a follow-up `ReadSubscription`. Invalid calendar dates are silently corrected by Maxio, so the endpoint parses `date` strictly. Time of day / zone sent is UNVERIFIED: send `date` at 12:00 +00:00 and compare the read-back date; do not send `SnapDay` (calendar billing only).
- **Switch for cancelled** (F6): `UpdateSubscription.ProductHandle` is an immediate "product change" ("new payment amount is calculated and charged at the normal start of the next period"; price point = new product's default). Whether Maxio accepts a product change on a `canceled` subscription is UNVERIFIED; the remarks make reactivation the documented route back to a live state, so for `Canceled` call `ReactivateSubscription` first (Body null ⇒ new billing period, charges the OLD product per the remarks), then `UpdateSubscription`. Success = response `Product.Handle == requested handle` (a delayed change would leave the old handle and set `NextProductHandle`). If the second call fails after the first succeeded the subscription is now active on the old plan: say so in the 4xx/5xx reason.
- **Plan price** (F8): request `price` is decimal major units → `PriceInCents = round(price * 100)`; reject `<= 0`, > 2 decimals, missing name/brand with 400. `Interval = 1`, `IntervalUnit = IntervalUnit.Month`. `Description` is required by the record: use the plan name when none given. Product handle: app-generated (`plan-{brandId}-{slug(name)}-{8 hex}`) so reconciliation can find it.
- **Currency price** (F9): `Price` on `CreateProductCurrencyPrice` is `int` while `CurrencyPrice.Price` returns `double` with `FormattedPrice`; the unit (major units vs cents) is UNVERIFIED — verify with the response's `FormattedPrice` on the first sandbox call and reject non-integral prices with 400 if the unit is major. Target price point = `Product.DefaultProductPricePointId` (call `ReadProductPricePoint` with `CurrencyPrices = true`). If the price point has `TrialPriceInCents` or `InitialChargeInCents` > 0 the roles `Trial`/`Initial` would also be required ("must mirror the structure of your primary pricing") — answer 422 "plan has trial/setup pricing, not supported" rather than guess. If a `CurrencyPrice` with that currency and role `Baseline` already exists use `UpdateProductCurrencyPrices` with its `Id`; else `CreateProductCurrencyPrices` with `Role = CurrencyPriceRole.Baseline`.

## 6. Assumptions & Blockers

**Blockers:** none found. (Every feature has an SDK operation.)

**Assumptions (major — the main agent should surface them):**
1. **Brand mapping** is by convention (one Maxio product family per catalog brand, handle `eshop-brand-{CatalogBrand.Id}`); Maxio has no brand field on products and custom-field resources cover only subscriptions/customers. Pre-existing sandbox products outside those families are not "offered plans", so `GET /api/plans` is empty until staff add plans via F8 (or products are filed into such families).
2. **Ownership link** is Maxio customer `reference` = JWT username (the only identity claim the JWT carries); non-owned subscriptions answer 404.
3. **No-card subscribing** uses `remittance`, which requires the sandbox site to have Relationship Invoicing (`Site.RelationshipInvoicingEnabled`) — read it at first call; if `false`, legacy value `invoice` would be the only no-card option (UNVERIFIED). `net_terms` may be required by the sandbox (UNVERIFIED).
4. **`paid`** = zero balance AND state not past_due/unpaid/soft_failure AND no open invoice with due amount > 0; whether `balance_in_cents` reflects invoice dues is UNVERIFIED.
5. **Usage "single day"**: `since_date=D`, `until_date=D+1` (documented recipe); the usage record carries only `created_at` (recording time) — the shopper's "usage on a day" is the usage recorded that day; site time zone UNVERIFIED; the until bound is inclusive so a midnight-D+1 record is post-filtered.
6. **Cancelled switch**: reactivate-then-change; reactivating bills the old plan once (new billing period) before the product change; Maxio may also accept a direct product change on a cancelled subscription (UNVERIFIED).
7. **Currency price unit** (`int` price on create vs `double` on update/read) UNVERIFIED; multi-currency requires the site to define non-primary currencies (`Site.NonPrimaryCurrencies`) — otherwise F9 answers 4xx (not a code defect).
8. **JSON field names** (`planHandle`, `name`/`price`/`brand`, `currency`/`price`, `date`) were not given by the task.
9. Next-billing time of day (12:00 UTC) and the verification read-back are UNVERIFIED against the sandbox timezone.
10. New EF entity + migration (`MaxioWriteClaim`) is part of the work (duplicate claims) — touches `src/Infrastructure`.
