# Maxio Advanced Billing — integration plan (eShopOnWeb subscriptions)

Skill: `dotnet-integrate-maxio-advanced-billing`. SDK source (plugin-relative): `sdk/dotnet/` — map `sdk/dotnet/sdk-map.md`, pages `sdk/dotnet/map/operations/`. Every path in a **source** cell is relative to `sdk/dotnet/`.
Target host: `src/PublicApi` (JWT). Store for local records/claims: `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`; in-memory provider here, SQL Server otherwise — `src/Infrastructure/Dependencies.cs`).

| Invariant | Operations | Enforced where |

Hazard (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).
Applies here: `ProductResponse.Product`, `CustomerResponse.Customer`, `CreateCustomerRequest.Customer` and `ErrorListResponse1.Errors` (a `required IReadOnlyList<string>` — a 422 whose `errors` is an object, not a list, fails deserialization) are `required`.

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Credentials bound from `IConfiguration` section `Maxio` (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, optional `Maxio:BaseUrl`) into an options class validated at startup (`ValidateOnStart`): `ApiKey` non-blank; `ProductFamilyHandle` non-blank; `Subdomain` non-blank unless `BaseUrl` is set; `BaseUrl`, when set, an absolute URI. Host refuses to start otherwise. `BasicAuth` is always assigned in code, so the SDK's `MAXIO_ADVANCED_BILLING_BASIC_AUTH_*` fallback is never the source. The password part is the constant `x` (map), so only the API key part needs checking. How `MAXIO_API_KEY` etc. reach those keys: decided — no env-var remapping in code; development loads them into PublicApi user-secrets (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:Environment`), other deployments supply `Maxio__ApiKey`-style env vars or a secret store. Implemented by `MaxioSettingsValidator` + `ValidateOnStart()` in `MaxioServiceCollectionExtensions.AddMaxioSubscriptionBilling`; test `Startup_FailsFast_WhenApiKeyIsMissing`. |
| 2 | Secret sourcing & rotation | Dev: user-secrets on `src/PublicApi` (`UserSecretsId` already in `PublicApi.csproj`) or process env vars; no value in any file. `AddMaxioAdvancedBillingClient` builds options once inside its singleton — a rotated key takes effect only on restart. Rotation without restart is not required by the task; if it becomes required, use `options.BasicAuthProvider` (`CredentialProvider<BasicAuthCredentials>?`, asked on every request) reading `IOptionsMonitor` — `sdk-map.md`. |
| 3 | Total timeout budget | Budget: 30 s per inbound API request for all Maxio calls it makes, enforced by a `CancellationTokenSource` (linked to `HttpContext.RequestAborted`, `CancelAfter(30 s)`) in the subscription service and passed as `cancellationToken` to every SDK call; SDK `Retry.Timeout`/retry counts set to fit inside it after loading `dotnet-configuration-resilience`. Decided: budget 30 s (`Maxio:RequestBudgetSeconds`, 5–120) via `MaxioSubscriptionBillingService.CreateBudget` (linked to `HttpContext.RequestAborted`); per attempt `Retry.Timeout` 10 s, `MaxRetries` 2; `HttpClient.Timeout` 15 s backstop; settling an unknown write gets its own 10 s (`SettleBudget`), so a spent budget cannot skip reconciliation. A budget expiry surfaces as 503. |
| 4 | Write-retry ownership | `CreateCustomer` and `CreateSubscription` are POST; `RetryOptions.Default().HttpMethodsToRetry` = GET, HEAD, PUT, OPTIONS — the SDK does not resend them (source `src/MaxioAdvancedBilling/Core/Configuration/RetryOptions.cs`). Keep POST out of `HttpMethodsToRetry`. The application never blindly re-sends either write: an unclear outcome goes to reconciliation (#11). The GET reads (`ListProductsForProductFamily`, `ReadCustomerByReference`, `FindSubscription`, `ListCustomerSubscriptions`) may be SDK-retried. |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: real key = `CreateCustomer.Reference` (`reference`) — remarks: "you can only create one customer for a given reference value" (`src/MaxioAdvancedBilling/Api/Customers.cs`); reference = the caller's stable eShop identity (decided: the Identity `UserName` resolved from JWT `ClaimTypes.Name`, trimmed and lower-cased — `MaxioSubscriptionBillingService.ResolveIdentityAsync`; chosen over `ApplicationUser.Id` because Identity row ids are regenerated on every in-memory re-seed, while user names are stable and never change in this app). Reconcile with `ReadCustomerByReference`. `CreateSubscription`: **no key** on `CreateSubscriptionOperationRequest` (only `Body`); `CreateSubscription.Reference` is an app-supplied lookup handle whose uniqueness the map does not state (`UNVERIFIED`) — set it to the claim's generated reference and reconcile with `FindSubscription` (then `ListCustomerSubscriptions` matching `Product.Handle`). The `Idempotency-Key` header the SDK sends is a fresh `Guid` per call and is not a key. |
| 6 | Observability | Log via the app's `ILogger` (`IAppLogger<>` exists in PublicApi): Information — customer ensured/created (Maxio customer id), subscription created (subscription id, product handle, state); Warning — reconciliation started/settled, claim released, 404-as-not-found paths; Error — provider errors with HTTP status and the parsed error messages (`ErrorListResponse1.Errors` / `Errors1`), never request bodies. Correlation: none of the in-scope error bodies (`ErrorListResponse1`, `CustomerErrorResponse1`) carries a request id; log `ApiException.StatusCode` and the inbound request's correlation id (`BaseRequest.CorrelationId()` pattern in PublicApi); any provider request-id header via `ApiException.Headers` is `UNVERIFIED`. ## 6. Assumptions & Blockers

**Blockers**
- None that stop planning. No Maxio capability needed by this task is missing from the SDK map: product listing by family handle (`handle:` prefix), customer lookup by reference, customer create with unique reference, subscription create by product handle + customer id, subscription lookup by reference, and per-customer subscription listing are all present.
- **Claim durability (accepted by the task):** the codebase's store is EF Core `CatalogContext`; with `UseOnlyInMemoryDatabase=true` it loses every claim and customer link on restart. Within a run, primary-key claims stop double-clicks. Across a restart, the only guards are provider-side: customer `reference` uniqueness (real) and a pre-create `ListCustomerSubscriptions` check for an existing live subscription to the same product (a read, not a refusal — a concurrent pair straddling a restart is not prevented). Durable prevention needs the SQL Server configuration (`CatalogConnection`) plus a migration for the new entities.

**Assumptions**
- Customer reference: decided — the Identity `UserName` (resolved from JWT `ClaimTypes.Name`, trimmed, lower-cased), in `MaxioSubscriptionBillingService.ResolveIdentityAsync`. `ApplicationUser.Id` was rejected because the in-memory Identity store regenerates ids on every restart, which would mint a second Maxio customer for the same person. Email = `ApplicationUser.Email`.
- Customer names: decided — optional `firstName`/`lastName` on `POST /api/subscriptions` (used only when the customer is first created); otherwise derived from the e-mail local part (`demouser@…` → "Demouser" / "Customer") by `CustomerNames.Derive`.
- `MAXIO_ENVIRONMENT`: decided — bound as optional `Maxio:Environment` (`US` default / `EU`, validated by `MaxioSettingsValidator`) and mapped to `ServerEnvironment.Us`/`.Eu` in `MaxioServiceCollectionExtensions.BuildClientOptions`; the Production `Site` and the `BaseUrl` override are set on both environments.
- Env-var mapping: decided — no remapping code. `MAXIO_*` values are loaded into PublicApi user-secrets for development; deployments set `Maxio__ApiKey`, `Maxio__Subdomain`, `Maxio__ProductFamilyHandle` (and optionally `Maxio__BaseUrl`) or use a secret store.
- Plan handle: decided — required in the `POST /api/subscriptions` body (`planHandle`); a missing handle → 400 (`CreateSubscriptionEndpoint.Validate`); no server-side default, so nothing is hard-coded.
- Plans offered: decided — non-archived products of the configured family with `RequireCreditCard != true` and a price (`ReadPlanCatalogAsync`), cached for `Maxio:PlanCacheSeconds` (default 60 s).
- Duplicate policy: decided — at most one live (not `canceled`/`expired`/`failed_to_create`) subscription per (user, product handle); a different plan is a separate subscription. Enforced locally by the `SubscriptionClaim` composite key and at Maxio by `FindLiveSubscriptionForPlanAsync` before every create, which also covers lost local state (verified live across an API restart).
- "Next billing date": decided — `nextBillingAt` = `NextAssessmentAt ?? CurrentPeriodEndsAt`; `currentPeriodEndsAt` is also returned (`MaxioSubscriptionBillingService.ToDetails`).
- Payment collection (added after live traffic): `Maxio:PaymentCollectionMethod`, default `remittance`, sent on every create (see the `CreateSubscription` row). Without it the sandbox refused to create a subscription with no payment method on file.
- `UNVERIFIED` (defensive directives on the sheet): `CreateCustomer` duplicate-reference error status/shape (always re-read on 422); `CreateSubscription.Reference` uniqueness (re-read falls back to list + product handle); provider request-id header (not captured). `ReadCustomerByReference` not-found = 404 was verified live on 2026-11-13.
- Metered component `api-call` is out of scope (no usage reporting requested); `PaymentProfiles`, webhooks and Ebb are not used.
