# Maxio Advanced Billing plan: eShopOnWeb recurring subscriptions (Subscribe hero flow)

SDK root: `sdk/dotnet/` in the maxio plugin (all `src/...` and `map/...` paths below are relative to it). Business rules: `business-rules/` in the same plugin. Project: `src/PublicApi` (net8, Ardalis/MinimalApi.Endpoint `IEndpoint<>` classes), EF Core `CatalogContext` (in-memory when `UseOnlyInMemoryDatabase=true`).

Facts about the caller identity (read from `src/Infrastructure/Identity/IdentityTokenClaimService.cs`): the JWT carries only `ClaimTypes.Name` (the user name) and `ClaimTypes.Role`. There is no email, no name-identifier and no first/last name claim. The `ApplicationUser` (Identity, `UserManager<ApplicationUser>` is registered in `Program.cs`) is the source of email and the stable `Id`.

Steps, in order:

1. **Configuration + client registration.** Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional) to a settings class; validate at startup; register `MaxioAdvancedBillingClient` as a singleton (no operation; see section 5 rows 1-3, 8).
2. **Plan catalog read (`GET /api/subscription-plans`)**: `client.ProductFamilies.ListProductsForProductFamily` with `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`, paged manually (PAGED READS). Map each `ProductResponse.Product` to a DTO (handle, name, description, price in cents, interval, interval unit). Archived products are excluded by default (rule `listComponents.6`, include_archived not set).
3. **Claim store**: new EF entity `SubscriptionClaim` keyed by user id on `CatalogContext` (DUPLICATE CLAIMS).
4. **Subscribe (`POST /api/subscriptions`)**, authenticated:
   1. Resolve the caller: `ClaimsPrincipal` name -> `UserManager<ApplicationUser>.FindByNameAsync` -> `Id`, `Email`. No Name claim or no user -> 401/404 before any Maxio call.
   2. Resolve the plan: request `planHandle` (or the configured default, section 6) must be one of the handles returned by step 2's list (CROSS-OPERATION INVARIANTS). Unknown -> 400 without a write.
   3. **Claim** the user (insert `SubscriptionClaim`). Refused -> second-caller path (DUPLICATE CLAIMS).
   4. Ensure customer: `Customers.ReadCustomerByReference` (reference = ApplicationUser.Id); on 404 `Customers.CreateCustomer`; on a create whose outcome is unknown re-read by reference (UNKNOWN OUTCOMES). Store the customer id on the claim row.
   5. `Subscriptions.CreateSubscription` with `CustomerId`, `ProductHandle`, `Reference`; no payment method, no trial, no components. Record subscription id on the claim row.
   6. Confirm back: map the `SubscriptionResponse.Subscription` (create response already carries them; no extra read needed) to plan handle/name, price (`ProductPriceInCents`), `State`, next billing date (`NextAssessmentAt`; `CurrentPeriodEndsAt` as the period end). Return 201.
5. **My subscriptions (`GET /api/my-subscriptions`)**, authenticated: resolve caller as above; read the user's `SubscriptionClaim` for the Maxio customer id; none -> empty list (200). Else `Customers.ListCustomerSubscriptions` (CustomerId from the claim), map each `Subscription` like step 4.6. Never accept a user id from the request.
6. EF migration for SQL Server path (the new table), tests (unit with the HttpClient stub seam, integration with in-memory DB).

A capability the map lacks: none for this scope. Metered component `api-call` is in the catalog but nothing in scope attaches or reports usage on it (see section 6).

## 2. CONTRACT SHEET

⚠ Signatures are generated code, verbatim. Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer using the record's own property names. Never flat arguments.

⚠ Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits.

Common to every operation row: trailing parameters `MaxioAdvancedBilling.Core.RequestOptions? requestOptions = null, System.Threading.CancellationToken cancellationToken = default` (as written in the map; resolve the `RequestOptions` namespace from the map/`Core/` source when writing code). Auth: `options.BasicAuth`. Server group `Production`. Throw-only. No pagination object: every list returns `IReadOnlyList<T>` and paging is manual via `Page`/`PerPage`.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The `ProductHandle` sent to `CreateSubscription` must be a handle (non-archived) this application offers, i.e. one returned in `Product.Handle` by the product-family list, not merely a product that exists at Maxio | `Subscriptions.CreateSubscription` <- `ProductFamilies.ListProductsForProductFamily` (family `handle:` + `Maxio:ProductFamilyHandle`) | In the subscribe handler, before the claim is written and before `CreateSubscription`: the request's plan handle is matched against a fresh plan list read; the same list read backs `GET /api/subscription-plans` |
| The `CustomerId` sent to `CreateSubscription` must be the id of the customer this application stored/looked up for the caller's reference | `Subscriptions.CreateSubscription` <- `Customers.ReadCustomerByReference` / `Customers.CreateCustomer` (id the app stored on the claim row) | Subscribe handler, between ensure-customer and `CreateSubscription`: the id used is read from the claim row / the lookup result, never from the request body |

### Client construction, auth, server node

- Class `MaxioAdvancedBilling.MaxioAdvancedBillingClient`; only constructor `(System.Net.Http.HttpClient httpClient, MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions options)`; DI form `services.AddMaxioAdvancedBillingClient(Action<MaxioAdvancedBillingClientOptions>)` (`ServiceCollectionExtensions.cs`, registers a singleton). Source: `sdk-map.md` *Getting a client*.
- Auth: HTTP Basic. `options.BasicAuth = new MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials { Username = <Maxio:ApiKey>, Password = "x" }`. Username is the Maxio API key; password is the constant `x` (`sdk-map.md` *Servers & auth*; rule `every-request.1`). Because it is set in code it wins over the SDK's own env vars (`MAXIO_ADVANCED_BILLING_BASIC_AUTH_*`).
- Environments: `MaxioAdvancedBilling.Servers.ServerEnvironment.Us` (default, `https://{site}.chargify.com`) / `.Eu` (`https://{site}.ebilling.maxio.com`). Declares no sandbox environment: sandbox is a separate Maxio *site* (its own subdomain), selected by `Maxio:Subdomain`.
- Subdomain / base URL (`Servers/ProductionOptions.cs`, `sdk-map.md` *Servers & auth*): `options.Server.Production.Us.Site = <Maxio:Subdomain>` fills the `{site}` template variable (default literal `"subdomain"`); `options.Server.Production.Us.BaseUrl` is the full template (default `https://{site}.chargify.com`). When `Maxio:BaseUrl` is set, assign it verbatim to `options.Server.Production.Us.BaseUrl` (the site variable is then irrelevant unless the value itself contains `{site}`). Use `Environment = ServerEnvironment.Us`; EU hosting is not requested by the task (rule `every-request.6`).
- Server groups touched: `Production` only. `Ebb` (`https://events.chargify.com/{site}`, used by event-based billing) is not touched by any operation here.

## 4. REQUIRED READING

Load all before implementing (plugin-qualified):

- `maxio:dotnet-error-handling` - every catch ladder (customer lookup/create, subscription create/find, plan list).
- `maxio:dotnet-client-initialization` - step 1 client registration.
- `maxio:dotnet-authentication` - step 1 BasicAuth wiring and startup check.
- `maxio:dotnet-configuration-resilience` - retries, per-call budget, server node, paging.
- `maxio:dotnet-calling-endpoints` - every operation call.
- `maxio:dotnet-models` - request payloads and response mapping.
- `maxio:dotnet-testing` - step 6 tests.

Hazard row (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

### DUPLICATE CLAIMS

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| `Customers.CreateCustomer` + `Subscriptions.CreateSubscription` (one subscribe per eShop user; double-click / concurrent POST) | New EF entity `SubscriptionClaim` in `CatalogContext` (the store the app already keeps its records in); columns: `UserId` (string, max 256, **primary key**), `Status` (Pending/Completed), `PlanHandle`, `SubscriptionReference`, `MaxioCustomerId` (int?), `MaxioSubscriptionId` (int?), `CreatedAtUtc`. In-memory and SQL Server both enforce the PK. A provider idempotency key is not available (row 5), so nothing stands beside it. | The primary key on `UserId`: the claim insert (`Add` + `SaveChangesAsync`) of the second caller violates it. Not a status read-then-write. | The subscribe handler's `catch (DbUpdateException)` around the claim `SaveChangesAsync` (in-memory raises `DbUpdateException` for a duplicate key on a separate scoped context; covered by a test that fires two concurrent requests). On the catch the handler reads the existing row: `Completed` -> 200 with the existing subscription (`ReadSubscription`); `Pending` -> settle per UNKNOWN OUTCOMES if older than the stale window, else 409 `request already in progress`. Claim is released (row deleted) when Maxio definitively refuses the call (`ApiException` with a 4xx typed error or `ResponseDeserializationException` on a non-2xx), so the user can retry after fixing the cause. | `MaxioBillingService.SubscribeAsync`: claim = `_db.SubscriptionClaims.Add` + `SaveChangesAsync` (catch of duplicate key -> `AnswerForLostClaimAsync`), then SDK call `_client.Subscriptions.CreateSubscription` (customer first via `EnsureCustomerAsync`: `ReadCustomerByReference`/`CreateCustomer`). Release: `SubscriptionClaims.Remove` in the `catch (BillingException ex) when (ex.Refused)`. Store refusal in-memory is `ArgumentException`, relational `DbUpdateException`; both caught. |

Claim order for the row: claim insert -> `Customers.ReadCustomerByReference`/`CreateCustomer` -> `Subscriptions.CreateSubscription` -> update claim to `Completed` with the ids. Policy: one claim per user, so a user subscribes once via this endpoint (`YOUR CALL — not in the map`: a second, different plan for the same user is out of scope; changing plans would be a separate operation).

Settling rule for both (in the failing write's own `catch` for `SdkConnectionException`, `SdkTimeoutException`, cancellation by the budget token, and non-typed `ApiException`/`ResponseDeserializationException` on a 2xx): re-read by reference with a fresh short-budget token. Found -> adopt it as the result (`Completed`, ids stored). Not found (`FindSubscription` `TryGetNoContent`/ReadCustomerByReference 404) -> the claim stays `Pending` (not released) and the caller gets 503; any later request that finds a `Pending` claim runs the same re-read first and only after the stale window (5 minutes, `YOUR CALL — not in the map`) with still nothing found deletes the claim so a new attempt can proceed. The re-read GET is retried by the SDK (GET is in the default retry verbs).

## 6. Assumptions & Blockers

Blockers: none. The SDK has every operation the scope needs, and the codebase has a store (EF `CatalogContext`) that keeps a claim past the process and enforces a primary key.

Assumptions and decisions the main agent must surface or settle (each marked where it is not in the map):

1. **Paid plan with no payment method (rule `createSubscription.7`, loud).** Maxio refuses a signup for a paid product when the product's options require payment information and the request has no payment method. The task states the sandbox catalog needs no payment method, so the plan sends none. Defensive handling: the plan list exposes `RequireCreditCard`; the subscribe handler, having already read the plan, answers 409/422 `plan requires a payment method` without calling Maxio when it is `true` (its `null` is treated as unknown, not false, rule `every-request.11`), and a Maxio 422 on `CreateSubscription` is surfaced with the joined error strings. Whether the sandbox actually accepts the signup is `UNVERIFIED` (only live traffic settles it). If it refuses, a payment method is required and that changes the request contract.
2. **Charge at creation (rule `createSubscription.10`).** `next_billing_at` is not sent, so any initial/trial charge is assessed at creation; with no trial and no setup fee the first period is charged at signup. The returned `NextAssessmentAt`/`CurrentPeriodEndsAt` are the next-billing date confirmed back. A subscription returned in `AwaitingSignup`/`Pending`/`PastDue` etc. is passed through as the state; the endpoint does not interpret it as success or failure beyond HTTP 201.
3. **Default plan (`eshop-pro`).** The task requires handles not to be hard-coded and gives only the four `Maxio:` keys, and the catalog has no flag marking a "default subscribe target". Proposal `YOUR CALL — not in the map`: `POST /api/subscriptions` accepts an optional `planHandle`; when omitted it uses an extra optional key `Maxio:DefaultPlanHandle` (not one of the four the task listed, so it is flagged for approval) validated against the plan list at request time. If the user rejects a fifth key, `planHandle` becomes required in the request.
4. **Customer first/last name.** `CreateCustomer` requires `first_name`, `last_name`, `email`, and the JWT/`ApplicationUser` provide only a user name and email (no name fields). `YOUR CALL — not in the map`: derive `FirstName` from the user name/email local part and `LastName` from a fixed placeholder, or add profile fields. Customers are created without address; rule `createCustomer.19`/`every-request.43`: such a customer is not eligible for tax calculation (accepted for this sandbox scope).
5. **Customer reference = `ApplicationUser.Id`** (stable, unlike the mutable user name), subscription reference `"eshop-sub-" + userId`. `YOUR CALL — not in the map`. If a user's email changes later, the Maxio customer email is not synced (out of scope).
6. **`ReadCustomerByReference` not-found is a raw 404 (`UNVERIFIED`).** The map row has Case B only (no typed 404), so the code treats `RawError.StatusCode == 404` as "no customer"; any other failure is not "not found".
7. **No `uniqueness_token`.** Rule `every-request.36` describes a top-level token, but no generated request/body type in scope declares it, so the plan relies on the claim row (a local control) plus reference-based reconciliation instead.
8. **`api-call` metered component** exists in the catalog but is not attached at signup (`components` is not sent) and no usage is reported: out of scope for the Subscribe flow. If it must be attached or metered, add `SubscriptionComponents` operations (new plan section).
9. **One claim per user** (one subscription per user via this endpoint), see DUPLICATE CLAIMS.
10. **Concurrency limit** (rule `every-request.26`): Maxio allows 4 concurrent calls per subdomain; the plan list should be cached in memory for a short TTL (`IMemoryCache` is registered) so shopper browsing does not consume them. `YOUR CALL — not in the map` (TTL; an invariant check must not read stale data for longer than the TTL).
11. **SQL Server path** needs an EF migration for `SubscriptionClaim` (existing `src/Infrastructure/Data/Migrations/`); the in-memory path needs none. Migration generation is implementation work.
12. **Project reference** to the SDK is a local path into the plugin install (`dotnet add reference <plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`), machine-local; the SDK targets `netstandard2.0` (usable from net8). Say so at hand-over.
13. **Secrets outside Development**: user-secrets only load in Development (host default); other environments need `Maxio__*` from their own provider (row 2).

## 7. Decisions settled in code (replaces every `YOUR CALL — not in the map`)

- Default plan: `POST /api/subscriptions` takes optional `planHandle`; when omitted, `Maxio:DefaultPlanHandle` (extra optional key, `MaxioSettings.DefaultPlanHandle`); neither -> 400.
- Customer names: `FirstName` = email local part, `LastName` = `"Customer"` (`MaxioBillingService.EnsureCustomerAsync`). References: customer = `ApplicationUser.Id`, subscription = `eshop-sub-<userId>` (`SubscriptionReferenceFor`).
- **Payment collection (found by live traffic, contradicts assumption 1/2):** with no payment method Maxio refused the signup ("No payment method was on file for the balance") even though the plans do not require a card, because the first period is charged at creation on automatic collection. `CreateSubscription.PaymentCollectionMethod` is therefore set from optional `Maxio:PaymentCollectionMethod`, default `remittance` (invoice, no card). `MaxioBillingService.CollectionMethodFor`.
- Timeouts: SDK per-attempt 10s, 2 retries (`MaxioServiceCollectionExtensions`); whole-call budgets 20s reads / 45s subscribe / 15s settle re-reads (`MaxioBillingService.Budget`). Log levels as in row 6. One claim per user; stale Pending window 5 min; plan-list cache 60s, only when complete.
- Credential check: `MaxioSettingsValidator` + `ValidateOnStart`; Subdomain optional when BaseUrl set.
- EF migration `AddSubscriptionClaim` added (table only).
