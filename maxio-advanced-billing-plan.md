# Maxio Advanced Billing plan — subscription billing in eShopOnWeb (`src/PublicApi`)

SDK root (plugin-relative): `sdk/dotnet/` · business rules: `business-rules/` (rule ids below as `listUsages.1` = `maxio-c4:listUsages.1`, `every-request.12`, …).
All Maxio calls go through the C# SDK against a Maxio **test-mode site** (SDK has no sandbox environment — see section 5 row 8). No Maxio stub anywhere.

## 1. Scope & sequence

Repo conventions (read): endpoints are `IEndpoint<IResult, …>` classes (MinimalApi.Endpoint) with `XEndpoint.cs` + `XEndpoint.XRequest.cs` + `XEndpoint.XResponse.cs`, one folder per group — exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (route `api/...`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`; staff = `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, …)]`). Brand list exemplar: `src/PublicApi/CatalogBrandEndpoints/CatalogBrandListEndpoint.cs` (`IRepository<CatalogBrand>`, `CatalogBrand.Brand` = brand name). The JWT built in `src/Infrastructure/Identity/IdentityTokenClaimService.cs` carries only `ClaimTypes.Name` (user name) and `ClaimTypes.Role`; there is no user-id claim. Error mapping lives in `src/PublicApi/Middleware/ExceptionMiddleware.cs` (only `DuplicateException`→409, everything else 500) — new "4xx with a reason" paths return a status + `BlazorShared.Models.ErrorDetails` (or add exception types mapped there; DECIDED).

### Business rules and how the plan answers the "pay attention" items

**Ownership (JWT user ↔ Maxio).** Link = Maxio customer `reference` == JWT `ClaimTypes.Name` (customer created on first subscribe with that reference; reference must be unique per site — `createCustomer.1`, so a second creator is refused by Maxio; `readCustomerByReference` is the exact-match lookup, `readCustomerByReference.1`, not `listCustomers q`). Every `{subscriptionId}` route first calls `ReadSubscription` and requires `Subscription.Customer.Reference` equals the caller's name (ordinal, ignore case); mismatch or Maxio 404 → the **same** 404 (no existence leak). Admin routes (#10, #11, plan routes) skip ownership but require the Administrators role. Never trust a customer/user id in the body or URL.

**Which plans a shopper sees.** Maxio "plans" = API **products**. Offered set = `ListProducts` (page until empty; archived are omitted by default — rule `include_archived`, `listProducts` rules) filtered to products whose `Product.ProductFamily` belongs to a catalog brand (family `Handle == "eshop-brand-{CatalogBrand.Id}"` OR family `Name` equals `CatalogBrand.Brand`, ignore case) and `ArchivedAt == null`. Plans not under a catalog brand are never offered or accepted. The same set gates subscribe and switch (CROSS-OPERATION INVARIANTS).

**Subscribing without a card (payment collection method).** `createSubscription.41` / `every-request.42`: statement sites accept `automatic|invoice`, Relationship Invoicing sites `automatic|remittance|prepaid`. No card ⇒ `CollectionMethod.Remittance` when `Site.RelationshipInvoicingEnabled == true`, else `CollectionMethod.Invoice` (from `ReadSite`, step 0b). A card-less `automatic` paid signup is refused (`createSubscription.7`), so `PaymentProfileAttributes`, `CreditCardAttributes`, `BankAccountAttributes`, `PaymentProfileId` are never sent. Omitting `next_billing_at` ⇒ initial charges assessed at creation (`createSubscription.10`) — as an invoice, not a card charge, under these collection methods.

**State rules (Maxio refuses; app pre-checks the ones the rules state, then maps any remaining 422 to 4xx with Maxio's message).**
- pause: `pauseSubscription.1` (next billing within 24h → refused), `pauseSubscription.2` (not eligible → 422). App gate: state ∈ {active, trialing} and `NextAssessmentAt` > now+24h, else 409 with reason. Result state `on_hold`; on hold nothing renews (`background.69`).
- resume: `resumeSubscription.1` only `on_hold` (422 otherwise). Resuming after the renewal date charges immediately (`resumeSubscription.3`).
- cancel: `cancelSubscription.6` already canceled → 422 (treat as 409 "already canceled"). No schedule params ⇒ immediate cancel (`cancelSubscription.1`); `cancel_at_end_of_period`/`scheduled_cancellation_at` need a site feature (`cancelSubscription.2`) — not sent.
- restart (= `ReactivateSubscription`): `reactivateSubscription.1` Maxio accepts canceled/unpaid/trial_ended; **the app only restarts `canceled`** (task: "restart one they cancelled"), others 409. Needs a payment profile only when a balance will be charged (`reactivateSubscription.12`); remittance/invoice collection issues an invoice instead.
- switch: `migrateSubscriptionProduct.1` migration only for active/trialing; `.2` target must differ from the current product; `.3` product_id or product_handle required; `.10/.11` card/proration refusals (422 → 4xx); cross-family migration drops components/coupons (`.5/.6`) — brands are families, so a cross-brand switch loses them: accepted, recorded in the response text. **Migration vs product change:** active/trialing → `MigrateSubscriptionProduct` (period reset + full price unless `preserve_period`); EVERY other state including **canceled** → `UpdateSubscription` with `product_handle` (`updateSubscription.3`: product changes now, new amount from next period, no proration; state is not changed — a cancelled subscription stays cancelled but is on the new plan). See A5.
- reactivation vs resume: `resume` = on-hold only; `reactivate` = canceled. They are never interchangeable.

**`paid`.** `Subscription.BalanceInCents` is "current outstanding subscription balance" (cents). On Relationship Invoicing the owed money is the open payable invoices, `AccountBalances.OpenInvoices.BalanceInCents` (`readAccountBalances.1`: cents, sums of open/pending payable invoices). `paid = true` iff `BalanceInCents <= 0` AND (site is statement-based OR `OpenInvoices.BalanceInCents <= 0`); a credit (negative) is "owes nothing". `PendingInvoices` are not yet payable → excluded. Missing/null balance ⇒ cannot decide ⇒ 502 with reason, never a guessed `true`. `ReadAccountBalances` is only called when `RelationshipInvoicingEnabled == true`.

**Metered usage for one day.** `ListUsages` is per component and only for metered/prepaid components (`listUsages.1`, quantity-based → refused). Steps: `ListSubscriptionComponents` (no `InUse` filter — archived components are included, `listSubscriptionComponents` rule, and past usage may sit on an archived component), keep `Kind == ComponentKind.MeteredComponent`, then per component `ListUsages(SinceDate = D, UntilDate = D+1 day)` — `since_date`/`until_date` are sent as dates (`.ToDate()`), both mean midnight of that date in the **site** time zone and `until_date` is inclusive of midnight (`listUsages.2`), so pass D+1 and ALSO filter client-side `Usage.CreatedAt` whose own-offset calendar date == D (timestamps come back in site tz, `every-request.12`). Page with `PerPage = 200` until a short/empty page (`every-request.23/24`). Sum `Quantity1` (int or string, parse as decimal) per component.

**Plan creation + brand mapping.** Brand ∈ shop catalog (`IRepository<CatalogBrand>`, by id or exact name — request carries the catalog brand **id** as `BrandId`; decided in `CreatePlanRequest`/`BillingService.CreatePlanAsync`). Maxio has no brand concept: brand ⇄ **product family** (`createProduct.2`: family must exist first; `createProductFamily.2`: family handle unique). Mapping above (`eshop-brand-{id}` handle; create the family on first use with `Name = CatalogBrand.Brand`). Product: `CreateOrUpdateProduct` requires name, description, price_in_cents, interval, interval_unit; monthly ⇒ `Interval = 1`, `IntervalUnit.Month`, price decimal → cents (rounded, > 0). `description` is required by the SDK and not in the task → name. `auto_create_signup_page` is not sent (rejected on catalog-experience sites, `createProduct.1`).

**Currency prices.** Currency must be one of `Site.NonPrimaryCurrencies` (`createProductCurrencyPrices.1`); prices go on the product's default (non-custom, `.3`) price point; must cover every role the price point defines — plans have no trial/setup so `CurrencyPriceRole.Baseline` only (`.2`); existing price in that currency ⇒ `UpdateProductCurrencyPrices` using that `CurrencyPrice.Id` (`updateProductCurrencyPrices.2` forbids updating what does not exist), else Create. Read with `CurrencyPrices = true` or the field is omitted (`product-price-points` rule).

**Next billing date actually causing billing.** `UpdateSubscription.next_billing_at` (`updateSubscription.10/.11/.12/.13`): invalid calendar dates roll over (validate first), the new date becomes the anchor of future billing, **the response has no next_billing_at — verify through `current_period_ends_at`**, and a `billing_date_change` webhook fires. The subscriber is billed on that date only if the subscription still renews: on hold / canceled / expired never renew (`background.69`, `cancelSubscription`), a past/ now date is not a schedule, and an `expires_at` before the date means it expires first. Gate: state ∈ {active, trialing}, date strictly after today (site-local), `ExpiresAt` null or after the date, else 409 with reason. A date-only value is noon site time (`every-request.14`); the SDK field is `DateTimeOffset`, so send 12:00:00 UTC on that date (same calendar date for site zones UTC-12…UTC+11) and read back: the date part of `CurrentPeriodEndsAt` (own offset) must equal the requested date, else 502. Billing on that date then follows collection method: automatic charge vs invoice (`background.59/.60`); for card-less subscriptions (remittance/invoice) "billed" = the renewal invoice is generated.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| a plan handle accepted by subscribe must be a plan this application offers (non-archived product whose family maps to a catalog brand) | `CreateSubscription.ProductHandle` ← `ListProducts` (+ `IRepository<CatalogBrand>`) | before `CreateSubscription` is called — in the offered-plan service (step 1) that `GET /api/plans` also uses |
| a plan handle accepted by switch must be one of the same offered set and differ from the subscription's current `Product.Handle` | `MigrateSubscriptionProduct.Migration.ProductHandle` / `UpdateSubscription.ProductHandle` ← `ListProducts` | before either write |
| a brand accepted by plan creation must be one of the shop's catalog brands, and the product must be created in that brand's family | `CreateProduct.ProductFamilyId` ← `IRepository<CatalogBrand>` + `ListProductFamilies`/`CreateProductFamily` | before `CreateProduct` |
| a currency accepted for a currency price must be one of the site's defined non-primary currencies | `CreateProductCurrencyPrices.Currency` ← `ReadSite.Site.NonPrimaryCurrencies` | before the write |

### Client construction / auth / server-node facts

- `new MaxioAdvancedBillingClient(HttpClient httpClient, MaxioAdvancedBillingClientOptions options)` (only constructor); DI: `services.AddMaxioAdvancedBillingClient(options => …)`. Options: `Environment`, `Retry`, `Logging`, `TimeProvider`, `Server`, `Hooks`, `BasicAuth`, `BasicAuthProvider`.
- Auth: HTTP Basic — `options.BasicAuth = new MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials { Username = <Maxio:ApiKey>, Password = "x" }`. A value set in code beats the SDK's own variables (`MAXIO_ADVANCED_BILLING_BASIC_AUTH_USERNAME/PASSWORD`), which are therefore not used.
- Servers: group `Production` only (none of the planned operations has a Server-group bullet; `Ebb` is not touched). `Us` → `https://{site}.chargify.com`, `Eu` → `https://{site}.ebilling.maxio.com`; subdomain goes in `options.Server.Production.Us.Site` / `.Eu.Site`; override point `options.Server.Production.Us.BaseUrl` / `.Eu.BaseUrl`. `Maxio:BaseUrl` set ⇒ assign it verbatim to BOTH `Production.Us.BaseUrl` and `Production.Eu.BaseUrl`; unset ⇒ leave defaults and set `Site`. Whether `{site}` is still substituted inside an overridden URL is `UNVERIFIED` (source `Servers/ProductionOptions.cs` declares the default template with `{site}` and the `TemplateParam.ForServer("site", …)` — no statement about overrides); a test must assert the final request host.
- Retries: defaults retry GET/HEAD/PUT/OPTIONS on 408/429/500/502/503/504, 3 retries, 1s exponential (`Core/Configuration/RetryOptions.cs`); POST and DELETE are not resent. Per-attempt `Timeout` semantics: `dotnet-configuration-resilience`.

## 6. Assumptions & Blockers

**Blockers (need the user/main agent before or while coding)**
- B1. Maxio test site must exist with: env vars `MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_ENVIRONMENT` set; at least one **non-primary currency** defined (otherwise feature 9 can only return 4xx "currency not defined", `createProductCurrencyPrices.1`); `Site.Test == true`. The site's invoice architecture is read at runtime but card-less signup on a site whose only allowed collection method is `automatic` cannot work.
- B2. Claim store needs a new `MaxioClaim` table: an EF entity in `CatalogContext` plus a SQL Server migration (`src/Infrastructure/Data/Migrations`, last migration `20211231093753_FixShipToAddress`); the in-memory provider (tests) needs no migration. If adding a migration is not acceptable, the duplicate-prevention requirement cannot be met and the user must choose.

**Assumptions (flag to user; all marked as decisions)**
- A1. "Plan" = Maxio product; "brand" = product family (Maxio has no brand type). Family belongs to brand `b` if handle `eshop-brand-{b.Id}` or name equals `b.Brand` (ignore case); missing family is created on first plan creation. `POST /api/admin/plans` takes brand as the catalog brand **id**; plan id in admin URLs and `plans` responses = Maxio product id; subscribe/switch take the product **handle**. DECIDED.
- A2. Plan handle for new plans = slug(name) (lowercase, `-`); duplicate ⇒ 409. Description sent = plan name (SDK requires it).
- A3. Customer for a new shopper: `Reference = ClaimTypes.Name`, `Email = ClaimTypes.Name`, first/last name derived from the local part of the e-mail (the JWT carries no names; SDK requires both). The user name is assumed to be an e-mail (true for seeded users in `AppIdentityDbContextSeed`).
- A4. One subscription per (user, plan) forever (claim key); to resume a cancelled plan use restart. Several different plans at once are allowed.
- A5. **Switch on a cancelled subscription = `UpdateSubscription` product change; state stays `canceled`** (Maxio migration is refused for non-active/trialing, `migrateSubscriptionProduct.1`). Whether Maxio accepts a product change on a canceled subscription is `UNVERIFIED` (only live traffic settles it); if it is refused the endpoint returns 4xx with Maxio's reason. If the user wants "switch also reactivates", say so and the plan changes to reactivate-then-migrate.
- A6. Switch uses `MigrateSubscriptionProduct` with `PreservePeriod` unset (period reset, full new price, `migrateSubscriptionProduct.8`), `IncludeCoupons` default; restart sends no options (new billing period, `reactivateSubscription.4`); cancel is immediate.
- A7. `paid` rule above; unknown balance ⇒ 502.
- A8. "Metered usage" = components of kind `metered_component` (prepaid usage components excluded); `quantity` summed per component, plus the individual usage records; day = site-local calendar date (site time zone is not exposed by `Site`; derived from the offset Maxio returns on `created_at`, `every-request.12`).
- A9. Staff next-billing-date: only for `active`/`trialing`, date after today, before any `ExpiresAt`; sent as 12:00 UTC on that date and verified by read-back (`UNVERIFIED` that site time zone falls in UTC-12…UTC+11 — read-back guards it).
- A10. Currency price units: `CreateProductCurrencyPrice.Price` is `int` and `UpdateCurrencyPrice.Price` `double`; the SDK docs say only "Price for the given role" — whether the unit is major units or cents is `UNVERIFIED`. Directive: after the write, `ReadProductPricePoint(CurrencyPrices = true)` and compare `CurrencyPrice.Price`/`FormattedPrice` with the staff input; mismatch ⇒ 502 and the first sandbox run decides the conversion (record the result here). The `price` the staff API accepts is a decimal in major units; a value that cannot be represented by the chosen wire unit ⇒ 400.
- A11. The 4xx error body shape: `ErrorDetails`-style `{statusCode, message}` (existing type in `BlazorShared.Models`); mapping of Maxio 422 → 422/409 and 404 → 404 chosen at implementation (DECIDED).
- A12. `Subscription.NextAssessmentAt` is used for the "within 24 hours" pause gate and `CurrentPeriodEndsAt` as the next-billing anchor read-back (both fields exist on `Subscription`; that they equal `next_billing_at` is `UNVERIFIED`).

## 8. Decisions made in code (settled `YOUR CALL` entries) and sandbox findings

- Error body shape / 4xx mapping: `BillingException(status, message)` mapped in `ExceptionMiddleware` to the existing `ErrorDetails` JSON; Maxio 404 → 404, other 4xx → same status with Maxio's reason, 401/403 → 502, 429 → 503, 5xx/transport → 502/504 (`MaxioGateway.Map`).
- Total budget: 60 s linked to `RequestAborted` per service call (`BillingService.Bound`); per-attempt SDK timeout 15 s, `HttpClient.Timeout` 20 s (`MaxioServiceCollectionExtensions`).
- Page caps: 25 pages × 200 (`BillingService.MaxPages`).
- Brand ⇄ family: `eshop-brand-{id}` handle preferred, else same name (`BrandFor`, `EnsureFamilyAsync`); brand is the catalog brand id in the request; plan id = Maxio product id; subscribe/switch take the handle. New plan handle = slug(name), duplicate → 409.
- Claims are in-flight only (released in `finally`, expire after 5 min) so a shopper can later subscribe again / hold several subscriptions; store = `MaxioClaims` table (`CatalogContext`, migration `AddMaxioClaims`).
- Verified live on the sandbox: subscribe (remittance, no card), `paid` true/false (zero-price plan → true; Relationship Invoicing account balances path), pause/resume/cancel/restart, switch on an ACTIVE subscription (migration) and on a CANCELLED one (UpdateSubscription product change accepted; state stays canceled — A5 resolved), usage for a day (sum + records, day filtered in site time zone +05:00), next billing date (read back from `NextAssessmentAt`/`CurrentPeriodEndsAt`; both move together).
- A10 (currency price unit): the sandbox site has NO non-primary currency (`non_primary_currencies` empty) and Maxio itself answers "Currency must be defined on the site level", so a currency price cannot be created there; the endpoint answers 400 with that reason. The unit stays UNVERIFIED; the code sends major units and refuses (502) if the read-back differs.
