# Maxio Advanced Billing integration plan: eShopOnWeb subscriptions

SDK root: `sdk/dotnet/` in the `maxio` plugin, called `<sdk>/` below. Business rules: `business-rules/` in the same plugin. Every map, source and rule path below is plugin-relative.
Integrate skill: `dotnet-integrate-maxio-advanced-billing`. Target host: `src/PublicApi` (JWT). The store is `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`): EF InMemory when `UseOnlyInMemoryDatabase=true`, SQL Server otherwise.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Reference the SDK project from `PublicApi.csproj` (ProjectReference to `<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`. This path works only on this machine, see §6). Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`. Fail fast at startup (PR #1). Register the client once with `AddMaxioAdvancedBillingClient`. | none (client construction) |
| 2 | Add a claim entity to `CatalogContext` with a **string primary key**. The key is the customer reference or the subscription reference. Columns: key, state (`Pending`/`Done`/`Unknown`), Maxio id (store it as `long` or string, rule `maxio-c4:every-request.21`), and timestamps. | none |
| 3 | `GET /api/subscription-plans` reads the plans offered in the family `handle:{Maxio:ProductFamilyHandle}`. It walks pages until a page comes back empty or short, and stops at a page cap. It returns handle, name, description, price in cents, interval and interval unit, plus a `Truncated` flag. Rules `maxio-c4:listProductsForProductFamily.1`, `maxio-c4:updateComponent.1` (`handle:` prefix), `maxio-c4:listComponents.6` (archived excluded by default), `maxio-c4:listComponents.8`/`maxio-c4:listInvoices.10` (paging). | `ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure the Maxio customer exists, keyed by a deterministic customer reference built from the JWT `ClaimTypes.Name` claim (written by `IdentityTokenClaimService`). Order: claim, then lookup by reference, then create only if absent, then record the id. Rules `maxio-c4:createCustomer.1` (reference unique on site), `maxio-c4:readCustomerByReference.1` (use lookup, not `q`), `maxio-c4:createCustomer.12` (organization defaults to the customer's name: leave it unset). | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5 | `POST /api/subscriptions {planHandle}`. First check `planHandle` against step 3's set (invariant below). Then claim the subscription reference, then reconcile (`FindSubscription` by reference, so the call is skipped if the subscription already exists), then call `CreateSubscription` with `ProductHandle`, `CustomerId` and `Reference`, then record the result. Return plan, price, state and next billing date. Rules `maxio-c4:createSubscription.1` (product required), `maxio-c4:createSubscription.4` (customer required), `maxio-c4:createSubscription.5` (never `customer_attributes` for an existing customer: it creates a duplicate customer), `maxio-c4:createSubscription.10` (no `next_billing_at`, so charges are assessed at creation), `maxio-c4:createSubscription.8` (a 422 with an `action_link` means 3DS), `maxio-c4:createSubscription.3` (`product` may be null). | `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription` |
| 6 | `GET /api/my-subscriptions` looks the customer up by reference. A 404 returns an empty list. Otherwise it lists that customer's subscriptions and maps them to the same DTO as step 5. Rule `maxio-c4:listCustomerSubscriptions.1` (null product). | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` |
| 7 | Error boundary: map SDK exceptions to HTTP results (a 422 refusal becomes 422 with Maxio's `errors[]`; config, auth or 404-family errors become 502/503; an unknown outcome is settled, see §UNKNOWN OUTCOMES). Tests use a stubbed `HttpClient`. | all of the above |

Out of scope, with no Maxio call: plan change (`SubscriptionProducts.MigrateSubscriptionProduct`), cancel, metered usage on `api-call`, and webhooks.

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none). Build that record with an object initializer that uses the record's own property names. Never pass flat arguments.
> ⚠ **Every SDK type is written fully qualified**, with the namespace its source path implies. Take that path from the map entry for THAT type, never from where a neighbouring type sits.

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Values bind from `IConfiguration` section `Maxio`. In `PublicApi/Program.cs`, before `builder.Build()`, the host throws (it refuses to start) when `Maxio:ApiKey` or `Maxio:ProductFamilyHandle` is null or whitespace, when `Maxio:Subdomain` is blank **and** `Maxio:BaseUrl` is blank, or when `Maxio:BaseUrl` is set but is not an absolute http(s) URI. The Basic password is the constant `x` (map), so `ApiKey` is the only secret part. The SDK's `MAXIO_ADVANCED_BILLING_BASIC_AUTH_*` fallback is never relied on. **Decided:** `MaxioSettingsValidator` (`IValidateOptions<MaxioSettings>`) registered with `.ValidateOnStart()` in `MaxioServiceCollectionExtensions.AddMaxioBilling`. It also validates `Maxio:Environment` (US/EU) and `Maxio:PaymentCollectionMethod`. Verified live: with a blank `Maxio:ApiKey` the host exits with `OptionsValidationException` naming the key and never listens |
| 2 | Secret sourcing & rotation | `Maxio:ApiKey` comes from environment variables or user-secrets, never from `appsettings*.json` (keys may appear there only with empty values). The DI singleton captures `BasicAuthCredentials` once, on first resolve, so a rotated key takes effect **only after a process restart**. The task asks for no rotation without a restart. If one is needed later, switch to `options.BasicAuthProvider` (`CredentialProvider<BasicAuthCredentials>`, asked on every request) reading `IOptionsMonitor` |
| 3 | Total timeout budget | The caller-facing budget is **30 s** per `/api/*` request. A linked `CancellationTokenSource(30 s)` over `HttpContext.RequestAborted` is passed as `cancellationToken` to every SDK call in the request. The SDK's own `Retry.Timeout` and retry count are set (per the companion) so retries fit inside that 30 s and do not extend it. Maxio's server cut-off is 120 s (rule `maxio-c4:every-request.31`), so a write that our budget cancels may still complete server-side. That case goes through §UNKNOWN OUTCOMES |
| 4 | Write-retry ownership | `RetryOptions.Default().HttpMethodsToRetry` = GET, HEAD, PUT, OPTIONS (source). The SDK may resend `ListProductsForProductFamily`, `ReadCustomerByReference`, `ListCustomerSubscriptions` and `FindSubscription`. It **never** resends `CreateCustomer` or `CreateSubscription` (POST), and the plan must not add POST to that list. The app owns any write re-attempt, and only after reconciliation proves the first one did not land |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: no key member on the record. The natural key is `CreateCustomer.Reference` (Maxio allows one customer per reference: remarks, rule `maxio-c4:createCustomer.1`). Reconcile with `ReadCustomerByReference`. `CreateSubscription`: no key member. Reconcile through `CreateSubscription.Reference` (subscription reference) with `FindSubscription`. Whether Maxio enforces uniqueness of subscription `reference` is **UNVERIFIED** (no rule states it), so the app-side claim is the only refusal. `Idempotency-Key` is not a key |
| 6 | Observability | Information: subscribe outcome with customer reference, Maxio customer id, subscription id, plan handle and state. Warning: Maxio 4xx refusals with operation name, status and `errors[]` text. Error: 5xx, connection or timeout failures, `ResponseDeserializationException`, and unknown outcomes (with the reference used to settle them). The generated error models (`ErrorListResponse1`, `CustomerErrorResponse1`) carry **no correlation-id field**, and the map names no request-id header. The correlation key in our logs is our own customer/subscription `reference`, which is searchable in Maxio. Never log email or names |
| 7 | Sensitive data | **Yes:** `CreateCustomer` carries `email`, `first_name` and `last_name` (PII). `LogRequestBody` stays off. `options.Logging.LoggerFactory` is assigned explicitly (DI supplies the container's), which leaves `MAXIO_ADVANCED_BILLING_LOG` unarmed. There are no form bodies, so the deny-list is not needed. Our own logs never echo request bodies. No card or bank data is in scope |
| 8 | Environment selection | Only the `Production` group is touched (`Ebb` is unused). `Environment = ServerEnvironment.Us` (default). The task gives no binding key for EU (see §6). ## 6. Assumptions & Blockers

**Blockers**

1. **The claim store does not outlive the process in this environment.** With `UseOnlyInMemoryDatabase=true`, `CatalogContext` is EF InMemory, so claims are lost on restart and are per-instance if PublicApi is scaled out. The codebase's durable path is `CatalogContext` on SQL Server (`UseOnlyInMemoryDatabase=false`), and that is where the claims belong in production. Mitigation in this plan: every create first reconciles against Maxio by reference (`ReadCustomerByReference`, `FindSubscription`), so after a restart the provider-side reference stops a duplicate. The window a lost claim leaves open is two concurrent requests across separate instances. Proceeding (headless). **Done:** hand-written migration `20261113120000_AddBillingClaims` (plus the model-snapshot entry) creates `BillingClaims` with the primary key on `Key` for the SQL Server path.
2. **The SDK reference only builds on this machine.** The ProjectReference points into this plugin's install directory, so CI and teammates without the plugin at the same path cannot build PublicApi. The SDK is not on NuGet. Report this at hand-over.

**Assumptions**

1. The task's env vars (`MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_DEFAULT_PRODUCT_FAMILY`) must reach the `Maxio:` keys. They do not do so on their own: `AddEnvironmentVariables` maps `Maxio__ApiKey`, not `MAXIO_API_KEY`. **Decided:** `MaxioServiceCollectionExtensions.AddMaxioEnvironmentVariableFallback` (called first in `Program.cs`) maps `MAXIO_API_KEY`/`MAXIO_SITE_SUBDOMAIN`/`MAXIO_DEFAULT_PRODUCT_FAMILY`/`MAXIO_ENVIRONMENT` onto `Maxio:ApiKey`/`Subdomain`/`ProductFamilyHandle`/`Environment` as the **lowest-precedence** source, so user-secrets (used in development; loaded from these variables), `Maxio__*` and appsettings all win. Values are never hard-coded or written into the repo.
2. `MAXIO_ENVIRONMENT` has no `Maxio:` binding key in the task. The SDK's environments are `Us`/`Eu`, with no sandbox. The plan keeps `ServerEnvironment.Us`. "Sandbox" means the sandbox **site** (`Maxio:Subdomain`). **Decided:** an optional `Maxio:Environment` key (`US` default, `EU`) fed by `MAXIO_ENVIRONMENT` selects `ServerEnvironment.Us`/`Eu`, and `Site`/`BaseUrl` are set on the matching options object (`MaxioServiceCollectionExtensions.BuildClientOptions`). Any other value fails startup validation.
3. One Maxio subscription per user per product family. A second `POST` for a different plan by a user who is already subscribed answers 409. Plan change (`MigrateSubscriptionProduct`) is out of scope. **Decided:** a `canceled`/`expired` subscription answers 409 ("reactivation is not supported here"; `SubscriptionBillingService.Existing`). Resubscribing would need a new subscription reference (a generation suffix) and is out of scope.
4. `CreateCustomer` requires non-null `FirstName`, `LastName` and `Email`. The JWT carries only `ClaimTypes.Name` (the user name, which is the email in eShopOnWeb). **Decided** (`SubscriptionBillingService.ResolveContactAsync`): the e-mail comes from `UserManager<ApplicationUser>.FindByNameAsync(name).Email`, falling back to the name when it is a valid address (otherwise 400). eShopOnWeb accounts have no personal names, so first name = the e-mail's local part (max 50 chars) and last name = `Customer`. Whether Maxio accepts empty strings is **UNVERIFIED**, so always send non-empty values.
5. The customer reference is built from the user **name**, not the Identity user Id: InMemory identity is reseeded on restart, while Maxio keeps the customer. **Decided** (`BillingReferences`): `eshop-cus-{sha256 hex[0..32]}` and `eshop-sub-{sha256 hex[0..32]}`. The prefix avoids collisions, and the hash keeps e-mail addresses out of references and logs (42 chars, within the 64-char claim key).
6. The task states both plans need no payment method. The plan sends no payment fields and no `next_billing_at`, so charges are assessed at creation (rule `maxio-c4:createSubscription.10`). If the site's product settings require payment after all (rule `maxio-c4:createSubscription.7`), Maxio will refuse with 422. That is surfaced as 422 with `errors[]`; it is not worked around. **Verified on the first sandbox call:** with automatic collection Maxio answered 422 "No payment method was on file for the $299.00 balance". Resolved through the documented `payment_collection_method` field (see the CreateSubscription contract row): subscriptions are created with `remittance` (collected by invoice) and come back `active`.
7. `receives_invoice_emails` is left at its default `true` (rule `maxio-c4:createSubscription.47`), so the sandbox site may email seeded users' addresses. **Decided:** leave the default. Invoice e-mails are how remittance-collected subscriptions get paid, so suppressing them would break collection.
8. Maxio's `uniqueness_token` (rules `maxio-c4:every-request.36`–`.40`) is not a member of the SDK's create request models, so it is not sent. Sending it via `AdditionalProperties` would go past the map and is not planned. Dedupe relies on the claim plus `reference`.
9. Rate and concurrency: Maxio queues more than 4 concurrent calls per subdomain (rule `maxio-c4:every-request.26`). Plan paging runs sequentially, and the SDK's GET retries cover 429 (rule `maxio-c4:every-request.28`).
10. Webhooks (`signup_success`, etc.) are out of scope. `GET /api/my-subscriptions` reads live state from Maxio, so renewals and state changes need no local sync.
