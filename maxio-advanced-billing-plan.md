## Assumptions & Blockers

- Minor assumption: one subscription per authenticated user and offered product handle; different plans may coexist. A repeat POST returns the existing provider subscription, including its actual state, instead of creating another.
- YOUR CALL — not in the map: use provider default product price with PaymentCollectionMethod=CollectionMethod.Remittance for invoice billing without a captured card; the public request does not accept custom prices, currency overrides, numeric customer/product IDs, external references, or payment information. Names may be supplied as profile data, but email and ownership come from the authenticated account.
- Deployment requirement: local InMemory configuration is supported for development and concurrency tests, but it cannot preserve claims across process restarts. Production-grade cross-process durability requires the repository's existing SQL CatalogContext deployment with the new migration applied. Provider reconciliation protects local restart recovery; it cannot create durable local claims in a volatile database.
- Live sandbox verified: both seeded plans return RequireCreditCard=false; default automatic collection rejected the initial balance with typed 422. SDK-supported CollectionMethod.Remittance successfully created both Basic and Pro subscriptions, active, with provider USD prices and next assessment timestamps. Repeated Pro POST returned the same subscription ID; account read returned both enrollments. The supplied seeded handles remain verification arguments, never application constants.
