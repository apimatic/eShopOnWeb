# Maxio Advanced Billing — subscription billing plan

Additive capability on eShopOnWeb PublicApi. Existing Catalog → Basket → Order checkout stays. Maxio is the billing system of record for recurring plans only.

Configuration is bound from the `Maxio` section. Binding keys (never raw environment-variable names in code): `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, optional `Maxio:BaseUrl`. Catalog handles and numeric ids are not constants. The family handle used on the wire is `handle:` plus the value of `Maxio:ProductFamilyHandle` (the configured value is the bare handle).

## 1. Scope & sequence

Exemplar to imitate for a JWT endpoint: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (`IEndpoint`, `MapPost("api/...")`, `[Authorize(..., AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, response type derived from `src/PublicApi/BaseResponse.cs`). Routes use the same no-leading-slash form: `api/subscription-plans`, `api/subscriptions`, `api/my-subscriptions`.

1. **SDK reference.** `ProjectReference` the plugin SDK project `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` from the project that compiles the client. Do not copy SDK source into the repo. The reference is machine-local to this plugin install.
2. **Client singleton.** Bind `Maxio`, fail fast on blank required keys, construct one `MaxioAdvancedBilling.MaxioAdvancedBillingClient` for the process (section Client, auth, server below). No component, usage, or payment-profile operation.
3. **`GET api/subscription-plans`.** `client.ProductFamilies.ListProductsForProductFamily` for the configured family, paging until a short page or the page cap. Returns handle, name, price, interval. Sets `truncated` when the cap cuts the list.
4. **`POST api/subscriptions`.** Caller sends a plan handle. Before any write, that handle must be one `Product.Handle` the list walk just collected. Then, in order: customer claim → `Customers.ReadCustomerByReference` or `Customers.CreateCustomer` → record the customer claim → subscription claim → `Subscriptions.CreateSubscription` → record the subscription claim. Response reads plan, price, state, next billing date off `SubscriptionResponse`.
5. **`GET api/my-subscriptions`.** `Customers.ReadCustomerByReference` for the caller. No customer (HTTP 404 on that read) → empty list, and this GET does not create a customer. Otherwise `Customers.ListCustomerSubscriptions` with `Customer.Id` from that response. Same plan/price/state/next-billing readback.
6. **Tests.** Duplicate primary-key claim before either write. Connection-failure tests named in UNKNOWN OUTCOMES. Load `maxio-advanced-billing:dotnet-testing` before stubbing the client.

`CreateSubscription.Components` is optional and is left unset. No component operation is on the list or subscribe path.

### DUPLICATE CLAIMS

Claim → SDK call → record the result. Insert the claim and `SaveChangesAsync` **before** the SDK call. Release the claim (delete the row) only when the provider **refuses** the call (answered error, and the reconcile read shows the write is absent). A connection failure leaves the row in `unknown` until a later call’s re-read settles it. Second caller: completed → re-read and return the current plan/price/state/next billing date (HTTP 200); in progress → do not call the SDK, HTTP 409 via existing `DuplicateException` (`src/PublicApi/Middleware/ExceptionMiddleware.cs`); unknown → re-read, and if still absent keep the row and return unknown (do not create again).

The claim entity’s **primary key is the claim key string**. Do not use `BaseEntity`’s `int Id` plus a unique index: the in-memory provider enforces primary keys, and a unique index may not be enforced. Verified on `Microsoft.EntityFrameworkCore.InMemory` 8.0.2: a second `SaveChangesAsync` of the same string key throws `System.ArgumentException` (`An item with the same key has already been added. Key: {key}`) with no inner exception.

## 6. Assumptions & Blockers

**Assumptions**

- Sandbox traffic is `ServerEnvironment.Us` plus `Maxio:Subdomain` on the Production US host, or `Maxio:BaseUrl` when set. `MAXIO_ENVIRONMENT` is not an SDK setting and is not a binding key. `ServerEnvironment.Eu` and the `Ebb` group are out of scope.
- Caller user id, email, and given/family name are taken from the authenticated PublicApi JWT. Which claims, and how a single display name fills required `FirstName` and `LastName`, are YOUR CALL — not in the map. `Email`, `FirstName`, and `LastName` are `required` on `CreateCustomer`. The customer `Reference` is that stable user id.
- Subscription `Reference` format is YOUR CALL — not in the map — and must be a pure function of that user id and the product handle, stable across retries, and the primary key of the subscription claim.
- `GET api/my-subscriptions` with no Maxio customer returns an empty list and does not create one. HTTP status for an `unknown` claim after a failed re-read is an error that leaves the claim in place (not 201, not a second create). In-progress duplicate is 409 via `DuplicateException`.
- Seeded products do not require a payment method. The call omits every payment-profile field. `RequireCreditCard == true` on a listed product blocks `CreateSubscription` for that handle. Null or false proceeds without a card, with `CreateSubscription.PaymentCollectionMethod` set to `CollectionMethod.Remittance` (`remittance`). The default automatic collection charges the opening balance at signup and returns 422 "No payment method was on file" even when `RequireCreditCard` is false. Remittance is the Relationship Invoicing method documented on that member for invoicing the balance instead of capturing a card. `NextBillingAt` and `DeferSignup` stay unset.
- `ReadProductFamilyRequest.Id` is `int` while that method’s remarks also mention `handle:my-family`. The list operation’s `ProductFamilyId` is the `string` that documents the `handle:` prefix, so the plan uses that and does not call `ReadProductFamily`.
- `ListCustomerSubscriptions` returns one list and has no page member. Remarks say it lists all of that customer’s subscriptions. No extra cap field.
- A missing customer reference’s HTTP status on `ReadCustomerByReference` is **UNVERIFIED** (Case B, no 404 accessor). Only 404 is treated as absent.
- Duplicate `CreateSubscription.Reference` rejection is **UNVERIFIED**. The claim is what stops the second send; `FindSubscription` settles an unknown outcome.
- In-memory claim rows live only as long as the process (`UseInMemoryDatabase("Catalog")`). The task accepts that. It is not a blocker.
- The metered component on the family is not an input or output of the operations above, so no component call is in this plan.
- Public DTO plan identity is `Product.Handle`. Numeric product ids are not accepted from the caller and are not hard-coded. `Customer.Id` is used only as the runtime `CustomerId` argument to `ListCustomerSubscriptions`.

**Blockers**

None.
