Business rules that change this plan (by id):
- Customer: a reference must be unique on the site (`createCustomer` first rule); create customers once, then reference them by id or reference. `createSubscription` rule "customer_attributes creates a new customer, pass customer_id/customer_reference for an existing one to avoid a duplicate" => always create the customer first and pass `CustomerId`, never `CustomerAttributes`.
- No card: a paid product needs a payment method unless collection is invoice-based; valid values are `remittance`/`automatic`/`prepaid` on Relationship Invoicing and `invoice`/`automatic` on Statements (`every-request.42`, `createSubscription` collection-method rules) => read the site and pick `remittance` or `invoice`.
- Without `next_billing_at` initial charges are assessed at creation (`createSubscription`); with a future one nothing is charged until that date. We omit it.
- Pause: refused when `next_billing_at` is within 24 hours, and 422 "not eligible to be put on hold" (`pauseSubscription`). Resume: only on-hold; after the renewal date it behaves like a reactivation and charges (`resumeSubscription`). Cancel: 422 if already canceled; no schedule params = immediate cancel (`cancelSubscription`). Reactivate: only canceled / unpaid / trial_ended (`reactivateSubscription`).
- Migrate: only active or trialing; same-product target fails; a balance with no card on file gives 422 (`migrateSubscriptionProduct`).
- Next billing date: invalid dates silently roll over (Feb 30 becomes Mar 2) so validate first; response carries no `next_billing_at`, verify through `current_period_ends_at` (`updateSubscription`). Dates without a time are interpreted at noon in the site time zone, timestamps with offset are absolute (`every-request.14`, `every-request.16`).
- Usage: `since_date`/`until_date` default to midnight, so one day D is `since_date=D&until_date=D+1`; metered components only (`listUsages`). Max 200 per page, default 20 (`every-request.23`).
- Account balances are in cents (`readAccountBalances`).
- Currency price: currency must already be defined on the site; prices must cover every role of the price point; custom price points not allowed; update requires an existing price (`createProductCurrencyPrices`, `updateProductCurrencyPrices`).
- Product create: family must exist first (`createProduct`); handles in paths need the `handle:` prefix (`createProduct` handle rule); archived products are omitted from lists unless `include_archived` (`listProducts`).
- Concurrency: at most 4 concurrent calls per subdomain (`every-request.26`).

Client construction / auth / server facts (source `sdk-map.md` *Getting a client*, *Servers & auth*; `Servers/ProductionOptions.cs`):
- Constructor: `new MaxioAdvancedBilling.MaxioAdvancedBillingClient(HttpClient httpClient, MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions options)`; DI helper `services.AddMaxioAdvancedBillingClient(options => ...)` (`ServiceCollectionExtensions.cs`).
- Auth: HTTP Basic. `options.BasicAuth = new MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials { Username = <Maxio:ApiKey>, Password = "x" }` (map: username is the API key, password is `x`). Leave the SDK's own env vars (`MAXIO_ADVANCED_BILLING_BASIC_AUTH_USERNAME/_PASSWORD`) unused: the settings come from `Maxio:` only, and a value set in code wins.
- Environments: `MaxioAdvancedBilling.Servers.ServerEnvironment` has only `Us` (default, `https://{site}.chargify.com`) and `Eu` (`https://{site}.ebilling.maxio.com`). There is NO sandbox member: the sandbox is a separate site subdomain on the same hosts. `Maxio:Environment` (`US` in the supplied env var) maps `US`/`EU` (case-insensitive) onto these.

1. Steps 0 and 1-11 resilience: the retry list covers PUT and not POST/DELETE, the default per-attempt timeout is far longer than a request budget, and per-attempt timeouts are not a total; a handler that chains several SDK calls compounds all of that. **MUST load maxio:dotnet-configuration-resilience**
7. Step 3 and writes generally: a write can succeed at Maxio and still throw in this process; a retry or double submit duplicates the customer or subscription. **MUST load maxio:dotnet-configuration-resilience**

### DUPLICATE CLAIMS

Claim store: table `MaxioOperationClaim` in `CatalogContext` (entity + `IEntityTypeConfiguration` in `src/Infrastructure/Data/Config`, migration in `src/Infrastructure/Data/Migrations`), columns `ClaimKey` (string, PRIMARY KEY), `Attempt` (string, GUID, doubles as the Maxio `Reference` for subscribes), `Result` (nullable string: Maxio id once known), `CreatedUtc`. The second claim for a key violates the primary key: `DbUpdateException` from `SaveChangesAsync` (the codebase's existing refusal style, mapped to 409 like `DuplicateException`). Released (row deleted) when the provider refuses the call, and for in-flight claims when the outcome is recorded; a claim older than 5 minutes with no `Result` is expired (deleted then retaken) so a crash cannot block a key forever; the customer mapping row is the one claim that is kept (it is the durable user -> Maxio customer id mapping).

## 7. Assumptions & Blockers

Assumptions (all minor unless marked):
- **A1 (decided: implemented in `MaxioBillingService.CreatePlanAsync`/`EnsureFamilyAsync`)** A plan's brand is stored as the Maxio **product family**: one family per catalog brand (family name = brand, handle = slug of brand). The user's request gives plans a brand but the SDK product model has no brand field. Plans offered = all non-archived products across all families; the plan DTO returns `{id, handle, name, monthlyPrice, priceInCents, brand (= ProductFamily.Name), interval}`.
- **A2 (decided as written; implemented in `EnsureCustomerAsync`)** Customer maps to the JWT identity by `Customer.Reference` = `User.Identity.Name` (the only identity claim in the token). One Maxio customer per user, created once under the `customer:{userName}` claim; every subscription for that user uses `CustomerId`. A user name that is not an e-mail is used as-is for `Email`; `FirstName`/`LastName` are derived from the local part (placeholder `Shopper` when empty) because the SDK marks them required.
- **A3 (decided as written; implemented in `SubscribeAsync`)** No-card subscribe uses `CollectionMethod.Remittance` when `Site.RelationshipInvoicingEnabled == true`, else `CollectionMethod.Invoice` (valid sets per site architecture, `every-request.42`). UNVERIFIED against the sandbox: whether a paid product on a site with `request_credit_card`/`require_credit_card` set still refuses a signup with no payment method. New plans created here set `RequireCreditCard = false`. If the sandbox refuses a pre-existing plan, subscribe answers 422 with Maxio's reason. A paid plan with invoice collection leaves an open invoice, so `paid` is `false` right after subscribing: that is the expected `paid` semantics.
- **A4 (decided as written; implemented in `BillingException` + `ExceptionMiddleware`)** Ownership failure and unknown subscription both answer the same 404 (no information leak). Plan-handle / brand / currency / date validation failures answer 400 or 422 with a reason; state-rule failures 409 with a reason; Maxio 422 payloads pass their first message through as the reason.
- **A5 (decided as written; implemented in `TakeClaimAsync`)** Concurrent-write claims are in-flight only (a shopper may legitimately hold several subscriptions, including two to the same plan, sequentially). The claim is not a "one subscription per plan" rule.
- **A6 (decided as written; implemented in `SetNextBillingDateAsync`)** Next billing date: the date is sent as `new DateTimeOffset(date, 12:00, UTC)` (noon UTC stays on the same calendar date for every site offset from UTC-12 to UTC+11; the map offers no site time-zone field to do better). Verified after the write through `CurrentPeriodEndsAt` (the response carries no `next_billing_at`); a mismatch is reported as a failed write, never as success. UNVERIFIED which of `CurrentPeriodEndsAt`/`NextAssessmentAt` the sandbox updates.
- **A7 (decided as written; implemented in `SwitchAsync`)** Switch on active/trialing uses `MigrateSubscriptionProduct` with `PreservePeriod` left at its default (false: billing period resets, full price of the new plan is charged now). This is Maxio's documented default; send `PreservePeriod = true` instead if a prorated switch is wanted.
- **A8 (decided as written; implemented in `SetCurrencyPriceAsync`)** Admin currency price takes `price` in major units. `CreateProductCurrencyPrice.Price` is an `int`: a whole number is created directly; a fractional price is created with the rounded integer and then corrected with `UpdateProductCurrencyPrices` (`UpdateCurrencyPrice.Price` is `double`), both under the same `currency:` claim. Only the `Baseline` role is sent (new plans have no trial or setup fee). The price point priced is the product's default price point (`Product.DefaultProductPricePointId`).
- **A9** New plan fields: `Handle` = lower-case slug of `name`; `Description` = name (required by the model); `Interval = 1`, `IntervalUnit = Month`; `PriceInCents = round(monthlyPrice * 100)` with monthlyPrice > 0; `AutoCreateSignupPage` is NOT sent (a Catalog-experience site refuses it, `createProduct` rule).
- **A10** The claim table needs one EF migration (`src/Infrastructure/Data/Migrations`); the in-memory provider used by the tests needs none.
- **A11** Tests: Maxio is not stubbed. Sandbox credentials reach the test host through user-secrets / `Maxio__*` env vars. Because step 0 fails the host at startup when `Maxio:` settings are missing, EVERY existing `PublicApiIntegrationTests` test also starts only when those settings exist; the main agent must decide how the test project supplies them (it cannot be `appsettings.test.json`, which is a repo file). User-secrets are only loaded by the default host builder in the `Development` environment; `WebApplicationFactory` hosts run as `Development` unless overridden (UNVERIFIED here, check when the first test runs).

Blockers (expected provider refusals the plan cannot design around):
- **B1 (confirmed on the sandbox: `non_primary_currencies` is empty, so the happy path cannot be exercised; the 422 refusal path is)** Feature 9 needs the currency to be defined on the Maxio site (multi-currency enabled and the currency configured): the map has no operation to define site currencies (`Sites` has only `ReadSite`, `ClearSite`, `ListChargifyJsPublicKeys`), and `createProductCurrencyPrices` refuses an undefined currency. The plan checks `Site.NonPrimaryCurrencies` first and answers 422 "currency not configured on the site" otherwise. For the sandbox test the site must already have a non-primary currency enabled; ask the user which one, or accept that the happy path cannot be exercised end to end.
- **B2 (decided; verified against the sandbox)** Switching a **canceled** subscription: the migration endpoint refuses anything but active/trialing (`migrateSubscriptionProduct` rule; `Api/SubscriptionProducts.cs` remarks), and the SDK offers no documented way to switch a canceled one other than `UpdateSubscription.ProductHandle`, whose docs do not state which states accept it. The plan uses `UpdateSubscription.ProductHandle` for canceled and every other non-active state and leaves the subscription canceled (a restart is the separate feature). The sandbox accepted `UpdateSubscription.ProductHandle` on a canceled subscription: it stays canceled on the new plan. (Alternative, not used) is reactivate then migrate (ends the switch with an `active` subscription, charges per Maxio's reactivation rules); confirm which the user wants before relying on it.
