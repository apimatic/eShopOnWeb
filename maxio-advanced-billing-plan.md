# Maxio Advanced Billing plan: eShopOnWeb subscriptions (PublicApi)

Skill: `maxio-advanced-billing:dotnet-integrate-maxio-advanced-billing`. SDK root (plugin-relative): `sdk/dotnet/`. Every `Source` path below is relative to that root. The map is `sdk/dotnet/sdk-map.md` plus `sdk/dotnet/map/operations/*.md`.

Repo facts read for this plan (read-only):
- The JWT carries exactly one identity claim, `ClaimTypes.Name` = the user's `UserName`, plus `ClaimTypes.Role` (`src/Infrastructure/Identity/IdentityTokenClaimService.cs:30`). It carries no Identity user-id claim. Seeded users have `UserName == Email` (`src/Infrastructure/Identity/AppIdentityDbContextSeed.cs:20,24`).
- Endpoint convention: `IEndpoint<IResult, TRequest, ...>` with `AddRoute` + `HandleAsync`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<T>().WithTags(...)`, request/response records split into `{Endpoint}.{Request|Response}.cs`. Exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`.
- The codebase already refuses duplicates by throwing `DuplicateException`, which `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps to 409. Every other exception becomes a 500 **with `exception.Message` written to the response body**.
- Records store: `src/Infrastructure/Data/CatalogContext.cs` (EF Core 8.0.2). Configs come from `ApplyConfigurationsFromAssembly`; exemplars are in `src/Infrastructure/Data/Config/`. In-memory database `"Catalog"` applies when `UseOnlyInMemoryDatabase` is set (`src/Infrastructure/Dependencies.cs:19-22`).
- `src/PublicApi/PublicApi.csproj` already has a `UserSecretsId`. `dotnet --version` in the repo root resolves to `10.0.400`, which is needed because the SDK builds with `LangVersion 14`.

That covers a drifted or malformed **2xx** response (a missing `required` member) and a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape. `ResponseDeserializationException` is an `ApiException` that keeps the HTTP status and names the target type, but it is **not** an `ApiException<TError>`. A catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

In this scope, the `required` members whose absence would trigger it are `ProductResponse.Product`, `CustomerResponse.Customer` and `ErrorListResponse1.Errors`. On C2 and S1, a `ResponseDeserializationException` on a 2xx means the write **succeeded**. Settle it through the unknown-outcome path; never report it as a failure.

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions** (surface to the user if any is wrong):
1. **User identity (decided at implementation):** the JWT's `ClaimTypes.Name` is resolved through `UserManager.FindByNameAsync` (`src/PublicApi/SubscriptionEndpoints/SubscriberResolver.cs`). The claim primary key is the Identity user id. The Maxio customer reference is keyed on the **normalized user name**, hashed, and not on the id: a live restart showed the in-memory Identity store re-seeds users with new ids, which would orphan the customer. The subscription reference is a fresh `eshop-sub-{guid}` per attempt, stored on the claim row before S1.
2. **Customer fields for `CreateCustomer` (decided):** `Email` = the Identity user's e-mail. `FirstName` and `LastName` are derived from the e-mail local part (`MaxioSubscriptionBillingService.DeriveNames`), with `LastName` = "Customer" when there is a single token.
3. **One subscription per user** through this app: the claim primary key is the user, as directed. A second `POST /api/subscriptions` for any plan returns the existing subscription (Active) or 409 (in progress). Plan changes and cancellation are out of scope.
4. **`MAXIO_ENVIRONMENT` is not bound.** The task fixes the binding keys to `ApiKey`, `Subdomain`, `ProductFamilyHandle` and `BaseUrl`. The SDK has no sandbox environment, only `Us`/`Eu` hosting regions, so the client always uses `ServerEnvironment.Us` and the sandbox is selected by subdomain. If the site is EU-hosted, this must change.
5. **No payment fields are sent**, relying on the task's statement that both plans require no payment method (S1-pay, UNVERIFIED).
6. **Next billing date = `Subscription.CurrentPeriodEndsAt`**, per its doc text. `NextAssessmentAt` is also returned for transparency (YOUR CALL whether to expose it).
7. **SDK reference is machine-local:** the `<ProjectReference>` targets this plugin's install path, so CI or another machine needs the plugin installed and the reference re-pointed. The repo resolves .NET SDK `10.0.400`, which the SDK's `LangVersion 14` needs; if that changes (`global.json` pins `8.0.x` with `latestFeature`), the SDK project will not compile.
8. **In-memory store:** claim rows do not survive a restart. Duplicate protection across restarts then rests on C2's provider-unique customer `reference` and the step 5(d) C3 adoption check, not on the claim. This is acceptable for the in-memory dev mode; SQL Server deployments need a migration for the new table, which the main agent must add (the in-memory provider ignores migrations).
