Steps:

1. Settings + client: `MaxioSettings` bound from section `Maxio` (keys `ApiKey`, `Subdomain`, `ProductFamilyHandle`, `BaseUrl`); fail-fast validation; singleton `MaxioAdvancedBillingClient` registered once (Program.cs). Reference the SDK csproj via `dotnet add reference` (local to this machine; never copy SDK source).
2. Persistence: two claim entities in `CatalogContext` (see DUPLICATE CLAIMS) + EF Core config + a SQL Server migration (ignored by in-memory).
3. `GET /api/subscription-plans` - `ProductFamilies.ListProductsForProductFamily` (family addressed as `handle:` + configured handle), paged manually, archived excluded. Maps to DTOs (handle, name, description, price, interval, trial/setup facts).
4. `POST /api/subscriptions` (body: plan handle only) - resolve user from token -> validate plan handle against step 3's fresh result (CROSS-OPERATION INVARIANTS) -> ensure customer (claim -> `Customers.CreateCustomer`, reconcile via `Customers.ReadCustomerByReference`) -> claim subscription -> `Subscriptions.CreateSubscription` (reconcile via `Subscriptions.FindSubscription`) -> record -> confirm via response (plan, price, state, next billing date).
5. `GET /api/my-subscriptions` - read the caller's subscription rows from the app store; for each completed row confirm live data with `Subscriptions.ReadSubscription`; settle `Unknown` rows via `Subscriptions.FindSubscription`.
6. Tests (PublicApiIntegrationTests style + unit tests with an `HttpClient` stub).

### DUPLICATE CLAIMS

Store = `CatalogContext` (the store the codebase keeps its records in). A claim is an `Add` + `SaveChanges` of a row whose primary key is the dedupe identity; EF Core InMemory and SQL Server both refuse a second row with the same key. Order for each row: claim -> SDK call -> record the result; release (delete the row) when the provider definitively refuses the call.

## 6. Assumptions & Blockers

Blockers: none. Every capability needed is in the map: list family plans (`ListProductsForProductFamily`, family addressable as `handle:<handle>`), customer create + lookup by reference, subscription create + find by reference + read, all with `Reference` fields for reconciliation. A persistence home that outlives the process exists (`CatalogContext` + SQL Server migration); in-memory dev loses rows on restart by design and the plan reconciles through the `Reference` lookups.

Assumptions:

- A1. Identity: the JWT has only the user-name claim; the handler resolves it with `UserManager<ApplicationUser>` to the Identity user id (the stable key, used as claim PK and `CreateCustomer.Reference`) and email. Unknown user -> 401/404.
- A2. `CreateCustomer` requires first name, last name and email, but eShop users have only email: first/last name will be derived from the email local part (fallback to the user name) - needs confirmation if real names exist elsewhere.
- A3. No restart-free credential rotation is required.
- A4. `Maxio:` defines no server-environment key, so `Environment` is fixed to `Us` (the sandbox host `https://{site}.chargify.com` pattern). `Maxio:BaseUrl` is applied to the Us node only.
- A5. Dedupe scope: one subscription per (user, plan handle). A user subscribing to a second, different plan is allowed; the same user + same plan twice (double-click) returns the first. If "one subscription per user in total" is wanted instead, the claim PK becomes `UserId` alone - say so.
- A6. Timeout/page-cap numbers are code constants (no extra `Maxio:` binding keys invented).
