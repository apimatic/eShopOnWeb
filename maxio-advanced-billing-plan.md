## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Config: bind `Maxio` section (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`) to an options class, validate on start, build `MaxioAdvancedBillingClientOptions` once, register via `services.AddMaxioAdvancedBillingClient(...)`. Env-var-to-user-secrets loader script (outside the repo's tracked secrets). | none (client construction) |
| 2 | Store: two EF entities in `CatalogContext` + configurations: `MaxioCustomerLink` (PK `UserId`) and `UserSubscription` (composite PK `UserId`+`PlanHandle`) | none |
| 3 | List plans (`GET /api/subscription-plans`): read all products of the configured product family by handle, drop archived, map to plan DTO (handle, name, description, price cents, interval, interval unit). Same read is the offered-set oracle for step 4. | `Products of family`: `ProductFamilies.ListProductsForProductFamily` (paged by hand) |
| 4 | Subscribe (`POST /api/subscriptions`): resolve caller from JWT `ClaimTypes.Name` to `ApplicationUser` (Id, Email) -> validate requested plan handle against the step-3 offered set (reject with 400/422 BEFORE any claim or SDK write) -> claim customer row (PK `UserId`) -> `Customers.ReadCustomerByReference` (reconcile) / `Customers.CreateCustomer` -> record Maxio customer id -> claim subscription row (PK `UserId`+`PlanHandle`) -> `Subscriptions.CreateSubscription` (no payment info) -> record subscription id/state -> return plan/price/state/next billing date. | `ProductFamilies.ListProductsForProductFamily`, `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`, `Subscriptions.CreateSubscription`, (settle) `Customers.ListCustomerSubscriptions` |
| 5 | My subscriptions (`GET /api/my-subscriptions`): caller from token -> stored `MaxioCustomerLink.MaxioCustomerId` (never from the request) -> list that customer's subscriptions (state, next billing date, product, price). No link = empty list, no SDK call. | `Customers.ListCustomerSubscriptions` |
| 6 | Error mapping, logging, tests (stubbed `HttpClient` seam), README note. | all |

Capabilities checked against the map, all present: customer create (`Customers.CreateCustomer`) and lookup by reference (`Customers.ReadCustomerByReference`), subscription create with product handle + customer id/reference and no payment profile (`Subscriptions.CreateSubscription`), list products by product-family handle with price (`ProductFamilies.ListProductsForProductFamily`, `ProductFamilyId` accepts `handle:<handle>`), list a customer's subscriptions with state/next billing/product/price (`Customers.ListCustomerSubscriptions`), DI registration with base URL override (`AddMaxioAdvancedBillingClient`, `options.Server.Production.Us.BaseUrl`). No capability blocker.

## 6. Assumptions & Blockers

**Blockers**

1. RESOLVED: `global.json` rollForward changed to `latestMajor` (run with `DOTNET_ROLL_FORWARD=Major`). Original note: `global.json` pins `sdk.version 8.0.x` with `rollForward latestFeature`, but the installed .NET SDKs are 9.0.309 and 10.0.x only (no 8.x), so `dotnet build` of the untouched repo is expected to fail SDK resolution; and the Maxio SDK source needs `LangVersion 14` (a .NET 10 SDK). Building at all needs a decision about `global.json` (an edit to an existing project file, which I did not make) or an installed 8.0 SDK plus the 10 SDK. Main agent: verify the baseline build and decide; the app itself stays on `net8.0`.
2. `MAXIO_ENVIRONMENT` has no binding key: the task fixes the config keys to exactly `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`, and the SDK's environment (`ServerEnvironment.Us`/`Eu`) is not one of them. Plan: `Environment` stays the SDK default `Us` (a sandbox is a `{site}` on the `Us` host); the value is loaded into user-secrets but nothing reads it. If an EU host is ever needed it goes through `Maxio:BaseUrl`.

**Assumptions**

1. Caller identity: the JWT has only `ClaimTypes.Name` (username) and roles (read in `IdentityTokenClaimService`). The user id is resolved with `UserManager<ApplicationUser>.FindByNameAsync(name)`; Maxio customer `reference` = `ApplicationUser.Id`, email from `ApplicationUser.Email`. A token whose user no longer exists returns 401/404.
2. `CreateCustomer` requires `FirstName`, `LastName`, `Email`, and `ApplicationUser` has no name fields. YOUR CALL — not in the map: derive first name from the username/email local part and use a fixed placeholder last name; surface in the response that names are placeholders. Needs user confirmation if real names exist elsewhere.
3. Default subscribe target: the request may omit the plan handle; the default is the handle `eshop-pro` held as a code constant (handles are stable per the task; no extra config key is allowed) and is still validated against the offered set like any other handle. If `eshop-pro` is not offered the request is rejected.
4. Policy (YOUR CALL — not in the map): one subscription per (user, plan). A repeated POST for the same plan returns the stored subscription (200, idempotent); a different offered plan is a separate subscription (no plan-switching logic in scope).
5. Next billing date shown = `Subscription.CurrentPeriodEndsAt` (doc: when the next regularly scheduled charge occurs); `NextAssessmentAt` is returned as a secondary field.
6. UNVERIFIED (only live traffic can settle): that Maxio accepts `CreateSubscription` with no payment profile and no `PaymentCollectionMethod` for these plans (task says payment not required; `Product.RequireCreditCard` is read and logged); that `ReadCustomerByReference` returns 404 for no match; that Maxio does not enforce uniqueness of customer `reference`, which is why the app-side claim is mandatory; that the provider rejects a duplicate subscription `reference` or not (we do not depend on it). A rejection of the no-payment create is a provider-side rejection the plan already expects only if the plans' settings differ from the task; if observed it is reported, not worked around.
7. Product price/state facts come from `Product.PriceInCents` for the offered plans and `Subscription.ProductPriceInCents` for held subscriptions (docs note these can differ after a price change).
8. EF entities live with the existing `CatalogContext` (migrations are ignored in dev in-memory; for a relational deployment a migration would be needed, outside this scope).
9. The metered component `api-call` is not touched (no component allocation in the Subscribe flow); no component operations are planned.

**Implementation decisions recorded after coding**

- `CreateSubscription` sets `PaymentCollectionMethod = Remittance` (found from the live sandbox: the default `automatic` collection answers 422 "No payment method was on file"; the plans need no card, so invoice billing is used).
- The plan handle is required in the request (no hard-coded default plan; handles are never baked into code).
- Stale `Pending` claims (older than 2 minutes) and `Unknown` claims can be taken over; a rotating `ClaimToken` concurrency token lets one taker win.
