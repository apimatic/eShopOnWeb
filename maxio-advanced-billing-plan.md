## 1. Scope & sequence

1. Startup: bind `Maxio:` options, validate, build `MaxioAdvancedBillingClient` once (DI singleton). Operations: none.
2. `GET /api/subscription-plans`: list plans of the configured product family. `client.ProductFamilies.ListProductsForProductFamily` with `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`.
3. `POST /api/subscriptions` (identity from token): resolve user (Identity) -> validate plan handle against step 2's list -> claim customer link -> `client.Customers.CreateCustomer` (or reconcile with `client.Customers.ReadCustomerByReference`) -> record customer id -> claim subscription -> `client.Subscriptions.CreateSubscription` (reconcile with `client.Subscriptions.FindSubscription`) -> record subscription id -> return plan/price/state/next billing date from the response.
4. `GET /api/my-subscriptions`: look up the caller's customer link in the local store; `client.Customers.ListCustomerSubscriptions` for that customer id; filter to the configured product family's plans (see invariants). No link -> empty list, no Maxio call.

Capability check: every needed capability exists in the map. No Blocker for capability. The metered component (`api-call`) is NOT attached at signup (out of the hero flow; see Assumptions). Handles are used everywhere (`product_handle`, `handle:` family prefix); no numeric product/family id is hard-coded.

Local store (EF Core, `CatalogContext`):

| Entity | Key | Columns | Role |
| --- | --- | --- | --- |
| `MaxioCustomerLink` | PK `UserId` (string, max 256; the Identity user id, see Assumptions) | `MaxioCustomerId int?`, `Status` (Claimed / Active), `CreatedUtc` | customer claim + mapping. Row inserted `Claimed` BEFORE `CreateCustomer`; completed after. |
| `MaxioSubscriptionLink` | composite PK (`UserId`, `PlanHandle`) | `MaxioSubscriptionId int?`, `Status` (Claimed / Active), `CreatedUtc` | subscription claim + mapping, one subscription per user per plan. |

Both rows hold a `Claimed` state, so a second caller who loses the insert sees an in-flight or completed result and never reaches the SDK.

> Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The `ProductHandle` sent to `CreateSubscription` must be a non-archived plan the application offers, i.e. one returned for the configured family (and equal to the handle shown to the shopper) | `CreateSubscription` <- `ListProductsForProductFamily` | in `IMaxioSubscriptionService.SubscribeAsync`, before any claim or write: it calls the same plan-list read as `GET /api/subscription-plans` (walk to completion) and rejects a handle not in it (HTTP 422/400 `unknown plan`); a plain `ReadProductByHandle` is not used because it would not prove the product is in this family |
| The `CustomerId` sent to `CreateSubscription` must be the one this app stored for that user (from `CreateCustomer` or reconciled `ReadCustomerByReference`), never caller-supplied | `CreateSubscription` <- `CreateCustomer` / `ReadCustomerByReference` (stored in `MaxioCustomerLink`) | in `SubscribeAsync`: read `MaxioCustomerLink.MaxioCustomerId` after the customer step; request body of `POST /api/subscriptions` has no customer field |

## 4. REQUIRED READING (load all before implementing)

- `maxio:dotnet-error-handling` : every catch ladder, the exception-to-HTTP mapping, reconciliation catches
- `maxio:dotnet-client-initialization` : step 1 client/DI registration
- `maxio:dotnet-authentication` : step 1 Basic auth and fail-fast
- `maxio:dotnet-calling-endpoints` : all calls
- `maxio:dotnet-models` : request bodies and nullable/open-enum responses
- `maxio:dotnet-configuration-resilience` : timeouts, retries, base URL, logging
- `maxio:dotnet-testing` : integration tests with a stubbed `HttpClient`

Hazard row (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 6. Assumptions & Blockers

Blockers: none. Persistence exists (`CatalogContext` + PK refusal), so DUPLICATE CLAIMS stands; all needed operations exist in the map.

Assumptions (the minor ones are proceed-with-default; the first four deserve a user glance):

1. **Caller identity key.** The JWT carries only `ClaimTypes.Name` (user name/email); there is no `NameIdentifier`. Plan: read `ClaimTypes.Name` from the token, resolve the Identity user via `UserManager<ApplicationUser>.FindByNameAsync` (registered in PublicApi Program.cs) and use `ApplicationUser.Id` as the stable user key (`MaxioCustomerLink.UserId`, Maxio customer `reference`) and `Email` for the Maxio customer. Unknown user -> 401. DECIDED/implemented in `CreateSubscriptionEndpoint`/`MySubscriptionsEndpoint` (`UserManager.FindByNameAsync`, `ApplicationUser.Id` as key, unknown user -> 401).
2. **Customer first/last name.** `CreateCustomer` requires `FirstName`, `LastName`, `Email`; Identity users carry only an email. Plan: `FirstName` = email local part, `LastName` = a fixed placeholder (e.g. `-`)... DECIDED/implemented in `MaxioSubscriptionService.FirstNameFrom` (+ LastName `-`).
3. **Default plan.** The task says `eshop-pro` is the default target but forbids hard-coded values. Plan: request body `planHandle` optional; when absent, use optional config key `Maxio:DefaultPlanHandle` (a key additional to the four in the task; deployed demo sets `eshop-pro`); when both absent -> 400. DECIDED/implemented: `MaxioSettings.DefaultPlanHandle`, used in `SubscribeAsync`; set via user-secrets, not in repo files.
4. **Metered component `api-call` is not attached** at signup (hero flow covers plan subscribe only; CreateSubscription `Components` left out). If the demo needs it attached, it needs `CreateSubscriptionComponent` (not read here) and a `Maxio:` key for the handle.
5. One subscription per (user, plan); a user may hold two different plans; a previously canceled subscription for the same plan blocks re-subscribe until a lifecycle step is added (out of scope).
6. "Next billing date" is `Subscription.NextAssessmentAt` (fall back to `CurrentPeriodEndsAt` when null); which one Maxio considers the date is UNVERIFIED (field docs not read).
7. `ReadCustomerByReference` and `FindSubscription` "not found" statuses: `FindSubscription` documents 404 via `TryGetNoContent`; `ReadCustomerByReference` is Case B and its not-found status is UNVERIFIED, so the reconcile treats any non-2xx `ApiException<RawError>` with `StatusCode == 404` as absent and anything else as "unknown".
8. Plans need no payment profile (per task); if Maxio answers 422 for a missing payment method the endpoint reports a 502-style failure with the provider message (not expected on the seeded catalog).
9. No config key selects `ServerEnvironment.Eu`; Us is used. Add one only if an EU-hosted site is needed.
10. The new SQL Server tables need an EF migration for production; dev/tests use in-memory and ignore migrations.
11. Whether the in-memory provider raises `DbUpdateException` or `InvalidOperationException` on a duplicate key depends on tracking state; the catch must cover what it actually raises and the test must prove two concurrent claims yield one SDK call.

- Added optional settings beyond the four task keys: `Maxio:DefaultPlanHandle`, `Maxio:PaymentCollectionMethod`.
