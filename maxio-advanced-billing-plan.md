## 1. Scope & sequence

1. **Config + startup fail-fast**: bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional). No SDK operation.
2. **Client construction** (singleton `MaxioAdvancedBillingClient`, options built once at registration). No operation.
3. **GET /api/subscription-plans**: `client.ProductFamilies.ListProductsForProductFamily` (family addressed as `handle:<Maxio:ProductFamilyHandle>`), page-walked with a page cap. Result is the offered set of plan handles.
4. **POST /api/subscriptions** (body: plan handle, REQUIRED: 400 when missing or blank, no default plan; per the task decision the catalog must stay swappable):
   1. validate the plan handle against the set from step 3 (re-listed from Maxio on this call), before any write;
   2. claim the user's enrollment row in the app store (primary key; refuses a second claim) BEFORE any SDK write;
   3. ensure the Maxio customer: `client.Customers.ReadCustomerByReference` then, if absent, `client.Customers.CreateCustomer` with `Reference` = deterministic reference derived from the app user id;
   4. `client.Subscriptions.CreateSubscription` with `ProductHandle` = validated plan handle, `CustomerId` of step 3, `Reference` = deterministic subscription reference;
   5. record the customer id, subscription id, state in the enrollment row; return plan/price/state/next-billing-date.
5. **GET /api/my-subscriptions**: read the caller's enrollment row(s) from the app store, then `client.Subscriptions.ReadSubscription` per stored subscription id for live plan/price/state/next billing date. Rows left in an unknown state are settled here with `client.Subscriptions.FindSubscription` / `client.Customers.ReadCustomerByReference` (see UNKNOWN OUTCOMES).

Not in scope: payment profiles (subscriptions use remittance collection, so no card is captured), components/metered `api-call` usage, cancel/upgrade, webhooks.

**Store design (YOUR CALL - not in the map; consequence of the claim rule)**: a new EF entity (e.g. `SubscriptionEnrollment`, plain class with private setters like the existing aggregates, optionally implementing `IAggregateRoot`) added as a `DbSet` on the existing `CatalogContext` with its own `IEntityTypeConfiguration` in `src/Infrastructure/Data/Config/`. Key = the app user id as a string PRIMARY KEY (max 256, like `Basket.BuyerId`); columns: plan handle, status (`Claimed`, `Active`, `Unknown`), Maxio customer id (nullable), Maxio subscription id (nullable), customer reference, subscription reference, timestamps. A primary key is used (not a unique index) because the EF in-memory provider enforces primary keys but may not enforce unique indexes. One enrollment per user in this iteration (so a double-click, or a Basic click after a Pro click, cannot create a second customer or subscription). For a real SQL Server database an EF migration for `CatalogContext` is needed; in-memory ignores it.

**DUPLICATE CLAIMS**

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |

## 6. Assumptions & Blockers

Blockers
- None identified. Capability check: list offered plans by family handle (`ListProductsForProductFamily`, accepts the `handle:` prefix), find/create customer by reference, create/read/find subscription are all in the map. The SDK has no sandbox environment member; sandbox targeting is by subdomain and key, as recorded (not a blocker).

Assumptions
1. **Identity**: the JWT has only the username claim. The caller's identity is the `ClaimTypes.Name` of the principal; the endpoint resolves the `ApplicationUser` through `UserManager` and uses its stable `Id` as the store key and the Maxio reference seed, and its `Email` for the customer. ApplicationCore stays free of Identity types (the endpoint passes plain values into the service). YOUR CALL - not in the map.
2. **Customer names**: Maxio's `CreateCustomer` requires `first_name`, `last_name` and `email`; the app's user record holds no first or last name. Assumption: derive them from the user (e.g. first name = username/email local part, last name = a fixed placeholder) until the app has a profile. Needs user confirmation if real names matter.
3. **One enrollment per shopper** (the primary key is the user id): a second distinct plan is refused with 409 in this iteration. Switching plans is out of scope.
4. **Plan handle**: required in the POST body (400 if missing/blank); there is no default plan. It is validated against the listed set.
5. **"Next billing date"** is `Subscription.NextAssessmentAt` (`next_assessment_at`); `CurrentPeriodEndsAt` is returned as well. Price shown is `Product.PriceInCents` converted for display; the response is returned in cents plus interval to avoid rounding.
6. **Metered component `api-call`** is not attached to the subscription (not part of the hero flow).
7. **Existing tests / hosts**: because startup now fails fast on blank Maxio config, `tests/PublicApiIntegrationTests` (which boots the PublicApi host) will need test-only configuration (non-secret dummy values supplied by the test host) to keep starting; the Web host registers no Maxio client and is unaffected, though it shares `CatalogContext`, so the new `DbSet` appears there too.
8. **ExceptionMiddleware** returns 500 with `exception.Message` for everything except `DuplicateException`; the new endpoints should return their own 400/404/409/502/504 results (or a small extension of the middleware) and never echo SDK or Maxio error text to the caller. YOUR CALL - not in the map.
9. **UNVERIFIED (live traffic only)**: that `ReadCustomerByReference` returns 404 (not 200 with empty) for an absent reference; that a subscription `Reference` is unique or at least returns the right subscription from `FindSubscription`; that a no-trial, no-payment-method plan lands in state `active` immediately with `next_assessment_at` populated. **LIVE RESULT (refuted)**: against the sandbox, `CreateSubscription` for the listed plans (product `require_credit_card` false) answers 422 "No payment method was on file for the ... balance"; with automatic collection and no payment profile the subscribe cannot succeed. RESOLVED: CreateSubscription now sets `PaymentCollectionMethod = CollectionMethod.Remittance`; live POST returns 200, state active, next_assessment_at populated (no payment profile needed). Defensive coding: treat a null `Subscription`, null `Id`, or null `NextAssessmentAt` in a 2xx as "outcome incomplete" and fall back to the re-read path rather than reporting success, and render `State` through the known-value `Match` with an `otherwise` arm.
10. The product family numeric ids in the task may be stale; the code uses only the handles (`handle:` + the value of `Maxio:ProductFamilyHandle`, plan handles from the listed products) and never a numeric id from the task.
