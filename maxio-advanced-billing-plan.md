## 6. Assumptions & Blockers

**Settled decisions (implementation):** (1) identity = JWT `ClaimTypes.Name` -> `UserManager.FindByNameAsync` (`SubscriptionBillingService.ResolveUserAsync`); email from Identity, first name = email local part, last name constant "Customer" (`CreateCustomerAsync`). (2) customer reference = `eshop-user-{Identity user id}` (`CustomerReferenceFor`). (3) `PaymentCollectionMethod = Remittance` is REQUIRED: with it unset Maxio rejected the create ("No payment method was on file"), verified live; set in `CreateSubscriptionAsync`. (4) plan price/interval displayed from `Product`; no default-plan fallback, `planHandle` required. (6) next billing date = `NextAssessmentAt ?? CurrentPeriodEndsAt` (`Apply`); `NextAssessmentAt` was populated live. Production-readiness YOUR CALLs: row 1 `MaxioSettings` + `AddMaxioBilling` (`ValidateDataAnnotations().ValidateOnStart()`); row 2 options built once in the singleton registration; row 3 `Bounded` = 30 s per operation, 10 s per attempt (`AttemptTimeout`); row 4 default retry verbs (no POST); row 6 `ILogger` in the service, `BillingException` messages are caller-safe; row 8 `Maxio:Subdomain` fills `{site}`, `Maxio:BaseUrl` assigned to `Production.Us/Eu.BaseUrl`, verified by test (path prefix and no trailing-slash issue: the SDK trims the slash).

Blockers: none. Every capability the task asks for exists in the map: listing products by product family (`ListProductsForProductFamily`, family addressed as `handle:<handle>`), customer lookup by reference (`ReadCustomerByReference`), and subscription creation with `customer_reference` and `product_handle` (`CreateSubscription`). Base URL: the SDK derives it from per-group, per-environment templates (`{site}` placeholder, default literal `"subdomain"`); a custom base URL can be set through `options.Server.Production.Us.BaseUrl` (and `.Eu`), used as a template with only `{site}` substituted.

Assumptions:
1. Caller identity is the JWT `ClaimTypes.Name` (only identity claim issued by `IdentityTokenClaimService`). The email, and first/last name required by `CreateCustomer` (`FirstName`, `LastName`, `Email` are `required`), are not in the token: assume the app resolves the user via the existing `UserManager<ApplicationUser>` (Identity), using the user name/email as email and a fallback for names (e.g. the part of the email before `@` for first name and a placeholder-free last name policy). YOUR CALL — not in the map.
2. Customer reference sent to Maxio = a stable key derived from the user's identity (e.g. the Identity user id looked up by name). If the user name can change, prefer the Identity user id; this must be decided at implementation. YOUR CALL — not in the map.
3. "Payment method not required": the plan sends no payment profile or card attributes. The map documents `payment_collection_method` values (`Automatic`, `Remittance`, `Prepaid`, `Invoice`) but not which one a no-card sandbox plan needs; whether `Automatic` with no payment profile is accepted is `UNVERIFIED`. If Maxio rejects the create with 422, surface the `ErrorListResponse1` message and do not retry; try leaving the member unset first (the plans are configured not to require a payment method), then `Remittance`. Treat a provider rejection of this kind as the one expected-failure risk; it is not provable from the map, so not recorded as a Blocker.
4. No trial, no setup fee: the app does not send price point, trial or initial-charge members; it displays `Product.PriceInCents`, `Interval`, `IntervalUnit` from the list. Default plan (`eshop-pro`) is presentation only; the endpoint always requires an explicit `planHandle` unless the product owner wants default fallback (not stated; none implemented).
5. Metered component `api-call` is not part of the subscribe flow (no `Components` sent); it is not read.
6. "Next billing date" is taken from `Subscription.NextAssessmentAt`, falling back to `CurrentPeriodEndsAt` when null; the map does not say which one the provider populates for a fresh subscription (`UNVERIFIED`).
7. Claims live in the in-memory EF store and do not survive a process restart; for a restarted process the reconciliation reads (`ReadCustomerByReference`, `FindSubscription`) are the recovery path. With a real database the PKs hold unchanged.
8. Currency is not shown beyond cents; the site default currency is assumed (no `Currency` sent).
