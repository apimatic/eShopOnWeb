# Maxio Advanced Billing plan: recurring subscriptions in eShopOnWeb PublicApi

SDK root (plugin-relative): `sdk/dotnet/` (map: `sdk/dotnet/sdk-map.md`; pages `sdk/dotnet/map/operations/*.md`). All "source" cells below are relative to that root.
Repo survey (pattern + exemplar):
- Endpoint style: MinimalApi.Endpoint `IEndpoint<IResult, TRequest, TDeps>` with `AddRoute` using `app.MapPost("api/...", [Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)] ...)`, `.Produces<T>().WithTags(...)`; request/response classes in sibling files deriving `BaseRequest`/`BaseResponse` (CorrelationId). Exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (+ its `.CreateCatalogItemRequest.cs` / `.CreateCatalogItemResponse.cs`). Endpoints auto-register via `AddEndpoints()`/`MapEndpoints()` in `src/PublicApi/Program.cs`.
- JWT: `src/Infrastructure/Identity/IdentityTokenClaimService.cs` puts ONLY `ClaimTypes.Name` (the username) and `ClaimTypes.Role` claims in the token. There is no NameIdentifier claim. `Program.cs` already registers ASP.NET Identity (`UserManager<ApplicationUser>`), so the stable user id is resolved from the token's Name claim via `FindByNameAsync` -> `ApplicationUser.Id`.
- Errors: `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps `DuplicateException` -> 409, everything else -> 500 (message echoed). Exemplar exceptions: `src/ApplicationCore/Exceptions/DuplicateException.cs`.
- Store: EF Core `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`, DbSets + `src/Infrastructure/Data/Config/*Configuration.cs`), repositories `IRepository<T>`/`EfRepository<T>` need `IAggregateRoot` + int `BaseEntity.Id`. In-memory selected by `UseOnlyInMemoryDatabase` in `src/Infrastructure/Dependencies.cs`.
- Logging: `IAppLogger<T>` (ApplicationCore/Interfaces) over ILogger. Tests: `tests/PublicApiIntegrationTests/ProgramTest.cs` (plain `WebApplicationFactory<Program>` + `appsettings.test.json`), `tests/UnitTests`.
- Config binding: `Program.cs` uses `builder.Configuration`; user-secrets (`UserSecretsId` already in PublicApi.csproj) load only when `ASPNETCORE_ENVIRONMENT=Development`.

## 1. Scope & sequence

1. Config + client registration: bind `Maxio:` section (ApiKey, Subdomain, ProductFamilyHandle, BaseUrl optional), validate at startup, build ONE `MaxioAdvancedBillingClient` singleton. Add `ProjectReference` from Infrastructure to `<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` (local to this machine; say so in hand-over). No ops.
2. Plan listing (`GET /api/subscription-plans`): `client.Products` is NOT used; use `client.ProductFamilies.ListProductsForProductFamily` with `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle`, paged by hand (page-number via `Page`/`PerPage`=200) -> map to DTO (handle, name, priceInCents, interval, intervalUnit, isDefault = handle `eshop-pro` is NOT hard-coded: default flagged only if a configured/derived rule exists; see §6 assumption A3).
3. Subscribe (`POST /api/subscriptions`): resolve user -> re-run step 2 listing and verify requested product handle is in it (invariant) -> claim row in `CatalogContext` (PK = user id) -> ensure customer (`Customers.ReadCustomerByReference`, then `Customers.CreateCustomer` if 404) -> persist customer id on claim -> `Subscriptions.CreateSubscription` (`CustomerId`, `ProductHandle`, `Reference`) -> persist subscription id/state -> return plan/price/state/next billing date from the create response.
4. My subscriptions (`GET /api/my-subscriptions`): resolve user -> load own mapping row -> `Subscriptions.ReadSubscription` for live state -> DTO. Rows in `Claiming`/`Unknown` state are settled first (step 3 reconciliation helpers) before reading.
5. Persistence: new entity `MaxioSubscriptionLink` (ApplicationCore/Entities, not an aggregate repository requirement; accessed through `CatalogContext` directly or a small repository) with PK = `UserId` (string), `MaxioCustomerId?`, `MaxioSubscriptionId?`, `ProductHandle`, `State` (Claiming / Active / Unknown), `ClaimedAtUtc`, `UpdatedAtUtc`; EF configuration file in `Data/Config`. One subscription per user (YOUR CALL, §7).
6. Error mapping, logging, tests (unit with HttpClient stub; PublicApi integration tests with stubbed Maxio HttpMessageHandler).
No capability is missing from the map: customer find-by-reference, create customer, list plans by family handle, create/read subscription, list customer subscriptions all exist. No Blocker.

| Invariant | Operations | Enforced where |
| --- | --- | --- |

## 3. Trap notes

- Step 1 client registration: the client captures its environment at construction and keeps a live server-options object; options are built once, so what you set when and how rotation behaves is a trap. MUST load maxio-advanced-billing:dotnet-client-initialization

## 6. Assumptions & Blockers

Blockers: none. Every needed capability exists in the SDK map.

Assumptions:
- A1. The user's identity is the ASP.NET Identity user id, resolved from the JWT `ClaimTypes.Name` claim (the only identity claim the existing token carries) via `UserManager<ApplicationUser>.FindByNameAsync`; the endpoints name that claim because `IdentityTokenClaimService.cs` was read. Token for a deleted user -> 401.
- A2. One subscription per user (claim PK = user id). A second subscribe for a different plan returns 409 "already subscribed"; same plan returns the existing subscription (idempotent).
- A3. "Default subscribe target is `eshop-pro`": the task fixes that handle but forbids hard-coding numeric ids, not handles; however `POST /api/subscriptions` with an omitted handle defaults to the plan handle `eshop-pro` only if present in the family listing, kept as a named constant/default in the endpoint request contract (not config key; the `Maxio:` section has exactly four keys). If absent from the listing -> 400.
- A4. Customer first/last name are required by the SDK but the app has only username/email: derive from the email local part (first) and a fixed placeholder last name ("Shopper"); email = `ApplicationUser.Email` (fall back to username if it is an email). Reference = user id.
- A5. CORRECTED at Step 4 (live sandbox): with `PaymentCollectionMethod` unset, `CreateSubscription` answered 422 "No payment method was on file for the $299.00 balance" even though the plan does not require a card. The call now sets `PaymentCollectionMethod = MaxioAdvancedBilling.Models.Enums.CollectionMethod.Remittance` (member doc: valid options for Relationship Invoicing are remittance/automatic/prepaid; file `Models/CreateSubscription.cs`, `Models/Enums/CollectionMethod.cs`); no payment profile is sent. Verified live: 201, state active.
- A6. No EF migration is added (in-memory only environment); SQL Server deployments need one (`MaxioSubscriptionLinks` table).
- A7. Maxio-side uniqueness of customer `reference` is `UNVERIFIED`; protection relies on the app claim.
- A8. `SubscriptionState`/`IntervalUnit` wire strings are passed to callers as text.
