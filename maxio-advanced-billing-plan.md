## 6. Assumptions & Blockers

**Blockers: none.** The map has every needed capability: list plans by family (`ListProductsForProductFamily`, needs the numeric family id, obtained by `ListProductFamilies` + client-side handle match since the map has no handle filter or read-family-by-handle), find customer by reference (`ReadCustomerByReference`), list a customer's subscriptions (`ListCustomerSubscriptions`).

Assumptions / YOUR CALL items:

1. **Default plan.** The task says Pro (`eshop-pro`) is the default subscribe target but lists only four config keys and forbids hard-coding handles. Planned: `POST /api/subscriptions` takes `planHandle` in the body; when omitted, use an optional extra config key `Maxio:DefaultPlanHandle` (set to `eshop-pro` in user-secrets/appsettings of the sandbox, not in code); if neither is present, 400. Decided: optional `Maxio:DefaultPlanHandle` (`MaxioSettings`, used in `SubscribeCoreAsync`); also added optional `Maxio:PaymentCollectionMethod` (default `remittance`) and `Maxio:RequestBudget`.
2. **Caller identity.** Token carries only `ClaimTypes.Name` (username) and role claims (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`); no user id. `UserKey` = normalized `ClaimTypes.Name`. Email for `CreateCustomer`: looked up via `UserManager<ApplicationUser>.FindByNameAsync` (already registered in PublicApi Program.cs), falling back to the username if it is an email. `FirstName`/`LastName` are required by `CreateCustomer` but `ApplicationUser` is not known to hold them: planned placeholder (local part of the email for first name, a fixed literal for last name). Decided: `MaxioSubscriptionService.UserKey` and `ResolveIdentityAsync` (placeholder last name "Shopper").
3. **Customer reference** = `UserKey` (stable, unique, caller-derived). Subscription `Reference` = deterministic string from (`UserKey`, plan handle). Decided: `UserKey`, `SubscriptionReference`.
4. **Payment method not required.** `CreateSubscription` sends no payment profile or `PaymentCollectionMethod`; remarks say payment info "may be required … depending on the options for the Product". The sandbox plans are stated as not requiring it; if Maxio answers 422 anyway this is a provider rejection to surface as a clear 4xx, not retried. VERIFIED LIVE: with automatic collection Maxio returned 422 "No payment method was on file"; the subscription is created with `payment_collection_method` = `remittance` (`CreateSubscription.PaymentCollectionMethod`, `Models/Enums/CollectionMethod.cs`), configurable via `Maxio:PaymentCollectionMethod`.
5. **Metered component `api-call`**: not sent on subscribe (no `Components`); the plan assumes the sandbox allows creating the subscription without allocating it. VERIFIED LIVE: subscriptions are created without components. Component listing is out of scope.
6. **Re-subscribe policy.** The subscription claim is per (user, plan) and permanent once `Completed`; a repeat POST returns the stored subscription. Cancelled-then-resubscribe is not supported in this scope. Decided: `EnsureSubscriptionAsync`.
7. **My-subscriptions** reads the customer id from the app's own `MaxioCustomerClaim`; a user with no claim gets an empty list (no Maxio call, no customer creation on read). Results filtered to subscriptions whose `Product.ProductFamily.Handle` equals the configured family when that field is populated. Decided: `ListMineCoreAsync`.
8. **Family id caching**: handle -> id may be cached in-process (singleton) after first resolution; the plan listing itself is never cached for the subscribe-time check.
9. **Not-found on `ReadCustomerByReference`** is expected as `ApiException<RawError>` with `StatusCode` 404 (map says Case B, no typed 404). VERIFIED LIVE: 404 as ApiException<RawError>.
10. In-memory EF store loses claims on restart: duplicates across restarts are then caught only by Maxio's own unique customer reference (customer) and by reconciliation via `ListCustomerSubscriptions` (subscription, checked before create). Production would use a real store; no new infra added.
