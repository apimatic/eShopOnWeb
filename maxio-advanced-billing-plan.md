# Maxio Advanced Billing plan — eShopOnWeb subscriptions (PublicApi)

SDK root (plugin-relative): `sdk/dotnet/` — map `sdk/dotnet/sdk-map.md`, pages `sdk/dotnet/map/operations/*.md`. All `source` cells below are relative to that SDK root unless they name a repo path.

Repo conventions read for this plan (exemplars to imitate, read at edit time):
- Endpoint shape: `MinimalApi.Endpoint` `IEndpoint<IResult, TRequest, ...>` with `AddRoute` + `HandleAsync`, JWT via `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.WithTags(...)`; request/response split into `<Endpoint>.<Request|Response>.cs` files — exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. Routes registered via `builder.Services.AddEndpoints()` / `app.MapEndpoints()` in `src/PublicApi/Program.cs`.
- Caller identity: the JWT carries only `ClaimTypes.Name` (= `UserName`) and `ClaimTypes.Role` — `src/Infrastructure/Identity/IdentityTokenClaimService.cs`. No user-id claim exists in the token.
- EF store: `src/Infrastructure/Data/CatalogContext.cs` (applies `IEntityTypeConfiguration<>` from assembly; exemplar config `src/Infrastructure/Data/Config/CatalogBrandConfiguration.cs`); in-memory switch in `src/Infrastructure/Dependencies.cs` (`UseOnlyInMemoryDatabase`).
- Duplicate → HTTP 409: `DuplicateException` (`src/ApplicationCore/Exceptions/DuplicateException.cs`) mapped by `src/PublicApi/Middleware/ExceptionMiddleware.cs`; every other exception becomes 500 with `exception.Message` in the body.
- Identity users are re-seeded on every start under the in-memory provider (`src/Infrastructure/Identity/AppIdentityDbContextSeed.cs` creates `demouser@microsoft.com` / `admin@microsoft.com`), so `ApplicationUser.Id` (a GUID) changes per process; `UserName` does not.

## 1. Scope & sequence

| # | Step | Operations |
| --- | --- | --- |
| 1 | Reference SDK project from `src/Infrastructure` (or `src/PublicApi`); bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`; fail fast; register client singleton | — (client construction) |
| 2 | EF claim tables in `CatalogContext`: `MaxioCustomerClaim` (PK = customer reference), `MaxioSubscriptionClaim` (PK = user key) + `IEntityTypeConfiguration` files | — |
| 3 | `GET /api/subscription-plans` — list products in family `handle:{Maxio:ProductFamilyHandle}`, walk pages, drop archived, map name/handle/price/interval | `ProductFamilies.ListProductsForProductFamily` |
| 4 | Ensure customer (idempotent): claim row → `ReadCustomerByReference` (404 ⇒ absent) → `CreateCustomer` with `Reference` → store `Customer.Id` | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5 | `POST /api/subscriptions` — validate plan handle against step 3's set; subscription claim row (with app-generated subscription reference) → `CreateSubscription` (`ProductHandle`, `CustomerId`, `Reference`) → store `Subscription.Id`, state; return plan/price/state/next billing date | `Subscriptions.CreateSubscription` (+ step 3, step 4) |
| 6 | Unknown-outcome reconciliation for steps 4/5 | `Customers.ReadCustomerByReference`, `Subscriptions.FindSubscription`, `Customers.ListCustomerSubscriptions` |
| 7 | `GET /api/my-subscriptions` — settle any open claim, resolve the caller's customer (local claim, else `ReadCustomerByReference`), `ListCustomerSubscriptions`, keep the family's subscriptions (Maxio is the system of record, so this survives a restart of the in-memory store). `ReadSubscription` is used on a repeat subscribe to check the stored subscription is still live | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions`, `Subscriptions.ReadSubscription` |
| 8 | Tests (stubbed HttpClient): happy path, double-submit, 422, connection failure after send | all above |

Out of scope: metered component `api-call` (no usage write requested), payment profiles, cancellation.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The plan handle a caller POSTs must be the `Product.Handle` of a non-archived product the family listing returned (default `eshop-pro` when omitted) | `CreateSubscription.ProductHandle` ← `ProductFamilies.ListProductsForProductFamily` (`handle:{Maxio:ProductFamilyHandle}`) | in the subscribe service, before the subscription claim and `CreateSubscription`; the service calls the plan-listing member (step 3) itself — unknown handle ⇒ 400, no claim, no SDK write |

## 6. Assumptions & Blockers

**Blockers:** none.

**Assumptions:**
1. **Customer reference = the eShop `UserName`** (the JWT's only identity claim, `ClaimTypes.Name`), optionally namespaced (e.g. `eshop:{UserName}`) — `YOUR CALL — not in the map`. `ApplicationUser.Id` is not used because the in-memory identity store re-seeds users with new GUIDs on every start (`AppIdentityDbContextSeed.cs`), which would create a new Maxio customer per restart. Maxio documents reference as the customer's "unique reference ID" (`Api/Customers.cs` remarks).
2. **Customer names:** `CreateCustomer` requires `FirstName`, `LastName`, `Email`; `ApplicationUser` has no name fields. Email = `ApplicationUser.Email` (via `UserManager.FindByNameAsync`), names derived (e.g. local part of the email / fixed "eShop" + "Shopper") — `YOUR CALL — not in the map`.
3. **Config vs env vars:** the app binds only `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl`. The provided `MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, `MAXIO_DEFAULT_PRODUCT_FAMILY` are copied into user-secrets under those keys (`dotnet user-secrets set Maxio:ApiKey …` in `src/PublicApi`); `MAXIO_ENVIRONMENT` has no binding key in the task — environment stays `ServerEnvironment.Us` (SDK default; the SDK has no sandbox member, sandbox = site `cp-exp-4`). If `MAXIO_ENVIRONMENT` means EU hosting, `Maxio:BaseUrl` covers it.
4. **One subscription per user** in this capability (subscription claim PK = user key). A user who wants a second plan gets the existing one back. Change to composite PK (user, product handle) if multiple concurrent plans are wanted.
5. **Plan selection (revised at implementation):** `planHandle` is required in the POST body; nothing is defaulted, because no plan handle may be hard-coded (the same build must run against another catalog). Validated against the family listing.
11. **Live sandbox results (implementation):** customer lookup by an unknown reference returned 404 (row 7 behaves as coded); a `Maxio:BaseUrl` without `{site}` is used verbatim (asserted by `ListPlansExcludesArchivedProductsAndUsesBaseUrlVerbatim`). Whether Maxio rejects a duplicate subscription `reference` is still `UNVERIFIED`; the app's PK claim does not rely on it.
6. **Family identifier:** `ProductFamilyId = "handle:" + Maxio:ProductFamilyHandle` (record doc). Numeric ids never hard-coded.
7. **"Not found" on `ReadCustomerByReference`** is Case B with no typed accessor; treating status 404 as absent is `UNVERIFIED` — any other error status is a failure, never "absent".
8. **Plans list filtering:** archived products excluded via `ArchivedAt == null` with `IncludeArchived` unset; the metered component `api-call` is not a product and does not appear in this list (components are a separate controller) — no component call is planned.
9. **Toolchain (non-SDK):** `global.json` pins `"version": "8.0.x", "rollForward": "latestFeature"`, which does not roll forward across major versions; with only the .NET 10 SDK installed the build may refuse to start. The main agent should check before baseline build and adjust `rollForward` (e.g. `latestMajor`) only if the user's environment requires it.
10. **SDK reference is machine-local:** `ProjectReference` into the plugin's `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`; CI without the plugin cannot build — to be stated at hand-over.
