# Maxio Advanced Billing integration plan: eShopOnWeb "Subscribe"

SDK source root (plugin-relative): `sdk/dotnet/` (all `Source` cells are relative to it). Business rules: `business-rules/` (rule ids `maxio-c4:...`).
Vocabulary: the task's "plan" is the SDK's **Product** (`product_handle`); "product family" is `ProductFamilies`.

## 1. Scope & sequence

Repo conventions (pattern, ONE exemplar):
- Endpoint style: `MinimalApi.Endpoint` `IEndpoint<IResult, TRequest, TDep>` + `AddRoute` + `HandleAsync`, one file per endpoint plus request/response files, response derives `BaseResponse` (correlation id). Exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (+ its `.CreateCatalogItemRequest.cs` / `.CreateCatalogItemResponse.cs`).
- Auth: `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` on the lambda (same exemplar, minus `Roles`). The token (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`) carries ONLY `ClaimTypes.Name` (the username) and `ClaimTypes.Role`; there is no `NameIdentifier`/`sub` claim. Caller identity = `ClaimTypes.Name`, resolved to `ApplicationUser.Id` via `UserManager<ApplicationUser>` (registered in `src/PublicApi/Program.cs`).
- Errors: `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps `DuplicateException` to 409 and everything else to 500 (leaks `exception.Message`).
- Store: `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`), entity config in `src/Infrastructure/Data/Config/*Configuration.cs` (exemplar `BasketConfiguration.cs`), registered in `src/Infrastructure/Dependencies.cs` (in-memory when `UseOnlyInMemoryDatabase=true`, else SQL Server). Repositories: `IRepository<T>` / `EfRepository<T>` (aggregate roots implement `IAggregateRoot`).
- Settings: `builder.Services.Configure<...>(builder.Configuration...)` in `Program.cs`; PublicApi has `UserSecretsId` already.
- Tests: `tests/PublicApiIntegrationTests/`, `tests/UnitTests/` (exemplar `tests/PublicApiIntegrationTests/CatalogItemEndpoints/CatalogItemGetByIdEndpointTest.cs`).

## 3a. DUPLICATE CLAIMS

Order for each row: claim (store write) -> SDK call -> record result. Store: `CatalogContext` (the app's own EF Core store, in-memory when `UseOnlyInMemoryDatabase=true`). The store's refusal is a **primary key** (enforced by the in-memory provider; a unique index is not). Maxio's `uniqueness_token` / injected `Idempotency-Key` are NOT used as the claim (the injected header is `Guid.NewGuid()` and `uniqueness_token` is not a member of any record in scope).

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| Ensure Maxio customer for user (`Customers.CreateCustomer`) | New entity `MaxioCustomerLink` in `CatalogContext`: PK `UserId` (the `ApplicationUser.Id`), `CustomerReference` (deterministic from `UserId`, never `Guid.NewGuid()` per call; not the email), `MaxioCustomerId int?`, `Status` (`Claimed`/`Created`/`Unknown`), `ClaimedAtUtc`. Row inserted and saved BEFORE the SDK call | primary key on `UserId`: second `SaveChanges` of the same `UserId` throws `DbUpdateException` (new context scope per request, so no tracked-entity short circuit) | the subscribe handler's catch of `DbUpdateException` around the claim insert: loser reloads the row; if `MaxioCustomerId` is set it proceeds with it; if `Status=Claimed` (winner in flight) it returns 409 "in progress" (retry later), never calls `CreateCustomer`. Claim is released (row deleted) only when Maxio definitively refused (`TryGetCustomerErrorResponse1` 422) | `MaxioSubscriptionBillingService.EnsureCustomerAsync` (claim: `_db.CustomerLinks.Add`+`SaveChangesAsync`; then `CompleteClaimedWriteAsync` -> `_client.Customers.CreateCustomer`). Catch: `catch (Exception ex) when (ex is DbUpdateException or ArgumentException)` (the in-memory provider raises ArgumentException) |
| Subscribe user to plan (`Subscriptions.CreateSubscription`) | New entity `MaxioSubscriptionLink` in `CatalogContext`: composite PK (`UserId`, `PlanHandle`) (**YOUR CALL — not in the map**: key on `UserId` alone if a shopper may hold only one subscription), `SubscriptionReference` (deterministic from the key, sent as `CreateSubscription.Reference`), `MaxioSubscriptionId int?`, `Status` (`Claimed`/`Created`/`Unknown`), `ClaimedAtUtc`. Inserted and saved BEFORE the SDK call and only after the customer link holds a customer id | composite primary key: second insert for the same (`UserId`,`PlanHandle`) throws `DbUpdateException` | the subscribe handler's catch of `DbUpdateException` around the claim insert: loser reloads the row and returns the stored subscription (200, read back via `ReadSubscription` if id known), or 409 "in progress" when `Status=Claimed`/`Unknown` after a bounded re-read via `FindSubscription`. Claim is deleted when Maxio definitively refuses (`TryGetErrorListResponse1` 422) so the user can retry; stale `Claimed` rows older than a timeout are settled by the unknown-outcome path, not blindly re-created | `MaxioSubscriptionBillingService.EnsureSubscriptionAsync` (claim: `_db.SubscriptionLinks.Add`+`SaveChangesAsync`; then `CreateSubscriptionAsync` -> `_client.Subscriptions.CreateSubscription`); same catch filter |

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Credentials are bound in code from `IConfiguration` (`Maxio:ApiKey`, user-secrets in dev) onto `options.BasicAuth`; the SDK's own env fallback is bypassed by always setting `BasicAuth`. Startup validation (`ValidateOnStart` or an explicit check in `Program.cs` before `Build`) refuses to start when `Maxio:ApiKey`, `Maxio:Subdomain` or `Maxio:ProductFamilyHandle` is null/blank/whitespace. `Maxio:BaseUrl` is optional but, when set, must be an absolute URL. Both parts of the credential are checked (the password is the fixed protocol constant). Source: YOUR CALL — not in the map |
| 2 | Secret sourcing & rotation | `ApiKey` from .NET user-secrets in dev (PublicApi already has a `UserSecretsId`) and from the deployment's configuration provider in prod; never in `appsettings*.json` or the repo. The client is built once at registration and captured by the singleton, so a rotated key takes effect only after process restart. Rotation without restart is not required |
| 3 | Total timeout budget | Per attempt: `options.Retry.Timeout = 10s` (explicit; default 100s is unusable) and `HttpClient.Timeout = 10s` backstop. Whole call: one `Bounded` helper in the single service fronting the SDK links `HttpContext.RequestAborted` with `CancelAfter(budget)`; budget **25s per HTTP request** shared by every SDK call in the handler (subscribe makes up to 4: list, create customer, create subscription, read-back). Enforced in that service, one value in options. Maxio itself cuts requests at 120s (rule `maxio-c4:every-request.31`), above our budget, hence unknown-outcome handling |
| 4 | Write-retry ownership | With default `HttpMethodsToRetry` (`GET, HEAD, PUT, OPTIONS`) the SDK never resends `CreateCustomer` or `CreateSubscription` (POST) on 5xx/timeout/connection fault; reads (`List...`, `ReadCustomerByReference`, `FindSubscription`, `ReadSubscription`) may be retried (up to `MaxRetries`, keep at 2 to stay inside the budget). `HttpMethodsToRetry` must NOT be widened to include POST. Basic auth is a static credential: no 401 re-send. The app does not layer its own retry on writes; recovery is reconcile-by-reference |

## 6. Assumptions & Blockers

Blockers: none that stop planning (the app's own store can hold the claims, so concern 9 is not a Blocker).

Assumptions / `YOUR CALL — not in the map` (to settle at implementation, task wins):
1. **Default plan.** The task calls `eshop-pro` the "default subscribe target", but hard-coding a handle is forbidden and the settings keys are exactly four (no default-plan key). The plan makes `planHandle` a REQUIRED field of `POST /api/subscriptions` (missing/blank -> 400); "default" is a client/UI choice made from the listed plans. Alternative needing your decision: a fifth settings key.
2. **Caller identity.** The JWT carries only the username (`ClaimTypes.Name`), no user id. Plan: resolve `ApplicationUser.Id` via `UserManager<ApplicationUser>` and key all rows on it; unknown user -> 401. Maxio customer `reference` derives from that id (not the email).
3. **Customer names.** `first_name` and `last_name` are required by `CreateCustomer` but eShopOnWeb's `ApplicationUser` only has user name/email. Plan: first name = local part of the email, last name = a neutral non-empty constant kept in the options class, email = `ApplicationUser.Email`. Tell me if you want a real name source.
4. **Payment method not required (risk, UNVERIFIED).** Rules `maxio-c4:createSubscription.7`/`.11` say Maxio refuses (422) a paid product when its options require payment information. The plan assumes the seeded plans (Pro $299, Basic $29) are configured with `require_credit_card=false` and that the site accepts a subscription without a payment profile. No payment attributes are sent and `payment_collection_method` is left unset (it must match the site architecture, rule `maxio-c4:every-request.42`). If Maxio answers 422, the app maps it to a 422/502 with the Maxio message and releases the claim; if that is systematic it becomes a Blocker to take to you. The plan list exposes `RequireCreditCard` so this is visible.
5. **Multiple subscriptions per user.** Claim key (`UserId`,`PlanHandle`) lets one shopper hold one subscription per plan; `UserId` alone would allow one total. Decision needed.
6. **"Next billing date"** field choice (`NextAssessmentAt` vs `CurrentPeriodEndsAt`), see contract sheet.
7. **No EF migration** is generated for the new tables (task: in-memory only; `Migrations/` targets SQL Server). With `UseOnlyInMemoryDatabase=false` the tables would not exist: the feature documents that it supports only the in-memory configuration, and the endpoints fail fast with a clear error otherwise. Say if you want a migration anyway.
8. **ApplicationCore/Infrastructure split.** Interface and entities in `ApplicationCore`, EF configs and the SDK-calling gateway in `Infrastructure`, endpoints in `PublicApi` (following the existing layering); the SDK is referenced from the project(s) that call it. The reference is a local `ProjectReference` to this plugin's install path (not portable to CI without the plugin).
9. **Pagination/page-size** of plan listing: `PerPage=200`, `MaxPages` small constant; plans are few.
10. **Error mapping.** `ExceptionMiddleware` turns unknown exceptions into 500 with the exception message; the new endpoints catch SDK and store exceptions themselves and return `IResult` (400 bad plan, 404 unknown user, 409 in progress, 422/502 Maxio refusal, 504/503 timeout/unknown) so Maxio internals are not leaked.
11. **`uniqueness_token`**: not used (see readiness row 5).
12. `ReadCustomerByReference`'s not-found status is not in the map (UNVERIFIED, see its row).

## 7. Decisions settled at implementation (replaces every `YOUR CALL`)

1. Default plan: `planHandle` is optional; when omitted `Maxio:DefaultPlanHandle` (optional extra key, set in user-secrets to the Pro handle, never in the repo) is used, else 400. Either way the plan must be in the live listing (`MaxioSubscriptionBillingService.SubscribeAsync`).
2. Identity: JWT name claim resolved via `UserManager` to `ApplicationUser.Id` (`CallerIdentity.ResolveAsync`); unknown user -> 401.
3. Customer name: first = email local part, last = constant `eShopOnWeb` (`EnsureCustomerAsync`).
4. Payment: live test showed Maxio refuses with 422 ("No payment method was on file") when collection method is left at its default. For plans with `require_credit_card=false` the code sets `payment_collection_method` = `remittance` (`MaxioSettings.NoPaymentMethodCollection`, overridable to `invoice`; `CollectionFor`). Verified live on the sandbox: subscription created, state active.
5. One subscription per (user, plan): composite key.
6. Next billing date = `NextAssessmentAt ?? CurrentPeriodEndsAt` (`ToView`).
7. No EF migration: in-memory only; link tables exist via model configuration only.
8. Layering: entities/interface/settings in ApplicationCore, service+DI in Infrastructure, endpoints in PublicApi.
9. Plan paging: `PerPage=200`, `Maxio:MaxPlanPages` (default 5).
10. Errors mapped in endpoints: 400 plan not listed, 401 unknown user, 409 in progress, 422 refused, 503 provider/unknown outcome.
11. `uniqueness_token` unused. 12. `ReadCustomerByReference`/`FindSubscription` not-found verified live = 404.
13. Extra tunables (all optional, defaults in `MaxioSettings`): per-attempt timeout 10s, request budget 25s, stale claim 120s.
