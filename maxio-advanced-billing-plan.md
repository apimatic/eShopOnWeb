# Maxio Advanced Billing plan: eShopOnWeb subscriptions

SDK root (plugin-relative): `sdk/dotnet/` in the `maxio-advanced-billing` plugin. All `src/...` and `map/...` paths below are relative to it. Root namespace `MaxioAdvancedBilling`. Every operation here is throw-only. None is a `Pageable`. All of them resolve through server group `Production` (sdk-map.md defaults table).

Repo exemplars (read them when you edit, not before):
- Endpoint shape: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. This is an `IEndpoint<...>` with `AddRoute` plus `HandleAsync`, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, and `.Produces<>()` / `.WithTags()`. Request and response types live in `Endpoint.X.cs` partial files and derive from `BaseRequest`/`BaseResponse` with `CorrelationId()`.
- 409 mapping: `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps `DuplicateException` (`src/ApplicationCore/Exceptions/DuplicateException.cs`) to 409.
- Store: `src/Infrastructure/Data/CatalogContext.cs`, with entity configs in `src/Infrastructure/Data/Config/*Configuration.cs`. In-memory or SQL Server is chosen in `src/Infrastructure/Dependencies.cs`.
- Caller identity: the JWT carries only `ClaimTypes.Name` = user name, plus roles (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`). PublicApi registers `AddIdentity<ApplicationUser, IdentityRole>` (`src/PublicApi/Program.cs`). User secrets are already enabled in `src/PublicApi/PublicApi.csproj` (`UserSecretsId`).

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter. Build it with an object initializer whose property names are the record's own, never with flat arguments. Every call has the shape `(Record request, RequestOptions? requestOptions = null, CancellationToken cancellationToken = default)`.
> ⚠ **Every SDK type is written fully qualified with the namespace its source path implies**, taken from the path the map gives for THAT type, never from where a neighbouring type sits. Request records are in `MaxioAdvancedBilling.Requests.<Controller>`, models in `MaxioAdvancedBilling.Models`, enums in `.Models.Enums`, AnyOf unions in `.Models.AnyOf`, and typed errors in `MaxioAdvancedBilling.Errors`. `RawError` is in `MaxioAdvancedBilling.Core.ErrorResponse`. `ApiException<T>` and the rest of the exception family are in `MaxioAdvancedBilling.Core.Exceptions`.

- **What triggers the catch.** The write's own `catch` covers `SdkConnectionException` (which includes `SdkTimeoutException`), `OperationCanceledException` from the budget token, and `ResponseDeserializationException` on the write.

## 6. Assumptions & Blockers

**Assumptions (decided, proceeding):**

- **A1, customer reference.** The Maxio customer `Reference` = the eShop user name from the JWT `ClaimTypes.Name`. Under `UseOnlyInMemoryDatabase=true`, `ApplicationUser.Id` is regenerated by the seed on every run, while the user name is stable. Using the name means a Maxio customer created in an earlier run is found by `ReadCustomerByReference` and adopted rather than duplicated.
- **A2, customer name fields.** `CreateCustomer` requires `FirstName`, `LastName` and `Email`, and eShop users have no name fields. Decision: `Email` = `ApplicationUser.Email` (via `UserManager.FindByNameAsync`), falling back to the user name. `FirstName` = the email local part. `LastName` = `"eShop"`. (YOUR CALL)
- **A3, local claims are lost on restart.** The in-memory store loses claims on restart. That is acceptable because both writes carry provider-side references: the customer reference is documented unique, and the subscription is found by reference before any create. A re-run therefore converges on the existing Maxio records. Under SQL Server, the two new entities need an EF migration for `CatalogContext`; the in-memory provider ignores migrations. (YOUR CALL: add the migration if `dotnet ef` is available, otherwise note it.)
- **A4, `MAXIO_ENVIRONMENT`.** It is **not bound** to any configuration key, because it is not one of the four mandated keys and inventing one would add a setting the deployment does not document. `options.Environment` stays the SDK default `ServerEnvironment.Us`. The current value of `MAXIO_ENVIRONMENT` is `US`, which is the `Us` wire value, so behaviour matches. An EU-hosted site is reached by setting `Maxio:BaseUrl` (for example `https://<site>.ebilling.maxio.com`), which is applied verbatim to `Server.Production.Us.BaseUrl`. Sandbox versus live is a property of the site and key, not of `ServerEnvironment`; the SDK declares no sandbox member.
- **A5, one subscription per plan.** One subscription - **A7, payment collection method.** Revised after live traffic: with `payment_collection_method` unset, the sandbox answered `CreateSubscription` with 422 `["No payment method was on file for the $299.00 balance"]`, so automatic collection needs a payment method.
