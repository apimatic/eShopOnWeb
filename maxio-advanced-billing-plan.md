SDK root (plugin-relative): `sdk/dotnet/` · map: `sdk/dotnet/sdk-map.md` + `sdk/dotnet/map/operations/*.md`. All `src/...` paths below are relative to that root; `A/` = `src/MaxioAdvancedBilling/`.

## 1. Scope & sequence

Repo facts read (exemplars to imitate): endpoint style = `IEndpoint<IResult, TRequest, TDeps>` with `AddRoute` + `HandleAsync`, `.Produces<>().WithTags("...Endpoints")`, request/response DTOs as separate files `Xxx.XxxRequest.cs` / `Xxx.XxxResponse.cs` — exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (+ `CatalogBrandEndpoints/CatalogBrandListEndpoint.cs` for a GET); auth = `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` on the lambda (exemplar: same Create file, there with Roles); error mapping = `src/PublicApi/Middleware/ExceptionMiddleware.cs` (`DuplicateException` -> 409, anything else -> 500); EF entity config = `IEntityTypeConfiguration<T>` in `src/Infrastructure/Data/Config/` (exemplar `BasketConfiguration.cs`) picked up by `CatalogContext.OnModelCreating` via `ApplyConfigurationsFromAssembly`; DbContext = `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`), in-memory vs SQL chosen in `src/Infrastructure/Dependencies.cs`; PublicApi `Program.cs` registers services before `builder.Build()`.
JWT facts read (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`): the token carries ONLY `ClaimTypes.Name` (the user name, e.g. an email) and `ClaimTypes.Role`. No `NameIdentifier`, no email claim, no first/last name. `ApplicationUser : IdentityUser` adds no fields.

## 6. Assumptions & Blockers

Blockers: none that stop planning.

Assumptions:
- A1 (identity — DECIDED in `SubscriptionService.ResolveUserAsync`): the JWT carries only `ClaimTypes.Name` and roles. Caller identity = that name claim, resolved to the Identity user via `UserManager<ApplicationUser>.FindByNameAsync` (registered in `src/PublicApi/Program.cs`); the userId used as customer/subscription reference and claim PK is the Identity user `Id`. A token whose user no longer exists -> 401.
- A2 (customer attributes — DECIDED in `SubscriptionService.EnsureCustomerAsync`: first name = email local part, last name = fixed `Shopper`): `CreateCustomer` requires `FirstName`, `LastName`, `Email`; `ApplicationUser` has only `Email`/`UserName`. `Email` = Identity user email; first/last name have no source in the app — derive from the email local part / a fixed placeholder for last name. Flag to the user.
- A3 (one subscription per user — DECIDED: claim PK = `SubscriptionClaim.UserId`, configured in `SubscriptionClaimConfiguration`): claim PK = `UserId` alone, so a user holds at most one app-recorded subscription (a second Subscribe, even to another plan, returns the existing one). If multiple concurrent plans per user are wanted, PK must become (`UserId`, `PlanHandle`).
- A4 (default plan — DECIDED differently from the draft: optional extra key `Maxio:DefaultPlanHandle` in `MaxioSettings`, used by `SubscribeAsync` when the body names no plan; unset means `planHandle` is required. The four mandated keys are unchanged): the task names `eshop-pro` as the default subscribe target but also forbids hard-coded values and allows exactly four `Maxio:` keys, so there is no config key to carry a default. Plan: `planHandle` is required in the POST body (validated against the family's plan list); `eshop-pro` appears only as a documented example and in tests. If the user wants a server-side default, they must approve a fifth key — surface this to the user.
- A5 (region): `Environment` is not among the four keys; `Us` (SDK default) is used and `Maxio:BaseUrl` is the escape hatch for EU (e.g. an `ebilling.maxio.com` URL).
- A6 (payment, UNVERIFIED): `CreateSubscription` docs say payment info "may be required depending on the options for the Product"; the task states payment method is not required and `Product.RequireCreditCard` is exposed. No payment profile is sent. Whether the provider needs `PaymentCollectionMethod = Remittance` to accept a payment-profile-less subscription is not in the map; defensive directive: leave `PaymentCollectionMethod` unset first (task says plan setup needs none), and if the sandbox returns a 422 asking for payment info, set `CollectionMethod.Remittance` — CONFIRMED live: the sandbox answered 422 "No payment method was on file" without it, so `SubscribeAsync` always sends `PaymentCollectionMethod = CollectionMethod.Remittance`, and return the typed error `Errors` text to the caller as a 4xx otherwise.
- A7 (not-found shape, UNVERIFIED): `ReadCustomerByReference` is Case B; its not-found status is not in the map. Defensive directive: treat `ApiException<RawError>` with `StatusCode == 404` as "customer absent"; any other status/exception is an error, never "absent".
- A8 (dev restarts): in-memory claim rows vanish on restart; after restart the POST re-derives state via `ReadCustomerByReference` and `FindSubscription`/`ListCustomerSubscriptions` before creating anything so the SDK write is still not duplicated; the claim write stays first. `GET /api/my-subscriptions` uses the same fallback.
- A9: new endpoints under `src/PublicApi/SubscriptionEndpoints/` (`SubscriptionPlanListEndpoint`, `CreateSubscriptionEndpoint`, `MySubscriptionsEndpoint` + DTO files), JWT `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` on all three (the plan list also requires auth since the user is "logged-in"); entity/config in `src/Infrastructure/Data`/`Config` (or ApplicationCore entity + Infrastructure config, following `Basket`).
- A10: SDK is referenced via local `ProjectReference` to `<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`, local to this machine (netstandard2.0 library; PublicApi targets whatever `global.json` 8.0 gives).
