# Maxio Advanced Billing plan: eShopOnWeb "Subscribe"

SDK source (plugin-relative): `sdk/dotnet/` (map: `sdk/dotnet/sdk-map.md`, pages `sdk/dotnet/map/operations/*.md`). Business rules: `business-rules/` (ids cited as `rule: <file>#<id>`). Paths in the **source** column are relative to `sdk/dotnet/`.

## 1. Scope & sequence

Additive, parallel to Catalog/Basket/Order. No existing entity/endpoint is changed. Endpoints in `src/PublicApi` (MinimalApi.Endpoint style), JWT only.

| # | Step | Operations |
| --- | --- | --- |
| 1 | Settings + client: bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` (optional); register one singleton `MaxioAdvancedBillingClient`; host fails fast on blank ApiKey/Subdomain/ProductFamilyHandle. | none |
| 2 | `GET /api/subscription-plans`: list plans offered by the configured product family (handle from config) and return handle, name, price (`PriceInCents` -> decimal), interval, interval unit, plus `trial`/setup info as returned. Same list-read is reused by step 3 as the legal-plan set. | `client.ProductFamilies.ListProductsForProductFamily` (page loop) |
| 3 | `POST /api/subscriptions` body `{ planHandle }`: (a) identity from JWT; (b) read plans (step 2) and reject (400) a `planHandle` not among them, BEFORE any write or claim; (c) write the claim row (DUPLICATE CLAIMS); (d) ensure Maxio customer (reference = eShop user identity); (e) create subscription; (f) record Maxio ids in the claim row, return plan/price/state/next-billing-date. On a repeat call with a completed claim: return the stored subscription re-read from Maxio (200), never create. | `ListProductsForProductFamily`, `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`, `Subscriptions.CreateSubscription`, settle: `Customers.ReadCustomerByReference`, `Subscriptions.FindSubscription`, `Customers.ListCustomerSubscriptions` |
| 4 | `GET /api/my-subscriptions`: resolve the caller's Maxio customer id from the local mapping (none -> empty list); read the customer's subscriptions; keep only those whose `Product.Handle` is in the offered plans; project plan/price/state/next billing date. | `Customers.ListCustomerSubscriptions` (+ `ListProductsForProductFamily`) |
| 5 | Persistence: two entities in `CatalogContext` (see DUPLICATE CLAIMS), EF config, a SQL Server migration for production; in-memory DB ignores migrations. | none |

### DUPLICATE CLAIMS

Order for every row: claim -> SDK call -> record the result. Persistence is the app's own `CatalogContext` store (the one the codebase keeps its records in), via two new aggregate entities (names YOUR CALL (settled, see 5b); suggested `MaxioCustomerLink` and `MaxioSubscriptionLink`): `MaxioCustomerLink { UserId (string, PK), MaxioCustomerId (int?), CreatedAt }`; `MaxioSubscriptionLink { UserId + PlanHandle (composite PK), State (Claimed/Completed/Unknown), MaxioCustomerId (int?), MaxioSubscriptionId (int?), Reference, CreatedAt }`. Both need `IAggregateRoot`, and since `BaseEntity.Id` is the codebase's key, the composite/string keys are mapped in their `IEntityTypeConfiguration` with `HasKey(...)` (ignoring `Id`, or key on it with a unique index only where the provider enforces it: a PK is refused by in-memory too, a unique index may not be). A provider idempotency token goes beside the claim, never in place of it.

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| `Subscriptions.CreateSubscription` (POST /api/subscriptions, same user + same plan) | `MaxioSubscriptionLink` in `CatalogContext` (insert, saved before any SDK write) | primary key `(UserId, PlanHandle)`: the store refuses the second insert | in the POST handler/service `catch` for `DbUpdateException` (and, on the same-context tracking path, `InvalidOperationException`/`ArgumentException` from the in-memory provider: exact type `UNVERIFIED`, test it) around the repository `AddAsync`; on catch: load the existing row, return its stored result if `Completed`, otherwise throw `DuplicateException` (-> 409 via `ExceptionMiddleware`). Release (delete the row) when Maxio refuses the create (typed 422 or other definite non-2xx), never when the outcome is unknown. | claim write: `MaxioSubscriptionService.SubscribeAsync` (`_db.SaveChangesAsync` after `MaxioSubscriptionLinks.Add`); catch: `HandleExistingClaimAsync` (in-memory provider raises `ArgumentException`, SQL Server `DbUpdateException`; both caught); then SDK call `_client.Subscriptions.CreateSubscription`; release: `ReleaseClaimAsync` |

## 5b. YOUR CALL decisions (settled in code)

- Entity names/keys: `MaxioCustomerLink` (PK `UserId`), `MaxioSubscriptionLink` (PK `UserId`+`PlanHandle`), configured in `Infrastructure/Data/Config/MaxioLinkConfiguration.cs`.
- Caller identity: JWT `ClaimTypes.Name` (`User.Identity.Name`, the e-mail) is the user id, the Maxio `Customer.Reference` and the customer e-mail (`CreateSubscriptionEndpoint`). FirstName = local part of the e-mail, LastName = `Customer` (`MaxioSubscriptionService.CreateCustomerAsync`).
- `PaymentCollectionMethod`: **`Remittance`** (`SubscribeAsync`). VERIFIED live: with it unset the sandbox answers 422 "No payment method was on file for the $299.00 balance" for both plans despite the plans being flagged "payment method not required"; with `Remittance` the subscription is created without card capture.
- Timeouts: per attempt 10s, `MaxRetries` 2 (`MaxioServiceCollectionExtensions`), whole-call budget 30s (`MaxioSubscriptionService.Budget`). Stale claim age 2 min (`StaleClaimAge`).
- Credential validation: `MaxioServiceCollectionExtensions.AddMaxioSubscriptions` / `RequireValue` (ApiKey, Subdomain, ProductFamilyHandle must be non-blank; BaseUrl optional).
- Default plan: `planHandle` is required in `POST /api/subscriptions` (no hard-coded default; 400 lists offered plans).
- `MAXIO_ENVIRONMENT` is not bound (only four keys); sandbox is selected by the subdomain/API key.
- Error mapping (`ExceptionMiddleware`): unknown plan 400, Maxio 4xx rejection passthrough (422), duplicate in progress 409, provider unavailable/unknown 502/503.

## 6. Assumptions & Blockers

Blockers: none. Persistence exists (EF Core `CatalogContext`; PK refused by the in-memory provider), so no Blocker for DUPLICATE CLAIMS.

Assumptions (please confirm / will be settled in code and recorded here):

1. **Default plan.** The task names `eshop-pro` as the default subscribe target but also forbids hard-coding and allows only four config keys. Plan: `POST /api/subscriptions` body `planHandle` is required; if it is omitted the API returns 400 listing offered plans. `eshop-pro` appears nowhere in code. (If a default is wanted, a fifth key would be needed; the task restricts keys, so not added.)
2. **Caller identity.** The issued JWT carries only `ClaimTypes.Name` (user name, which eShop sets to the e-mail) and roles. "Eshop user id" / customer reference = that Name claim value, unless the main agent resolves `ApplicationUser.Id` through `UserManager` (YOUR CALL (settled, see 5b); mind that a rename would orphan the link). Name/e-mail for the Maxio customer: `Email` = the name claim; `FirstName`/`LastName` are `required` by `CreateCustomer` and the token has no such claims: needs a decision (YOUR CALL (settled, see 5b): derive from the identity record, or the local part of the e-mail).
3. **No payment method.** Task says plans do not require one, so none is sent. `UNVERIFIED`: whether Maxio accepts the create for a paid plan ($299) without a payment profile (rule: subscriptions.md "product's options require payment information"); if the seeded plan actually requires one, the provider returns 422 and that is a Blocker to raise. `PaymentCollectionMethod` is left unset (YOUR CALL (settled, see 5b): `Remittance`/`Automatic`).
4. **Sandbox.** There is no sandbox `ServerEnvironment`; sandbox = a separate site via `Maxio:Subdomain`/`Maxio:BaseUrl`. `MAXIO_ENVIRONMENT` has no `Maxio:` key (exactly four keys allowed); it is only a loader-side label.
5. **Numeric ids** are never stored as constants; the Maxio customer id and subscription id come from responses. Plan price shown = `Product.PriceInCents` of the product (default price point), in cents/100 (currency not on `Product`; label as site currency).
6. **Persisted subscription state** is not authoritative: `GET /api/my-subscriptions` and the POST reply read state/next billing (`NextAssessmentAt`, nullable) live from Maxio.
7. **Migration.** A SQL Server migration for the two entities is generated for production (`src/Infrastructure/Data/Migrations`); in-memory runs ignore it and rely on the model's keys.
8. **Subscription reference uniqueness** at Maxio is `UNVERIFIED`; the settle path also matches by product handle in `ListCustomerSubscriptions`.
9. **PublicApi project reference.** SDK is not on NuGet: add `<ProjectReference>` to `sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` in the plugin (local to this machine; say so in the hand-over). `netstandard2.0` is consumable from the repo's target framework; the repo uses central package management (`Directory.Packages.props`), the SDK has its own.
