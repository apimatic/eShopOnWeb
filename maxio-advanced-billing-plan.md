**Repo conventions (read; one exemplar each)**
- Endpoint = `IEndpoint<IResult, TRequest, ...>` class with `AddRoute(IEndpointRouteBuilder)` using `app.MapPost("api/...", [Authorize(... AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)] ...)`, `.Produces<TResponse>().WithTags("...Endpoints")`, request/response classes in sibling files `X.XRequest.cs` / `X.XResponse.cs` (`BaseRequest`/`BaseResponse` with `CorrelationId()`): exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (+ its `.CreateCatalogItemRequest.cs`, `.CreateCatalogItemResponse.cs`). Endpoints are discovered by `AddEndpoints()` / `MapEndpoints()` in `src/PublicApi/Program.cs`; no registration needed per endpoint.
- Error mapping: `src/PublicApi/Middleware/ExceptionMiddleware.cs` maps `DuplicateException` -> 409, anything else -> 500 with message. New expected failures (unknown plan 400/404, billing unavailable 502/503) need explicit mapping; do not leak SDK exception messages. Exemplar for the exception type: `src/ApplicationCore/Exceptions/DuplicateException.cs`.
- Persistence exemplar: `src/Infrastructure/Data/CatalogContext.cs` (configs applied via `ApplyConfigurationsFromAssembly`), `src/Infrastructure/Data/Config/BasketConfiguration.cs`; DB provider chosen in `src/Infrastructure/Dependencies.cs` (`UseOnlyInMemoryDatabase`). Repository: `IRepository<T>`/`EfRepository<T>` registered open-generic in `Program.cs`; a claim write may use `CatalogContext` directly if `IRepository<T>` requires `IAggregateRoot`.
- Identity from token: the JWT built in `src/Infrastructure/Identity/IdentityTokenClaimService.cs` carries ONLY `ClaimTypes.Name` (the user name) and `ClaimTypes.Role`. There is no email or NameIdentifier claim. The user id and email must be resolved with `UserManager<ApplicationUser>.FindByNameAsync(User.Identity.Name)` (registered in `Program.cs`). Never take a user id from a request body or query.
- Config binding exemplar: `Program.cs` uses `Configure<T>(builder.Configuration...)` and `GetRequiredSection`.

### Client construction / auth / server

- Client: `new MaxioAdvancedBilling.MaxioAdvancedBillingClient(HttpClient, MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions)`; DI: `services.AddMaxioAdvancedBillingClient(options => ...)` (map `sdk-map.md` *Getting a client*). Options members: `Environment`, `Retry`, `Logging`, `TimeProvider`, `Server`, `StreamReadTimeout`, `Hooks`, `BasicAuth`.
- Auth: HTTP Basic: `options.BasicAuth = new MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials { Username = <Maxio:ApiKey>, Password = "x" }` (map *Servers & auth*: username is the API key, password is `x`; `Username`/`Password` both `required`). Password `x` is the documented protocol constant, not a configurable secret.
- Server: group `Production` only (every operation in scope; `Ebb` is not touched). `options.Environment` default `ServerEnvironment.Us` (`MaxioAdvancedBilling.Servers.ServerEnvironment`). Default base URL template `https://{site}.chargify.com` with `options.Server.Production.Us.Site` (default literal `"subdomain"`) -> set `Site = Maxio:Subdomain`. `Maxio:BaseUrl` when set: assign verbatim to `options.Server.Production.Us.BaseUrl` (a plain string property of `src/MaxioAdvancedBilling/Servers/ProductionOptions.cs`, whose default is a `{site}` template; a value without `{site}` is used as given - how a trailing slash/path is joined is `UNVERIFIED`). Eu environment is not used: Maxio:* has no key to select it.

## 6. Assumptions & Blockers

**Blockers**: none found. The map covers customer create/read-by-reference, subscription create/read/list-by-customer and family-scoped product listing by handle (`handle:` prefix documented on the request member).

**Assumptions**
1. One active subscription per eShopOnWeb user in this family (the claim PK is `UserId`); a second POST for the same user, even for a different plan, returns the existing result / 409 rather than creating another. If multiple subscriptions per user are wanted, the claim key must become (`UserId`, `PlanHandle`) - tell me and I will revise the rows.
2. "Default" for `eshop-pro` is not a field of the family listing; the POST requires an explicit plan handle (no hard-coded default plan).
3. The token carries only the user name; user id and email come from `UserManager<ApplicationUser>`. The Maxio customer `FirstName`/`LastName` are required by the SDK but the identity user has no such fields (to be read at implementation from `ApplicationUser`); if absent, the email local part / user name is used as a placeholder (decision at implementation time).
4. Metered component `api-call` is not enrolled by Subscribe (no `components` sent); no payment profile sent (plans do not require one). If Maxio rejects creation with a payment-required 422 the call fails with a mapped 4xx; that would be provider behaviour contradicting the seeding statement (`UNVERIFIED`).
5. Plan listing excludes archived products (`IncludeArchived` not set); `Product.Handle` null items are skipped.
6. Customer ids / subscription ids from Maxio are stored only after being returned by Maxio in this run; seeded numeric ids are never used.
7. EF migrations are only needed for the SQL Server path; in-memory run needs none.
8. Sandbox isolation relies on configured site/key (SDK has no sandbox environment), see row 8.
9. `UNVERIFIED`: trailing-slash/path handling of `Maxio:BaseUrl` override; whether Maxio enforces uniqueness of subscription `reference`.

**Implementation notes (post-build)**
