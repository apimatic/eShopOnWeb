# Maxio Advanced Billing plan: eShopOnWeb subscriptions (PublicApi)

Skill: `maxio-advanced-billing:dotnet-integrate-maxio-advanced-billing`. SDK source and map: `sdk/dotnet/` inside the maxio-advanced-billing plugin (all **source** paths below are relative to that SDK root). Build reference: `<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj` (not on NuGet; the ProjectReference is machine-local, see §6).

Repo exemplars (imitate them, don't copy them):
- endpoint: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (`IEndpoint<…>` + `AddRoute` + `MapPost("api/…")` + `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` + `.Produces<>().WithTags()`, request/response split into `*Endpoint.*Request.cs` / `*Response.cs`, `BaseRequest`/`BaseResponse` with `CorrelationId()`)
- store: `src/Infrastructure/Data/CatalogContext.cs` + `src/Infrastructure/Data/Config/CatalogBrandConfiguration.cs` (`IEntityTypeConfiguration<T>`, auto-applied)
- DI: `src/PublicApi/Program.cs`
- error mapping: `src/PublicApi/Middleware/ExceptionMiddleware.cs` (`DuplicateException` becomes 409, everything else 500)
- caller identity: `src/Infrastructure/Identity/IdentityTokenClaimService.cs`. The JWT carries **only** `ClaimTypes.Name` (= user name, which is the email for the seeded users) and `ClaimTypes.Role`. There is no user-id claim.

## 1. Scope & sequence

| # | Step | Operations |
|---|---|---|
| 1 | Reference the SDK project and bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, `Maxio:BaseUrl` with fail-fast validation. Register the client (Production server group; `Site` from Subdomain, or `BaseUrl` verbatim when it's set). | none |
| 2 | Add a claim/link store to `CatalogContext`: a customer-link row and a subscription-enrollment row, each keyed by a **string primary key** (see DUPLICATE CLAIMS). | none |
| 3 | One billing service class fronting the SDK. Every call goes through one bounded helper (budget token linked to `RequestAborted`). | all below |
| 4 | `GET /api/subscription-plans`: list the configured family's plans, walking pages with a cap and a partial flag. | `ProductFamilies.ListProductsForProductFamily` |
| 5 | Ensure the Maxio customer for the caller: claim the row, then `ReadCustomerByReference` (adopt an existing customer, which covers restart and a lost in-memory store), then `CreateCustomer` if none exists, then record the customer id. A 422 or an unknown outcome on create is settled by `ReadCustomerByReference`. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 6 | `POST /api/subscriptions`: validate the plan handle against step 4's set. Resolve the site's invoicing architecture with `Sites.ReadSite`, cached for the process lifetime (only a successful, non-null read is cached). A failed or indeterminate read fails the subscribe with 502/503 **before** any claim or write. Then claim the enrollment, adopt any existing subscription carrying the same reference (`ListCustomerSubscriptions`), else `CreateSubscription` with `PaymentCollectionMethod` = `Remittance` (Relationship Invoicing) or `Invoice` (legacy), then record the result. Reply with plan, price, state and next billing date. An unknown outcome is settled with `ListCustomerSubscriptions` matched on `reference`. | `Sites.ReadSite`, `Subscriptions.CreateSubscription`, `Customers.ListCustomerSubscriptions` |
| 7 | `GET /api/my-subscriptions`: read the caller's subscriptions using the **stored** customer id, falling back to `ReadCustomerByReference` when no link row exists. Settle any enrollment rows left `Unknown`. | `Customers.ListCustomerSubscriptions`, `Customers.ReadCustomerByReference` |
| 8 | Tests (stubbed `HttpClient`), then a live sandbox run: authenticate, list plans, subscribe twice, list my subscriptions. | none |

Not used (the map has them, but they're out of scope): `Subscriptions.FindSubscription`, `Subscriptions.ListSubscriptions`, `Customers.ListCustomers`, `ProductFamilies.ReadProductFamily`, `Products.ReadProductByHandle`.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
|---|---|---|
| The plan handle a caller sends to `POST /api/subscriptions` must be the `Product.Handle` of a non-archived product returned for the configured family (`handle:` + `Maxio:ProductFamilyHandle`). | `CreateSubscription` (`product_handle`) ← `ListProductsForProductFamily` | In the billing service's subscribe method, **before** the enrollment claim and `CreateSubscription`. It calls the same plan-listing member that backs `GET /api/subscription-plans`. If the handle is missing, reply 400 and make no claim and no SDK write. If that plan listing came back partial and the handle wasn't seen, reply 503 rather than 400. |
| The offered plan must not need a payment method, because this flow captures none: `Product.RequireCreditCard != true` on the product returned for that handle. | `CreateSubscription` ← `ListProductsForProductFamily` | Same member and check as above. Such plans are also left out of `GET /api/subscription-plans`. |
| `customer_id` on `CreateSubscription` must be the `Customer.Id` that `CreateCustomer` or `ReadCustomerByReference` returned **for this caller's own reference**, as stored in the caller's customer-link row. It never comes from caller input. | `CreateSubscription` (`customer_id`) ← `CreateCustomer` / `ReadCustomerByReference` | In the billing service's subscribe method, which reads the caller's link row (keyed by the caller-derived reference) before `CreateSubscription`. |
| `payment_collection_method` on `CreateSubscription` must be a value the doc lists as valid for the site's invoicing architecture, and never `automatic` (this flow captures no payment method). `Site.RelationshipInvoicingEnabled == true` means send `CollectionMethod.Remittance`; `== false` means send `CollectionMethod.Invoice`; `null` or a failed read means no write. | `CreateSubscription` (`payment_collection_method`) ← `Sites.ReadSite` | In the billing service's subscribe method, through the process-cached architecture resolver. It runs **before** the enrollment claim and `CreateSubscription`. A read failure or a null flag returns 502/503 with no claim and no SDK write, and isn't cached. Code: `SubscriptionBillingService.SubscribeAsync` (after the plan check, before `EnsureCustomerAsync`) calls the singleton `SiteCollectionMethodCache.GetOrResolveAsync(ReadSiteCollectionMethodAsync, …)`; `SubscriptionBillingService.ReadSiteCollectionMethodAsync` (`_client.Sites.ReadSite`) maps the flag; the method is passed through `EnrollAsync` to `CreateSubscriptionAsync` as `CreateSubscription.PaymentCollectionMethod`. Tests: `SiteCollectionMethodTests`. |
| `CustomerId` on `ListCustomerSubscriptions` must be the caller's own stored `Customer.Id`. It's never accepted from the request. | `ListCustomerSubscriptions` ← `CreateCustomer` / `ReadCustomerByReference` | In the billing service's my-subscriptions method, which takes the id from the caller's link row, or from `ReadCustomerByReference(caller reference)` when no link row exists yet. |

**Hazard (verbatim):** a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

(This hits this scope directly: `ProductResponse.Product`, `CustomerResponse.Customer`, `SiteResponse.Site`, `CreateCustomerRequest.Customer`, `CreateSubscriptionRequest.Subscription` and `ErrorListResponse1.Errors` are `required`. On the two POSTs, a `ResponseDeserializationException` with a 2xx status means the write **landed**, so it's an unknown outcome to reconcile, not a failure.)

## 6. Assumptions & Blockers

**Blockers:** none. Every capability in scope (list plans by family handle, look up a customer by reference, create a customer, create a subscription, list a customer's subscriptions) is on the map.

**Assumptions** (decide at implementation; none of them blocks):
- **A1, claim durability.** `CatalogContext` runs on the EF in-memory provider here, so claim rows don't survive a restart. That's acceptable because a restart-lost claim is backed up by the provider-side re-reads that run **after** the claim: `ReadCustomerByReference` before `CreateCustomer`, and the `ListCustomerSubscriptions` reference-match before `CreateSubscription`. Against SQL Server the claims are durable. A new entity needs an EF migration for SQL Server deployments: `YOUR CALL — not in the map`. The in-memory run ignores migrations.
- **A2, `MAXIO_ENVIRONMENT`.** The task mandates no `Maxio:` key for it, and the SDK's `ServerEnvironment` has only `Us`/`Eu` (no sandbox member). The plan uses `ServerEnvironment.Us` (map default) and doesn't bind `MAXIO_ENVIRONMENT`. The sandbox is selected by the site subdomain and API key. If an EU site is ever required, adding a key is `YOUR CALL — not in the map`.
- **A3, customer identity and reference.** The JWT carries only `ClaimTypes.Name` (no user id), and the in-memory Identity store re-creates users with new ids on each run. So the customer reference is derived deterministically from the normalized user name (recommended: `eshop-` + a truncated lowercase-hex SHA-256 of the upper-cased user name, so no raw email sits in the reference). This keeps it stable across restarts. Maxio's max reference length isn't in the map; keep it ≤ 40 chars. `YOUR CALL — not in the map`.
- **A4, required customer names.** `CreateCustomer` requires `first_name`, `last_name` and `email`, but `ApplicationUser` holds only `UserName`/`Email`. Plan: `Email` = the user's email (or the user name when that's empty), `FirstName` = the email's local part, `LastName` = a fixed placeholder (e.g. `"Customer"`). `YOUR CALL — not in the map`.
- **A5, one subscription per user per plan.** The enrollment claim key is (customer reference, plan handle). A repeat subscribe to the same plan returns the existing subscription; a different plan creates a second subscription. Cancel/resubscribe is out of scope, so a canceled subscription keeps its reference and blocks resubscribing to that plan until cancel is in scope. `YOUR CALL — not in the map`.
- **A6, the settings' env-var names.** `MAXIO_API_KEY` etc. don't bind to `Maxio:ApiKey` by themselves. The plan copies them into user-secrets (dev). An optional code fallback that maps the four `MAXIO_*` variables onto the `Maxio:` keys when those are absent is `YOUR CALL — not in the map`, and it must never write their values anywhere.
- **A7, SDK reference portability.** The `ProjectReference` points into this machine's plugin install (`<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`). CI and teammates need the plugin installed and the reference re-pointed. The SDK targets `netstandard2.0` with `LangVersion 14`, which needs the installed .NET 10 SDK (the repo's `global.json` pins 8.0.x; per the task, use roll-forward).
- **A8, error mapping to callers.** Provider 422 on subscribe becomes 400/422 with Maxio's `errors` strings. Provider 401/403 or misconfiguration (404 on the family) becomes 502/500. Budget exhaustion on a read becomes 504. Unknown write outcome becomes 202 with state `unknown`. In-progress claim becomes 409 (via the existing `DuplicateException` mapping in `ExceptionMiddleware`). `YOUR CALL — not in the map`.
- **A9, collection method (decided by the coordinator, settled).** `CreateSubscription` sends `payment_collection_method` = `remittance` when `Site.RelationshipInvoicingEnabled == true`, and `invoice` when it's `false`. The architecture is read with `Sites.ReadSite` and cached for the process lifetime. A failed read, or a `null` flag, fails the subscribe before any claim or write and isn't cached. No new configuration key.
