# Maxio Advanced Billing plan: eShopOnWeb subscription billing (PublicApi)

SDK root (plugin-relative): `sdk/dotnet/`. Every map/source citation below is relative to it. Project reference to add (from `src/PublicApi/PublicApi.csproj`): `<plugin-root>/sdk/dotnet/src/MaxioAdvancedBilling/MaxioAdvancedBilling.csproj`.

Repo exemplars to copy, one per convention:
- MinimalApi `IEndpoint<…>` + `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` + `.Produces<>().WithTags()`: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`. Request/response DTOs derive from `BaseRequest`/`BaseResponse` (`src/PublicApi/BaseMessage.cs` carries `CorrelationId()`).
- Entity config: `src/Infrastructure/Data/Config/BasketConfiguration.cs`. DbContext: `src/Infrastructure/Data/CatalogContext.cs`. Store selection (`UseOnlyInMemoryDatabase`): `src/Infrastructure/Dependencies.cs`.
- Caller identity: the JWT carries only `ClaimTypes.Name` = userName, plus roles (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`). The codebase already keys per-user records by userName (`Basket.BuyerId`, max length 256).
- Error translation: `src/PublicApi/Middleware/ExceptionMiddleware.cs`. It writes `exception.Message` to the client on any unhandled exception.
- Integration tests: `tests/PublicApiIntegrationTests/ProgramTest.cs` (`WebApplicationFactory<Program>`, config from `appsettings.test.json`).

## 1. Scope & sequence

| # | Step | Operations |
|---|------|------------|
| 1 | Add the SDK `ProjectReference` to PublicApi. Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle` and `Maxio:BaseUrl` into one settings class. Validate it at startup (PROD #1). Register the client once with `services.AddMaxioAdvancedBillingClient(...)`. | none (client construction) |
| 2 | Add claim/link entities to `CatalogContext` with string primary keys (DUPLICATE CLAIMS). They are plain EF entities with no SDK types. | none |
| 3 | Add one billing service class that fronts the SDK. Every call goes through one budget helper (PROD #3). It translates SDK exceptions into application exceptions so `ExceptionMiddleware` never echoes an SDK message. | all below |
| 4 | Plan catalogue. Walk the pages of the configured family's products (ProductFamilyId = `"handle:" + Maxio:ProductFamilyHandle`), drop archived products, and map them to plan DTOs. | `ProductFamilies.ListProductsForProductFamily` |
| 5 | Ensure a customer. Claim, then look up by reference. On 404, create. Record the Maxio customer id. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 6 | Subscribe. Check the plan handle against step 4's list (INVARIANTS). Take the claim, then look up by the deterministic subscription reference (adopt it if found), else create. Record the result. | `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription`, `Subscriptions.ReadSubscription` (on a completed claim) |
| 7 | My subscriptions. Resolve the customer by reference (do not create), list their subscriptions, and map plan/price/state/next-billing-date. | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` |
| 8 | Endpoints: `GET api/subscription-plans`, `POST api/subscriptions`, `GET api/my-subscriptions`. All three are JWT-authenticated. The caller is `HttpContext.User.Identity.Name`. | n/a |
| 9 | Tests: the duplicate-claim race, the unknown-outcome connection failure on both writes, and the page-cap truncation. Existing PublicApi integration tests must keep starting (Assumptions A7). | stubs |

Not in scope: metered usage for `api-call` (Ebb server group), payment profiles, cancel/upgrade.

## 2. CONTRACT SHEET

> ⚠ SIGNATURES ARE GENERATED CODE, VERBATIM. Each operation that takes input takes ONE request record as its first parameter, built with an object initializer using the record's own property names. Never pass flat arguments. Body-carrying operations wrap the body model in the record's `Body` member.
> ⚠ EVERY SDK TYPE IS WRITTEN FULLY-QUALIFIED, with the namespace its own source path implies (taken from that type's path, never from a neighbour). Request records live in `MaxioAdvancedBilling.Requests.<Controller>`, models in `MaxioAdvancedBilling.Models`, enums in `.Models.Enums`, AnyOf unions in `.Models.AnyOf`, typed errors in `MaxioAdvancedBilling.Errors`, `RawError` in `MaxioAdvancedBilling.Core.ErrorResponse`, and exceptions in `MaxioAdvancedBilling.Core.Exceptions`.

## 3. Trap notes

- **Step 1 (registration):** the DI extension runs `configure` lazily inside the singleton factory, so "registered" is not "validated". A bad setting surfaces on the first request unless something else fails the host first. **MUST load `maxio-advanced-billing:dotnet-client-initialization`**
- **Step 1 (auth):** a never-set `BasicAuth` is skipped silently and the call is still sent. A 401 can mean "nothing was sent" as easily as "wrong key". **MUST load `maxio-advanced-billing:dotnet-authentication`**
- **Step 1 (servers):** `Environment` is captured at construction while `Server` is read per request. Setting `BaseUrl`/`Site` on an environment other than the selected one is ignored silently. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- **Step 1 (timeouts):** what `RetryOptions.Timeout` and `HttpClient.Timeout` each bound, and which one is retried, decide whether the PROD #3 budget holds. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- **Step 1 (logging):** the DI path turns the SDK request logger on from the container. What it emits at which level, and what the redaction covers (query vs path vs body), decides PROD #7. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- **Steps 4–7 (calling):** every op takes one request record, and two of them (`CreateCustomer`, `CreateSubscription`) wrap the body in a nullable `Body`. Getting either wrong compiles but sends an empty body. **MUST load `maxio-advanced-billing:dotnet-calling-endpoints`**
- **Steps 4–7 (models):** `SubscriptionResponse.Subscription` is nullable while `CustomerResponse.Customer`/`ProductResponse.Product` are required. Enums are open records, not C# enums. `Errors1` is an AnyOf union. Mapping these naively loses data or throws. **MUST load `maxio-advanced-billing:dotnet-models`**
- **Step 4 (paging):** the SDK does not page this list. A hand-driven loop that trusts the provider to end it can spin or silently truncate. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`**
- **Steps 5–6 (errors):** Case A vs Case B differ per operation in this scope (CreateCustomer/CreateSubscription/FindSubscription/ListProductsForProductFamily are typed; ReadCustomerByReference/ReadSubscription/ListCustomerSubscriptions are raw). A catch written for one shape misses the other. **MUST load `maxio-advanced-billing:dotnet-error-handling`**
- **Steps 5–6 (unknown outcomes):** a connection failure, an SDK timeout, our own budget cancelling, or an unreadable 2xx on a POST does not mean the write failed. Reporting it as failed duplicates the customer/subscription on the user's retry. **MUST load `maxio-advanced-billing:dotnet-configuration-resilience`** and **`maxio-advanced-billing:dotnet-error-handling`**
- **Step 3 (error boundary):** `ExceptionMiddleware` echoes `exception.Message`, and SDK exception messages name the failed call. An untranslated SDK exception leaks provider detail to the client. **MUST load `maxio-advanced-billing:dotnet-error-handling`**
- **Step 9 (tests):** forcing a connection failure after send, faking a 422 typed body, and asserting the outgoing body need the SDK's HttpClient seam, not a mocked interface. **MUST load `maxio-advanced-billing:dotnet-testing`**

> **Hazard (verbatim):** a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 5. PRODUCTION READINESS

| # | Concern | Decision |
|---|---|---|
| 1 | Credential fail-fast | Bind the `Maxio` section into one settings class with `AddOptions<…>().Bind(…).Validate(…).ValidateOnStart()`, plus an explicit check in `Program.cs` before `builder.Build()` so a misconfigured host never starts. Rules: `Maxio:ApiKey` non-blank (whitespace counts as blank). `Maxio:ProductFamilyHandle` non-blank. **Either** `Maxio:BaseUrl` non-blank and an absolute `https` URI, **or** `Maxio:Subdomain` non-blank. The Basic credential has two parts: the username comes from `ApiKey` (checked) and the password is the constant `"x"` from the map (non-blank by construction). |
| 2 | Secret sourcing & rotation | Values come from .NET user-secrets (PublicApi already has `UserSecretsId` `bf7152d7-…`), loaded by the main agent from `MAXIO_API_KEY`/`MAXIO_SITE_SUBDOMAIN`/`MAXIO_DEFAULT_PRODUCT_FAMILY` into `Maxio:ApiKey`/`Maxio:Subdomain`/`Maxio:ProductFamilyHandle`. No value goes into any repo file. Other deployments supply the same keys through environment variables (`Maxio__ApiKey`, …) or a secret store. The options object is built once inside the DI singleton, so a rotated key takes effect **only after a process restart**. Restart-on-rotate is the accepted procedure; no hot rotation. |
| 3 | Total timeout budget | Per attempt: `options.Retry = RetryOptions.Default() with { Timeout = 10s, MaxRetries = 2 }`. The client is registered over a **named** `HttpClient` (`MaxioAdvancedBilling`), not the shared unnamed client `AddMaxioAdvancedBillingClient` uses, with `HttpClient.Timeout = 15 s` as a per-attempt backstop and `PooledConnectionLifetime = 5 min`. The options object is built once in that singleton factory. **Whole call:** one budget helper in the billing service links `HttpContext.RequestAborted` and `CancelAfter`, and every SDK call goes through it. The caller-facing budget is **20 s** for `GET api/subscription-plans` and `GET api/my-subscriptions`, and **30 s** for the whole `POST api/subscriptions` handler (one token shared by every call in it). Unknown-outcome settlement (PROD #11) runs on its own fresh 10 s token, not linked to `RequestAborted`. Worst case for POST is therefore about 40 s. |
| 4 | Write-retry ownership | `CreateCustomer` and `CreateSubscription` are both POST and are **never resent by the SDK**: `HttpMethodsToRetry` stays at its default, and adding POST is forbidden. GETs (`ListProductsForProductFamily`, `ReadCustomerByReference`, `FindSubscription`, `ReadSubscription`, `ListCustomerSubscriptions`) may be retried by the SDK. No PUT/PATCH/DELETE in scope. |
| 5 | Idempotency & ambiguous writes | **CreateCustomer:** its request record has no key member. `CreateCustomer.Reference` (`reference`) is a provider-enforced uniqueness constraint (remarks), not a key. It is deterministic per user (A3), so a repeat create is refused, and reconciliation goes through `ReadCustomerByReference`. **CreateSubscription:** no key member, and `reference` uniqueness is `UNVERIFIED`. The deterministic `Reference` (A4) plus the claim row and `FindSubscription` before create/after failure are the protection. The SDK-injected `Idempotency-Key` header is a fresh GUID per call and is **not** a key. |
| 6 | Observability | The billing service logs through `ILogger<T>`. **Information**: each Maxio operation outcome with operation name, the hashed customer/subscription reference (the cross-call correlation key) and the Maxio ids. `CorrelationId()` is not logged, because the deterministic reference already ties every call for one shopper/plan together. **Warning**: provider 4xx with `ex.StatusCode` and the typed `Errors` strings (`ErrorListResponse1.Errors` / `Errors1`). **Error**: connection/timeout/deserialization, and every outcome left `Unknown`. Provider correlation id: none. The in-scope error bodies (`ErrorListResponse1`, `CustomerErrorResponse1`) carry only `errors`. A provider request-id response header is `UNVERIFIED` and is not invented; the app's `CorrelationId()` is the correlation key. `appsettings.json` minimum level is `Warning`, so the SDK's own Information request lines are suppressed. That is accepted, because the service-level lines above replace them. |
| 7 | Sensitive data | Yes. `CreateCustomer` carries `first_name`, `last_name` and `email` (personal data). Settings: `options.Logging.LogRequestBody = false` explicitly; `options.Logging.LoggerFactory` assigned explicitly from the container's `ILoggerFactory` (never null, so the `MAXIOADVANCEDBILLINGCLIENT_LOG` env var cannot force body logging); no form bodies in scope, so no deny-list keys. The service never logs request bodies, emails or names. References sent as the query param `reference` are masked by the SDK's query allow-list, but are already a hash (A3/A4). `ExceptionMiddleware` must never receive a raw SDK exception (Step 3). |
| 8 | Environment selection | Server groups: `Production` (touched by every op in scope) and `Ebb` (not touched). Environment members: `Us` (default) and `Eu`. Every deployment sets `Environment = Us`, with `Production.Us.Site = Maxio:Subdomain`, or `Production.Us.BaseUrl = Maxio:BaseUrl` when that is set (an EU-hosted site uses the BaseUrl override, A6). The SDK declares **no sandbox environment**. Test traffic stays off live because the only site this build talks to is the one `Maxio:Subdomain`/`Maxio:BaseUrl` names, supplied per machine from user-secrets (sandbox site `cp-exp-4` here). The repo carries no value, so a fresh clone talks to nothing until configured. |
| 9 | Duplicate prevention under concurrency | See **DUPLICATE CLAIMS**. The claims live in `CatalogContext` (the codebase's own store) with string primary keys. |
| 10 | Partial results | See **PAGED READS**. `ListCustomerSubscriptions` has no paging params and returns the full list, so it has no cap. |
| 11 | Unknown outcomes | See **UNKNOWN OUTCOMES**. Each POST's own `catch` re-reads by the deterministic reference on a fresh token. If the re-read cannot settle it, the claim row stays `Unknown`, and the next POST or GET for that user re-runs the same settle member. |

## 6. Assumptions & Blockers

**Blockers:** none. Every capability in scope (customer lookup/create by reference, subscription create/find-by-reference/read/list-for-customer, product family product listing by handle) is in the map.

**Assumptions** (`YOUR CALL — not in the map` unless labelled otherwise):

- **A1. Plan selection.** `POST api/subscriptions` takes the plan handle in its body as a required field (e.g. `planHandle`). The Swagger example and the verification guide use `eshop-pro`. No default-plan setting is added, because the task fixes the `Maxio:` keys to exactly four and a hard-coded `eshop-pro` would break against another catalogue. Product price points are not used: subscribing by `ProductHandle` takes the product's default price point, and the list endpoint shows `Product.PriceInCents`/`Interval`/`IntervalUnit`.
- **A2. Identity.** The caller is `HttpContext.User.Identity.Name` (the JWT `ClaimTypes.Name` = userName). `ApplicationUser.Id` is regenerated on every in-memory restart, so it is **not** used as the Maxio key. userName is stable, matching `Basket.BuyerId`.
- **A3. Customer reference.** It is deterministic and PII-free: a fixed prefix plus a lowercase hex SHA-256 of the normalized (upper-invariant) userName. Maxio's reference length/charset limits are `UNVERIFIED`, so keep it ≤ 255 chars, `[a-z0-9-]` only. `CreateCustomer` needs `FirstName`/`LastName`/`Email` (all required). `ApplicationUser` has no names, so: `Email` = the user's Identity email (fallback: userName); `FirstName` = the email local part; `LastName` = a fixed non-blank placeholder (e.g. `"Shopper"`). Whether Maxio accepts placeholder names is `UNVERIFIED`; a 422 surfaces its `Errors`.
- **A4. Subscription reference / business rule.** One subscription per (user, plan) through this app. The reference is a fixed prefix plus a hex SHA-256 of `normalizedUserName + "|" + planHandle`. A repeat POST for the same plan returns the existing subscription (200) whatever its state. Re-subscribing after a cancellation is out of scope. Subscribing to a different plan creates a second subscription.
- **A5. Data loss on restart.** Under `UseOnlyInMemoryDatabase=true` the claim rows vanish on restart. The cross-restart guard is therefore the provider read: `ReadCustomerByReference` before `CreateCustomer`, the provider's customer-reference uniqueness, and `FindSubscription` before `CreateSubscription`. Concurrency within a run is guarded by the claim rows. For the SQL Server path, the new entities need an EF migration. If the tooling is unavailable, report it rather than skipping it silently.
- **A6. `MAXIO_ENVIRONMENT`.** The task gives no `Maxio:` key for it, and "exactly these keys" rules out inventing one, so it is not bound. `ServerEnvironment.Us` is used everywhere. An EU-hosted site must set `Maxio:BaseUrl`. If the sandbox site turns out to be EU-hosted and `Maxio:BaseUrl` is not supplied, every call will fail to reach it; tell the user rather than guess.
- **A7. Test host.** `tests/PublicApiIntegrationTests` boots the real `Program` through `WebApplicationFactory<Program>`, so the PROD #1 fail-fast will stop those tests on any machine without Maxio settings. The test host must supply **non-secret placeholder** `Maxio:*` values (or override the registration with a stubbed client). Real keys never go into test config.
- **A8. `GET api/my-subscriptions`.** It shows only subscriptions whose `Product.ProductFamily.Handle` equals `Maxio:ProductFamilyHandle` (the plans this app offers). If no Maxio customer exists for the user, it returns an empty list and creates nothing. It settles any `Unknown` subscription claim for the user first.
- **A9. Build portability.** The SDK `ProjectReference` points into this machine's plugin install, so CI, the PublicApi `Dockerfile` and teammates cannot build without the plugin at the same path. The SDK also pulls `Microsoft.Extensions.Http`/`Logging.Abstractions` 10.0.8 transitively into a net8.0 app under the repo's central package management. Check for NU1605/NU1608 at the first restore.
- **A10. Layering.** The SDK-facing code (settings, registration, billing service, DTOs, endpoints) lives in `src/PublicApi`, so `src/Web` and `src/Infrastructure` take no SDK dependency. Only the claim entities and their EF configuration go into ApplicationCore/Infrastructure, and they have no SDK types.
