# Maxio Advanced Billing integration plan: eShopOnWeb subscriptions (PublicApi)

SDK: NuGet `sohail-ab-sdk` (version-less), root namespace `MaxioAdvancedBilling`, source ref `main`. Every contract fact below comes from `sdk-map.md`, `map/operations/*.md` or the source file named in its row (paths relative to the SDK root).

## 1. Scope & sequence

| # | Step | Operations |
| --- | --- | --- |
| 1 | Add the package to `src/PublicApi` (the repo uses central package management: `Directory.Packages.props`). Bind the `Maxio:` section (`Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, optional `Maxio:BaseUrl`) to an options class with start-up validation. Register the client once (singleton). Secrets go to PublicApi user-secrets (`UserSecretsId` is already in `src/PublicApi/PublicApi.csproj`). | none (client construction, §2 *Client facts*) |
| 2 | Add the persistence to `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`): two claim/link entities keyed by a **string primary key** (customer reference; subscription reference), each with an `IEntityTypeConfiguration` beside `src/Infrastructure/Data/Config/CatalogBrandConfiguration.cs`. | none |
| 3 | Add one Maxio billing service (the only class that calls the SDK; it owns the call budget and error translation). | all below |
| 4 | `GET /api/subscription-plans`: list the products in the configured family. Drop archived ones. Map them to a plan DTO (handle, name, description, price, interval). | `ProductFamilies.ListProductsForProductFamily` |
| 5 | Ensure the customer (idempotent): claim → `ReadCustomerByReference` → (404) `CreateCustomer` → record the Maxio customer id. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 6 | `POST /api/subscriptions` (body: product handle, default `eshop-pro` when omitted, YOUR CALL): validate the handle against step 4 → ensure the customer (step 5) → claim → `FindSubscription` by our reference (state lost on restart) → `CreateSubscription` → record the result. Return plan/price/state/next-billing-date. | `ProductFamilies.ListProductsForProductFamily`, `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription` |
| 7 | `GET /api/my-subscriptions`: resolve the customer by reference, then list their subscriptions. Return an empty list on a customer 404. | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` |
| 8 | Tests: stub the SDK `HttpClient` (unit tests), and make PublicApi integration tests start with Maxio config present (start-up validation would otherwise fail `tests/PublicApiIntegrationTests/ProgramTest.cs`). | all |

Endpoint convention to imitate: `MinimalApi.Endpoint` `IEndpoint<...>` classes with `AddRoute` + `HandleAsync`, `.Produces<T>().WithTags(...)`, one request/response file per class. Exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (JWT `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`). Error translation exemplar: `src/PublicApi/Middleware/ExceptionMiddleware.cs` (maps `DuplicateException` → 409, everything else → 500). Caller identity: the JWT that `src/Infrastructure/Identity/IdentityTokenClaimService.cs` issues carries only `ClaimTypes.Name` (the user name, which is the e-mail for seeded users) plus `ClaimTypes.Role`. It carries no user-id claim.

> ⚠ Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits. (Request records sit in `MaxioAdvancedBilling.Requests.<Controller>`, e.g. `MaxioAdvancedBilling.Requests.ProductFamilies`.)

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The `product_handle` accepted by `POST /api/subscriptions` must be one returned for the configured family (`"handle:" + Maxio:ProductFamilyHandle`) and not archived (`ArchivedAt == null`). Any other handle → 400 before calling the provider | `CreateSubscription` ← `ListProductsForProductFamily` | the billing service's subscribe method, before the subscription claim and `CreateSubscription`. It calls the same plan-listing method `GET /api/subscription-plans` uses (cache optional) |
| `CreateSubscription.CustomerId` must be the `Customer.Id` that this application's ensure-customer step got for this user's reference (stored on the customer link row) | `CreateSubscription` ← `ReadCustomerByReference` / `CreateCustomer` (stored result) | the billing service's subscribe method, after ensure-customer returns, before `CreateSubscription` |
| `ListCustomerSubscriptions.CustomerId` must be the `Customer.Id` resolved for the caller's own reference (never a client-supplied id) | `ListCustomerSubscriptions` ← `ReadCustomerByReference` | the billing service's my-subscriptions method, before `ListCustomerSubscriptions` |
| The caller's customer reference is derived from the JWT `ClaimTypes.Name`, never from the request body | `ReadCustomerByReference` / `CreateCustomer` ← the token issued by `IdentityTokenClaimService` | each subscription endpoint's handler, which reads the user from the token before calling the service |

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind `Maxio:` to an options class with `ValidateOnStart()`. Refuse to start when `Maxio:ApiKey` is null/whitespace, or `Maxio:ProductFamilyHandle` is null/whitespace, or `Maxio:Subdomain` is null/whitespace while `Maxio:BaseUrl` is unset, or `Maxio:BaseUrl` is set but is not an absolute http(s) URI. The Basic password is the fixed `x` from the map, so the only variable part is checked. Because the SDK's `configure` runs at first resolve, validation lives in the options pipeline, not in `configure`. The integration test host must supply test values (`tests/PublicApiIntegrationTests/appsettings.test.json` or the factory's config). |
| 2 | Secret sourcing & rotation | Source is PublicApi user-secrets in development (`dotnet user-secrets set Maxio:ApiKey …`, from the `MAXIO_API_KEY` value the user holds), and environment/config providers elsewhere (`Maxio__ApiKey`). Nothing goes in repo files. The singleton client captures `BasicAuth` once, at first resolution, so a rotated key takes effect on process restart. No hot rotation is required by the task. |
| 3 | Total timeout budget | Per attempt: `Retry.Timeout = 10s`. The whole `HandleAsync` gets one linked `CancellationTokenSource` (`HttpContext.RequestAborted` + `CancelAfter(30s)`), owned by the billing service and passed to every SDK call in the request. POST /api/subscriptions makes up to 5 calls (list, read customer, create customer, find, create), all under that one 30 s budget. |
| 4 | Write-retry ownership | Keep the default `HttpMethodsToRetry`. `CreateCustomer` and `CreateSubscription` (POST) are never resent by the SDK. The GETs (`ListProductsForProductFamily`, `ReadCustomerByReference`, `FindSubscription`, `ListCustomerSubscriptions`) may be retried. Nobody widens the verb list. |
| 5 | Idempotency & ambiguous writes | `CreateCustomer`: there is no idempotency member on `CreateCustomerOperationRequest`. The natural key is `CreateCustomer.Reference`, which the provider documents as unique ("only create one customer for a given reference value"); reconcile with `ReadCustomerByReference`. `CreateSubscription`: no idempotency member, and `CreateSubscription.Reference` has no documented uniqueness (UNVERIFIED); reconcile with `FindSubscription(Reference)`. The `Idempotency-Key` header is not a key. |
| 6 | Observability | SDK request/response lines at `Information` and failures at `Warning`/`Error` through the host `ILoggerFactory` (PublicApi default level is `Warning`, so only failures and retries show by default). The billing service logs: plan-list failures at `Error`; claim conflicts at `Information`; unknown outcomes at `Warning`, with the claim key, operation and HTTP status. The SDK exposes no provider correlation id on these error bodies (`RawError`, `ErrorListResponse1`, `CustomerErrorResponse1` carry none), so log the claim key/subscription reference as the correlation value and the ASP.NET `TraceIdentifier`. |
| 7 | Sensitive data | Yes: `CreateCustomer` carries e-mail and names, and the reference (derived from the user name/e-mail) is a query param on the two lookups. Keep `LogRequestBody = false` and set `Logging.LoggerFactory` explicitly to the host factory. ## 6. Assumptions & Blockers

- **Blocker / major assumption: durability of claims.** The task mandates `UseOnlyInMemoryDatabase=true`, so `CatalogContext` loses every claim and link row on restart, and the claims hold only within one process (no multi-instance). The plan keeps the claims in `CatalogContext` (the codebase's own store, durable under its SQL Server configuration) and covers restarts with provider re-reads after the claim: `ReadCustomerByReference` (provider-unique reference) and `FindSubscription` (reference uniqueness UNVERIFIED). Under in-memory mode, a double-click that straddles a restart is not provably stopped. The user should accept this for the in-memory environment. For SQL Server mode, an EF migration for the two new tables is needed (in-memory ignores migrations): YOUR CALL whether to add it now.
- Customer reference = a deterministic value from the JWT `ClaimTypes.Name` (user name), not `ApplicationUser.Id`. Reason: the in-memory identity store re-seeds users with new GUID ids on every start (`src/Infrastructure/Identity/AppIdentityDbContextSeed.cs`), so an id-based reference would create a new Maxio customer after each restart.
- `CreateCustomer` requires `FirstName`/`LastName`/`Email`, and `ApplicationUser` has no name fields (`src/Infrastructure/Identity/ApplicationUser.cs`). Assumed: e-mail from the user record (or the name claim), with first/last name derived from it or from placeholders. YOUR CALL.
- One subscription per (user, plan handle). Subscribing to the other plan is allowed. Re-subscribing to a plan after cancellation is out of scope (there is no cancel route). YOUR CALL if the user wants one active subscription per family instead.
- `POST /api/subscriptions` body: `{ "productHandle": "..." }`, defaulting to `eshop-pro` when omitted. Hard-coding `eshop-pro` as a default conflicts with "hard-code none of their values"; alternatively make the handle required. YOUR CALL (the handle is still validated against the family listing).
- `GET /api/my-subscriptions` lists all of the customer's subscriptions from Maxio. Whether to filter to the configured family (`Subscription.Product.ProductFamily.Handle`) is YOUR CALL.
- `MAXIO_ENVIRONMENT` and `MAXIO_DEFAULT_PRODUCT_FAMILY` have no binding keys beyond `Maxio:ProductFamilyHandle`. Assumed: `MAXIO_DEFAULT_PRODUCT_FAMILY` → `Maxio:ProductFamilyHandle`, `MAXIO_SITE_SUBDOMAIN` → `Maxio:Subdomain`, `MAXIO_API_KEY` → `Maxio:ApiKey`, and `MAXIO_ENVIRONMENT` (sandbox) has no SDK counterpart (the SDK has only `Us`/`Eu`, and the site selects sandbox). The client stays on `ServerEnvironment.Us`. If the site is EU-hosted, a `Maxio:` environment key would be needed, which the task's key list does not include.
- Both plans are documented by the task as needing no payment method. If the site's product actually has `require_credit_card = true`, `CreateSubscription` would be refused (422). The plan-list DTO surfaces `RequireCreditCard` so this is visible; it is not treated as a blocker.
- Observation for the main agent (not SDK): `global.json` pins `8.0.x` with `rollForward: latestFeature`, which does not roll to a .NET 10 SDK. The environment has only .NET 10.
- The `404 → not found` reading of `ReadCustomerByReference` and the duplicate-reference `422` on `CreateCustomer` are UNVERIFIED (Case B / undocumented statuses). The code branches on them defensively, as the sheet says.

### Resolutions at implementation time (2026-10-20)

- Durability: accepted for in-memory mode, as the task states. Provider re-reads after the claim cover a restart, and a restart test proved it live: 200 `already_subscribed`, no second create. For SQL Server, migration `20261020050809_AddBillingClaims` creates only the `BillingClaims` table. Unrelated model drift that the scaffolder picked up was removed.
- Customer reference: `eshop-` + the first 16 bytes of SHA-256 of the upper-cased user name, as hex. It is deterministic and puts no e-mail in query strings or logs. Customer e-mail comes from `ApplicationUser.Email`, first name from its local part, last name `eShopOnWeb`.
- `productHandle` is **required**, with no hard-coded default, because the build must run against other catalogs. It is validated against the configured family's non-archived products.
- `GET /api/my-subscriptions` lists all of the caller's Maxio subscriptions, with no family filter. Reading never creates a customer.
- `require_credit_card` was not the blocker; the collection method was (see the *Collection method* row).
- `MAXIO_ENVIRONMENT` is not bound. The client stays on `ServerEnvironment.Us`, and live calls to the sandbox site succeeded.
