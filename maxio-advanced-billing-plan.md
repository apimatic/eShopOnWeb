# Maxio Advanced Billing plan — eShopOnWeb "Subscribe" (.NET)

SDK source (plugin-relative): `sdk/dotnet/` (map: `sdk/dotnet/sdk-map.md`, pages `sdk/dotnet/map/operations/`). All "source" cells below are relative to that root.
Maxio vocabulary: a "plan" in the task is a **Product** in the SDK; a "product family" is `ProductFamilies`.

## 1. Scope & sequence

| Step | What | Operations |
| --- | --- | --- |
| 1 | Bind `Maxio:` options (ApiKey, Subdomain, ProductFamilyHandle, BaseUrl), fail fast at startup, register one singleton `MaxioAdvancedBillingClient` in PublicApi DI | none |
| 2 | `GET /api/subscription-plans` — list the configured family's plans | `Products`-side: `ProductFamilies.ListProductsForProductFamily` (family addressed as `handle:<Maxio:ProductFamilyHandle>`) |
| 3 | `POST /api/subscriptions` — validate plan against step-2 list; claim customer row; ensure Maxio customer; claim subscription row; create subscription; record result; return plan/price/state/next billing date | `ListProductsForProductFamily`, `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`, `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription` |
| 4 | `GET /api/my-subscriptions` — read caller's stored customer id, list their subscriptions in the configured family | `Customers.ListCustomerSubscriptions` |
| 5 | EF Core store: two new entities in `CatalogContext` (`src/Infrastructure/Data`), configs in `Data/Config`, no migration needed (in-memory provider) | none |

Repo conventions (survey; read-only): endpoints are `IEndpoint<IResult, TRequest, ...>` classes with `AddRoute(IEndpointRouteBuilder)`, request/response DTO in sibling partial-named files, `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` on the lambda, `.Produces<T>().WithTags(...)` — exemplar `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (+ `CatalogItemGetByIdEndpoint.cs` for GET). Responses extend `BaseResponse` (`src/PublicApi/BaseResponse.cs`), requests extend `BaseRequest`. EF entities+config exemplar: `src/Infrastructure/Data/Config/BasketConfiguration.cs`; context `src/Infrastructure/Data/CatalogContext.cs` (`ApplyConfigurationsFromAssembly`); in-memory wiring `src/Infrastructure/Dependencies.cs`. JWT issued by `src/Infrastructure/Identity/IdentityTokenClaimService.cs` carries ONLY `ClaimTypes.Name` (the username) and `ClaimTypes.Role` — no NameIdentifier, no email claim.

### DUPLICATE CLAIMS

Order for every row: claim (EF Core save in `CatalogContext`) → SDK call → record result. Release the claim when the provider refuses the call (422 / Case-A rejection / definite non-2xx); keep it (state `Unknown`) when the outcome is unknown.

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| `Customers.CreateCustomer` (ensure customer for the token's user) | New entity `MaxioCustomerLink` in `CatalogContext` (the app's existing EF store): `UserKey` (normalized `ClaimTypes.Name`), `MaxioCustomerId int?`, `Status` (Claimed/Created/Unknown), timestamps | Primary key on `UserKey`: the second concurrent claim `Add`+`SaveChangesAsync` of the same key fails (in-memory provider enforces PKs) | `catch (DbUpdateException)` (the in-memory provider's duplicate-key `InvalidOperationException` is also caught) around the claim save; the loser then reads the winner's row and returns its result (or 409 while still `Claimed`) — no SDK call is made | `SubscriptionService.TryClaimAsync` in `EnsureCustomerAsync` (claim; catch there), then `SubscriptionService.WriteAsync` -> `Customers.CreateCustomer` || `Subscriptions.CreateSubscription` | New entity `MaxioSubscriptionLink` in `CatalogContext`: composite PK (`UserKey`, `PlanHandle`), `MaxioSubscriptionId int?`, `Reference` (deterministic `eshop:{UserKey}:{PlanHandle}`), `Status`, timestamps | Composite primary key on (`UserKey`, `PlanHandle`): double-click for the same plan is refused by the store before the SDK call | `catch (DbUpdateException)` around the claim save; the loser returns the stored subscription (200 with `Created=false`) or 409 if still in flight | `SubscriptionService.TryClaimAsync` in `EnsureSubscriptionAsync` (claim; catch there), then `SubscriptionService.WriteAsync` -> `Subscriptions.CreateSubscription` |

## 6. Assumptions & Blockers

Blockers: none. (The persistent claim store exists: the app's EF Core `CatalogContext` with PK enforcement; no Docker/broker needed.)

Assumptions / YOUR CALLs:
1. **Caller identity** — the JWT carries only `ClaimTypes.Name` (username) and roles; no NameIdentifier/email claim (read in `IdentityTokenClaimService.cs`). `UserKey` = normalized (upper-invariant) `ClaimTypes.Name`. Decided: `SubscriptionService.UserKeyOf`.
2. **Customer name/email** — `CreateCustomer` requires `FirstName`, `LastName`, `Email`; the token has none. Plan: look up the Identity user by name (`UserManager<ApplicationUser>` already registered in PublicApi) for the email (eShop usernames are emails); first/last name have no source, so derive from the email local part / fixed placeholder for last name. Decided: `SubscriptionService.DescribeUserAsync` (Identity e-mail; names derived from the local part, `Customer` placeholder surname).
3. **Default plan** — the task says Pro (`eshop-pro`) is the default subscribe target, but handles must not be hard-coded and the config keys are fixed at four. Plan: `planHandle` in the POST body is required; the default is applied by the caller/UI (sample client uses `eshop-pro`), and a missing handle returns 400. Decided: `SubscribeRequest.PlanHandle` is required (400 when missing); the client sends `eshop-pro` by default.
4. **Plan = Product** — plans come only from `ListProductsForProductFamily` for `handle:<Maxio:ProductFamilyHandle>`; numeric product/family ids are never configured or hard-coded; only handle strings are used in `CreateSubscription.ProductHandle`.
5. **No payment method** — no payment-profile, credit-card, or price-point fields are set; if Maxio nevertheless rejects creation (422) the response is surfaced as 422 to the caller. Whether sandbox accepts creation without payment for plans configured "not required" is UNVERIFIED (live traffic only). Plans are offered exactly as the list returns them (no filtering on `RequireCreditCard`); a subscribe attempt that Maxio rejects is mapped from the 422.
6. **Reference uniqueness at Maxio** is UNVERIFIED (map silent); the app claim is the guarantee, references enable reconciliation only. A customer with that reference existing in Maxio outside this app (found by `ReadCustomerByReference`) is adopted.
7. **One subscription per (user, plan)** — a second subscribe to the same plan returns the existing subscription (200, `created=false`), not a second one; subscribing to a different plan creates a separate subscription. Decided: `SubscriptionService.EnsureSubscriptionAsync` (composite PK).
8. **Not-found status on `ReadCustomerByReference`** (Case B) is expected 404 but UNVERIFIED; any non-404 error other than a definite 4xx is treated as unknown-outcome-safe (no create attempted blindly; surfaced as 502).
9. **Maxio:BaseUrl** is applied via `options.Server.Production.Us.BaseUrl`; the selected `ServerEnvironment` is `Us` (sandbox site cp-exp-1 is on the default group). If the site is EU-hosted the deployment must change the environment — no such setting is among the four keys, so this is not configurable without a fifth key. Decided: `MaxioServiceCollectionExtensions.AddMaxioSubscriptions`.
10. **In-memory store** is per process and lost on restart: after restart the claim rows vanish, so reconciliation via references (`ReadCustomerByReference`/`FindSubscription`) is what prevents a duplicate subscription after a restart. Noted as a limitation of the stated environment.
11. **Payment collection (live finding)** — with the default (automatic) collection, sandbox rejected a subscription to `eshop-pro` with 422 "No payment method was on file for the $299.00 balance". Decided: `CreateSubscription.PaymentCollectionMethod = Enums.CollectionMethod.Remittance` (documented on `Models/CreateSubscription.cs`; invoice billing, no card capture), set in `SubscriptionService.EnsureSubscriptionAsync`. Verified live: subscription created, state `active`. `Subscription.NextAssessmentAt` verified live as next billing date (one month out).
12. **Not-found on `ReadCustomerByReference`** verified live as 404 (`ApiException<RawError>`); `FindSubscription` 404 handled as `ApiException<FindSubscriptionError>`.
