# Maxio subscription billing implementation plan

## Scope & sequence

| Step | Implementation decision and SDK operations |
|---|---|
| 1. Configuration and client | Add the published `AsadAli.AdvancedBilling.Sdk` package to `src/PublicApi`; bind one validated options object from exactly `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`. Load the three supplied credential/catalog environment-variable values into those user-secret keys without persisting their values. Register one long-lived `HttpClient` pipeline and construct the SDK client through DI. Select `ServerEnvironment.Us`; if `BaseUrl` is nonempty assign it verbatim to the Production/US override, otherwise set the Production/US `Site` variable from `Subdomain`. Never log the key or an Authorization header. No SDK operation. |
| 2. Application boundary | Define an application-owned `ISubscriptionBillingService` and API DTOs so endpoint/domain code does not expose generated SDK models. Add a single exception-translation boundary returning the PublicApi project's normal problem/error shape. All endpoints require JWT authorization and resolve user id/profile exclusively from the authenticated principal/application user store. |
| 3. Catalog | Resolve the configured family handle at runtime with `ProductFamilies.ListProductFamilies`; match it ordinally by `ProductFamily.Handle`, then use the returned runtime id only as the argument to `ProductFamilies.ListProductsForProductFamily`. Use `Sites.ReadSite` for site currency. Filter archived products and map each plan to handle, name, description, price-in-cents, interval, interval-unit, and currency. Cache this read-only catalog briefly if consistent with project conventions, but never cache failures. `GET /api/subscription-plans` returns this list. No seeded numeric id or product handle is embedded in code. |
| 4. Durable correlation and idempotency | Persist an application-owned billing link/operation row keyed uniquely by `(UserId, ProductHandle)` and carrying deterministic customer/subscription references, Maxio ids returned at runtime, state, timestamps, and an operation status/lease token. Add a unique index for the deterministic subscription reference. Use a per-key async lock for the in-memory provider plus the database uniqueness/claim transition for multi-request ownership. The owner alone may make a create call; duplicate requests wait/reload and return the same confirmed subscription. A stale pending operation is recovered by lookup before any new create attempt. |
| 5. Ensure customer | Derive a stable, non-PII customer reference from the authenticated eShop user id. Call `Customers.ReadCustomerByReference`; on 404 call `Customers.CreateCustomer` with required first name, last name, email and the reference. On a create 422 (including a create race), re-read by reference and accept the returned customer; if it still does not exist, surface the validation failure. Persist only returned runtime ids/references, never configured numeric ids. |
| 6. Subscribe | `POST /api/subscriptions` accepts an application DTO containing `productHandle`. Under the idempotency ownership from step 4, first call `Subscriptions.FindSubscription` with the deterministic subscription reference. If found, reconcile/persist and return it. If absent, resolve and validate the requested handle against the configured-family catalog, ensure the customer, then call `Subscriptions.CreateSubscription` with `ProductHandle`, `CustomerReference`, `Reference`, and an explicit non-automatic `PaymentCollectionMethod`: `Remittance` when `Site.RelationshipInvoicingEnabled` is true, otherwise `Invoice`. This honors the no-card signup while selecting a value valid for the site's invoicing architecture. On a typed 422 or an unknown transport outcome, perform `FindSubscription` before deciding the attempt failed; never blindly issue another application-level create. Return `201 Created` for a new enrollment and the project's normal successful replay response for an existing one, always including plan, price, state, and next billing date. |
| 7. Account view | `GET /api/my-subscriptions` looks up the customer by deterministic reference. A 404 is an empty list. Otherwise call `Customers.ListCustomerSubscriptions`, filter to subscriptions whose returned product belongs to the configured family, reconcile local links, and map live Maxio data to account DTOs: subscription reference/id, product handle/name, product price-in-cents, currency, state, and `NextAssessmentAt` (with `CurrentPeriodEndsAt` as a separate field, not substituted silently). Maxio remains the billing system of record; the local table is correlation/idempotency state. |
| 8. Errors and observability | Validate malformed/unknown product handles locally. Translate deterministic Maxio validation/not-found conditions without exposing raw bodies; translate authentication/configuration, timeout, transport, malformed response, and other upstream failures to the project's safe dependency-failure response. Log operation name, user/link correlation ids, status and latency, but no credentials/PII/raw Maxio body. Respect request cancellation end to end (`ct:`). |
| 9. Tests and live proof | Unit-test service orchestration/idempotency, including concurrent double-submit, stale-pending recovery, customer create race, subscription replay, missing customer, malformed envelopes, each typed/raw error path, and DTO mapping. Use a fake `HttpMessageHandler` with the real SDK client for exact URL/auth/body/envelope tests; add authenticated PublicApi endpoint tests (401 without JWT and success with JWT). Build/test with SDK roll-forward settings, run PublicApi detached with `UseOnlyInMemoryDatabase=true` on the assigned port, obtain its JWT, exercise the three endpoints twice for the same product, assert the same subscription and one Maxio enrollment, then stop the exact PID. |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 1 (client registration) — constructing or owning the `HttpClient` at the wrong lifetime can exhaust connections and make tests exercise a different pipeline. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential timing, Basic-auth manager wiring, and rotation determine whether calls silently leave without valid authentication. **MUST load `dotnet-authentication`** before supplying credentials.

⚠ Steps 3, 5, 6, and 7 (calls) — optional parameters without C# defaults and the literal `ct` parameter can mis-bind or drop cancellation. **MUST load `dotnet-calling-endpoints`** before the first call.

⚠ Steps 3, 5, 6, and 7 (models) — generated required members, nullable response envelopes, string-enum wrappers, wire names, and dropped unmodeled fields can turn a plausible mapper into a compile/runtime defect. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 1 and 6 (resilience) — retry verb/transport behavior, timeout scope, base-URL overrides, and manual pagination determine whether a write may be re-sent and whether the full catalog is returned. **MUST load `dotnet-configuration-resilience`** before configuring the client or idempotent write path.

⚠ Step 8 (error boundary) — Case A typed accessors and Case B raw errors have different safe extraction paths, and raw payload/log handling can leak customer or provider details. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (error boundary) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (error boundary) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 9 (tests) — mocking generated controllers/models couples tests to SDK internals and misses actual serialization, auth and envelope behavior. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- Assumption: `MAXIO_ENVIRONMENT` is not bound into `Maxio:` because the required section permits exactly four keys and the SDK has no sandbox environment enum; sandbox/live is a property of the selected Maxio site. The integration uses the US hosting template unless `Maxio:BaseUrl` overrides it verbatim.
- Assumption: the authenticated eShop profile can supply the required non-null first name, last name, and email for `CreateCustomer`; if it cannot, the application rejects enrollment before calling Maxio rather than inventing customer data.
- Assumption: `POST /api/subscriptions` supplies a product handle selected from `GET /api/subscription-plans`; there is no server-hardcoded default product handle, so the same build works with a different configured family/catalog.
- `UNVERIFIED`: the SDK map/source exposes subscription `Reference` plus `FindSubscription`, but does not state a server-side uniqueness guarantee or a reference length limit. Use a deterministic bounded reference, database/process ownership to guarantee double-click idempotency, and lookup-based reconciliation for ambiguous outcomes; do not claim provider-enforced uniqueness.
- Blockers: none. The bundled SDK exposes every operation required by this design.
