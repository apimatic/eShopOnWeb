| Subscription reference | Deterministic, opaque, versioned value derived from `(userId, productHandle)`; persist it and use it in `FindSubscription`/create. ## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 2 (configuration/server selection) — server-node selection and a custom base URL can route different controller groups differently; a wrong override silently targets the wrong host. **MUST load `dotnet-configuration-resilience`** before wiring `Maxio:BaseUrl` or site selection.

⚠ Step 3 (client registration) — `HttpClient` ownership/lifetime and SDK-wrapper lifetime determine socket reuse and testability. **MUST load `dotnet-client-initialization`** before registration.

⚠ Step 3 (authentication) — credential timing/rotation and the generated auth-manager shape determine whether requests receive Basic auth. **MUST load `dotnet-authentication`** before setting credentials.

⚠ Steps 4, 6, 7, and 9 (calling operations) — many nullable optional parameters have no C# default and positional calls can mis-bind; operation cancellation and envelope access must match the generated surface. **MUST load `dotnet-calling-endpoints`** before the first call.

⚠ Steps 4, 6, 7, and 9 (models) — generated required members, nullable response inners, wire names, and `StringEnum<T>` handling determine whether requests compile and responses map safely. **MUST load `dotnet-models`** before constructing or projecting SDK models.

⚠ Steps 6, 7, and 10 (error boundary) — typed and raw errors require different catch/accessor paths, and a typed accessor is not a universal fallback. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 7 (idempotent create) — retry triggers and verb gating determine whether a failed subscription write can be re-sent, which directly affects the documented exactly-once limitation and ambiguity recovery. **MUST load `dotnet-configuration-resilience`** before selecting retry options.

⚠ Step 3 (timeouts and logging) — the SDK timeout and the registered `HttpClient` timeout bound different parts of execution, while diagnostics require an application seam. **MUST load `dotnet-configuration-resilience`** before tuning either.

⚠ Step 10 (2xx schema drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Step 10 (non-2xx schema drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 11 (tests) — the correct seam to fake and the behavior worth asserting are not controller internals. **MUST load `dotnet-testing`** before writing integration-layer tests.

## 5. Assumptions & Blockers

- **Assumption:** `Maxio:Subdomain` identifies a US-hosted sandbox site, matching the SDK's `ServerEnvironment.Us`/Production server group. The task provides no `Maxio:Environment` binding key and requires the Maxio section to use exactly the four named keys.
- **Assumption:** The HTTP subscribe request supplies a product handle returned by `GET /api/subscription-plans`. No default product handle is hard-coded because the same build must work with a different catalog and the allowed configuration has no default-product key.
- **Assumption:** The application's trusted identity/profile path can provide the required `FirstName`, `LastName`, and `Email` values for `CreateCustomer`; absence must be handled as an application validation/profile-completion outcome before calling Maxio.
- **Blocker/contract limit:** The SDK map exposes no native idempotency key on `CreateSubscription`, and it does not say `CreateSubscription.Subscription.Reference` is unique. Strict provider-side exactly-once behavior across an ambiguous network outcome cannot be proven from the allowed source. The plan guarantees durable single-owner behavior for ordinary double-click/concurrent application requests and requires reference-based reconciliation, but provider uniqueness remains **UNVERIFIED**.
