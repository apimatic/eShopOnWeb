## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — the generated extension captures configuration once and uses the shared unnamed `HttpClient`; lifetime, handler rotation, and blast radius can be wrong for a billing integration. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — a Basic-auth credentials object has required members and must be configured before client construction; secret sources and rotation must not leak into code or logs. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 2–6 (calls) — list/search signatures contain nullable parameters without C# defaults and response models have one-level envelopes; positional calls or skipped unwrapping silently select the wrong contract. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–6 (models) — the records are immutable and fields/nullability are not an acceptance rule; enum and optional nested-response handling affect request serialization and public DTO mapping. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 3–7 (error boundary) — customer and subscription writes are Case A while reads/lists are Case B; using a raw accessor on a typed error, or assuming every error has a typed accessor, loses the actionable provider result. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 4 (idempotent write) — retry/timeout configuration can cause an ambiguous subscription-create outcome, so whether a failed write can be re-sent must be reconciled through the deterministic Maxio reference before a second write. **MUST load `dotnet-configuration-resilience`** before tuning the client.

⚠ Step 7 (tests) — mocking controller wrappers tests SDK internals rather than the generated HTTP path, envelopes, and thrown error types. **MUST load `dotnet-testing`** before writing tests.

⚠ Steps 3–7 (error boundary) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary; **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Steps 3–7 (error boundary) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

|---|---|
