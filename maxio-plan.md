## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency and consistency boundary

| Question | Grounded answer / directive | Grounding |
|---|---|---|
| Does SDK subscription creation support a server idempotency key? | **No exposed capability.** `CreateSubscription` has only `body` and `ct`; its generated request supplies empty path/query/header parameter collections. There is no request-options/custom-header argument. | `operations/Subscriptions.md`; `Api/Subscriptions.cs` (map-named source gap lookup) |
| Is customer creation safely deduplicated? | The Maxio operation explicitly guarantees at most one customer for a supplied unique `reference`. Use lookup → create → lookup-on-conflict/error, plus the local unique user mapping. | `operations/Customers.md` |
| Is subscription `reference` a server uniqueness constraint? | **UNVERIFIED.** The SDK exposes create/reference and singular lookup, but neither map nor source states reference uniqueness. It is a correlation/reconciliation key, not a lock or proof of server idempotency. | `operations/Subscriptions.md`; `models/records-2-Cr-Ne.md`; `Models/Subscription.cs` |
| What ordinary double-click protection is possible? | A durable database uniqueness constraint on `(UserId, ProductHandle)` plus an atomic intent claim ensures only one application owner calls create; all concurrent/repeated requests observe/wait for/reuse that intent. A deterministic subscription reference allows preflight and reconciliation. | Application-layer directive; no unsupported SDK claim |
| What is not provably possible? | Unconditional global exactly-once subscription creation across ambiguous network response loss, SDK/internal re-send behavior, process crash, or multiple writers that bypass the shared intent store cannot be guaranteed by this SDK contract. Never report an unknown outcome as success and never blindly re-create it. | Absence of an SDK idempotency/header contract above |
| Safe ambiguous-outcome policy | After any ambiguous create exception, call `FindSubscription(reference)`. If found, verify caller/customer/product/reference and adopt. If absent, retain durable `OutcomeUnknown`, return a retriable upstream-unavailable/problem response, and reconcile with future reads/polls; do not issue another create automatically. This preserves at-most-one intent at the cost of possible manual resolution. | `operations/Subscriptions.md` |

## Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership and SDK wrapper lifetime determine connection reuse and whether DI registration is safe. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential timing/rotation and the Basic-auth manager boundary determine whether calls consistently carry the configured secret. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Step 1 (server and resilience) — base-server selection, retry gates, timeout scope, cancellation, and client logging have consequences that option names do not reveal. **MUST load `dotnet-configuration-resilience`** before registering/tuning the client.

⚠ Step 3 (catalog calls) — generated nullable parameters without C# defaults must still be supplied, and manual pagination must not mis-bind positional arguments. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–7 (models/projection) — required envelopes, nullable inner data, `StringEnum<T>` wire values, and immutable request initialization can otherwise produce incorrect DTOs or compile failures. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Step 5 (subscription write) — whether a failed write can be re-sent and how transport ambiguity affects an operation with no idempotency-key parameter determines the safety of retry/reconciliation. **MUST load `dotnet-configuration-resilience`** before allowing the create call.

⚠ Step 7 (error boundary) — Case A typed errors and Case B raw errors have different access paths, and a typed fallback is not equivalent to a raw-error catch. **MUST load `dotnet-error-handling`** before writing the boundary.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (tests) — the correct fake seam and assertions must cover observable requests/responses without binding tests to generated controller internals. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- The POST contract requires a `productHandle` obtained from `GET /api/subscription-plans`; no seeded handle (`eshop-pro`, `basic-plan`) is hard-coded, so the same build supports a different configured catalog.
- The authenticated identity/application user store can supply non-empty first name, last name, and email for `CreateCustomer`; these are SDK-required fields. If the JWT itself lacks them, the integration must resolve the application user by the stable token subject—never accept them as authoritative POST fields.
- The SDK has no sandbox/live selector. Under this brief, `ServerEnvironment.Us` plus the sandbox site/key targets the sandbox; `MAXIO_ENVIRONMENT` may be used only as a fail-fast test safety check and is not bound as an additional `Maxio:` key.
- **Capability gap:** the plugin/SDK exposes no subscription-creation idempotency key and does not document subscription-reference uniqueness. The design can make ordinary concurrent/repeated HTTP double-clicks single-owner through a durable application intent and can reconcile known references, but it cannot honestly promise unconditional exactly-once creation across ambiguous transport loss, SDK re-send, crashes, or writers outside that store. Strict server-guaranteed exactly-once semantics are blocked by this missing Maxio SDK capability; the safe response is `OutcomeUnknown` quarantine, not another create.
- The in-memory provider required on this machine preserves the unique intent only within one host run. Production must use the repository’s durable relational provider and migration/unique index; restart-surviving idempotency cannot be demonstrated with the mandated in-memory local run.
