## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal C# identifier. The
> cancellation-token parameter really is named `ct`: in named arguments write `ct:`, never
> `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** (e.g.
> `MaxioAdvancedBilling.Models.Enums.SubscriptionState`, `MaxioAdvancedBilling.Models.AnyOf.SubscriptionIdOrReference`,
> `MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials`, and the **client-config types**:
> `MaxioAdvancedBilling.Servers.ServerEnvironment`, `MaxioAdvancedBilling.Core.Configuration.RetryOptions`,
> `MaxioAdvancedBilling.Core.Configuration.ServerOptions`). The map carries these namespaces (a members table
> names the namespace, or a row gives the source path `Core/Configuration/…` ⇒ namespace
> `MaxioAdvancedBilling.Core.Configuration`) — do not drop them to the root or `.Models`, or the implementer
> guesses the wrong `using` and the build breaks.

### 2.0 Client construction / auth / server override

- NuGet package: `AsadAli.AdvancedBilling.Sdk`. Root namespace: `MaxioAdvancedBilling`.
- Client class: `MaxioAdvancedBilling.MaxioAdvancedBillingClient`; only ctor:
  `MaxioAdvancedBillingClient(HttpClient httpClient, MaxioAdvancedBillingClientOptions options)`.
- Options class: `MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions` — properties: `Environment`
  (`MaxioAdvancedBilling.Servers.ServerEnvironment`), `Retry` (`MaxioAdvancedBilling.Core.Configuration.RetryOptions`),
  `Server` (`MaxioAdvancedBilling.Core.Configuration.ServerOptions`), `BasicAuth`
  (`MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials?`).
- Auth is HTTP Basic only: `options.BasicAuth = new BasicAuthCredentials { Username = "<api_key>", Password = "x" }`
  — literal `"x"` password, API key as username. No other scheme exists on this client (no OAuth/Bearer/API-key
  property to confuse with).
- Environment: `ServerEnvironment.Us` (default) → `https://{site}.chargify.com`; `ServerEnvironment.Eu` →
  `https://{site}.ebilling.maxio.com`. For this integration set `Environment = ServerEnvironment.Us`.
- **Base URL / subdomain override point (the one fact this brief specifically asked for):**
  `options.Server.Production.Us.Site = "apimatic-hackathon"` sets `{site}` in the URL template for the
  Production server group under the US environment. To override the whole base URL outright (e.g. a
  mock/proxy host) use `options.Server.Production.Us.BaseUrl = "https://..."` instead — a literal URL with no
  `{site}` placeholder is used as-is and wins over the templated `Site` substitution. Build your own
  config-layer resolution as: if an explicit `BaseUrl` override is configured, set
  `options.Server.Production.Us.BaseUrl` directly (skip `Site`); else set `options.Server.Production.Us.Site`
  to the subdomain-derived value. There is a second, separate server group — `options.Server.Ebb.Us.*` — used
  only by the event-ingest endpoints (`RecordEvent`/`BulkRecordEvents`), not touched by this integration's
  scope (UC2 uses `CreateUsage`, a Production-server metered-usage endpoint, not the Ebb events stream).
  Source of all the above: `sdk-map.md` "Servers & auth" section, `Server.cs`, `ServerOptions.cs`.
- DI alternative: `services.AddMaxioAdvancedBillingClient(o => { o.BasicAuth = ...; o.Server.Production.Us.Site = ...; })`.
- `RetryOptions` (`MaxioAdvancedBilling.Core.Configuration.RetryOptions`, all members `required` — build from
  `RetryOptions.Default()`): `StatusCodesToRetry`, `HttpMethodsToRetry` (idempotent verbs only by default —
  GET/HEAD/PUT/OPTIONS), `MaxRetries`, `Delay`, `Timeout` (per-attempt, nullable), `BackOffFactor`,
  `UseExponentialBackoff`, `MaxJitter`, `OnRetry`.

### 2.2a UC1 addendum — card-capture path on `CreateSubscription` (both sandbox products require payment method at signup)

**Trigger:** live sandbox confirmed both `eshop-pro` ($299.00) and `basic-plan` ($29.00) reject `CreateSubscription` with a 422 ("No payment method was on file for the $X.XX balance") when no payment method is supplied — the plan's earlier UC0 assumption ("requires payment method off") does not hold for this sandbox as currently seeded. Per §3 Trap notes / UC1 failure-scenario note, this plan does **not** touch product configuration (operator/UC0 scope) and instead exercises the card-capture path below.

**1. Exact shape to set on `CreateSubscription.CreditCardAttributes`.** The field named `credit_card_attributes` on `MaxioAdvancedBilling.Models.CreateSubscription` is declared as type `MaxioAdvancedBilling.Models.PaymentProfileAttributes?` — **not** a distinct `CreditCardAttributes` type (there is a separate, much sparser `MaxioAdvancedBilling.Models.CreditCardAttributes` record in the SDK — `FullNumber`/`ExpirationMonth`/`ExpirationYear` (both `string?`) only — but it is used elsewhere, not as `CreateSubscription`'s `credit_card_attributes` field; confirmed by reading `Models/CreateSubscription.cs` line 149, which declares `public PaymentProfileAttributes? CreditCardAttributes { get; init; }`). `CreateSubscription` also exposes `PaymentProfileAttributes (payment_profile_attributes): PaymentProfileAttributes?`, documented in source as "alias to credit_card_attributes" — set **one or the other, not both**; this plan uses `CreditCardAttributes` for clarity.

`MaxioAdvancedBilling.Models.PaymentProfileAttributes` full field list relevant to a fresh (non-stored) card (all nullable; source doc-comments from `Models/PaymentProfileAttributes.cs`):

| Field (wire) | Type | Required for a card payment? | Notes |
|---|---|---|---|
| `FullNumber` (`full_number`) | `string?` | Yes — "The full credit card number (string representation, i.e. 5424000000000015)" | The example digit-string in the doc-comment (`5424000000000015`) is illustrative formatting only, not a stated test-mode value — do not treat it as a real sandbox test card (see gap in item 3 below). |
| `ExpirationMonth` (`expiration_month`) | `MaxioAdvancedBilling.Models.AnyOf.ExpirationMonth2?` (AnyOf union of `int`/`string`) | Yes, except for vault-token subscription-import | Construct via `ExpirationMonth2.Int(5)` or `ExpirationMonth2.String("05")` — never `new ExpirationMonth2(...)`. |
| `ExpirationYear` (`expiration_year`) | `MaxioAdvancedBilling.Models.AnyOf.ExpirationYear2?` (AnyOf union of `int`/`string`) | Yes, except for vault-token subscription-import | Construct via `ExpirationYear2.Int(2028)` or `.String("2028")`. |
| `Cvv` (`cvv`) | `string?` | "Optional, may be required by your gateway settings" — not unconditionally required per source | 3- or 4-digit CVV. |
| `FirstName` / `LastName` (`first_name`/`last_name`) | `string?` | Optional — "If omitted, the first_name/last_name from customer attributes will be used" | |
| `CardType` (`card_type`) | `MaxioAdvancedBilling.Models.Enums.CardType?` (StringEnum) | "Optional, used only for Subscription Import" — not needed for a plain new-card submission | |

| `MaskedCardNumber`, `CurrentVault`, `VaultToken`, `CustomerVaultToken`, `Id`, `PaymentType`, `PaypalEmail`, `PaymentMethodNonce`, `GatewayHandle`, `LastFour` | various | Not applicable to a fresh full-number card submission — these are for subscription-import/vault-token or alternate-gateway (PayPal/Square) flows, out of this plan's scope. |

**2. `BankAccountAttributes` alternative, and `PaymentProfileId` as a stored-profile reference — confirmed.** `MaxioAdvancedBilling.Models.CreateSubscription.BankAccountAttributes: MaxioAdvancedBilling.Models.BankAccountAttributes?` is a real, separate alternative (ACH/GoCardless) — fields `BankName`/`BankRoutingNumber`/`BankAccountNumber` (required for ACH per source doc-comments), `BankAccountType`, `BankBranchCode`/`BankIban` (GoCardless), `BankAccountHolderType`, `CurrentVault` (`MaxioAdvancedBilling.Models.Enums.BankAccountVault?`), `VaultToken`, `CustomerVaultToken`. Not used by this plan (card path only). **`PaymentProfileId` is confirmed as the stored-profile alternative** — source doc-comment on `CreateSubscription.PaymentProfileId` (`Models/CreateSubscription.cs` line 120): "The Payment Profile ID of an existing card or bank account, which belongs to an existing customer to use for payment for this subscription. If the card, bank account, or customer does not exist already, or if you want to use a new (unstored) card or bank account for the subscription, use `payment_profile_attributes` instead." **Set exactly one of `PaymentProfileId` XOR `CreditCardAttributes`/`BankAccountAttributes` XOR `PaymentProfileAttributes`** — not more than one path. The operation that creates a standalone stored payment profile (referenceable later by id) is `PaymentProfiles.CreatePaymentProfile(CreatePaymentProfileRequest? body, ct)` → `CreatePaymentProfileRequest.PaymentProfile` (`MaxioAdvancedBilling.Models.CreatePaymentProfile`, same field shape as `PaymentProfileAttributes` plus a required-for-creation `CustomerId (customer_id): int?` — doc-comment: "Required when creating a new payment profile) The Chargify customer id.") → returns `PaymentProfileResponse.PaymentProfile` (`MaxioAdvancedBilling.Models.OneOf.PaymentProfile` — a **union** of `CreditCardPaymentProfile`/`BankAccountPaymentProfile`/`PaypalPaymentProfile`/`ApplePayPaymentProfile`, read via `TryGetCreditCardPaymentProfile(out CreditCardPaymentProfile)` etc. — whose `.Id` becomes the `PaymentProfileId` for a later `CreateSubscription` call). `PaymentProfiles.ListPaymentProfiles(int? customerId, int? page = 1, int? perPage = 20, ct)` lists existing profiles for a customer (Case B `RawError`; empty array not 404 if none). This plan does **not** need the separate-call path — it sets `CreditCardAttributes` directly inline on `CreateSubscription`, which is sufficient in one call (see item 4).

**3. Sandbox test card number — GAP, SDK/map is silent.** Searched the full clone (`Models/`, `Api/`, `map/`) for any embedded test-mode card number convention. Findings:
  - The **only** test-mode convention the SDK source itself encodes is the **`bogus` vault** — `MaxioAdvancedBilling.Models.Enums.AllVaults.Bogus` / `CreditCardVault.Bogus` / `BankAccountVault.Bogus` (StringEnum constant `"bogus"`), documented as "The vault that stores the payment profile with the provided `vault_token`. Use `bogus` for testing." This applies to the **`CurrentVault`+`VaultToken`** subscription-import path (doc-comments on those two fields are explicitly scoped to "Subscription Import"), **not** to a plain `FullNumber`/`ExpirationMonth`/`ExpirationYear`/`Cvv` submission — there is no vault field to set when submitting a raw card number this way, so `bogus` does not apply to this plan's card-capture flow as designed.
  - Both `Api/Subscriptions.cs` and `Api/PaymentProfiles.cs` XML doc-comments explicitly say: "Do not use real card information for testing. See the Sites articles that cover testing your site setup … for more details on testing in your sandbox" — this is a pointer to an **external** Maxio help-center article (URL, not embedded content), which this agent's guard does not permit fetching (out of scope: SDK map/source only, never external docs).
  - The single illustrative digit-string that appears anywhere in the SDK source (`5424000000000015`, in `PaymentProfileAttributes.FullNumber`'s doc-comment: "i.e. 5424000000000015") is presented purely as a **format example** ("string representation") with no statement that it is a valid test/sandbox card — treating it as a working test card would be guessing beyond what the source states.
  - **Conclusion: the SDK and its map are silent on a concrete sandbox test-card number.** This plan does not invent one. **Decision needed from you (the user/product owner):** either (a) supply a real Maxio-provided sandbox test card number from your Maxio dashboard/gateway test-mode docs (external to this SDK — not something this agent can grep or confirm), or (b) if the sandbox's connected gateway is itself a test/bogus gateway, any well-formed card number may be accepted without a real charge — confirm the sandbox's actual gateway configuration (also outside the SDK/map's visibility) before choosing a value. Whichever value you supply, wire it through `CreditCardAttributes.FullNumber` unchanged; this plan's contract for that field is complete regardless of which literal digits you use.

**4. One call is sufficient — confirmed, no separate profile-creation call required.** Setting `CreditCardAttributes` (or `BankAccountAttributes`) directly on the same `CreateSubscription` request body creates the payment profile **and** the subscription atomically in one call — this is exactly what `PaymentProfileAttributes`'s "alias to credit_card_attributes" framing and `PaymentProfileId`'s doc-comment ("if you want to use a new (unstored) card … use `payment_profile_attributes` instead") describe: `PaymentProfileId` is the *only* path that requires a prior separate `CreatePaymentProfile` call (or a pre-existing profile from a previous subscription/lookup); `CreditCardAttributes` is the *inline, single-call* path. For this brief's card-capture flow, set `CreditCardAttributes` on `CreateSubscription` directly — no `PaymentProfiles.CreatePaymentProfile` call needed first.

Recommended C# shape for the `CreateSubscription` request in this flow (named arguments per the sheet's convention; illustrative — final digits/expiry are the open decision in item 3):
```csharp
var subscription = new CreateSubscription
{
    ProductHandle = "eshop-pro",           // or "basic-plan"
    CustomerReference = customerReference,  // from the resolved Customer.Reference
    CreditCardAttributes = new PaymentProfileAttributes
    {
        FullNumber = "<sandbox test card — see GAP item 3, not populated by this plan>",
        ExpirationMonth = ExpirationMonth2.Int(12),
        ExpirationYear = ExpirationYear2.Int(2030),
        Cvv = "123",
        FirstName = customerFirstName,
        LastName = customerLastName,
    },
};
```

### 2.6 Error handling — types and accessors, for wrapping in `BillingProviderException`

- Every operation **throws**; there is **no** `{Operation}Result` no-throw variant anywhere in this SDK (247/247 operations are throw-only).
- `SdkException<TError>` (`MaxioAdvancedBilling.Core.Exceptions.SdkException<TError>`) exposes one member: `Error: TError`.
- **Case A (typed)** — `TError` is a per-operation `{Operation}Error : MaxioAdvancedBilling.Core.ErrorResponse.ApiError` (namespace `MaxioAdvancedBilling.Errors`). It exposes one `TryGet…(out …)` per possible response shape **plus** the inherited `TryGetRawError(out MaxioAdvancedBilling.Core.ErrorResponse.RawError)` fallback. **`TryGetRawError` is not a catch-all — it only fires for statuses that have no more specific typed accessor; check it last, and enumerate every `TryGet…` the operation's row lists (this sheet already does, per operation above) rather than assuming `TryGetRawError` catches everything.**
- **Case B (raw)** — `TError` is `MaxioAdvancedBilling.Core.ErrorResponse.RawError` directly: `StatusCode: HttpStatusCode`, `ReadAsString(): string`, `ReadAsJson<T>(): T?` (throws `JsonException` if body isn't valid JSON — prefer `ReadAsString()` unless the body shape is confirmed JSON), `ReadAsBytes(): ReadOnlyMemory<byte>`.
- Recommended `BillingProviderException` wrapping shape (one place, applied to every call site in scope):
  ```csharp
  catch (SdkException<{Operation}Error> ex)   // Case A — one branch per TryGet* this sheet lists for the op
  {
      if (ex.Error.TryGet{TypedBody}(out var body)) throw new BillingProviderException(DescribeTypedBody(body), ex);
      else if (ex.Error.TryGetRawError(out var raw)) throw new BillingProviderException($"HTTP {(int)raw.StatusCode}: {raw.ReadAsString()}", ex);
  }
  catch (SdkException<RawError> ex)            // Case B
  {
      throw new BillingProviderException($"HTTP {(int)ex.Error.StatusCode}: {ex.Error.ReadAsString()}", ex);
  }
  catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)  // connection failure — NOT an SdkException
  {
      throw new BillingProviderException("Maxio unreachable", ex);
  }
  ```
- **Typed 422 payload quirk to defend against (label: UNVERIFIED against live traffic):** `CustomerErrorResponse1` (the `CreateCustomer`/`UpdateCustomer` 422 payload) is `{ Errors: MaxioAdvancedBilling.Models.Errors? }`, and `Errors` (confirmed from `Models/Errors.cs`) declares **only** `PerPage (per_page): IReadOnlyList<string>?` and `PricePoint (price_point): IReadOnlyList<string>?` — fields that make no sense for a customer-validation error (e.g. a duplicate `reference`). This looks like a generated artifact that does not model real customer-error keys (no `email`/`reference` field). **Defensive directive:** when `TryGetCustomerErrorResponse1` succeeds, best-effort extract `PerPage`/`PricePoint` if present, but always **also** call `TryGetRawError` as a second attempt and prefer its raw body text for the exception message if the typed fields are both empty — do not assume the typed accessor alone yields a usable message for this operation.
- **`CancelSubscriptionApiError`'s 422 accessor returns a *union*, not a flat model:** `TryGetCancelSubscriptionErrorResponse(out CancelSubscriptionErrorResponse)` — and `CancelSubscriptionErrorResponse` (`MaxioAdvancedBilling.Models.AnyOf` — actually generated as a `OneOf`-shaped type per `unions.md`) is itself `ErrorListResponse1 | SingleErrorResponse1`, read via a **second** `TryGet…` call: `errResp.TryGetErrorListResponse1(out ErrorListResponse1 e1)` or `errResp.TryGetSingleErrorResponse1(out SingleErrorResponse1 e2)` (`SingleErrorResponse1.Error: string !req`). Two-level unwrap — don't stop at the outer `TryGet`.
- Several "typed" 404 accessors (e.g. `TryGetNoContent(out RawError)` on `ReadSubscriptionComponentError`, `CancelDelayedCancellationError`, etc.) still hand back a plain `RawError` — the accessor name is status-specific but the payload type carries no more structure than Case B; treat it identically to `TryGetRawError` once matched.

## 3. Trap notes (skill-derived, attached to the step where they bite)

- **Step 0 (client/DI):** the SDK does not own the `HttpClient` — construct/reuse one long-lived instance (or register via `IHttpClientFactory`), never one per request; the `MaxioAdvancedBillingClient` itself is also meant to be constructed once and reused, not per-call. If using `AddMaxioAdvancedBillingClient(...)` in DI, set `BasicAuth` and `Server.Production.Us.Site` inside that registration callback (or before constructing the client directly) — not after. (dotnet-client-initialization, dotnet-authentication)
- **Step 0 (retries):** `RetryOptions.HttpMethodsToRetry` defaults to idempotent verbs only (`GET/HEAD/PUT/OPTIONS`) — `CreateSubscription`, `CreateUsage`, `MigrateSubscriptionProduct`, `CancelSubscription`(DELETE), `InitiateDelayedCancellation`(POST), `PauseSubscription`(POST) are **not retried** on a transient failure by default. For `CreateUsage` specifically (a POST that is logically idempotent per-call only if you dedupe by memo/timestamp yourself — the API itself does not deduplicate), consider your own retry-with-idempotency-key discipline at the call site rather than relying on SDK retry. `Timeout` on `RetryOptions` is **per attempt**, not total — bound a whole call with a `CancellationToken` instead. (dotnet-configuration-resilience)
- **Steps 1, 2, 3, 4, 5, 6 (all list/multi-optional-param calls):** call every operation with **named arguments** — several nullable query params (e.g. `ListProductsForProductFamily`'s `dateField…include`, `ListSubscriptions`'s 14 leading params, `ListUsages`'s `sinceId…untilDate`) have **no C# default** despite being nullable, so a positional call mis-binds or fails to compile. Pass `null` explicitly by name for anything not in use. (dotnet-calling-endpoints)
- **Step 1 (UC0 handle lookups):** don't assume every "by id" path param quietly also accepts `"handle:xxx"` just because an operation's prose says the *resource* supports handle lookup — the map/source showed `ReadProductFamily`'s `id` is a hard `int`, so that specific method cannot. Confirm the parameter's declared C# type before relying on a handle string; prefer the SDK's dedicated by-handle methods (`ReadProductByHandle`, `FindComponent`) where they exist.
- **Step 2/3 (unions in path params):** `CreateUsage`/`ListUsages` take `SubscriptionIdOrReference` and `ComponentIdModel` — both `AnyOf` unions — **construct with the static factories** (`SubscriptionIdOrReference.Int(id)` / `.String(reference)`, `ComponentIdModel.Int(id)` / `.String(handle)`), never `new SubscriptionIdOrReference(...)` (no object-initializer on a union). (dotnet-models)
- **Step 3 (enum read-back):** `Subscription.State` is a `StringEnum<SubscriptionState>`, not a C# `enum` — compare with `==` (value-based) or read `.Value` for the raw wire string; don't `switch` on it as if it were a BCL enum without first confirming `StringEnum<T>`'s pattern-matching support, and guard unknown/future values with `IsKnownValue()`/`TryGetKnownValue(...)` rather than assuming the 15 values above are exhaustive forever. (dotnet-models)
- **Step 4 (usage idempotency under retry):** because `CreateUsage` is a POST and is not auto-retried, a network blip after the server accepted the usage but before your code observed the response risks a double-record if your own application-level retry naively re-calls `CreateUsage` with the same quantity — read `SubscriptionComponent.UnitBalance` before and after to detect a possible double-apply, or maintain your own dedupe key in the `Memo` field.
- **Step 5 (UC3 migration vs delayed change):** these are **two unrelated code paths** in this SDK, not one operation with a flag — don't try to unify them into a single call; see the GAP note in §2.4 for the preview asymmetry (no preview exists for the delayed/no-proration path).
- **Step 6 (lifecycle preconditions):** for every "the server enforces X" note in §2.5, the SDK performs **no client-side precondition check** — it always attempts the HTTP call and surfaces the server's 422/404 through the typed error. Where this plan says "caller must check `State` first," that's purely to short-circuit a doomed round-trip for a better UX; it is not required for correctness (the server is authoritative either way).
- **Step 7 (error handling, all steps):** never write a shared `Describe(ApiError e)` helper typed to the `ApiError` base — it can only reach `TryGetRawError` (the base class's only member) and silently misses every typed 422/404 body this sheet lists per operation. Read the typed `TryGet…` accessors **inside each operation's own `catch (SdkException<{Operation}Error>)` block**, where the concrete type is known, and keep only the `RawError`/connection-failure fallback shared. (dotnet-error-handling)
- **Step 7 (logging/first-run verification):** because a wrong verb or a mis-substituted path segment (e.g. passing `ComponentIdModel.String("api-call")` where the server actually expects `"handle:api-call"`) compiles cleanly and only shows up as a runtime 404, attach a temporary logging `DelegatingHandler` to the `HttpClient` for the first real run of each new operation in this plan and confirm the verb/path/query on the wire before trusting the happy path. (dotnet-configuration-resilience)
