## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Application idempotency and source-of-record boundary

| Concern | Directive | Source |
|---|---|---|

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership and SDK wrapper lifetime determine connection reuse and testability. **MUST load `maxio-sdk:dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential timing, configuration sourcing, and rotation determine whether every request is authenticated safely. **MUST load `maxio-sdk:dotnet-authentication`** before setting credentials.

⚠ Steps 2, 4–7 (calls) — nullable parameters without C# defaults must still be passed, and positional calls can silently bind the wrong filter. **MUST load `maxio-sdk:dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 2, 4–7 (models) — envelopes, required initializers, nullable response members, and `StringEnum` conversion can otherwise produce compile failures or incorrect DTOs. **MUST load `maxio-sdk:dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 5–6 (write resilience) — whether a failed subscription write can be re-sent and what an SDK timeout actually bounds directly affect duplicate-risk and latency. **MUST load `maxio-sdk:dotnet-configuration-resilience`** before configuring retries/timeouts or finalizing reconciliation.

⚠ Step 8 (error boundary) — typed and raw operations expose different catch/accessor paths, so one generic SDK catch ladder loses provider semantics. **MUST load `maxio-sdk:dotnet-error-handling`** before writing the boundary.

⚠ Step 8 (2xx drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Step 8 (non-2xx drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `maxio-sdk:dotnet-error-handling`** before writing that boundary.

⚠ Step 9 (tests) — mocking generated controllers couples tests to SDK internals and misses serialization/auth/server behavior. **MUST load `maxio-sdk:dotnet-testing`** before choosing the seam.

## 5. Assumptions & Blockers

- **Assumption — identity data:** the application can resolve an immutable local user ID plus non-empty first name, last name, and email for `CreateCustomer`; those three customer fields are SDK-required. If claims do not carry all three, the application must resolve them from its own identity store or apply an explicit validated fallback policy before calling Maxio.
- **Assumption — catalog:** the configured family exists and its selectable products expose non-null handle, name, price, interval, and interval unit; malformed/incomplete entries are rejected or omitted defensively rather than guessed.
- **Assumption — default price point:** the requested product's default price point is the intended charge because the create payload deliberately omits both product-price-point selectors. The product handle is caller-supplied from the dynamically returned configured-family catalog; seeded handles are verification data, not hard-coded integration settings.
- **Assumption — payment:** the target sandbox products do not require a stored payment instrument, matching the brief; the request intentionally sends no card, bank, or payment-profile fields and explicitly selects `CollectionMethod.Remittance` so Maxio does not attempt automatic collection.
- **Assumption — local idempotency scope:** one active/nonterminal enrollment per caller+product is the desired double-click rule. A future explicit re-subscribe policy after cancellation is an application decision.
- **UNVERIFIED — subscription-reference uniqueness:** only live provider behavior could establish whether duplicate subscription references are rejected. The map promises lookup by reference but not uniqueness; the design therefore relies on an atomic application claim for double-click safety and uses reference only for reconciliation.
- **Blockers:** none for implementing the described hero flow. An absolute provider-level exactly-once guarantee across ambiguous transport failures cannot be claimed from the mapped SDK contract alone because `CreateSubscription` exposes no idempotency-key parameter and subscription-reference uniqueness is unverified; surface ambiguous outcomes as pending/reconciling rather than issuing an uncoordinated second create.
