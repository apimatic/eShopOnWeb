# Maxio recurring-subscription billing plan

## Scope & sequence

| Step | Implementation work | Maxio operations |
|---|---|---|
| 1. Package and configuration | Add NuGet `AsadAli.AdvancedBilling.Sdk` **1.0.2** to the project that owns the Maxio adapter (or pin `1.0.2` in central package management). Keep the API key out of committed JSON and use environment variables/user-secrets. Validate required values at startup. Seed/default the non-secret family handle to `eshop-subscribe`; do not store or use seeded resource IDs. | — |
| 2. Client and sandbox guard | Register a long-lived `HttpClient` pipeline and SDK client through the existing DI composition root. Use Basic auth, US Production server group, configured subdomain, and the optional base-URL override exactly as described in the contract sheet. Before serving Maxio-backed reads and, critically, before every write (a short positive cache is acceptable), call the sandbox guard; fail closed unless the returned `Site.Test` is exactly `true`. When no base override is present, also require returned `Site.Subdomain` to equal configured `Maxio:Subdomain`. | `Sites.ReadSite` |
| 3. Persistence and application boundary | Add billing entities/repositories through the repository's existing domain/infrastructure conventions: `MaxioCustomerLink` keyed uniquely by canonical eShop user ID, and `MaxioSubscriptionLink` keyed uniquely by `(UserId, ProductHandle)` with deterministic customer/subscription references, lifecycle (`Pending`, `Completed`, `RetryableFailure`, `TerminalFailure`), lease/version, timestamps, last sanitized error, and cached confirmation fields. Add database unique constraints, not only process locks. With the development in-memory database, uniqueness/recovery lasts only for that process lifetime; after restart, deterministic Maxio reference lookups rebuild links. Keep Maxio DTOs inside the infrastructure adapter. | — |
| 4. Caller identity | Require the existing PublicApi JWT policy on all three endpoints. Resolve canonical user ID from the authenticated principal's immutable subject/name-identifier claim; resolve email/name from trusted claims or the user store. Never accept user/customer identity from route, query, or body. Return 401 for no valid principal and a validation/problem response if the trusted profile lacks a usable email (Maxio customer creation requires email). | — |
| 5. Plan discovery | Implement `GET /api/subscription-plans`. Manually page through all active products using named arguments and the documented default `perPage: 20`; filter locally by exact `Product.ProductFamily.Handle == Maxio:ProductFamilyHandle`, `ArchivedAt == null`, and non-null product handle. Return only API DTO fields such as handle, name, description, price-in-cents, interval, interval-unit, and site currency. The seeded results are expected to include `eshop-pro` and `basic-plan`, but discovery/validation must not hardcode them. The seeded `api-call` component is not used by these endpoints. | `Sites.ReadSite`, `Products.ListProducts` |
| 6. Reserve an idempotent subscription request | Implement `POST /api/subscriptions` with body `{ productHandle }`; an optional caller `Idempotency-Key` may be recorded, but correctness must not depend on it. Validate the exact handle against Step 5's family-filtered results. In a short database transaction, atomically insert/claim the `(UserId, ProductHandle)` subscription link. A completed row returns the existing confirmation; another live lease returns 202 with a status/location or a retryable conflict; only the lease owner may call Maxio. Never hold a database transaction across an HTTP call. | `Products.ListProducts` |
| 7. Ensure one customer | Derive a deterministic, non-PII reference from the canonical user ID (versioned prefix plus SHA-256). Check the local unique user link, then reconcile with `ReadCustomerByReference`. On 404, create from trusted profile data with that reference. If create returns 422 or the response is ambiguous, look up the same reference again before failing. Verify every recovered customer has the expected reference, then complete/upsert the local link. The Maxio-generated numeric customer ID may be stored only as diagnostic response data; it is not a resource key and is never used in a request. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 8. Create/reconcile one subscription | Derive a deterministic subscription reference from `(canonical user ID, exact product handle)` using a versioned prefix plus SHA-256. Before POST, call `FindSubscription(reference)`. If found, require exact matching `Subscription.Customer.Reference` and `Subscription.Product.Handle`, then repair the local row. If 404, create with `ProductHandle`, `CustomerReference`, `Reference`, and `PaymentCollectionMethod = CollectionMethod.Invoice`; omit all payment-profile/card/bank fields. After any ambiguous transport/timeout/deserialization outcome, reconcile by reference before allowing a retry. On typed 422, preserve safe validation detail and reconcile once before marking terminal. The local unique reservation is the duplicate-prevention authority; remote reference uniqueness and idempotency are not assumed. | `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription` |
| 9. Confirmation and current-user listing | Map creation/reconciliation to `{ reference, plan: { handle, name }, priceInCents, state, nextBillingDate }`, where actual subscription price is `Subscription.ProductPriceInCents`, state is `Subscription.State`, and nullable next billing date is `Subscription.NextAssessmentAt`. Implement `GET /api/my-subscriptions` by querying only the caller's local links and refreshing each through `FindSubscription(reference)`; never accept another user's reference and never enumerate the whole Maxio site. If an in-memory restart leaves no links, rediscover this configured family's product handles, derive this caller's deterministic reference for each, probe `FindSubscription`, and rebuild only exact customer/product matches. If a recovered response does not match the expected customer/product reference, quarantine it and return a safe conflict/problem rather than exposing it. | `Products.ListProducts`, `Subscriptions.FindSubscription` |
| 10. Error boundary and observability | Translate known Maxio validation/not-found/auth/rate-limit/upstream cases to RFC 7807 without secrets or raw bodies; attach correlation/reference identifiers, structured logs, and metrics for reconciliation, duplicates prevented, latency, and upstream status. Keep unexpected response-body drift distinct from deterministic provider rejection. Do not log Basic auth, API key, or full customer data. | All above |
| 11. Tests | Add domain/service, persistence, endpoint authorization, and HTTP-adapter tests using the SDK's `HttpClient` seam and the repository's existing test stack. Cover configuration/base URL, sandbox fail-closed behavior, pagination/family filtering, spoof resistance, customer and subscription concurrency, crash-window reconciliation, ambiguous POST outcomes, response mapping, error shapes, JSON drift, cancellation, and in-memory restart recovery. Assert one outbound customer POST and one outbound subscription POST under concurrent double-clicks. | All above |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Application/API invariants

| Concern | Required behavior |
|---|---|
| Stable identifiers | The configured family handle `eshop-subscribe`, product handles (currently `eshop-pro`, `basic-plan`), and component handle `api-call` are strings. Never resolve them once and persist/use numeric seeded IDs. Requests use `ProductHandle`/`CustomerReference`/`Reference`; component is out of scope until usage recording is added. |
| Customer key | `customerReference = "eshop-customer-v1-" + lowercaseHex(SHA256(canonicalUserIdUtf8))`; unique local `UserId` and unique `CustomerReference`. Hashing avoids PII; the versioned algorithm must never change without a migration. |
| Subscription key | `subscriptionReference = "eshop-sub-v1-" + lowercaseHex(SHA256(canonicalUserId + "\n" + exactProductHandle))`; unique local `(UserId, ProductHandle)` and unique `SubscriptionReference`. Exact handle comparison; do not lowercase an API handle. |
| Double-click/concurrency | Acquire ownership with a database atomic insert/update and unique constraint. A process-local semaphore may reduce contention but is not correctness. Non-owners never issue POST. Completed duplicates return the same semantic result. Expired pending leases first reconcile by reference. |
| Crash/ambiguous-write recovery | Lookup deterministic reference before every POST and after any uncertain POST outcome. Finalize local state only after response/reference/customer/product validation. Never automatically issue a second POST merely because the first response was lost. |
| No payment method | Use `CollectionMethod.Invoice`; do not send any card, bank, payment profile ID, or payment-profile attributes. Startup/readiness must also verify the sandbox seed products are compatible with paymentless signup; the mapped product flags `RequireCreditCard`/`RequestCreditCard` can be surfaced as a configuration error when true. Live acceptance remains governed by Maxio validation. |
| Confirmation | `plan.handle/name` from nested `Subscription.Product`; `priceInCents` from `Subscription.ProductPriceInCents`; `state` from `Subscription.State`; nullable `nextBillingDate` from `Subscription.NextAssessmentAt`. Do not substitute `CurrentPeriodEndsAt` under the same name; it may be returned separately if useful. |
| HTTP behavior | `GET` endpoints return 200; POST new completion returns 201, replayed completion 200, owned in-progress duplicate 202 (with safe retry/location metadata), unauthenticated 401, invalid/unavailable plan 400/404, sandbox violation/configuration failure 503, upstream validation 422, upstream throttling 503 with bounded `Retry-After`, and unexpected upstream failure 502/503 per the application's existing problem conventions. |

## Trap notes

⚠ Step 2 (client registration) — `HttpClient` ownership and the SDK wrapper lifetime can cause socket exhaustion or handler churn if registered at the wrong seam. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 2 (authentication) — credential timing, Basic-auth manager shape, and safe configuration rotation affect whether requests are authenticated without leaking secrets. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 2, 5, 7–9 (calls) — many nullable SDK parameters have no C# default, named arguments must use literal generated names, and envelopes add a payload level. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 5, 7–9 (models) — required initializers, JSON wire names, and string-enum wrappers can silently produce invalid requests or mappings when treated like ordinary mutable DTOs/C# enums. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 2 and 6–10 (resilience) — retry/timeout scope, POST transport-failure behavior, cancellation, manual pagination, base-URL selection, and absent built-in logging directly affect duplicate prevention and total request latency. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing the write-reconciliation state machine.

⚠ Steps 7–10 (error boundary) — Case A typed errors and Case B raw errors expose different safe access paths; confusing them loses status/detail or throws while translating. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 10 (2xx JSON drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Step 10 (non-2xx JSON drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 11 (tests) — mocking generated controllers/models couples tests to SDK internals and misses real serialization, auth, query, and error behavior. **MUST load `dotnet-testing`** before writing integration-layer tests.

## Assumptions & Blockers

- Assumption: the repository's authenticated user has an immutable claim/user-store key plus a trusted email. Customer first/last names come from trusted profile data; if absent, the product owner must choose a deterministic non-deceptive fallback or require profile completion before customer creation.
- Assumption: `Maxio:ProductFamilyHandle` is `eshop-subscribe` in the target sandbox and that family contains active `eshop-pro` and `basic-plan` products configured for paymentless signup. `api-call` is a future metered-usage concern and no usage endpoint is in this scope.
- Assumption: one subscription per user per product handle is the desired duplicate rule. Re-subscription after cancellation needs an explicit lifecycle/generation policy; until chosen, return the existing terminal subscription rather than creating another.
- Blocker/capability gap: the SDK map exposes no per-call idempotency header/key for `CreateCustomer` or `CreateSubscription`, and the map does not establish live subscription-reference uniqueness. The plan therefore cannot promise provider-side idempotency; database uniqueness, serialized ownership, deterministic references, and post-ambiguity lookup are mandatory.
- Blocker/capability gap: the SDK has no sandbox environment selector. `ReadSite().Site.Test == true` is the available contract-grounded guard; if that field is null/false or the call cannot be completed, writes must remain disabled.
- Blocker/capability gap: the generated `CustomerErrorResponse1.Errors` shape is suspicious for customer validation and live payload fidelity is unverified. Extract best-effort through the documented accessor, fall back to a generic safe message, and use reference lookup for race recovery.
- Blocker/capability gap: an in-memory development database loses local leases/mappings at restart and cannot coordinate multiple processes. Deterministic reference reconciliation repairs state after restart, but production duplicate guarantees require a durable shared database with unique constraints and concurrency tokens.
