# Maxio recurring subscriptions — implementation plan

## 1. Scope & sequence

1. **Runtime/configuration and client registration.** Add the SDK package if absent; bind the four `Maxio:*` keys, map the named deployment credentials into them, configure the US production server node or the verbatim `Maxio:BaseUrl` override, and register one `MaxioAdvancedBillingClient` over the app's long-lived `HttpClient`.
2. **JWT-gated plan discovery.** Implement `GET /api/subscription-plans`; call `ListProductsForProductFamily` with `handle:<Maxio:ProductFamilyHandle>`, manually page through products, and expose only plan handles and current recurring price metadata.
3. **JWT-gated subscription creation.** Implement `POST /api/subscriptions`; take only a plan handle (and the application-chosen idempotency key if its API contract requires one), derive the Maxio customer and subscription references from the validated JWT identity, resolve/create the customer, find the subscription by reference, and create it only when absent.
4. **JWT-gated subscription reads.** Implement `GET /api/my-subscriptions`; resolve the Maxio customer from the validated JWT identity and call `ListCustomerSubscriptions`, mapping each returned subscription to plan, price, state, and next billing date.
5. **Error boundary, resilience, and tests.** Add the SDK Case-A/Case-B exception translation and `JsonException` boundary, configure bounded calls/retry policy appropriate to non-idempotent writes, use the requested in-memory database/runtime settings, and test the HTTP seam, envelopes, handles, duplicate-click paths, paging, auth, and failures.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

All operations are async and throw; this SDK has no `…Result` no-throw siblings.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the SDK client, `HttpClient` lifetime, generated DI extension, and nested server override have separate lifetime/configuration consequences that are not visible in the constructor alone. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — the credential property, Basic-auth construction order, and configuration source must line up before the client is constructed. **MUST load `dotnet-authentication`** before wiring credentials.
- ⚠ Step 2 (calling plans) — list/search parameters are numerous nullable values without defaults, and a wrong paging/handle argument can compile while sending the wrong request. **MUST load `dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Step 2–4 (models) — generated envelopes, nullable inner records, wire names, and enum wrappers determine whether a response is safely mapped; a public DTO must not dereference an absent inner payload. **MUST load `dotnet-models`** before constructing or mapping SDK models.
- ⚠ Step 5 (error boundary) — Case-A typed errors and Case-B raw errors expose different access paths, and an SDK-exception-only ladder does not cover every deserialization failure. **MUST load `dotnet-error-handling`** before writing catches or middleware.
- ⚠ Step 1 and Step 5 (resilience) — retry/status/transport behavior, per-attempt limits, whole-call cancellation, base URL, and logging interact with a non-idempotent subscription write. **MUST load `dotnet-configuration-resilience`** before tuning the client or retry policy.
- ⚠ Step 5 (testing) — the correct seam is the SDK's supplied `HttpClient`, and status-triggered and transport-triggered retry paths must be tested separately for writes. **MUST load `dotnet-testing`** before writing integration tests.

System.Text.Json.JsonException reaches the boundary from two directions and they need opposite handling:

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- **Assumption — JWT identity:** the existing PublicApi host validates JWTs and exposes a stable identity value through its authenticated principal; the implementer will use that value and will not trust identity fields from the POST body. Exact claim selection is `YOUR CALL — not in the map`.
- **Assumption — one intent per reference:** a repeated click for the same authenticated identity and plan/intent is meant to return the existing Maxio subscription rather than create a second subscription. If the product must support multiple simultaneous subscriptions to the same plan, the POST contract needs a caller-supplied idempotency key; that application choice is `YOUR CALL — not in the map`.
- **Assumption — payment scope:** no raw or tokenized payment input was requested. The configured recurring product must accept signup without payment input; otherwise adding a trusted payment-token flow is required before that product can be enabled.
- **Assumption — sandbox configuration:** deployment supplies the sandbox-compatible value for `Maxio:Subdomain` and, where necessary, `Maxio:BaseUrl`; no sandbox URL or credential value is hard-coded.
- **Assumption — in-memory runtime:** the requested in-memory database is acceptable for this reference-app run/test environment. It does not provide durable cross-restart idempotency coordination; stable Maxio references plus the application collision/re-read path remain required, and multi-instance coordination is `YOUR CALL — not in the map`.
- **Blockers:** none for the requested single-reference-app flow, provided the Maxio product family handle and payment requirements satisfy the assumptions above.
