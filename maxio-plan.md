# Maxio subscription billing plan

## Scope & sequence

| Step | Design / build order | Maxio operations |
|---|---|---|
| 0. At-most-one-send invariant | The installed resilience skill supplies the missing safety mechanism: every `CreateSubscription` logical operation runs inside a caller-opened `AsyncLocal` write scope and through a `DelegatingHandler` that counts before network send and blocks attempt 2+. Combine that transport guard with a unique enrollment row/per-key gate and a durable send-authorized marker. No raw HTTP, guessed header, or undocumented reference-uniqueness assumption is used. | `CreateSubscription`, `FindSubscription` |
| 1. Package and configuration | Add NuGet `AsadAli.AdvancedBilling.Sdk` pinned to `1.0.2` to `src/PublicApi` only. Bind and validate an internal `MaxioOptions` from section `Maxio:` with exactly `ApiKey`, `Subdomain`, `ProductFamilyHandle`, and optional `BaseUrl`. Put values in PublicApi user-secrets from `MAXIO_API_KEY`, `MAXIO_SITE_SUBDOMAIN`, and `MAXIO_DEFAULT_PRODUCT_FAMILY`; do not write values to tracked files. The SDK map has no sandbox environment member: the sandbox site uses the Production/US server group and the configured site subdomain. `MAXIO_ENVIRONMENT` is therefore a deployment guard, not a fifth `Maxio:` option and not a URL. If `Maxio:BaseUrl` is nonempty, assign that exact string to the Production/US base URL (no derivation, trimming, or suffixing); otherwise set the Production/US `Site` to `Subdomain`. | none |
| 2. Client boundary | Register named long-lived `HttpClient` pipelines and construct SDK clients behind a narrow application-owned `IMaxioBillingGateway`. Read/lookups use a normal SDK client and may retry. The write SDK client uses a `SingleSendHandler : DelegatingHandler`. The caller opens a `MaxioWriteScope` whose state lives in `AsyncLocal`; `SendAsync` increments that scope’s attempt count **before** `base.SendAsync`, permits attempt 1, and on attempt >1 throws a private `DuplicateSendBlockedException : Exception` that must **not** derive from `HttpRequestException`. Do not store the marker on `HttpRequestMessage`, because the SDK builds a fresh request per attempt. Set Basic auth from configuration; never expose SDK records from PublicApi endpoints. Keep catalog IDs transient and never persist/configure seeded numeric IDs. | none |
| 3. Plan catalog | Resolve the configured family dynamically: call `ListProductFamilies`, exact-match `ProductFamily.Handle`, require its runtime `Id`, then page `ListProductsForProductFamily` using that runtime ID rendered invariantly. Use `page=1..N`, `perPage=20`, and stop when a page contains fewer than 20 records. Exclude records with `ArchivedAt != null`; de-duplicate by nonempty handle. Map `Name`, `Handle`, `Description`, `PriceInCents`, `Interval`, and `IntervalUnit`. A missing/ambiguous configured family is a dependency/configuration failure, not an empty catalog. | `ProductFamilies.ListProductFamilies`; `ProductFamilies.ListProductsForProductFamily` |
| 4. Current-user identity | Every endpoint is JWT-authenticated and gets the immutable user key from the token/current-user service, never from request JSON. Load email/name from the application identity store; a valid email is required because Maxio customer creation requires it. Derive opaque deterministic references (for example fixed-length SHA-256-based values) from the immutable user ID and, for subscriptions, the exact plan handle. Never use mutable email as the reference key. | none |
| 5. Validate subscribe target | Accept only `{ "productHandle": "..." }`. Call `ReadProductByHandle`, require `ArchivedAt == null`, and verify the returned nested `ProductFamily.Handle` exactly equals configured `ProductFamilyHandle`; reject cross-family or missing products. Do not trust client-supplied numeric IDs or prices. | `Products.ReadProductByHandle` |
| 6. Ensure customer | `ReadCustomerByReference(deterministicUserReference)`. On its documented 404, call `CreateCustomer` with required first name, last name, email and the same unique reference. If create returns 422 (including a concurrent unique-reference winner), re-read by reference; only treat it as success if that exact customer now exists. Maxio explicitly guarantees customer-reference uniqueness. | `Customers.ReadCustomerByReference`; `Customers.CreateCustomer` |
| 6a. Resolve no-card collection | Before persisting the durable subscription-send authorization, call `Sites.ReadSite`. If `Site.RelationshipInvoicingEnabled == true`, select `CollectionMethod.Remittance`; otherwise select `CollectionMethod.Invoice`. Pass the selected value as `CreateSubscription.PaymentCollectionMethod`. This prevents the provider from defaulting to automatic collection and rejecting the signup for having no payment method, while sending no card/payment-profile data. A site-read failure occurs before send authorization and is a dependency failure, not an unknown create outcome. | `Sites.ReadSite` |
| 7. Idempotent enrollment | Use an application enrollment record uniquely keyed by `(UserId, ProductHandle)` with deterministic `CustomerReference`, deterministic `SubscriptionReference`, status, concurrency token, a durable `SendAuthorizedAt`/attempt marker, and optional returned Maxio ID; it is coordination/projection data, never the billing system of record. Under a per-key in-process async gate (required for EF InMemory within one run) and a durable unique-row/compare-and-swap gate in production: (1) call `FindSubscription(reference)` first and reconcile/return when found; (2) only the unique owner may atomically persist the send-authorized marker; (3) once that marker commits, no request may ever authorize another `CreateSubscription` POST for that enrollment; (4) the owner opens `MaxioWriteScope` and calls the SDK write client once with `ProductHandle`, `CustomerReference`, and deterministic `Reference`; (5) the handler permits only the first network send and blocks every SDK retry with `DuplicateSendBlockedException`; (6) after the sentinel, any transport ambiguity, timeout, cancellation, or crash-after-authorization, call `FindSubscription` through the read client. If found, reconcile to confirmed. If not found, persist `Unknown`; all later subscribe attempts may re-run lookup but must never issue a second POST. `Unknown` is permanent with respect to automatic creation and changes only when a lookup discovers the Maxio subscription or an operator explicitly resolves it. This deliberately trades automatic recovery for the mandated at-most-one-create guarantee. | `Subscriptions.FindSubscription`; `Subscriptions.CreateSubscription` |
| 8. Read my subscriptions | Resolve the customer by deterministic reference; documented 404 means `[]`. Otherwise call `ListCustomerSubscriptions(customerId)`, require the returned subscription customer/product projections, and include only products whose nested family handle matches configuration. Read plan/price/state/next-billing live from Maxio, not from the enrollment row. | `Customers.ReadCustomerByReference`; `Customers.ListCustomerSubscriptions` |
| 9. HTTP surface | Follow PublicApi endpoint conventions and JWT authorization on `GET /api/subscription-plans`, `POST /api/subscriptions`, `GET /api/my-subscriptions`. Suggested response projection: `{ id, plan: { handle, name }, priceInCents, currency, interval, intervalUnit, state, nextBillingAt }`; for plans omit fields not supplied by Maxio (notably product currency). For subscription `nextBillingAt`, map `NextAssessmentAt ?? CurrentPeriodEndsAt`; for price use `ProductPriceInCents` and fall back to nested product `PriceInCents` only when absent. `POST` returns `201` for a newly confirmed subscription and `200` for idempotent replay/reconciliation, with the same projection. | operations from Steps 3–8 |
| 10. Error boundary | Translate every SDK error at the gateway boundary to application exceptions/problem details; never leak API keys, raw bodies, or SDK models. Distinguish configured-catalog failure, caller product rejection, Maxio validation rejection, not-found-as-control-flow, throttling/transient dependency failure, malformed response, cancellation, and programming/configuration errors. Log correlation/reference hashes and status, not PII/secrets. | all above |
| 11. Tests and live proof | Unit-test the gateway with the SDK’s `HttpClient` seam and fixture JSON for every envelope/error shape; test service concurrency/reconciliation with fakes; endpoint-test JWT ownership and status contracts. Prove the handler with a primary handler that throws `HttpRequestException` after recording attempt 1: assert exactly one downstream network send, attempt 2 is blocked by the private sentinel, and a subsequent GET reconciliation may retry. Prove concurrent double-clicks create one enrollment/send authorization and one upstream POST. Prove sentinel/transport failure plus missing lookup persists `Unknown`, and every later request performs lookup only with zero additional POSTs. Then smoke-test the sandbox: authenticate PublicApi, list both family plans, submit the same plan concurrently, confirm one Maxio subscription, and list it with matching price/state/next date. Stop every detached host by PID. | all above |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different child namespaces. Dropping a type to the root or to `.Models` makes the
> implementer guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 1 (package/config) — the NuGet package ID and imported root namespace differ, and the map version must stay aligned with the installed version or generated names can fail at compile time. **MUST load `dotnet-client-initialization`** before package/client wiring.

⚠ Step 2 (client registration) — SDK-client and underlying `HttpClient` lifetimes differ; the wrong ownership model can exhaust sockets or discard the handler pipeline. **MUST load `dotnet-client-initialization`** before registering the client.

⚠ Step 2 (authentication) — credentials must be present at construction and rotation/configuration mistakes surface as 401/403 while risking secret exposure in logs. **MUST load `dotnet-authentication`** before wiring Basic auth.

⚠ Steps 2 and 7 (server/resilience) — retry configuration cannot disable all write re-sends; the single-send handler’s scope lifetime, marker location, exception base type, and count-before-send ordering determine whether duplicate-subscription safety actually holds. **MUST load `dotnet-configuration-resilience`** before configuring the client or enabling the write path.

⚠ Steps 3–8 (calls) — optional parameters without C# defaults must still be passed, positional list calls easily mis-bind, and cancellation uses the literal named argument `ct:`. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–9 (models) — required/init-only envelopes, nullable inner records, JSON wire names, and `StringEnum<T>` conversion affect both request validity and safe projection. **MUST load `dotnet-models`** before building or mapping models.

⚠ Step 10 (error boundary) — Case A typed errors and Case B raw errors require different catch/read paths; treating one as the other loses provider detail or causes a second exception. **MUST load `dotnet-error-handling`** before writing any catch ladder.

⚠ Step 10 (2xx JSON drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 10 (non-2xx JSON drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 11 (tests) — mocking generated controllers couples tests to SDK internals and misses actual serialization/envelope/error behavior. **MUST load `dotnet-testing`** before writing integration tests.

## Assumptions & Blockers

- No unresolved plugin blocker remains. Subscription reference uniqueness is still undocumented and is deliberately not assumed; the plugin-grounded single-send handler plus durable authorization invariant provides the required at-most-one-create guarantee.
- At-most-one semantics require a permanent automatic-creation `Unknown` state after any send-authorized outcome that lookup cannot confirm. Neither lease expiry, process restart, repeated POST endpoint calls, nor a missing reconciliation result may authorize another `CreateSubscription`; only later lookup discovery or explicit operator resolution may leave `Unknown`.
- The SDK exposes only `ServerEnvironment.Us` and `.Eu`, not a distinct sandbox member. The supplied sandbox is treated as a US-hosted site reached through the Production server-group template using `Maxio:Subdomain`; `Maxio:BaseUrl`, when supplied, replaces that base verbatim.
- The configured family handle may change across deployments and catalog numeric IDs may change on reseed. Every ID is therefore resolved from the configured handle at runtime and never persisted/configured as catalog identity.
- Subscription creation omits card/payment-profile fields and explicitly selects the site-architecture-appropriate nonautomatic collection method (`Remittance` for RI, `Invoice` for legacy), because a live 422 confirmed that the provider otherwise defaulted to automatic collection and required a payment method for the signup balance. The API accepts any nonarchived product handle in the configured family, including `eshop-pro` and `basic-plan`; `eshop-pro` is a UI/default choice, not a server-side hard-coded target.
- Maxio remains authoritative for customer/subscription existence and subscription price/state/dates. The local enrollment row exists only for authorization-safe correlation, concurrency, crash recovery, and the in-memory single-run caveat stated by the user.
