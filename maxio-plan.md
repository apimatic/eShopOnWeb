## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 2 (client registration) — `HttpClient` ownership and the SDK wrapper lifetime can create socket churn or stale configuration if registered at the wrong lifetime. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 2 (authentication) — the generated credentials property and when configuration is captured determine whether authentication is actually attached and safely rotatable. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 4–9 (calls) — generated nullable parameters without C# defaults still must be passed, and positional calls can silently bind the wrong filter while cancellation uses the literal name `ct`. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 4–10 (models) — required envelope members, nullable inner subscription payloads, init-only records, `StringEnum<T>` values, and JSON wire names can make apparently reasonable construction or mapping fail. **MUST load `dotnet-models`** before constructing requests or projecting responses.

⚠ Steps 6–8 (idempotent write) — retry/timeout configuration determines whether a failed write can be re-sent and therefore whether reconciliation must run before another create. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing the lease/reconciliation boundary.

⚠ Step 11 (error boundary) — Case A typed errors and Case B raw errors expose different safe access paths; assuming one catch shape loses status or provider details. **MUST load `dotnet-error-handling`** before writing any catch ladder.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 12 (tests) — faking SDK controller internals couples tests to generated implementation and misses the real HTTP serialization/error behavior. **MUST load `dotnet-testing`** before choosing the test seam.

## Production error and verification matrix

| Scenario | Required behavior |
|---|---|
| Caller unauthenticated / required stable user claim absent | Existing JWT/auth convention produces 401/403; never fall back to a body-supplied identity. |
| Config absent/invalid | Fail host startup with key names only. Validate nonblank API key, family handle, and either a valid subdomain or nonblank absolute BaseUrl. Never echo values. |
| Family/product/customer/subscription read 404 | Plans family missing → sanitized upstream catalog/configuration problem; requested product missing → API 404; customer missing on `my-subscriptions` → empty list; customer/subscription miss inside create → proceed through the idempotent create/reconcile state machine. |
| Customer create 422 | Re-read by unique reference first to resolve a race; if absent, surface sanitized 422/409 ProblemDetails. |
| Subscription create 422 | Mark ledger `Rejected`; return sanitized business validation details. A later retry may re-attempt only after an explicit state transition/lease acquisition and a fresh `FindSubscription` reconciliation. |
| Timeout, transport failure, upstream 429/5xx, cancellation | Keep ambiguous create ledger `Pending`; distinguish caller cancellation from timeout; use 503/502 and retry hints under the error-handling/resilience rules. Never blindly create again. |
| Missing/null/malformed 2xx envelope | Treat as upstream protocol error, not success; leave ambiguous writes reconcilable. |
| Concurrent same user + same product | Exactly one lease owner reaches `CreateSubscription`; waiters reload/reconcile and return the same Maxio subscription. |
| Same user + different products | Independent unique keys/leases; both may subscribe. |
| Sandbox smoke | Start PublicApi with in-memory DB and required roll-forward flags; acquire a JWT; list plans; POST `eshop-pro` twice (including concurrent requests); assert same Maxio subscription ID/reference; GET mine; optionally repeat with `basic-plan`. Stop the detached host by recorded PID. No numeric seeded ID is used. |

## REQUIRED READING

Load all of these **before implementation starts**. The contract sheet deliberately does not carry their contents.

- `dotnet-authentication` — Step 2, Basic-auth credentials and configuration capture.
- `dotnet-calling-endpoints` — Steps 4–9, generated parameter binding, async calls, and `ct` cancellation.
- `dotnet-models` — Steps 4–10, required request/envelope members, nullability, wire names, and string-enum mapping.

- `dotnet-testing` — Step 12, `HttpClient` test seam and behavior-focused coverage.

## Assumptions & Blockers

- **Assumption:** `POST /api/subscriptions` requires a `productHandle`; `eshop-pro` is the default demo/verification input and `basic-plan` is the alternate, but neither catalog handle is compiled into production selection logic. The only catalog selector in configuration is `Maxio:ProductFamilyHandle`.
- **Assumption:** Maxio `Subscription.NextAssessmentAt (next_assessment_at)` is exposed as the API's `nextBillingDate`; if Maxio returns null, the API returns null rather than synthesizing a date.
- **Assumption:** the configured product-family handle is addressed as `handle:{value}` in the string `productFamilyId` path parameter. The product-family operation map documents the `handle:my-family` resource form, and `ListProductsForProductFamily` exposes that path value as `string`.
- **UNVERIFIED but not relied upon:** the SDK map exposes lookup by subscription `Reference` but does not state that subscription references are unique. Duplicate prevention therefore rests on the application database lease/unique key; `FindSubscription` is reconciliation only. Customer-reference uniqueness, by contrast, is explicitly documented by `CreateCustomer`.
- **Blockers:** None. The bundled plugin map exposes all customer, product-family/product, subscription create/find/list, server override, auth, response, and error contracts required for this scope.
