# Maxio recurring-subscription billing — implementation plan

## 1. Scope & sequence

1. Add the NuGet dependency `AsadAli.AdvancedBilling.Sdk` and bind the named Maxio settings (`ApiKey`, `Subdomain`, `Environment`, `ProductFamilyHandle`, optional `BaseUrl`) without committing secrets. Register one long-lived `MaxioAdvancedBillingClient` over the app's `HttpClientFactory` pipeline.
2. Implement `GET /api/subscription-plans`: list product families, select the configured family by stable handle, use its returned id only as the path value for listing products, then expose product handles and recurring price metadata. No numeric product or family id is hardcoded.
3. Implement `POST /api/subscriptions`: take the plan handle from the request and caller identity from the existing JWT principal; resolve the plan; look up the Maxio customer by deterministic eShop-user reference and create it if absent; look up the deterministic subscription reference and create it if absent; return the Maxio-backed plan, price, state, and next billing date.
4. Implement `GET /api/my-subscriptions`: derive the customer reference from the JWT, resolve the Maxio customer, list that customer's subscriptions, and map only subscriptions belonging to that customer into the public response. Preserve Maxio as the billing system of record; do not alter the existing cart flow.
5. Add one exception boundary for SDK calls, bounded cancellation/retry configuration, safe provider-error translation, and structured diagnostics that never log credentials or payment data.
6. Add unit/contract tests at the `HttpClient` handler seam, then run the app locally with `UseOnlyInMemoryDatabase=true`; perform sandbox end-to-end checks for plan discovery, first enrollment, repeated enrollment, and the authenticated subscription list while exercising the unchanged cart flow.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members
table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.

All operation methods are async and throw on non-2xx; there are no generated `…Result` no-throw variants.

### Idempotency and concurrency contract

The SDK surface contains no idempotency-key field or operation parameter. Use deterministic references derived from the authenticated eShop user and requested plan handle (for example, an application-owned canonical encoding of both values; do not use a display name). The flow is lookup → create-if-missing → re-lookup/reconcile. The application must choose and implement its own coordination for simultaneous requests; the SDK contract does not provide a lock or transaction across customer creation and subscription creation. A POST transport failure is ambiguous because SDK transport retries can resend a POST; reconcile by `FindSubscription` before issuing another create. A 422 from either create must not be blindly converted to success: re-read the deterministic reference and accept only a matching resource, otherwise translate the original typed error.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the SDK client and the `HttpClient`/handler pipeline have different lifetime implications, and a shared unnamed factory client can widen timeout/logging changes to unrelated callers. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — credentials must be present before client construction, and a configuration binding mistake changes the Basic-auth header rather than failing at compile time. **MUST load `dotnet-authentication`** before setting credentials.
- ⚠ Step 2–4 (calls) — nullable parameters without C# defaults must still be supplied, and list/search calls with many parameters can silently bind the wrong argument when called positionally. **MUST load `dotnet-calling-endpoints`** before writing calls.
- ⚠ Step 2–4 (models) — generated records use wire names distinct from C# names, required members are initializer obligations, and enum/union values need generated access patterns. **MUST load `dotnet-models`** before constructing or mapping models.
- ⚠ Step 5 (error boundary) — typed errors and `RawError` reach the boundary through different accessors, and a no-throw `…Result` path is unavailable here. **MUST load `dotnet-error-handling`** before writing catches or translation middleware.
- ⚠ Step 1 and Step 5 (resilience) — status-triggered retries and transport-triggered retries have different write-duplication consequences, while per-attempt timeout and whole-call cancellation are separate concerns. **MUST load `dotnet-configuration-resilience`** before configuring retry, timeout, base URL, or diagnostics.
- ⚠ Step 6 (tests) — mocking an SDK wrapper can miss serialization, envelope, route, and retry behavior; the supported seam is the `HttpClient` handler. **MUST load `dotnet-testing`** before writing integration tests.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary. These rows belong in the FIRST sheet, not a later revision: the boundary is written early, and a caveat that arrives afterwards arrives too late to shape it.

## 5. Assumptions & Blockers

- Assumption — the existing JWT principal exposes a stable user identifier plus the first name, last name, and email needed by the SDK's required `CreateCustomer` fields; if any are absent, the API must reject the enrollment with an application validation error rather than inventing identity data.
- Assumption — one deterministic subscription reference is intended per authenticated eShop user and plan handle, so a user may hold separate Maxio subscriptions for separate plan handles; changing that policy is an application decision.
- Blocker — the bundled SDK exposes only `ServerEnvironment.Us` and `ServerEnvironment.Eu`; it documents the default US production URL and does not document a sandbox environment or sandbox hostname. To guarantee the requested sandbox target, deployment must supply `Maxio:BaseUrl` with the approved sandbox URL, or the owner must authorize the documented SDK default/another server mapping. The plan does not invent that URL.
- Blocker — the `CreateSubscription` Notes state that payment information may be required depending on the selected product. This request supplies no payment-profile/token contract or public payment endpoint. The owner must confirm that the configured sandbox products accept the chosen no-payment request, or define the approved token/payment-profile input before enrollment can be accepted reliably.
