## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency and concurrency contract

| Capability | Grounded conclusion / directive | Source |
|---|---|---|
| Customer identity | `CreateCustomer` documents that only one customer may use a given `reference`; `ReadCustomerByReference` returns the single match. Use the eShop user reference as the provider uniqueness boundary and re-read after a create race. | `operations/Customers.md` |
| Subscription write | `CreateSubscription` accepts `CreateSubscriptionRequest? body, ct` only; there is no SDK idempotency header/argument. The request model has `Reference`, and `FindSubscription` can search it, but neither operation/model row states that reference is unique. Use a durable application uniqueness gate for double-click/concurrent execution; use deterministic `Reference` + `FindSubscription` only for recovery/reconciliation, not as the concurrency primitive. | `operations/Subscriptions.md`; `records-2-Cr-Ne.md` |
| Provider retry ambiguity | A transport-level ambiguous outcome can leave a subscription created even though the caller did not receive it. Persist an in-progress idempotency row before the call; on retry, perform reference lookup before any new create, and only the durable lease owner may create. Provider truth wins during recovery. | `operations/Subscriptions.md` (create/find surface); resilience semantics intentionally delegated below. |
| Components | The requested three API endpoints do not require an SDK component operation or a `CreateSubscription.Components` payload. The seeded `api-call` component is therefore verified as catalog setup only and is not attached or allocated. Adding metered usage is outside this scope and needs a separate contract sheet. | `records-2-Cr-Ne.md` |

## Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership and DI lifetime can create socket churn or dispose a shared pipeline if wired incorrectly. **MUST load `dotnet-client-initialization`** before registering the client.

⚠ Step 1 (credentials) — credential placement, rotation, and configuration timing can silently yield 401/403 or leak a secret. **MUST load `dotnet-authentication`** before wiring Basic auth.

⚠ Steps 2–5 (calls) — generated list methods have nullable parameters with no C# defaults, and cancellation uses the literal named argument `ct`; positional or guessed named calls can mis-bind or fail compilation. **MUST load `dotnet-calling-endpoints`** before the first operation call.

⚠ Steps 2–5 (models) — required init-only members, response envelopes, wire names, and `StringEnum` handling can cause malformed requests or null dereferences when treated like ordinary mutable DTOs/C# enums. **MUST load `dotnet-models`** before constructing or projecting SDK models.

⚠ Step 4 (create/retry) — whether and when an ambiguous failed write may be sent again determines whether a double-click or transport failure can create duplicate subscriptions. **MUST load `dotnet-configuration-resilience`** before setting retry/timeout options or finalizing the durable idempotency flow.

⚠ Step 3 (pagination) — an apparently successful first page can silently omit catalog products if termination and cancellation are not implemented against the generated manual pagination surface. **MUST load `dotnet-configuration-resilience`** before implementing the product loop.

⚠ Step 6 (typed/raw exceptions) — operations in this sheet mix typed Case A errors with raw Case B errors; assuming one catch shape drops status/detail or misses failures. **MUST load `dotnet-error-handling`** before writing the boundary.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 (tests) — faking generated controllers couples tests to SDK internals and misses real serialization, error, and cancellation behavior. **MUST load `dotnet-testing`** before choosing the test seam.

## Assumptions & Blockers

- Assumption: `Maxio:Subdomain` identifies a US-hosted Maxio site; the requested configuration has no region selector. An EU-hosted site would require an explicit configuration decision and `ServerEnvironment.Eu` wiring.
- Assumption: the authenticated eShop identity/profile can supply a stable user key plus non-empty first name, last name, and email. `CreateCustomer` requires all three text fields; if the existing identity store cannot supply them, customer creation is blocked until an authoritative profile source or onboarding requirement is chosen.
- Assumption: one POST request carries a caller-generated idempotency key, and the application has durable transactional storage capable of a unique `(user-key, idempotency-key)` constraint/lease. An in-memory lock is not sufficient for multi-instance or restart-safe production behavior.
- Assumption: `Maxio:ProductFamilyHandle` matches exactly one active family and products `eshop-pro` and `basic-plan` are in that family, unarchived, and configured by Maxio to require no card. The live verification step must prove this external catalog state.
- Blocker: the SDK exposes no provider idempotency-key parameter for `CreateSubscription`, and the map does not establish subscription-reference uniqueness. Production-safe double-click prevention therefore requires the durable application idempotency record described above; if schema/persistent storage changes are forbidden, that requirement cannot be met across processes/restarts.
- Assumption: the seeded `api-call` component is contextual catalog data. None of the three requested routes accepts component quantity or records usage, so this plan does not attach, allocate, or report it. If that behavior is intended, it requires a follow-up requirement and expanded component-operation contract sheet.
- **UNVERIFIED assumption requiring live confirmation:** the target sandbox uses legacy Statements Architecture, for which the generated `CollectionMethod` documentation permits `Invoice` (`"invoice"`). The SDK source cannot reveal the live site's billing architecture; if Maxio rejects `invoice` as invalid, the site is likely on Relationship Invoicing and the owner must confirm whether cardless `Remittance` (`"remittance"`) is the intended business behavior before changing the request.
- Capability gap with a safe workaround: although the `ReadProductFamily` operation note says the provider path accepts `handle:{handle}`, the generated SDK method is `ReadProductFamily(int id, CancellationToken ct = default)` and cannot express that string value. The plan therefore resolves the family through `ListProductFamilies` and an exact handle match, then uses the returned runtime ID; no seeded numeric ID is used. (`operations/ProductFamilies.md`)
- Blocker: live verification requires a real sandbox subdomain and API key supplied through user-secrets/environment; neither may be written to the repository.
