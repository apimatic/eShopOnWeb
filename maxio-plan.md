# Maxio recurring subscriptions plan for eShopOnWeb

## 1. Scope & sequence

1. Add the `AsadAli.AdvancedBilling.Sdk` package through NuGet and register one long-lived `MaxioAdvancedBilling.MaxioAdvancedBillingClient` in the existing `src/PublicApi` composition root. Bind the four requested configuration keys, select the US Production server, set `Production.Us.Site` from `Maxio:Subdomain`, and apply `Maxio:BaseUrl` only as the Production/US base-URL override.
2. Preserve the existing PublicApi JWT boundary and add the three additive routes from the brief. The route/auth policy and PublicApi DTO names are application decisions; they are not Maxio SDK contracts.
3. Implement plan discovery for `GET /api/subscription-plans`: call `client.ProductFamilies.ListProductFamilies(...)`, exact-match the configured `Maxio:ProductFamilyHandle` against `ProductFamily.Handle`, require a usable `ProductFamily.Id`, then manually page through `client.ProductFamilies.ListProductsForProductFamily(...)`. Project each product into the PublicApi plan DTO using the product handle/name, price, interval, interval unit, and available product-price-point identity.
4. Implement durable customer resolution before enrollment. Read the existing user-to-Maxio mapping from the app’s existing data layer; when absent, call `client.Customers.ReadCustomerByReference(...)` using a deterministic application-user reference. Only a genuine 404 is an absence. If absent, call `client.Customers.CreateCustomer(...)` with the required customer fields and the same unique reference, then persist the returned Maxio customer ID. Handle the provider’s documented unique-reference race by re-reading the reference after a duplicate/validation outcome before deciding that creation failed.
5. Implement idempotent subscription enrollment for `POST /api/subscriptions`: use an atomic application mapping/claim for the authenticated user and selected plan, look up an existing Maxio subscription by deterministic `Reference` with `client.Subscriptions.FindSubscription(...)`, and return the existing mapping/subscription when found. Otherwise call `client.Subscriptions.CreateSubscription(...)` with `CustomerId`, `ProductHandle`, optional selected `ProductPricePointHandle`, and the deterministic `Reference`; persist the Maxio subscription ID only after the response is usable. On an ambiguous transport or body-processing failure, reconcile with `FindSubscription` before allowing another create. The SDK has no idempotency-key parameter on this operation; the local uniqueness/claim and reconciliation strategy is therefore required for the requested behavior.
6. Implement `GET /api/my-subscriptions` by resolving the authenticated user’s persisted Maxio customer mapping and calling `client.Customers.ListCustomerSubscriptions(customerId, ct: ...)`. Project each non-null `SubscriptionResponse.Subscription` into the PublicApi subscription DTO with plan, price, state, and the best-effort billing-date rule in the contract sheet.
7. Put all Maxio calls behind one integration boundary. Translate typed and raw SDK failures, transport/cancellation failures, and deserialization failures into caller-safe PublicApi errors; preserve provider 4xx meaning where available, do not expose SDK/framework exception text, and never treat an unreadable response as “not found.”
8. Add unit/integration-layer tests using the SDK’s `HttpClient`/fake-handler seam: plan-family matching and pagination, customer lookup/create races, subscription lookup/create idempotency, reconciliation after ambiguous writes, exact outgoing routes/body wire names, response projection, JWT route authorization, configuration/base-URL behavior, and every provider/transport/JSON error branch. Match the repository’s existing test framework and assertion style.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

**Billing-date contract boundary — `UNVERIFIED`:** the map exposes `Subscription.CurrentPeriodEndsAt (current_period_ends_at): System.DateTimeOffset?` and `Subscription.NextAssessmentAt (next_assessment_at): System.DateTimeOffset?`, but no `NextBillingAt` response member. ## 3. Trap notes

- ⚠ Step 1 (client and DI registration) — the SDK client and the `HttpClient`/handler pipeline have different lifetime implications, and generated DI registration may capture options at registration. **MUST load `dotnet-client-initialization`** before wiring `MaxioAdvancedBillingClient`.
- ⚠ Step 1 (configuration/resilience) — retry and timeout settings do not describe a whole-call budget, and a handler/logging choice can affect the wrong `HttpClient` scope. **MUST load `dotnet-configuration-resilience`** before tuning retries, timeouts, base URL, or logging.
- ⚠ Step 1 (Maxio credentials) — the SDK’s Basic credential property and secret-loading order are easy to confuse with the PublicApi JWT boundary. **MUST load `dotnet-authentication`** before wiring Maxio credentials.
- ⚠ Step 2 (PublicApi JWT) — the application’s JWT policy, identity claims, and route conventions are not in the SDK map; choosing claim names or policy names without inspecting the repository would create an application contract. **MUST load `dotnet-authentication`** for the Maxio side and resolve the app-side JWT convention from the repository.
- ⚠ Step 3 (plan discovery) — list methods have leading nullable parameters with no C# defaults and manual page/per-page pagination; positional calls can bind or page incorrectly. **MUST load `dotnet-calling-endpoints`** and **MUST load `dotnet-configuration-resilience`** before implementing discovery.
- ⚠ Step 3 (model projection) — SDK C# property names differ from snake_case wire names, enums are generated string-enum records, and nullable response envelopes must be unwrapped explicitly. **MUST load `dotnet-models`** before constructing or projecting models.
- ⚠ Step 4 (customer create) — provider uniqueness is tied to the documented `reference` behavior, while a concurrent lookup/create race still needs an application-side recovery path. **MUST load `dotnet-error-handling`** before translating the typed 422 error.
- ⚠ Step 5 (subscription enrollment) — a POST may have an ambiguous provider outcome after transport failure, and the SDK operation has no generated idempotency-key parameter. **MUST load `dotnet-configuration-resilience`** and **MUST load `dotnet-error-handling`** before selecting the write/reconciliation boundary.
- ⚠ Step 5 (request body) — `CreateSubscriptionRequest` is a required outer wrapper around a model whose fields are mostly nullable; C# `required` alone does not select the provider fields that make a call acceptable. **MUST load `dotnet-models`** before constructing the request.
- ⚠ Step 6 (error boundary) — Case A typed errors and Case B raw errors have different accessors and namespaces; a shared `ApiError` helper cannot read operation-specific typed payloads. **MUST load `dotnet-error-handling`** before writing catches or middleware.
- ⚠ Step 6 (error boundary) — a connection failure or cancellation is outside `SdkException<TError>` and can escape an SDK-exception-only ladder. **MUST load `dotnet-error-handling`** before translating provider failures.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary. These rows belong in the FIRST sheet, not a later revision: the boundary is written early, and a caveat that arrives afterwards arrives too late to shape it.
- ⚠ Step 7 (tests) — the correct SDK seam is the supplied `HttpClient` backed by a fake `HttpMessageHandler`; retry-trigger tests must distinguish status faults from transport faults. **MUST load `dotnet-testing`** before writing tests.

## 5. Assumptions & Blockers

- Assumption: the Maxio account is US-hosted, because the requested bindings contain no environment selector; use `ServerEnvironment.Us`. If the sandbox account is EU-hosted, the application must supply a separately approved environment-selection decision before implementation.
- Assumption: the authenticated application identity has a stable user identifier plus the name/email values needed for `CreateCustomer`; the exact claim names and existing data-layer APIs are repository decisions not inspected in this plan.
- Blocker: the brief does not specify the approved payment path for products that require payment information. The map’s `CreateSubscription` Notes say payment information may be required; implementation needs a decision between an existing Maxio payment-profile ID, an approved tokenized profile model, or a product configuration that requires no payment input. Raw card collection must not be introduced by assumption.
- Blocker: the existing data layer must support a durable user-to-Maxio mapping and an atomic uniqueness/claim mechanism for customer and subscription enrollment. If it cannot provide that boundary, the requested idempotency guarantee cannot be made solely by the generated SDK.
- `UNVERIFIED` (not a map-resolvable fact): the SDK response has no `NextBillingAt`; the plan uses `CurrentPeriodEndsAt` best-effort and requires the caller-safe unavailable representation when absent. Do not substitute `NextAssessmentAt` without a separate product decision/verification.
