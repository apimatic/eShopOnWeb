## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership, the generated DI registration lifetime, handler rotation, and named-vs-default client blast radius affect connection reuse and DNS freshness. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credentials must be populated at the correct options property and time, or every endpoint fails at the auth boundary. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 2–7 (operation calls) — leading nullable parameters without C# defaults, literal named argument `ct:`, controller ownership, and response envelopes can silently mis-bind or be unwrapped at the wrong level. **MUST load `dotnet-calling-endpoints`** before the first call.

⚠ Steps 2–7 (model mapping) — immutable required members, nullable success envelopes, string-enum readback, unknown enum values, and dropped unknown JSON fields affect request construction and response projection. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Step 5 (idempotent write) — the SDK's retry pipeline can re-send a POST after a transport failure, and the map does not establish subscription-reference uniqueness; this can duplicate an enrollment unless send guarding and reconciliation are designed together. **MUST load `dotnet-configuration-resilience`** before registering the write path.

⚠ Steps 1–7 (server, timeout, cancellation, pagination, logging) — selecting the wrong nested server node ignores the base override; retry/timeout options do not by themselves bound the whole request, manual pagination can truncate plans, and first-run wire verification needs an HTTP handler. **MUST load `dotnet-configuration-resilience`** before tuning or live verification.

⚠ Steps 4–7 (error translation) — Case A and Case B exceptions have different namespaces and access paths; omitting a typed accessor loses the provider rejection, while parsing raw bodies speculatively can throw again. **MUST load `dotnet-error-handling`** before writing the boundary.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (tests) — the SDK client is concrete and its supported test seam is the injected `HttpClient`; success, each exact error case, JSON drift, cancellation, pagination, double-click concurrency, status failure, and transport retry need behavior-level assertions. **MUST load `dotnet-testing`** before writing integration tests.

## 5. Assumptions & Blockers

### Assumptions

- The application can load non-secret account profile values for the authenticated user: first name, last name, and email are required by `CreateCustomer`.
- `Maxio:Subdomain` addresses a US-hosted site when `Maxio:BaseUrl` is absent, because the SDK's default is `ServerEnvironment.Us` and the requested configuration keys contain no geography selector.
- The public `nextBillingDate` will be projected from Maxio's `Subscription.NextAssessmentAt`; `CurrentPeriodEndsAt` may also be returned to preserve the distinction visible in the SDK model.
- Application persistence/concurrency owns the single-writer claim for a deterministic user + plan subscription reference. The SDK provides lookup and create operations, but no documented idempotency-key input.

### Blockers

- None. The bundled SDK map exposes product-family/product discovery, exact customer lookup/create, subscription lookup/create, and customer-subscription listing. Direct `ReadProductFamily` is generated with `int id` even though its Notes mention `handle:...`; the plan avoids that mismatch by resolving the configured handle through `ListProductFamilies`, so it is not a blocker.
