## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — client/`HttpClient` lifetime and dependency-injection construction can create socket churn or stale handlers if wired at the wrong seam. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — credential timing/rotation and the generated Basic-auth manager shape can silently produce unauthenticated calls. **MUST load `dotnet-authentication`** before setting credentials.
- ⚠ Steps 2–5 (calls) — optional generated parameters without C# defaults and response-envelope nesting make positional calls and direct payload reads compile incorrectly or mis-bind. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 2–5 (models) — required initializers, nullable provider fields, `StringEnum<T>`, and exact JSON wire names can break request construction and projection. **MUST load `dotnet-models`** before constructing or mapping models.
- ⚠ Steps 2 and 7 (pagination) — list completeness, cancellation, and page termination are application responsibilities around the generated page/per-page surface. **MUST load `dotnet-configuration-resilience`** before implementing pagination.
- ⚠ Steps 1 and 4 (resilience) — whether a failed write can be re-sent, what timeout bounds, and which retry knobs apply determine duplicate-subscription risk after an ambiguous transport outcome. **MUST load `dotnet-configuration-resilience`** before configuring retries/timeouts.
- ⚠ Step 6 (error boundary) — Case A typed errors and Case B raw errors expose different access paths, so a shared catch ladder can lose status/body details. **MUST load `dotnet-error-handling`** before writing that boundary.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

- ⚠ Step 7 (tests) — mocking generated controller internals couples tests to implementation and misses real serialization/error behavior. **MUST load `dotnet-testing`** before writing tests.

## 5. Assumptions & Blockers

### Assumptions

- A repeat enrollment for the same authenticated user and product handle is a replay of the original enrollment, not a request for a second parallel subscription.
- `Maxio:ProductFamilyHandle` is matched exactly to `ProductFamily.Handle`; all numeric family/product IDs are discovered at runtime and are never API inputs or configuration.
- The configured catalog's subscribe targets do not require payment information, as stated in the brief. The request intentionally omits all payment-profile/card/bank fields; Maxio's operation Notes say product configuration decides whether payment is required.
- The application's trusted identity data can supply the required Maxio customer `FirstName`, `LastName`, and `Email`. The stable authenticated user ID becomes the customer reference; exact normalization/reference formatting is an application decision.
- The US Production server group is correct for the named sandbox because the allowed configuration contract has no hosting-region key. A nonstandard/EU/mock target must supply `Maxio:BaseUrl` under this brief's exact-key constraint.
- `Subscription.NextAssessmentAt` is exposed as next billing date because it is the SDK field that directly names the next assessment; `CurrentPeriodEndsAt` remains available separately.

### Blockers

- None for implementation planning. The SDK map does not document uniqueness of `CreateSubscription.Reference`; therefore the application must not claim provider-enforced subscription idempotency and must retain its atomic single-writer/reconciliation record. Whether live Maxio rejects duplicate subscription references is **UNVERIFIED** and is not required for the double-click guard described here.
