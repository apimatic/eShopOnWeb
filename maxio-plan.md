# Maxio Advanced Billing recurring-subscription integration plan

## Scope & sequence

| Step | Additive implementation | SDK operations |
|---|---|---|
| 1 | Add the published package to the project that owns the Maxio adapter: `<PackageReference Include="AsadAli.AdvancedBilling.Sdk" Version="1.0.2" />`. | 2 | Register a reusable `HttpClient` pipeline and construct the SDK client from validated options. Use Basic auth, US/sandbox Production server selection, and the BaseUrl/Subdomain precedence in the client-facts table below. Keep the SDK behind an application-owned `IMaxioBillingGateway` so PublicApi handlers and tests do not depend on generated controllers. | Client construction only. (`sdk-map.md`) |
| 3 | Add JWT-authorized `GET /api/subscription-plans`. Read all product-family envelopes, select the one whose `ProductFamily.Handle` exactly equals configured `ProductFamilyHandle`, then page through all non-archived products for that family. Map each product to an application DTO containing product id/handle/name/description, default price in cents, interval/unit, and default price-point id/handle/name. Return a configuration/not-found failure if the family is absent or an expected required identifier is null; never substitute a hard-coded family/product/price-point id. | `ProductFamilies.ListProductFamilies`; `ProductFamilies.ListProductsForProductFamily`. |
| 4 | Derive billing identity exclusively from the authenticated principal. Use an immutable JWT subject/NameIdentifier as the application identity and as the basis of the stable Maxio customer reference; never accept a customer id/reference/email from the POST body. Require the claims needed for Maxio's required customer fields (`FirstName`, `LastName`, `Email`) or reject before calling Maxio. | None. |
| 5 | Implement `EnsureCustomer`: lookup by stable customer reference; on 404 create with that same unique reference; if create returns 422, re-read by reference to resolve a concurrent creator, and only treat it as success when the lookup now succeeds. The Maxio customer contract explicitly makes `reference` unique, so this closes the normal double-click race for customer creation. | `Customers.ReadCustomerByReference`; `Customers.CreateCustomer`. |
| 6 | Add an application-owned subscription-intent/idempotency record with a database unique constraint on the chosen business key (authenticated subject + selected product id for one-subscription-per-plan semantics), and explicit `Pending`, `Succeeded`, `Unknown`, and `Failed` outcomes. Only the transaction winner may call Maxio; concurrent POSTs read/replay the recorded result. Validate the requested product id by enumerating the configured family before creating. Use a deterministic subscription reference for later lookup/reconciliation, but do not claim that reference is provider-enforced unique. | Product-family operations; `Subscriptions.FindSubscription`; `Subscriptions.CreateSubscription`. |
| 7 | Add JWT-authorized `POST /api/subscriptions` with body `{ "productId": <int> }`. Reconcile by deterministic subscription reference first; ensure the customer; then create using `ProductId`, `CustomerReference`, and `Reference`. Deliberately omit all payment-profile/card/bank fields and do not hard-code a collection method. Persist the resulting provider subscription id/reference/state. A product/site that requires a payment profile will reject this with the documented 422 path and is an environment/seed-data concern. | `Subscriptions.FindSubscription`; `Customers.ReadCustomerByReference`; `Customers.CreateCustomer`; `Subscriptions.CreateSubscription`. |
| 8 | Add JWT-authorized `GET /api/my-subscriptions`. Resolve the current user's customer by reference; treat customer 404 as an empty list; then list that customer's subscriptions. Map each envelope to id/reference, plan name/handle, `ProductPriceInCents`, state, and `NextAssessmentAt` as `nextBillingAt`. Preserve nulls; do not relabel `CurrentPeriodEndsAt` as a billing date. | `Customers.ReadCustomerByReference`; `Customers.ListCustomerSubscriptions`. |
| 9 | Put one application error boundary around the gateway. Distinguish auth/config errors, 404 lookup absence, 422 validation/rejection, other provider HTTP responses, cancellation, transport failures, and malformed success/error JSON. Do not expose API keys or raw provider bodies to clients; log a sanitized provider status/correlation context. | All operations below. |
| 10 | Add tests at the application seam: JWT required on all three endpoints; identity cannot be spoofed; family pagination; no hard-coded ids; missing family; null/malformed envelopes; customer lookup/create/race; same-product double click admits one winner; replay returns the stored result; create body omits payment fields; 422 mapping; 404 empty list; subscription DTO mapping; cancellation; malformed 2xx and non-2xx JSON; and the unresolved ambiguous-write case is surfaced as `Unknown`, never silently retried by application code. | All operations below. |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 1–2 (package/client registration) — generated client construction does not reveal the correct `HttpClient` ownership, factory, or DI lifetime; choosing the wrong lifetime can exhaust sockets or discard the configured handler pipeline. **MUST load `dotnet-client-initialization`** before registering it.

⚠ Step 2 (authentication) — credentials must be populated at the correct construction/DI point and protected during rotation; a misplaced or stale credential becomes a 401/403. **MUST load `dotnet-authentication`** before wiring auth.

⚠ Steps 3, 5–8 (endpoint calls) — nullable parameters without C# defaults still must be passed, and positional list calls can silently bind the wrong filters; response envelopes add a payload level. **MUST load `dotnet-calling-endpoints`** before the first call.

⚠ Steps 3, 5–8 (model mapping) — required/init-only records, nullable envelopes, and `StringEnum<T>` value extraction can otherwise produce compile failures or malformed DTOs. **MUST load `dotnet-models`** before constructing or mapping models.

⚠ Steps 2, 6, 9 (resilience/idempotency) — determine whether and when a failed `POST` can be re-sent, what timeout/cancellation bounds, and how manual pagination terminates; the consequence is an ambiguous or duplicated non-idempotent write. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing the subscription-intent state machine.

⚠ Step 9 (error boundary) — Case A typed accessors and Case B raw bodies require different catch/read mechanics, and the customer 422 payload is structurally suspicious; mishandling loses status or leaks provider data. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 9 (2xx JSON drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 9 (non-2xx JSON drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 10 (tests) — faking generated controllers couples tests to SDK internals and misses serialization/error behavior; the wrong seam makes double-click and malformed-payload tests give false confidence. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- **Assumption:** The JWT issuer supplies an immutable subject/NameIdentifier plus trustworthy first name, last name, and email claims. If it does not, the product owner must define a non-spoofable profile source before customer creation can be implemented.
- **Assumption:** Seeded products in the configured family are sandbox products configured by Maxio to permit subscription creation without a payment profile. The SDK permits omission of every payment field, but the operation contract warns that product options may still require payment and return 422.
- **Assumption:** One recurring subscription per authenticated user per selected product is the intended double-click business key. If multiple legitimate subscriptions to the same product are allowed, the POST contract needs a caller-generated application idempotency key and a corresponding unique constraint instead.
- **Blocker — strict provider-side subscription exactly-once:** The mapped SDK surface has no idempotency-key parameter on `CreateSubscription`, and the map does not state that subscription `Reference` is unique. `FindSubscription(reference)` supports lookup/reconciliation but is not a uniqueness guarantee. An application unique intent prevents two ordinary double-click requests from concurrently issuing two calls, but the integration cannot truthfully guarantee that Maxio will not create a duplicate after an ambiguous transport outcome. This must be accepted as a known limitation or resolved with a provider-supported capability outside the mapped SDK before claiming end-to-end exactly-once behavior.
