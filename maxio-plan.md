| 8. PublicApi surface and UI | Add JWT-protected endpoints exactly `GET /api/subscription-plans`, `POST /api/subscriptions`, and `GET /api/my-subscriptions`, following the repository's endpoint/result/validation conventions. Add the authenticated browse/subscribe/account UI without changing cart/order checkout. Disable repeat submission while pending, but treat server idempotency as authoritative. | 9. Error boundary and observability | Translate validation/not-found/auth/config/provider/transient/cancellation failures into the repository's stable problem-details contract. Log correlation ID, operation name, safe Maxio status, local idempotency key, and remote IDs; never log API keys or raw personal/error payloads. Preserve cancellation. Treat malformed success/error JSON separately as required below. | All operations |
| 10. Tests and sandbox verification | Add adapter tests at the `HttpClient` seam, service concurrency tests against the real database uniqueness constraint, endpoint auth/contract tests, and opt-in sandbox tests. Sandbox verification must discover the configured family and assert the returned `eshop-pro` `$299/month` and `basic-plan` `$29/month` values only from live responses, then issue concurrent/repeated creates and a lost-response simulation. ## API contracts and application behavior

| Endpoint | Request | Success response | Important failures |
|---|---|---|---|
| `GET /api/subscription-plans` | JWT only | `200` list of `{ handle, name, description, priceInCents, interval, intervalUnit, requestCreditCard, requireCreditCard }` | `401`; `503` for invalid Maxio configuration/family resolution; translated provider failure |
| `POST /api/subscriptions` | JWT; `{ productHandle, firstName?, lastName? }` (`firstName`/`lastName` only needed when the identity profile lacks them) | `201` newly created or `200` replay: `{ id, reference, productHandle, productName, priceInCents, state, nextBillingAt }` | `400/422` local/provider validation; `404` product not offered; `409` recovered reference points at a different user/product; `401`; translated provider failure |
| `GET /api/my-subscriptions` | JWT only | `200` list of the subscription DTO above; empty when no Maxio customer exists | `401`; translated provider failure |

`nextBillingAt` maps to Maxio `Subscription.NextAssessmentAt`. Do not relabel `CurrentPeriodEndsAt` as the next billing date. All amount values remain integer cents through the backend.

## Idempotency state machine

1. Compute a stable customer reference from the authenticated issuer+subject and a stable subscription reference from that customer reference+validated product handle. The format is application-owned, versioned, non-PII, and deterministic.
2. Acquire the unique local `(subject, productHandle)` provisioning row. A completed row returns its saved remote identity; an in-flight row does not issue another write.
3. Before a write, call `FindSubscription(reference: ..., ct: ...)`. A found record is accepted only when nested customer reference and product handle match the expected values.
4. Ensure the customer with `ReadCustomerByReference`; customer creation is race-safe because the Maxio map explicitly documents customer `reference` as unique. Recover a concurrent 422 by reading that reference again.
5. Call `CreateSubscription` once from the provisioning owner. Save its remote ID/reference and response atomically with `Succeeded`.
6. If the outcome is ambiguous, set `Unknown`; reconcile with `FindSubscription` before any later create. On create 422, perform the same lookup and accept only an exact match.
7. Do not claim an absolute provider-side no-duplicate guarantee until the blocker below is resolved: the SDK surface has reference lookup but no idempotency-key/header argument, and the map does not document subscription-reference uniqueness.

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

- ⚠ Step 1–2 (client registration) — `HttpClient` ownership/lifetime and the options-construction seam affect connection reuse and testability. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 2 (authentication) — credential placement/rotation and 401/403 diagnosis affect whether secrets are applied safely. **MUST load `dotnet-authentication`** before wiring credentials.
- ⚠ Step 3–7 (endpoint calls) — generated nullable parameters without defaults and envelope unwrapping can silently mis-bind or map the wrapper instead of its payload. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Step 3–7 (models) — required init-only members, wire names, and `StringEnum<T>` handling affect request validity and DTO mapping. **MUST load `dotnet-models`** before constructing payloads.
- ⚠ Step 2, 5, 9 (configuration/resilience) — retry/timeout/base-URL behavior determines whether a failed write can be re-sent and how ambiguous outcomes must be reconciled. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing idempotency.
- ⚠ Step 9 (error boundary) — typed and raw operation errors require different status/body access paths, and unsafe parsing can discard usable provider context. **MUST load `dotnet-error-handling`** before writing catches.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 10 (tests) — the correct fake seam and behavior-oriented assertions determine whether tests cover serialization, errors, cancellation, and races rather than SDK internals. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- Assumption: The requested `api-call` component is seeded context for later usage billing, not part of the current recurring-plan browse/subscribe/account hero flow; no component operation is called and no component ID/handle is hard-coded.
- Assumption: The two products require no payment method as stated; the create payload intentionally omits all payment/profile fields and relies on provider product configuration.
- Assumption: The authenticated identity supplies a stable subject and authoritative email. Maxio's `CreateCustomer` model requires first name, last name, and email; if the eShop profile lacks names, the subscribe request/UI must collect them before provisioning.
- Assumption: `MAXIO_ENVIRONMENT` is a sandbox/deployment safety marker. It is not mapped to `ServerEnvironment`, because the map defines that SDK enum as hosting region (`Us`/`Eu`), not sandbox versus production.
- **BLOCKER / UNVERIFIED:** The map exposes subscription-reference lookup but no SDK idempotency-key capability and no documented uniqueness constraint for `CreateSubscription.Reference`. Therefore the absolute requirement that a lost response/retry can never create duplicate Maxio subscriptions cannot be certified from this SDK. Production enablement requires either an authoritative Maxio guarantee of unique subscription references/idempotent creation or successful sandbox proof covering simultaneous requests and a response-loss retry; otherwise the required capability is unsupported.
