# Maxio Advanced Billing subscription integration plan

## 1. Scope & sequence

Implement the application-facing integration in this order:

1. Register one long-lived Maxio client and configure the production server/authentication.
2. Resolve the authenticated eShopOnWeb principal to one stable, application-owned customer reference and validate the configured product-family handle.
3. List the configured family, select the exact stable ProductFamily.Handle, then list that family’s products page by page and expose plan/catalog metadata.
4. Ensure the Maxio customer with ReadCustomerByReference; create it with CreateCustomer only when absent; reconcile a concurrent create by looking up the same reference again.
5. Enroll the requested plan idempotently: derive one stable subscription reference for the application’s enrollment intent, find it with FindSubscription, and create it with CreateSubscription only when absent. Use a durable application idempotency record/unique constraint and an application-level per-key serialization boundary around the read/create/reconcile sequence.
6. Map the subscription response to the application’s plan, price, state, and next-billing-date result, then list the current user’s subscriptions through the ensured customer with ListCustomerSubscriptions.
7. Add handler-seam tests for request construction, envelopes, paging, success mapping, 404 absence, typed 422 errors, concurrent-create reconciliation, transport-failure behavior, and malformed JSON.

The SDK exposes no idempotency-key parameter in these generated method signatures. The durable idempotency key, persistence, lock/lease, crash recovery, and whether multiple subscriptions per user/plan are allowed are application decisions; use the same deterministic reference to reconcile an uncertain POST before retrying it.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named ct: in named
arguments write ct:, never cancellationToken:.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (Core/Configuration/… ⇒ …Core.Configuration; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to .Models makes the implementer guess the wrong using, and the build breaks.

### Client construction, authentication, and server-node facts

- Install package AsadAli.AdvancedBilling.Sdk; import root namespace MaxioAdvancedBilling. The client is MaxioAdvancedBilling.MaxioAdvancedBillingClient; options are MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions.
- Construct with exactly MaxioAdvancedBilling.MaxioAdvancedBillingClient(System.Net.Http.HttpClient httpClient, MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions options), or use the generated AddMaxioAdvancedBillingClient registration.
- Set options.BasicAuth to MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials: Username is the Maxio API key and Password is literal "x". Load the API key from the application configuration binding key chosen by the repository; no raw environment-variable name is prescribed here.
- options.Environment is MaxioAdvancedBilling.Servers.ServerEnvironment: Us (US, default) uses https://{site}.chargify.com; Eu (EU) uses https://{site}.ebilling.maxio.com.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the HttpClient/handler lifetime and generated client lifetime affect connection reuse, handler rotation, DNS freshness, and the blast radius of default-factory configuration. **MUST load dotnet-client-initialization** before wiring the client.
- ⚠ Step 1 (authentication) — a missing/late credential assignment or the wrong options binding can turn every operation into an authentication failure, and the API key must not be embedded in source. **MUST load dotnet-authentication** before setting credentials.
- ⚠ Step 2 (JWT identity) — accepting a caller-supplied user id, mutable email, or an unvalidated claim can associate a Maxio customer/subscription with the wrong principal; the exact claim-to-reference normalization is an application decision. **MUST load dotnet-calling-endpoints** before writing the boundary that supplies SDK arguments.
- ⚠ Step 3 (catalog calls) — the list signatures contain leading nullable parameters with no C# defaults, and positional calls can silently mis-bind filters or paging. **MUST load dotnet-calling-endpoints** before the first list call.
- ⚠ Step 3 (catalog models) — C# property names differ from JSON wire names, nullable response envelopes require a deliberate missing-payload policy, and enum values are generated string-enum members. **MUST load dotnet-models** before mapping catalog models.
- ⚠ Step 4 (customer ensure) — a read-then-create sequence can race across requests/deployments; creating a duplicate or treating every 422 as success can bind the wrong customer. **MUST load dotnet-error-handling** before translating lookup/create failures.
- ⚠ Step 5 (subscription enrollment) — whether a failed non-idempotent write can be re-sent safely is a production decision; an uncertain POST can otherwise produce a duplicate enrollment or an unreconciled provider-side success. **MUST load dotnet-configuration-resilience** before tuning retries/timeouts or implementing the write boundary.
- ⚠ Step 5 (subscription request) — nullable generated request members do not prove that a product, price point, customer, reference, or payment prerequisite is acceptable to the provider. **MUST load dotnet-models** before constructing the nested request.
- ⚠ Step 6 (error boundary) — Case-A typed errors and Case-B raw errors have different access paths; a catch ladder that assumes TryGetRawError everywhere loses the documented payload. **MUST load dotnet-error-handling** before writing catches or translation middleware.
- ⚠ Step 6 (whole-call deadline) — per-attempt retry/timeout controls, request cancellation, and the application’s total call budget can bound different portions of the sequence. **MUST load dotnet-configuration-resilience** before setting them.
- ⚠ Step 7 (tests) — retry status faults and transport faults exercise different paths, and the SDK’s HttpClient is the test seam. **MUST load dotnet-testing** before stubbing the SDK.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- **Blocker:** the product’s payment configuration may require payment information for CreateSubscription; the supplied request does not specify an existing PaymentProfileId or an approved tokenized card/bank flow. Resolve by either supplying a valid Maxio payment profile/approved payment attributes through the application boundary or confirming that the configured products permit enrollment without payment information. Do not send raw card data unless the application’s PCI/compliant payment design explicitly authorizes it.
- **Blocker:** the repository’s configuration binding key for the Maxio API key, server environment/site/base URL, and configured product-family handle was not supplied in the task. The implementer must bind these using the repository’s existing configuration conventions; no new raw environment-variable name is assumed here.
- **Blocker:** the repository’s durable persistence/locking mechanism and policy for one versus multiple subscriptions per user are not supplied. Production idempotency requires the implementer to choose a durable unique key/lease and recovery path for the customer reference and enrollment reference before enabling writes.
- **Assumption:** the authenticated request supplies a validated, stable principal identity and Maxio customer Reference will be the application’s deterministic representation of that identity; the exact JWT claim name and normalization are YOUR CALL — not in the map.
- **Assumption:** catalog selection is exact-handle based: one configured product-family handle selects one family, and the caller selects a product Handle plus optional ProductPricePointHandle; display names are presentation only.
- **Assumption:** the integration will use CurrentPeriodEndsAt as its next-billing-date field and will preserve nullable SDK values or apply an application-owned missing-data policy rather than inventing dates.
