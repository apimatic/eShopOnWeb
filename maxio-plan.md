## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 2 (client registration) — SDK-client and `HttpClient` ownership/lifetimes can create socket exhaustion or bypass the intended handler pipeline. **MUST load `dotnet-client-initialization`** before wiring DI.

⚠ Step 2 (authentication) — credential placement/timing and secret rotation determine whether calls are authenticated without rebuilding unsafe client infrastructure. **MUST load `dotnet-authentication`** before setting credentials.

⚠ Steps 5–9 (calls) — optional parameters without C# defaults must still be passed explicitly, and positional calls can silently mis-bind adjacent nullable values. **MUST load `dotnet-calling-endpoints`** before writing the first call.

⚠ Steps 5–10 (models) — response envelopes add a wrapper level, nullable members require protocol validation, and `StringEnum<T>` mapping differs from C# enums. **MUST load `dotnet-models`** before building or projecting models.

⚠ Steps 3, 6–9, 11 (errors) — Case A and Case B exceptions have different access paths, and the generated customer 422 payload is suspiciously unrelated to customer uniqueness. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Steps 2, 7–8 (resilience/idempotency) — retry/timeout behavior determines whether a failed subscription write can be re-sent and therefore whether the durable claim alone proves provider-side exactly-once creation. **MUST load `dotnet-configuration-resilience`** before tuning the client or finalizing write recovery.

⚠ Steps 5 and 9 (pagination) — only the product-family product list here is manually paged; treating an operation with no pagination parameters as paged would invent a contract. **MUST load `dotnet-configuration-resilience`** before implementing list loops.

⚠ Step 12 (testing) — the supported fake seam is tied to the SDK's `HttpClient` construction, while tests that mock generated controller internals become brittle. **MUST load `dotnet-testing`** before writing adapter tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a
  `JsonException` from deserialization, **not** as an `SdkException` — so an
  SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape
  throws `JsonException` *while the error object is being constructed*, so the `JsonException`
  **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that
  maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage,
  and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- **Assumption — enrollment cardinality:** the hero flow permits at most one Maxio subscription per application user and product handle. A later re-subscribe-after-cancel workflow is outside this scope and would need an explicit enrollment-attempt/idempotency key rather than the unique `(UserId, ProductHandle)` claim.
- **Assumption — identity profile:** the application identity store can supply nonempty first name, last name, and email for the authenticated immutable user ID. Those three fields are required by `CreateCustomer`; the POST body is not allowed to override them.
- **Contract limitation — provider exactly-once:** the mapped `CreateSubscription` signature exposes no idempotency-key parameter, and its Notes do not state that `CreateSubscription.Reference` is unique. The application plan prevents two double-click requests from issuing two application-level creates and reconciles by `FindSubscription`, but provider-side exactly-once behavior under an SDK transport retry is not provable from the SDK contract. This is not resolved by assuming reference uniqueness.
- **No implementation blocker:** the requested catalog/customer/subscription operations, fields, envelopes, and lookup paths exist in the mapped SDK surface.
