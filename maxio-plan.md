# Maxio recurring-subscription integration plan

## Scope & sequence

| Step | Implementation sequence | Maxio operations | Grounding |
|---|---|---|---|
| 1 | Add the published `AsadAli.AdvancedBilling.Sdk` package and register one configured SDK client for the PublicApi integration. Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; fail startup validation for missing required values and never log the key. | Client construction only | `sdk-map.md` |
| 2 | Protect all three PublicApi routes with the app's JWT policy. Derive a stable, non-PII Maxio customer reference from immutable authenticated identity (issuer + subject/name-identifier), and obtain required email/name values from trusted claims/user data. | — | Application concern; SDK customer field contract below |
| 3 | Resolve the configured product family by enumerating families and matching `ProductFamily.Handle` exactly. Do not configure or persist numeric catalog IDs. For the plans endpoint, use the matched response's numeric `Id` only as an ephemeral address for the subsequent family-products call, page until exhaustion, and map product handle/name/description/price/interval/archive/card-requirement fields. | `ProductFamilies.ListProductFamilies`; `ProductFamilies.ListProductsForProductFamily`; optionally `Products.ReadProductByHandle` to revalidate POST input | `operations/ProductFamilies.md`; `operations/Products.md` |
| 4 | Ensure one Maxio customer per authenticated eShop user: lookup by the stable reference; on 404 create with required first name, last name, and email plus that reference; if concurrent creation loses with 422, lookup again by reference. Never use email as identity. | `Customers.ReadCustomerByReference`; `Customers.CreateCustomer` | `operations/Customers.md` |
| 5 | Before subscription creation, validate the requested product handle belongs to the configured family, is not archived, and does not require a card. Acquire a durable application-owned unique claim keyed by `(authenticated user id, normalized product handle)` before any Maxio write. Reconcile via stable subscription reference and the customer's subscription list; any same-handle subscription blocks creation under the default policy. | `Products.ReadProductByHandle`; `Subscriptions.FindSubscription`; `Customers.ListCustomerSubscriptions` | `operations/Products.md`; `operations/Subscriptions.md`; `operations/Customers.md` |
| 6 | Create with `ProductHandle`, `CustomerReference`, and the deterministic subscription `Reference`; omit all payment-profile/card/bank fields. Return the created subscription projection. Commit the durable claim only after success; on an ambiguous transport/provider failure, retain/reconcile the claim rather than issuing a blind second POST. | `Subscriptions.CreateSubscription` | `operations/Subscriptions.md` |
| 7 | Implement `GET /api/my-subscriptions` by resolving the customer reference, treating customer 404 as an empty list, and calling the customer-scoped subscription list. Map plan handle/name, snapshot price, state, interval, and next assessment date. Use `ReadSubscription` only when a known returned subscription needs refreshing; never accept an arbitrary cross-customer numeric ID from the route. | `Customers.ReadCustomerByReference`; `Customers.ListCustomerSubscriptions`; optionally `Subscriptions.ReadSubscription` | `operations/Customers.md`; `operations/Subscriptions.md` |
| 8 | Translate SDK/provider failures at the integration boundary, preserve cancellation, validate nullable envelopes, and test auth, mapping, pagination, customer races, durable same-plan exclusion, 404s, 422s, malformed 2xx/non-2xx JSON, and ambiguous POST outcomes. | All above | `sdk-map.md` and operation pages above |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Identity, duplicate prevention, and search limitations

| Fact / directive | Contract consequence | Grounding |
|---|---|---|
| Customer reference is unique. | `CreateCustomer` permits only one customer for a given `reference`; `ReadCustomerByReference` returns one customer. Lookup → create → 422/relookup safely converges a customer race, provided the same deterministic identity reference is always used. | `operations/Customers.md` |
| No stable-handle family read exists in this generated surface. | `ReadProductFamily` takes `int id` even though its prose mentions `handle:my-family`; do not guess a string into that signature. Enumerate families and match `ProductFamily.Handle`; use the returned numeric ID only for the immediately following list call. | `operations/ProductFamilies.md`; `records-3-Of-Su.md` |
| Product handle lookup is direct. | `ReadProductByHandle(string apiHandle, ...)` validates a requested stable product handle; still verify the returned nested family handle because the lookup is site-wide. | `operations/Products.md`; `records-3-Of-Su.md` |
| Subscription reference lookup exists, but uniqueness/idempotency is not documented. | `FindSubscription(reference)` is a reconciliation/preflight lookup only. The create signature has no idempotency-key parameter, and the map does not say `CreateSubscription.Reference` is unique. **UNVERIFIED:** live uniqueness cannot be assumed; use a durable application-side unique user+plan claim (or equivalently strong distributed serialization), then best-effort reconcile by reference/list after ambiguous outcomes. | `operations/Subscriptions.md`; `records-1-Ac-Cr.md` |
| Customer subscription list is unpaginated. | `ListCustomerSubscriptions(customerId)` returns the customer's whole list and has no state/product filter. Compare `Subscription.Product?.Handle` application-side. Under the default strict policy, any existing same-handle record—regardless of state—blocks another create. | `operations/Customers.md`; `records-3-Of-Su.md`; policy assumption below |
| Site subscription list cannot solve customer+handle identity. | `ListSubscriptions` filters product by numeric ID and exposes no customer-reference or product-handle filter; do not use it for hero-flow duplicate prevention. | `operations/Subscriptions.md` |
| POST outcome may be ambiguous. | A timeout/transport failure does not prove the subscription was not created. Hold the durable claim in a reconciling state, call `FindSubscription(stableReference)` and `ListCustomerSubscriptions`, and return a retriable/accepted application result rather than issuing an immediate blind duplicate POST. | `operations/Subscriptions.md`; retry hazard delegated below |

## Trap notes

- ⚠ Step 1 (client registration) — the SDK wrapper and its `HttpClient`/handler pipeline have different lifetime concerns; incorrect ownership can exhaust sockets or discard configured handlers. **MUST load `dotnet-client-initialization`** before registering the client.
- ⚠ Step 1 (authentication) — credential timing, configuration sourcing, and rotation affect whether requests are authenticated and secrets remain out of code/logs. **MUST load `dotnet-authentication`** before wiring `BasicAuth`.
- ⚠ Step 1 (server and resilience) — the retry/timeout/base-URL option names do not reveal the effective call boundary or whether a failed write can be re-sent, which directly affects duplicate subscriptions. **MUST load `dotnet-configuration-resilience`** before configuring the client.
- ⚠ Steps 3–7 (calls) — nullable generated parameters without C# defaults must still be supplied and positional calls can silently bind the wrong filter/date slot. **MUST load `dotnet-calling-endpoints`** before the first endpoint call.
- ⚠ Steps 3–7 (models) — required/init-only members, JSON wire names, `StringEnum<T>` values, nullable envelopes, and union construction/access can otherwise produce compile failures or malformed payloads. **MUST load `dotnet-models`** before constructing or mapping SDK models.
- ⚠ Steps 4–8 (error boundary) — Case A typed errors and Case B raw errors expose different safe access paths; treating a typed accessor as a catch-all loses provider detail. **MUST load `dotnet-error-handling`** before writing catches or middleware translation.
- ⚠ Step 8 (tests) — choosing the wrong fake seam couples tests to generated controller internals and misses the actual serialized request/response/error behavior. **MUST load `dotnet-testing`** before writing integration tests.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## Assumptions & Blockers

- **Assumption:** the configured sandbox is US-hosted. The stated settings contain no US/EU selector; an EU site requires adding an explicit region setting and using the separate EU Site/BaseUrl override points. (`sdk-map.md`)
- **Assumption:** sandbox products intended for this hero flow are configured so payment information is not required. The SDK operation explicitly says product options may require payment; omitting payment fields cannot override that. (`operations/Subscriptions.md`)
- **Assumption:** an authenticated eShop user has a stable immutable subject/name-identifier plus a trusted email. `CreateCustomer` requires non-null first name, last name, and email; define deterministic nonempty name fallbacks or block with validation when claim/user-profile data is incomplete. (`records-1-Ac-Cr.md`)
- **Assumption:** “prevent same-plan subscriptions” means strict lifetime uniqueness: any customer subscription with the same product handle blocks creation, including canceled/expired/failed records. If re-subscription after a terminal state is desired, product policy must explicitly name the allowed `SubscriptionState` values. (`records-3-Of-Su.md`; `enums.md`)
- **Blocker for horizontally scaled correctness:** the SDK exposes no create idempotency-key parameter and does not document subscription-reference uniqueness. A process-local lock alone cannot guarantee double-click safety across replicas/restarts; implementation needs a durable unique `(user, plan)` claim or distributed serialization under application control. (`operations/Subscriptions.md`; `records-1-Ac-Cr.md`)
- **Contract limitation:** `Product` exposes price in cents but no currency field. The plans endpoint can truthfully return `priceInCents`; returning currency requires a separately grounded site/price-point contract outside the stated flow. (`records-3-Of-Su.md`)
- **UNVERIFIED provider-payload limitation:** the generated `CustomerErrorResponse1.Errors` model contains only `per_page` and `price_point`, which is visibly unrelated to customer validation. Customer 422 detail must be extracted best-effort and fall back to a generic safe message. (`records-1-Ac-Cr.md`)
