# Maxio Advanced Billing subscription capability — implementation plan

## 1. Scope & sequence

1. Add the published `AsadAli.AdvancedBilling.Sdk` dependency if the target project does not already reference it. Register one long-lived `MaxioAdvancedBillingClient` through the application's DI convention, bind the API key and configured product-family handle, select `ServerEnvironment.Us` by default, and apply the optional Production/US `BaseUrl` override.
2. Put all Maxio access behind one application integration service. It must use only `MaxioAdvancedBillingClient` operations, never direct Maxio HTTP calls. At the boundary, use the validated request identity supplied by the existing JWT authentication path to derive a stable customer reference and a stable logical-subscription reference.
3. Implement `GET /api/subscription-plans`: list product families, select the configured family by exact `ProductFamily.Handle`, list that family’s products page by page, and map each product to the application’s plan/price DTO.
4. Implement `POST /api/subscriptions`: validate the requested plan against the configured family, reconcile/find the stable Maxio customer, create the customer only when the reference is absent, reconcile/find the stable subscription, create it only when absent, and map the resulting subscription to plan/price/state/next-billing-date. Re-read after an ambiguous write outcome before reporting failure.
5. Implement `GET /api/my-subscriptions`: resolve the current JWT identity to its Maxio customer, list that customer’s subscriptions, and map every returned subscription to plan/price/state/next-billing-date.
6. Add application-owned error translation, bounded cancellation, and tests through the SDK’s `HttpClient` seam. Verify the outgoing SDK paths, query names, request envelopes, and response envelopes with a fake handler before live verification.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 3. Trap notes

- Step 1 (client registration) — the SDK owns neither the supplied `HttpClient` nor the application’s client lifetime, and changing server/base-URL selection is nested per server/environment. **MUST load `dotnet-client-initialization`**.
- Step 1 (configuration and BaseUrl) — retry/timeout settings do not by themselves bound a whole request, and the SDK’s `Timeout` is not the same concern as the registered `HttpClient` timeout. **MUST load `dotnet-configuration-resilience`**.
- Step 1 (authentication) — credentials must be applied through the generated options property before construction, with the API key kept in configuration. **MUST load `dotnet-authentication`**.
- Step 2 (JWT identity) — the JWT claim-to-reference mapping and the stable logical-subscription key are application decisions; choosing them inconsistently breaks customer/subscription reconciliation. **MUST load `dotnet-calling-endpoints`** for the SDK call boundary.
- Step 3 (plan discovery) — list/search signatures contain nullable parameters with no C# defaults, and the product list is manually paginated. **MUST load `dotnet-calling-endpoints`**.
- Step 4 (request/response models) — generated request wrappers, nullable response envelopes, string enums, and wire names differ from C# property names. **MUST load `dotnet-models`**.
- Step 4 (write safety) — a failed POST may have executed and the SDK cannot disable transport retries by setting a zero retry count; an application guard/reconciliation policy is required for the requested idempotent behavior. **MUST load `dotnet-configuration-resilience`**.
- Step 4/5 (provider failures) — typed Case-A errors require every listed accessor with `TryGetRawError` last, while Case-B errors expose raw status/body directly; connection failures and parse failures are separate from both. **MUST load `dotnet-error-handling`**.
- Step 6 (tests) — fake the `HttpClient` supplied to the SDK with a `HttpMessageHandler`, and assert real outgoing method/path/query/body plus both status and transport write-failure behavior. **MUST load `dotnet-testing`**.

## 5. Assumptions & Blockers

- Assumption — the application already validates JWTs and exposes a stable identity to the endpoint layer. Exact claim names and the claim-to-Maxio-reference mapping are not specified by the task or SDK map; they are `YOUR CALL — not in the map`.
- Assumption — one Maxio customer represents each JWT identity, and one logical Maxio subscription is keyed by that identity plus the selected plan. If the product allows multiple simultaneous subscriptions to the same plan, the application must supply a distinct idempotency key or persistence key; the SDK does not provide one.
- `UNVERIFIED` — the map documents customer-reference uniqueness but does not document provider enforcement of subscription `Reference` uniqueness. The implementation must retain an application-side idempotency/concurrency boundary and reconcile after ambiguous writes; it must not claim provider-side exactly-once behavior.
- Assumption / potential blocker — the requested POST contract does not specify a payment-profile or tokenized payment input. `CreateSubscription` Notes say payment information may be required by product settings. The implementation can create subscriptions without that extra payload only for configured products whose signup rules permit it; otherwise the application must define a safe tokenized-payment input path before this capability is complete.
- `UNVERIFIED` — live Maxio payloads may omit nullable `Subscription.Product`, price, state, or period-end fields even though the generated model declares them. Extract best effort, preserve nullable output, and fall back to the generic integration error when the requested response cannot be formed; do not treat a malformed body as “no subscription.”
- Application configuration binding key names for the API key, product-family handle, site/environment, and optional Production/US `BaseUrl` override are not supplied by the task or map: `YOUR CALL — not in the map`. The implementer must bind them using the project’s established configuration convention.
