# Maxio subscription billing implementation plan

## Scope & sequence

| Step | Implementation outcome | Maxio operations |
|---|---|---|
| 1. Configuration and client | Add the published `AsadAli.AdvancedBilling.Sdk` package to `src/PublicApi`; bind and validate only `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; register one long-lived `HttpClient` pipeline and the SDK client. If `BaseUrl` is non-empty, assign it unchanged to the Production/US server node; otherwise select US and set that node's `Site` from `Subdomain`. Basic auth is API key / literal `"x"`. | none |
| 2. Application boundary and persistence | Add an application-owned Maxio gateway, DTOs, provider-exception translator, and a subscription-enrollment/idempotency entity. A waiter reloads/reconciles the intent rather than creating independently. | none |
| 3. Browse plans | Resolve the configured family handle at runtime by listing families and matching `ProductFamily.Handle` ordinally; never persist/configure a seeded numeric catalog ID. | 4. Subscribe | Take only a product handle from the authenticated request. Resolve it through Maxio and require its nested family handle to equal the configured family. | 5. Show my subscriptions | Derive the same customer reference from the token identity. A customer lookup 404 returns an empty list. | 6. HTTP endpoints | Add JWT-authorized PublicApi endpoints following its existing endpoint conventions: `GET /api/subscription-plans`, `POST /api/subscriptions`, and `GET /api/my-subscriptions`. Never accept a user/customer identifier from the request. Map provider validation/conflict to stable 4xx problem details, provider/auth/transport/contract failures to stable 5xx/502/503 problem details, and propagate request cancellation. Existing basket/order routes remain untouched. | all above through the gateway only |
| 7. Tests and verification | Unit-test domain/idempotency behavior and gateway mapping; test SDK traffic through a fake `HttpMessageHandler`; add PublicApi endpoint authorization/identity/contract tests; then build/test and run a sandbox smoke flow using a JWT. No test contains credentials or seeded numeric IDs. | all above through controlled HTTP responses; sandbox smoke only for live calls |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency directive

The application guarantee is one subscription per `(authenticated user ID, product handle)`. Insert/get a unique intent before any provider write; the winning request owns the transition, while concurrent double-click requests await/reload/reconcile the same row. Customer creation is additionally protected by Maxio's documented unique customer `reference`. Before a subscription POST—and whenever ownership is recovered after a timeout/crash—call `FindSubscription` with the deterministic subscription reference. Never create from a stale failed row until reconciliation has completed. Store the Maxio customer/subscription IDs only as runtime results, not seeded configuration.

**UNVERIFIED:** the bundled map exposes subscription `Reference` and singular `FindSubscription`, but does not state that Maxio enforces uniqueness for subscription references. Do not claim that it does. The durable unique intent/serialized owner provides double-click idempotency; the reference provides recovery. On any ambiguous outcome or 422, accept a found subscription only after its reference, customer reference, and product handle exactly match; otherwise leave the intent recoverable and surface an indeterminate/provider error rather than issuing another create in the same request.

### Error-boundary directives

- Preserve HTTP status and safe provider validation messages via each operation's documented typed accessor or `RawError`; never parse `Exception.ToString()`. Do not leak credentials, URLs containing secrets, raw customer data, or arbitrary provider bodies to API callers.
- A successful HTTP response can still be unusable because several inner SDK fields are nullable. Validate the business-required fields named above and translate a missing/mismatched envelope into a provider-contract 502 while retaining sanitized diagnostics.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

## Trap notes

⚠ Step 1 (client registration) — the SDK wrapper and its underlying `HttpClient` have different lifetime/ownership concerns; getting this wrong causes socket/pipeline and DI failures. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential timing, rotation, and configuration placement determine whether Basic auth is actually attached and whether secrets leak. **MUST load `dotnet-authentication`** before assigning authentication.

⚠ Steps 3–5 (calls) — generated optional parameters without C# defaults and the literal `ct` name make positional or assumed-default calls bind incorrectly. **MUST load `dotnet-calling-endpoints`** before writing the first SDK call.

⚠ Steps 3–5 (models) — required members, nullable envelope members, JSON wire names, and `StringEnum<T>` values can silently corrupt request construction or response mapping. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 1, 2, and 4 (resilience/idempotency) — retry and timeout settings can change whether a failed write is sent again and how long ownership remains ambiguous; the application idempotency protocol must be designed with those consequences. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing write recovery.

⚠ Steps 4–6 (exception translation) — typed and raw provider errors have different access paths, and malformed success/error JSON reaches a different catch path with different status-information consequences. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 7 (tests) — mocking generated controllers couples tests to SDK internals and misses real serialization/error construction; choose the supported HTTP seam and assert observable behavior. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- Assumption: one enrollment is allowed per authenticated user and product handle; the Basic and Pro handles are separate intents and may coexist.
- Assumption: `ApplicationUser` supplies only stable `Id`, `UserName`, and `Email`; it has no first/last-name fields. Existing registered/seeded users provide a usable email in `Email` or email-shaped `UserName`. Customer names are produced by the deterministic identity-only fallback defined in the `CreateCustomer` row, and the endpoint never accepts identity/customer fields as authoritative request data.
- Assumption: `MAXIO_ENVIRONMENT` is an execution guard indicating the sandbox target, not an SDK server selector. The requested `Maxio:` binding contract contains exactly the four named keys; sandbox/live is selected by the configured Maxio site, while the SDK's environment choice is hosting region (US/EU). No `Maxio:Environment` key is invented.
- Assumption: SQL Server is the production persistence/concurrency authority. `UseOnlyInMemoryDatabase=true` is sufficient for the requested single-process smoke test but loses local enrollment rows on restart; deterministic Maxio customer/subscription references rehydrate live state within the limits described above.
- Blockers: none. Every required Maxio operation is exposed by the bundled SDK map.
