# Maxio subscription capability plan

## 1. Scope & sequence

1. Register the Maxio client and bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; use the production server group pointed at the configured sandbox host.
2. `GET /api/subscription-plans`: call `ProductFamilies.ListProductsForProductFamily` with `handle:` + `Maxio:ProductFamilyHandle`; map each `ProductResponse.Product` to the public plan/price/recurrence shape.
3. `POST /api/subscriptions`: obtain the authenticated token identity and its stable application user reference; resolve the Maxio customer with `Customers.ReadCustomerByReference`, create it with `Customers.CreateCustomer` when the lookup is a 404, then resolve the subscription with `Subscriptions.FindSubscription` by a stable reference and create it with `Subscriptions.CreateSubscription` when the lookup is a 404. Validate the requested product handle against the configured family catalog before creating.
4. `GET /api/my-subscriptions`: resolve the Maxio customer by the authenticated identity reference and call `Customers.ListCustomerSubscriptions`; map each inner subscription to plan/price/state/next-billing-date output.
5. Keep the feature additive and parallel to existing PublicApi behavior. Persist the application user-id-to-Maxio customer/subscription mapping where the app’s existing persistence allows; otherwise document the in-memory lifetime caveat and retain Maxio reference lookups for remote idempotency.
6. Add convention-matching tests for authenticated access, catalog mapping, customer/subscription idempotency, provider errors, and the nullable response fields; build and run the project’s tests/end-to-end sandbox verification after implementation.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members
table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — the SDK wrapper, registered `HttpClient`, and handler lifetime have different ownership consequences. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential binding and the point at which credentials enter client construction are not implied by the options type. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Step 2 (catalog and endpoint calls) — nullable parameters without C# defaults can be mis-bound, especially on list operations with many filters. **MUST load `dotnet-calling-endpoints`** before writing the first SDK call.

⚠ Step 2 (request/response mapping) — JSON wire names, required nested members, `StringEnum<T>` values, and nullable response envelopes are easy to mishandle. **MUST load `dotnet-models`** before constructing models or mapping them.

⚠ Step 3–4 (error boundary) — typed errors and raw errors expose different accessors, and a typed error’s raw fallback is not a universal catch for every SDK exception. **MUST load `dotnet-error-handling`** before writing catches or translation middleware.

⚠ Step 1–4 (resilience) — retry status/method selection, transport retry behavior for writes, per-attempt timeout, base URL selection, and manual pagination affect this flow’s correctness. **MUST load `dotnet-configuration-resilience`** before configuring the client or pagination.

⚠ Step 6 (tests) — the SDK’s test seam and the required behavior assertions must follow the app’s existing test framework rather than SDK internals. **MUST load `dotnet-testing`** before writing tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary. These rows belong in the
FIRST sheet, not a later revision: the boundary is written early, and a caveat that arrives
afterwards arrives too late to shape it.

## 5. Assumptions & Blockers

- **Resolved:** the configured sandbox plan accepts a no-card subscription when `PaymentCollectionMethod.Invoice` is supplied; no payment-profile/token input is required.
- **Resolved:** `CreateCustomer` requires `FirstName`, `LastName`, and `Email`; the integration supplies the authenticated token identity as the email and derives deterministic display names from it.
- **Minor assumption:** the public POST request supplies a product handle, and the integration validates it against the configured product-family catalog; the exact DTO/property name follows existing PublicApi conventions and is `YOUR CALL — not in the map`.
- **Minor assumption:** the stable reference format for the authenticated user and subscription is an application-owned choice, provided it remains deterministic and unique; the SDK only requires the customer `reference` to be unique and uses subscription `reference` for lookup.
- **Minor assumption:** mapping `Subscription.CurrentPeriodEndsAt` to the public next-billing-date field follows the Subscriptions operation Notes because the response does not return `next_billing_at`; the source map cannot prove live payload presence beyond the generated nullable model, so null must remain representable.
- **Minor assumption:** the persisted userId-to-subscription mapping and its in-memory fallback are application-layer choices; no persistence or concurrency policy is set by the SDK contract.
