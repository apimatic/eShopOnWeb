# Maxio recurring subscriptions plan — `src/PublicApi`

## Scope & sequence

| Step | Additive implementation work | SDK operations |
|---|---|---|
| 1 | Add the published `AsadAli.AdvancedBilling.Sdk` NuGet package to the project that owns `src/PublicApi`; never reference or copy SDK source. Bind the exact keys `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; credentials remain external user-secrets. Register one sandbox-only client configuration. | Client construction only. (`sdk-map.md`) |
| 2 | Add a catalog service behind `GET /api/subscription-plans`: list product families, select the single exact `ProductFamily.Handle == Maxio:ProductFamilyHandle`, then page all non-archived products for the returned runtime family ID. Return stable product handle, display name, price in cents, and billing interval; never persist or configure seeded numeric catalog IDs. | `ProductFamilies.ListProductFamilies`, `ProductFamilies.ListProductsForProductFamily`. (`operations/ProductFamilies.md`) |
| 3 | Validate the posted plan handle for `POST /api/subscriptions` with the handle endpoint and verify its returned `Product.ProductFamily.Handle` equals the configured family handle. The SDK can create by `ProductHandle`; the runtime product ID need not be sent. | `Products.ReadProductByHandle`. (`operations/Products.md`) |
| 4 | Resolve authenticated identity from the JWT's stable issuer+subject identity and the application's user profile. Derive and persist one deterministic Maxio customer reference. Lookup first; if absent, create with that reference. Concurrent requests serialize on the local customer row. Because Maxio explicitly makes customer `reference` unique, a create race that returns 422 is reconciled by a second lookup; it is success only when that lookup returns the expected reference. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer`. (`operations/Customers.md`) |
| 5 | Make subscription creation idempotent at the application boundary. Transactionally acquire a durable subscription-intent row before any provider write; its unique key coalesces the same user's double-click for the selected plan, and its durable ID becomes `CreateSubscription.Subscription.Reference`. While one row is `Creating`, only its owner may call Maxio. Replays first call `FindSubscription(reference)` and return the found subscription; only a confirmed 404 permits the first create attempt. After any ambiguous failure, leave the row reconcilable and run `FindSubscription` before another create call. | `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription`. (`operations/Subscriptions.md`) |
| 6 | Add JWT-protected `GET /api/my-subscriptions`: resolve the same persisted Maxio customer ID/reference and list that customer's subscriptions. Map each envelope to plan (`Subscription.Product.Name`/`Handle`), price (`ProductPriceInCents`, with `CurrentBillingAmountInCents` available), state, and next billing date (`NextAssessmentAt`; `CurrentPeriodEndsAt` is also available but is a distinct field). | `Customers.ListCustomerSubscriptions`. (`operations/Customers.md`; `records-3-Of-Su.md`; `records-4-Su-We.md`) |
| 7 | Put a provider exception translation boundary around every SDK call, preserving status and best-effort provider detail without leaking credentials. Add unit/integration tests around identity isolation, pagination, create races, replays, missing envelopes, typed/raw errors, and ambiguous-write reconciliation. | All operations above. (`sdk-map.md`; relevant operation pages) |

The local uniqueness transaction is what makes simultaneous double-click requests converge before the SDK write. `FindSubscription` provides recovery/reconciliation by reference, but the map does **not** state that subscription references are unique and `CreateSubscription` has no idempotency-key parameter. Do not describe the provider operation itself as exactly-once; see **Assumptions & Blockers**.

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 1 (client registration) — client-wrapper and `HttpClient` ownership/lifetime choices affect connection reuse and test seams. **MUST load `dotnet-client-initialization`** before registering the SDK.

⚠ Step 1 (credentials) — Basic credentials must be bound without leaking the API key and must be present when the client is constructed. **MUST load `dotnet-authentication`** before wiring authentication.

⚠ Steps 2–6 (calls) — nullable generated parameters without C# defaults still must be passed, response envelopes add a payload level, and the cancellation argument is named `ct`. **MUST load `dotnet-calling-endpoints`** before the first operation call.

⚠ Steps 2–6 (models) — required/init-only members, enum wrappers, nullable envelopes, JSON wire names, and `AnyOf` construction can otherwise produce compile-time or mapping defects. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 1 and 5 (resilience/idempotency) — retry and timeout option names do not reveal whether a failed write can be re-sent, how long the whole call can last, or how cancellation interacts with reconciliation; getting this wrong can duplicate a subscription after an ambiguous failure. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing the create state machine.

⚠ Step 7 (typed/raw provider failures) — Case A accessors are status-specific and Case B exposes only `RawError`; using exception text as the payload loses structured status/body handling. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 7 — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 (tests) — faking generated controllers couples tests to SDK internals and misses serialization/envelope/error behavior. **MUST load `dotnet-testing`** before adding integration tests.
