## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 2 (client registration) — `HttpClient` ownership/lifetime and SDK wrapper lifetime are distinct; getting the seam wrong causes connection churn or stale handler behavior. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 2 (authentication) — credentials must exist at client construction and the generated auth property/name is easy to confuse with headers. **MUST load `dotnet-authentication`** before wiring auth.
- ⚠ Steps 4/6/7/8 (calls) — many nullable generated parameters have no C# default, named arguments must use literal identifiers, and response envelopes add a level. **MUST load `dotnet-calling-endpoints`** before the first operation call.
- ⚠ Steps 4/6/7/8 (models) — generated records are immutable/init-only, nullable response members require guards, and string-backed enums are not C# enums. **MUST load `dotnet-models`** before constructing or mapping models.
- ⚠ Steps 6/7/10 (boundary) — Case A typed errors and Case B raw errors require different catch/accessor paths; otherwise expected absence and validation failures become outages. **MUST load `dotnet-error-handling`** before writing the boundary.
- ⚠ Step 7 (idempotent write) — whether a failed write can be re-sent and how timeout/retry layers interact determines whether one application command can become multiple wire writes. **MUST load `dotnet-configuration-resilience`** before configuring retries or the wire-once handler.
- ⚠ Steps 4/8 (pagination/resilience) — pagination completion, timeout scope, base URL override, cancellation, and stale-cache behavior must be made explicit. **MUST load `dotnet-configuration-resilience`** before implementing them.
- ⚠ Step 11 (tests) — fake at the stable application seam for orchestration tests and use the SDK's supported HTTP seam only for adapter contract tests; coupling tests to generated controllers makes them brittle. **MUST load `dotnet-testing`** before writing tests.
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The existing authenticated identity path can resolve a stable, nonblank application user ID plus a usable email, first name, and last name without trusting request-body identity fields. If profile data is incomplete, POST fails before contacting Maxio with a safe client/profile error. **YOUR CALL — not in the map**.
- Idempotency means at most one subscription per application user and product handle; an intentional second purchase of the same plan returns the existing Maxio subscription. **YOUR CALL — not in the map**.
- Products that require/request payment details are not “available” to this no-card capability and are excluded/rejected. Adding card or 3DS collection is out of this scope. The CreateSubscription Notes explicitly make payment requirements product-dependent; the exclusion policy is **YOUR CALL — not in the map**.
- `nextBillingDate` maps to Maxio's nullable `Subscription.NextAssessmentAt`; null remains null. The SDK model supplies that field, while the public DTO name is **YOUR CALL — not in the map**.
- Customer-reference uniqueness is provider-documented. Subscription-reference lookup is provider-documented, but subscription-reference uniqueness is not stated in the map; therefore application serialization and wire-once handling are mandatory and provider-side uniqueness is **UNVERIFIED**, never an idempotency dependency.
- Development/live verification uses a Maxio site whose `Site.Test` is true. The app enforces that guard outside Production; deployment policy for a future live Maxio site is **YOUR CALL — not in the map**.

### Blockers

- None. Every required Maxio operation and model is present in the bundled v1.0.2 map; the generated customer-422 payload mismatch is handled defensively and marked **UNVERIFIED** rather than left open.
