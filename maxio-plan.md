# Maxio Advanced Billing integration plan

## Scope & sequence

| Step | Implementation outcome | SDK operations |
|---|---|---|
| 1 | Add the published `AsadAli.AdvancedBilling.Sdk` package to `src/PublicApi`; bind and validate `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; register one long-lived `HttpClient` pipeline and an SDK-backed billing gateway. Keep the API key in environment variables or user-secrets only. Use the sandbox site's subdomain/credentials; this SDK exposes only US/EU hosting, not a separate sandbox enum. | Client construction only |
| 2 | Require the existing JWT bearer policy on all three routes. At the boundary, derive the immutable caller key from `ClaimTypes.NameIdentifier` or `sub`; obtain first name, last name, and email from trusted claims/application profile, never from a caller-supplied Maxio customer id/reference. | 3 | Implement `GET /api/subscription-plans`: request every page for `productFamilyId: $"handle:{configuredFamilyHandle}"`, exclude archived products, retain only the provisioned handles `eshop-pro` and `basic-plan`, and return handle/name/price-in-cents/billing interval. Never expose or persist product numeric ids. | `ProductFamilies.ListProductsForProductFamily` |
| 4 | Implement `POST /api/subscriptions` with `{ productHandle, idempotencyKey }`: validate both; read the product by stable handle and require its returned `ProductFamily.Handle` to match configuration; resolve component `api-call` by handle and require its family to match; ensure the Maxio customer by unique reference (lookup, create on 404, lookup again after a concurrent-create 422); and create the subscription using stable product/customer references. Initialize the resolved metered/event component with `UnitBalance = 0`; its numeric id is runtime-only. | `Products.ReadProductByHandle`; `Components.FindComponent`; `Customers.ReadCustomerByReference`; `Customers.CreateCustomer`; `Subscriptions.FindSubscription`; `Subscriptions.CreateSubscription` |
| 5 | Make Step 4 double-click safe with a durable idempotency ledger having a unique `(CallerSubject, IdempotencyKey)` key and storing the request fingerprint, deterministic Maxio reference, state, and successful response. Derive `subscriptionReference = "eshop-sub:" + lowercase-hex(SHA256(subject + "\n" + idempotencyKey))`. Under the unique claim, replay the stored response for the same fingerprint and return 409 for key reuse with a different product. Before a write and after any ambiguous write failure, call `FindSubscription(reference)`; never issue a second application-level create when that reference already exists. This prevents concurrent/double-click sends from the application; provider-side behavior after an SDK-internal transport retry is not asserted. | `Subscriptions.FindSubscription`; `Subscriptions.CreateSubscription` |
| 6 | Implement `GET /api/my-subscriptions`: resolve the caller's customer by reference; return an empty list on customer 404; otherwise list that customer's subscriptions and map plan handle/name, `ProductPriceInCents`, state, and `NextAssessmentAt` as `nextBillingAt`. | `Customers.ReadCustomerByReference`; `Customers.ListCustomerSubscriptions` |
| 7 | Add one exception-translation boundary around the gateway, structured logs with operation/correlation id but no credentials or full provider bodies, cancellation propagation, bounded pagination, startup/configuration validation, and stable API problem details (400/401/404/409/422/502/503/504 as appropriate). Typed payload extraction is best-effort and falls back to the generic message/status path. | All above operations |
| 8 | Add unit and HTTP integration tests for JWT isolation, plan filtering/pagination, envelope mapping, customer races, durable idempotency/replay/conflict, ambiguous writes, all typed/raw/JSON error paths, cancellation, configuration, and secret absence. Use a fake HTTP handler at the SDK `HttpClient` seam; do not mock generated controllers/models. | All above operations |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 1 (client registration) — client/`HttpClient` ownership and DI lifetime can exhaust sockets or bypass the intended handler pipeline. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (configuration) — whether retry, timeout, cancellation, base-URL overrides, and manual pagination bound the intended work is not visible from option names; write retries can interact with the idempotency guarantee. **MUST load `dotnet-configuration-resilience`** before registering/tuning the client or pagination loop.

⚠ Step 1 (credentials) — auth must be configured in the correct options callback and rotated without embedding secrets in source or logs. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 3–6 (calls) — nullable parameters without C# defaults still have to be supplied, positional arguments can mis-bind, envelopes add a payload level, and cancellation uses the literal `ct` name. **MUST load `dotnet-calling-endpoints`** before writing the first SDK call.

⚠ Steps 3–6 (models) — generated records use required/init-only members, string-backed enums and union factories; confusing C# names with wire names or dereferencing nullable payloads breaks requests and mappings. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 4–7 (errors) — Case A and Case B expose different bodies and a naive catch ladder loses useful provider detail or leaks it to clients. **MUST load `dotnet-error-handling`** before writing the integration boundary.

⚠ Step 7 (2xx JSON drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 (non-2xx JSON drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (tests) — mocking generated controllers couples tests to SDK internals and misses serialization, query, envelope, and error-construction behavior. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- Assumption: `api-call` is provisioned in product family `eshop-subscribe` as a metered or event-based component; the integration fails closed at startup/request validation if its returned kind/family/archived state does not match, rather than guessing another initialization field.
- Assumption: an authenticated caller has stable `sub`/name-identifier plus trusted first-name, last-name, and email data available from JWT claims or the application's identity profile; Maxio customer creation cannot proceed without all three required fields.
- Assumption: the POST contract may require an opaque client-generated `idempotencyKey`; the client reuses it for retries/double-clicks and generates a new one for a genuinely new purchase intent.
- Assumption: sandbox means a Maxio test-mode site selected by its sandbox subdomain/API key (or the explicit verbatim base-URL override); the generated SDK has US/EU values but no separate sandbox enum.
- Blockers: none for implementation planning.
