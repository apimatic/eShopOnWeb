# Maxio subscription-billing integration contract plan

## 1. Scope & sequence

Implementation is additive and application-owned; this sheet defines only the Maxio call surface and the decisions it forces.

1. Register one reusable `MaxioAdvancedBilling.MaxioAdvancedBillingClient` and configure the production server for the selected region.
2. From the configured product-family handle, call `client.ProductFamilies.ListProductsForProductFamily` with `productFamilyId: "handle:" + configuredHandle`; manually consume all pages and select one returned product as the application’s plan.
3. For the JWT user, call `client.Customers.ReadCustomerByReference` with the stable application reference. On its documented 404, call `client.Customers.CreateCustomer` with the required customer fields and the same reference; re-read after an ambiguous create outcome.
4. For the selected plan, call `client.Subscriptions.FindSubscription` with a deterministic subscription reference. On its documented 404, call `client.Subscriptions.CreateSubscription` with the customer ID, selected product handle (and selected product price-point handle when applicable), and that reference; re-read after an ambiguous create outcome.
5. Call `client.Customers.ListCustomerSubscriptions` with the ensured Maxio customer ID, then unwrap each response and map the plan, price, state, and next-billing-date fields below.
6. Put the SDK exception boundary around every call, preserve typed-vs-raw error information, and test success, 404 recovery, validation failures, malformed bodies, concurrent callers, and ambiguous writes through the `HttpClient` seam.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members
table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.

### Client, authentication, server, and configuration facts

- Package: `AsadAli.AdvancedBilling.Sdk`; root namespace: `MaxioAdvancedBilling`.
- Construct `MaxioAdvancedBilling.MaxioAdvancedBillingClient(System.Net.Http.HttpClient httpClient, MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions options)` once over a reusable `System.Net.Http.HttpClient`; DI may use the generated `AddMaxioAdvancedBillingClient` extension.
- Options are `MaxioAdvancedBilling.MaxioAdvancedBillingClientOptions.Environment: MaxioAdvancedBilling.Servers.ServerEnvironment`, `.Retry: MaxioAdvancedBilling.Core.Configuration.RetryOptions`, `.Server: MaxioAdvancedBilling.Servers.ServerOptions`, and `.BasicAuth: MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials?`.
- Authentication is HTTP Basic: `MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials.Username` is the Maxio API key and `MaxioAdvancedBilling.Core.Authentication.Basic.BasicAuthCredentials.Password` is the literal `"x"`. Load the key from an application configuration binding key or secret store; the binding-key name is `YOUR CALL — not in the map`.
- `MaxioAdvancedBilling.Servers.ServerEnvironment.Us` is the default and uses `https://{site}.chargify.com`; `MaxioAdvancedBilling.Servers.ServerEnvironment.Eu` uses `https://{site}.ebilling.maxio.com`. Set `options.Server.Production.Us.Site` (or the matching EU site) to the Maxio subdomain; the map documents `subdomain` as the default site template value. Base URL overrides belong under the selected production server/environment node.
- Retry settings are `MaxioAdvancedBilling.Core.Configuration.RetryOptions`; use `MaxioAdvancedBilling.Core.Configuration.RetryOptions.Default()` as the starting point if tuning is needed. Do not use retry settings as the application’s idempotency mechanism for subscription creation.

### Idempotency and concurrency recommendations

- Customer identity: use one stable application reference for the JWT user in `CreateCustomer.Reference (reference)` and `ReadCustomerByReference(reference)`. The CreateCustomer Notes state that `reference` must be unique and only one customer may be created for a given reference.
- Subscription identity: use one deterministic application reference per intended user/plan enrollment in `CreateSubscription.Reference (reference)` and `FindSubscription(reference)`. The map exposes the lookup by reference; it does not document a provider-side uniqueness guarantee for subscription references.
- Treat lookup-then-create as a non-atomic workflow. The application must provide its own durable uniqueness/coordination mechanism for the customer reference and enrollment reference; the concrete store, lock, and ownership rules are `YOUR CALL — not in the map`.
- If a create call has an ambiguous outcome, query the same reference before issuing another create. If a concurrent create returns a typed validation error, re-read by the same reference and return the existing resource only when the application’s identity/plan match; otherwise surface the original rejection. Do not manufacture an idempotency header or request field—the mapped signatures expose none.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the SDK’s client/DI lifetime and the `HttpClient`/handler lifetime are separate concerns; choosing the wrong registration can change connection reuse and handler rotation. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (server and retry configuration) — retry, timeout, base-URL, and logging options hide per-attempt versus whole-call boundaries and method/status eligibility; a non-idempotent enrollment can be duplicated if the integration treats resilience as idempotency. **MUST load `dotnet-configuration-resilience`** before configuring the client.
- ⚠ Step 2–5 (endpoint calls) — leading nullable parameters without C# defaults and the literal cancellation-token name can cause omitted arguments or mis-bound query values. **MUST load `dotnet-calling-endpoints`** before writing calls.
- ⚠ Step 2–5 (request/response models) — generated records use nested envelopes, nullable fields, wire names, StringEnum values, and union accessors that are not visible from a domain model. **MUST load `dotnet-models`** before constructing or mapping models.
- ⚠ Step 3–4 (credentials) — the SDK’s Basic-auth credential property and credential timing are easy to confuse with the package id or root namespace. **MUST load `dotnet-authentication`** before supplying credentials.
- ⚠ Step 2–5 (error boundary) — typed Case-A errors and Case-B `MaxioAdvancedBilling.Core.ErrorResponse.RawError` errors reach catches differently, and each operation’s accessor is operation-specific. **MUST load `dotnet-error-handling`** before writing catches or translation middleware.
- ⚠ Step 6 (tests) — mocking the controller rather than the supplied `HttpClient` can miss serialization, envelopes, query wire names, retry duplication, and typed/raw exception behavior. **MUST load `dotnet-testing`** before writing integration tests.

System.Text.Json.JsonException reaches the boundary from two directions and they need opposite handling:

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- **Blocker — JWT identity fields:** the repository’s JWT claim names and the application’s stable reference policy were not supplied. The implementer must provide a stable user reference plus values for the SDK-required `FirstName`, `LastName`, and `Email` fields, or choose an application-owned fallback before `CreateCustomer` can be considered complete.
- **Blocker — payment configuration:** the `CreateSubscription` Notes state that payment information may be required depending on the selected product. The implementer must decide whether the selected product/site permits a subscription without payment data or provide a supported `PaymentProfileId`, `PaymentProfileAttributes`, `CreditCardAttributes`, or `BankAccountAttributes` path; the task does not supply payment data.
- **Assumption — one enrollment identity:** “idempotently creating/enrolling a subscription” is interpreted as one deterministic subscription reference per application user and selected plan. Whether a user may hold multiple subscriptions or switch an existing enrollment is `YOUR CALL — not in the map`.
- **Assumption — plan selection:** the application selects one non-archived `MaxioAdvancedBilling.Models.Product` from the family’s paged results. The selection rule and presentation are `YOUR CALL — not in the map`.
- **Assumption — production region/site:** use `MaxioAdvancedBilling.Servers.ServerEnvironment.Us` and the configured production site unless deployment configuration selects the documented EU environment; the binding keys for those application settings are `YOUR CALL — not in the map`.
- **UNVERIFIED — billing timestamp:** the map exposes `current_period_ends_at` and `next_assessment_at`, but no `next_billing_at`; the plan therefore uses the defensive mapping directive in §2 and does not claim live-wire equivalence.
