# Maxio subscription integration plan

## 1. Scope & sequence

| Step | Application work | Maxio operations |
|---|---|---|
| 1. Package, configuration, DI | Add NuGet package `AsadAli.AdvancedBilling.Sdk` pinned to `1.0.2`; bind and validate only `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; register the long-lived HTTP pipeline and SDK client. Use Basic auth. Configure the Production/US server node with `Maxio:Subdomain`, unless `Maxio:BaseUrl` is non-empty, in which case assign that value verbatim to the node's `BaseUrl`. Never log credentials. | none |
| 2. Catalog resolver | Resolve the configured family handle at runtime with `ListProductFamilies`; require one non-archived family with that exact handle, then paginate `ListProductsForProductFamily` using its just-resolved ID (converted to a string). Return non-archived products, including seeded handles `eshop-pro` and `basic-plan`, mapped from Maxio fields. Cache only for a short bounded period and invalidate/retry on a missing selected handle; Maxio remains the catalog source. | `ProductFamilies.ListProductFamilies`, `ProductFamilies.ListProductsForProductFamily` |
| 3. Plan validation | For a requested plan handle, call `ReadProductByHandle`, reject a missing/archived product, and verify `Product.ProductFamily.Handle` exactly equals `Maxio:ProductFamilyHandle`. Never accept a caller-supplied numeric product or price-point ID. | `Products.ReadProductByHandle` |
| 4. Customer ensure | Derive a deterministic customer reference from the authenticated application's stable user ID. Call `ReadCustomerByReference`; on 404 create a customer with required first name, last name, email, and the same reference. If create returns a race-shaped rejection, re-read by reference and proceed only if found; the create Notes guarantee customer reference uniqueness. | `Customers.ReadCustomerByReference`, `Customers.CreateCustomer` |
| 5. Idempotency reservation | Before any subscription write, atomically reserve the application key `(user ID, plan handle)` in durable storage with a unique constraint and processing lease/state. A retry/second caller observes the same reservation. A worker/owner always performs the Maxio reference lookup before POST, and records the returned Maxio subscription ID/state. This is application design, required because the SDK map does not promise subscription-reference uniqueness and transport outcomes may be ambiguous. | none; `YOUR CALL — not in the map` |
| 6. Subscription lookup/create | Derive a deterministic subscription reference from the stable user ID and selected product handle. `FindSubscription` first. If found, verify its customer reference and product handle before returning it. If 404, create with `ProductHandle`, `CustomerReference`, `Reference`, and `PaymentCollectionMethod = CollectionMethod.Remittance`; omit numeric IDs and payment-instrument data. The live sandbox requires `remittance` to avoid automatic collection of the signup balance even though the products do not require a stored payment method. On ambiguous failure leave the reservation retryable; the next attempt starts with `FindSubscription`. Do not issue a second POST merely because the first call timed out. | `Subscriptions.FindSubscription`, `Subscriptions.CreateSubscription` |
| 7. Account projection | Resolve the customer by deterministic reference. A 404 means an empty list. Otherwise call `ListCustomerSubscriptions`, keep subscriptions whose nested product family handle equals `Maxio:ProductFamilyHandle`, and map plan name/handle, `ProductPriceInCents`, `State`, and `NextAssessmentAt` (plus identifiers useful to the caller). | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` |
| 8. HTTP boundary | Implement the task-specified authenticated endpoints `GET /api/subscription-plans`, `POST /api/subscriptions`, and `GET /api/my-subscriptions`; resolve the caller only from the JWT/application identity path. Map provider validation/not-found/conflict separately from dependency/authentication/timeout failures; emit safe problem details and structured logs without secrets or full provider bodies. | all above |
| 9. Tests and live verification | Unit-test mapping, exact-handle/family validation, all 404 and 422 branches, malformed 2xx/non-2xx JSON, retries after unknown write outcome, and concurrent double-clicks. At the HTTP seam, assert request paths, Basic auth, JSON wire names, response envelopes, cancellation, and no duplicate POST. Then perform sandbox smoke tests for both seeded handles. | all above |

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — client/`HttpClient` ownership and DI lifetime determine connection reuse and testability. **MUST load `dotnet-client-initialization`** before registering the client.
- ⚠ Step 1 (authentication) — credential timing and configuration sourcing determine whether every request is authenticated without leaking the key. **MUST load `dotnet-authentication`** before setting `BasicAuth`.
- ⚠ Steps 2–7 (calls) — optional parameters without C# defaults can silently mis-bind, and cancellation uses the literal `ct` name. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 2–7 (models) — nullable response envelopes, generated `StringEnum<T>` values, and immutable required request members require SDK-specific construction/access patterns. **MUST load `dotnet-models`** before building payloads or DTO mapping.
- ⚠ Steps 4–8 (error boundary) — Case A typed errors and Case B raw errors have different status/body access paths; an incorrect catch ladder loses actionable failures. **MUST load `dotnet-error-handling`** before writing catches.
- ⚠ Step 6 (write resilience) — transport/status retry behavior can replay a subscription POST and timeout scope can leave an unknown outcome; this directly shapes the idempotency recovery path. **MUST load `dotnet-configuration-resilience`** before configuring retries/timeouts.
- ⚠ Step 2 (pagination/resilience) — product pagination, cancellation, timeout, base-URL override, and logging require explicit policy choices. **MUST load `dotnet-configuration-resilience`** before configuring the client or catalog loop.
- ⚠ Step 9 (tests) — the supported HTTP seam and behavior-focused fake strategy determine whether tests cover real serialization/error behavior without coupling to generated controllers. **MUST load `dotnet-testing`** before writing tests.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The application can resolve a stable authenticated user ID plus non-empty first name, last name, and email; their exact claims/store source and deterministic Maxio reference format are application decisions.
- The configured product family exists and has non-null ID/handle values, and the catalog's subscribable products have non-null handle, price, interval, and interval-unit values. Missing/null contract data is handled as a dependency/catalog configuration failure, never defaulted to a numeric ID or price.
- The task-provided sandbox products do not require a stored payment method. The integration sends `payment_collection_method: remittance` so the signup balance is not collected automatically, and deliberately does not capture or send card/bank data.
- `Maxio:BaseUrl`, when non-empty, already contains the complete intended Production API base address; no suffix, subdomain, or normalization is applied.
- The application persistence layer can enforce a durable unique idempotency reservation in production. The task-noted in-memory mode provides this guarantee only within one running process and loses it on restart.

### Blockers

- None. Subscription-reference uniqueness remains explicitly `UNVERIFIED`, but does not block implementation because application-owned durable serialization plus lookup-before-create/recovery supplies the required double-click safety.
