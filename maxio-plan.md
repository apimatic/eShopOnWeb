# Maxio Advanced Billing integration plan

## 1. Scope & sequence

Add the three additive, JWT-protected application routes requested by the brief:

| Step | Application work | Maxio sequence |
|---|---|---|
| 1 | Register one server-side Maxio client and bind the supplied `Maxio:*` settings. Keep JWT authentication at the PublicApi boundary; the Maxio client uses its own Basic credentials. | Configure `MaxioAdvancedBillingClient` once, then reuse it for all calls. |
| 2 | `GET /api/subscription-plans` | `ListProductFamilies` → select the family whose `ProductFamily.Handle` matches `Maxio:ProductFamilyHandle` → manually page `ListProductsForProductFamily` using the resolved family ID only for that request → map product handles and display/pricing fields into the application response. |
| 3 | `POST /api/subscriptions` | Derive the authenticated application identity and customer data at the application boundary → `ReadCustomerByReference` → if the lookup is a not-found response, `CreateCustomer` with the stable application reference → `FindSubscription` by the stable enrollment reference → if absent, `CreateSubscription` with `ProductHandle`, `CustomerReference`, and `Reference`. |
| 4 | `GET /api/my-subscriptions` | Resolve the customer by the same stable reference with `ReadCustomerByReference` → use its transient `Customer.Id` with `ListCustomerSubscriptions` → map each non-null `SubscriptionResponse.Subscription`. |
| 5 | Apply one exception boundary and tests around the service used by all three routes. | Preserve each operation's Case A/Case B error shape, inspect raw status/body only through documented accessors, and test both response deserialization and outbound wire requests. |

The application must use handles from configuration or the request (`Maxio:ProductFamilyHandle` and product handles returned by discovery), not persisted numeric product or family IDs. Numeric IDs may be used transiently because the SDK signatures require them for customer subscription listing and for the family-to-products call.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members
table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.**

All records below are in `MaxioAdvancedBilling.Models`; operation controllers are in
`MaxioAdvancedBilling.Api`; typed errors are in `MaxioAdvancedBilling.Errors`; raw error and
exception types are in `MaxioAdvancedBilling.Core.ErrorResponse` and
`MaxioAdvancedBilling.Core.Exceptions` respectively.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the SDK client wraps a supplied `HttpClient`, and server/base-URL overrides are nested per server and environment; a lifetime or placement mistake changes connection reuse or the host reached. **MUST load `dotnet-client-initialization`** before registration.
- ⚠ Step 1 (Maxio credentials) — the PublicApi JWT boundary and the SDK's Maxio Basic credential boundary are separate; setting the wrong credential or setting it after client construction causes authorization failure. **MUST load `dotnet-authentication`** before wiring credentials.
- ⚠ Step 2–4 (endpoint calls) — nullable list/search parameters can have no C# default, and positional calls can silently bind the wrong values; use the literal parameter names and `ct:`, especially for the two product-listing calls. **MUST load `dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Step 2–4 (models) — request wrappers, JSON wire names, nullable response envelopes, and `StringEnum<T>`/union handling are not obvious from the application DTOs; a dropped or misnamed field changes the provider request. **MUST load `dotnet-models`** before constructing or mapping SDK models.
- ⚠ Step 3–5 (errors) — every SDK operation is throw-only, and Case A typed errors and Case B raw errors expose different accessors; a typed error's 422 body is not read through `TryGetRawError`. **MUST load `dotnet-error-handling`** before writing the boundary.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 1 and Step 5 (resilience) — retry, timeout, cancellation, pagination, and logging controls have independent scopes, and a non-idempotent POST requires an explicit decision about retry/replay consequences. **MUST load `dotnet-configuration-resilience`** before tuning the client or accepting defaults.
- ⚠ Step 5 (tests) — the reliable SDK seam is the supplied `HttpClient`/fake handler; success, typed-error, raw-error, malformed-body, wire-name, and duplicate-enrollment paths need behavior assertions rather than only invocation assertions. **MUST load `dotnet-testing`** before writing tests.

## 5. Assumptions & Blockers

### Assumptions

- The target integration project is `src/PublicApi/PublicApi.csproj`; the repo context shows existing JWT bearer dependencies and central `net8.0` targeting, but this plan does not assume any uninspected endpoint or claim names.
- The deployment uses the SDK's US Production server by default. `Maxio:Subdomain` is the configured site value; `Maxio:BaseUrl` is an optional Production/US override. If the account is EU-hosted, the application must make the corresponding server-environment choice using the SDK's documented EU option.
- `Maxio:ProductFamilyHandle` identifies the one family intended for public plan discovery. A missing or ambiguous match is treated as configuration failure by the application rather than falling back to a numeric ID.
- The stable customer reference and stable subscription reference are derived consistently from the authenticated application identity; their exact format is application-owned.
- The customer lookup's not-found status is **UNVERIFIED** from the map and scoped source; the implementation must inspect `RawError.StatusCode`, take the not-found branch only for the observed not-found status, and fall back to the generic provider-error mapping for every other status.

### Blockers

- The SDK's `CreateSubscription` signature has no idempotency-key parameter. A read-before-create flow is retry-friendly, but strict exactly-once behavior under concurrent requests requires application-owned coordination for the stable enrollment reference; the SDK alone cannot provide that guarantee.
- The request does not specify how the JWT principal supplies the `CreateCustomer` required `FirstName`, `LastName`, and `Email`. The application must map existing identity data or add an application request contract before the customer-creation path can be complete.
- The `CreateSubscription` Notes state that payment information may be required depending on product configuration. The requested contract supplies no payment-profile/token flow; enrollment is blocked for products that require payment data until that application contract is provided, and raw card handling must not be invented here.
