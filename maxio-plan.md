### 2.1 Client construction, auth, servers (map: `sdk-map.md`)

- Constructor: `new MaxioAdvancedBillingClient(HttpClient httpClient, MaxioAdvancedBillingClientOptions options)`. Provide your own long-lived `HttpClient` (or `IHttpClientFactory`); the SDK does not own it. Also register via `services.AddMaxioAdvancedBillingClient(o => { ... })` (registers the client transient, backed by the default `IHttpClientFactory` client).
- `MaxioAdvancedBillingClientOptions` members: `Environment: ServerEnvironment`, `Retry: RetryOptions`, `Server: ServerOptions`, `BasicAuth: BasicAuthCredentials?`.
- **Auth**: `options.BasicAuth = new BasicAuthCredentials { Username = "<api_key>", Password = "x" }` — literal password `"x"`. Set before constructing the client / inside the `AddMaxioAdvancedBillingClient` callback. Load the API key from configuration, not hardcoded.
- **Environment**: `options.Environment = ServerEnvironment.Us` (default) or `ServerEnvironment.Eu`. `Us` → `https://{site}.chargify.com`; `Eu` → `https://{site}.ebilling.maxio.com`.
- **Subdomain**: `options.Server.Production.Us.Site = "your-subdomain"` (and `.Eu.Site` for EU env).
- **Base-URL override (must win verbatim over subdomain)**: `options.Server.Production.Us.BaseUrl = "https://explicit-host"` (and `.Eu.BaseUrl`). This is a **literal override of the whole templated URL** for that environment/server group — setting it makes `Maxio:BaseUrl` win outright; only set `.Site` when no explicit `BaseUrl` override is configured. Composition-root mapping: `Maxio:Environment` (US/EU) → `options.Environment`; `Maxio:BaseUrl` (if set) → `options.Server.Production.{Us|Eu}.BaseUrl` for the selected environment; else `Maxio:Subdomain` → `options.Server.Production.{Us|Eu}.Site`.
- **Recommendation — use the SDK's generated client directly as the Infrastructure billing client.** There is no separate lower-level "raw HTTP" surface to wrap; `MaxioAdvancedBillingClient` already takes an `HttpClient` you supply, so register it via `services.AddMaxioAdvancedBillingClient(...)` (typed-client-equivalent pattern) and inject `MaxioAdvancedBillingClient` into an Infrastructure adapter class that implements your own `IBillingClient`-style abstraction — do not hand-roll a second HttpClient wrapper underneath it.
- Ebb (events) server group exists only for `SubscriptionComponents` event-ingestion ops (`RecordEvent`, `BulkRecordEvents`, `ActivateEventBasedComponent`) — not used by any UC above.
- Every operation is **throw-only**: `SdkException<TError>` — no `{Operation}Result` no-throw variants exist in this SDK (ignore that section of the companion skills).

### 2.7 Error-handling shape (applies to every call above)

- Every operation throws `SdkException<TError>` — never returns a no-throw result (`{Operation}Result` variants are **absent** across this whole SDK, 0 of 247 operations).
- **Case A** (typed): catch `SdkException<{Operation}Error>` (namespace `MaxioAdvancedBilling.Errors`) and branch over **every** `TryGet…` accessor listed per row above, `TryGetRawError` **last** (it is not a catch-all — a status with a more specific accessor never sets it).
- **Case B** (raw): catch `SdkException<RawError>` (namespace `MaxioAdvancedBilling.Core.ErrorResponse`) and read `ex.Error.StatusCode` / `ex.Error.ReadAsString()` directly — `RawError` has no `TryGet…` accessors at all. Prefer `ReadAsString()` over `ReadAsJson<T>()` unless you know the body is JSON (`ReadAsJson<T>()` throws `JsonException` otherwise).
- 3 `using`s needed for a Case-A catch: `MaxioAdvancedBilling.Core.Exceptions` (`SdkException<T>`), `MaxioAdvancedBilling.Core.ErrorResponse` (`ApiError`, `RawError`), `MaxioAdvancedBilling.Errors` (the `{Operation}Error` type). Case B needs only the first two.
- Connection failures (`HttpRequestException`, `TaskCanceledException`) are **not** covered by `SdkException<T>` — guard every call site (including reads) and convert both exception families to one internal billing-provider exception type at the Infrastructure adapter boundary.

## 3. Trap notes (attach to the steps above)

1. **Product-family id type is inconsistent across operations** — `Products.CreateProduct`, `Components.CreateMeteredComponent` (and the other `Create*Component` ops), and `ProductFamilies.ListProductsForProductFamily` all take `productFamilyId` as **`string`**, while `Components.ArchiveComponent`, `Components.ListComponentsForProductFamily`, and `ProductFamilies.ReadProductFamily`'s `id` take **`int`**. This is literal generated code, not a typo — pass the correct CLR type per operation (Step 0, 1a).
2. **List/search operations have many leading nullable params with no C# default** — call every multi-param list op (`ListProductsForProductFamily`, `ListComponentsForProductFamily`, `ListCustomerSubscriptions` is fine — it's single-param, but `ListUsages`, `ListSubscriptions`, `ListCustomers` are not) with **named arguments**, passing `null` explicitly for skipped filters (Steps 0d, 1a, 2c).
3. **`SubscriptionIdOrReference` / `ComponentIdModel` are AnyOf unions, not plain overloads** — build with `SubscriptionIdOrReference.Int(id)` / `.String(reference)` and `ComponentIdModel.Int(id)` / `.String(handle)`; there is no implicit `int`/`string` → union assignment for a method parameter (only for record properties) (Step 2b).
4. **`ReadComponent`'s handle form needs an explicit `handle:` prefix** — pass `componentId: "handle:my-handle"`, not the bare handle; the bare form only works for `FindComponent` (site-wide, Case B, no 404 typed accessor) (Step 2a).
5. **`CancelSubscription`'s `CancelAtEndOfPeriod`/`ScheduledCancellationAt` require the "Schedule Subscription Cancellation" site feature** per the operation's own doc note — for the end-of-period cancellation UC, prefer the dedicated `InitiateDelayedCancellation` endpoint instead, which the notes do not gate behind that feature (Step 4b).
6. **`ResumeSubscription`'s parameter is a *query* param, not a body** (`calendar_billing['resumption_charge']` ← `calendarBillingResumptionCharge`) — pass `null` for non-calendar-billing subscriptions (Step 4a).
7. **Every enum is `StringEnum<T>`/`IntEnum<T>`, not a C# enum** — construct with the static members shown in this sheet (e.g. `PricingScheme.PerUnit`) or `EnumType.FromValue("wire_value")` for a value not known at compile time; compare with `==` (value equality) (all steps with enum fields).
8. **Request bodies nest an inner resource record** (e.g. `CreateProductFamilyRequest.ProductFamily`, `CreateCustomerRequest.Customer`) — every Create/Update op in this SDK wraps its payload one level deep; read the exact wrapper name from this sheet before writing the object initializer (all Create/Update steps).
9. **`RetryOptions` defaults only retry `GET/HEAD/PUT/OPTIONS`** — none of the mutating calls in this plan (`POST`/`DELETE` migrations, cancellations, usage recording) are retried by default; if you add retry for `PUT`-based ops (`UpdateProduct`, `UpdateComponent`, `UpdateSubscription`, `ReactivateSubscription`, `ResumeSubscription`) confirm they're safe to retry (they are idempotent PUTs) before opting in.
10. **First-run wire verification** — attach a logging `DelegatingHandler` to the shared `HttpClient` for the first live call of each new operation and confirm verb/path/query before trusting a 2xx (path/query values are not type-checked against the route internally).

## 4. Assumptions & Blockers

- **`Proration`'s on/off semantics are not fully specified by the map/source** — the `Proration` record (used on both `SubscriptionProductMigration` and `SubscriptionMigrationPreviewOptions`) carries only `PreservePeriod: bool?`; nothing in the map states whether *presence* of the object (vs. `null`) is what turns proration on, or whether omission still prorates by a site default. **Defensive-coding directive**: for "apply now with proration", pass `Proration = new Proration { PreservePeriod = false }` and read the actual `ProratedAdjustmentInCents`/`ChargeInCents` back from the preview response to confirm a non-zero prorated effect before committing; for "apply at next renewal without proration" use `UpdateSubscription.ProductChangeDelayed` instead (that path's "no proration" behavior *is* explicitly documented). Verify the `Proration`-object semantics against a sandbox call (with the logging handler from Trap #10) before shipping — this is unverified from static source alone.
- **`CreateOrUpdateProduct` has no `Taxable` boolean** — only `TaxCode: string?` is exposed at product creation (the `Taxable` bool only appears on the `Product` *response* record). There is no map-visible lever to force "taxable off" explicitly at creation; leaving `TaxCode` unset relies on the site's default (commonly non-taxable unless a code is set). This is a genuine SDK-surface gap, not an oversight — flag to the product owner if explicit-off enforcement is required (would need a site-level tax configuration check outside this SDK's surface).
- **`CreateOrUpdateProduct` has no setup-fee/initial-charge field** — `InitialChargeInCents` only exists on `CreateProductPricePoint` (a separate price-point endpoint, not in scope per the UC0 description). "No setup fee" is satisfied by simply not creating a custom price point — the auto-generated default price point carries no initial charge.
- **No SDK-level atomic upsert for customers** — "find-or-create keyed by a stable reference" is implemented as `ReadCustomerByReference` (404 → `CreateCustomer`); a race between two concurrent first-time calls for the same reference is possible and will surface as a `422` on `CreateCustomer` (`TryGetCustomerErrorResponse1`) — the retry-then-lookup-again pattern should be implemented by the caller, since the SDK has no built-in idempotency key for this call.
- **"Active subscription" state set for duplicate detection (UC1) is a business decision, not an SDK fact** — the sheet lists all 15 `SubscriptionState` values; which subset (e.g. `Active` + `Trialing`, or also `PastDue`/`Unpaid`) counts as "already subscribed" for eShopOnWeb's purposes is left to product decision, not invented here.
- No blockers found that would stop planning — every capability requested across UC0–UC4 and the client/auth/error-handling questions resolved to a concrete, map-grounded operation, model, or enum.
