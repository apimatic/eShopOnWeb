## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — client/handler lifetime and the ownership of the `HttpClient` used by the SDK affect connection reuse and testability. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (credentials) — Basic credentials must be installed at the correct construction/registration point, and configuration must not disclose the API key. **MUST load `dotnet-authentication`** before wiring credentials.
- ⚠ Steps 2–5 (operations) — list/search signatures have nullable required-to-pass parameters and response envelopes add a model level; positional calls or direct reads from the wrapper misbind or lose data. **MUST load `dotnet-calling-endpoints`** before writing calls.
- ⚠ Steps 2–5 (models) — generated records are immutable, `required` differs from nullable, and string-enum values/JSON names cannot be guessed from ordinary C# enum conventions. **MUST load `dotnet-models`** before constructing or mapping models.
- ⚠ Step 4 (idempotent write) — retry/timeout behavior can determine whether a failed write can be re-sent, which directly affects duplicate-enrollment protection. **MUST load `dotnet-configuration-resilience`** before configuring the client or write retry policy.
- ⚠ Step 6 (error boundary) — typed and raw SDK exceptions have different status/body access paths; error translation must not rely on a generic accessor that is absent for the operation. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 6 (2xx payload drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 6 (non-2xx payload drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 6 (tests) — the SDK client is concrete, so tests must use its documented HTTP-client seam rather than coupling to SDK internals. **MUST load `dotnet-testing`** before writing integration tests.

## 5. Assumptions & Blockers

### Assumptions

- The authenticated application account data can supply nonempty first name, last name, email, and an immutable user identifier; these are required to build `CreateCustomer` and a stable customer reference. **YOUR CALL — not in the map**
- A subscription request identifies the product by handle. The service resolves it exclusively within the configured product family and rejects unknown, archived, missing-handle, or missing-ID products. **YOUR CALL — not in the map**
- A durable application enrollment/idempotency record (unique on immutable user identity plus product handle) and serialization around its remote write will be added. It must survive process restarts in production; the explicitly requested in-memory development mode has the stated restart limitation. **YOUR CALL — not in the map**

### Blockers

- None.
