# Maxio Advanced Billing .NET SDK — eShopOnWeb subscription endpoints plan

## 1. Scope & sequence

Four routes on `src/PublicApi` (JWT-authenticated). All Maxio lookups keyed by **handle/reference strings**, never numeric IDs (seeded numeric IDs are stale-on-purpose). Sequence of work:

1. **Client registration & config** — add `AsadAli.AdvancedBilling.Sdk` to `src/PublicApi`; register the client via `AddMaxioAdvancedBillingClient`; bind a `Maxio:` config section; set Basic credentials, `ServerEnvironment.Us`, and `Server.Production.Us.Site` from the site subdomain (env `MAXIO_SITE_SUBDOMAIN`, e.g. `cp-exp-8`), with an optional `Maxio:BaseUrl` override to redirect to a mock host. Uses **no** Maxio operation.
2. **GET /api/subscription-plans** — `client.ProductFamilies.ListProductsForProductFamily(...)` with the family handle from config (`eshop-subscribe`), plus `client.Sites.ReadSite()` for the display currency. Uses rows: [PF-1], [S-1].
3. **POST /api/subscriptions** — idempotent find-or-create:
   1. resolve the caller's stable Maxio `reference` (opaque ASP.NET user id from the bearer token) and the required customer name/email attributes (see Assumptions A1);
   2. find the customer: `client.Customers.ReadCustomerByReference(reference, ...)` — 404 ⇒ none;
   3. if none, `client.Customers.CreateCustomer(...)`; if that 422s (reference already taken by a racing request), **re-run the lookup** and use the winner;
   4. validate the requested plan handle against the family's products via `ListProductsForProductFamily` (reuse the route-2 helper; 404 = family config broken);
   5. dedupe guard: `client.Customers.ListCustomerSubscriptions(customerId, ...)`, match `Subscription.Product?.Handle == planHandle` with a live state ⇒ return that subscription instead of creating;
   6. `client.Subscriptions.CreateSubscription(...)` with `product_handle` + `customer_reference` only (no payment members — product does not require a card).
   Uses rows: [C-1], [C-2], [C-3], [PF-1], [SU-1].
4. **GET /api/my-subscriptions** — `ReadCustomerByReference` (404 ⇒ empty list), then `ListCustomerSubscriptions(customerId, ...)`; per-subscription enrichment fields come from the nested `Subscription` object. Uses rows: [C-1], [C-3] (+ defensive [SU-2]).
5. **Error boundary + tests** — one exception-mapping layer around the SDK calls (see REQUIRED READING), then tests faking the SDK's `HttpClient` seam.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**

> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

**Idempotency answers (a)/(b) restated for the implementer.** (a) Customer find-or-create is `ReadCustomerByReference(reference)` → 404 → `CreateCustomer` (with the same reference); a 422 on create = a racing request won the reference → re-run the lookup. No list+filter needed. (b) Subscription duplicates are **not prevented server-side** — guard client-side with `ListCustomerSubscriptions(customerId)`, matching `Subscription.Product?.Handle == requestedPlanHandle`; **how "live" a state is decides whether the match counts as "already subscribed"** (state grouping below — YOUR CALL which states block a re-subscribe).

**Money / dates:** all prices are `long?` cents (`price_in_cents`, `product_price_in_cents`) — the display amount is cents ÷ 100, with the currency code from `Site.Currency` (chooser) or `Subscription.Currency` (subscription views); currency is a plain string code, not an enum. "Next billing date" candidates on a subscription (both `DateTimeOffset?`): `current_period_ends_at` = end of the current period, "when the next regularly scheduled attempted charge will occur" (the billing date on a healthy sub) and `next_assessment_at` = when capture will be *tried/retried*; they diverge only after a failed renewal. Pick `CurrentPeriodEndsAt` (fall back to `NextAssessmentAt`) — the two-meaning choice is YOUR CALL.

## 3. Trap notes

Hazards only — each must be resolved by loading the named companion skill, not by this note.

- ⚠ Step 1 (client registration) — the SDK client wraps a long-lived `HttpClient`; registration shape, builder/options, and DI lifetime (reuse via `IHttpClientFactory`) are not visible in the constructor signature. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (auth) — Maxio auth is **HTTP Basic**: `BasicAuth = new BasicAuthCredentials { Username = <api key>, Password = "x" }` — the API key is *not* sent in a header named after the key; the brief's "MAXIO_API_KEY header" assumption must be corrected to "load the API key into `BasicAuthCredentials.Username`". **MUST load `dotnet-authentication`** before setting credentials.
- ⚠ Step 1 (server/base URL) — `Environment` selects only the host family (`https://{site}.chargify.com` US vs `https://{site}.ebilling.maxio.com` EU); subdomain and any mock/dev redirect are separate `Server.Production.Us.Site` / `.Us.BaseUrl` settings, and the retry/timeout options do **not** bound a whole call the way the names suggest. **MUST load `dotnet-configuration-resilience`** before registering or tuning the client.
- ⚠ Steps 2–4 (every call) — several signatures have nullable parameters with **no C# default** (`ListProductsForProductFamily` pre-`page` params, `ReadSubscription`'s `include`); a positional call mis-binds them. Call every operation with named arguments. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 2–4 (models) — every response wraps its payload in a single envelope property (`ProductResponse.Product`, `CustomerResponse.Customer`, `SubscriptionResponse.Subscription` — the last is **nullable**); state/interval/collection-method values are `StringEnum<T>` records, not C# enums; required request members must be set in the initializer. **MUST load `dotnet-models`** before building payloads or mapping responses.
- ⚠ Steps 2–4 (error boundary) — the same SDK exposes **Case A** (typed `SdkException<{Op}Error>` with per-status `TryGet…` accessors) and **Case B** (`SdkException<RawError>`) operations, and there are **no no-throw/"Result" variants** — every operation throws; the catch ladder must be per-operation-shape. **MUST load `dotnet-error-handling`** before writing any `try/catch`.
- ⚠ Error boundary (drifted/malformed **2xx**) — a missing `required` member in a successful body surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Error boundary (drifted **non-2xx**) — a non-2xx body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 3 (subscribe write, resilience) — a **transport** failure (`HttpRequestException`) is retried on every verb, POST included — `POST /subscriptions.json` can execute more than once; retry/status options change which statuses trigger a resend but not this. Since the API has no server-side duplicate protection, a retried POST is a second-subscription risk the boundary must make visible. **MUST load `dotnet-configuration-resilience`** before tuning retries on this route.
- ⚠ Step 3 (plan validation) — product-family addressing in URL params uses the literal `handle:` prefix (`"handle:eshop-subscribe"`); product handles in `Product.Handle` are bare (`eshop-pro`). Do not mix the two forms.
- ⚠ Step 4 (list richness) — whether `ListCustomerSubscriptions` populates the nested `Subscription.Product` on the wire is not guaranteed by the model; guard for `null` and enrich via `ReadSubscription`. (`UNVERIFIED` — only live traffic settles it.)
- ⚠ Step 5 (tests) — the SDK surface is classes over `HttpClient`; the fakeable seam and the assertion approach are the skill's subject, not guessable from signatures. **MUST load `dotnet-testing`** before writing tests.

## 5. Assumptions & Blockers

- **A1 (assumption, needs an app decision before Step 3 compiles clean)** — `CreateCustomer` requires `first_name`, `last_name`, `email` (required members in `Models/CreateCustomer.cs`). The POST /api/subscriptions handler must therefore be able to supply those three from the caller's identity (JWT claims) or an app-side profile, keyed by the same user id used as `reference`. If the eShop bearer token carries no email/full name, Step 3 cannot create a Maxio customer — that is a feature-blocker the app team must resolve with its identity claims; the SDK offers no customer-without-email shape.
- **A2 (assumption)** — The `Maxio:` config section supplies: product-family handle (`eshop-subscribe`), API key, site subdomain (env `MAXIO_SITE_SUBDOMAIN`), and an optional base-URL override. Exact binding keys inside the section are the app team's (`YOUR CALL — not in the map`); the SDK facts are that the key goes to `BasicAuthCredentials.Username`, the subdomain to `Server.Production.Us.Site`, and an override to `Server.Production.Us.BaseUrl`.
- **A3 (assumption, sandbox behavior — `UNVERIFIED`)** — Whether the live sandbox's card-less create of a $299/mo no-trial plan returns immediately with a live state (and does not attempt an immediate $299 capture with no card on file) is only settled by live traffic. The SDK-legal request (SU-1, no payment members) is what the seed catalog asserts works; if live verification shows an immediate-capture attempt instead, the `CreateSubscription.NextBillingAt (next_billing_at): DateTimeOffset?` member is the documented knob to defer capture ("no trial or initial charges will be applied … no payment will be captured at all").
- **A4 (assumption, response richness — `UNVERIFIED`)** — Nested `Subscription.Product` in list/create responses is expected but not guaranteed by the SDK model; the sheet's null-guard + `ReadSubscription` fallback covers it. Not a blocker.
- **A5 (assumption)** — Maxio's US environment host (`{site}.chargify.com`) is correct for the `cp-exp-8` sandbox; if that sandbox is EU-hosted, the only change is `Environment = ServerEnvironment.Eu` (host becomes `{site}.ebilling.maxio.com`). Minor; one config decision.
- **A6 (no blocker)** — Nothing in the map documents a server-side (customer, product) subscription-uniqueness constraint or a duplicate signal on `CreateSubscription`; the client-side [C-3] guard is therefore the mechanism, and a *true concurrent* double-subscribe race (both requests pass the guard before either creates) can still produce two subscriptions. Consequence for the app team: if "never two subscriptions under a double-click" must hold under concurrency, the app must serialize subscribes per user (the SDK provides no atomic check-and-create); a sequential double-click is fully covered by the guard.
