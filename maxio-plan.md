# Maxio recurring subscriptions in eShopOnWeb

## 1. Scope & sequence

1. Register the NuGet client and configuration-backed Maxio options for the Production server after making the PublicApi runtime closure coherent with the SDK’s dependency line. Bind `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, optional `Maxio:BaseUrl`, and the sandbox credential set supplied through the same binding keys.
2. Add the JWT-authenticated `src/PublicApi` routes. The application identity from the validated token drives the customer reference; the route layer and response DTOs are application decisions.
3. Implement `GET /api/subscription-plans` with `client.ProductFamilies.ListProductsForProductFamily(...)`, using the configured product-family handle and manual page traversal.
4. Implement the shared customer resolution used by `POST /api/subscriptions` and `GET /api/my-subscriptions`: `ReadCustomerByReference`, then `CreateCustomer` on a documented 404, then re-lookup after a competing create.
5. Implement `POST /api/subscriptions`: reserve an application idempotency record, resolve the Maxio customer, preflight with `FindSubscription` by deterministic subscription reference, then call `CreateSubscription` with product and customer handles/references. Reconcile an uncertain or duplicate result by looking up that reference.
6. Implement `GET /api/my-subscriptions` with `ListCustomerSubscriptions` and project each `SubscriptionResponse.Subscription` into the public plan/price/state/next-billing-date DTO.
7. Add boundary handling and tests for typed errors, raw errors, malformed 2xx/non-2xx JSON, pagination, customer races, duplicate requests, cancellation, and configuration failures.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal C# identifier. The cancellation-token parameter really is named `ct`: in named arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

All operation calls are async, throw-only, and use `System.Threading.CancellationToken`. There are no generated `…Result`/`ApiResult` no-throw variants.

## 3. Trap notes

⚠ Step 1 (client registration) — an incorrectly owned or rebuilt `HttpClient` pipeline can change connection lifetime and request behavior. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credentials supplied under the wrong option/property or after client construction can turn a valid call into an authentication failure. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Step 2 (calling endpoints) — the generated nullable parameters without C# defaults must be passed explicitly, and positional calls can bind filters to the wrong parameter. **MUST load `dotnet-calling-endpoints`** before writing the first SDK call.

⚠ Step 2 (models) — generated JSON wire names, required members, `StringEnum<T>` values, and union accessors are not interchangeable with application property names or C# enums. **MUST load `dotnet-models`** before constructing or projecting SDK models.

⚠ Step 3 (error boundary) — Case A typed errors and Case B raw errors reach different generic catches, and typed errors do not become a catch-all raw error. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 1/5 (resilience and pagination) — retry, timeout, base-URL, and page-loop settings can alter write safety, cancellation behavior, or result completeness. **MUST load `dotnet-configuration-resilience`** before tuning them.

⚠ Step 7 (testing) — stubbing the wrong seam can test SDK internals instead of the PublicApi integration behavior. **MUST load `dotnet-testing`** before writing tests.

⚠ A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.
