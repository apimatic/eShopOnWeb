## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## Trap notes

⚠ Step 3 (client registration) — `HttpClient` ownership and SDK-wrapper lifetime can cause socket churn or stale configuration if registered at the wrong seam. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 3 (authentication) — credential timing, configuration sourcing, and 401/403 diagnosis affect whether Basic auth is actually attached and whether secrets leak. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 4–7 (calls) — optional parameters without C# defaults and the literal `ct` name make positional or misnamed calls bind incorrectly. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 4–7 (models) — generated immutable records, nullable response envelopes, JSON wire names, and `StringEnum<T>` mapping can silently corrupt request/DTO mapping. **MUST load `dotnet-models`** before constructing or reading models.

⚠ Steps 3 and 6 (resilience/idempotency) — retry/timeout configuration may re-send or prolong a failed subscription write, making an ambiguous outcome a duplicate-provider-state risk. **MUST load `dotnet-configuration-resilience`** before client tuning or create/reconciliation logic.

⚠ Step 8 (error boundary) — typed Case A and raw Case B exceptions expose status/body through different paths; treating them uniformly loses actionable errors. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Step 8 (2xx JSON drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (non-2xx JSON drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 8 (tests) — mocking generated controllers/types couples tests to SDK internals and misses serialization, auth, cancellation and error-shape behavior. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- **BLOCKER — provider-side exactly-once is not established.** The SDK contract has no idempotency-key surface, and neither its map nor pinned source says subscription `Reference` is unique. Local transactional uniqueness will stop concurrent/double-click application requests, and `FindSubscription` supports reconciliation, but implementation must not claim absolute duplicate prevention after an ambiguous POST until an opt-in `cp-exp-1` sandbox contract test proves repeated-reference behavior or Maxio provides a written guarantee. Do not work around this with numeric IDs or blind retries.
- A user may have at most one eShop-created subscription per product handle. If legitimate repeated purchases of the same plan are required, the product owner must define an explicit client idempotency key/order identifier before the persistence key and subscription reference can be finalized.
- The authenticated eShop user record supplies non-empty first name, last name and email, because `CreateCustomer` requires all three. If it does not, return a profile-completion/validation response; do not fabricate values.
- `MAXIO_ENVIRONMENT` contains the hosting region (`US` in the current environment), not a sandbox marker. Store it in top-level user-secret `MaxioEnvironment`, validate exactly `US`/`EU`, and select `ServerEnvironment.Us` plus `Server.Production.Us` or `ServerEnvironment.Eu` plus `Server.Production.Eu` at runtime; do not hardcode the region. The `cp-exp-1` site may be sandboxed independently of this hosting-region choice.
- `Maxio:ProductFamilyHandle` is `eshop-subscribe`; the default POST target is stable product handle `eshop-pro`; `basic-plan` is also returned/allowed. The seeded metered component handle `api-call` is intentionally unused because no usage endpoint is in this scope.
- Products are configured not to require payment, so creation omits all payment-profile/card/bank members and leaves `PaymentCollectionMethod` unset. If sandbox returns a payment-required 422, stop and correct Maxio product configuration; do not add raw card handling.
- The public API's `nextBillingAt` is sourced from generated `Subscription.NextAssessmentAt (next_assessment_at)`; the generated response has no `NextBillingAt` property. It remains nullable.
