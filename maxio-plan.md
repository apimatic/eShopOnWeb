# Maxio subscription billing plan and CONTRACT SHEET

## Scope & sequence

| Step | Implementation order | Maxio SDK operations |
|---|---|---|
| 1 | Add NuGet package `AsadAli.AdvancedBilling.Sdk` version `1.0.2` (the version mapped from source tag `v1.0.2`). Bind one validated `MaxioOptions` object from `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; reject missing required values at startup and never log the API key. Register one long-lived `HttpClient` pipeline and construct the SDK client through DI. | Client construction only. |
| 2 | Implement an application-owned `IMaxioBillingGateway` adapter. Keep SDK types inside this adapter and return application DTOs/results so endpoints and unit tests do not depend on generated SDK records or exceptions. | All operations below. |
| 3 | Resolve the configured product family by stable handle: call `ListProductFamilies`, require exactly one non-archived inner family whose `Handle` ordinally equals the configured handle, require its nullable `Id`, then call every page of `ListProductsForProductFamily` with that numeric ID rendered invariantly. Exclude archived/incomplete products and map handle, name, description, price, interval and interval unit. Never persist or configure seeded numeric IDs. | `ProductFamilies.ListProductFamilies`; `ProductFamilies.ListProductsForProductFamily`. |
| 4 | On subscription creation, validate the requested product handle with `Products.ReadProductByHandle`; require its inner product to be unarchived and its inner `ProductFamily.Handle` to equal the configured family handle. This prevents subscribing to an arbitrary product on the site. | `Products.ReadProductByHandle`. |
| 5 | Ensure a customer for the JWT subject. Use the stable eShop user ID as the Maxio customer `reference`; first call `ReadCustomerByReference`. On 404, call `CreateCustomer` with the required eShop profile name/email plus that reference. Maxio documents customer reference uniqueness, so on create 422 (the concurrent-create race), re-read by reference and accept only the recovered exact customer; do not blindly issue another create. | `Customers.ReadCustomerByReference`; `Customers.CreateCustomer`. |
| 6 | Coordinate subscription idempotency before the remote write with a durable application row having unique `(UserId, ProductHandle)` and a unique, stable `MaxioSubscriptionReference`, plus state (`Pending`, `Created`, `Failed`), Maxio IDs and a concurrency token. One transaction/claim owns the write; concurrent double-clicks reload/wait on the same row and never become a second writer. The owner calls `FindSubscription(reference)` before `CreateSubscription`. If found, reconcile the row. If 404, create with `ProductHandle`, `CustomerReference`, and `Reference`. After any ambiguous outcome, call `FindSubscription` and reconcile; never intentionally issue another create until absence is known. Treat the local row only as coordination/recovery data: Maxio remains the billing system of record. | `Subscriptions.FindSubscription`; `Subscriptions.CreateSubscription`. |
| 7 | Map the create response back to plan handle/name, `ProductPriceInCents` (falling back to inner product `PriceInCents` only when the subscription field is absent), state, currency, and next billing date (`NextAssessmentAt`; if absent expose null rather than inventing a date). Require a non-null inner subscription and ID. | Response from `Subscriptions.CreateSubscription` or `Subscriptions.FindSubscription`. |
| 8 | For `GET /api/my-subscriptions`, lookup the customer by the JWT subject reference. A lookup 404 returns an empty collection without creating a customer. Otherwise call `ListCustomerSubscriptions(customerId)`, require the customer ID, and map live Maxio responses; local mappings are not the read authority. | `Customers.ReadCustomerByReference`; `Customers.ListCustomerSubscriptions`. |
| 9 | Put one exception-translation boundary around the gateway, preserve cancellation, classify Case A/Case B errors, and expose safe application errors. Do not leak provider payloads, credentials, or PII. | Every operation. |
| 10 | Test the adapter with a fake `HttpMessageHandler` injected through the SDK's `HttpClient` constructor; test endpoint/application code against `IMaxioBillingGateway`. Keep live sandbox tests explicit/opt-in and use only environment/user-secret configuration. | Every operation and error branch below. |

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency boundary and capability trust

| Fact / directive | Trust status | Evidence |
|---|---|---|
| Maxio explicitly allows only one customer per supplied `reference`; lookup by reference returns one customer. The lookup-before-create plus 422/re-read race recovery is a grounded customer idempotency strategy. | Verified by map. | `operations/Customers.md` |
| Subscriptions expose request `Reference` and `FindSubscription(reference)`, so a persisted stable reference supports preflight and recovery. The map does **not** state that subscription references are unique, unlike its explicit customer uniqueness statement. | **UNVERIFIED server-side uniqueness.** Use reference lookup only as reconciliation, not as proof that Maxio will reject a concurrent duplicate. | `operations/Subscriptions.md`; `records-2-Cr-Ne.md` |
| Application uniqueness/claiming prevents two endpoint requests (including a double-click) from intentionally issuing two create calls. The SDK retry layer can resend a POST after a transport failure, and the mapped SDK has no idempotency-key parameter or no-retry operation variant. | **Plugin capability gap for a hard exactly-once guarantee under ambiguous transport failure.** Never launch a second application-level create after ambiguity; reconcile and surface an indeterminate/in-progress result. A hard guarantee requires Maxio to document/enforce subscription-reference uniqueness or expose an idempotency primitive. | `sdk-map.md`; `operations/Subscriptions.md`; `dotnet-configuration-resilience` hazard |

### HTTP/API result mapping

| Endpoint | Application behavior |
|---|---|
| `GET /api/subscription-plans` | JWT required. Return dynamically resolved active products from the configured family. Provider/configuration failures become a safe 502/503-style problem; configured family missing is a configuration/catalog error, not an empty success. |
| `POST /api/subscriptions` | JWT required. Body contains only the selected `productHandle`; identity/profile come from the authenticated principal/application user store. Return 201 for the owner-created subscription and 200 for an idempotent replay/reconciliation; return the same confirmation shape. Reject a handle outside the configured family. A claimed write still in progress/indeterminate must not trigger another POST. |
| `GET /api/my-subscriptions` | JWT required. A Maxio customer 404 returns 200 with an empty list. Otherwise return live Maxio subscriptions with plan, price, state and nullable next billing date. |

## Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership and DI lifetimes can cause socket churn or stale handler behavior if the generated wrapper and transport are registered with the wrong lifetimes. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential timing, auth-manager shape, and secret rotation determine whether calls authenticate and whether secrets leak into configuration/logging. **MUST load `dotnet-authentication`** before wiring Basic auth.

⚠ Steps 3–8 (endpoint calls) — optional parameters without C# defaults can silently mis-bind when called positionally, and the cancellation parameter's literal name is `ct`. **MUST load `dotnet-calling-endpoints`** before writing the first SDK call.

⚠ Steps 3–8 (model mapping) — required members, nullable response inners, JSON wire names, and `StringEnum<T>` value extraction can otherwise produce compile failures or incorrect DTO values. **MUST load `dotnet-models`** before constructing or mapping SDK records.

⚠ Steps 1 and 6 (resilience) — retry/timeout settings affect whether a failed subscription write can be re-sent and whether a caller's time budget is actually bounded; this directly affects duplicate risk and recovery. **MUST load `dotnet-configuration-resilience`** before configuring the client or write recovery.

⚠ Step 9 (error boundary) — Case A accessors and Case B raw payloads require different catch/read paths, and fallback payloads must be handled without leaking provider details. **MUST load `dotnet-error-handling`** before writing the boundary.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 10 (tests) — faking generated controller types couples tests to internals and misses serialization, paths and error construction; the appropriate seam changes by test layer. **MUST load `dotnet-testing`** before writing tests.

## Assumptions & Blockers

- Assumption: the JWT subject is the stable eShop user ID and the application can load non-empty first name, last name and email for Maxio's required customer-create fields; these values are not accepted from the request body.
- Assumption: `Maxio:Subdomain` selects a sandbox/test-mode Maxio site. The SDK has only US/EU hosting environments, not a separate sandbox enum.
- Configuration ambiguity: the mandated `Maxio:` keys omit a hosting-region key although `MAXIO_ENVIRONMENT` is supplied. With only those keys, use `ServerEnvironment.Us` for subdomain-derived URLs and let `Maxio:BaseUrl` override the Production URL verbatim. Supporting derived EU URLs requires an authorized region key or an explicit EU BaseUrl.
- **Blocker / capability gap:** the SDK map exposes no idempotency-key parameter and does not document subscription-reference uniqueness, while the SDK transport policy may retry POST after transport failure. Persisted claiming guarantees that a double-click does not intentionally launch two writes, but the plugin cannot ground a hard exactly-once guarantee if the first POST has an ambiguous transport outcome. This remains `UNVERIFIED` until Maxio documents/enforces uniqueness or exposes a server-side idempotency primitive.
