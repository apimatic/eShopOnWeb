# Maxio recurring-subscription integration plan

## 1. Scope & sequence

| Step | Maxio operation(s) | Contract-driven implementation outcome |
|---|---|---|
| 1. Configure client | none | Bind only `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle`, and optional `Maxio:BaseUrl`; create one SDK client over an `IHttpClientFactory`-owned `HttpClient`; use Basic auth. Never persist a credential value in the repository. |
| 2. Resolve configured catalog | `ProductFamilies.ListProductFamilies` | Enumerate families and require one exact `ProductFamily.Handle` match to `Maxio:ProductFamilyHandle`. Do not use seeded numeric IDs. The generated `ReadProductFamily(int id, ...)` cannot accept the Notes-documented `handle:...` form, so listing and exact matching is the map-supported handle path. |
| 3. List plans | `ProductFamilies.ListProductsForProductFamily` | Pass the dynamically resolved family ID as a string, page until exhausted, request `includeArchived: false`, and expose each non-archived product's stable handle, name, description, default price, recurrence, and payment-method requirement. |
| 4. Validate selected plan | `Products.ReadProductByHandle` | Resolve the caller-supplied stable product handle, then require `Product.ProductFamily.Handle` to equal the configured family handle and `ArchivedAt` to be null. Reject products requiring payment details because this flow intentionally sends none. |
| 5. Ensure customer | `Customers.ReadCustomerByReference`, then when absent `Customers.CreateCustomer`, followed by `ReadCustomerByReference` on a create conflict/race | Use the authenticated application's immutable user ID as the Maxio customer `Reference`. Maxio documents customer reference uniqueness. Supply the required first name, last name, and email from the application's user profile. |
| 6. Reserve one application enrollment | none | Before the provider write, atomically reserve a unique application key such as `(UserId, ProductHandle)` with a durable `Pending/Succeeded/Failed-or-Unknown` state. Concurrent callers observe the same reservation and do not both call Maxio. This is application-owned concurrency and persistence. |
| 7. Reconcile before create | `Customers.ListCustomerSubscriptions` | Search the customer's subscriptions for the deterministic `Subscription.Reference` chosen by the application and the selected product handle. If one exists, persist/return it instead of creating. This is reconciliation, not provider-enforced uniqueness. |
| 8. Create enrollment | `Subscriptions.CreateSubscription` | Send `ProductHandle`, `CustomerReference`, and a deterministic correlation `Reference`. Omit all payment profile/card/bank fields only after Step 4 confirms the selected seeded/configured product does not require them. Do not send numeric product/customer IDs. |
| 9. Confirm enrollment | `Subscriptions.ReadSubscription` | Read by the returned subscription ID and map provider ID, product handle/name, price, state, recurrence, reference, and both provider date candidates. Use the best-effort next-billing projection specified below. |
| 10. List my enrollments | `Customers.ReadCustomerByReference`, `Customers.ListCustomerSubscriptions` | A missing customer maps to an empty list. Otherwise map all returned subscriptions for the authenticated user; never accept a customer ID/reference from the HTTP caller. |
| 11. Error boundary and tests | all operations above | Translate typed and raw provider failures at one integration boundary, preserve cancellation, avoid secret/body logging, and test through the SDK's `HttpClient` seam plus application persistence/concurrency seams. |

The intended PublicApi routes, JWT identity extraction, local entity/repository layout, HTTP status policy, and response DTO names are application decisions and are not SDK contract facts.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the SDK wrapper's DI lifetime are different decisions; the wrong lifetime can exhaust sockets or discard handler policy state. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — credential timing, rotation, and configuration sourcing are not expressed by the credential record's shape. **MUST load `dotnet-authentication`** before assigning Basic credentials.
- ⚠ Steps 2–10 (calling operations) — optional nullable parameters without defaults must still be passed, and positional calls can silently bind the wrong filters. **MUST load `dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Steps 3–10 (models) — required initializers, nullable response envelopes, `StringEnum` values, JSON wire names, and dropped unmodeled fields can make apparently valid mappings wrong. **MUST load `dotnet-models`** before constructing or projecting models.
- ⚠ Steps 1 and 6–9 (resilience/idempotency) — determine whether and when a failed write can be sent again, what timeout is actually bounded, how cancellation interacts with retries, and what the application must do for ambiguous POST outcomes. **MUST load `dotnet-configuration-resilience`** before client registration or the create workflow.
- ⚠ Step 11 (error boundary) — typed Case A and raw Case B exceptions have different extraction paths; a catch ladder that assumes every error is typed or that raw fallback always exists loses provider detail. **MUST load `dotnet-error-handling`** before writing any catch block.
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 11 (tests) — the stable seam is transport/application abstraction, not generated controllers or model implementation details; otherwise package regeneration makes tests brittle. **MUST load `dotnet-testing`** before writing tests.

## 3. Assumptions & Blockers

### Assumptions

- The configured site is US-hosted when `Maxio:BaseUrl` is absent. A different host/region is supplied through the task-mandated verbatim base-URL override because no `Maxio:Environment` binding key was authorized.
- The authenticated application user has an immutable ID plus usable first name, last name, and email; these are required SDK request members for separate customer creation.
- The selected catalog products intentionally require no payment method. The integration rejects a dynamically discovered plan when `RequireCreditCard == true` rather than inventing card/3DS handling outside this scope.
- One application user may have at most one enrollment per product handle. The deterministic correlation/reference and local uniqueness key follow that interpretation of “a double-click never creates two subscriptions.”
- The HTTP projection may expose a nullable best-effort `nextBillingDate` from `NextAssessmentAt ?? CurrentPeriodEndsAt`; the map does not define a literal next-billing field, so this mapping is `UNVERIFIED` and must remain null-safe.

### Blockers

- **Genuine plugin capability gap — unconditional subscription exactly-once creation cannot be guaranteed.** The complete SDK map exposes `CreateSubscription.Reference` and `Subscription.Reference`, but it documents no uniqueness guarantee for that value, no provider idempotency-key parameter/header on `CreateSubscription`, and no atomic create-or-return or lookup-by-subscription-reference operation. `ListCustomerSubscriptions` permits best-effort pre/post reconciliation, and an application database reservation collapses ordinary concurrent double-clicks, but neither can prove that an ambiguous provider write produced exactly one subscription. Under the user's rule “if the plugin does not expose a capability you need, STOP,” implementation must not claim the absolute “never creates two subscriptions” guarantee until Maxio/plugin contract support for provider-enforced subscription idempotency is available or the requirement is explicitly narrowed to application-level concurrent-request deduplication.
