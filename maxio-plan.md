## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (registration) — the generated extension's client lifetime and unnamed `HttpClient` choice affect handler isolation and connection freshness. **MUST load `dotnet-client-initialization`** before registering the client.
- ⚠ Step 1 (authentication) — the Basic credential property, credential initialization order, and secret lifecycle determine whether every request is authenticated correctly. **MUST load `dotnet-authentication`** before setting credentials.
- ⚠ Steps 2–6 (calls) — nullable parameters without C# defaults and the literal `ct` name make reconstructed positional calls mis-bind or fail to compile. **MUST load `dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Steps 2–6 (models) — nullable response envelopes, init-only/required request members, wire-name differences, and forward-compatible string-enum reads affect both serialization and API output. **MUST load `dotnet-models`** before constructing or projecting SDK models.
- ⚠ Steps 2–7 (error boundary) — Case A and Case B exceptions expose status/body through different paths, and omitting a typed accessor silently loses the provider rejection. **MUST load `dotnet-error-handling`** before writing any catch ladder.
- ⚠ Steps 1 and 5 (resilience/idempotency) — retry eligibility, total call bounds, and whether a failed `CreateCustomer`/`CreateSubscription` can be sent more than once directly affect the no-duplicate guarantee. **MUST load `dotnet-configuration-resilience`** before configuring the client or write path.
- ⚠ Step 7 (tests) — the SDK test seam and the difference between status faults and transport faults determine whether duplicate-write tests prove the intended guarantee. **MUST load `dotnet-testing`** before integration tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The configured sandbox is US-hosted. The SDK's `ServerEnvironment` selects US versus EU hosting; it has no sandbox/production constant. A supplied `Maxio:BaseUrl` remains the explicit host override.
- The authenticated application profile can provide nonempty first name, last name, and email values required by `MaxioAdvancedBilling.Models.CreateCustomer`; fallback policy for incomplete profiles is an application decision.
- The configured product-family handle and posted product handles are compared exactly, and numeric Maxio IDs are treated only as runtime-discovered/persisted values, never configuration.
- The seeded target products require no payment instrument, but live sandbox traffic verified that an omitted collection method still selects immediate automatic collection and returns 422 without a card. `CollectionMethod.Remittance` is therefore supplied explicitly for this current Relationship Invoicing site.
- Customer `reference` uniqueness is provider-documented in `CreateCustomer` Notes. Subscription `Reference` is searchable, but neither its model nor `CreateSubscription`/`FindSubscription` Notes state uniqueness; provider enforcement is **UNVERIFIED**, so the no-double-click guarantee must not rely on it.
- Persistence, a per-logical-subscription concurrency claim/unique constraint, claim expiry/recovery, and HTTP response/error DTOs are application-owned decisions (`YOUR CALL — not in the map`).

### Blockers

- None. The SDK map/source resolves every required call. The unverified subscription-reference uniqueness does not block implementation because application-level serialization plus post-failure reconciliation can be implemented without assuming provider uniqueness.
