## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

All model records below are immutable records with `init`-only properties. `required` means the object initializer must set the member; nullable properties are optional. Response envelopes must be unwrapped through their named inner property.

## 3. Trap notes

⚠ Step 0 (client registration) — client and handler lifetime mistakes can exhaust sockets or bypass the application's managed HTTP pipeline. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 0 (authentication) — credential timing/rotation and the generated credentials property shape affect every request. **MUST load `dotnet-authentication`** before supplying credentials.

⚠ Steps 1–4 (operation calls) — many nullable parameters have no C# defaults, positional calls can silently mis-bind, and response envelopes add an inner layer. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 1–4 (models) — required initializers, nullable response members, string-enum value extraction, and wire-name/C#-name differences can break payloads or projections. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 2–4 (error boundary) — Case-A typed errors and Case-B raw errors require different catch/accessor paths, and typed fallback bodies are not interchangeable with status-specific payloads. **MUST load `dotnet-error-handling`** before writing any catch ladder.

⚠ Step 3 (write idempotency) — determine whether and when a failed `CreateCustomer` or `CreateSubscription` attempt can be re-sent by the SDK; duplicate remote effects are the consequence. **MUST load `dotnet-configuration-resilience`** before configuring the client or relying on application idempotency.

⚠ Steps 0–4 (timeouts, base URL, pagination, diagnostics) — SDK timeout/retry settings, the registered `HttpClient` timeout, server override selection, page traversal, and safe observability are separate concerns. **MUST load `dotnet-configuration-resilience`** before registration/tuning.

⚠ Step 5 (tests) — the generated concrete client surface is not the correct fake seam, and SDK-internal assertions make tests brittle. **MUST load `dotnet-testing`** before writing integration-layer tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- **Assumption — no payment capture:** the task's sandbox premise is authoritative that signup must work without a payment method. Live typed 422 evidence showed that omitting `payment_collection_method` still attempted to collect the signup balance. The corrected request therefore omits all payment-profile/card/bank fields but explicitly chooses the architecture-valid non-automatic collection value: `Remittance` for Relationship Invoicing and `Invoice` for legacy Statements.
- **Assumption — application identity material:** the application can resolve a stable immutable user ID plus values for Maxio's required customer first name, last name, and email without trusting the subscribe request body. The exact claim/store mapping is `YOUR CALL — not in the map`.
- **Assumption — stated idempotency scope:** ordinary repeated/concurrent HTTP requests are serialized by durable application state and a per-key lock in the single-process in-memory development host, with deterministic Maxio references used for reconciliation.
- **Blocker for an absolute remote exactly-once claim:** the SDK exposes no idempotency-key/header parameter, the map does not state that subscription `reference` is unique, and only live/provider confirmation could establish whether duplicate creates with the same reference are rejected. The prescribed defensive state machine prevents deliberate duplicate posts and reconciles ambiguous results, but the available Maxio contract cannot prove that an internally retried/ambiguous `CreateSubscription` never produces two remote subscriptions. This limitation must be reported rather than represented as a provider-backed guarantee.
