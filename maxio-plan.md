## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — client/`HttpClient` ownership and lifetime choices can exhaust sockets or bypass the intended handler pipeline. **MUST load `dotnet-client-initialization`** before registering the client.

⚠ Step 1 (authentication) — credential timing and the Basic-auth manager shape determine whether every call is authenticated. **MUST load `dotnet-authentication`** before wiring `Maxio:ApiKey`.

⚠ Steps 2–7 (calls) — optional SDK parameters without C# defaults can silently mis-bind when positional calls are used, and cancellation must reach `ct`. **MUST load `dotnet-calling-endpoints`** before writing the first operation call.

⚠ Steps 2–7 (models) — required initializers, nullable response envelopes, string-backed enums and unknown enum values can turn plausible mapping code into compile errors or null dereferences. **MUST load `dotnet-models`** before constructing or mapping SDK records.

⚠ Steps 2 and 7 (pagination) — the SDK returns one page and does not aggregate list operations, so an incomplete loop silently hides catalog data. **MUST load `dotnet-configuration-resilience`** before implementing pagination.

⚠ Steps 4–6 (write idempotency) — retry triggers and ambiguous transport outcomes determine whether a failed write can be sent again; this directly affects the durable claim/reconciliation design. **MUST load `dotnet-configuration-resilience`** before configuring the client or finalizing write recovery.

⚠ Step 1 (timeouts) — SDK retry/timeout settings and caller cancellation bound different parts of a call; a mistaken boundary can leave requests running longer than the HTTP contract. **MUST load `dotnet-configuration-resilience`** before setting resilience options.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a
  `JsonException` from deserialization, **not** as an `SdkException` — so an
  SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape
  throws `JsonException` *while the error object is being constructed*, so the `JsonException`
  **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that
  maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage,
  and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Steps 5–8 (error translation) — Case A typed errors and Case B raw errors require different catch shapes, and provider payloads must not leak through the public API. **MUST load `dotnet-error-handling`** before implementing endpoint error mapping.

⚠ Step 9 (tests) — faking generated controllers binds tests to SDK internals and misses serialization/error behavior. **MUST load `dotnet-testing`** before choosing the test seam.

## 5. Assumptions & Blockers

### Assumptions

- A shopper may own at most one subscription for a given product handle. Without that rule or a caller-supplied idempotency key, the server cannot distinguish a double-click from an intentional second subscription to the same plan. `YOUR CALL — not in the map`
- The authenticated application identity can resolve stable user ID, first name, last name and email; the latter three are required by `MaxioAdvancedBilling.Models.CreateCustomer`. `YOUR CALL — not in the map`
- The configured site is US-hosted. The SDK's `ServerEnvironment` distinguishes US from EU hosting, not sandbox from production, and the mandated configuration keys include no EU selector. `sdk-map.md`
- This flow supports products that do not require a payment profile. Products with `RequireCreditCard == true` are excluded/rejected because card capture and 3DS are outside the requested endpoints. `records-3-Of-Su.md`
- Maxio remains the billing system of record; local persistence is a concurrency/audit/reconciliation aid, and `GET /api/my-subscriptions` reads current Maxio state. `YOUR CALL — not in the map`

### Blockers / bounded uncertainties

- **UNVERIFIED:** Neither the SDK map nor the map-named `CreateSubscription` model source says that a subscription `Reference` is unique, although `FindSubscription` looks one up by reference. Do not claim provider-enforced subscription idempotency. The application-side unique write claim guarantees the double-click case; deterministic reference lookup provides reconciliation. Strict exactly-once creation after an unknowable network outcome cannot be proven from this SDK contract alone and must surface as an ambiguous/pending state for reconciliation rather than blindly issuing a new create.
- No planning blocker prevents implementation of the requested sandbox hero flow under the assumptions above.
