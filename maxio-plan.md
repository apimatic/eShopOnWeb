# Maxio subscription billing — plan

## 1. Scope & sequence

| Step | Work | Maxio operation(s) |
|---|---|---|
| 1 | Add the SDK package and a PublicApi-only, validated `Maxio` options binding. Construct the SDK client through DI, use Basic credentials, pin the production server group to the configured site, and use the optional base-URL override verbatim. | client construction only |
| 2 | Add an authenticated subscription application boundary. Resolve caller identity exclusively from the JWT claims, derive a stable Maxio customer reference from the immutable application user id, and use that reference to reconcile any locally persisted external id. | `ReadCustomerByReference`, `CreateCustomer` |
| 3 | Resolve the configured product family by **handle** on every catalog refresh; list only that family’s non-archived products and expose plan handle, display name, description, price, cadence, and card requirement at `GET /api/subscription-plans`. Never use the supplied numeric seed IDs. | `ListProductFamilies`, `ListProductsForProductFamily` |
| 4 | Add `POST /api/subscriptions`. Accept only a plan handle, resolve it from Step 3’s family-scoped catalog, ensure the caller’s Maxio customer, then create or return the stable referenced subscription. Return the provider-confirmed id, plan, price, state, and next assessment date. | `FindSubscription`, `CreateSubscription` (plus Steps 2–3 calls) |
| 5 | Add `GET /api/my-subscriptions`. Resolve the caller’s customer by stable reference and list its subscriptions; map each provider response into the same account DTO. | `ReadCustomerByReference`, `ListCustomerSubscriptions` |
| 6 | Make repeated writes safe: use a durable application uniqueness boundary for `(user id, plan handle)` plus a per-key in-process gate; before every create and after any ambiguous create outcome, call `FindSubscription` using the deterministic subscription reference. Customer creation follows the same lookup/create/re-read pattern around its provider-enforced unique reference. | `ReadCustomerByReference`, `CreateCustomer`, `FindSubscription`, `CreateSubscription` |
| 7 | Add focused integration-layer tests at the HTTP seam and configuration validation tests; build, test, and live-verify with the sandbox. | all above, via the `HttpClient` seam |

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — SDK client/`HttpClient` ownership and lifetime must preserve the test seam and avoid rebuilding handlers per request. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — Basic credential setup must occur in the SDK options path and cannot leak secrets through source-controlled configuration. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 2–5 (endpoint calls) — list/search signatures require explicit nullable no-default arguments; positional arguments can silently bind the wrong query values. **MUST load `dotnet-calling-endpoints`** before writing calls.

⚠ Steps 2–5 (models) — required response/request members, nullable envelopes, `StringEnum<T>`, and JSON wire names must be handled without assuming ordinary C# enums or non-null nested payloads. **MUST load `dotnet-models`** before mapping or constructing SDK models.

⚠ Step 6 (write retry) — the retry/timeout configuration’s treatment of an interrupted write determines whether the same provider-side subscription can be re-sent. **MUST load `dotnet-configuration-resilience`** before tuning client resilience.

⚠ Steps 2–6 (provider errors) — Case A typed errors and Case B raw errors expose different safe status/body access paths; a catch ladder that assumes one shape loses deterministic rejection information. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Steps 2–6 (2xx schema drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Steps 2–6 (non-2xx schema drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 (tests) — faking SDK controller internals instead of the `HttpClient` seam makes tests depend on generated implementation details rather than observable error and idempotency behaviour. **MUST load `dotnet-testing`** before tests.

## 5. Assumptions & Blockers

| Type | Item |
|---|---|
| Assumption | The JWT identity supplies (or the application can safely derive) an immutable user id plus a usable email and non-empty first/last-name strings, because `CreateCustomer` requires `FirstName`, `LastName`, and `Email`. Identity-claim selection is application-owned. |
| Assumption | The chosen application subscription policy is one stable provider subscription per `(user id, plan handle)`; a request for that pair returns the existing referenced subscription rather than creating a second one. This is the double-click policy. |
| UNVERIFIED | The map documents `FindSubscription` by reference and `CreateSubscription.Reference`, but does not document that a subscription reference is unique or atomically idempotent. Sandbox verification must prove the lookup/create/re-read behavior for the configured site. |
| Blocker | Live `CreateSubscription` returned 422 `No payment method was on file for the $299.00 balance` for the stated seed. The SDK source identifies `PaymentCollectionMethod`, but does not establish that any collection-method value waives payment validation or identify the site’s billing architecture. Immediate cardless creation with the requested active-billing semantics is blocked until the selected architecture/policy (`Remittance` for current Relationship Invoicing or `Invoice` for legacy Statements) is proven accepted by sandbox traffic or the catalog/site setup is corrected. |
