## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership and the SDK wrapper lifetime can create socket/lifetime failures if wired at the wrong seam. **MUST load `dotnet-client-initialization`** before registering the client.
- ⚠ Step 1 (authentication) — credentials must be present at client construction and secret/configuration handling affects every request. **MUST load `dotnet-authentication`** before wiring credentials.
- ⚠ Steps 2–9 (endpoint calls) — generated methods have many nullable parameters with no C# defaults, literal named-argument identifiers, and response envelopes that can be misbound or read at the wrong level. **MUST load `dotnet-calling-endpoints`** before writing the first call.
- ⚠ Steps 3–9 (models/enums) — SDK string-enum construction/comparison and nullable response fields can silently corrupt status/scheduling/redaction decisions when treated like ordinary C# enums. **MUST load `dotnet-models`** before mapping provider data.
- ⚠ Steps 2–9 (error boundary) — Case B raw errors, typed deserialization failures, and status/body extraction have distinct paths; a partial catch ladder can leak SDK failures into order operations or misclassify deterministic rejections. **MUST load `dotnet-error-handling`** before writing any catch block.
- ⚠ Steps 1, 3–9 (resilience/base URL/pagination) — retry triggers, timeout scope, custom server-node wiring, and manual continuation affect duplicate writes, cancellation safety, whole-range reconciliation, and host selection. **MUST load `dotnet-configuration-resilience`** before configuring the client or retry/paging behavior.
- ⚠ Step 10 (tests) — faking generated controllers instead of the supported transport seam couples tests to SDK internals and misses wire/envelope/error behavior. **MUST load `dotnet-testing`** before writing integration tests.
- ⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- `Twilio:AccountSid` identifies the same account used for Basic authentication and owns `Twilio:MessagingServiceSid`.
- `Twilio:MessagingServiceSid` identifies a Messaging Service whose sender pool resolves the scheduled follow-up to `Twilio:FromNumber`; live verification must confirm the returned scheduled message has that `From` value so it is included by reconciliation.
- The application chooses the exact follow-up delay within the requested “few days” and computes `sendAt` as an absolute `DateTimeOffset` sufficiently in the future for provider acceptance.
- The application persists order/contact/notification/idempotency state and implements authorization, transactions, and operator retry/escalation; those are outside the provider SDK contract.

### Blockers

- None. The SDK map exposes every required provider capability. The exact post-redaction representation of `Body` is live-behavior-only and is handled by a concrete verification directive rather than treated as a capability gap.
