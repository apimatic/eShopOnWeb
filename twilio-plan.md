## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Trust limits and defensive directives

| Item | Directive | Classification/source |
|---|---|---|
| Scheduled-send time window | Use a fixed three-day delay, normalized to UTC. The generated signature accepts `DateTimeOffset?` and the enum says fixed scheduling requires a Messaging Service, but neither map nor map-named source states the provider's earliest/latest scheduling bounds. Treat provider rejection as a failed follow-up notification while preserving dispatch, and exercise a three-day live create/cancel in verification. | `UNVERIFIED`; `map/operations/Api20100401Message.md`; `map/models/enums.md` |
| Scheduled `From` + `MessagingServiceSid` | The generated operation permits both optional parameters and contains no acceptance rule. Send both to satisfy the configured-sender/reconciliation requirement; if live traffic disproves simultaneous acceptance, that is provider behavior not settled by the SDK source and must be returned to this agent before changing the contract. | `UNVERIFIED`; `map/operations/Api20100401Message.md` |
| Redaction sentinel | The operation notes explicitly identify `UpdateMessage.body` as the redaction path but do not specify the exact string. Send `body: ""`, `status:null`, then fetch best-effort and require provider body to be empty/redacted before reporting disposal complete; retain metadata and never fall back to `DeleteMessage`. | `UNVERIFIED`; `map/operations/Api20100401Message.md` |
| Reconciliation time precision | Generated source documents provider `DateSent` filters as GMT dates while the signature serializes `DateTimeOffset` values. Query a UTC date-wide superset with server-side `From`, paginate completely, then parse `DateSent` and locally retain exact `[from,to]` inclusive. This protects completeness regardless of whether the live endpoint honors time-of-day precision. | `UNVERIFIED`; `Api/Api20100401Message.cs` and `map/operations/Api20100401Message.md` |
| Malformed or drifted provider fields | Extract SID/status/error/timestamps best-effort. Preserve a generic integration-failure outcome when an expected optional field is absent; never throw through an order operation merely because a 2xx response omitted data. | `UNVERIFIED`; model members are nullable in `map/models/records-1-Ac-Ca.md` |

## 3. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership and DI lifetime can cause connection churn or disposed handlers. **MUST load `dotnet-client-initialization`** before wiring either client.
- ⚠ Step 2 (authentication) — credential timing, per-environment configuration, and secret rotation can turn valid configuration into 401/403 failures. **MUST load `dotnet-authentication`** before setting auth.
- ⚠ Steps 3–10 (endpoint calls) — long generated signatures contain nullable parameters with no C# defaults, and positional calls can silently bind the wrong filter or scheduling input. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 4–7 (models/enums) — SDK string-enum construction/reading and nullable response members can cause incorrect status comparisons or payload construction. **MUST load `dotnet-models`** before using these types.
- ⚠ Steps 4–10 (business boundary) — provider exceptions must be translated without allowing messaging failure to escape an order transition, while retaining actionable provider details. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Steps 1, 4, 5, 8, 10 (resilience/base URL/pagination) — retry, timeout, transport-failure, server-node, and manual-page behavior can duplicate writes, miss pages, or bypass the configured messaging host. **MUST load `dotnet-configuration-resilience`** before configuring or calling these paths.
- ⚠ Step 11 (tests) — faking generated controller internals creates brittle tests and can fail to exercise serialization/error behavior. **MUST load `dotnet-testing`** before writing integration-layer tests.
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- Assumption: “a few days later” is implemented as exactly three days after dispatch.
- Assumption: `LookupResponse.Valid == true` plus a non-empty provider-returned E.164 `PhoneNumber` is the provider acceptance criterion at contact registration; deliverability can still later be `undelivered`, as required by the unreachable fixture.
- Assumption: reconciliation is by provider `DateSent` and exact inclusive instants; date-only provider filtering is widened and exact-filtered locally so no in-range record is omitted.
- Blockers: none. The SDK exposes lookup/canonicalization, message create/fetch/list/update, provider scheduling, scheduled cancellation, and body redaction. The live-only uncertainties above have explicit defensive directives and verification checks rather than open implementation rows.
