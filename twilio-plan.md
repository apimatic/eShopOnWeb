## 3. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

All five operations below are throw-only and have no `...Result` alternative.

## 4. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` lifetime and generated client DI lifetime can make sockets or handlers unsafe if wired incorrectly. **MUST load `dotnet-client-initialization`** before registering the client.
- ⚠ Step 1 (authentication) — credential construction, rotation, and configuration timing can silently produce unauthenticated calls or leak secrets. **MUST load `dotnet-authentication`** before setting `AccountSidAuthToken`.
- ⚠ Steps 3–11 (endpoint calls) — generated optional parameters have no C# defaults, named argument binding and response envelopes can otherwise call/read the wrong shape. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 3–11 (models/enums) — nullable response members and `StringEnum<T>` handling can corrupt validation/status decisions if treated as ordinary C# enums or assumed present. **MUST load `dotnet-models`** before mapping provider models.
- ⚠ Steps 3–11 (error boundary) — Case-B raw errors, transport failures, cancellation, and serialization failures cross different exception paths and can either escape or be misreported. **MUST load `dotnet-error-handling`** before writing any catch ladder.
- ⚠ Step 1 and every provider write/list (resilience) — retries, total latency, messaging-only server overrides, request logging, and full pagination can duplicate writes, miss records, or expose message data if configured from surface names alone. **MUST load `dotnet-configuration-resilience`** before configuring these behaviors.
- ⚠ Step 12 (tests) — mocking generated controllers instead of the supported HTTP seam makes tests couple to SDK internals and miss wire behavior. **MUST load `dotnet-testing`** before writing integration tests.
- ⚠ Steps 3–11 (2xx deserialization) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Steps 3–11 (non-2xx deserialization) — a **non-2xx** body that does not match its operation's generated error shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- “A few days later” is fixed at three days after dispatch.
- The configured Messaging Service contains `Twilio:FromNumber` as its sender. Scheduled creation uses the service because the map explicitly marks scheduling as Messaging-Services-only. Provider sender assignment on the live account is **UNVERIFIED**: after creation/fetch, persist `From`; if it is non-empty and differs from `Twilio:FromNumber`, immediately cancel that scheduled message, mark the notification failed due to configuration mismatch, and never let it go out.
- The provider's v2 `LookupResponse.Valid == true` plus its returned canonical `PhoneNumber` is the validation boundary. Delivery failure remains a later provider outcome; it does not retroactively make registration invalid.
- Reconciliation interprets the HTTP range as `from` inclusive and `to` exclusive. Because the provider parameters are strict `DateSent>`/`DateSent<`, query the provider with minimally widened bounds where necessary, then apply the exact requested time boundary locally; the sender restriction remains server-side on every request.
- A durable cancellation/redaction retry worker is allowed because it never sends the scheduled follow-up; the provider, not the application, owns the delayed send.

### Blockers

- None.

## 7. Build and live verification sequence

1. Set `global.json` roll-forward to `latestMajor`; run commands with `DOTNET_ROLL_FORWARD=Major`. Load credential values from the named environment variables into **PublicApi .NET user-secrets without echoing them**, using the exact `Twilio:*` keys. Do not write values into the repository.
2. Build the solution and tests. Run PublicApi detached on an assigned port with `UseOnlyInMemoryDatabase=true`; poll its health/auth endpoint, retain its PID, and stop it after verification.
3. Obtain separate shopper/admin JWTs using PublicApi's existing authentication endpoint and role. Do not print tokens or phone values in captured logs.
4. Register only the destination from the configured Canadian test-number secret. Confirm POST returns `contactNumberId`, GET returns it, and invalid syntax is rejected without persistence.
5. Place one order with a minimal catalog item/quantity. Confirm `orderId`; poll order notifications and provider fetch until the placed message is `Delivered` (or the strongest terminal delivery outcome returned by the live account). This is the real reachability proof.
6. Dispatch that same order. Confirm one dispatch notification and one follow-up with a provider SID/status `Scheduled`, a send time three days later, and provider `From` equal to configured `Twilio:FromNumber` when populated.
7. Cancel immediately. Confirm the order remains cancelled, cancellation SMS has its own notification, and repeated provider fetch reports the follow-up `Canceled`. Wait/poll long enough to distinguish accepted state updates; do not wait three days.
8. Dispose content for one provider-backed notification. Fetch it again through the SDK and confirm body is null/empty while SID/status remain. Confirm API projections no longer return local content.
9. Delete the Canadian contact, confirm it disappears, and confirm no later send path selects it.
10. Register only the configured unreachable US test destination. Place a minimal order and poll until its notification is terminal `Undelivered`/`Failed` (expected live-account outcome, not a defect).
11. Resend that failed notification with one fresh idempotency key. Confirm returned new `notificationId`. Repeat the exact key and prove the same ID/provider SID is returned and provider message count does not increase. Use one second fresh key only if needed to prove a genuine second attempt.
12. Request reconciliation over a UTC range bracketing this run. Confirm it spans every page, includes these provider SIDs, aligns local rows, exposes no account traffic from other senders, and identifies any deliberately created application-only failure. Delete the unreachable contact.
13. Stop the detached PublicApi PID and verify no stale process remains on the assigned port.
