## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — client/`HttpClient` lifetimes and the DI extension's ownership boundary can cause socket exhaustion or stale handler behavior if guessed. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 2 (authentication) — credential construction, secret rotation, and per-environment configuration shape determine whether requests authenticate without exposing secrets. **MUST load `dotnet-authentication`** before setting auth.
- ⚠ Steps 3, 5–12 (calling operations) — required nullable positional parameters, named-argument binding, response shape, and cancellation-token propagation can silently call with the wrong wire fields. **MUST load `dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Steps 3, 5–12 (models/enums) — generated records have optional members and generated string-enum construction/comparison rules; treating them like ordinary C# enums or required response members corrupts state handling. **MUST load `dotnet-models`** before mapping responses.
- ⚠ Steps 5–12 (errors) — all in-scope operations are Case B and other exception families can cross the boundary; an incomplete catch ladder can incorrectly fail the domain operation or misclassify a provider rejection. **MUST load `dotnet-error-handling`** before writing the boundary.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Steps 1–2, 5–12 (resilience/base URL/pagination) — retry triggers can duplicate writes, timeout layers can leave calls running longer than expected, server-node overrides can affect the wrong provider capability, and list continuation is manual. **MUST load `dotnet-configuration-resilience`** before configuring these paths.
- ⚠ Step 13 (tests) — mocking generated controllers couples tests to SDK internals and misses real form/query/auth behavior. **MUST load `dotnet-testing`** before building the test seam.

## 5. Assumptions & Blockers

### Assumptions

- Every lifecycle event targets every active contact number owned by the order's shopper; deleting one number suppresses only that destination and cancels its pending follow-ups.
- “A few days later” means three days after dispatch, expressed as a UTC `DateTimeOffset`.
- Reconciliation uses an inclusive `[from, to]` application interval after a conservative provider-side GMT-date query; `from > to` is invalid.
- `Failed` and `Undelivered` are eligible for operator resend. A canceled delivery-feedback notification is never eligible, even though it did not reach the shopper. Other statuses remain ineligible until refreshed into a terminal outcome.
- Application notification IDs and provider message SIDs are distinct durable identifiers; all public operator routes use the application ID and the gateway resolves the provider SID internally.

### Blockers

- None. The mapped/generated SDK exposes validation with provider canonicalization, message create/fetch/list/update, fixed scheduling, scheduled cancellation, and provider-body redaction. The one live-only uncertainty (sub-day precision of the provider's legacy date filter) is handled defensively without widening beyond the configured sender.
