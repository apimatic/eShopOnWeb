| Step | Work and SDK operations |
| --- | --- |

| 2 | Register a shopper number by calling `LookupsV2PhoneNumber.FetchPhoneNumber3` with `fields: "validation"`; store `LookupResponse.PhoneNumber` only when `Valid == true`. All remaining optional lookup arguments are explicitly `null`. |
| 3 | Persist contact numbers, order state, notification attempts, provider SID/status/error data, scheduled-send time, content-disposal state, resend idempotency key, and cancellation work. | 4 | After an order is durably placed, create placed messages with `Api20100401Message.CreateMessage`; a provider failure is recorded but cannot roll back or fail the order request. Resolve all currently active shopper numbers at the time of the event. **YOUR CALL — not in the map.** |
| 5 | After dispatch is durably recorded, create the immediate dispatch message and a second provider-scheduled message for UTC now plus three days using `CreateMessage` with `ScheduleType.Fixed`, `SendAt`, `MessagingServiceSid`, `From`, `To`, and `Body`. Persist each returned SID/status independently. |
| 6 | On order cancellation, and on deletion of a contact number, find every not-yet-sent scheduled provider message in scope and call `Api20100401Message.UpdateMessage` with `Status: Canceled`. Attempt synchronously, persist cancellation work before returning, and retry ambiguous/transient cancellations through a durable hosted worker that first calls `FetchMessage`; this worker cancels provider work and never sends the follow-up itself. Underlying order/contact state remains successful even if Twilio is unavailable. **YOUR CALL — not in the map.** |
| 7 | For order/notification reads, call `FetchMessage` for records with a provider SID to refresh provider-owned status/error/body-disposal evidence; isolate every refresh failure and retain the last observed provider state. |
| 8 | For resend, atomically insert/find a notification-attempt row under a unique `(source notification id, caller idempotency key)` constraint before `CreateMessage`. Replays return that row's `notificationId` and never call Twilio again; a fresh key creates a distinct attempt. Do not retry an ambiguous create because the SDK operation has no caller-supplied provider idempotency key. **YOUR CALL — not in the map.** |
| 9 | For content disposal, call `UpdateMessage` with `Body: string.Empty`, then `FetchMessage`; report success only after the provider returns no retrievable message text while retaining SID/status/timestamps locally. Exact empty-string redaction behaviour is `UNVERIFIED`; the generated method documentation explicitly identifies `UpdateMessage` as the redaction operation. |
| 10 | Reconcile by repeatedly calling `ListMessage` with `from: Twilio:FromNumber`, provider date bounds, `PageSize: 1000`, and each provider `PageToken` extracted from `NextPageUri` until exhausted. Query an inclusive day-expanded range because the method docs describe GMT date filters, then apply the caller's exact ISO-8601 instants locally. Match provider SID to local SID and emit provider-only and local-only rows. Never issue an unfiltered-by-`From` provider query. |
| 11 | Unit-test the transport seam, failure isolation, owner/role authorization, resend uniqueness/concurrency, paging, cancellation retry, and content verification; then perform the minimum live flow only with the two supplied safe destinations. |

Multiple active numbers are all notified. A deleted number is excluded immediately from new sends, resends refuse an attempt whose destination contact is no longer active, and already-scheduled messages for that contact enter provider-cancellation work. **YOUR CALL — not in the map.**

Repository conventions to imitate: endpoint registration/administrator authorization in `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`; authenticated identity value from `src/Infrastructure/Identity/IdentityTokenClaimService.cs`; EF context registration in `src/Infrastructure/Dependencies.cs`; aggregate mapping in `src/Infrastructure/Data/Config/OrderConfiguration.cs`; repository/specification ownership filtering in `src/ApplicationCore/Specifications/CustomerOrdersSpecification.cs`.

## 3. Trap notes

- Client setup: `HttpClient` ownership/lifetime and DI wrapper lifetime can cause connection churn and stale configuration. **MUST load `twilio-platforms-team:dotnet-client-initialization`.**
- Authentication: scheme application, secret binding, and credential rotation can turn a missing value into an unauthenticated network call. **MUST load `twilio-platforms-team:dotnet-authentication`.**
- Calls: the long generated signatures, nullable-without-default parameters, named arguments, response-envelope level, and absence of a real provider idempotency key can mis-bind or duplicate work. **MUST load `twilio-platforms-team:dotnet-calling-endpoints`.**
- Models: string-backed enums, nullability, required members, and extension data can produce invalid payload construction or brittle reads. **MUST load `twilio-platforms-team:dotnet-models`.**
- Error boundary: Case B provider failures, non-SDK transport failures, cancellation, and safe RawError inspection can otherwise escape or leak data. **MUST load `twilio-platforms-team:dotnet-error-handling`.**
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException`, so an SDK-exception-only catch ladder lets it escape. **MUST load `twilio-platforms-team:dotnet-error-handling`.**
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so it **replaces** the `SdkException` and the HTTP status is destroyed with it. **MUST load `twilio-platforms-team:dotnet-error-handling`.**
- Resilience: retry eligibility, per-attempt versus total timeout, base-URL nodes, manual pagination, ambiguous writes, hooks, and body logging can violate latency, duplicate, completeness, routing, or privacy requirements. **MUST load `twilio-platforms-team:dotnet-configuration-resilience`.**
- Tests: faking the wrong layer can couple tests to generated controllers and fail to assert the provider request actually built. **MUST load `twilio-platforms-team:dotnet-testing`.**

## 6. Assumptions & Blockers

### Assumptions

- "A few days" means three days, computed in UTC. **YOUR CALL — not in the map.**
- All active registered numbers receive each event; deletion and resend always re-check that the contact remains active. **YOUR CALL — not in the map.**
- `Twilio:FromNumber` is authorized for the configured Messaging Service and may be supplied with `MessagingServiceSid` so even scheduled traffic originates from the configured application sender. The generated create form accepts both and the scheduling enum requires a Messaging Service; live verification confirms the account relationship. `Api/Api20100401Message.cs` and `Models/Enums/MessageEnumScheduleType.cs`.
- Exact empty-string body redaction is `UNVERIFIED`. Defensive directive: call `UpdateMessage(body: string.Empty, status: null)`, then call `FetchMessage`; never mark disposal complete or return success until provider content is absent/empty. The capability itself is present: generated docs identify `UpdateMessage` as used to redact message body text.
- Provider list filters are documented as GMT dates although the generated arguments are `DateTimeOffset`; reconciliation queries provider-side with configured `From` and day-expanded bounds, traverses every page, then applies exact caller instants locally. `Api/Api20100401Message.cs`.
- A provider accepted-but-unrecorded create cannot be deterministically correlated without its returned SID. It is intentionally visible as provider-only/local-unknown in reconciliation, and same-key resend replay remains suppressed. **YOUR CALL — not in the map.**

### Blockers

None. The generated SDK covers validation/canonicalization, immediate and scheduled create, scheduled cancellation, status fetch, body redaction, and sender/date-filtered listing. The two explicitly `UNVERIFIED` wire outcomes above have defensive verification paths and do not require a substitute API.
