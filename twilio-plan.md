## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 2 (client registration) — transport ownership and DI lifetime can create socket churn or dispose shared handlers. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 2 (credentials) — credential initialization/rotation and secret handling determine whether auth reaches every call without leaking. **MUST load `dotnet-authentication`** before setting auth.
- ⚠ Steps 3–10 (calls) — generated optional parameters lack C# defaults and positional binding can silently target the wrong wire field. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 4–10 (models/enums) — nullable response members and `StringEnum<T>` representation can turn a provider outcome into an incorrect application state. **MUST load `dotnet-models`** before mapping models.
- ⚠ Steps 2, 4, 5, 8 (resilience) — retry/timeout/base-server mechanics can duplicate a non-idempotent send or route only some calls to the override host. **MUST load `dotnet-configuration-resilience`** before configuring the client.
- ⚠ Steps 3–10 (error boundary) — Case-B raw errors, transport errors, cancellation, and deserialization failures cross different exception paths; a partial catch ladder can either leak failures into order operations or misclassify caller errors. **MUST load `dotnet-error-handling`** before writing the boundary.
- ⚠ Verification — faking SDK internals instead of the transport seam can leave the real form/query/server-node contract untested. **MUST load `dotnet-testing`** before writing integration tests.

## 4. REQUIRED READING

Load every item below **before implementation starts**. This sheet deliberately does not carry their contents.

- `dotnet-client-initialization` — client/DI/transport lifetime in Step 2.
- `dotnet-authentication` — credential construction and secret lifecycle in Step 2.
- `dotnet-calling-endpoints` — exact invocation discipline in Steps 3–10.
- `dotnet-models` — nullable records and generated string enums in Steps 3–10.
- `dotnet-configuration-resilience` — retry, timeout, base-server, logging, and manual pagination hazards in Steps 2, 4, 5, 8, and 10.
- `dotnet-error-handling` — complete integration boundary for every provider call.
- `dotnet-testing` — transport-seam tests and live-test separation.

Mandatory error-boundary hazards:

- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.
- A **non-2xx** body that does not match its operation's generated error shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The application defines the reconciliation range as provider `sent_date`, because that is the only message date filter exposed by `ListMessage`; exact ISO-8601 instants are enforced locally after a widened provider query. Provider records with no sent date are outside that sent-time range.
- A three-day `SendAt` satisfies “a few days later.” The map documents `Fixed` scheduling with a Messaging Service but does not document the provider's accepted scheduling window.
- Destination usability at registration means Lookup v2 returns `Valid == true` and a canonical `PhoneNumber`. It is not a promise of later carrier delivery.
- Application authorization, persistence, atomic caller-key deduplication, notification text, no-number selection policy, contact-number deletion semantics, and order-state concurrency are intentionally left to the implementer; the SDK map does not define them.

### Blockers

- None. The SDK map/source exposes every required provider capability. The scheduling field combination, redacted-body representation, and exact timestamp wire behavior require live verification and are marked `UNVERIFIED`, but none is an open SDK-surface gap.
