# PayPal (PayPalServerSdk) integration plan — eShopOnWeb PublicApi

SDK: NuGet `AsadAli.Checkout.Sdk` (install version-less: `dotnet add package AsadAli.Checkout.Sdk` — floats to latest; this sheet is grounded against release `v1.0.1`, source commit `9653d18`). Root namespace `PayPalServerSdk`, client `PayPalServerSdkClient`, options `PayPalServerSdkClientOptions`. All operations are throw-only (no `…Result` variants exist).

## 1. Scope & sequence

1. **Package + client registration** — add NuGet package; bind `PayPal:*` config; register client via `AddPayPalServerSdkClient` (or construct manually); wire environment, optional base-URL override, OAuth credentials.
2. **Error boundary** — one translation layer around all SDK calls (Case A typed / Case B raw / `JsonException` both directions).
3. **Authorize order** — `Orders.CreateOrder` (intent AUTHORIZE) → `Orders.AuthorizeOrder` with raw-card **or** vaulted-card payment source; persist order id + authorization id/status.
4. **Capture at fulfilment** — `Payments.CaptureAuthorizedPayment`; read captured amount, PayPal fee, net from `SellerReceivableBreakdown`; persist capture id/status.
5. **Reauthorize stale authorization** — `Payments.ReauthorizePayment` (days 4–29 only); on 422 surface a clear "cannot reauthorize" error.
6. **Void on cancel** — `Payments.VoidPayment`.
7. **Refund** — `Payments.RefundCapturedPayment` (full = null body, partial = `Amount`), caller-supplied `payPalRequestId` idempotency key; persist refund ids/statuses.
8. **Saved cards (vault)** — `Vault.CreatePaymentToken` (direct card flow; setup-token flow documented as alternative), `Vault.ListCustomerPaymentTokens`, `Vault.GetPaymentToken`, `Vault.DeletePaymentToken`; pay with vaulted card via `CardRequest.VaultId`.
9. **Reconciliation** — `TransactionSearch.SearchTransactions` paged over the whole date range.
10. **Tests** — fake the `HttpClient` seam.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

Namespaces: client/options/DI `PayPalServerSdk` · controllers `PayPalServerSdk.Api` (accessed via client properties — no direct construction) · records `PayPalServerSdk.Models` · enums `PayPalServerSdk.Models.Enums` · typed errors `PayPalServerSdk.Errors` · `SdkException<T>` `PayPalServerSdk.Core.Exceptions` · `RawError`/`ApiError` `PayPalServerSdk.Core.ErrorResponse` · `RequestOptions` `PayPalServerSdk.Core` · `RetryOptions`/`LoggingOptions` `PayPalServerSdk.Core.Configuration` · `ServerEnvironment`/`DefaultOptions` `PayPalServerSdk.Servers` · `ServerOptions` `PayPalServerSdk` · `OAuth2ClientCredentials` `PayPalServerSdk.Core.Authentication.OAuth2.ClientCredentials` · `IOAuth2TokenStrategy<T>` `PayPalServerSdk.Core.Authentication.OAuth2`.

### Client construction / auth / server-node facts

- **Install**: `dotnet add package AsadAli.Checkout.Sdk` (version-less; floats to latest; sheet grounded on `v1.0.1`).
- **Construct**: `new PayPalServerSdkClient(HttpClient httpClient, PayPalServerSdkClientOptions options)` — or DI: `services.AddPayPalServerSdkClient(o => { … })` (extension in namespace `PayPalServerSdk`; source `ServiceCollectionExtensions.cs`).
- **Options** (`PayPalServerSdkClientOptions`, root namespace): `Environment: ServerEnvironment` · `Retry: RetryOptions` · `Logging: LoggingOptions` · `Server: ServerOptions` · `Oauth2: OAuth2ClientCredentials?` · `Oauth2TokenStrategy: IOAuth2TokenStrategy<OAuth2ClientCredentials>?`.
- **Environment**: `ServerEnvironment` (`PayPalServerSdk.Servers`, `Servers/ServerEnvironment.cs`) has exactly ONE member in v1.0.1: `ServerEnvironment.Sandbox`. **There is no Production member** — see Blockers.
- **Base-URL override (verbatim, every call incl. OAuth token)**: `o.Server.Default.Sandbox.BaseUrl = "<PayPal:BaseUrl>"`. Chain: `ServerOptions.Default: DefaultOptions` (`PayPalServerSdk`) → `DefaultOptions.Sandbox: DefaultOptions.SandboxOptions` (`PayPalServerSdk.Servers`) → `BaseUrl: string` (default `https://api-m.sandbox.paypal.com`). Every operation path resolves through this one template (`Servers/DefaultOptions.cs`), and the OAuth token URL is built from the same resolver (`server.Default("/v1/oauth2/token")` in `AuthSchemes.cs`) — so the override covers the credential/token request too.
- **OAuth client-credentials**: `o.Oauth2 = new OAuth2ClientCredentials { ClientId = <PayPal:ClientId>, ClientSecret = <PayPal:ClientSecret> }` — both `required` init properties; optional `Scope`. Default strategy POSTs form `grant_type=client_credentials` with a Basic `Authorization` header to `/v1/oauth2/token` on the configured base URL; leave `Oauth2TokenStrategy` null unless customizing token caching.
- **Config mapping**: `PayPal:Environment` = `Sandbox` → `o.Environment = ServerEnvironment.Sandbox`, no override. `Production` → no enum member exists; set `o.Server.Default.Sandbox.BaseUrl` to the production host from config. `PayPal:BaseUrl` set → always applied verbatim (wins over environment default).

### Error handling (map: `sdk-map.md` error model + per-op rows above)

- All failures throw `SdkException<TError>` (`PayPalServerSdk.Core.Exceptions`); the payload is `ex.Error`.
- **Case A** (39 of 40 ops — everything in scope except SearchTransactions): `TError` is a typed `{Operation}Error : ApiError` (`PayPalServerSdk.Errors`) with `TryGetError(out Error)` / `TryGetError1(out Error1)` (Vault ops) / `TryGetNoContent(out RawError)` (Payments 500s) / inherited `TryGetRawError(out RawError)` fallback. The accessor returns `true` only for its listed statuses — always end the ladder with `TryGetRawError`.
- Error payload records (`PayPalServerSdk.Models`): `Error`/`Error1`: `Name (name): string !req`, `Message (message): string !req`, `DebugId (debug_id): string !req`, `Details (details): IReadOnlyList<ErrorDetails/ErrorDetails1>?` → `Issue (issue): string !req`, `Field (field)`, `Value (value)`, `Description (description)`, `Location (location)`. Read `Name` + `Details[].Issue` for the machine-readable reason (e.g. reauthorize-not-allowed).
- **Case B** (SearchTransactions): `SdkException<RawError>` — `ex.Error.StatusCode: HttpStatusCode`, `ReadAsString()`, `ReadAsJson<T>()`, `ReadAsBytes()`.
- 401/403 ⇒ check `ClientId`/`ClientSecret`, environment, and base-URL override before touching call sites.

## 3. Trap notes (hazard per step — load the named skill; the note deliberately does not resolve it)

> ⚠ Step 1 (client registration) — the SDK's `HttpClient`/handler pipeline has a specific ownership/lifetime model (the DI extension registers the wrapper as a singleton over `IHttpClientFactory`); getting this wrong exhausts sockets. **MUST load `dotnet-client-initialization`** before wiring DI.
> ⚠ Step 1 (auth) — credentials must be set before client construction and come from configuration, never hardcoded; token acquisition/caching has its own semantics. **MUST load `dotnet-authentication`**.
> ⚠ Steps 3–9 (every call) — many nullable parameters have no C# default and mis-bind positionally; call with named arguments (`payPalRequestId:`, `body:`, `ct:`). **MUST load `dotnet-calling-endpoints`**.
> ⚠ Steps 3–9 (models) — enums are `StringEnum<T>` (static members / `FromValue`, not C# enum members), `required` init properties must be set in the initializer, and unmodeled JSON fields are silently dropped on deserialize. **MUST load `dotnet-models`**.
> ⚠ Step 2 (error boundary) — which exception types actually reach a catch block, and what a typed `TryGet…` accessor does on a non-matching status, are not what a signature suggests. **MUST load `dotnet-error-handling`**.
> ⚠ Step 1 (resilience) — whether a failed non-idempotent POST (authorize/capture/refund) can be re-executed by the retry pipeline, what `Timeout` actually bounds, and the absence of a built-in logging hook. Pair every write with a `payPalRequestId`. **MUST load `dotnet-configuration-resilience`** before tuning `Retry`/`Logging`.
> ⚠ Step 10 (tests) — the test seam is the `HttpClient` constructor argument, not mocking SDK types. **MUST load `dotnet-testing`**.
> ⚠ Step 3 (authorize response shape) — `UNVERIFIED` (live-traffic only): whether the default `prefer = "return=minimal"` body includes `purchase_units.payments.authorizations`. Defensive directive: pass `prefer: "return=representation"` on `AuthorizeOrder`; if `PurchaseUnits/Payments` is still null, fall back to `GetOrder(id)` and read the authorization from there. Same directive for `SellerReceivableBreakdown` on `CaptureAuthorizedPayment` — fall back to `GetCapturedPayment(captureId)`.
> ⚠ Step 3 (3DS/SCA) — `UNVERIFIED` (live-traffic only): whether sandbox card `4111 1111 1111 1111` forces a 3DS challenge. Defensive directive: do NOT set `CardRequest.Attributes.Verification` to `ScaAlways` (default is `OrdersCardVerificationMethod.ScaWhenRequired`); after authorize, if `Order.Status == OrderStatus.PayerActionRequired` fail the payment loudly — this integration has no browser round-trip to complete a challenge. See Blockers.
> ⚠ Step 5 (reauthorize window) — per the operation contract: reauthorize only from day 4 to day 29 after the original authorization, once, amount ≤ ~115% / +$75; after 30 days a new order+authorize is required. Map 422 (`TryGetError` → `Error.Details[].Issue`) to a clear "reauthorization not possible" domain error.

  - a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
  - a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- `dotnet-configuration-resilience` — Step 1 (retries/backoff, timeout semantics, base URL, pagination, logging).
- `dotnet-testing` — Step 10 (faking the `HttpClient` seam, error-path coverage).

## 5. Assumptions & Blockers

- **BLOCKER (production environment)**: v1.0.1 `ServerEnvironment` has exactly one member, `Sandbox` (`Servers/ServerEnvironment.cs`) — there is no first-class Production environment. Production must be reached via the base-URL override (`o.Server.Default.Sandbox.BaseUrl`). The SDK pins only the sandbox host (`https://api-m.sandbox.paypal.com`); the production host value is NOT in the SDK and must come from configuration (`PayPal:BaseUrl`, conventionally `https://api-m.paypal.com` — `UNVERIFIED` from SDK evidence). Recommend: drive the host entirely from config and treat `PayPal:Environment` as a default-host selector.
- **Potential BLOCKER (3DS on sandbox test card)**: whether direct card authorize with `4111 1111 1111 1111` completes without a payer-action/3DS round-trip in sandbox is `UNVERIFIED` — only a live sandbox call settles it. If PayPal returns `PAYER_ACTION_REQUIRED`, the no-browser authorize flow cannot complete and a 3DS-capable (browser) path would be required. Defensive directives in Trap notes; confirm with one live sandbox authorize before building further on it.
- **Assumption (vaulted-card payment path)**: paying with a saved card uses `CardRequest.VaultId` = the vault payment-token id (map-grounded field). `PaymentSource.Token` (`TokenType.BillingAgreement` only) is NOT the vault-card path.
- **Vault customer identity (grounded, `Models/Customer.cs`)**: `Customer.Id` is PayPal-generated (max 22, `^[0-9a-zA-Z_-]+$`) — omit it in `CreatePaymentToken` and read it back from `PaymentTokenResponse.Customer.Id`; the merchant's own shopper key belongs in `Customer.MerchantCustomerId` (max 64, `^[0-9a-zA-Z-_.^*$@#]+$`). Use the PayPal-generated id for `ListCustomerPaymentTokens`.
- **Assumption (PCI scope)**: passing raw card data server-side requires the merchant's advanced-card-processing entitlement (stated as enabled in sandbox) and carries PCI SAQ D burden for production (per `CardRequest` doc note).
- **UNVERIFIED (minimal vs representation bodies)**: whether `prefer = "return=minimal"` responses include authorization/capture breakdown fields; defensive `prefer: "return=representation"` + GET-fallback directives are in the Trap notes.
- **Idempotency (grounded)**: `payPalRequestId` exists on CreateOrder, AuthorizeOrder, CaptureOrder, CaptureAuthorizedPayment, ReauthorizePayment, RefundCapturedPayment, VoidPayment, CreatePaymentToken, CreateSetupToken. Reuse one key per logical operation across retries; distinct keys for distinct partial refunds. Persist all PayPal ids (order, authorization, capture, refunds) + statuses on the payment record.
