# PayPal integration plan

## 1. Scope & sequence

| Step | Application responsibility | PayPal SDK operations |
|---|---|---|
| 1. Client and configuration | Install `AsadAli.Checkout.Sdk` version-less; bind `PayPal:ClientId`, `PayPal:ClientSecret`, `PayPal:Environment`, `PayPal:Currency`, and optional `PayPal:BaseUrl`; construct one long-lived SDK client over an `IHttpClientFactory` client. Configure Sandbox and, when present, set the Default/Sandbox server `BaseUrl` before constructing the client. | Client construction and OAuth2 client credentials; no endpoint call. |
| 2. Place local order | Create the application's existing order/order-item aggregate from server-side catalog prices, caller identity, configured currency, and a persisted immutable total. Initial payment state is awaiting payment. No card data and no PayPal object is created. | None. |
| 3. Authorize | Under a per-order concurrency/idempotency boundary, create a PayPal order with intent `AUTHORIZE`, one purchase unit, exact local total/currency, and stable `invoice_id`/`custom_id` correlation. Persist its PayPal order ID, then authorize it with either a transient card or the owned active vaulted-card ID in `CardRequest.VaultId`. Use deterministic `PayPal-Request-Id` values for both writes and persist the authorization ID/status/amount/timestamps/expiration. Reject any response amount/currency not exactly equal to the local total. If PayPal returns `PAYER_ACTION_REQUIRED`, stop and report the browser challenge rather than creating an approval flow. | `Orders.CreateOrder`, `Orders.AuthorizeOrder`; optionally `Payments.GetAuthorizedPayment` to refresh ambiguous/current state. |
| 4. Fulfil/capture | Operator-only. Refresh the current authorization. During the initial honor period capture it; when stale but still inside the reauthorization window, call reauthorize with the exact authorized amount, persist the returned replacement authorization ID/status/expiration, then capture it. Outside the provider's reauthorization window, or on a provider rejection that says it cannot be renewed, return an actionable “new shopper authorization required” result. Capture once with `FinalCapture=true`, the exact order total, and a deterministic request ID. Persist captured amount/status plus `SellerReceivableBreakdown.GrossAmount`, `PaypalFee`, and `NetAmount`; mark fulfilled only after a successful capture response. | `Payments.GetAuthorizedPayment`, `Payments.ReauthorizePayment`, `Payments.CaptureAuthorizedPayment`; `Payments.GetCapturedPayment` for ambiguous-result recovery/refresh. |
| 5. Cancel | Operator-only or owned shopper action as the application route policy requires; before fulfillment, serialize with capture/refund, call void using a deterministic request ID, persist PayPal's returned authorization status, then mark cancelled. A fully captured authorization cannot be voided. | `Payments.VoidPayment`. |
| 6. Refund | Owned order action. Reserve the requested amount transactionally against `captured - all non-failed refund reservations`; key the reservation by `(capture ID, caller idempotency key)`. Replays return the existing refund. For a full refund send an empty `RefundRequest`; for a partial refund send exact currency/amount. Pass the same caller key as `payPalRequestId`, persist returned refund ID/status/amount, and refresh pending/ambiguous records by ID. | `Payments.RefundCapturedPayment`, `Payments.GetRefund`. |
| 7. Save/list/delete cards | Save by sending the transient card directly to Vault with a stable merchant-customer correlation and deterministic request ID. Persist only PayPal payment-token ID, PayPal customer ID, brand/type/last digits/expiry, and lifecycle state. List only the caller's PayPal customer, manually traversing `page` through `TotalPages`; intersect/synchronize with owned active local records. Delete only after local ownership check, call provider delete, then mark the local token inactive. Before reuse, require owned/active state and optionally refresh with get-by-ID. | `Vault.CreatePaymentToken`, `Vault.ListCustomerPaymentTokens`, `Vault.GetPaymentToken`, `Vault.DeletePaymentToken`. |
| 8. Reconciliation | Operator-only. Parse the two ISO-8601 instants, validate `from <= to`, and manually request every page. Match PayPal transactions to local orders using stored provider authorization/capture/refund IDs first, then the unique `invoice_id`/`custom_id`. Emit matched, PayPal-only, and eShop-only rows. An empty recent sandbox result is valid because the provider notes reporting lag. | `TransactionSearch.SearchTransactions`. |
| 9. Tests/live gate | Unit-test outgoing paths, wire names, headers, amount formatting, paging, challenge behavior, ownership, duplicate clicks, ambiguous writes, refund reservations, and sanitized logging through the `HttpClient` seam. Then perform one sandbox direct-card authorize/capture/refund and one vault-save/reuse authorization. | All operations above. |

Application persistence, endpoint DTOs, authorization policies, state-machine names, locking, and transaction boundaries are **YOUR CALL — not in the map**. SDK facts below constrain those decisions.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — the generated DI helper's client lifetime and unnamed `HttpClient` blast radius affect connection rotation and handler isolation. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential timing, caching, refresh, and 401 invalidation are hidden behind the nullable OAuth options. **MUST load `dotnet-authentication`** before wiring secrets.

⚠ Step 1 (server/resilience) — the environment-specific server node, whole-call budget, retry triggers, and request logging can change duplicate-write and secret-exposure behavior. **MUST load `dotnet-configuration-resilience`** before configuring BaseUrl, retry, timeout, or handlers.

⚠ Steps 3–8 (endpoint calls) — nullable parameters without C# defaults must still be supplied, list/search calls are easy to mis-bind positionally, and `ct` is the literal cancellation argument. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–8 (models) — required init-only members, string-enum handling, nullable response members, and wire names affect acceptance and state interpretation. **MUST load `dotnet-models`** before building or reading SDK models.

⚠ Steps 3–8 (write idempotency) — transport failures can re-send POSTs independently of status-code retry settings; every logical write must reuse its provider request ID and local operation record. **MUST load `dotnet-configuration-resilience`** before enabling/tuning retries.

⚠ Steps 3–8 (error boundary) — Case A typed errors and Case B raw errors require different catch/accessor paths; assuming one common error envelope destroys actionable provider details. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Steps 3–8 (2xx drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Steps 3–8 (non-2xx drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 7 (manual list paging) and Step 8 (manual search paging) — neither operation has generated auto-pagination despite exposing page fields, so incorrect termination silently truncates or loops the report/list. **MUST load `dotnet-configuration-resilience`** before implementing traversal.

⚠ Step 9 (tests) — fake the supplied `HttpClient` handler, test status and transport retry triggers separately, and match the repository's existing framework/style. **MUST load `dotnet-testing`** before writing integration tests.

## 5. Assumptions & Blockers

- Assumption — the sandbox merchant is enabled for direct card processing and card vaulting, exactly as the task states.
- Assumption — `PayPal:Environment` resolves to the SDK's mapped `ServerEnvironment.Sandbox`; the SDK map exposes no other environment member.
- Assumption — application order identifiers are made globally unique in PayPal `invoice_id`/`custom_id` correlation strings; the exact encoding is **YOUR CALL — not in the map**.
- Assumption — direct-card acceptance is account/live-traffic behavior. Treat `OrderStatus.PayerActionRequired` as a hard stop and report it; no approval round-trip is planned. `UNVERIFIED` until sandbox execution.
- Blockers — none. The SDK map covers every required PayPal operation. Transaction reporting lag and an empty recent range are documented provider behavior, not a capability gap.
