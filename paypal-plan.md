# PayPal .NET integration plan for eShopOnWeb

## 1. Scope & sequence

1. Register one long-lived `PayPalServerSdkClient` and OAuth2 client-credentials configuration.
2. Create an order with `AUTHORIZE` intent and a direct card payment source; authorize it with `Orders.AuthorizeOrder`.
3. Capture the resulting authorization with `Payments.CaptureAuthorizedPayment`; void an uncaptured authorization with `Payments.VoidPayment`; refund a capture with `Payments.RefundCapturedPayment`; read authoritative states with the corresponding `Get*` operations.
4. Vault a card with `Vault.CreatePaymentToken`, list/read/delete saved payment tokens, and use a saved token as `PaymentSource.Token` in a new order.
5. Reconcile with `TransactionSearch.SearchTransactions` (page through `page`, using the response totals) and optionally `SearchBalances`; account for the reporting lag stated in the operation Notes.
6. Carry a stable application idempotency key into every operation that exposes the generated `payPalRequestId` parameter, and load the resilience/error/testing skills before implementation.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal
C# identifier. The cancellation-token parameter really is named `ct`: in named
arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take
each one from that type's own map row, never from where a neighbouring type sits. A members
table names the namespace outright; otherwise the row's source path implies it
(`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
namespace). Enums, unions, auth, server and client-config types are spread across different
child namespaces, and two types configured side by side in the same options object routinely
live in different ones. Dropping a type to the root or to `.Models` makes the implementer
guess the wrong `using`, and the build breaks.

All operations are async and throw-only; there are no `…Result` variants. Every `RequestOptions?` is `PayPalServerSdk.Core.RequestOptions?`; every `CancellationToken` is `System.Threading.CancellationToken`; controller properties are on `PayPalServerSdk.PayPalServerSdkClient`.

## 3. Trap notes

⚠ Step 1 (client registration) — client lifetime, `HttpClient` ownership, and the DI registration shape affect connection reuse and test seams. **MUST load `paypal-sdk:dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (auth) — OAuth2 credential placement, token caching/refresh, and 401/403 diagnosis are configuration concerns, not call-site headers. **MUST load `paypal-sdk:dotnet-authentication`** before wiring credentials.

⚠ Step 1/5 (configuration and reconciliation) — retry status/method selection, transport retries, per-attempt timeout versus whole-call cancellation, server-node/base-URL overrides, pagination, and logging redaction have consequences for writes and reports. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before configuring them.

⚠ Step 2–5 (calls) — leading nullable parameters without defaults must be passed explicitly, named arguments must use the literal generated names, and response resources differ between direct records and envelopes. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before writing calls.

⚠ Step 2/4 (models) — JSON wire names differ from C# names; required members, empty versus null collections/bodies, enum values, and PCI-sensitive card fields determine serialization and handling. **MUST load `paypal-sdk:dotnet-models`** before constructing or mapping models.

⚠ Step 2–5 (error boundary) — typed accessors are operation-specific and `TryGetRawError` belongs last; Case B exposes `RawError` directly, and connection failures are not `SdkException<T>`. **MUST load `paypal-sdk:dotnet-error-handling`** before writing catches or translation.

⚠ Step 6 (tests) — fake the supplied `HttpClient` through a `HttpMessageHandler`, assert request method/path/query/body and both status and transport retry behavior, and mirror the existing test stack. **MUST load `paypal-sdk:dotnet-testing`** before writing tests.

## 4. REQUIRED READING

Load these before implementation starts; this sheet deliberately names the hazards and pointers but does not carry the companion skills' contents.

- `paypal-sdk:dotnet-client-initialization` · Step 1 client construction, lifetime, DI, and HttpClient seam.
- `paypal-sdk:dotnet-authentication` · Step 1 OAuth2 credentials, token lifecycle, and auth failures.
- `paypal-sdk:dotnet-configuration-resilience` · Steps 1 and 5 server/base URL, retries, timeouts, logging, and pagination.
- `paypal-sdk:dotnet-calling-endpoints` · Steps 2–5 operation calls, parameter order, response use, and cancellation.
- `paypal-sdk:dotnet-models` · Steps 2 and 4 request/response models, wire names, required members, enums, and PCI-sensitive card data.
- `paypal-sdk:dotnet-error-handling` · Steps 2–5 exception boundary and provider/transport failure translation.
- `paypal-sdk:dotnet-testing` · Step 6 HttpClient-handler tests and retry/error coverage.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- Assumption: “direct card authorize” means Orders v2 with `CheckoutPaymentIntent.Authorize`, followed by `Orders.AuthorizeOrder`, then Payments authorization operations; the map has no standalone direct-card authorization operation.
- Assumption: vault saved cards means the Vault payment-token lifecycle (`CreatePaymentToken`, `ListCustomerPaymentTokens`, `GetPaymentToken`, `DeletePaymentToken`) and application-owned customer association.
- Assumption: transaction reconciliation is reporting-based and will use `SearchTransactions` with explicit pages and the operation's three-hour visibility caveat; eShopOnWeb must choose its own persistence, matching, and replay policy.
- Blockers: none in the SDK contract map.
