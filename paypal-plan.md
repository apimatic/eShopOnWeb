# PayPal payments and saved cards — implementation plan

## 1. Scope & sequence

| Step | Application work | PayPal SDK operations |
|---|---|---|
| 1 | Add `AsadAli.Checkout.Sdk` to `src/PublicApi` and, because this repository uses NuGet Central Package Management, add `<PackageVersion Include="AsadAli.Checkout.Sdk" Version="1.0.0" />` to `Directory.Packages.props`; bind and validate `PayPal:ClientId`, `PayPal:ClientSecret`, `PayPal:Environment`, `PayPal:Currency`, and optional `PayPal:BaseUrl`; construct one SDK client over an `IHttpClientFactory` client. `PayPal:Environment` must resolve to the SDK's only mapped environment, Sandbox. | 3 | `POST /api/orders`: authenticate the shopper, load catalog items and prices server-side, create the existing order/order-items in `AwaitingPayment`, and return top-level `orderId`. No card or PayPal call is needed until `/pay`. | No call |
| 4 | `POST /api/orders/{orderId}/pay`: enforce ownership and serialize payment attempts. Create one PayPal order with `AUTHORIZE`, one purchase unit, exact configured currency/value, and stable local `orderId` in `invoice_id` and `custom_id`; persist the PayPal order ID. Then authorize it with either an ephemeral direct `CardRequest` or a `CardRequest.VaultId` that came from this shopper's active local payment-method record. | 6 | `POST /api/orders/{orderId}/fulfil` (administrator): if authorization is still in its initial honor period, capture it. On a stale capture rejection in that eligible window, perform that same one-time renewal and retry capture under the persisted idempotency identity. At/after day 30, or when provider status/error makes reauthorization impossible, return an operator-actionable conflict containing safe provider status, authorization ID/timestamps, debug ID, and “shopper must re-pay”; never silently create a new authorization because one-off card details no longer exist. Pending capture remains pending and is refreshed, not duplicated. | `Payments.GetAuthorizedPayment`, `Payments.ReauthorizePayment`, `Payments.CaptureAuthorizedPayment`, `Payments.GetCapturedPayment` |
| 7 | `POST /api/orders/{orderId}/cancel` (administrator): only before capture/fulfilment. Serialize against fulfilment, call void with a stable request ID, persist provider authorization status, and mark cancelled only after `VOIDED`. Repeated cancel returns the prior result. | `Payments.VoidPayment`, optional `Payments.GetAuthorizedPayment` readback |
| 8 | `POST /api/orders/{orderId}/refunds`: authenticate and enforce shopper ownership. | 9 | `POST /api/payment-methods`: enforce authentication; create a setup token from the ephemeral card and stable merchant customer reference, then create a permanent payment token from that setup token. | 10 | `GET /api/payment-methods`: list only locally owned active methods. | 11 | `GET /api/my-orders`: query only caller-owned existing orders and project the local order plus current persisted payment/authorization/capture/refund state. ## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

All calls are throw-only; there are no `…Result` no-throw variants. `prefer: "return=representation"` is required on writes whose response fields are persisted.

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the SDK wrapper's DI lifetime determine connection reuse and disposal safety. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential placement, token caching, and rotation determine whether secrets and tokens are safely reused. **MUST load `dotnet-authentication`** before setting `Oauth2`.

⚠ Steps 4–12 (endpoint calls) — optional parameters without C# defaults will mis-bind or fail compilation in positional calls, and response payloads are not all shaped alike. **MUST load `dotnet-calling-endpoints`** before the first operation call.

⚠ Steps 4–12 (models) — generated required members, init-only records, nullable fields, string-enum construction/comparison, and wire names determine valid payloads and safe reads. **MUST load `dotnet-models`** before constructing requests.

⚠ Steps 4–12 (write retries, timeout, pagination, logging) — transport retry behavior can resend POSTs, timeout layers can leave ambiguous writes, paging is caller-owned, and logging can expose payment data unless explicitly controlled. **MUST load `dotnet-configuration-resilience`** before configuring the client or retrying/paging calls.

⚠ Steps 4–12 (error boundary) — Case A typed errors, Case B raw errors, raw fallback accessors, and status preservation require distinct catch paths. **MUST load `dotnet-error-handling`** before writing any catch ladder.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 13 (tests) — fake the HTTP transport seam rather than generated concrete controllers, and assert observable integration behavior across provider responses. **MUST load `dotnet-testing`** before writing tests.

## 5. Assumptions & Blockers

### Assumptions

- The configured PayPal merchant has the direct-card and vault capabilities stated in the task; the SDK map confirms the required operations but cannot confirm an account's live entitlements.
- `PayPal:Environment` is validated as Sandbox because `ServerEnvironment.Sandbox` is the only environment member in this SDK release. `PayPal:BaseUrl`, when supplied, still selects that sandbox server node but replaces its base URL verbatim.
- A full refund means the unrefunded remainder of the one capture. The application still enforces the captured ceiling locally before PayPal is called.
- Transaction reconciliation intentionally uses balance-affecting transaction records (`balance_affecting_records_only=Y`) and `transaction_info`, which carry capture/refund amount, fee, IDs, status, and invoice/custom matching fields. Authorization holds are reconciled through the persisted order/payment state and payment GET operations rather than treated as ledger movement.

### Blockers

- None. The mapped SDK surface covers order authorization, authorization renewal/capture/void, refunds, two-step card vaulting and token use, complete paged transaction search, and the all-calls base URL override.
