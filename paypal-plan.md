## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (client registration) — client/`HttpClient` ownership and the DI extension’s unnamed-client behavior can change handler scope and socket lifetime. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential timing, rotation and token-strategy ownership determine whether OAuth uses current configuration. **MUST load `dotnet-authentication`** before wiring authentication.

⚠ Step 1 (base URL/resilience) — server-node selection, whole-call cancellation, retry eligibility, and transport retries can change which host is called and whether a write is sent again. **MUST load `dotnet-configuration-resilience`** before configuring the client.

⚠ Step 4/6 (request models) — nullable model members do not establish provider acceptance; enum and record construction plus JSON wire names must match generated types. **MUST load `dotnet-models`** before constructing card, vault, order, money, capture, or refund models.

⚠ Step 4/6 (operation calls) — nullable parameters without defaults must still be passed, and named arguments must use the literal generated names. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 4–12 (error boundary) — typed versus raw error cases and unknown write outcomes require different access paths and reconciliation behavior. **MUST load `dotnet-error-handling`** before writing any catch ladder.

⚠ Step 12 (tests) — the supported fake seam and behavior-first test boundary determine whether tests survive SDK regeneration. **MUST load `dotnet-testing`** before writing integration tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The access-control paragraph explicitly names fulfil, cancel, and reconciliation as administrator actions and says every other endpoint is shopper-scoped; therefore `/refunds` is implemented as authenticated shopper-owned despite the earlier narrative calling refund an operator flow. This is an application authorization decision, not an SDK fact.
- Currency has one configured value per running deployment. Existing orders snapshot that currency and their catalog-derived total; changing configuration never changes an existing payable amount.
- A merchant customer reference sent to Vault is an opaque stable application identifier, never an email address or bearer-token claim with disclosure risk.
- A recent, empty transaction-search response is returned as a valid empty provider report with its range/refresh metadata; it is not classified as a reconciliation gap solely because sandbox reporting lags.

### Blockers

- None. The map covers order authorization, capture, void, refund, direct-card vaulting/reuse, token retrieval/deletion, and transaction search. Direct-card reauthorization eligibility is deliberately provider-decided by the documented operation; the mandated actionable replacement/re-entry paths handle an authorization that cannot be renewed.
