# PayPal .NET SDK integration plan — eShopOnWeb

## 1. Scope & sequence

1. Register the sandbox SDK client and OAuth client-credentials authentication.
2. Expose PublicApi order creation and payment initiation: create an `AUTHORIZE` order, then authorize or confirm it with a direct card or a saved vault token; capture immediately for pay-now flows where the order intent is `CAPTURE`.
3. Save/list/delete customer payment tokens through Vault and use the token as the payment source for later orders.
4. Fulfil orders by inspecting the authorization, reauthorizing a stale authorization when permitted, then capturing; support void/cancel.
5. Refund captured payments fully or partially with a caller-supplied idempotency key.
6. Reconcile operators with TransactionSearch over the complete requested date range, manually advancing the SDK's page parameter.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal C# identifier. The cancellation-token parameter really is named `ct`: in named arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

⚠ A request model may mark nothing required, and then `required?` selects nothing for you. Carry the Notes-named fields tied to acceptance; the map Notes do not make any additional field mandatory for these flows.

### Client, authentication, server, and SDK-wide facts

- NuGet package: `AsadAli.Checkout.Sdk` (version-less installation per the map); root namespace `PayPalServerSdk`; target `netstandard2.0`.
- Construct `new PayPalServerSdk.PayPalServerSdkClient(HttpClient httpClient, PayPalServerSdk.PayPalServerSdkClientOptions options)`, or use `AddPayPalServerSdkClient`. `Environment` is `PayPalServerSdk.Servers.ServerEnvironment`; select `ServerEnvironment.Sandbox`. Options also expose `Retry`, `Logging`, `Server`, `Oauth2`, and `Oauth2TokenStrategy`.
- OAuth is client credentials: `PayPalServerSdk.Core.Authentication.OAuth2.ClientCredentials.OAuth2ClientCredentials` with `ClientId`, `ClientSecret`, optional `Scope`; assign to `options.Oauth2`. The SDK map also exposes `Oauth2TokenStrategy` (`IOAuth2TokenStrategy<OAuth2ClientCredentials>?`). Load credentials from the application's configuration binding, using the sandbox credentials supplied for this task; do not hardcode secrets or invent configuration key names.
- The SDK is throw-only: no `…Result` variants. `SdkException<TError>` is in `PayPalServerSdk.Core.Exceptions`; typed errors are in `PayPalServerSdk.Errors`; `RawError` is in `PayPalServerSdk.Core.ErrorResponse`.

## 3. Trap notes

⚠ Step 1 (client registration) — the SDK client and the supplied `HttpClient` have lifetime/handler-rotation consequences, and server/base-URL overrides are nested under server and environment. **MUST load `paypal-sdk:dotnet-client-initialization`** and **MUST load `paypal-sdk:dotnet-configuration-resilience`** before wiring the client.

⚠ Step 1 (credentials) — the accepted OAuth property, credential loading, token refresh, and sandbox selection must agree; a 401/403 can be configuration-shaped. **MUST load `paypal-sdk:dotnet-authentication`**.

⚠ Steps 2–6 (calls) — nullable parameters without C# defaults must still be passed, and named `ct:` is the only cancellation-token identifier. **MUST load `paypal-sdk:dotnet-calling-endpoints`**.

⚠ Steps 2–5 (models) — direct cards, vault tokens, stored credentials, and generated string enums have model/wire-name and construction hazards; card numbers also create PCI scope. **MUST load `paypal-sdk:dotnet-models`**.

⚠ Steps 2–6 (errors) — typed Case A accessors differ from Case B `RawError`, and status handling must preserve retry/idempotency decisions. **MUST load `paypal-sdk:dotnet-error-handling`**.

⚠ Steps 3–6 (resilience) — retrying non-idempotent writes, stale authorization renewal, per-attempt timeout, and manual page loops affect duplicate charges and reconciliation completeness. **MUST load `paypal-sdk:dotnet-configuration-resilience`**.

⚠ Step 7 (tests) — the SDK's `HttpClient` constructor is the fake-handler seam; test both status and transport-failure paths, including write-once behavior. **MUST load `paypal-sdk:dotnet-testing`**.

- `paypal-sdk:dotnet-configuration-resilience` · retries, timeouts, server selection, logging, and manual pagination.
- `paypal-sdk:dotnet-testing` · `HttpClient` fake-handler seam and error/transport test coverage.

System.Text.Json.JsonException reaches the boundary from two directions and they need opposite handling:

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

- The user supplied sandbox credentials/configuration to the deployment, but no literal values or application configuration binding keys were included in this brief; bind the supplied values through the application's existing configuration path. No invented key names are part of this plan.
- “PublicApi JWT endpoints” is treated as an application-routing requirement. The SDK contract supplies OAuth client-credentials authentication; JWT issuance/validation and PublicApi route design are application decisions, not SDK facts. **YOUR CALL — not in the map.**
- The map has no dedicated transaction-reconciliation operation beyond `SearchTransactions`; complete-range reconciliation must manually drive its `page` query parameter and accept the documented three-year/three-hour reporting limits.
- Direct PAN/CVV card submission is represented by `CardRequest`; the map explicitly notes PCI SAQ D implications. Hosted-fields/tokenized input is an application/payment-page decision. **YOUR CALL — not in the map.**
