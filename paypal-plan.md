## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Reconciliation runtime correction

| Existing defect | Precise correction | Source |
|---|---|---|
| Gateway sends caller `to` verbatim (the failing request sent `UtcNow + 5 minutes`) and formats with round-trip `"O"`; `"O"` is syntactically allowed because fractional seconds and offsets are valid RFC3339, but future-bound acceptance is not in the SDK contract. | Compute `now = DateTimeOffset.UtcNow`; `effectiveTo = to.ToUniversalTime() > now ? now : to.ToUniversalTime()`; validate `fromUtc < effectiveTo`, `effectiveTo - fromUtc <= TimeSpan.FromDays(31)`, and the documented three-year lookback; format both with `ToString("yyyy-MM-dd'T'HH:mm:ss'Z'", CultureInfo.InvariantCulture)`. The clamp is defensive (`YOUR CALL`), while the format/range constraints are mapped. | `Api/TransactionSearch.cs`; future clamp is YOUR CALL — not in the map |
| Gateway catches `SdkException<RawError>` and discards its body, leaving no way to know which deterministic query rule caused HTTP 400. | In that catch, read `var providerBody = ex.Error.ReadAsString();` and carry a sanitized form plus `(int)ex.Error.StatusCode` through `PayPalProviderException`. Do not call a nonexistent typed accessor. A best-effort JSON projection may be attempted, but its live shape is `UNVERIFIED`; always retain the raw diagnostic fallback. | `operations/TransactionSearch.md`; `sdk-map.md` |

## 3. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the DI helper's registration shape affect connection reuse. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (credentials) — credential placement, secret rotation, and token strategy ownership are not settled by the option names. **MUST load `dotnet-authentication`** before wiring authentication.
- ⚠ Step 1 (base URL/retries/timeouts) — retry triggers, transport retries on writes, total-call timing, custom-server selection, pagination, and logging have consequences beyond the visible options. **MUST load `dotnet-configuration-resilience`** before configuration.
- ⚠ Step 3 (endpoint calls) — optional parameters without C# defaults can silently mis-bind positional calls; response models are returned directly rather than through a uniform envelope. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Step 3 (models) — required init members, nullable-but-provider-significant fields, `StringEnum<T>` values, and unknown-field behavior affect every request and response mapper. **MUST load `dotnet-models`** before constructing payloads.
- ⚠ Steps 3–9 (error boundary) — Case A typed errors and the Case B transaction-search error expose different safe access paths; retryability and HTTP translation must follow the actual exception shape. **MUST load `dotnet-error-handling`** before writing any catch ladder.
- ⚠ Steps 3–9 (2xx drift) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Steps 3–9 (non-2xx drift) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 10 (tests) — faking generated controllers couples tests to SDK internals; the reusable `HttpClient`/handler is the protocol seam. **MUST load `dotnet-testing`** before writing integration-layer tests.

## 5. Assumptions & Blockers

### Assumptions

- One PayPal purchase unit represents one eShop order. At order creation the application persists `paymentReference = "eshop-" + Guid.NewGuid().ToString("N")`; both `invoice_id` and `custom_id` carry that globally unique value for merchant-wide uniqueness and reconciliation. The local numeric order ID remains an API/database identifier and is consulted during reconciliation only as a legacy fallback for old provider records. This is an application mapping, not an SDK requirement.
- Direct vaulting uses `Vault.CreatePaymentToken` with `PaymentTokenRequest.PaymentSource.Card` and the authenticated shopper's stable application identifier in `customer.merchant_customer_id`; no setup-token/browser flow is planned because the requested sandbox account permits direct card vaulting.
- Saved-card payments use `OrderAuthorizeRequestPaymentSource.Card.VaultId`. Because the shopper explicitly initiates each later order, the stored-credential metadata is `PaymentInitiator.Customer`, `StoredPaymentSourcePaymentType.OneTime`, and `StoredPaymentSourceUsageType.Subsequent`.
- Reauthorization is attempted through `Payments.ReauthorizePayment` after the documented honor period and before its documented outer authorization window; a typed refusal is surfaced with PayPal's error name, issue, description and debug ID as the operator-actionable “cannot renew” outcome. The SDK map describes this operation as reauthorizing an “authorized PayPal account payment” and does not separately guarantee direct-card eligibility.
- Provider statuses and identifiers are persisted as returned. Pending captures/refunds are refreshed with their corresponding GET operation before the application claims a terminal financial state.
- `PayPal:BaseUrl`, when non-empty, is trusted as a complete verbatim base address and assigned to `options.Server.Default.Sandbox.BaseUrl`; URI validity is checked at startup without rewriting it.

### Blockers

- None. The SDK map contains operations for order authorization, authorization retrieval/reauthorization/capture/void, capture refund, direct card vaulting/token deletion, and paged transaction search. The reauthorization scope caveat above requires defensive operator-facing handling but does not prevent implementing the required attempt-and-report behavior.
