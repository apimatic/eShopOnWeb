# PayPal .NET SDK integration plan for eShopOnWeb PublicApi

## 1. Scope & sequence

1. Add and register the pinned `AsadAli.Checkout.Sdk` 1.0.1 client; configure OAuth2 and the sandbox/server node.
2. Create checkout orders with `Orders.CreateOrder`, then use the returned order ID with `Orders.AuthorizeOrder` or `Orders.CaptureOrder` after buyer approval. Use `Orders.GetOrder` for reconciliation of the order resource.
3. For an authorization ID, use `Payments.GetAuthorizedPayment`, `Payments.CaptureAuthorizedPayment`, or `Payments.VoidPayment`; use `Payments.GetCapturedPayment` and `Payments.RefundCapturedPayment`/`Payments.GetRefund` for settlement and refunds.
4. Implement saved-card/vault lifecycle with `Vault.CreateSetupToken`, `Vault.GetSetupToken`, `Vault.CreatePaymentToken`, `Vault.GetPaymentToken`, `Vault.ListCustomerPaymentTokens`, and `Vault.DeletePaymentToken`. Use the resulting payment-token ID in the checkout payment source as specified by the model rows.
5. Reconcile provider activity with `TransactionSearch.SearchTransactions` and account balances with `TransactionSearch.SearchBalances`; persist the application’s own cursor/last-run and provider IDs according to the application design.
6. Put all SDK calls behind the application’s error boundary. Supply `payPalRequestId` on write operations where the generated signature exposes it, and make retry/replay decisions using the required resilience guidance.

## 2. CONTRACT SHEET

**Signatures are generated code, verbatim — every parameter name is the literal C# identifier. The cancellation-token parameter really is named `ct`: in named arguments write `ct:`, never `cancellationToken:`.**

**Every SDK type is written fully-qualified with the namespace the map gives it** — take each one from that type's own map row, never from where a neighbouring type sits. A members table names the namespace outright; otherwise the row's source path implies it (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root namespace). Enums, unions, auth, server and client-config types are spread across different child namespaces, and two types configured side by side in the same options object routinely live in different ones. Dropping a type to the root or to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

All operations are async/throw-only; no `…Result` variants exist. All records below are in `PayPalServerSdk.Models`; all enums are in `PayPalServerSdk.Models.Enums`; operation controllers are exposed as client properties. `RequestOptions` is the generated SDK request-options type; its namespace is not specified by the map row and must be taken from the installed package’s public API if referenced. Do not invent a substitute type.

## 3. Trap notes

- ⚠ Step 1 (client registration) — the SDK wrapper and registered `HttpClient` have different lifetime concerns; rebuilding the handler/client pipeline per request can break reuse and resilience. **MUST load `paypal-sdk:dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — credentials must be supplied through the options credential properties and the environment/server node must match the deployment; hardcoded secrets or late credential assignment can produce auth failures. **MUST load `paypal-sdk:dotnet-authentication`** before wiring credentials.
- ⚠ Step 2 (endpoint calls) — generated nullable parameters without C# defaults must be passed explicitly, and optional-heavy search/list calls can bind incorrectly positionally. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before writing calls.
- ⚠ Step 2/4 (models) — generated records use wire names distinct from C# names, and stored payment sources/tokens have nested model shapes. **MUST load `paypal-sdk:dotnet-models`** before constructing payloads or mapping responses.
- ⚠ Step 3/4 (idempotency and retries) — a transport failure can replay a write, while retry/timeout settings do not express the application’s whole-operation idempotency policy. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before configuring retries, timeout, server selection, or logging.
- ⚠ Step 6 (error boundary) — typed and raw errors use different accessors, and an accessor is not interchangeable across error classes. **MUST load `paypal-sdk:dotnet-error-handling`** before writing catches or translation middleware.
- ⚠ Step 7 (tests) — the test seam is the SDK’s `HttpClient` constructor, and tests must assert integration behaviour rather than SDK internals. **MUST load `paypal-sdk:dotnet-testing`** before stubbing calls.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary. These rows belong in the FIRST sheet, not a later revision: the boundary is written early, and a caveat that arrives afterwards arrives too late to shape it.
