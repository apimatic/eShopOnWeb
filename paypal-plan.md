## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency and state directives forced by the SDK surface

| Directive | Exact consequence | Source |
|---|---|---|
| Stable PayPal request IDs | `CreateOrder`, `AuthorizeOrder`, `ReauthorizePayment`, `CaptureAuthorizedPayment`, `VoidPayment`, `RefundCapturedPayment`, and `CreatePaymentToken` each expose `payPalRequestId`; reuse one persisted stable value for retries of the same logical write. A refund's caller key is the exact `payPalRequestId` and a local unique key for that capture. `DeletePaymentToken` exposes no request-ID parameter, so local serialized state/ownership is the idempotency guard. | operation pages above |
| Local concurrency | Claim a payment/refund state transition atomically before the remote write; record request key and resulting provider ID/status; on repeat, return/refresh the same logical result rather than starting another write. | YOUR CALL — not in the map |
| Amount invariant | Build PayPal amount from the persisted catalog-priced local total and configured currency; compare every returned authorization/capture/refund currency/value to the intended values before advancing local state. | YOUR CALL — not in the map |
| Full versus partial refund | SDK Notes require empty JSON payload for full refund and `amount` for partial. The SDK does not maintain cumulative application limits; the local capture/refund ledger must prevent requested cumulative refunds from exceeding captured value. | `operations/Payments.md`; `records-2-Pa-Ve.md` |

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the DI extension determine whether sockets and handlers are safely reused. **MUST load `paypal-sdk:dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential construction, token caching, and secret rotation have behavior the options property alone does not show. **MUST load `paypal-sdk:dotnet-authentication`** before wiring credentials.

⚠ Steps 4–9 (endpoint calls) — nullable parameters without defaults still must be supplied and list/search positional calls are especially easy to mis-bind. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before the first call.

⚠ Steps 4–9 (models) — required/init-only fields, string-enum construction, optional response members, and wire-name/C#-name differences can silently produce invalid or unreadable payloads. **MUST load `paypal-sdk:dotnet-models`** before constructing payloads.

⚠ Steps 4–9 (errors) — each operation's typed-versus-raw error case and accessor ladder differ, so a catch-all guessed from one operation loses actionable status/body data. **MUST load `paypal-sdk:dotnet-error-handling`** before writing the boundary.

⚠ Step 1 and write steps (resilience) — retry triggers, transport failures on writes, timeout bounds, manual pagination, base-server selection, and logging/redaction can change idempotency and card/secret exposure. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before client tuning or logging.

⚠ Step 10 (tests) — the safe seam for simulating generated-SDK traffic and errors must not couple tests to generated controller internals. **MUST load `paypal-sdk:dotnet-testing`** before writing integration tests.

⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- One PayPal purchase unit represents one eShop order; the configured currency is used for the entire order, authorization, capture, and refunds.
- A PayPal payment token is created directly from the supplied card through `CreatePaymentToken`; no setup-token/browser approval flow is added.
- The application persists the PayPal customer ID returned with the first token plus its own stable merchant-customer correlation, and always gates token lookup/use/delete by the authenticated local owner.
- Reconciliation joins on every persisted provider ID plus the stable invoice/custom correlation; matching policy and the HTTP response DTO are application decisions.

### Blockers

- None.
