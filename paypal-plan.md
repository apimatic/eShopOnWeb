## 1. Scope & sequence

The main agent owns repo layout, DI wiring location, and config plumbing. The SDK-facing steps, in
dependency order:

1. **Client & DI setup** — register one long-lived `PayPalServerSdkClient` via
   `AddPayPalServerSdkClient(...)`; set OAuth2 client-credentials + environment + (optional) base-URL
   override in the callback. (Caps 10.)
2. **Authentication** — supply `ClientId`/`ClientSecret` from configuration. (Cap 10.)
3. **Vault a card** — `client.Vault.CreatePaymentToken(...)` from raw card; read vault id + safe
   display data; `client.Vault.DeletePaymentToken(...)` to remove. (Cap 8.)
4. **Authorize a payment** — `client.Orders.CreateOrder(...)` with `intent=AUTHORIZE` and a card
   payment source (raw card = cap 1; `card.vault_id` = cap 2), then `client.Orders.AuthorizeOrder(...)`;
   read authorization id + status. Idempotency key on both. (Caps 1, 2, 7, 11.)
5. **Capture** — `client.Payments.CaptureAuthorizedPayment(...)`; read captured amount + fee + net.
   Idempotency key. (Caps 3, 7.)
6. **Reauthorize** — `client.Payments.ReauthorizePayment(...)` before capture on a stale hold; detect
   non-reauthorizable via typed error. (Cap 4.)
7. **Void** — `client.Payments.VoidPayment(...)` to release the hold. (Cap 5.)
8. **Refund** — `client.Payments.RefundCapturedPayment(...)` full or partial; per-request idempotency
   key; read refund id + status. (Caps 6, 7.)
9. **Transaction search** — `client.TransactionSearch.SearchTransactions(...)`; page across the whole
   range. (Cap 9.)

## CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal C# identifier. The
> cancellation-token parameter really is named `ct`: in named arguments write `ct:`, never
> `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take each one
> from that type's own map row, never from where a neighbouring type sits. Enums, unions, auth, server
> and client-config types are spread across different child namespaces, and two types configured side
> by side in the same options object routinely live in different ones. Dropping a type to the root or
> to `.Models` makes the implementer guess the wrong `using`, and the build breaks.

### Client construction, auth, environment, base URL (source-confirmed)

`PayPalServerSdkClientOptions` properties (map `sdk-map.md`): `Environment: ServerEnvironment`,
`Retry: RetryOptions`, `Logging: LoggingOptions`, `Server: ServerOptions`,
`Oauth2: OAuth2ClientCredentials?`, `Oauth2TokenStrategy: IOAuth2TokenStrategy<OAuth2ClientCredentials>?`.

- **Constructor**: `new PayPalServerSdkClient(HttpClient httpClient, PayPalServerSdkClientOptions options)`.
- **DI**: `services.AddPayPalServerSdkClient(o => { /* set o.Oauth2, o.Environment, o.Server */ });`
  (`ServiceCollectionExtensions.cs`).
- **Auth (bearer)**: set `o.Oauth2 = new OAuth2ClientCredentials { ClientId = "...", ClientSecret = "...", Scope = null }`.
  `ClientId` and `ClientSecret` are `required`; `Scope` is `string?` (optional). The SDK performs the
  `POST /v1/oauth2/token` client-credentials exchange itself, caches the token, and attaches
  `Authorization: Bearer <token>` to every call — **you do not build a bearer header yourself**
  (source: `OAuth2ClientCredentialsStrategy.cs`, `OAuth2Scheme.cs`).
- **Environment**: `o.Environment = ServerEnvironment.Sandbox`. `Sandbox` is the ONLY member the map/
  source exposes (`Servers/ServerEnvironment.cs`). There is no `Production`/`Live` member in this SDK
  release — see Assumptions & Blockers.
- **Base-URL override (cap 10)** — SUPPORTED and verbatim: `o.Server.Default.Sandbox.BaseUrl = "<url>"`.
  Path: `ServerOptions.Default` (`DefaultOptions`) `.Sandbox` (`SandboxOptions`) `.BaseUrl` (`string`,
  default `https://api-m.sandbox.paypal.com`). **This override is honored by EVERY call including the
  OAuth2 token request** — the token URL is built as `server.Default("/v1/oauth2/token")`, resolved from
  the same `Sandbox.BaseUrl` (source-confirmed: `AuthSchemes.cs`, `Servers/DefaultOptions.cs`). So a
  configured `PayPal:BaseUrl` naturally routes token + all API traffic to the same host. When
  `PayPal:BaseUrl` is unset, leave the default in place.

### Idempotency (caps 6, 7) — how to set PayPal-Request-Id

There is **no** request-options helper for this header — it is a **dedicated string parameter**
`payPalRequestId` on each write operation. Pass your caller-supplied key there; pass `null` to omit.
Operations that accept it: `CreateOrder`, `AuthorizeOrder`, `CaptureOrder`, `CaptureAuthorizedPayment`,
`ReauthorizePayment`, `VoidPayment` (named `payPalRequestId`, different position — see rows),
`RefundCapturedPayment`, `CreatePaymentToken`, `CreateSetupToken`. Same key ⇒ PayPal returns the original
result (no double charge); two DISTINCT keys for two partial refunds of one capture ⇒ both succeed.

### Payment source construction (caps 1, 2, 11)

- **Raw card (cap 1) — CONFIRMED shape.** `OrderRequest.PaymentSource` is type `PaymentSource`
  (records-2 `Models/PaymentSource.cs`); `new PaymentSource { Card = new CardRequest { ... } }` is correct
  (`Card (card): CardRequest?`). **`CardRequest` has NO `!req` fields** — all are optional, so setting only
  `Number`, `Expiry`, `SecurityCode`, `Name` compiles and is a valid plain sandbox card auth. `CardRequest`
  (records-1 `Models/CardRequest.cs`) full field list: `Name (name): string?`, `Number (number): string?`
  (`"4111111111111111"`), `Expiry (expiry): string?` (`"YYYY-MM"`, future), `SecurityCode (security_code): string?`,
  `BillingAddress (billing_address): Address?`, `Attributes (attributes): CardAttributes?`,
  `VaultId (vault_id): string?`, `SingleUseToken (single_use_token): string?`,
  `StoredCredential (stored_credential): CardStoredCredential?`, `NetworkToken (network_token): NetworkToken?`,
  `ExperienceContext (experience_context): CardExperienceContext?`. `StoredCredential` and `ExperienceContext`
  are **optional and irrelevant to a plain sandbox card auth** — leave both unset (they drive stored-
  credential/card-on-file semantics and 3DS return/cancel URLs respectively).
- **Vaulted card (cap 2)** — reference the saved card by setting **`CardRequest.VaultId (vault_id): string?`**
  = the vault id returned from `CreatePaymentToken` (do NOT resend PAN). ⚠ Do **not** use the `Token`
  payment source for a vaulted *card*: `Token.Type` is `TokenType`, whose ONLY value is
  `BillingAgreement (BILLING_AGREEMENT)` — that path is for PayPal-wallet billing agreements, not cards.
- **Billing address for AVS (optional)** — `CardRequest.BillingAddress` and vault
  `PaymentTokenRequestCard.BillingAddress` are both type `Address` (records-1 `Models/Address.cs`). Fields:
  `AddressLine1 (address_line_1): string?`, `AddressLine2 (address_line_2): string?`,
  `AdminArea2 (admin_area_2): string?` (city), `AdminArea1 (admin_area_1): string?` (state/province),
  `PostalCode (postal_code): string?`, **`CountryCode (country_code): string !req`** (the ONLY required
  field — 2-letter ISO). If you set `BillingAddress` at all, `CountryCode` must be provided.
- **Reconciliation stamp (cap 9 ↔ orders)** — `PurchaseUnitRequest` (records-2 `Models/PurchaseUnitRequest.cs`)
  carries all three echo-back fields, all optional strings: `ReferenceId (reference_id): string?`,
  `CustomId (custom_id): string?`, `InvoiceId (invoice_id): string?`. Stamp your eShop order id onto
  `CustomId` and/or `InvoiceId` at CreateOrder; these come back in transaction search as
  `TransactionInfo.CustomField` / `TransactionInfo.InvoiceId` (note: `custom_id` → `custom_field` on the
  search side). `ReferenceId` distinguishes multiple purchase units within one order.
- **Amount to the cent (caps 1)** — `PurchaseUnitRequest.Amount (amount): AmountWithBreakdown !req` with
  `CurrencyCode (currency_code): string !req` + `Value (value): string !req`. `Value` is a **decimal
  string** (e.g. `"49.99"`), NOT a number — format the order total as a fixed-2-decimals string in the
  configured currency so the held amount equals the total to the cent. `Money` (used by capture/refund/
  reauthorize) has the same two `!req` string fields.

### Challenge / 3DS detection (cap 11) — stop, do not build an approval round-trip

- **Primary signal:** `Order.Status` / `OrderAuthorizeResponse.Status` == `OrderStatus.PayerActionRequired`
  (wire `PAYER_ACTION_REQUIRED`). When present, STOP and report — a browser approval is required.
- **Card 3DS liability:** on the response payment source,
  `PaymentSourceResponse.Card (CardResponse)` → `AuthenticationResult (AuthenticationResponse)` →
  `LiabilityShift (LiabilityShiftIndicator)` — values `No (NO)`, `Possible (POSSIBLE)`, `Unknown (UNKNOWN)`;
  a non-`No` shift plus a pending/action-required status is the "shopper must approve" case. Do not
  auto-follow HATEOAS approval links.

### Transaction search — detail shape for reconciliation (cap 9)

`SearchResponse.TransactionDetails` is `IReadOnlyList<TransactionDetails>?` (records-2). Each
`TransactionDetails` (records-2 `Models/TransactionDetails.cs`) nests the reconciliation values under
`TransactionInfo (transaction_info): TransactionInformation?`. Full accessor paths from `td`
(`TransactionInformation`, records-2 `Models/TransactionInformation.cs`):

| Reconciliation value | Accessor path | C# type (wire name) |
|---|---|---|
| PayPal transaction id (equals capture id / refund id) | `td.TransactionInfo.TransactionId` | `string?` (`transaction_id`) |
| Transaction amount | `td.TransactionInfo.TransactionAmount` | `Money?` (`transaction_amount`) → `.Value` (decimal string), `.CurrencyCode` |
| Fee (PayPal fee on the txn) | `td.TransactionInfo.FeeAmount` | `Money?` (`fee_amount`) |
| Transaction status | `td.TransactionInfo.TransactionStatus` | **`string?`** (`transaction_status`) — a plain string here, NOT the `CaptureStatus`/`RefundStatus` enum |
| Initiation date/time | `td.TransactionInfo.TransactionInitiationDate` | `string?` (`transaction_initiation_date`) — ISO-8601 string |
| Updated date/time | `td.TransactionInfo.TransactionUpdatedDate` | `string?` (`transaction_updated_date`) — ISO-8601 string |
| Invoice id echoed back | `td.TransactionInfo.InvoiceId` | `string?` (`invoice_id`) |
| Custom field echoed back | `td.TransactionInfo.CustomField` | `string?` (`custom_field`) |

To line PayPal's ledger up against eShop orders: match `td.TransactionInfo.TransactionId` to your stored
capture/refund id, and/or read back your own stamp via `InvoiceId` / `CustomField` (see the
`PurchaseUnitRequest` reconciliation-stamp fields below). `td` also carries `PayerInfo`, `ShippingInfo`,
`CartInfo`, `StoreInfo`, `AuctionInfo`, `IncentiveInfo` (all optional, not needed for reconciliation).
UNVERIFIED against live: whether `custom_field`/`invoice_id` are always echoed for card-funded
transactions — read defensively (null-check each) and fall back to `TransactionId` matching.

### Transaction search — paging the whole range (cap 9)

- **Date format:** `start_date`/`end_date` are ISO-8601 **date-time with offset** strings (e.g.
  `2026-01-01T00:00:00-0000`), passed as the `startDate`/`endDate` string params — the SDK does not take
  `DateTime`. UNVERIFIED whether PayPal accepts a bare date; format as full ISO-8601 date-time with
  offset defensively.
- **Iterate all pages:** `SearchResponse.TotalPages (total_pages): int?` and `Page (page): int?` — there
  is NO SDK auto-pager (map: pagination none). Loop `page = 1..TotalPages`, calling with named
  `page:`/`pageSize:`, accumulating `TransactionDetails`. Start from the first response's `TotalPages`;
  stop when `page > TotalPages` or the list is empty. `pageSize` max per PayPal is bounded — keep the
  `100` default unless tuned. Do not read only page 1.

## Trap notes (load the named skill before writing that step)

> ⚠ Step 1 (client & DI) — the SDK client wraps one long-lived `HttpClient`; whether it may be rebuilt
> per request or must come from `IHttpClientFactory`, and which lifetime the wrapper takes, is not
> visible in the constructor. **MUST load `dotnet-client-initialization`** before wiring DI.

> ⚠ Step 1/2 (auth) — whether credentials must be set before construction vs. in the DI callback, and
> how the cached bearer token is refreshed/rotated, is not shown by the `Oauth2` property. **MUST load
> `dotnet-authentication`** before wiring credentials.

> ⚠ Step 1 (resilience) — `RetryOptions.HttpMethodsToRetry` gates only the **status-code** retry
> trigger; what happens to a non-idempotent `POST` on a **transport** failure, and what `Timeout`
> actually bounds (per-attempt vs. whole call), are not on the option names — this matters directly for
> authorize/capture/refund double-execution. **MUST load `dotnet-configuration-resilience`** before
> tuning retries/timeouts/base-URL.

> ⚠ Steps 3–9 (building bodies) — `Money`/`AmountWithBreakdown` `Value` is a decimal STRING not a
> number; enums are `StringEnum<T>` built via `Enum.FromValue(...)`/static members, not C# enums; and
> unmodeled JSON fields are dropped on deserialize. **MUST load `dotnet-models`** before constructing
> any request payload.

## REQUIRED READING — load BEFORE implementation starts

These `dotnet-*` companion skills carry the defaults, worked examples, and gotchas this sheet
deliberately does **not** restate. Load each before writing the step it governs:

| Skill | Governs |
|---|---|
| `dotnet-client-initialization` | Step 1 — client construction, `HttpClient` lifetime, DI registration |
| `dotnet-authentication` | Step 2 — supplying `OAuth2ClientCredentials`, token refresh/rotation |
| `dotnet-configuration-resilience` | Step 1 — retries/backoff, timeout semantics, base-URL selection, paging |
| `dotnet-calling-endpoints` | Steps 3–9 — named-argument calls, request/response envelopes, async/cancellation |
| `dotnet-models` | Steps 3–9 — building request models, `StringEnum`, required/nullable, wire names |
| `dotnet-error-handling` | Every step — the Case A/B boundary, reading status + error body safely |
| `dotnet-testing` | Tests — faking the `HttpClient` seam |

**Mandatory error-boundary hazards (`System.Text.Json.JsonException` reaches the boundary from two
directions — opposite handling):**

- A drifted or malformed **2xx** body (a missing `required` member — e.g. `Money.Value`,
  `SellerReceivableBreakdown.GrossAmount`, `Error.Message`) surfaces as a `JsonException` from
  deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape
  the integration boundary.
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws
  `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the
  `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException`
  to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries
  something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## Assumptions & Blockers

1. **No live/production environment member (cap 10).** `ServerEnvironment` exposes only `Sandbox`
   (map *Servers & auth*; source `Servers/ServerEnvironment.cs`). To point at PayPal Live you must set
   `o.Server.Default.Sandbox.BaseUrl` to the live host (`https://api-m.paypal.com`) — there is no
   `Live`/`Production` enum member, and the base-URL slot is literally named `Sandbox`. This is a real
   SDK limitation for this release, not an omission in the sheet. The task's configurable
   `PayPal:BaseUrl` is the correct override and covers this.
2. **`CaptureOrder` vs. `CaptureAuthorizedPayment`.** Cap 3 (capture a HELD authorization) uses
   `client.Payments.CaptureAuthorizedPayment(authorizationId, …)` → `CapturedPayment` (carries
   `seller_receivable_breakdown`). `client.Orders.CaptureOrder` is the direct order-capture path (returns
   `Order`) and is NOT the authorize-then-capture flow — assumed out of scope for cap 3. Confirm if the
   app instead wants single-step order capture.
3. **Idempotency-key parameter position varies.** `payPalRequestId` is param #4 on `VoidPayment` but
   #2/#3 elsewhere — rows give the exact per-op position. Use named `payPalRequestId:` to avoid
   mis-binding. Assumed the caller supplies one deterministic key per logical authorize/capture/refund.
4. **Vault-from-setup-token path exists but assumed not needed.** `CreateSetupToken` +
   `CreatePaymentToken` with `Token = VaultTokenRequest{ Type = SetupToken }` is available; cap 8 as
   written (create a payment token directly from raw card) uses `CreatePaymentToken` with a
   `PaymentTokenRequestCard`. Confirm if a two-step setup-token flow is required.
5. **`SearchTransactions` date format (cap 9) is UNVERIFIED against live.** The param is a plain string;
   only live traffic confirms the exact accepted ISO-8601 shape. Directive: format as full ISO-8601
   date-time with offset, and on a Case-B error read `ex.Error.ReadAsString()` to surface PayPal's own
   validation message rather than assuming.
6. No blockers prevent implementation. All ten+one capabilities map to concrete SDK operations; the
   only genuine SDK gap (no Live environment member) has a supported workaround (base-URL override).
