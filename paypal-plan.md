| 6 | On fulfilment, recover the current authorization, reauthorize when its initial honor period is stale but it remains renewable, then capture the exact outstanding authorized amount as a final capture. | 8 | On full/partial refund, reserve the caller key under a unique local constraint, cap the amount at captured minus already refunded/in-flight, and pass that same key as `payPalRequestId`. Persist the returned refund and poll/recover by ID when needed. | `Payments.RefundCapturedPayment`; `Payments.GetRefund` | `operations/Payments.md` |
| 9 | Reconcile an ISO-8601 interval by splitting it into API-supported windows of at most 31 days and, within every window, requesting every `page` through `TotalPages`. ## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

⚠ Step 1 (package) — a version-less install can be newer than the mapped `v1.0.1` contract; any compile drift must be returned to the PayPal SDK agent map-first instead of guessed around. **MUST load `dotnet-calling-endpoints`** before the first operation call.

⚠ Step 2 (client registration) — `HttpClient` ownership and generated-client lifetime determine connection reuse and testability. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 2 (credentials) — credential timing, auth strategy selection, and secret rotation affect every call and a wrong boundary presents as 401/403. **MUST load `dotnet-authentication`** before setting credentials.

⚠ Steps 4–9 (operation calls) — many nullable parameters have no C# default and must be passed explicitly; response resources are not interchangeable and named arguments must match generated identifiers. **MUST load `dotnet-calling-endpoints`** before calling endpoints.

⚠ Steps 4–9 (models) — required/init members, `StringEnum<T>`, JSON wire names, and dropped unmodeled fields can make a compiling payload or mapper wrong. **MUST load `dotnet-models`** before building or reading models.

⚠ Steps 4–9 (errors) — each operation's Case A/Case B boundary and accessor determines whether status/details survive translation. **MUST load `dotnet-error-handling`** before writing any catch/translation layer.

⚠ Steps 2 and 4–9 (resilience) — retry eligibility, transport-failure behavior, timeout scope, base URL, manual pagination, and body logging can duplicate writes, truncate reports, or expose card data if configured incorrectly. **MUST load `dotnet-configuration-resilience`** before configuring the client or retries/logging.

⚠ Step 10 (testing) — the stable seam is the injected HTTP pipeline; faking generated controller internals produces brittle tests. **MUST load `dotnet-testing`** before integration tests.

⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The configured merchant is entitled to direct card processing and Vault v3 in sandbox, as stated in the brief. The SDK's own client summary labels Vault v3 “Available in the US only”; this assumption is necessary outside the stated fixture.
- A shopper payment is customer-initiated and one-time, so saved-card reuse sends `PaymentInitiator.Customer`, `StoredPaymentSourcePaymentType.OneTime`, and `StoredPaymentSourceUsageType.Subsequent` with `CardRequest.VaultId`.
- The application supplies one stable, provider-safe `merchant_customer_id` per shopper and stores the returned PayPal customer ID; the SDK does not define the application's identity mapping.
- The local order total remains immutable after the pay attempt is claimed. Every create/authorize/reauthorize/capture/refund amount is derived from that persisted catalog-priced total and configured currency.
- Fresh transaction-search ranges may be empty because the mapped API documents up to three hours of reporting lag; this is not treated as a capability gap.
- An authorization outside PayPal's renewable period cannot be recreated from a one-off card because the application correctly did not retain PAN/CVC. The operator-facing result must instruct that shopper payment is required again.

### Blockers

- None for the stated sandbox fixture. A live `PAYER_ACTION_REQUIRED` response is the mandated stop condition for verification, not a missing SDK capability and not authorization to build a browser approval flow.
