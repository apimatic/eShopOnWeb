# PayPal implementation plan

## 1. Scope & sequence

| Step | Application work | PayPal operations |
| --- | --- | --- |
| 1 | Bind/validate `PayPal:` configuration, register one long-lived transport and SDK client, and set the shared Default server override so `BaseUrl` covers OAuth token acquisition and API operations. | Client construction/auth |
| 2 | Extend the existing `Order` aggregate with payment/fulfilment/refund state and extend the existing buyer payment-method model; configure EF persistence and migration. | None |
| 3 | Add a shopper-owned order from current catalog prices and configured currency. | None |
| 4 | Authorize an order with a one-off card or the caller's active vault token; persist PayPal order/authorization IDs, status, amount and expiry. | `Orders.CreateOrder`, `Orders.AuthorizeOrder` |
| 5 | Fulfil idempotently; inspect/renew stale authorization once, capture exactly the order total, and persist captured amount, fee and net. | `Payments.GetAuthorizedPayment`, `Payments.ReauthorizePayment`, `Payments.CaptureAuthorizedPayment` |
| 6 | Cancel idempotently before fulfilment and release the authorization. | `Payments.VoidPayment` |
| 7 | Refund by caller key, enforcing the locally captured/refunded ceiling, persisting each PayPal refund, and refreshing a pending refund on idempotent replay. | `Payments.RefundCapturedPayment`, `Payments.GetRefund` |
| 8 | Save/list/delete shopper-owned cards without persisting PAN/CVC. | `Vault.CreatePaymentToken`, `Vault.DeletePaymentToken` |
| 9 | Page through the whole reporting range and compare PayPal transaction/invoice/reference IDs with local orders/payments/refunds. | `TransactionSearch.SearchTransactions` |
| 10 | Build, automated tests, then sandbox authorization/capture/refund and saved-card reuse verification. | All above |

## 3. Trap notes

- Client registration: transport lifetime/ownership errors can exhaust sockets or split OAuth caches — **MUST load `paypal-platforms-team:dotnet-client-initialization`**.
- Authentication: credential/options timing and custom token lifecycle can make calls unauthenticated or refresh incorrectly — **MUST load `paypal-platforms-team:dotnet-authentication`**.
- Calls: optional generated parameters, cancellation and real provider request IDs can silently mis-bind or defeat idempotency — **MUST load `paypal-platforms-team:dotnet-calling-endpoints`**.
- Models: required/init-only members, string-enum semantics and nested response envelopes can serialize or read the wrong shape — **MUST load `paypal-platforms-team:dotnet-models`**.
- Error boundary: typed-vs-raw operation errors and provider correlation details can be lost by a generic catch ladder — **MUST load `paypal-platforms-team:dotnet-error-handling`**.
- A drifted or malformed 2xx body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, not as an `SdkException`, so an SDK-exception-only catch ladder lets it escape — **MUST load `paypal-platforms-team:dotnet-error-handling`**.
- A non-2xx body that does not match its operation's generated error shape throws `System.Text.Json.JsonException` while the error object is being constructed, so it replaces the `SdkException` and the HTTP status is destroyed with it — **MUST load `paypal-platforms-team:dotnet-error-handling`**.
- Resilience/reconciliation: retry eligibility, per-attempt timeout, body logging and manual pagination can duplicate writes, overrun request budgets, leak PAN/CVC or truncate reports — **MUST load `paypal-platforms-team:dotnet-configuration-resilience`**.
- Tests: faking generated controllers instead of the transport produces brittle tests that do not assert the actual PayPal request — **MUST load `paypal-platforms-team:dotnet-testing`**.

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind `PayPal:ClientId`, `ClientSecret`, `Environment`, `Currency`, `BaseUrl` in PublicApi startup and refuse startup when the four required settings are missing/blank, environment is not sandbox for this task, currency is not three uppercase letters, or an optional BaseUrl is not absolute HTTPS. |
| 2 | Secret sourcing & rotation | Development credentials come from PublicApi .NET user-secrets populated from the named environment variables; deployments provide configuration/environment mappings. Options and credentials are built once into singleton SDK/token services, so rotation takes effect on process restart. |
| 3 | Total timeout budget | SDK per-attempt timeout is 15 seconds; each application call links the HTTP request token to a 45-second total deadline. Fulfil may use separate bounded get/reauthorize/capture calls; reconciliation bounds each page independently. |
| 4 | Write-retry ownership | Disable SDK retries for all writes; application retries by repeating stable provider request IDs after an ambiguous result and first reconciling local/provider state. GET reporting/authorization reads may retry transient failures within the total deadline. |
| 5 | Idempotency & ambiguous writes | Every order payment and vault record gets a persisted random reference, avoiding collisions when local integer IDs restart. Create/authorize/capture/reauthorize/void and vault creation derive stable provider request IDs from that reference; refund derives a hash-backed provider key from `(payment reference, caller key)` and has a unique local `(order payment,key)` row. Vault delete has no provider key, so local deletion wins and failed provider cleanup remains retryable. Provider GET/readback plus stored IDs resolves ambiguous calls. |
| 6 | Observability | Log operation name, eShop order/method/refund ID, PayPal resource ID/status and PayPal `debug_id`; never log request bodies or caller DTOs. Provider correlation is warning/error level; successful lifecycle transitions are information level. |
| 7 | Sensitive data | Card request models carry PAN/CVC/name/address. SDK `LogRequestBody` stays off and an explicit logger factory prevents `PAYPALCLIENT_LOG` from enabling body logging. Application logs never interpolate card DTOs. Card fields exist only in request memory and are never attached to EF entities. |
| 8 | Environment selection | One `Default` server group exists. `PayPal:Environment=Sandbox` selects `ServerEnvironment.Sandbox`; blank BaseUrl uses `https://api-m.sandbox.paypal.com`. A nonblank `PayPal:BaseUrl` replaces both resource and OAuth token bases verbatim. Production is deliberately rejected in this sandbox-targeted task build configuration rather than risking misrouted test traffic. |

## 6. Assumptions & Blockers

- Minor assumption: the JWT `ClaimTypes.Name` value is the stable shopper identifier, matching the existing order `BuyerId` convention.
- Minor assumption: the API order shipping address is required because the existing `Order` aggregate requires it; catalog item prices are snapshotted when the order is created.
- Minor assumption: refund is an authenticated shopper action scoped to their own fulfilled order, as the task classifies only fulfil/cancel/reconciliation as operator actions.
- Runtime stop condition: if sandbox responds with a payer/browser challenge, verification stops and reports that response without adding an approval round-trip.
- Blockers: none in the SDK map.
