## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Provider-error boundary directives

- Case A: catch the operation’s exact fully-qualified `SdkException<TypedError>`, call its named typed accessor first, then `TryGetRawError`. Sanitize `Name`, `Message`, `DebugId`, `Details[].Issue/Description`; never echo raw bodies or any request card fields.
- Case B (`SearchTransactions` only): read status/body through `RawError`; log a bounded, redacted diagnostic and map it to the application problem contract.
- A provider decline/validation/conflict is a deterministic payment problem, not automatically a retryable outage. A transport timeout or deserialization failure after a write is ambiguous: keep the operation ledger pending and retry/recover under the same provider request ID.
- Provider status `PayerActionRequired` is an explicit unsupported-challenge outcome for this headless integration, not an authorization success.

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and generated DI shape determine whether sockets and handlers are safely reused. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential timing, scheme-manager behavior, and secret rotation determine whether calls authenticate consistently. **MUST load `dotnet-authentication`** before setting credentials.

⚠ Step 4 (first call) — optional parameters without C# defaults and response-envelope depth can silently mis-bind or read the wrong level. **MUST load `dotnet-calling-endpoints`** before writing calls.

⚠ Steps 4–13 (models) — init-only required members, string-enum construction, nullable response members, and wire-name/C#-name differences can create malformed bodies or unsafe reads. **MUST load `dotnet-models`** before constructing or mapping models.

⚠ Steps 4–13 (error boundary) — each operation’s typed-vs-raw exception case and accessor order determine whether provider rejections retain their status/details. **MUST load `dotnet-error-handling`** before writing any catch ladder.

⚠ Steps 1 and 4–13 (resilience) — retry triggers, write replay, total-call cancellation, base URL selection, pagination, and logging/redaction interact with idempotency and ambiguous outcomes. **MUST load `dotnet-configuration-resilience`** before configuring the client or retrying writes.

⚠ Step 14 (tests) — the generated client’s stable fake seam and behavior-focused assertions determine whether tests survive SDK regeneration. **MUST load `dotnet-testing`** before creating SDK test doubles.

⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The target is the SDK release represented by the bundled map (`v1.0.1`); package installation remains version-less as required, and any compile-time drift is returned to the PayPal SDK agent for a map/source-grounded fix.
- `PayPal:Environment` is `Sandbox`. The mapped SDK exposes only `ServerEnvironment.Sandbox`; a different PayPal account in the same sandbox is supported through different credentials, and a custom endpoint is supported through `PayPal:BaseUrl`.
- The SDK operation Notes document a three-day honor period and a 29-day reauthorization period. They say multiple reauthorizations are possible, while the `ReauthorizeRequest` record summary says only one; this generated-document disagreement is **UNVERIFIED**. The application uses a durable generation/request ID per renewal, attempts renewal when stale, and turns a provider rejection into the required actionable “pay again” outcome rather than guessing.
- `ReauthorizePayment` is the mapped renewal operation. Its Notes call the resource an “authorized PayPal account payment” and do not expressly confirm or reject direct-card authorization renewal; direct-card acceptance is **UNVERIFIED** until sandbox/live traffic. The implementation still uses this sole mapped renewal path and handles a deterministic rejection actionably.
- Direct vault creation is supported by the mapped `CreatePaymentToken` operation and its explicit `PaymentTokenRequestPaymentSource.Card` model; setup-token/browser approval is not part of this direct-card design.
- The public refund endpoint is owner-scoped, not administrator-only, because the task explicitly limits administrator-only actions to fulfil, cancel, and reconciliation even though its narrative also calls refund an operator flow.

### Blockers

- None for the requested sandbox implementation. A real `PAYER_ACTION_REQUIRED` response is a mandated stop condition for live verification, not a missing SDK capability or a reason to add browser approval.
