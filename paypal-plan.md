## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

All operation methods are asynchronous and throw on non-2xx. `RequestOptions` is `PayPalServerSdk.Core.Request.RequestOptions`; cancellation is `System.Threading.CancellationToken`.

## 3. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the SDK wrapper lifetime can create connection or credential-state failures if wired by signature alone. **MUST load `paypal-sdk:dotnet-client-initialization`** before registration.
- ⚠ Step 1 (credentials) — credential creation, rotation, and when the token strategy reads them affect 401 recovery. **MUST load `paypal-sdk:dotnet-authentication`** before wiring secrets.
- ⚠ Step 1 (base URL/retries/timeouts/logging) — retry eligibility, transport failures on writes, timeout scope, custom-server behavior, pagination, and possible sensitive logging affect correctness and duplicate-risk. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before configuration.
- ⚠ Step 3 (calling methods) — optional parameters without C# defaults and the response nesting can silently bind/read the wrong shape. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 3–8 (models) — init-only required members, string-enum behavior, wire names, and nullable response members affect every payload/state transition. **MUST load `paypal-sdk:dotnet-models`** before model construction.
- ⚠ Steps 3–10 (error boundary) — typed versus raw error cases and their accessors differ by operation, changing the safe catch ladder. **MUST load `paypal-sdk:dotnet-error-handling`** before catches/middleware.
- ⚠ Step 11 (tests) — the correct SDK fake seam and assertions must cover effects, errors, ambiguity, and retries without coupling to generated internals. **MUST load `paypal-sdk:dotnet-testing`** before tests.
- ⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.
- ⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The application creates exactly one PayPal purchase unit per eShop order, so one order total maps to one authorization and capture.
- Shopper identity/role enforcement, durable state-transition locking, endpoint DTOs, and local persistence layout are application concerns; the SDK map does not prescribe them.
- Direct `CreatePaymentToken` with the mapped raw-card request is used because the task requires headless vaulting and the Vault operation explicitly accepts `PaymentTokenRequestPaymentSource.Card`; no setup-token/browser flow is introduced.
- Reauthorization is attempted only inside the operation Notes' days 4–29 window. The Notes describe the operation as reauthorizing an authorized PayPal account payment; whether the enabled sandbox accepts it for the direct-card authorization is **UNVERIFIED** until live traffic. Defensively, handle a typed 422/other rejection as “authorization cannot be renewed; shopper must authorize again,” preserving the provider debug ID for operators. Do not silently mark fulfilment successful.
- At 30 days the operation Notes require creation of a new authorized payment rather than reauthorization. Because one-off card details are deliberately not stored, that case must tell the operator the shopper must pay again; a saved-card order may start a new idempotent PayPal order/authorization attempt only under an explicit application state transition.

### Blockers

- None.
