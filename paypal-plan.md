## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

⚠ **All operations below are `async Task<T>`-returning (method names as shown; await them). No operation has a no-throw `…Result` variant — throw-only across the whole SDK** (`sdk-map.md` §Error-handling model).

- ⚠→✅ **RESOLVED LIVE 2026-09-04 (B2 closed, affirmative):** the Notes' "PayPal account payment" wording does **not** exclude cards — a fresh **card-funded** authorization (CreateOrder `intent=AUTHORIZE` + `AuthorizeOrder payment_source.card`) was **accepted at `POST /v2/payments/authorizations/{id}/reauthorize`** and rejected *only* on the day-window rule, inside the 3-day honor period, with typed **HTTP 422 `{"name":"UNPROCESSABLE_ENTITY","details":[{"issue":"REAUTHORIZATION_TOO_SOON","description":"A reauthorization is only allowed once from Day 4 to Day 29 since the date of the original authorization."}]}`**. ### 2.7 Idempotency support per operation (brief item 8)

**Hard contract fact (map + source agree):** NO method in `operations/Orders.md`, `operations/Payments.md`, `operations/Vault.md`, `operations/TransactionSearch.md` accepts an idempotency-key parameter, and `RequestOptions` (the only per-request hook — `PayPalServerSdk.Core.RequestOptions`) exposes **just `LogLevel?`** — there is no custom-header escape hatch (`Core/RequestOptions.cs`, map gap → named source). ## 3. Trap notes (hazards, attached to the step where they bite)

- ⚠ Step 0 — SDK retry/timeout options do **not** bound a whole logical call, are **not** the timeout of an `HttpClient` you register elsewhere, and which calls may re-execute on transport failure changes what "at most once" means for authorize/capture/refund writes. **MUST load `dotnet-configuration-resilience`** before tuning `RetryOptions` (note: all `RetryOptions` members are `required` — build from `RetryOptions.Default()`).
- ⚠ Step 0 — client lifetime vs `HttpClient` lifetime, and the DI registration shape (`AddPayPalServerSdkClient`): getting this wrong re-mints tokens per request. **MUST load `dotnet-client-initialization`**.
- ⚠ Steps 1–7 — the `payPalRequestId`-style no-default parameters bind only if written explicitly; positional calls silently mis-assign strings. **MUST load `dotnet-calling-endpoints`**.
- ⚠ Steps 1–6 — every enum member is a `StringEnum` static/`FromValue`, every record `init`-only with `required`; string fields you invent (statuses, brands, currencies) round-trip unchecked. **MUST load `dotnet-models`**.
- ⚠ Every step — the catch ladder: Case A typed errors do not retain the HTTP status (§2.9); `TryGetNoContent(out RawError)` exists on Payments-case ops at 500; one op here is Case B (`SearchTransactions`). **MUST load `dotnet-error-handling`**.
- ⚠ Error boundary, both directions (include verbatim in the boundary design):
  - a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
  - a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.
- ⚠ Tests — the fakeable seam is the `HttpClient` constructor argument, not controller internals; error/edge paths (Case A vs B, `TryGetNoContent`) each need a fixture. **MUST load `dotnet-testing`** before stubbing.

## 5. Assumptions & Blockers

**Blockers (plan is wrong until resolved — do not code around them silently):**

- **B1 — caller-supplied idempotency is NOT possible with SDK v1.0.1.** No method parameter accepts an idempotency key; `RequestOptions` carries only `LogLevel`; the SDK auto-sends a random `Idempotency-Key` per call (source: `Api/*.cs` builders, `Core/RequestOptions.cs`). A retried refund/authorize/capture from the app therefore presents a NEW key every time. The brief's "same key → PayPal never double-refunds" cannot be met through the SDK as published. Resolution options, in order: (1) newer package version — re-check after `dotnet add package` (version-less install floats; if a newer release adds the parameter, that is drift to report per the staleness rule, not to assume); (2) application-level idempotency (accept the caller key, persist in-flight + result, return stored result on replay — the app's own store is the dedupe layer; whether a double-send window exists after a crash is `YOUR CALL — not in the map`); (3) bounded by provider data: pre-refund check via `Refund.SellerPayableBreakdown.TotalRefundedAmount`/capture `Amount` so a replayed partial can be refused on amount grounds.
- ~~B2~~ — **RESOLVED 2026-09-04 (live sandbox probe) — no longer a blocker; kept for the record.** Re-authorization of a **card-funded** authorization IS accepted by the provider: a fresh card auth (CreateOrder `intent=AUTHORIZE` + `AuthorizeOrder payment_source.card`) sent to `/v2/payments/authorizations/{id}/reauthorize` inside the 3-day honor period was rejected **solely on the day-window rule** — typed HTTP 422 `UNPROCESSABLE_ENTITY`, `details[0].issue = REAUTHORIZATION_TOO_SOON`, description *"A reauthorization is only allowed once from Day 4 to Day 29 since the date of the original authorization."* — i.e. rejection was on timing, not funding-source class.
