# PayPal integration plan

## 1. Scope & sequence

| Step | Application work | PayPal operations |
| --- | --- | --- |
| 1 | Extend the existing `Order` aggregate with a durable globally unique payment reference, payment/fulfilment state, provider identifiers, monetary results, refunds, optimistic concurrency, and buyer-scoped specifications; persist saved payment methods without PAN/CVC. | None (`YOUR CALL — not in the map`) |
| 2 | Vendor the pinned generated SDK source, bind and validate `PayPal:*`, configure a long-lived HTTP transport, sandbox/default server, optional verbatim base-URL override, bounded calls, safe logging, and exception translation. | Client/auth/server construction |
| 3 | Place orders using current catalog prices and expose buyer-scoped reads. | None (`YOUR CALL — not in the map`) |
| 4 | Authorize an exact order total with either transient card data or an owned active vault token; persist every returned order/authorization id, status, amount, and expiry. | `Orders.CreateOrder`, `Orders.AuthorizeOrder` |
| 5 | Fulfil by refreshing authorization state, reauthorizing after the honor period when allowed, then capturing exactly once; persist gross, PayPal fee, and net. | `Payments.GetAuthorizedPayment`, `Payments.ReauthorizePayment`, `Payments.CaptureAuthorizedPayment` |
| 6 | Cancel only before fulfilment and release the hold exactly once. | `Payments.VoidPayment` |
| 7 | Refund a captured payment under the caller key, enforcing the local remaining refundable amount and persisting provider refund state. | `Payments.RefundCapturedPayment` |
| 8 | Save, list, and delete buyer-owned cards; expose only token id, brand, last digits, and expiry. | `Vault.CreatePaymentToken`, `Vault.DeletePaymentToken` |
| 9 | Reconcile every PayPal reporting page with orders in the requested range through the unique invoice id. | `TransactionSearch.SearchTransactions` |
| 10 | Add domain, persistence, gateway, endpoint, authorization, idempotency, and error-path tests; build, run tests, and exercise real sandbox authorization/capture/refund/vault reuse headlessly. | All above |

## 3. Trap notes

- Client lifetime and `HttpClient` ownership affect token/connection reuse and socket exhaustion — **MUST load `paypal-platforms-team:dotnet-client-initialization`**.
- Credential population timing and OAuth token lifecycle affect whether calls authenticate and refresh safely — **MUST load `paypal-platforms-team:dotnet-authentication`**.
- Generated optional parameters, literal named arguments, and response envelopes can silently mis-bind or be read at the wrong level — **MUST load `paypal-platforms-team:dotnet-calling-endpoints`**.
- Immutable records, string-enum comparisons, nullability, and unknown response fields affect request construction and provider-state mapping — **MUST load `paypal-platforms-team:dotnet-models`**.
- Typed-versus-raw provider errors and status preservation affect safe, actionable API error translation — **MUST load `paypal-platforms-team:dotnet-error-handling`**.
- Retry eligibility, total timeout budgeting, server override, pagination, and body logging affect duplicate writes, availability, coverage, and PCI data exposure — **MUST load `paypal-platforms-team:dotnet-configuration-resilience`**.
- The transport seam and assertions on built requests determine whether tests verify behavior without coupling to SDK internals — **MUST load `paypal-platforms-team:dotnet-testing`**.
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException`, so an SDK-exception-only catch ladder lets it escape — **MUST load `paypal-platforms-team:dotnet-error-handling`**.
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so it **replaces** the `SdkException` and the HTTP status is destroyed with it — **MUST load `paypal-platforms-team:dotnet-error-handling`**.

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind `PayPal:*` at PublicApi composition, validate `ClientId`, `ClientSecret`, `Environment`, and `Currency` as nonblank, accept blank optional `BaseUrl`, and refuse host startup on invalid settings. |
| 2 | Secret sourcing & rotation | Client id/secret come from .NET user-secrets populated from the named environment variables, then normal deployment configuration. DI constructs and captures one validated options snapshot for the process; credential rotation takes effect on process restart. |
| 3 | Total timeout budget | SDK attempt timeout is 20 seconds. Each gateway operation creates a linked 60-second total deadline (including any SDK retries for eligible reads); endpoint cancellation also propagates. |
| 4 | Write-retry ownership | SDK retry methods remain the documented defaults, so all scoped POST/DELETE writes are not resent by the SDK. GET reporting/state lookups may retry. Application-level repeat handling and provider request ids own write recovery. |
| 5 | Idempotency & ambiguous writes | Stable `PayPal-Request-Id`s: globally unique durable payment reference + phase for Create/Authorize/Capture/Reauthorize/Void; caller refund key (namespaced with that reference) for Refund; a fresh per-save operation id for Vault Create so a deleted card can be saved again while SDK retries within that call retain the same id. Local aggregate state makes repeated pay/fulfil/cancel no-ops returning current state. Refund keys are unique per order; the same key returns the stored refund, distinct keys allow partial refunds within remaining capture. Vault delete has no real provider key: mark deleted locally only after success/not-found equivalence. |
| 6 | Observability | Log operation name, local order/payment-method id, provider resource id/status, and provider `debug_id` on typed failures; never log DTOs or bodies. Information for lifecycle transitions, warning for pending/provider rejections, error for transport/schema failures. |
| 7 | Sensitive data | Card number/CVC/address traverse save/pay requests. SDK `LogRequestBody` is forced off and `LoggerFactory` is explicitly assigned so `PAYPALCLIENT_LOG` cannot enable body logging; application logs never interpolate request objects or card fields. |
| 8 | Environment selection | The SDK has one `Default` server group and its sole `Production` member points to `https://api-m.sandbox.paypal.com`. Development/test require `PayPal:Environment=Sandbox`; this integration rejects other values. `PayPal:BaseUrl`, when nonblank, verbatim-overrides `Default.Production.BaseUrl` and therefore both API and `/v1/oauth2/token` credential requests. |

## 6. Assumptions & Blockers

- Minor assumption: request amounts are expressed in the configured two-decimal currency because the task requires cent-exact holds; local totals not representable to two decimals are rejected before provider contact.
- Minor assumption: the existing JWT `ClaimTypes.Name` username is the stable shopper owner key used by existing orders.
- Minor assumption: saved-card creation uses Vault `CreatePaymentToken` directly with the supplied card source; the generated request explicitly supports card details and avoids a browser-only setup-token approval round trip.
- Minor assumption: an authorization is considered stale for fulfilment at three days from provider `create_time`; reauthorization is attempted once. Provider rejection outside the reauthorization window is translated to an actionable conflict explaining that a fresh payment authorization is required.
- No planning blockers: every required provider capability is present in the supplied SDK map.
