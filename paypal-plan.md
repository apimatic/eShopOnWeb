# PayPal implementation plan

## 1. Scope & sequence

| Step | PayPal SDK operations | Required behavior |
|---|---|---|
| 1. Package/client | none | Add the version-less `AsadAli.Checkout.Sdk` package to `src/PublicApi`; bind `PayPal:ClientId`, `PayPal:ClientSecret`, `PayPal:Environment`, `PayPal:Currency`, and optional `PayPal:BaseUrl`; register one long-lived HTTP pipeline and the SDK client. Reject non-sandbox environment values for this task. Never log credentials, access tokens, raw card request bodies, or SDK request/response bodies containing card data. |
| 2. Save a card | `Vault.CreateSetupToken` -> `Vault.CreatePaymentToken`; optionally `Vault.GetPaymentToken` to resolve an ambiguous result | Submit the direct card only to PayPal. Create a setup token using a deterministic operation request ID and a stable merchant-customer ID; if the result is `PAYER_ACTION_REQUIRED`, stop and report the challenge without building an approval round-trip. Otherwise exchange the setup token for a permanent payment token. Persist only the PayPal payment-token ID, PayPal customer ID if returned, brand/type/last digits/expiry, provider status, local owner, and active/deleted state. Never persist number, security code, or full billing address. |
| 3. List/delete saved cards | `Vault.DeletePaymentToken`; `Vault.GetPaymentToken` only when provider-state confirmation is needed | List from the locally owned active records so one user cannot enumerate another user's PayPal customer. Before delete, authorize local ownership; on success mark the record inactive and make it unusable. A repeated delete is a local idempotent success. An ambiguous remote delete is reconciled with `GetPaymentToken`; provider 404 means deleted. |
| 4. Start authorization | `Orders.CreateOrder` -> `Orders.AuthorizeOrder`; `Orders.GetOrder` for recovery | The local order already contains the catalog-derived immutable total. At `/pay`, create one PayPal order with `AUTHORIZE`, one purchase unit, exact configured currency/value, and local order ID in both `invoice_id` and `custom_id`; do not send card data in `CreateOrder`. Persist its PayPal order ID before authorizing. Authorize by sending either a one-off `CardRequest` or an owned active saved token as `CardRequest.VaultId`. Use distinct deterministic PayPal request IDs for create and authorize. Persist order/authorization IDs, statuses, amount/currency, creation/update/expiration timestamps, and sanitized processor/status details. `PAYER_ACTION_REQUIRED` is a terminal challenge report for this headless integration. |
| 5. Fulfil/capture | `Payments.GetAuthorizedPayment`; when stale `Payments.ReauthorizePayment`; then `Payments.CaptureAuthorizedPayment`; `Payments.GetCapturedPayment` for recovery/pending refresh | Check provider authorization state. During the documented honor-period renewal window, reauthorize the exact original amount with a stable operation request ID, store every returned ID/status/timestamp, then capture exact order total with `FinalCapture=true` and a stable capture request ID. Mark fulfilled only after capture reports `COMPLETED`; persist capture amount plus `seller_receivable_breakdown.gross_amount`, `paypal_fee`, and `net_amount`. `PENDING` remains capture-pending and a repeat fulfil refreshes it rather than creating another capture. Outside the original authorization window, return an actionable operator error requiring the shopper to authorize again. |
| 6. Cancel | `Payments.VoidPayment`; `Payments.GetAuthorizedPayment` for recovery | Only an uncaptured authorization can be cancelled. Use a stable void request ID. A local cancelled state or provider `VOIDED` is idempotent success; captured/partially captured states are rejected and directed to refund. |
| 7. Refund | `Payments.RefundCapturedPayment`; `Payments.GetRefund` for recovery/pending refresh | Persist a unique `(capture, caller idempotency key)` operation before calling PayPal and generate/store one stable provider request ID for it. The same caller key returns the same local/provider refund; distinct keys create legitimate partial refunds. Under the order/capture concurrency lock, reserve the requested amount and reject totals above captured amount. Omit `amount` for full remaining refund; include exact `Money` for partial refund. Persist refund ID/status/amount/timestamps and seller payable breakdown. |
| 8. Reconcile | `TransactionSearch.SearchTransactions` for page 1 through `TotalPages` | Pass validated ISO-8601 range strings, request `fields="transaction_info"`, use `balanceAffectingRecordsOnly="N"`, `pageSize=100`, and increment `page` until all returned pages are read. Match provider `transaction_id`/`paypal_reference_id` first against stored PayPal order, authorization, capture, and refund IDs; use `invoice_id`/`custom_field` secondarily. Emit matched, PayPal-only, eShop-only, and amount/status differences. Since the operation notes document up to three hours reporting lag, label recent local-only rows pending reporting; an empty provider result is a valid report, not a capability gap. |
| 9. Tests/live check | all above | Unit-test ownership, amount formatting, state transitions, operation-key recovery, page exhaustion, and exception mapping through an SDK-facing adapter. In one PublicApi in-memory-host run, use the supplied sandbox card to save/reuse, authorize, void a separate order, authorize/capture/refund, and run reconciliation. Stop immediately if a provider response requires payer/browser action. |

Application persistence, aggregate layout, locking mechanism, endpoint DTOs, JWT identity extraction, and role policy names are **YOUR CALL — not in the SDK map**. The SDK facts below are the boundary the implementation must honor.

## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency, renewal, and challenge directives

| Fact / directive | Contract | Source |
|---|---|---|
| PayPal request IDs | The SDK has explicit nullable `payPalRequestId` parameters on CreateOrder, AuthorizeOrder, capture, reauthorize, void, refund, CreateSetupToken, and CreatePaymentToken. Source comments say Orders keys are stored 6 hours (up to 72 by account arrangement), Payments keys 45 days, Vault keys 3 hours. Always pass a stable, per-logical-operation ID. Local operation records remain authoritative after those windows. | `operations/Orders.md`; `operations/Payments.md`; `operations/Vault.md`; `Api/Orders.cs`; `Api/Payments.cs`; `Api/Vault.cs` |
| Ambiguous writes | On timeout/transport/5xx, never generate a new request ID. Reissue under the stored ID or recover with the corresponding GET. Do not enable blind POST transport retries without this operation ledger. | consequence of explicit request-ID contract; retry mechanics require companion skill |
| Renewal window | Operation Notes: initial honor period is three days; reauthorization is available after that within the original 29-day authorization period; after 30 days create a new authorized payment instead. | Renewal-count inconsistency | `ReauthorizePayment` operation Notes say multiple reauthorizations are possible; `ReauthorizeRequest` model summary says only once. These generated definitions disagree. **UNVERIFIED:** do not impose an invented lifetime count; persist each result, allow at most one attempt in a single fulfil execution, and treat PayPal's typed 422 issue/description as authoritative/actionable on later attempts. | `operations/Payments.md`; `records-2-Pa-Ve.md` |

## 3. Trap notes

- ⚠ Step 1 (client registration) — the lifetime and `HttpClient` ownership choices can exhaust connections or defeat handler reuse. **MUST load `dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (credentials) — credential timing, token caching, and rotation cannot be inferred from nullable option properties. **MUST load `dotnet-authentication`** before wiring secrets.
- ⚠ Step 1/4 (resilience) — retry and timeout settings can resend writes or fail to bound the caller's total latency; custom base-server selection and manual pagination have additional consequences. **MUST load `dotnet-configuration-resilience`** before configuring them.
- ⚠ Step 2/4 (calls) — generated optional parameters without C# defaults and the response-envelope depth can silently mis-bind/read the wrong object. **MUST load `dotnet-calling-endpoints`** before the first call.
- ⚠ Step 2/4 (models) — init-only required members, string-enum construction/comparison, nullability, and wire names can produce invalid payloads despite compiling. **MUST load `dotnet-models`** before constructing payloads.
- ⚠ Step 2-8 (errors) — typed Case A errors and raw Case B errors require different catch/accessor paths, and unknown bodies need a safe fallback. **MUST load `dotnet-error-handling`** before writing the boundary.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `dotnet-error-handling`** before writing that boundary.
- ⚠ Step 9 (tests) — faking generated controllers couples tests to SDK internals and misses the real HTTP envelope. **MUST load `dotnet-testing`** before adding the adapter tests.
