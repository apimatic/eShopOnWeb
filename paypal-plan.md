## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Idempotency and persistence contract

| Concern | Directive | Source |
|---|---|---|
| Provider request key | Every generated write signature that exposes `payPalRequestId` writes it as `PayPal-Request-Id`. Persist a deterministic key before the call and reuse it for every retry/recovery of that same logical operation; never generate it inside the retry loop. Orders keys are documented as stored for 6 hours (account-manager extension to 72); Payments keys for 45 days; Vault create keys for 3 hours. | source: `Api/Orders.cs`, `Api/Payments.cs`, `Api/Vault.cs` |
| SDK-added header | Generated write methods also add a new random `Idempotency-Key` header per invocation. Do not treat that random header as the PayPal deduplication key; the controllable provider key is the explicit `payPalRequestId` parameter. | source: `Api/Orders.cs`, `Api/Payments.cs`, `Api/Vault.cs` |
| Logical keys | Persist separate keys for PayPal order creation, authorization, each reauthorization, capture, void, setup-token creation, payment-token creation, and each refund. Refund's persisted provider key is exactly the caller-supplied idempotency key (after validating length/character policy in the application); distinct keys permit distinct partial refunds. | YOUR CALL — key derivation/storage not in the map |
| Ambiguous result | Never issue a different key after timeout/unknown completion. Retry with the same key inside the provider retention window and/or use the stored PayPal resource ID with the mapped GET. If no resource ID was returned and the retention window has elapsed, surface manual reconciliation instead of risking a duplicate write. | YOUR CALL — recovery policy not in the map |
| App concurrency | Unique constraints on logical operation/key plus optimistic concurrency or a serializable transaction must ensure two app requests cannot both reserve a capture/refund. Count pending/reserved refunds against the remaining refundable balance until they fail definitively. | YOUR CALL — not in the map |

### Application/API boundaries

| Concern | Required application behavior | Source |
|---|---|---|
| Identity/ownership | Resolve shopper identity only from JWT claims. Persist owner ID on orders/payment methods. Shopper routes query and mutate by `(resourceId, ownerId)`; do not reveal whether another shopper's ID exists. Operators may fulfil/cancel/reconcile under the app's existing administrator role. Refund remains shopper-owned per the requested route set unless the application intentionally grants the administrator an additional policy. | YOUR CALL — not in the map |
| Payment-method privacy | Raw PAN, expiry, CVC, name/address DTOs exist only in request memory long enough to call PayPal; never persist them, put them in exception messages, structured logs, traces, telemetry, or HTTP body logging. Persist token ID, PayPal customer ID, brand/type, last digits, display expiry, owner, status, timestamps. | Source confirms raw-card fields: `records-1-Ac-Pa.md`, `records-2-Pa-Ve.md`; storage/logging is YOUR CALL |

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership and DI lifetime determine connection reuse and testability. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (authentication) — credential placement, token caching, rotation, and custom strategy behavior are not visible from the options property names. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 3–8 (calls) — nullable parameters without defaults still must be passed, list/search parameters can silently mis-bind positionally, and responses may place the needed data below an envelope. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–8 (models) — required members, init-only records, string-enum comparisons, and nullable response members affect payload validity and state reads. **MUST load `dotnet-models`** before constructing or mapping SDK models.

⚠ Steps 3–8 (error boundary) — typed and raw operation errors require different catch/accessor paths, and retry classification depends on preserving the provider result. **MUST load `dotnet-error-handling`** before writing the boundary.

⚠ Steps 1 and 3–8 (resilience) — retry eligibility, transport failures, timeout scope, pagination, server override, and logging can duplicate writes or leak sensitive bodies if configured incorrectly. **MUST load `dotnet-configuration-resilience`** before tuning the client.

⚠ Step 9 (tests) — the stable fake seam and assertions must cover effects, error/accessor branches, ambiguous writes, ownership, and concurrency without coupling to generated internals. **MUST load `dotnet-testing`** before writing tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The merchant account is sandbox-enabled for direct card processing, vaulting, and transaction reporting as stated in the task.
- `PayPal:Environment` is expected to resolve to sandbox for this delivery; the mapped SDK exposes no other environment member.
