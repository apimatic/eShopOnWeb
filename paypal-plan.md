# PayPal integration plan

## 1. Scope & sequence

| Step | Application work | PayPal operations |
| --- | --- | --- |
| 1 | Add a pinned build reference to the mapped generated SDK; bind and validate `PayPal:` settings; register a long-lived HTTP transport and SDK client. | Client/auth/server configuration |
| 2 | Extend the existing `Order` aggregate with payment/fulfilment state and refund children; extend the existing buyer/payment-method aggregate; add EF mappings and a migration. | None |
| 3 | Add JWT shopper endpoints to create catalog-priced orders and list only the caller's orders. | None |
| 4 | Add one-off-card and owned-saved-card authorization with stable per-order provider request IDs and persisted pending/success state. | `Orders.CreateOrder`, `Orders.AuthorizeOrder` |
| 5 | Add operator fulfilment, including authoritative authorization refresh, renewal after the honor period, and idempotent capture. | `Payments.GetAuthorizedPayment`, `Payments.ReauthorizePayment`, `Payments.CaptureAuthorizedPayment` |
| 6 | Add operator cancellation that releases an uncaptured hold. | `Payments.VoidPayment` |
| 7 | Add shopper partial/full refunds with caller idempotency keys, pre-call amount reservation, and provider IDs/statuses. | `Payments.RefundCapturedPayment` |
| 8 | Add shopper-owned card create/list/delete without persisting PAN/CVC. | `Vault.CreatePaymentToken`, `Vault.DeletePaymentToken` |
| 9 | Add operator reconciliation, splitting ranges into provider-supported windows and reading every page. | `TransactionSearch.SearchTransactions` |
| 10 | Add unit/integration coverage, build/test, then exercise direct-card authorization, saved-card authorization, capture, cancel, refund, and reconciliation against sandbox. | All operations above |

## 3. Trap notes

- Client lifetime and `HttpClient` ownership affect socket/resource safety. **MUST load `paypal-platforms-team:dotnet-client-initialization`.**
- Credential construction and validation affect whether requests are authenticated at all. **MUST load `paypal-platforms-team:dotnet-authentication`.**
- Generated optional parameters, async calls, cancellation, and real provider request IDs can silently mis-bind or lose idempotency. **MUST load `paypal-platforms-team:dotnet-calling-endpoints`.**
- Immutable models, `StringEnum<T>`, required members, nested response envelopes, and wire/C# names can produce malformed requests or reads. **MUST load `paypal-platforms-team:dotnet-models`.**
- Typed versus raw errors and safe provider correlation extraction determine the application error boundary. **MUST load `paypal-platforms-team:dotnet-error-handling`.**
- A drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException`, so an SDK-exception-only catch ladder lets it escape. **MUST load `paypal-platforms-team:dotnet-error-handling`.**
- A **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so it **replaces** the `SdkException` and the HTTP status is destroyed with it. **MUST load `paypal-platforms-team:dotnet-error-handling`.**
- Retry eligibility, total deadlines, base-URL override, full pagination, and body logging can cause duplicate/slow writes, partial reports, or card-data exposure. **MUST load `paypal-platforms-team:dotnet-configuration-resilience`.**
- The `HttpClient` transport seam and behaviour-focused assertions govern isolated integration tests. **MUST load `paypal-platforms-team:dotnet-testing`.**

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | Bind `PayPal:` during PublicApi startup and refuse startup when `ClientId`, `ClientSecret`, `Environment`, or `Currency` is missing/blank or when environment is not sandbox for this task. Validate optional `BaseUrl` as an absolute HTTPS URI. |
| 2 | Secret sourcing & rotation | Values come only from .NET configuration/user-secrets. Registration materializes immutable options once and the singleton SDK captures them; credential rotation takes effect after process restart. Zero-downtime rotation would require a custom rotating token/client factory and is outside this no-new-infrastructure scope. |
| 3 | Total timeout budget | SDK per-attempt timeout is 20 seconds with retries disabled for provider writes; application calls link the request token to a 30-second absolute deadline, which is the caller-visible maximum budget. Reconciliation GET calls use the same total deadline per page. |
| 4 | Write-retry ownership | Disable SDK automatic retries for all calls. The application retries no provider write automatically; a client replay resumes the same logical operation using persisted state and the same PayPal request ID. Reads/pages can be retried only by an explicit higher-level request replay. |
| 5 | Idempotency & ambiguous writes | Create/authorize/capture/renew/void use deterministic operation keys derived from the persisted globally unique order payment reference and operation; refunds persist the caller key before the provider call and derive a bounded provider request ID from that key plus the order reference; card creation persists a generated operation ID in the local pending method before the call. Ambiguous captures/refunds remain pending, are read back from PayPal when their provider ID is known, and otherwise replay with the same key. |
| 6 | Observability | Log operation name, local order/payment-method ID, provider resource IDs/status, and typed error `DebugId`; never log request/response bodies or raw errors. Information for state transitions, warning for actionable provider rejection, error for transport/deserialization failures. |
| 7 | Sensitive data | Card requests contain PAN/CVC/name/address. `LogRequestBody` remains off and `LoggerFactory` is explicitly assigned so `PAYPALCLIENT_LOG` cannot activate body logging. Application logs never include inbound payment bodies. The database stores only provider token ID, brand, last digits, and expiry. |
| 8 | Environment selection | The SDK exposes one `Default` group and only `Sandbox`, defaulting to `https://api-m.sandbox.paypal.com`. Development/test uses `PayPal:Environment=Sandbox`; optional `PayPal:BaseUrl` replaces `Default.Sandbox.BaseUrl` and therefore also the OAuth token URL. No production environment exists in this mapped SDK; this task intentionally targets sandbox and startup rejects other values. |

## 6. Assumptions & Blockers

- Assumption (`YOUR CALL — not in the map`): `POST /api/orders` includes a shipping-address object because the existing `Order` aggregate requires one, while item prices and descriptions are always read from the catalog.
- Assumption (`YOUR CALL — not in the map`): shopper order actions use `ClaimTypes.Name`; operator actions can target any order and use the existing `Administrators` role.
- Assumption (`YOUR CALL — not in the map`): direct card vaulting uses `Vault.CreatePaymentToken` with the request model's card source; if live sandbox instead returns `PAYER_ACTION_REQUIRED`, verification stops as mandated rather than implementing browser approval.
- Assumption (`YOUR CALL — not in the map`): local transaction serialization uses an in-process per-resource lock for the mandated single in-memory host plus optimistic EF concurrency and pre-call pending records for SQL Server deployments; no new distributed infrastructure is introduced.
- Blockers: none. The mapped SDK covers every required provider capability.
