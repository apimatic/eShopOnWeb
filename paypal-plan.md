## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

All operation methods are asynchronous and throw on non-success; the SDK has no `...Result` no-throw variants. `PayPalServerSdk.Core.Request.RequestOptions? requestOptions = null` and `System.Threading.CancellationToken ct = default` are the final parameters shown below. The map records all listed model records in `PayPalServerSdk.Models`, enums in `PayPalServerSdk.Models.Enums`, controllers in `PayPalServerSdk.Api`, and generated operation errors in `PayPalServerSdk.Errors`.

## 3. Trap notes

⚠ Step 1 (client registration) — `HttpClient` ownership, the SDK wrapper lifetime, and the supported DI seam determine whether connections and OAuth state are safely reused. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 1 (credentials) — credential placement, secret loading, and custom token-strategy responsibilities can turn a valid client into 401/403 failures. **MUST load `dotnet-authentication`** before wiring authentication.

⚠ Steps 4–9 (calls) — many nullable parameters have no C# default and positional calls can silently bind the wrong filter/header; response envelopes also differ between Orders and Payments. **MUST load `dotnet-calling-endpoints`** before the first operation call.

⚠ Steps 4–9 (models) — required members, init-only records, `StringEnum<T>` status values, and JSON wire names affect request acceptance and persisted state extraction. **MUST load `dotnet-models`** before constructing payloads.

⚠ Steps 4–9 (error boundary) — Case A typed errors and the Case B raw transaction-search error require different extraction paths; a generic catch loses actionable provider details. **MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Step 1 and all writes (resilience) — retry triggers, timeout scope, transport failures on POST, pagination, base-address behavior, and SDK logging can change whether a money-moving request is repeated or sensitive card data is exposed. **MUST load `dotnet-configuration-resilience`** before configuring the client.

⚠ Step 10 (tests) — the supported fake seam and the behavior worth asserting are not controller-internal SDK types. **MUST load `dotnet-testing`** before writing integration-layer tests.

- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- The supplied sandbox merchant is entitled for direct-card processing and v3 card vaulting as stated in the task. The SDK source describes Vault as available in the US only; merchant entitlement, not the generated client, determines actual availability.
- The API accepts the direct-card fields represented by `PaymentTokenRequestPaymentSource.Card`; the generated model marks every card field nullable, so runtime acceptance must be verified with the supplied sandbox fixture.
- `PayPal:Currency` is a valid PayPal currency code and application order totals are rendered as invariant decimal strings at the currency's precision. Currency arithmetic and rounding are application responsibilities.
- Local ownership checks, state-machine transitions, database concurrency, administrator authorization, secret binding/user-secrets loading, HTTP response shapes, and log redaction are application responsibilities (`YOUR CALL — not in the map`).
- `SearchTransactions` may legitimately return no rows for recent sandbox activity because reporting lags; the report remains complete when it iterates all reported pages.

### Blockers

- **Guaranteed direct-card reauthorization is not covered by the SDK contract.** `ReauthorizePayment` is the only reauthorization operation, and its map Notes explicitly describe reauthorizing an authorized **PayPal account payment**, while the task requires renewing a direct-card authorization. The SDK exposes no card-specific alternative. Applicability to direct-card authorizations is therefore **UNVERIFIED** until sandbox traffic proves it. The implementation may attempt the mapped operation and must translate a typed 400/403/404/422 rejection into an operator-actionable “authorization cannot be renewed; obtain a new payment authorization” outcome, but the contract cannot promise renewal succeeds for cards.
- **The built-in `ServerOptions` member shape is absent from the SDK map.** The mapped client source does prove that one supplied `HttpClient`/`RawClient` is shared by OAuth and every controller, so the application can enforce `PayPal:BaseUrl` for every outgoing SDK request with that transport seam. Using an undocumented `ServerOptions` member instead would be guesswork.
