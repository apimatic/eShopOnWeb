## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Application invariants forced by the contract

| Invariant | Directive | Source |
|---|---|---|
| Exact amount | Convert the persisted decimal total to a culture-invariant currency string at the currency’s configured precision; use the same `Money` value in create, reauthorize, and capture. Reject any response currency/value mismatch and reconcile before advancing local state. | Model shape: `records-1-Ac-Pa.md`; formatting/validation: YOUR CALL — not in the map |
| Saved-token reuse | Do **not** use `PaymentSource.Token`: map `TokenType` exposes only `BILLING_AGREEMENT`. A vaulted card is supplied as `OrderAuthorizeRequestPaymentSource.Card = new CardRequest { VaultId = savedPayPalTokenId }`. | `records-1-Ac-Pa.md`; `enums.md` |
| Reauthorization trust | Provider Notes say reauthorization is available after the initial three-day honor period and within the 29-day authorization period, but scope the operation to an “authorized PayPal account payment.” Eligibility of a direct-card authorization is therefore **UNVERIFIED**. Attempt the mapped operation; on typed 4xx/422 rejection extract `Name/Issue/Description/DebugId`, preserve the authorization, and return an actionable “shopper must submit a new payment” conflict. Also, operations Notes say multiple reauthorizations are possible while the `ReauthorizeRequest` model summary says only once; do not rely on multiple reauthorizations. | `operations/Payments.md`; `records-2-Pa-Ve.md`; live direct-card eligibility is `UNVERIFIED` |

## 3. Trap notes

- ⚠ Step 1 (client registration) — the generated DI extension’s singleton/default-client lifetime and the app’s handler/timeout isolation affect DNS freshness and unrelated clients. **MUST load `paypal-sdk:dotnet-client-initialization`** before wiring the client.
- ⚠ Step 1 (authentication) — credential timing, secret sourcing, OAuth caching, and 401 refresh behavior are not visible in the options property names. **MUST load `paypal-sdk:dotnet-authentication`** before setting `Oauth2`.
- ⚠ Steps 4–10 (endpoint calls) — nullable parameters without C# defaults must still be passed, and list/search calls are safest with named arguments. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before the first call.
- ⚠ Steps 4–10 (models) — SDK records are init-only, requiredness is independent of provider acceptance, and SDK statuses are string-enums rather than C# enums. **MUST load `paypal-sdk:dotnet-models`** before building payloads or reading statuses.
- ⚠ Steps 4–10 (error boundary) — typed and raw error cases expose different safe access paths, so a single catch shape loses diagnostics. **MUST load `paypal-sdk:dotnet-error-handling`** before writing catches.
- ⚠ Steps 1 and 4–10 (resilience) — retry/timeout knobs, transport resends of writes, total call bounds, manual paging, and redacted logging can change financial effects. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before client tuning or write calls.
- ⚠ Step 11 (tests) — the stable seam is the supplied `HttpClient`; faking generated controller internals makes tests brittle. **MUST load `paypal-sdk:dotnet-testing`** before integration tests.
- ⚠ Error boundary — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary. **MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.
- ⚠ Error boundary — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed. **MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.

## 5. Assumptions & Blockers

### Assumptions

- `POST /api/orders/{orderId}/refunds` is shopper-scoped because the brief classifies every endpoint other than fulfil, cancel, and reconciliation as shopper-scoped; an administrator may still be granted a separate policy if the app’s existing authorization model requires it.
- The configured currency is a single ISO currency used for every new order. Existing orders retain their snapshotted currency if configuration later changes.
- Reconciliation is a money-movement report: it uses SearchTransactions’ default balance-affecting behavior and compares captured/refunded local events, not un-captured holds. Recent empty results remain valid because reporting lag is expected.
- Saving a card uses the mapped direct-card `CreatePaymentToken` request. A separate setup-token/browser approval flow is intentionally excluded by the headless direct-card requirement.
- A direct-card authorization’s eligibility for `ReauthorizePayment` is **UNVERIFIED** as described above; provider rejection is handled as the required actionable non-renewable case rather than bypassed.

### Blockers

- None. The SDK map contains create/authorize/read, reauthorize/capture/void/refund, direct-card vault, delete/read token, and transaction-search operations. The direct-card reauthorization trust limit does not block implementation because the required behavior explicitly includes an actionable branch for an authorization PayPal will not renew.
