## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

## 3. Trap notes

- ⚠ Step 1 (client registration) — `HttpClient` ownership/lifetime and the generated DI extension can create connection churn or dispose a handler incorrectly if wired from signature knowledge alone. **MUST load `paypal-sdk:dotnet-client-initialization`** before constructing/registering the client.
- ⚠ Step 1 (authentication) — credential timing, auth-manager construction and secret rotation determine whether the first request is authenticated. **MUST load `paypal-sdk:dotnet-authentication`** before wiring credentials.
- ⚠ Step 4 (calling operations) — generated optional parameters without defaults must still be passed, and positional calls can bind the many nullable headers/filters incorrectly. **MUST load `paypal-sdk:dotnet-calling-endpoints`** before the first SDK call.
- ⚠ Steps 4–10 (models) — required members, nullable acceptance fields, string-enum handling and response nesting can silently lose IDs/statuses if treated like ordinary mutable DTOs. **MUST load `paypal-sdk:dotnet-models`** before constructing/reading models.
- ⚠ Steps 4–10 (error boundary) — typed Case-A accessors and raw Case-B errors have different extraction paths; treating them alike loses provider detail/status. **MUST load `paypal-sdk:dotnet-error-handling`** before writing the boundary.
- a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary;
- a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

  **MUST load `paypal-sdk:dotnet-error-handling`** before writing that boundary.
- ⚠ Steps 4–10 (resilience/idempotency) — retry triggers, per-attempt/total timeout boundaries, base URL selection and transport retries on writes determine whether a failed operation can safely be re-sent. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before configuring retries/timeouts or pagination.
- ⚠ Steps 4–6 (sensitive logging) — generated request logging and application structured logging can expose transient PAN/CVC unless disabled/redacted at the boundary. **MUST load `paypal-sdk:dotnet-configuration-resilience`** before enabling any SDK logging.
- ⚠ Step 11 (tests) — faking generated controllers couples tests to implementation and can miss real serialization/error behavior; the correct HTTP/application seam is not visible in controller signatures. **MUST load `paypal-sdk:dotnet-testing`** before writing integration-layer tests.

## 5. Assumptions & Blockers

- **Assumption:** The configured sandbox merchant has direct-card and US Payment Method Tokens/Vault eligibility as stated in the task; the SDK's own client summary says its Vault controller is available in the US only.
- **Assumption:** The app owns the local aggregate/API/persistence/identity/state-machine design. The map settles only PayPal contracts; all rows labeled `YOUR CALL — not in the map` remain implementer decisions, not SDK facts.
- **Assumption:** A setup-token or order response with `PAYER_ACTION_REQUIRED`, or payer-action/approve HATEOAS, is treated as the browser challenge named in the task: live verification stops and reports it; no approval round-trip is built.
- **Blocker — stale direct-card renewal is not covered by the supplied SDK contract:** `Payments.ReauthorizePayment` exists, but its authoritative operation Notes say it “Reauthorizes an authorized PayPal account payment”; the requested payment source is a direct card. The map/source exposes no other reauthorization operation. Implement the documented call for eligible authorizations and the actionable 4–29-day / 30-day handling above, but the supplied source cannot guarantee renewal of a stale **card** authorization. If sandbox rejects it, that is the genuine capability gap and must be reported rather than bypassed or guessed.
- **No blocker for reconciliation lag:** `SearchTransactions` is present with manual page parameters and total-page response; its Notes explicitly permit up to three hours of lag, so an empty fresh range is valid.
