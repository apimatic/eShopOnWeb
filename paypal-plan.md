## 2. CONTRACT SHEET

> **Signatures are generated code, verbatim — every parameter name is the literal
> C# identifier. The cancellation-token parameter really is named `ct`: in named
> arguments write `ct:`, never `cancellationToken:`.**
>
> **Every SDK type is written fully-qualified with the namespace the map gives it** — take
> each one from that type's own map row, never from where a neighbouring type sits. A members
> table names the namespace outright; otherwise the row's source path implies it
> (`Core/Configuration/…` ⇒ `…Core.Configuration`; a file at the repo root ⇒ the root
> namespace). Enums, unions, auth, server and client-config types are spread across different
> child namespaces, and two types configured side by side in the same options object routinely
> live in different ones. Dropping a type to the root or to `.Models` makes the implementer
> guess the wrong `using`, and the build breaks.

### Operations

All methods are throw-only; no `…Result` variants exist. For every write below, `payPalRequestId` is serialized as `PayPal-Request-Id`. Pass `prefer: "return=representation"` wherever the signature has `prefer`, because the default is only `return=minimal`. The generated source additionally emits a new random `Idempotency-Key` header internally; application/provider effect-idempotency must rely on the stable mapped `PayPal-Request-Id` plus persisted state, not that random header.

## 3. Trap notes

⚠ Step 2 (client registration) — client/`HttpClient` lifetime, named-vs-unnamed factory blast radius, and the generated singleton lifetime affect DNS/handler reuse. **MUST load `dotnet-client-initialization`** before wiring the client.

⚠ Step 2 (authentication) — credential setup, token caching/renewal, and 401 behavior are not established by the options property names. **MUST load `dotnet-authentication`** before wiring credentials.

⚠ Steps 3–8 (calls) — nullable parameters without defaults must still be supplied, named arguments must match generated identifiers, and response envelopes differ by operation. **MUST load `dotnet-calling-endpoints`** before the first SDK call.

⚠ Steps 3–8 (models) — generated required members, nullable acceptance fields, string-enums, and init-only construction can silently alter the wire body if treated like ordinary DTOs. **MUST load `dotnet-models`** before constructing payloads.

⚠ Steps 2–8 (resilience) — transport retries can resend writes, timeout knobs do not all bound the whole call, server override is nested, and these list/search operations require manual pagination. **MUST load `dotnet-configuration-resilience`** before registration or write calls.

⚠ Steps 3–8 (error boundary) — a drifted or malformed **2xx** body (a missing `required` member) surfaces as a `System.Text.Json.JsonException` from deserialization, **not** as an `SdkException` — so an SDK-exception-only catch ladder lets it escape the integration boundary.

⚠ Steps 3–8 (error boundary) — a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape throws `System.Text.Json.JsonException` *while the error object is being constructed*, so the `JsonException` **replaces** the `SdkException` and the HTTP status is destroyed with it — a boundary that maps every `JsonException` to a 5xx then reports a deterministic rejection as an outage, and a caller that retries 5xx retries something that can never succeed.

**MUST load `dotnet-error-handling`** before writing that boundary.

⚠ Verification tests — the `HttpClient`/handler is the SDK seam; mocking generated controller internals makes tests brittle and misses wire behavior. **MUST load `dotnet-testing`** before writing integration-layer tests.

## 5. Assumptions & Blockers

### Assumptions

- The configured merchant is enabled for direct card processing and US vault operations, as the brief states; the SDK itself labels Vault as available in the US only.
- The application formats configured-currency amounts to the currency's two-decimal representation required by this brief and rejects totals that cannot be represented exactly to the cent.
- A newly created PayPal order is separate from the existing eShop order row; the eShop order ID is carried as PayPal `invoice_id`/`custom_id`, while PayPal IDs are persisted separately.
- A one-off card that reaches the 30-day original authorization boundary cannot be silently authorized again because the application correctly did not retain its PAN/CVC; the actionable result is that shopper payment authorization is required again.

### Blockers

- None. The SDK map/source exposes every PayPal operation required by the brief. A provider response of `PAYER_ACTION_REQUIRED` is a runtime stop condition required by the brief, not a missing SDK capability.
