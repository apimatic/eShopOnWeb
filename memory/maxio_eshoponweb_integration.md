Built the full Maxio Advanced Billing subscription integration into eShopOnWeb per `plan.md` (UC0-UC4, ApplicationCore/Infrastructure/Web/PublicApi layers, maxio-sdk plugin as sole Maxio reference). All 98 solution tests pass and every UC was live-verified end-to-end against the real `apimatic-hackathon` sandbox (subscribe, usage, plan-change preview/commit with stale-token rejection, pause/resume/cancel/reactivate) via both the PublicApi JWT surface and the Web cookie-auth Razor Pages.

Three non-obvious runtime issues surfaced only when actually *running* the app (not caught by `dotnet build`/`dotnet test`):

1. **`AsadAli.AdvancedBilling.Sdk`'s transitive deps drag in a `10.0.8` servicing train** (`Microsoft.Extensions.Http`, `Polly`, `System.Net.Http.Json`, `System.Net.ServerSentEvents` all pinned to exactly `10.0.8` in its nuspec). This bumped `System.Text.Json`/`System.Net.Http.Json` to `10.0.8` project-wide via normal NuGet transitive resolution, but left `Microsoft.Bcl.AsyncInterfaces` resolved at a stale `7.0.0` - a real assembly-version mismatch (`FileNotFoundException` for `Microsoft.Bcl.AsyncInterfaces, Version=10.0.0.8`) that only manifests when something forces eager load of all referenced assemblies (here: `MinimalApi.Endpoint`'s `Assembly.GetTypes()` reflection scan in `AddEndpoints()`). Fix: add an explicit `<PackageReference Include="Microsoft.Bcl.AsyncInterfaces" Version="10.0.8" />` (added to `Infrastructure.csproj` + `Directory.Packages.props`) to pull that package up to the matching train. **Why this matters going forward:** `dotnet build`/`dotnet test` gave zero errors/warnings despite this being fully broken at runtime - always actually run+curl the host after adding/upgrading a package with a wide transitive footprint, don't trust a clean build.
2. **Maxio path params expect the numeric ID, not the handle, even when the SDK method parameter is typed `string`.** `ProductFamilies.ListProductsForProductFamily(string productFamilyId, ...)` 404s when passed the family's handle (`"eshop-subscribe"`) - it needs the numeric ID as a string (`"3008866"`). Confirmed via direct curl against the sandbox. Handle-based lookups only work on endpoints explicitly designed for it (`Components.FindComponent(handle)`, `Products.ReadProductByHandle(handle)`, `Customers.ReadCustomerByReference(reference)`) or as body fields (`CreateSubscription.ProductHandle`, `SubscriptionProductMigration.ProductHandle`). Don't assume a `string`-typed path param accepts a handle - verify per-operation.
3. **The shared `apimatic-hackathon` sandbox has data drift across tasks/participants.** The env var `MAXIO_DEFAULT_PRODUCT_FAMILY` was set to `metermate-consulting` (an unrelated family belonging to a different demo scenario), while `plan.md`'s explicit spec (family `eshop-subscribe` id `3008866`, products `eshop-pro`/`basic-plan`, component `api-call`) matched a *different*, independently-verified family also present in the same sandbox. Went with `plan.md`'s values (verified live via curl) over the env var. Also: the seeded eShopOnWeb demo identities (`demouser@microsoft.com`, `admin@microsoft.com`) already had real leftover Maxio subscriptions/usage from prior test runs when this session started - expect pre-existing state when testing against this sandbox, don't assume a clean slate.

See `[[eshoponweb-repo-conventions]]` for the eShopOnWeb-side architectural conventions this integration mirrors.
