# Square integration plan — eShopOnWeb PublicApi

SDK: Square .NET SDK shipped in the `square` plugin at `sdk/dotnet/` (plugin-relative; referenced as a
`ProjectReference`, never copied). All contract facts below come from `sdk/dotnet/sdk-map.md`, its
`map/operations/*.md` pages, and the declaring files those pages name.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Settings (`Square:*`), fail-fast validation, named `HttpClient`, client factory (merchant client + unauthenticated OAuth client) | — |
| 2 | Persistence: `SquareConnection` (encrypted tokens), `SquareOAuthState` (single-use state), `SquareCatalogLink` (claim + item/variation/photo ids), `SquareOrderLink` (claim + Square order id) in `CatalogContext` + SQL migration | — |
| 3 | Flow 1 connect: build sign-in URL; callback validates/consumes state, exchanges code, reads merchant, stores tokens; token provider refreshes on expiry; connection status | `OAuth.ObtainToken`, `Merchants.RetrieveMerchant` |
| 4 | Merchant context: merchant id, active location, currency (cached per connection generation) | `Merchants.RetrieveMerchant`, `Locations.ListLocations` |
| 5 | Flow 2 catalog sync: read linked objects, re-link by marker SKU when no link exists, create/update per item, count created/updated/unchanged | `Catalog.BatchRetrieveCatalogObjects`, `Catalog.SearchCatalogObjects`, `Catalog.UpsertCatalogObject` |
| 6 | Flow 2 photo: validate JPEG/PNG ≤ 5 MB, ensure item synced, upload as primary image | `Catalog.CreateCatalogImage`, `Catalog.RetrieveCatalogObject` |
| 7 | Flow 3 orders: ensure gift-message definition, create eShop order + Square order, upsert gift message; read back | `OrderCustomAttributes.RetrieveOrderCustomAttributeDefinition`, `OrderCustomAttributes.CreateOrderCustomAttributeDefinition`, `Orders.CreateOrder`, `OrderCustomAttributes.UpsertOrderCustomAttribute`, `OrderCustomAttributes.RetrieveOrderCustomAttribute`, `Orders.RetrieveOrder` |
| 8 | PublicApi endpoints, error boundary, offline tests (stub `HttpMessageHandler`), live sandbox verification | all of the above |

## 2. CONTRACT SHEET

> ⚠ Signatures are generated code, verbatim — each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer whose property names are the record's own, never flat arguments.
> ⚠ Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits (`Models/` → `Square.Models`, `Models/Enums/` → `Square.Models.Enums`, `Requests/<Ctl>/` → `Square.Requests.<Ctl>`, `Core/Models/` → `Square.Core.Models`, `Core/Exceptions/` → `Square.Core.Exceptions`, `Core/ErrorResponse/` → `Square.Core.ErrorResponse`).

All operations: **Case B** (`Square.Core.Exceptions.ApiException<Square.Core.ErrorResponse.RawError>`; accessors `StatusCode`, `ReadAsBytes()`, `ReadAsString()`, `ReadAsJson<T>()`), throw-only, no pagination, server group `Default` (source: `sdk-map.md` defaults table). Every response model carries `Errors (errors): IReadOnlyList<Square.Models.Error>?`; `Error` = `Category (category): ErrorCategory, required` · `Code (code): ErrorCode, required` · `Detail (detail): string?` · `Field (field): string?` (source `Models/Error.cs`).

- Steps 3–7 — which exception types reach the catch ladder; unknown outcome after a write's connection fails. **MUST load `square:dotnet-error-handling`**
- Step 8 — which seam to fake and how to read request bodies in the stub. **MUST load `square:dotnet-testing`**

Hazard (verbatim): a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | `SquareSettings` bound from `Square:` (`Environment`, `ApplicationId`, `ApplicationSecret`, `RedirectUri`, optional `AccessToken`) with `ValidateOnStart`: blank ApplicationId/ApplicationSecret/RedirectUri, a non-absolute RedirectUri, or an Environment other than `sandbox`/`production` stops the host; message names the key, never the value. `AccessToken` optional (sign-in deployments). |
| 2 | Secret sourcing & rotation | Values come from configuration (user-secrets in dev, env/secret store in prod). App credentials are read once at startup (restart to rotate). Merchant OAuth tokens live encrypted (ASP.NET Core Data Protection) in `SquareConnection` and are rotated by refresh without restart; the SDK client is rebuilt when the connection generation changes. |
| 3 | Total timeout budget | Named `HttpClient` `Timeout = 15 s` (backstop) + `RetryOptions.Timeout = 10 s` per attempt; every endpoint's Square work runs under one linked `CancellationToken` deadline (`SquareTimeouts.Deadline`: 45 s for connect/callback/connection/orders/photo, 180 s for a catalog sync) linked to `HttpContext.RequestAborted`; a deadline that fires maps to 504. |
| 4 | Write-retry ownership | SDK default `HttpMethodsToRetry` kept (GET/HEAD/PUT/OPTIONS). Every Square write in scope is POST → never resent by the SDK. The app itself resends only writes carrying a real idempotency key (UpsertCatalogObject, CreateOrder, CreateCatalogImage, UpsertOrderCustomAttribute, CreateOrderCustomAttributeDefinition) and only on 429/connection failure, with the same key. |
| 5 | Idempotency & ambiguous writes | UpsertCatalogObject: `UpsertCatalogObjectRequest.IdempotencyKey`, stored on `SquareCatalogLink.PendingIdempotencyKey` before the call. CreateOrder: `CreateOrderRequest.IdempotencyKey` stored on `SquareOrderLink.IdempotencyKey`. CreateCatalogImage: `CreateCatalogImageRequest.IdempotencyKey` stored on the link's photo claim. UpsertOrderCustomAttribute: `UpsertOrderCustomAttributeRequest.IdempotencyKey` (value write is a set — resending is harmless). CreateOrderCustomAttributeDefinition: deterministic key per merchant + 409/CONFLICT treated as "exists". ObtainToken: no key — authorization code is single-use; refresh grant returns the same refresh token (harmless to repeat). The generated `Idempotency-Key` header is not relied on. |
| 6 | Observability | SDK `Logging.LoggerFactory` = host `ILoggerFactory` (request/response lines at Information, retries Warning); headers/bodies off. App logs Square `errors[].code`/`category` + HTTP status (never detail text containing user data) and the eShop ids involved. |
| 7 | Sensitive data | In scope: client secret, auth code, access/refresh tokens (ObtainToken body/response), gift message (customer content). `LogRequestBody = false`, `LoggerFactory` assigned explicitly on every client (disarms `SQUARECLIENT_LOG`). Tokens encrypted at rest; never returned by any endpoint. Gift message never persisted in eShop DB nor logged. |
| 8 | Environment selection | One server group (`Default`): Production `https://connect.squareup.com`, Sandbox `https://connect.squareupsandbox.com`. `Square:Environment` must be explicitly `sandbox` or `production` (no default) → `ServerEnvironment.Sandbox/Production`; sign-in URL uses the same group's base URL. Tests replace the primary handler so no traffic leaves the process. |
| 9 | Duplicate prevention under concurrency | See DUPLICATE CLAIMS. Additionally catalog writes are serialized in-process (Square rejects concurrent catalog updates with 429). |
| 10 | Partial results | Catalog sync batches retrieves in chunks of 100 ids, all chunks always read; sync response reports `failed` count + per-item `items[].error` so a partially applied sync is visible to the caller. The marker search follows `cursor` for at most 5 pages and, if cut short, fails the item instead of concluding "not found" (which would create a duplicate). |
| 11 | Unknown outcomes | See UNKNOWN OUTCOMES. |

### DUPLICATE CLAIMS

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| Create Square item for an eShop item (sync / photo pre-sync) | `SquareCatalogLinks` row, PK (`MerchantId`, `CatalogItemId`), inserted with state `PendingCreate` + idempotency key | Primary-key violation on insert of the same (merchant, item) | `catch (Exception ex) when (SquareClaims.IsDuplicateKey(ex))` (SQL Server: `DbUpdateException`; EF in-memory: `ArgumentException`) → item reported as failed/"in progress", never created twice | `SquareCatalogSync.TryClaimCreateAsync` → `SquareCatalogSync.CreateAsync` (via `UpsertAsync`, `Catalog.UpsertCatalogObject`) |
| Update Square item (name/price change) | same row; `ConcurrencyStamp` concurrency token rewritten with state `PendingUpdate` + key | Concurrency-token mismatch | `catch (DbUpdateConcurrencyException)` in `TrySaveClaimAsync` → item reported as "in progress" | `SquareCatalogSync.TryClaimUpdateAsync` → `SquareCatalogSync.ReconcileAsync` (via `UpsertAsync`) |
| Upload product photo | same link row; photo claim fields (`PhotoState=Pending`, `PhotoSha256`, `PhotoIdempotencyKey`) under `ConcurrencyStamp` | Concurrency-token mismatch (a fresh, different upload already holds the claim) | `catch (DbUpdateConcurrencyException)` in `TryClaimAsync` → `SquareIntegrationException(Conflict)` → 409 | `SquareCatalogPhotoService.TryClaimAsync` → `SquareCatalogPhotoService.UploadAsync` (`Catalog.CreateCatalogImage`) |
| Create Square order for an eShop order | `SquareOrderLinks` row, PK `OrderId`, inserted in the same SaveChanges as the eShop order, state `Pending` + idempotency key | Primary-key violation (one Square order per eShop order) | `catch (Exception ex) when (SquareClaims.IsDuplicateKey(ex))` in `SquareOrderService.PlaceOrderAsync` → 409 | `SquareOrderService.PlaceOrderAsync` (order + link saved together) → `SquareOrderSync.CreateSquareOrderAsync` (`Orders.CreateOrder`) |
| Connect (store merchant tokens) | `SquareOAuthStates` row (PK = SHA-256 of state) deleted on use | Delete of an already-deleted row → concurrency failure | `catch (DbUpdateConcurrencyException)` in `TryConsumeStateAsync` → callback refused | `SquareOAuthService.TryConsumeStateAsync` → `SquareOAuthService.CompleteAsync` (`OAuth.ObtainToken`) |

## 6. Assumptions & Blockers

- Assumption: eShop prices are in the merchant location's currency (no FX conversion); amount = price × 10^minor-units (table of zero/three-decimal ISO currencies).
- Assumption: `POST /api/orders` accepts an optional `shipToAddress`; when absent the order ships to the Square location's address ("in-store pickup") because the existing `Order` requires an address.
- Assumption: Square order line items are ad-hoc (name + `base_price_money` + quantity) so price always equals the eShop order price; the docs do not state how `catalog_object_id` and `base_price_money` interact.
- Assumption (from task): scopes `MERCHANT_PROFILE_READ ITEMS_READ ITEMS_WRITE ORDERS_READ ORDERS_WRITE`; String schema `$ref` for the custom attribute.
- UNVERIFIED: whether Square deduplicates a re-sent `CreateCatalogImage` with the same key → reconciliation reads the item instead of relying on it.
- YOUR CALL (made at implementation): every variation the shop creates carries SKU `eshop-item-{catalogItemId}`; when no link exists the sync re-links the item it finds by that SKU instead of creating another one, so a lost link table (e.g. the in-memory store after a restart) does not create duplicates.
- YOUR CALL: a Square rejection of `CreateOrder` withdraws the just-saved eShop order (nothing half-placed); an unknown outcome keeps it `Pending` and answers 202.
- Live sandbox finding: order custom-attribute updates require `version` (see contract row) — the gift message write settles unknown outcomes by reading the attribute first.
- Blockers: none.
