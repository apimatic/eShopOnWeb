# Maxio Advanced Billing implementer notes

Plan: `maxio-advanced-billing-plan.md` (same folder). The skill used is `maxio-advanced-billing:dotnet-integrate-maxio-advanced-billing`. Names only in this file, never values.

## Files and what each one does

Repo-wide
- `global.json`: changed to `version 8.0.100`, `rollForward latestMajor`, so the .NET 10 SDK that the plugin SDK needs (C# 14) gets picked.

ApplicationCore (`src/ApplicationCore/Entities/BillingAggregate/`)
- `BillingClaim.cs`: an abstract claim row. It holds a string PK `Key`, `State`, a `Version` concurrency token, and timestamps. It provides `TakeOver`, `MarkUnknown` and `IsStalePending`.
- `BillingClaimState.cs`: the state enum `Pending | Completed | Unknown`.
- `BillingCustomerLink.cs`: Key = customer reference. Also stores `ProviderCustomerId`.
- `SubscriptionEnrollment.cs`: Key = `{customerReference}:{planHandle}`, which is also the Maxio subscription `reference`. Also stores `ProviderSubscriptionId`.

Infrastructure
- `Data/CatalogContext.cs`: adds the `BillingCustomerLinks` and `SubscriptionEnrollments` DbSets.
- `Data/Config/BillingCustomerLinkConfiguration.cs`, `SubscriptionEnrollmentConfiguration.cs`, `BillingClaimColumns.cs`: string PKs (max 255). State is stored as a string. `Version` is set with `IsConcurrencyToken()`.
- `Data/Migrations/*_AddSubscriptionBilling.*`: tool-generated. It creates the two billing tables and an index on `SubscriptionEnrollments.CustomerReference`.
- `Data/Migrations/CatalogContextModelSnapshot.cs`: regenerated by the tool. Only `AddSubscriptionBilling` ships: the main agent deleted the separate drift migration (`SyncCatalogModelNullability`, which altered existing Orders/OrderItems/Catalog columns to NOT NULL) to keep the change additive. Do not recreate it. The pre-existing model-vs-schema nullability drift is therefore left as it was before this work.

PublicApi
- `PublicApi.csproj`: adds a `ProjectReference` to `$(MaxioAdvancedBillingSdkProject)`. It defaults to `..\..\..\marketplace\plugins\maxio-advanced-billing\sdk\dotnet\src\MaxioAdvancedBilling\MaxioAdvancedBilling.csproj`, and an error target fires if that path is missing.
- `Program.cs`: calls `builder.Services.AddMaxioBilling(builder.Configuration)`. After `AddEnvironmentVariables()` it also calls `builder.Configuration.AddMaxioEnvironmentFallback(builder.Configuration)`.
- `Billing/MaxioSettings.cs`: `MaxioSettings` binds `Maxio:ApiKey`, `Maxio:Subdomain`, `Maxio:ProductFamilyHandle` and `Maxio:BaseUrl`. `MaxioSettingsValidator` names the failing key, never its value.
- `Billing/MaxioConfigurationExtensions.cs` covers DI and the client options:
  - Options are registered with `ValidateOnStart`.
  - A named HttpClient `MaxioAdvancedBilling` is registered with Timeout 15s and `PooledConnectionLifetime` 5m.
  - A singleton `MaxioAdvancedBillingClient` is built over that HttpClient.
  - `SiteCollectionMethodCache` is registered as a singleton; `SubscriptionBillingService` as scoped.
  - `CreateClientOptions` sets: Environment Us; BasicAuth {ApiKey, "x"}; Retry = Default with {MaxRetries 2, Timeout 10s}, which keeps the default verbs so POST is never retried; Logging with an explicit LoggerFactory and LogRequestBody=false; Production.Us/Eu.Site = Subdomain; Production.Us/Eu.BaseUrl = BaseUrl verbatim when set.
  - `AddMaxioEnvironmentFallback` maps MAXIO_API_KEY, MAXIO_SITE_SUBDOMAIN and MAXIO_DEFAULT_PRODUCT_FAMILY onto blank keys, in memory only.
- `Billing/CustomerReference.cs`: builds `"eshop-"` + the first 32 hex chars of SHA-256(upper-invariant user name). The result is 38 characters.
- `Billing/BillingException.cs`: the single failure type. It carries the status, a title, a caller-safe message and Maxio's `errors` strings.
- `Billing/BillingModels.cs`: `BillingCaller`, `PlanCatalog(Plans, IsPartial)`, `SubscribeOutcome`, `SubscribeResult`.
- `Billing/SiteCollectionMethodCache.cs`: process-lifetime cache of the `CollectionMethod` for CreateSubscription. Single-flight (`SemaphoreSlim`), `Volatile` read of the cached reference; caches only a value the resolver returned, so a throw (failed read, null flag) leaves it empty. The resolver delegate comes from the service, so the SDK call stays in the service.
- `Billing/SubscriptionBillingService.cs`: the only class that calls the SDK. Its main members:
  - Public: `GetPlansAsync`, `SubscribeAsync`, `GetMySubscriptionsAsync`.
  - Subscribe order: plan-handle check, then `SiteCollectionMethodCache.GetOrResolveAsync(ReadSiteCollectionMethodAsync)`, then `EnsureCustomerAsync` (first claim), then `EnrollAsync` / `CreateSubscriptionAsync` with `PaymentCollectionMethod`.
  - Site: `ReadSiteCollectionMethodAsync` (true → Remittance, false → Invoice, null → 502 ProviderFailure, logged at Error; Case B errors via `FromProviderStatus`, SDK failures via `TranslateSdkFailure`: 401/403/404/5xx → 502, 429/unreachable → 503, timeout → 504).
  - Plan listing: `ListPlansCoreAsync` (page cap and partial flag).
  - Customer: `EnsureCustomerAsync`, `CreateCustomerAsync`, `TrySettleCustomerAsync`, `ReadCustomerByReferenceAsync`, `ResolveCustomerIdForReadAsync`.
  - Subscription: `EnrollAsync`, `CreateSubscriptionAsync`, `TrySettleSubscriptionAsync`, `SettleEnrollmentsAsync`, `ListCustomerSubscriptionsCoreAsync`.
  - Claims: `ClaimAsync`, `DeleteClaimAsync`, `RestoreClaimAsync`, `TrySaveAsync`.
  - Budgets: 30s per request (linked to RequestAborted), 15s for each independent settle re-read. A Pending claim older than 2 min is stale.
- `SubscriptionEndpoints/`: three `IEndpoint` classes (`SubscriptionPlanListEndpoint`, `CreateSubscriptionEndpoint`, `MySubscriptionListEndpoint`), their request/response classes, the DTOs (`SubscriptionPlanDto`, `SubscriptionDto`, `PriceDto`, `BillingIntervalDto`), and `BillingEndpointSupport`, which maps a BillingException to ProblemDetails with `correlationId` and `errors`. The endpoints use `[Authorize(JwtBearer)]` with no role requirement, under the tag `SubscriptionEndpoints`.
- `README.md`: a section describing the configuration keys.

Tests
- `tests/PublicApiIntegrationTests/appsettings.test.json`: obviously fake `Maxio:*` placeholders. `BaseUrl` is `http://127.0.0.1:9/`, so nothing can reach a real site.
- `tests/FunctionalTests/PublicApi/ApiTestFixture.cs`: adds the same placeholders through in-memory config. Without them, the functional tests' PublicApi host would fail `ValidateOnStart`.
- `tests/PublicApiIntegrationTests/Billing/`:
  - `FakeMaxio.cs`: a stateful HttpMessageHandler stub of the six routes (incl. `GET /site.json`, flag set by `RelationshipInvoicingEnabled`, default true; null omits the field), with an `Intercept` hook and `CreatedSubscriptionCollectionMethod(body)`.
  - `BillingTestHarness.cs`: shared in-memory root, unique database per test; one `SiteCache` per harness shared by all its services (as the singleton is).
  - `SubscriptionBillingServiceTests.cs`: 25 tests.
  - `SiteCollectionMethodTests.cs`: 8 tests (remittance / invoice body, read ordering, null flag → 502 no claim no POST not cached, 401 → 502 not cached and re-read, unreachable → 503, success cached, concurrent first subscribes share one read).
  - `BillingClaimStoreTests.cs`: pins the store's refusal types.
  - `MaxioSettingsTests.cs`: validator, client options and env fallback.
  - `SubscriptionEndpointsTests.cs`: WebApplicationFactory tests covering 401, 201/200, 400 ProblemDetails, empty list and the Swagger document.

## SDK calls used

All calls are on the `Production` server group and every one goes through the service.
- `client.ProductFamilies.ListProductsForProductFamily(new ListProductsForProductFamilyRequest { ProductFamilyId = "handle:"+family, Page, PerPage = 200 })` (Case A: `TryGetString` for 404, then `TryGetRawError`).
- `client.Customers.ReadCustomerByReference(new ReadCustomerByReferenceRequest { Reference })` (Case B; only a 404 means the customer is absent).
- `client.Customers.CreateCustomer(new CreateCustomerOperationRequest { Body = new CreateCustomerRequest { Customer = new CreateCustomer { FirstName, LastName, Email, Reference } } })` (Case A: `TryGetCustomerErrorResponse1` → `Errors1.TryGetListOfString` / `TryGetCustomerError`).
- `client.Customers.ListCustomerSubscriptions(new ListCustomerSubscriptionsRequest { CustomerId })` (Case B).
- `client.Subscriptions.CreateSubscription(new CreateSubscriptionOperationRequest { Body = new CreateSubscriptionRequest { Subscription = new CreateSubscription { ProductHandle, CustomerId, Reference, PaymentCollectionMethod } } })` (Case A: `TryGetErrorListResponse1`). `PaymentCollectionMethod` is `MaxioAdvancedBilling.Models.Enums.CollectionMethod.Remittance` or `.Invoice`, never `Automatic`.
- `client.Sites.ReadSite(cancellationToken: token)`: no request record. Reads `SiteResponse.Site.RelationshipInvoicingEnabled` (`bool?`). Case B (`ApiException<RawError>`), then `catch (SdkException)`.

Every ladder ends with `catch (SdkException)`, so `ResponseDeserializationException`, `AuthSchemeException` and the connection errors are all caught.

## Pitfalls hit

- A `bash -c` heredoc containing C# char literals (`'-'`) broke the shell with "unexpected EOF". I wrote those files with the Write tool instead.
- The EF in-memory provider throws **ArgumentException**, not DbUpdateException, for a duplicate primary key. `IsStoreRefusal` therefore catches `DbUpdateException or ArgumentException`, and the claim is then confirmed by re-reading the key. The behaviour is pinned in `BillingClaimStoreTests`. Concurrency-token conflicts do raise `DbUpdateConcurrencyException` in-memory.
- Creating a new `InMemoryDatabaseRoot` for every test made EF throw `ManyServiceProvidersCreatedWarning`. The fix was one static root plus unique database names.
- The first `dotnet ef migrations add` pulled in pre-existing drift (Orders/OrderItems/Catalog nullability). I split it into two tool-generated migrations by temporarily adding `builder.Ignore<...>()` for the billing entities, generating the drift migration, then removing the Ignore and generating the billing migration. The snapshot was not hand-edited. The drift migration was later deleted by the main agent (additive change only); the billing migration and snapshot stay as generated. `ef migrations remove` needs a DB (LocalDB is absent), so I deleted the files and ran `git checkout` on the snapshot instead.
- Package versions: the SDK's transitive packages (Microsoft.Extensions.* / System.Text.Json 10.0.8) produced no restore or build errors, and the ASP.NET Core 8 host runs with them. The WebApplicationFactory tests prove this. The plugin was not touched.
- `global.json`'s old value `8.0.x` was being ignored. It is now a valid version with `latestMajor`.
- LIVE (main agent): without `payment_collection_method`, CreateSubscription for `eshop-pro` answered 422 "No payment method was on file for the $299.00 balance". Fix round 1 sends remittance/invoice from the site's architecture; whether that avoids the signup charge is still to be confirmed live.
- The site-read connection-failure test takes about 3 s, because the SDK retries the GET twice (1 s + 2 s backoff). A 401 is used for the "read failure is not cached" test since the SDK does not retry it.

## Deviations from the plan (all were YOUR CALL items, or the shape the plan left open)

- The plan said `AddMaxioAdvancedBillingClient` over the default unnamed HttpClient. I registered the singleton myself over a **named** HttpClient instead, to keep the timeout and handler off other unnamed consumers. The semantics are the same: options are built once on first resolve, so rotation needs a restart.
- 409 "in progress" and all billing errors are returned as ProblemDetails by the endpoints, not through `DuplicateException`/`ExceptionMiddleware`. That middleware echoes `exception.Message`.
- When a CreateCustomer outcome is unknown and can't be settled, subscribe returns **503** ("still being set up, retry") and the link is left `Unknown`. A subscription outcome that is unknown and unsettled returns **202** with state `unknown`.
- Status mapping: provider 5xx and unknown-status write failures are treated as unknown outcomes. On reads: 401/403/404/other 4xx/5xx give 502, 429 and unreachable give 503, timeouts give 504.
- `planHandle` is required in POST /api/subscriptions. No handle is hard-coded as a default.
- The plan price `currency` is null, because Maxio's `Product` model has no currency field. Subscription prices carry `Subscription.Currency`.
