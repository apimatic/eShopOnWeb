## 1. Scope & sequence

Ordered implementation steps; each names the SDK operations it uses. Every Finix fact below is from the map or the map-named source file.

1. **Config + SDK wiring** — bind `Finix:Username`, `Finix:Password`, `Finix:MerchantId`, `Finix:Environment`, `Finix:Currency`, `Finix:BaseUrl` into one options record; fail startup on any missing/blank value; validate `Currency` and `Environment`/`BaseUrl` pairing; register the client (`AddFinixApiReferenceClient` or `new FinixApiReferenceClient(HttpClient, options)`). No Finix operation.
2. **Payment persistence** — app-owned tables (new EF entities on `CatalogContext`): shopper→Finix buyer identity, saved card (Finix PI id + masked fields), order payment attempt (authorization id/state, capture transfer id/state, captured amount, fee, net), refund claim rows, action-claim rows. No Finix operation.
3. **Buyer identity per shopper** — `client.Identities.CreateIdentity`; settle an unknown outcome with `client.Identities.ListIdentities`.
4. **Saved cards (Flow 2)** — `client.PaymentInstrumentsApi.CreatePaymentInstrument` (card variant), `GetPaymentInstrument`, `ListPaymentInstruments`, `UpdatePaymentInstrument` (disable — the map has no delete).
5. **Place order** — read `CatalogItem` rows through the existing repository; construct the existing `Order`/`OrderItem`/`CatalogItemOrdered`; total from `Order.Total()`. No Finix operation.
6. **Pay (authorize only)** — `client.AuthorizationsApi.CreateAuthorization` with `AuthorizationAllFields` (`amount` = order total in cents, `source` = payment instrument id, `merchant` = `Finix:MerchantId`, `idempotency_id` = attempt key, `tags` = order id); re-read with `GetAuthorization` on an unknown outcome.
7. **Fulfil (capture)** — `client.AuthorizationsApi.CaptureAuthorization` (`capture_amount` = held amount); `GetAuthorization` to confirm `transfer`; `client.TransfersApi.GetTransfer` for Finix `fee`, `amount`, `state`; net = amount − fee.
8. **Cancel (release)** — `client.AuthorizationsApi.VoidAuthorization`; `GetAuthorization` to confirm `is_void` / `void_state`.
9. **Refund after fulfilment** — `client.TransfersApi.CreateTransferReversal` on the capture transfer with `refund_amount`; `client.TransfersApi.GetTransfer` for the reversal; `client.TransfersApi.ListTransferReversals` to compute already-refunded and to settle an unknown outcome.
10. **My orders / reconciliation reads** — `client.AuthorizationsApi.ListAuthorizations` and `client.TransfersApi.ListTransfers` (date filters, cursor paging, `type` filter for reversals), walked to `Page.NextCursor == null`.
11. **Error boundary** — one translation layer for `ApiException<TError>` (Case A), `ResponseDeserializationException`, `SdkConnectionException`, `SdkTimeoutException`, `AuthSchemeException`; map `GenericError` details to HTTP responses.
12. **Tests** — stubbed `HttpClient` per `dotnet-testing`, including a forced connection failure per write in **UNKNOWN OUTCOMES**.

> **Capability notes (not invented):** capture is `CaptureAuthorization`, not `CreateTransfer` — no `TransfersRequest` variant carries an authorization id, and `CaptureAuthorization`'s `<remarks>` says the capture sets the Authorization's `transfer` field. Refunds are Finix **Reversals** (`POST /transfers/{transfer_id}/reversals`) — the map has no `Refunds` controller. See §6 for what the map lacks.

### 2b. Client construction, auth and server facts

- **Construction**: only constructor `FinixApiReferenceClient(HttpClient httpClient, FinixApiReferenceClientOptions options)`. DI alternative `services.AddFinixApiReferenceClient(options => { … })` manages the `HttpClient` through `IHttpClientFactory` (`README.md`). Credentials/options are read when the client is constructed.
- **Auth (HTTP Basic)**: `options.BasicAuth = new FinixApiReference.Core.Authentication.Basic.BasicAuthCredentials { Username = …, Password = … }` (both `required`), or `options.BasicAuthProvider` (asked per request). Every operation in scope carries an `Auth: options.BasicAuth` bullet. A `null` `BasicAuth` is filled from `FINIX_API_REFERENCE_BASIC_AUTH_USERNAME` / `FINIX_API_REFERENCE_BASIC_AUTH_PASSWORD`; **blank is treated as configured** — the SDK checks presence, never content (`README.md`).
- **Environment**: exactly one member, `FinixApiReference.Servers.ServerEnvironment.Production` (value `production`, "Sandbox server"). `options.Environment` defaults to it.
- **Server groups**: one group, `Default`; base URL `https://finix.sandbox-payments-api.com`. Every operation resolves `_server.Default(path)` (`src/FinixApiReference/Server.cs`).
- **BaseUrl override**: `options.Server.Default.Production.BaseUrl` (`ServerOptions` → `DefaultOptions.ProductionOptions.BaseUrl`, default sandbox). It is the base for every call, used verbatim; there is no other override point. Live host documented in `src/FinixApiReference/FinixApiReferenceClient.cs`: `https://finix.live-payments-api.com` — set `BaseUrl` to it when `Finix:Environment=live` (the SDK has no live environment member).
- **Namespaces to import** (child namespaces are not transitive): `FinixApiReference`, `FinixApiReference.Api`, `FinixApiReference.Models`, `FinixApiReference.Models.AnyOf`, `FinixApiReference.Models.Enums`, `FinixApiReference.Requests.<Controller>`, `FinixApiReference.Errors`, `FinixApiReference.Core.Authentication.Basic`, `FinixApiReference.Core.Configuration`, `FinixApiReference.Core.ErrorResponse`, `FinixApiReference.Core.Exceptions`, `FinixApiReference.Servers`.
- **Errors**: throw-only everywhere (135/135 Case A). On error `ApiException<TError>` exposes `.Error`, `.StatusCode`, `.Headers`, `.ContentType`. Case A payload is the typed `{Operation}Error` with `TryGetGenericError` + inherited `TryGetRawError`.
- **Idempotency**: every non-GET call sends a fresh `Idempotency-Key: Guid.NewGuid()` header (visible in each `Api/*.cs`) — not a key. Real keys are body members: `idempotency_id` on `AuthorizationAllFields` and `TransferAllFields`; **none** on `RefundTransfer`, `PaymentInstrumentCard1` or `Buyer`.
- **Retry defaults** (`RetryOptions.Default()`): statuses 408, 429, 500, 502, 503, 504; methods `GET`, `HEAD`, `PUT`, `OPTIONS`; `MaxRetries = 3`, `Delay = 1s`, exponential, `BackOffFactor = 2`, `MaxJitter = 500ms`, `Timeout = 100s`.
- **Sensitive**: `CreatePaymentInstrument` sends PAN (`number`) and CVV (`security_code`) in a JSON body. `LoggingOptions.LogRequestBody` defaults `false`; JSON bodies are logged verbatim with no redaction when on. `AddFinixApiReferenceClient` always supplies the container's `ILoggerFactory`, so `FINIX_API_REFERENCE_LOG` is not consulted under DI (`README.md`).
- **Response status**: not on the return value; only via `SdkHook.OnResponse` (per attempt) or the error path.

### 2c. CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| A `paymentMethodId` accepted by pay must be one this app returned for that shopper — returned by the card list and still enabled | `CreateAuthorization` ← `ListPaymentInstruments` (+ `GetPaymentInstrument`) | the pay handler's pre-check: load the stored card row for the caller, then `GetPaymentInstrument` confirms `Enabled` and `Identity` matches the shopper's buyer identity |
| An `authorizationId` used for capture or void must be the one stored for that order by the pay call, in state `SUCCEEDED` and not `IsVoid` | `CaptureAuthorization`, `VoidAuthorization` ← `CreateAuthorization` | the fulfil/cancel handler's pre-check against the persisted payment attempt; re-read with `GetAuthorization` before the write |
| A `transferId` used for refund must be the capture transfer recorded at fulfil, type `DEBIT`, state `SUCCEEDED` | `CreateTransferReversal` ← `CaptureAuthorization` (`Authorization.Transfer`) | the refund handler's pre-check: stored capture transfer id, confirmed by `GetTransfer` |
| A refund amount must be ≤ captured amount minus the sum of that transfer's existing reversals | `CreateTransferReversal` ← `ListTransferReversals` | the refund handler sums `Transfer.Amount` of the parent's reversals before writing; also checks `RefundTransfer.refund_amount` ≤ parent `Transfer.Amount` |
| The amount held must equal the order total in cents | `CreateAuthorization` ← the order row (`Order.Total()`) | after `CreateAuthorization`, compare `Authorization.Amount` with the computed total; on mismatch void and fail |
| `Currency` sent must equal the configured `Finix:Currency` and be representable (`USD`/`CAD`) | `CreateAuthorization` ← config | startup validation + the pay handler's amount/currency builder |
| The `merchant` sent must be the configured `Finix:MerchantId` on every write | `CreateAuthorization` ← config | one request factory used by pay only |
| The `idempotency_id` used by pay must be readable back through the authorization list | `CreateAuthorization` ← `ListAuthorizations` | the unknown-outcome settle path filters `IdempotencyId` |
| The `orderId` put in `tags` must be the one reconciliation matches against app orders | `CreateAuthorization`, `CreateTransferReversal` (via parent transfer) ← app order store | the reconciliation matcher reads `Authorization.Tags` / `Transfer.Tags` and the stored ids |
| A shopper's saved card and orders must never be reachable by another shopper | every read/write ← `CreateIdentity` (per-shopper buyer identity) | every handler filters by the caller's `ClaimTypes.Name` before any SDK call |

## 3. Trap notes

- Union bodies (`AuthorizationsRequest`, `PaymentInstrumentsRequest`, `TransfersReversalsRequest`, `IdentitiesRequest`) cannot be built with a plain object initializer — `MUST load dotnet-models`.
- `required` members differ per union variant (e.g. `AuthorizationMinimalFields` lacks `idempotency_id`), and `CreateAuthorizationRequest.Body` is nullable while the API needs it — `MUST load dotnet-models`.
- List responses wrap the payload one level down in `_embedded`; reading the top-level type yields nothing — `MUST load dotnet-calling-endpoints`.
- `VoidAuthorizationRequest`'s id member is `AuthorizationIdVoidTo`, not `AuthorizationId`; `GetAuthorizationRequest` has no `FinixVersion` — `MUST load dotnet-calling-endpoints`.
- Case A typed errors, the `RawError` fallback and `ResponseDeserializationException` are three different catch shapes — `MUST load dotnet-error-handling`.
- The default retry set includes `PUT` but not `POST`, so capture/void can be resent while create/refund are not — `MUST load dotnet-configuration-resilience`.
- `RetryOptions.Timeout` is not the whole-call budget; the total budget and what bounds a call need the companion — `MUST load dotnet-configuration-resilience`.
- Cursor paging plus the implicit 30-day window on list endpoints — `MUST load dotnet-configuration-resilience`.
- `HttpClient` ownership/lifetime and the DI registration's option capture — `MUST load dotnet-client-initialization`.
- Credentials left `null` fall back to SDK environment variables, and blank counts as configured — `MUST load dotnet-authentication`.
- A JSON body carrying PAN/CVV is logged verbatim when request-body logging is on, and the log env switch is not the only way it turns on — `MUST load dotnet-configuration-resilience`.
- Stubbing the SDK's `HttpClient` seam and forcing a post-send connection failure — `MUST load dotnet-testing`.

**Mandatory hazard row (verbatim):** a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

If no-restart rotation is required, switch to `BasicAuthProvider` (asked per request) — decision recorded here, not implemented by default. |
| 3 | **Total timeout budget** | `Finix:TimeoutSeconds` (default 20) sets both `HttpClient.Timeout` and `RetryOptions.Timeout` per attempt; every endpoint passes `HttpContext.RequestAborted` as the caller's cancellation token, which is the only whole-call bound. POST writes are not retried (default method list); PUT capture/void may be retried. Member: `FinixServiceCollectionExtensions.AddFinixPayments`. |

### DUPLICATE CLAIMS

Claim → SDK call → record the result. The claim is a write of its own, in the app's store, before the SDK call.

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| Pay (`POST /api/orders/{orderId}/pay`) | `CatalogContext` payment-attempt entity, primary key = `OrderId` | primary-key insert of the attempt row (a second attempt for the same order cannot insert) | `catch` around `SaveChanges` for the duplicate key (`DbUpdateException` / in-memory tracking conflict), returned as `409` | `PaymentService.PayAsync` (persisted `OrderPayment.IdempotencyId` + `Status = Authorizing` write) → `FinixPaymentGateway.CreateAuthorizationAsync` |
| Fulfil (`POST /api/orders/{orderId}/fulfil`) | `CatalogContext` action-claim entity, primary key = (`OrderId`, `Fulfil`) | primary-key insert of the claim row | same catch, `409` | `PaymentService.FulfilAsync` → `PaymentService.ClaimActionAsync(orderId, "FULFIL")` → `FinixPaymentGateway.CaptureAuthorizationAsync` |
| Cancel (`POST /api/orders/{orderId}/cancel`) | `CatalogContext` action-claim entity, primary key = (`OrderId`, `Cancel`) | primary-key insert of the claim row | same catch, `409` | `PaymentService.CancelAsync` → `PaymentService.ClaimActionAsync(orderId, "CANCEL")` → `FinixPaymentGateway.VoidAuthorizationAsync` |
| Refund (`POST /api/orders/{orderId}/refunds`) | `CatalogContext` refund-claim entity, primary key = (`OrderId`, caller idempotency key) | primary-key insert of the claim row (distinct keys insert distinct rows, so distinct partial refunds stay legitimate) | same catch; the existing row's `refundId` is returned instead of a second refund | `PaymentService.RefundAsync` (`RefundRecord` composite-key insert) → `FinixPaymentGateway.CreateReversalAsync` |

## 6. Assumptions & Blockers

**Blockers / provider gaps (map lacks the capability the task asks for):**

1. **No `DeletePaymentInstrument` operation.** `PaymentInstrumentsApi` has 8 operations and none deletes. `DELETE /api/payment-methods/{id}` must therefore be implemented as (a) app-side tombstone so the card is never listed or usable, plus (b) `UpdatePaymentInstrument` with `PaymentInstrumentDisableAPaymentInstrument { Enabled = false }`, which the operation's `<remarks>` documents as disabling the instrument "so it can't be used in requests". The card itself remains at Finix. If a true provider-side delete is required, this integration cannot deliver it.
2. **No `Refunds` resource.** Refunds are Finix **Reversals**: `CreateTransferReversal` (POST `/transfers/{transfer_id}/reversals`, returns a `Transfer` of type `REVERSAL`), read back with `GetTransfer`, listed with `ListTransferReversals`. Consequences: the refund id is a Transfer id (`refundId` = reversal `Transfer.Id`); there is **no** global reversal list with date filters — refunds inside a reconciliation range are found via `ListTransfers` with `type=REVERSAL` and `created_at.gte/lte`.
3. **No tokenization / hosted-fields operation.** The only card-ingest path in the map is `CreatePaymentInstrument` with raw `number` + `security_code`; its own `<remarks>` say this "should only be done for testing purposes" and that hosted fields or the JS client are required to stay out of PCI scope. The `PaymentInstrumentTokenCard` variant accepts a token, but no operation in this SDK mints one. **Live card capture with raw PAN is therefore out of PCI scope for a production deployment; sandbox/test-card use (the stated scope) is fine.** Any live rollout needs a token source outside this SDK.
4. **`Finix:Currency` is only representable as `USD` or `CAD`.** `Currency` is an open enum with static members `Usd`/`Cad` and **no public factory**; `TryGetKnownValue` cannot construct an undeclared value. Any other ISO code must fail startup validation. If a non-USD/CAD currency is required, this SDK cannot express it in a request body.
5. **No caller-supplied key on refunds.** `RefundTransfer` exposes only `refund_amount`; the endpoint prose says `idempotency_id` is available on `/transfers/{id}/reversals`, but the generated record has no such member. The caller's idempotency key is therefore enforced only by the app's claim store, and a post-send failure is settled by `ListTransferReversals` (amount match) — **`UNVERIFIED`**: whether Finix would also dedupe on an `idempotency_id` sent through `AdditionalProperties` cannot be confirmed from the map.
6. **Date-filter serialization mismatch (worked around with a request hook).** The SDK serializes `DateTimeOffset` query values with an offset (`ParameterFlattener` → `JsonSerializerOptions.Web`), but Finix's list endpoints accept only `yyyy-MM-ddTHH:mm:ss` (observed live: `422 Must be in format 2018-01-26T11:21:23`). `FinixServiceCollectionExtensions.NormalizeDateRangeQuery` rewrites only `.gte`/`.lte` query values via `SdkHook.OnRequest`; all other query values are untouched. Without it every date-filtered list call fails.
7. **Partial reversal requires a settled capture.** Finix rejects a partial reversal of a `PENDING` capture transfer ("please reattempt to reverse with full amount or wait until Transfer has succeeded"). `PaymentService.RefundAsync` refreshes the transfer and returns an actionable `409` for a partial while `PENDING`; full reversals work immediately. Live verification confirmed partial refunds succeed once the sandbox transfer settles (~60–80 s).
8. **`ListTransfers` with `type=ALL` returned no rows in sandbox.** Omitting the `type` filter returns every type (DEBIT/REVERSAL/...); `PaymentService.ReconcileAsync` uses the unfiltered call.

**Assumptions about the user's intent:**

6. **"Capture" = `CaptureAuthorization`.** No `TransfersRequest` variant carries an authorization id, so no `CreateTransfer` call is made for capture. The capture transfer id comes from `Authorization.Transfer` after `CaptureAuthorization`.
7. **Order creation and card saving are not deduplicated.** Each call creates a distinct order/card; neither moves money. The caller-supplied key exists only for refunds (as specified). Recorded as a decision, not a gap.
8. **Payment state lives in `CatalogContext`** (the app's existing in-memory-capable store) as new entities — payment attempt (authorization id/state, capture transfer id/state, captured amount, fee, net), saved card (PI id, buyer identity id, last4, brand, expiry, owner), shopper→identity map, refund claims, action claims. `UseOnlyInMemoryDatabase=true` gives per-process isolation as the task requires. The plan adds no SQL Server dependency.
9. **Order totals** are computed from catalog prices via the existing `Order.Total()` decimal; the cents conversion must reject any total whose cent value is not integral, so the hold equals the total to the cent.
10. **"Net proceeds"** is computed as `Transfer.Amount − Transfer.Fee` from `GetTransfer` after capture; Finix reports both fields on the `Transfer`.
11. **One buyer Identity per shopper**, created lazily on first card save and reused; its id is persisted and is the `identity` on every `PaymentInstrumentCard1`.
12. **Caller identity** is `ClaimTypes.Name` from the JWT (`IdentityTokenClaimService` issues `ClaimTypes.Name` + `ClaimTypes.Role`); admin role value is `Administrators` (`BlazorShared/Authorization/Constants.cs`).
