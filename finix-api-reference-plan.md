# Finix API Reference integration plan — eShopOnWeb card payments & saved cards

SDK root cited throughout: `sdk/dotnet/` (plugin-relative; in this repo `.opencode/sdk/dotnet/`). Map: `sdk/dotnet/sdk-map.md`, operations: `sdk/dotnet/map/operations/`. All contract facts below are read from that copy.

Scope guard: APIMatic-generated **Finix API Reference .NET SDK** (`FinixApiReference`), C#/.NET only. No other API or language.

## 1. Scope & sequence

Repo conventions to imitate (pattern + the ONE exemplar to read at edit time):
- Endpoint = one class per operation implementing `IEndpoint<IResult, TRequest, TDep>`, route in `AddRoute`, JWT scheme + role in the `[Authorize]` attribute: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`; list endpoint with paging math: `src/PublicApi/CatalogItemEndpoints/CatalogItemListPagedEndpoint.cs`.
- Request/response DTOs derive from `BaseRequest`/`BaseResponse` and carry `CorrelationId()`: `src/PublicApi/BaseResponse.cs`, `src/PublicApi/BaseRequest.cs`.
- Records live in EF `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`), which switches to `UseInMemoryDatabase` when `UseOnlyInMemoryDatabase=true` (`src/Infrastructure/Dependencies.cs`); repositories are `IRepository<>`/`IReadRepository<>` (`src/ApplicationCore/Interfaces/IRepository.cs`).
- Administrator role constant: `BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS` (`src/BlazorShared/Authorization/Constants.cs`).
- Caller identity claim: `ClaimTypes.Name` (the only identity claim minted) — `src/Infrastructure/Identity/IdentityTokenClaimService.cs`.

Sequence (each step names the Finix operations it uses; no project code is written by this plan):

1. **Configuration + client (no Finix operation).** Bind section `Finix` keys `Username`, `Password`, `MerchantId`, `Environment`, `Currency`, `BaseUrl`; validate all required non-blank at startup; register the SDK once (`AddFinixApiReferenceClient`); set `BasicAuth`, `Environment`, `Server.Default.Production.BaseUrl`, `Logging`, `Retry` (see §2 client facts). Then **`GetMerchant`** once at startup to prove the merchant id/credentials are real (fail startup on 401/403/404).
2. **Buyer identity per shopper** — **`CreateIdentity`** with the `Buyer` arm; persist `Identity.Id` on a shopper profile record (keyed by the JWT `ClaimTypes.Name`). Reuse for both flows; never create a second identity for the same shopper. `ListIdentities` is only the unknown-outcome re-read.
3. **Save a card (Flow 2)** — `POST /api/payment-methods` → **`CreatePaymentInstrument`** with the raw-card arm, `Identity` = the caller's stored buyer identity. Persist only `{paymentMethodId, shopperId, last4, brand, expMonth, expYear, enabled}` from `PaymentInstrumentCard`. Never persist `Number`/`SecurityCode`.
4. **List saved cards** — `GET /api/payment-methods` → **`ListPaymentInstruments`** filtered by `OwnerIdentityId` = caller's stored identity, walking `page.next_cursor`; drop `enabled == false`.
5. **Remove a saved card** — `DELETE /api/payment-methods/{paymentMethodId}` → ownership check against the stored row, then **`UpdatePaymentInstrument`** with the disable arm (`enabled=false`), then **`GetPaymentInstrument`** to confirm `enabled=false`; mark the stored row disabled. (The map has no delete operation for payment instruments; disable is the documented removal — `PaymentInstrumentCard.enabled` doc and `PaymentInstrumentDisableAPaymentInstrument`.)
6. **Place an order (Flow 1)** — `POST /api/orders` → app-only: validate catalog item ids/quantities against `CatalogItems`, build `Order`/`OrderItem`, store status `AwaitingPayment`, `BuyerId` = JWT name. Return `orderId`.
7. **Pay = AUTHORIZE (hold)** — `POST /api/orders/{orderId}/pay` → resolve source: (a) saved card → stored row owned by caller and `enabled`, re-confirmed with **`ListPaymentInstruments`**; or (b) one-off card details → **`CreatePaymentInstrument`** (raw-card arm, same buyer identity, not persisted as a saved method). Then **`CreateAuthorization`** with `AuthorizationAllFields`: `amount` = order total in cents, `currency`, `merchant`, `source`, app-generated `idempotency_id`, `statement_descriptor`. Persist `Authorization.Id`, `state`, `amount`, `idempotency_id`, `source`, `expires_at`. Hold, never capture.
8. **Fulfil = CAPTURE** — `POST /api/orders/{orderId}/fulfil` (administrator) → eligibility: stored `Authorization` still `SUCCEEDED`, `is_void != true`, `expires_at` in the future (re-read with **`GetAuthorization`**). Then **`CaptureAuthorization`** with `capture_amount` = the stored authorized amount; then **`GetTransfer`** on `Authorization.transfer` to read Finix's `amount`, `fee`, `state`. Persist capture transfer id, captured amount, fee, net (`amount - fee`), status `Fulfilled`. A hold that cannot be captured returns the operator message from `failure_code`/`failure_message` (and the `expires_at`/state reason) — never a bare 500.
9. **Cancel before fulfilment** — `POST /api/orders/{orderId}/cancel` (administrator) → only while `AwaitingPayment`/held; **`VoidAuthorization`** with `void_me=true`; persist `void_state`/`is_void`; status `Cancelled`; no transfer exists.
10. **Refund after fulfilment** — `POST /api/orders/{orderId}/refunds` → claim on the caller-supplied idempotency key (see §3 DUPLICATE CLAIMS), compute already-refunded = stored refunds re-checked with **`ListTransferReversals`** (walk pages), reject if `already + requested > captured`; then **`CreateTransferReversal`** on the stored capture transfer id with `refund_amount`. Persist `Transfer.Id` as `refundId`, amount, state. Never allow the sum of refunds to exceed the captured amount.
11. **Shopper order history** — `GET /api/my-orders` → app-only: orders where `BuyerId` = JWT name, joined with stored payment state (hold/capture/refund ids and statuses).
12. **Reconciliation** — `GET /api/reconciliation?from&to` (administrator) → **`ListTransfers`** with `created_at.gte`/`created_at.lte` (ISO-8601 → `DateTimeOffset`), `merchant` = configured merchant id, walking `page.next_cursor` to the end; line each transfer up to the stored capture/refund transfer ids; report Finix-only transfers, app-only payments with no Finix transfer, and amount mismatches. `SettlementsApi` is deliberately not used: a `Settlement` is a payout batch, not a per-order transaction, so it cannot be lined up one-to-one with an eShop order; the per-transaction Finix record is the `Transfer` (capture = `DEBIT`, refund = `REVERSAL`).

### 2.2 CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| A `paymentMethodId` accepted by pay must be one the caller's card list returned **and** still enabled | `POST /api/orders/{orderId}/pay` ← `ListPaymentInstruments` | source resolution before `CreateAuthorization`: `ListPaymentInstruments(OwnerIdentityId = caller identity)` result contains the id and its `enabled != false` |
| A `paymentMethodId` accepted by delete must be one the caller's card list returned | `DELETE /api/payment-methods/{id}` → `UpdatePaymentInstrument` ← `ListPaymentInstruments` | ownership/enabled lookup against the stored card rows (populated from `ListPaymentInstruments`) before `UpdatePaymentInstrument` |
| An `orderId` accepted by pay/fulfil/cancel/refunds must be an order this application created for that caller (any order for the administrator) | pay/fulfil/cancel/refunds ← `POST /api/orders` (stored `Order.Id`) | order lookup by `(orderId, BuyerId)` (or `orderId` alone for admin) before any Finix call |
| The `AuthorizationId` captured/voided must be the one stored from the order's authorization | `CaptureAuthorization`, `VoidAuthorization` ← `CreateAuthorization` (stored `Authorization.Id`) | stored payment row read and state-checked before capture/void |
| The `TransferId` refunded must be the `Transfer` returned by this order's capture | `CreateTransferReversal` ← `CaptureAuthorization` (stored `Authorization.transfer`) | stored `captureTransferId` used; caller never supplies a transfer id |
| A refund amount must not push cumulative refunds beyond the captured amount | `CreateTransferReversal` ← `CreateTransferReversal` (stored refunds) + `ListTransferReversals` | `alreadyRefunded + requested <= capturedAmount` checked before the reversal; `alreadyRefunded` = max(stored, Finix `ListTransferReversals` sum) |
| `capture_amount` must be one the authorization reported | `CaptureAuthorization` ← `CreateAuthorization` (stored `Authorization.Amount`) | stored authorized cents used as `CaptureAmount`; never recomputed from the order |
| The `identity` on a new payment instrument must be the caller's stored buyer identity | `CreatePaymentInstrument` ← `CreateIdentity` (stored `Identity.Id`) | stored identity id injected server-side; caller cannot supply it |
| The `merchant` on an authorization must be the configured merchant Finix recognises | `CreateAuthorization` ← `GetMerchant` | startup `GetMerchant` succeeds for `Finix:MerchantId`; that id is the only value used for `merchant` |
| A disabled card must never be listed again | `GET /api/payment-methods` ← `UpdatePaymentInstrument` | list filters stored rows on `enabled` after the disable re-read (`GetPaymentInstrument`) |

## 3. Trap notes

Attached to the step where each bites; each states the hazard, not the fix.

1. **Client/DI** — a required Basic credential left `null` is filled from the SDK's own environment variables when the client is constructed, so a half-configured deployment surfaces as `AuthSchemeException` on the first call rather than at startup, and the options object is built once inside a singleton. **MUST load `dotnet-authentication`** and **MUST load `dotnet-client-initialization`**.
2. **Base URL** — `Finix:BaseUrl` is used as the whole base address and the SDK appends its own paths; a value carrying a trailing path or missing scheme silently sends every call somewhere else. **MUST load `dotnet-configuration-resilience`**.
3. **Timeouts/retries** — what `RetryOptions.Timeout` actually bounds is not the whole call, and the retried verb set decides whether a POST/PUT money write is ever resent. Getting this wrong double-authorizes or double-captures. **MUST load `dotnet-configuration-resilience`**.
4. **Pagination** — every list operation caps a page at `limit` 100 and hands back a cursor the SDK does **not** follow; stopping at the first page makes the reconciliation report lie about coverage. **MUST load `dotnet-configuration-resilience`**.
5. **Sensitive data** — JSON request bodies are logged verbatim when `LogRequestBody` is on, and leaving `LoggerFactory` unset lets an environment variable arm body logging with no code change; the card PAN/CVV paths make that a breach. **MUST load `dotnet-configuration-resilience`**.
6. **Calling convention** — each operation takes one request record as its first parameter plus `requestOptions` and `cancellationToken`; passing the body model directly, or flattening its members, does not compile. **MUST load `dotnet-calling-endpoints`**.
7. **Unions** — `CreatePaymentInstrument`, `PaymentInstrumentsResponse`, `PaymentInstrumentsResponse1`, `PaymentInstruments3`, `AuthorizationsRequest`, `AuthorizationsRequest1` and `TransfersReversalsRequest` are open `AnyOf` unions: build through the static factory/implicit conversion, read through `TryGet…`, and treat a body no variant accepts as `TryGetUnknown` (a silently different arm means the wrong field was read). **MUST load `dotnet-models`**.
8. **Required-but-nullable** — `Address` marks `Line1`, `City`, `Region`, `PostalCode`, `Country` `required` while typing them `string?`/`Country?`; a partial object initializer fails to compile, and `Address` is only set when every member is supplied. **MUST load `dotnet-models`**.
9. **Enum binding** — `Currency` is an open string enum with no public factory: `Finix:Currency` can only resolve to a declared member (`USD`/`CAD`) or the host must refuse to start; casting a string will not compile and `TryGetKnownValue` returns false for anything else. **MUST load `dotnet-models`**.
10. **Errors** — every operation is throw-only Case A; the `{Operation}Error` classes differ per operation and a drifted/malformed body throws `ResponseDeserializationException`, which is not `ApiException<TError>`. **MUST load `dotnet-error-handling`**.
11. **Idempotency** — the `Idempotency-Key` header the SDK sends is a fresh `Guid.NewGuid()` per call (`Api/AuthorizationsApi.cs`, `Api/TransfersApi.cs`, `Api/PaymentInstrumentsApi.cs`) and deduplicates nothing; only a key-shaped member on the request record is a key, and capture/void/reversal records have none. **MUST load `dotnet-calling-endpoints`**.
12. **Testing** — the only seam is the `HttpClient` handed to the constructor, while the DI extension builds its own from `IHttpClientFactory`; stubbing the wrong layer tests nothing. **MUST load `dotnet-testing`**.

**Hazard row (verbatim, always applies):** a body that does not match its declared type — a drifted or malformed **2xx** response (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`; a catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 9. Assumptions & Blockers

**Blockers:** none. Every capability the task needs exists in this SDK: buyer identity (`CreateIdentity`), payment instrument create/list/get/disable (`CreatePaymentInstrument`/`ListPaymentInstruments`/`GetPaymentInstrument`/`UpdatePaymentInstrument`), authorize (`CreateAuthorization`), capture (`CaptureAuthorization`), void (`VoidAuthorization`), refund (`CreateTransferReversal`), refunds read (`ListTransferReversals`), transaction read/list for reconciliation (`GetTransfer`/`ListTransfers`), merchant read (`GetMerchant`). There is **no delete** operation for a payment instrument — `DELETE /api/payment-methods/{id}` is implemented as the documented disable (`enabled=false`), and the API's own doc on `PaymentInstrumentCard.enabled`/`PaymentInstrumentDisableAPaymentInstrument` is the basis.

**Assumptions (task-level, not map facts):**
- The task's `FINIX_ENVIRONMENT` is the sandbox environment (`ServerEnvironment.Production` is the only member and hosts `finix.sandbox-payments-api.com`); any other value is rejected at startup.
- `FINIX_CURRENCY` must be `USD` or `CAD` (the only `Currency` members); other currencies are rejected at startup because the open enum has no public factory.
- `FINIX_MERCHANT_ID` is a merchant the credentials can read; startup `GetMerchant` enforces it.
- One Finix buyer `Identity` per shopper, created lazily and stored; one-off card payments reuse it but create a payment instrument that is not saved as a shopper payment method.
- `POST /api/orders` and `POST /api/payment-methods` carry no caller idempotency key, so a retried create may produce a duplicate order/saved card (no money moves); this is accepted rather than claimed.
- Refund idempotency is app-enforced only: `RefundTransfer` exposes no key member, so Finix cannot deduplicate a reversal.
- `refundId` returned by `POST /api/orders/{orderId}/refunds` is the reversal `Transfer.Id`; `net proceeds = Transfer.Amount - Transfer.Fee`, and when `Fee` is null the fee/net are reported as null ("Finix reported no fee") rather than assumed zero.
- `POST /api/orders/{orderId}/refunds` is shopper-scoped (the task lists only fulfil, cancel and reconciliation as operator actions); fulfil, cancel and reconciliation are administrator-only.
- Direct card-detail submission is documented by the map as testing-only/PCI-scope; this build targets the sandbox as instructed and stores no PAN/CVV. A production card-present/PCI posture would need hosted tokenization, which this SDK surface does not offer here.
- The app keeps its records in the existing EF `CatalogContext` (in-memory when `UseOnlyInMemoryDatabase=true`); a claim that must outlive the process is not available with the in-memory provider, so duplicate prevention is per-host — acceptable for this task's per-host isolated stores.
