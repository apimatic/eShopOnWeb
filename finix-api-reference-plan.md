# finix-api-reference-plan.md

Integration: Finix card payments + saved cards for eShopOnWeb (`src/PublicApi`).
SDK: Finix API Reference .NET (`FinixApiReference`), source root `.opencode/sdk/dotnet/` (paths below are relative to that root).
Scope: hold → capture → refund, saved cards, reconciliation. Additive to the existing catalog/basket/order flow.

---

## 1. Scope & sequence

| # | Step | Finix operations used |
| --- | --- | --- |
| 1 | Bind `Finix:*` configuration, fail-fast validation, build the singleton `FinixApiReferenceClient` (Basic auth, base URL/override, retry/logging posture). | none |
| 2 | Persist payment state: extend `Order`; add `SavedPaymentMethod`, `RefundRecord`, `FinixOperationClaim`, `FinixBuyerProfile` to `CatalogContext` (+ EF configs). | none |
| 3 | Resolve the shopper's Finix buyer `Identity` (create once, cache id). | `Identities.CreateIdentity`; `Identities.ListIdentities` (unknown-outcome re-read) |
| 4 | Saved cards: `POST/GET/DELETE /api/payment-methods` — create card PI, list caller's saved cards, disable + remove on delete. | `PaymentInstrumentsApi.CreatePaymentInstrument`, `GetPaymentInstrument`, `ListPaymentInstruments`, `UpdatePaymentInstrument` |
| 5 | `POST /api/orders` — create the existing `Order` + `OrderItem`s from catalog ids/quantities at catalog prices; status `AwaitingPayment`. | none |
| 6 | `POST /api/orders/{orderId}/pay` — authorize the order total (saved card by `paymentMethodId`, or one-off card details → transient PI); hold only, no capture. | `PaymentInstrumentsApi.CreatePaymentInstrument` (one-off only); `AuthorizationsApi.CreateAuthorization`; `ListAuthorizations`/`GetAuthorization` (unknown outcome) |
| 7 | `POST /api/orders/{orderId}/fulfil` (Administrators) — capture the hold, read Finix's captured amount + fee + computed net. A hold that can no longer be captured is returned as an operator-actionable conflict (authorization `state` + `failure_code`/`failure_message`), not an unexplained failure. | `AuthorizationsApi.CaptureAuthorization`, `GetAuthorization`; `TransfersApi.GetTransfer` |
| 8 | `POST /api/orders/{orderId}/cancel` (Administrators) — void the hold, release funds. | `AuthorizationsApi.VoidAuthorization`, `GetAuthorization` |
| 9 | `POST /api/orders/{orderId}/refunds` (Administrators) — full/partial refund of the capture with a caller idempotency key; reject any amount above `captured − already refunded`. | `TransfersApi.CreateTransferReversal`, `ListTransfers` (unknown outcome) |
| 10 | `GET /api/my-orders` — caller's orders with payment state (local read). | none |
| 11 | `GET /api/reconciliation?from=&to=` (Administrators) — Finix transfers over the whole date range, matched against eShop orders/refunds. | `TransfersApi.ListTransfers` (cursor walk) |
| 12 | Sandbox verification: test card 5200 8282 8282 8210, exp 12/2029, CVC 022; authorize → capture → refund; save card → reuse on a second order. | all of the above |

**Response identifiers (top-level, per the task):** `orderId` from `POST /api/orders`; `paymentMethodId` from `POST /api/payment-methods`; `refundId` from `POST /api/orders/{orderId}/refunds` (the Finix refund transfer id, falling back to the stored claim key). The rest of each response shape is **decided and implemented**: each response also carries the local order id and the Finix ids/state/amounts needed to drive the next step (`PaymentContracts.cs`).

**Endpoint map:** `POST /api/orders` (shopper), `POST /api/orders/{orderId}/pay` (shopper), `POST /api/orders/{orderId}/fulfil` (Administrators), `POST /api/orders/{orderId}/cancel` (Administrators), `POST /api/orders/{orderId}/refunds` (Administrators), `GET /api/my-orders` (shopper), `GET /api/reconciliation` (Administrators), `POST/GET /api/payment-methods` (shopper), `DELETE /api/payment-methods/{paymentMethodId}` (shopper). Each action is its own route — no combined pay/fulfil/refund call. The three operator routes use `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` (value `"Administrators"`), exactly as `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` does.

**Repo conventions (exemplars):** minimal-API `IEndpoint<TResponse, TRequest, …>` classes under `src/PublicApi/<Feature>Endpoints/` with `AddRoute` (`MapPost`/`MapGet`/`MapDelete`) — imitate `CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` and `DeleteCatalogItemEndpoint.cs`; responses derive from `BaseResponse` (correlation id) like `BaseResponse.cs`; persistence through `IRepository<T>`/`IReadRepository<T>` over `CatalogContext` (`Infrastructure/Data/CatalogContext.cs`); errors flow through `Middleware/ExceptionMiddleware.cs`; caller identity is the JWT `ClaimTypes.Name` issued by `Infrastructure/Identity/IdentityTokenClaimService.cs`.

## 2. CONTRACT SHEET

- **Signatures below are generated code, verbatim.** Each operation that takes input takes **ONE request record as its first parameter** (an operation with no inputs takes none), built with an object initializer whose property names are the record's own — never flat arguments.
- **Every SDK type is written fully-qualified with the namespace its source path implies**, taken from the path the map gives for THAT type — never from where a neighbouring type sits. (`Requests/*` → `FinixApiReference.Requests.<Controller>`; `Models/*` → `FinixApiReference.Models`; `Models/AnyOf/*` → `FinixApiReference.Models.AnyOf`; `Models/Enums/*` → `FinixApiReference.Models.Enums`; `Errors/*` → `FinixApiReference.Errors`; `Api/*` → `FinixApiReference.Api`.)

All operations below are **Case A (typed)**; `TryGetRawError([NotNullWhen(true)] out RawError?)` is the inherited fallback on every typed error. All are on server group **`Default`**; every response is a single body (no pagination unless a Pagination cell says so). No operation has a no-throw `…Result` variant.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| A `paymentMethodId` accepted by pay must be a card this application saved for the caller | `AuthorizationsApi.CreateAuthorization` (pay) ← `PaymentInstrumentsApi.ListPaymentInstruments` (filtered `owner_identity_id` = the caller's stored Finix buyer identity) | the pay endpoint loads the caller's `SavedPaymentMethod` row by `paymentMethodId` + `BuyerId` before `CreateAuthorization`; a missing/foreign row is rejected before the SDK call |
| A `paymentMethodId` accepted by delete must be a card this application saved for the caller | `PaymentInstrumentsApi.UpdatePaymentInstrument` (disable) ← `PaymentInstrumentsApi.ListPaymentInstruments` (filtered `owner_identity_id`) | the delete endpoint loads the caller's `SavedPaymentMethod` row by id + `BuyerId` before `UpdatePaymentInstrument` |
| An `orderId` accepted by an operator action must be an order this application created | `AuthorizationsApi.CaptureAuthorization` / `VoidAuthorization` / `TransfersApi.CreateTransferReversal` ← the `Order` stored by `POST /api/orders` (and returned by `GET /api/my-orders`) | each operator endpoint loads the `Order` by `orderId` and checks its stored Finix ids/status before the SDK call |
| An `idempotencyKey` accepted by refunds must not already have produced a refund for this order | `TransfersApi.CreateTransferReversal` ← the earlier `CreateTransferReversal` result stored in `RefundRecord` | the refund claim (`refund:{orderId}:{idempotencyKey}` primary key) is inserted before `CreateTransferReversal`; a duplicate PK rejects the request |
| A `source` sent to authorize must be a `PaymentInstrument.Id` that exists | `AuthorizationsApi.CreateAuthorization` ← `PaymentInstrumentsApi.CreatePaymentInstrument` (one-off) or the stored `SavedPaymentMethod.FinixPaymentInstrumentId` | the pay handler uses only the id returned by the create call or the stored row; never a caller-supplied raw PI id |

## 3. Trap notes

- **Step 1 — client lifetime.** When the client's options are built and captured decides whether a rotated credential or a changed base URL ever reaches a call; getting it wrong silently pins the first configuration. **MUST load `dotnet-client-initialization`.**
- **Step 1 — Basic auth.** Basic is a two-part credential; how a missing or blank part fails, and when, is not obvious from the property names. **MUST load `dotnet-authentication`.**
- **Step 1 — retries/timeouts/logging.** Which verbs the SDK resends, what `Timeout` actually bounds, and what an unset `LoggerFactory` can switch on are governed by the resilience skill; guessing them silently duplicates writes or logs card data. **MUST load `dotnet-configuration-resilience`.**
- **Step 2/4/6 — models and unions.** Unions are open on read and response payloads sit one level down; reading them as flat records or C# enums mis-binds fields. **MUST load `dotnet-models`.**
- **Step 6/9/11 — calling endpoints.** The request-record/`requestOptions` shape, and where the wire route and behavioural prose actually live, are not on the map row; getting them wrong sends the wrong call. **MUST load `dotnet-calling-endpoints`.**
- **Step 6–10 — error boundary.** A 2xx body that drifts from its declared type, or a non-2xx body that does not match the operation's generated error, surfaces as `ResponseDeserializationException`, which is **not** an `ApiException<TError>` and escapes a catch ladder that only handles `ApiException<TError>`. **MUST load `dotnet-error-handling`.**
- **Step 12 — verification.** The seam for faking HTTP and for failing a connection mid-write is not obvious from the SDK surface; stubbing the wrong layer makes the unknown-outcome tests meaningless. **MUST load `dotnet-testing`.**

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | **Credential fail-fast** | Bind a `FinixOptions` from the `Finix` configuration section (`Username`, `Password`, `MerchantId`, `Environment`, `Currency`, `BaseUrl`). At startup, refuse to start when `Username`, `Password`, or `MerchantId` is null/blank (all three checked — Basic is two-part and MerchantId is required by every authorization), when `Environment` is not `sandbox`/`live`, or when `Currency` does not resolve through `Currency.TryGetKnownValue` (only `USD`/`CAD` are declared). The check runs before the client is first resolved, so a bad deployment never reaches a first-call `AuthSchemeException`. |
| 2 | **Secret sourcing & rotation** | Locally `dotnet user-secrets`; in deployment environment variables `FINIX_USERNAME`/`FINIX_PASSWORD`/`FINIX_MERCHANT_ID` mapped to `Finix:*`. `AddFinixApiReferenceClient` builds and captures options once in the singleton, so rotation requires a process restart. | 3 | **Total timeout budget** | `RetryOptions.Default().Timeout = 100s` bounds each attempt; POSTs are not retried, so a pay/capture/refund call has a ≤100s budget; PUTs (capture/void/disable) may run up to `1 + MaxRetries` attempts. | 4 | **Write-retry ownership** | SDK may resend **PUT** writes: `CaptureAuthorization`, `VoidAuthorization`, `UpdatePaymentInstrument` (idempotent by resource id). ## 6. Assumptions & Blockers

**Blockers: none.** The map covers every required capability: buyer identity (`CreateIdentity`), card tokenization/save (`CreatePaymentInstrument` + `PaymentInstrumentTokenCard` alternative), hold (`CreateAuthorization`), capture (`CaptureAuthorization`), void (`VoidAuthorization`), refund (`CreateTransferReversal` with `RefundTransfer`), saved-card disable (`UpdatePaymentInstrument`), status re-reads (`GetAuthorization`, `GetTransfer`, `GetPaymentInstrument`), and transaction listing with a date range and cursor (`ListTransfers`).

Assumptions:

- **No live server environment in the SDK.** `ServerEnvironment` declares only `Production`, whose host is the Finix sandbox. `FINIX_ENVIRONMENT=live` must therefore be accompanied by `Finix:BaseUrl` set to the live host; the sandbox target here uses `ServerEnvironment.Production` unchanged.
- **Currency set is closed in practice.** `Currency` declares only `USD` and `CAD`; `FINIX_CURRENCY` must be one of them or startup fails fast.
- **One-off card payments need a Payment Instrument.** `AuthorizationAllFields.Source` is a Payment Instrument id, so a one-off card is first passed to `CreatePaymentInstrument` (with the shopper's buyer identity) and the resulting id is used as `Source`; that transient PI id is **not** persisted as a saved card.
- **Buyer identity is per shopper.** One Finix `Identity` (`Type = PERSONAL`, `IdentityRoles = [BUYER]`, `Entity` with only the fields the app has) is created per `BuyerId` and cached in `FinixBuyerProfile`. `Entity5` fields are all optional, so a minimal identity is accepted by the SDK model.
- **Refund idempotency is application-owned.** `RefundTransfer` carries only `refund_amount` and `CreateTransferReversal` has no idempotency member, so the caller's key is enforced by the refund claim PK; two distinct partial refunds use two distinct keys and both proceed.
- **Reconciliation is transfer-based.** Captures and refunds are `Transfer`s; the report lists `ListTransfers` over `created_at.gte`/`created_at.lte`. Holds (`Authorization`) are not transfers and are not in that report.
- **Net proceeds are computed.** `Transfer` exposes `Amount` and `Fee` but no `net` field; net = captured `Amount` − `Fee`.
- **Refund amount is an `int`.** `RefundTransfer.RefundAmount` is `int` while `CaptureAuthorization.CaptureAmount`/`Transfer.Amount` are `long`; catalog-order totals are far below `int.MaxValue` cents, so the plan validates the refund amount against `captured − refunded` and then casts to `int`.
- **Card address, if supplied, needs all required `Address` members.** `Address.Line1`, `City`, `Region`, `PostalCode`, and `Country` are all `required`; the plan omits `Address` unless the caller supplies a complete one.
- **Cents conversion.** Catalog `Price` is `decimal`; order total → cents by round-half-away-from-zero, so the authorized amount equals the order total to the cent.
- **Claim store lifetime.** `CatalogContext` is the app's own store (SQL Server in production). In this environment it runs in-memory and is per-host; claims therefore do not outlive the process, which is acceptable because each sandbox flow is driven against one `PublicApi` process.
- **BuyerId is the JWT `ClaimTypes.Name`.** This matches the existing `Order.BuyerId` and the token issued by `IdentityTokenClaimService`.
- **PCI caveat on `CreatePaymentInstrument`.** Its `<remarks>` warn that creating PIs directly via the API is for testing and that hosted fields keep you out of PCI scope. The task mandates card details in the request and the sandbox test card; the app never persists the PAN/CVV.
- **Payment Instrument Association is optional and not used.** It only assigns buyer-PI fees to a merchant. **Decision:** no association is created; sandbox authorizations succeeded without one because each authorization names `Finix:MerchantId` directly.
- **Finix date-filter format differs from the SDK's.** Finix expects `created_at.gte/lte` as `yyyy-MM-ddTHH:mm:ss` with no offset, while the SDK serializes `DateTimeOffset` with an offset. `ReconcileAsync` passes a per-call `SdkHook.OnRequest` (`NormalizeDateRangeQuery`) that rewrites only the `created_at.*` query values; every other parameter is untouched.
- **Partial refunds need a settled capture.** Finix accepts a full reversal while the capture transfer is `PENDING`, but a partial reversal requires `SUCCEEDED`. `RefundAsync` polls `GetTransfer` for up to 64 seconds before a partial reversal; if it is still `PENDING` it returns `409 CAPTURE_PENDING` with the operator action. The sandbox capture settled in ~15–55 seconds during verification.
- **Authorization idempotency is per order instance.** The deterministic key is `eshop-order-{orderId}-{orderDate.UtcTicks}-auth`, not just the local integer id, so a sandbox account that retains prior idempotency ids does not collide after the in-memory database resets between runs.
- **Existing `PaymentMethod` entity is unused.** `ApplicationCore/Entities/BuyerAggregate/PaymentMethod.cs` exists but is not in `CatalogContext`; the plan adds its own `SavedPaymentMethod` entity rather than reviving it.
