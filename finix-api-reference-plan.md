# finix-api-reference-plan.md — Finix card payments + saved cards for eShopOnWeb

Every **Source** label below is relative to the SDK root `.opencode/sdk/dotnet` (the map's own paths are relative to that root). `UNVERIFIED` and `YOUR CALL — not in the map` are used exactly as §7 defines.

## 1. Scope & sequence

Additive only: new entities/configurations/DbSets beside the existing ones, new endpoints beside `src/PublicApi/CatalogItemEndpoints/`, no change to existing order/order-item shapes beyond added properties.

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Config + client: bind `Finix:` section, fail-fast validation, one `FinixApiReferenceClient` singleton (owned `HttpClient`, logging/retry/server set explicitly). Add the SDK `ProjectReference` to `PublicApi`. | none |
| 2 | Persistence: `ShopperFinixIdentity`, `SavedCard`, `PaymentOperationClaim`, `RefundRecord` entities + EF configurations + `CatalogContext` DbSets; additive `Order` payment-state properties. | none |
| 3 | Finix gateway service (thin, per-group wrapper) used by every endpoint; maps typed errors to operator/shopper messages. | `CreateIdentity`, `ListIdentities`, `CreatePaymentInstrument`, `GetPaymentInstrument`, `ListPaymentInstruments`, `UpdatePaymentInstrument`, `CreateAuthorization`, `GetAuthorization`, `CaptureAuthorization`, `VoidAuthorization`, `GetTransfer`, `CreateTransferReversal`, `ListTransferReversals`, `ListTransfers`, `ListAuthorizations` |
| 4 | `POST /api/orders` — order from catalog ids+quantities, identity from JWT, total stored in cents, status `AwaitingPayment`. Order creation is intentionally **not** deduplicated: two identical orders are legitimate. | none |
| 5 | `POST /api/orders/{orderId}/pay` — resolve caller identity; saved-card path or raw-card path (raw card first creates a **one-off** `Payment Instrument`, never saved); authorize full stored total. | `CreateIdentity` (reuse), `CreatePaymentInstrument` (raw-card only), `GetPaymentInstrument` (saved card), `CreateAuthorization` |
| 6 | `POST /api/orders/{orderId}/fulfil` — operator; capture the stored authorization, then read the capture `Transfer` for amount/fee. If the capture response omits the transfer id, re-read the authorization before reporting an operator message. | `CaptureAuthorization`, `GetAuthorization` (re-read), `GetTransfer` |
| 7 | `POST /api/orders/{orderId}/cancel` — operator; void the stored authorization. | `VoidAuthorization`, `GetAuthorization` (re-read) |
| 8 | `POST /api/orders/{orderId}/refunds` — shopper-scoped per the mandate; refund the capture `Transfer` full/partial with caller key; app caps cumulative refunds and settles a duplicate reversal from Finix's error reference. | `CreateTransferReversal`, `ListTransferReversals` (settlement), `GetTransfer` |
| 9 | `GET /api/my-orders` — caller's orders with payment state. | none |
| 10 | `GET /api/reconciliation?from=&to=` — walk every page of Finix transfers + authorizations in range, match against eShop orders both directions. Finix date filters are normalized to the provider's bare ISO-8601 form at the SDK request hook. | `ListTransfers`, `ListAuthorizations` |
| 11 | `POST /api/payment-methods`, `GET /api/payment-methods`, `DELETE /api/payment-methods/{paymentMethodId}` — save, list, remove (Finix disable + local tombstone). | `CreateIdentity` (first save), `CreatePaymentInstrument`, `GetPaymentInstrument`, `ListPaymentInstruments` (settlement), `UpdatePaymentInstrument` (disable) |
| 12 | Tests (HTTP-handler stub) + end-to-end verification with the sandbox test card. | all of the above |

App-side state (not SDK contract): `Order` gains `PaymentReference` (Guid used as the provider idempotency id), `PaymentStatus`, `FinixAuthorizationId`, `FinixAuthorizationState`, `FinixTransferId`, `FinixCaptureState`, `AuthorizedAmountCents`, `CapturedAmountCents`, `FeeCents`, `NetCents`, `RefundedAmountCents`, `PaymentFailureCode`, `PaymentFailureMessage`; `RefundRecord` keeps `(OrderId, IdempotencyKey)` unique plus the Finix refund id and state; the total in cents is fixed at order creation and never recomputed from catalog prices. Endpoint conventions follow `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs` (`IEndpoint<…>`, `MapPost("api/…")`, `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`, `.Produces<T>()`, `.WithTags(...)`); caller identity is the JWT `ClaimTypes.Name` that `src/Infrastructure/Identity/IdentityTokenClaimService.cs` writes; records live in `CatalogContext` (`src/Infrastructure/Data/CatalogContext.cs`), which is also the `UseOnlyInMemoryDatabase` store (`src/Infrastructure/Dependencies.cs`).

**CROSS-OPERATION INVARIANTS**

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| A `source` accepted by an authorization must be a Payment Instrument id this application created (saved card or one-off) | `CreateAuthorization` ← `CreatePaymentInstrument` (+ app `SavedCard` store) | `PayOrder` resolves the instrument id from the caller's saved-card row or from the just-created one-off instrument; never accepts an id from the request body |
| A saved instrument id accepted by pay must be one `GET /api/payment-methods` offers the caller, and must still be `enabled` | `CreateAuthorization` ← `GetPaymentInstrument` (+ app `SavedCard` store) | `PayOrder` checks the caller's non-deleted `SavedCard` row, then `GetPaymentInstrument.Enabled != false` and `Identity == caller's Finix identity` |
| An `authorization_id` accepted by capture/void must be the `Id` returned by the create call | `CaptureAuthorization`, `VoidAuthorization` ← `CreateAuthorization` | `FulfilOrder` / `CancelOrder` use the stored `Order.FinixAuthorizationId`; never a request-supplied id |

## 3. Trap notes

- Step 1 — the DI helper builds its own `HttpClient`; a timeout you set on a different `HttpClient` is not the one the SDK uses, and handler lifetime decides DNS staleness — **MUST load dotnet-client-initialization**.
- Step 1 — a blank half of a Basic credential is not a missing credential: the first call fails before anything is sent with `AuthSchemeException`, not a 401 — **MUST load dotnet-authentication**.
- Step 1 — `FINIX_API_REFERENCE_LOG=trace` can turn request-body logging on with no code change and no deploy, and card data travels in a JSON body the SDK logs verbatim — **MUST load dotnet-configuration-resilience**.
- Step 1 — the SDK's retry defaults already include `PUT`, so capture and void can be resent without your code asking — **MUST load dotnet-configuration-resilience**.
- Step 1 — the per-attempt `Timeout` and the caller-visible budget are not the same number; what each knob actually bounds decides whether a caller waits past the request's budget — **MUST load dotnet-configuration-resilience**.
- Steps 2–11 — every operation takes one request record as its first parameter and several responses wrap their payload one level down; reading the return value as the resource yields the wrong object — **MUST load dotnet-calling-endpoints**.
- Steps 2–11 — `AuthorizationsRequest`, `AuthorizationsRequest1`, `TransfersReversalsRequest`, `PaymentInstrumentsRequest`/`Request1`, `CreatePaymentInstrument`, `IdentitiesRequest` are open unions: constructing a variant, reading one back, and handling an unrecognised arm are three different APIs — **MUST load dotnet-models**.
- Steps 2–11 — `Currency` has no public factory; a raw config string does not implicitly convert, and an unknown value must be rejected rather than constructed — **MUST load dotnet-models**.
- Steps 2–11 — a union's `required` members live on the variant, not on the union; an omitted required member is a compile error, an omitted optional one silently changes server behaviour — **MUST load dotnet-models**.
- Steps 4–8 — a typed `ApiException<TError>` is not the only failure: a drifted or malformed 2xx body escapes as `ResponseDeserializationException`, which is not an `ApiException<TError>` — **MUST load dotnet-error-handling**.
- Steps 4–8 — `GenericError` nests its messages under `_embedded.errors`; `ex.Message` is not the provider's actionable text, and the operator needs `code` + `message` + `logref` — **MUST load dotnet-error-handling**.
- Step 10 — the next-page cursor is on the response envelope, and a short page is not the end signal; stopping on page size silently truncates the reconciliation range — **MUST load dotnet-configuration-resilience**.
- Steps 5–8 — a write whose connection drops may already have reached Finix; retrying it without a settlement read can double-charge — **MUST load dotnet-configuration-resilience**.
- Step 8 — Finix rejects a partial reversal while the capture `Transfer` is still `PENDING`, but accepts a full reversal; a duplicate caller key can still surface as a 409 that carries the existing reversal id — **MUST load dotnet-error-handling**.
- Step 10 — the generated SDK formats `created_at` filters with fractional seconds and `Z`, while Finix's sandbox accepts only a bare ISO-8601 date-time — **MUST load dotnet-configuration-resilience**.
- Step 12 — stubbing `FinixApiReferenceClient` is not the seam; the `HttpClient` handler is — **MUST load dotnet-testing**.

## 6. Assumptions & Blockers

**Blockers: none.** Every capability the task needs exists on the map: authorize/capture/void, refund via transfer reversal, card instrument create/get/list/disable, identity create/list, and cursor-paged date-filtered lists.

Assumptions (all resolved by the implementation and live sandbox verification):

1. `CreateAuthorization` accepts only a Payment Instrument id in `source`; the raw-card path creates a one-off instrument (`CreatePaymentInstrument`) and never saves it. Verified live: raw-card pay created `PIaNdv36f2vXVVguDogwsbS2` and no `SavedCard` row.
2. A saved card needs a Finix `Identity` because `PaymentInstrumentCard1.Identity` is required. `ShopperIdentityService` creates one `Buyer` identity per shopper (email plus names derived from the email) and stores it. Verified live: card save and raw-card pay both created identities successfully.
3. `Transfer` has no net-proceeds member. `Fee (fee): long?` is the only fee field, so "net proceeds" is computed as `Amount - (Fee ?? 0)` in `OrderPaymentService`. The sandbox reported fee `0`, net equal to captured amount. **YOUR CALL — decided: `NetCents = CapturedAmountCents - FeeCents`.**
4. The capture response's `Authorization.Transfer` is the capture transfer id. If it comes back null, `FulfilOrderAsync` re-reads with `GetAuthorization` and reports an operator message instead of guessing.
5. `RefundTransfer.RefundAmount` is `int`; a single refund is limited to `int.MaxValue` cents. Cumulative refunds are capped app-side against `CapturedAmountCents` because the map does not state that Finix enforces the sum.
6. `ListPaymentInstruments.OwnerIdentityId` is read as the buyer identity used at instrument creation (`PaymentInstrumentCard.Identity`). Verified live: `FindCardAsync` settlement works for saved-card creation.
7. `Finix:Environment=live` has no SDK member; live traffic requires `Finix:BaseUrl`. The task targets sandbox, so the built-in sandbox URL is used by default.
8. Order totals are converted to cents once at order creation with `Money.ToCents` (`decimal.Round(total * 100, 0, MidpointRounding.AwayFromZero)`). Verified live: 2 × 850 = 1700, 1 × 1950 = 1950, 1 × 850 = 850, and Finix authorized exactly those amounts. **YOUR CALL — decided: store `TotalCents` on the order and never recompute it.**
9. Two distinct cards for one shopper with the same `last4` and expiry are treated as one saved card by the card-save claim key; the Finix `fingerprint` is stored on first success and can be used to detect the collision. **YOUR CALL — decided: claim key `CARD:{shopper}:{last4}:{expMonth}:{expYear}`.**
10. `CatalogContext` is the app record store; a new `SavedCard` entity is added instead of repurposing the unused `PaymentMethod` entity. SQL Server deployments need a migration for the new tables; the in-memory path (`UseOnlyInMemoryDatabase=true`) needs none. **YOUR CALL — decided: new entities, no migration generated for the in-memory verification path.**
11. The SDK is referenced by local `ProjectReference` to `.opencode/sdk/dotnet/src/FinixApiReference/FinixApiReference.csproj`; that path is machine-local and a CI runner without the plugin cannot build it.
12. Live-verified: Finix rejects the SDK's `created_at` filter format (`yyyy-MM-ddTHH:mm:ss.fffZ`) with `422 INVALID_FIELD` and requires `yyyy-MM-ddTHH:mm:ss`. `NormalizeFinixDateQuery` rewrites those query values at `SdkHook.OnRequest`; reconciliation then walked 16 pages / 1307 Finix records and matched eShop authorizations, captures and refunds. **YOUR CALL — decided: keep the hook, do not fork the SDK.**

## Verification guide (sandbox)

1. **Start** PublicApi with the in-memory store and roll-forward: set `UseOnlyInMemoryDatabase=true`, `ASPNETCORE_ENVIRONMENT=Development`, `DOTNET_ROLL_FORWARD=Major`; run `dotnet run --project src/PublicApi --launch-profile PublicApi`. Bind only the assigned port block (the launch profile uses 43503/43504).
2. **Tokens** - `POST /api/authenticate` for `demouser@microsoft.com` / `Pass@word1` (shopper) and `admin@microsoft.com` / `Pass@word1` (operator). Send `Authorization: Bearer <token>` on every other call.
3. **Save a card** - `POST /api/payment-methods` with the Mastercard test card `5200 8282 8282 8210`, expiry `12/2029`, CVC `022`, any name. Keep the top-level `paymentMethodId`.
4. **Order** - `POST /api/orders` with `{"items":[{"catalogItemId":5,"quantity":2}]}`; the response is `AwaitingPayment` with `totalCents` from catalog prices.
5. **Authorize** - `POST /api/orders/{orderId}/pay` with `{"paymentMethodId":"..."}` (saved card) or `{"card":{"number":"5200 8282 8282 8210","expirationMonth":12,"expirationYear":2029,"name":"...","securityCode":"022"}}` (one-off). `authorizedAmountCents` must equal `totalCents`.
6. **Capture at fulfilment** - `POST /api/orders/{orderId}/fulfil` as admin; the response carries `capturedAmountCents`, `feeCents`, `netCents` and the Finix `transferId`.
7. **Refund** - `POST /api/orders/{orderId}/refunds` with `{"amountCents":500,"idempotencyKey":"refund-1"}`. A partial refund may return `409 CAPTURE_STILL_PENDING` until Finix moves the capture to `SUCCEEDED`; retry the same request. Repeating the same key returns the same `refundId`; a different key is a second partial refund; an amount above the remaining captured balance is rejected.
8. **Cancel before capture** - create another order, pay it, then `POST /api/orders/{orderId}/cancel` as admin; the hold is voided and `released` is true.
9. **My orders / reconciliation** - `GET /api/my-orders` (shopper) shows the state; `GET /api/reconciliation?from=...&to=...` (admin, ISO-8601) walks every page and returns matched and unmatched Finix/eShop records plus `truncated`/`nextCursor`.
10. **Saved-card lifecycle** - `GET /api/payment-methods` lists only the caller's cards; `DELETE /api/payment-methods/{paymentMethodId}` removes it; a later pay with that id fails with `PAYMENT_METHOD_NOT_FOUND`. Another shopper cannot list, use or delete it.
