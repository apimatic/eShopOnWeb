# finix-api-reference-plan.md

Integration: Finix API Reference .NET SDK (`FinixApiReference`, root namespace) into eShopOnWeb `src/PublicApi`.
SDK source (map root): `.opencode/sdk/dotnet/` (plugin-relative; all `Source` paths below are relative to it).
Plan owner: `finix-api-reference-planner`. No project code is written by this plan.

---

## 1. Scope & sequence

Implementation order. Each step names the operations it uses. A capability the map lacks is a Blocker (§6), never an invented data path.

| # | Step | Operations used |
| --- | --- | --- |
| 1 | **Config + client wiring.** Bind the `Finix:` section (`Username`, `Password`, `MerchantId`, `Environment`, `Currency`, `BaseUrl`) from `IConfiguration` (env vars `FINIX_*`; values in user-secrets for `src/PublicApi`). Fail fast at startup on any blank part. Register `FinixApiReferenceClient` as a singleton with `BasicAuth`, `ServerEnvironment.Production`, `Logging.LogRequestBody = false`, GET-only retries. If `Finix:BaseUrl` set, assign it to `options.Server.Default.Production.BaseUrl`. | none |
| 2 | **Persistence (app-owned).** Add EF entities to `CatalogContext`: `OrderPayment` (1:1 with `Order`, carries payment state, authorization id, capture transfer id, captured cents, fee cents, refunded cents, currency), `SavedCard` (shopper → Finix identity id + payment-method id + last4/brand/expiry), `PaymentOperation` (claim key primary key), `RefundRecord` (claim key → refund id). No migration needed under the in-memory provider. | none |
| 3 | **Shopper Finix identity bootstrap.** Create one `Identity` per shopper (token name) on first use; persist `identityId`. `ListIdentities` exists as a tag/email fallback lookup but is not on the hot path. | `Identities.CreateIdentity` |
| 4 | **Saved cards (Flow 2).** Create a card (`purpose=saved` tag, shopper identity, full details in the request only); list by `owner_identity_id` + saved tag and intersect with `SavedCard`; `DELETE` = disable (`enabled=false`) after an ownership read. | `PaymentInstrumentsApi.CreatePaymentInstrument`, `ListPaymentInstruments`, `GetPaymentInstrument`, `UpdatePaymentInstrument` |
| 5 | **`POST /api/orders`.** Reuse `Order`/`OrderItem`/`CatalogItemOrdered`; price each line from `CatalogItem.Price`; total to cents; create `OrderPayment` in `AwaitingPayment`; respond with top-level `orderId`. | none |
| 6 | **`POST /api/orders/{orderId}/pay` (shopper).** Claim `pay:{OrderPayment.ProviderKey}` (a per-order GUID, so the provider key is unique across in-memory restarts). Card details ⇒ create a one-off PI (`purpose=oneoff`) then authorize its id; saved card ⇒ authorize its id. `CreateAuthorization` with `amount` = order total cents, `currency`, `merchant`, `source`, `idempotency_id` = claim key, `tags` carrying `orderId`. Persist authorization id + state. | `PaymentInstrumentsApi.CreatePaymentInstrument` (card-details path), `AuthorizationsApi.CreateAuthorization` |
| 7 | **`POST /api/orders/{orderId}/fulfil` (admin).** Claim `fulfil:{orderId}`. `GetAuthorization` to test capturability; if not capturable return the operator explanation from `state`/`is_void`/`void_state`/`expires_at`/`failure_code`/`failure_message`. Else `CaptureAuthorization` with `capture_amount` = held amount, read `transfer`, then `GetTransfer` for captured amount + `fee`; net = `amount - fee`. Persist. | `AuthorizationsApi.GetAuthorization`, `CaptureAuthorization`, `TransfersApi.GetTransfer` |
| 8 | **`POST /api/orders/{orderId}/cancel` (admin).** Claim `cancel:{orderId}`. `VoidAuthorization` with `void_me = true`; persist `is_void`/`void_state`. Funds released, nothing captured. | `AuthorizationsApi.VoidAuthorization` |
| 9 | **`POST /api/orders/{orderId}/refunds` (admin or order owner).** Claim `refund:{orderId}:{callerKey}`. Wait for the capture transfer to leave `PENDING` (sandbox takes ~20-30 s), `GetTransfer` (capture) for captured cents; `ListTransferReversals` (all pages, fail closed if truncated) for already-refunded; reject amount > captured − refunded. `CreateTransferReversal` with `refund_amount`; the provider extension field `idempotency_id` is `refund:{ProviderKey}:{callerKey}` so it is unique across runs. Persist refund id/state; respond top-level `refundId`. | `TransfersApi.GetTransfer`, `ListTransferReversals`, `CreateTransferReversal` |
| 10 | **`GET /api/my-orders` (shopper).** Read `Order` + `OrderPayment` by `BuyerId` = token name. | none |
| 11 | **`GET /api/reconciliation?from&to` (admin).** Parse ISO-8601 to `DateTimeOffset`. Drain `ListTransfers` and `ListAuthorizations` across all pages; filter `CreatedAt` to the requested range in the app because the SDK's `DateTimeOffset` query serialization (`yyyy-MM-ddTHH:mm:ss.fffZ`) is rejected by the sandbox with `422 INVALID_FIELD` (live-verified); the API's no-filter default window is 30 days, so `from` older than that sets `complete=false`. Line up against stored order payment ids and `tags.orderId`; classify `matched` / `finixOnly` / `eshopOnly`; expose a `complete` flag. | `TransfersApi.ListTransfers`, `AuthorizationsApi.ListAuthorizations` |
| 12 | **Error boundary, logging, tests.** One exception translation for the SDK family; never log card fields or request bodies; unit/integration tests via the `HttpClient` stub seam. | none |

Amount convention: `Order.Total()` is a `decimal` in major units; Finix `amount`/`capture_amount`/`refund_amount` are **integer cents**. Convert once (`total * 100`, reject non-integral cents) and compare the held amount to that integer.

## 2. CONTRACT SHEET

> Signatures are generated code, verbatim — each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer whose property names are the record's own, never flat arguments.

> Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits.

Controller accessors: `client.Identities` · `client.PaymentInstrumentsApi` · `client.AuthorizationsApi` · `client.TransfersApi`.

**Union variants not used, stated so they are not mistaken for the path:** `AuthorizationsRequest` has 13 variants — only `AuthorizationAllFields` is used; `AuthorizationMinimalFields` (amount/currency/merchant/source, no `idempotency_id`, no `tags`) and `AuthorizationAuthorizationWithCvv` (source + `security_code`) exist but are not the path; 3DS, card-present, buyer-charges, motor-vehicle-rental, gaming, lodging, level-2, level-3, recurring variants are out of scope. `PaymentInstrumentsRequest` has 14 variants — only `PaymentInstrumentCard1` is used (bank, Plaid, token, Apple/Google Pay variants out of scope). `TransfersReversalsRequest` has 3 variants — only `RefundTransfer` is used.

**Which request records mark nothing required:** `ListPaymentInstrumentsRequest`, `ListTransfersRequest`, `ListAuthorizationsRequest` mark no member required — the carried optional fields above are exactly the ones the endpoint's prose ties to acceptance/scope, and every omitted filter is named in the row.

**Live-verified SDK limitation — date filters.** The SDK serializes `CreatedAtGte`/`CreatedAtLte` through `ToIso8601()` as `yyyy-MM-ddTHH:mm:ss.fffZ`. The Finix sandbox rejects that with `422 INVALID_FIELD: Must be in format 2018-01-26T11:21:23` (observed live). Reconciliation therefore does **not** send `created_at` filters; it drains all pages of `ListTransfers`/`ListAuthorizations` (scoped by `Merchant`) and filters `CreatedAt` client-side. The API's no-filter default is the last 30 days, so a `from` older than 30 days sets `complete=false`. `ListTransferReversals` needs no date filter and is unaffected.

### 2.3 Client construction, auth, server-node facts

- Constructor: `new FinixApiReferenceClient(HttpClient httpClient, FinixApiReferenceClientOptions options)` — the only constructor. DI alternative: `services.AddFinixApiReferenceClient(options => { … })`, which registers a **singleton** and builds the options object once inside the factory; if `Logging.LoggerFactory` is unset it takes the container's `ILoggerFactory` (`src/FinixApiReference/ServiceCollectionExtensions.cs`).
- Options surface (`src/FinixApiReference/FinixApiReferenceClientOptions.cs`): `Environment: ServerEnvironment`, `Retry: RetryOptions`, `Logging: LoggingOptions`, `TimeProvider`, `Server: ServerOptions`, `StreamReadTimeout: TimeSpan?`, `Hooks: IReadOnlyList<SdkHook>`, `BasicAuth: BasicAuthCredentials?`, `BasicAuthProvider`.
- Auth: `options.BasicAuth = new FinixApiReference.Core.Authentication.Basic.BasicAuthCredentials { Username = …, Password = … }` — both members `required` (`src/FinixApiReference/Core/Authentication/Basic/BasicAuthCredentials.cs`). The SDK's own env fallback reads `FINIX_API_REFERENCE_BASIC_AUTH_USERNAME` / `FINIX_API_REFERENCE_BASIC_AUTH_PASSWORD` (`src/FinixApiReference/AuthSchemes.cs`) — **this deployment supplies the credential in code from `Finix:Username`/`Finix:Password` and does not use those SDK variables.**
- Environments (`src/FinixApiReference/Servers/ServerEnvironment.cs`): exactly one member, `ServerEnvironment.Production` (wire `production`, **hosting = sandbox**). There is no live member; live traffic requires the `Finix:BaseUrl` override.
- Server group (`sdk-map.md` *Servers & auth*): one group, `Default`; `Production` base URL `https://finix.sandbox-payments-api.com`; override point `options.Server.Default.Production.BaseUrl` (`src/FinixApiReference/ServerOptions.cs` → `src/FinixApiReference/Servers/DefaultOptions.cs`).
- Logging: `LoggingOptions` is a record with `LoggerFactory: ILoggerFactory?`, `LogRequestHeaders`, `LogResponseHeaders`, `LogRequestBody`, `BodySizeLimit`, `LoggableContentTypes`, `RedactedHeaders`, `RedactedKeys`, `UnmaskHeaders`, `RedactionPlaceholder` (`src/FinixApiReference/Core/Configuration/LoggingOptions.cs`). Leaving `LoggerFactory` unset arms `FINIX_API_REFERENCE_LOG`, whose `trace` forces body logging on.
- Every non-GET call sends `Idempotency-Key: Guid.NewGuid()` from the generated code (`Api/AuthorizationsApi.cs`, `Api/TransfersApi.cs`, `Api/PaymentInstrumentsApi.cs`) — **not a caller key**.
- The client's own doc-comment states `idempotency_id` is available on `/transfers`, `/authorizations` and `/transfers/{id}/reversals`, is scoped per endpoint, and that a repeat raises an exception (`src/FinixApiReference/FinixApiReferenceClient.cs`, *Idempotent Requests*).
- `Payment Instruments` are tied to one `Identity` and the identity cannot be changed after creation (`src/FinixApiReference/FinixApiReferenceClient.cs`, `PaymentInstrumentsApi` summary).
- `UpdatePaymentInstrument` is documented to disable the instrument "so it can't be used in requests" (`src/FinixApiReference/Api/PaymentInstrumentsApi.cs` remarks) — there is no delete operation among the 8.
- `CaptureAuthorization` sets `Authorization.transfer` to the id of the Transfer that moves funds (`src/FinixApiReference/Api/AuthorizationsApi.cs` remarks).
- `VoidAuthorization` releases funds, leaves the transaction incomplete, makes the Authorization uncapturable, and can take up to seven days to remove the hold (`src/FinixApiReference/Api/AuthorizationsApi.cs` remarks).
- `Transfer` carries `amount: long?` and `fee: long?` but **no net field**; net proceeds is `amount - fee`, computed by the app (`src/FinixApiReference/Models/Transfer.cs`).

## 6. Assumptions & Blockers

**Blockers:** none. Every capability the flows need is present in the map; the near-misses (no delete operation, no `idempotency_id` member on `RefundTransfer`) are recorded as limitations below, each with a supported path.

**Assumptions / limitations:**

1. **Delete is a disable.** `PaymentInstrumentsApi` has 8 operations and **no delete**; `UpdatePaymentInstrument` is documented to disable an instrument "so it can't be used in requests" (`enabled=false`). The app therefore treats `DELETE /api/payment-methods/{id}` as a disable and filters `Enabled == false` out of its own listing, which satisfies "not listed / not usable". The instrument is not physically removed at Finix.
2. **Refund idempotency is app-owned.** `RefundTransfer` declares only `refund_amount` — no `idempotency_id`, no `tags`. The client's own doc-comment says `idempotency_id` is accepted on `/transfers/{id}/reversals`, so the implementation sends it through `RefundTransfer.AdditionalProperties` as `refund:{ProviderKey}:{callerKey}` **in addition to** the app's `PaymentOperation` claim; the claim is authoritative. A provider-side conflict surfaces through `TryGetRawError` because `CreateTransferReversal` declares no 422 accessor.
3. **PCI scope.** `CreatePaymentInstrument`'s remarks say creating payment instruments directly via the API should only be done for testing and that hosted fields must be used in production. This integration targets the sandbox, so direct creation is used for both the saved-card and the one-off-card paths; a production build would replace the card-details collection with hosted fields and keep the same PI-id-based authorize call.
4. **One-off cards reuse the identity.** `PaymentInstrumentCard1.Identity` is required, so every shopper needs a Finix `Identity`; a one-off card is created as a PI under that same identity (tagged `purpose=oneoff`) and its id is the authorization `source`. One-off PIs are excluded from the saved-card listing by tag and by the `SavedCard` index.
5. **Currency is USD or CAD only.** `Currency` declares exactly `Usd`/`Cad` and has no public factory; `FINIX_CURRENCY` must be one of those or startup fails. This environment uses `USD`.
6. **Fee and net.** `Authorization` has no fee field; the fee is read from the capture `Transfer.Fee`. `Transfer` has no net field, so net proceeds is `Transfer.Amount - Transfer.Fee`, computed by the app and labelled as computed, not Finix-reported.
7. **Capturability is decided defensively.** The map does not spell out which `State1` value means "hold live but not yet captured". The plan decides capturability from `IsVoid`, `VoidState`, `ExpiresAt`, `Transfer` and `FailureCode` on a fresh `GetAuthorization`, and returns those values in the operator explanation — it never guesses from `State` alone.
8. **The SDK has no live environment.** `ServerEnvironment` declares only `Production`, which hosts the sandbox. `Finix:Environment=live` therefore requires `Finix:BaseUrl`; the plan makes that a startup error rather than silently sending live traffic to the sandbox.
9. **In-memory persistence is per host and per run.** Orders, payments and saved cards live only in the `PublicApi` process's in-memory store, so the whole flow must be exercised in one run through `PublicApi` alone. No migration is added (the provider ignores them).
10. **Caller identity and admin role.** Caller identity is the token's `ClaimTypes.Name` (the username), matching `Order.BuyerId`; the operator role is `BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS` (`"Administrators"`), the role the project already uses for privileged endpoints.
11. **`Order` has no payment state.** Payment state is added as a 1:1 `OrderPayment` entity keyed by `OrderId` rather than by widening `Order`; this keeps `Order`/`OrderItem` reuse intact.
12. **Request bodies for the non-provider idempotency keys.** The task mandates a caller key only for refunds. `POST /api/orders` and `POST /api/payment-methods` therefore take an **optional** `IdempotencyKey` in the request body (an additive request field, `YOUR CALL — not in the map`); when supplied, the claim makes a second click return the first result, and when omitted the operation still works. Refunds require `idempotencyKey`.
13. **`YOUR CALL — not in the map` items** (decided at implementation, recorded in the code): the shape of every response other than the three mandated top-level ids; the `OrderPayment` state names; the reconciliation entry shape and its `complete` flag; the `PaymentOperation` key format; the tags used to mark saved vs one-off instruments; and the 30 s per-attempt / 90 s total timeout numbers.
14. **Reconciliation date filtering is client-side.** The SDK's `DateTimeOffset` query serialization (`yyyy-MM-ddTHH:mm:ss.fffZ`) is rejected by the sandbox (`422 INVALID_FIELD: Must be in format 2018-01-26T11:21:23`), so the implementation does not send `created_at` filters; it pages all merchant transactions and filters `CreatedAt` in the app. The no-filter default window is 30 days, so `complete=false` when `from` is older. This is a live-verified SDK/API mismatch, not an invented data path.
15. **Capture and refund wait for settlement.** Sandbox capture transfers stay `PENDING` for ~20-30 s. Fulfilment polls `GetTransfer` (up to 60 s under the 90 s request budget) and persists the Finix-reported amount/fee/net; refunds wait for the transfer to leave `PENDING` before requesting a partial reversal, because Finix refuses partial reversals on a pending transfer with an actionable `CONFLICT` message.
16. **Delete has a claim too.** `DELETE /api/payment-methods/{id}` writes `disable:{buyerId}:{paymentMethodId}` before the provider call, so a concurrent double delete is refused by the same primary key and a completed claim returns success.
