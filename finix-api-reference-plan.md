# finix-api-reference-plan.md

Integration: Finix card payments + saved cards in eShopOnWeb, exposed from `src/PublicApi` as JWT-authenticated `/api/` endpoints.
SDK root (plugin-relative): `.opencode/sdk/dotnet/` — map `sdk-map.md`, operations under `map/operations/`, shapes under `src/FinixApiReference/`. No other SDK copy is used.

## 1. Scope & sequence

| # | Step | Operations used |
| --- | --- | --- |
| 1 | Bind `Finix:` settings (`Username`, `Password`, `MerchantId`, `Environment`, `Currency`, `BaseUrl`), validate at startup, register the singleton client and options once | none (client construction only) |
| 2 | Persistence: add app entities to the existing `CatalogContext` (`ShopperFinixIdentity`, `SavedCard`, `SavedCardClaim`, `OrderPayment`, `OrderOperationClaim`, `RefundRecord`, `RefundLock`) + EF migration | none |
| 3 | `POST /api/orders` — place an order from catalog item ids + quantities using `Order`/`OrderItem`; order starts `AwaitingPayment` | none |
| 4 | `POST /api/payment-methods` — lazily create the shopper's buyer identity, then save the card; store only safe fields | `Identities.CreateIdentity`, `PaymentInstrumentsApi.CreatePaymentInstrument` |
| 5 | `GET /api/payment-methods` — the caller's saved cards from the app store (safe descriptor fields only) | none |
| 6 | `DELETE /api/payment-methods/{paymentMethodId}` — remove from the app and disable at Finix | `PaymentInstrumentsApi.UpdatePaymentInstrument` |
| 7 | `POST /api/orders/{orderId}/pay` — resolve source (saved card or one-off card → instrument), authorize the order total (hold, no capture) | `PaymentInstrumentsApi.CreatePaymentInstrument` (one-off only), `AuthorizationsApi.CreateAuthorization` |
| 8 | `POST /api/orders/{orderId}/fulfil` — ADMIN; capture the hold, then read the capture transfer for captured amount/fee | `AuthorizationsApi.GetAuthorization`, `AuthorizationsApi.CaptureAuthorization`, `TransfersApi.GetTransfer` |
| 9 | `POST /api/orders/{orderId}/cancel` — ADMIN; void the hold before capture | `AuthorizationsApi.GetAuthorization`, `AuthorizationsApi.VoidAuthorization` |
| 10 | `POST /api/orders/{orderId}/refunds` — full or partial refund against the capture transfer, caller-supplied idempotency key | `TransfersApi.CreateTransferReversal` |
| 11 | `GET /api/my-orders` — caller's orders + payment state from the app DB | none |
| 12 | `GET /api/reconciliation?from&to` — ADMIN; walk every page of Finix transfers and authorizations in range and line them up with app records | `TransfersApi.ListTransfers`, `AuthorizationsApi.ListAuthorizations` |
| 13 | Tests: stub the SDK HTTP seam; cover claim rejection, unknown-outcome re-reads, capture/void/refund state transitions | all of the above (stubbed) |

## 2. CONTRACT SHEET

Signatures are generated code, verbatim — each operation that takes input takes ONE request record as its first parameter (an operation with no inputs takes none), built with an object initializer whose property names are the record's own, never flat arguments.
Every SDK type is written fully-qualified with the namespace its source path implies, taken from the path the map gives for THAT type, never from where a neighbouring type sits.

### 2.2 CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| A saved-card id used as the authorization `source` must be a payment instrument owned by this shopper's buyer identity and still enabled | `PaymentInstrumentsApi.GetPaymentInstrument` → `AuthorizationsApi.CreateAuthorization` | before `CreateAuthorization`: `SavedCard` lookup by `(ShopperId, PaymentInstrumentId)` then `GetPaymentInstrument`, checking `Identity == ShopperFinixIdentity.IdentityId` and `Enabled != false` |
| `AuthorizationId` for capture, void and re-read must be the id this app stored from `CreateAuthorization` | `AuthorizationsApi.CreateAuthorization` → `AuthorizationsApi.CaptureAuthorization` / `VoidAuthorization` / `GetAuthorization` | `OrderPayment.AuthorizationId` (never taken from the request) |
| A refund `TransferId` must be the capture transfer id this app stored from the capture (`Authorization.transfer`) | `AuthorizationsApi.CaptureAuthorization` (+`TransfersApi.GetTransfer`) → `TransfersApi.CreateTransferReversal` | `OrderPayment.CaptureTransferId`, set only from a capture whose `Transfer` is non-null |
| A void target must be the stored authorization and the order must not be captured | `AuthorizationsApi.CreateAuthorization` / `CaptureAuthorization` → `VoidAuthorization` | `OrderPayment` status transition (`Authorized` → `Voiding`), checked before `VoidAuthorization` |
| A refund amount must be ≤ captured amount minus this app's recorded refunds against that capture transfer | `TransfersApi.GetTransfer` (+ app refund rows) → `TransfersApi.CreateTransferReversal` | before `CreateTransferReversal`: `RefundAmount <= OrderPayment.CapturedAmountCents - OrderPayment.RefundedCents` |
| A `paymentMethodId` on DELETE must be one this shopper saved | `SavedCard` store → `PaymentInstrumentsApi.UpdatePaymentInstrument` | `SavedCard` lookup by `(ShopperId, PaymentInstrumentId)` before the disable call |
| The `identity` on a saved card must be the buyer identity this app created for that shopper | `Identities.CreateIdentity` → `PaymentInstrumentsApi.CreatePaymentInstrument` | `ShopperFinixIdentity` row keyed by the JWT `ClaimTypes.Name` |
| The reconciliation `merchant` filter must be the same merchant id sent as the authorization `merchant` | `AuthorizationsApi.CreateAuthorization` → `TransfersApi.ListTransfers` / `AuthorizationsApi.ListAuthorizations` | `Finix:MerchantId` bound once into the singleton options |

### 2.5 Contract notes that decide call shape

- **Raw card details are not accepted by `CreateAuthorization`.** `AuthorizationAllFields.Source` is documented as “ID of the `Payment Instrument` where funds get debited”, and `PaymentInstrumentCard1` is the model that accepts `number`/`expiration_month`/`expiration_year`/`security_code`. A one-off card therefore costs two calls: `CreatePaymentInstrument` (variant `.PaymentInstrumentCard1`) then `CreateAuthorization` with the returned instrument id as `source`.
- **No idempotency member on the refund body.** `RefundTransfer` declares only `refund_amount`; its `AdditionalProperties` bag (`Core/Models/AdditionalProperties.cs`, `IDictionary<string, JsonElement>` with `Set(string, object?)`) is the only way to put `idempotency_id` on the wire. `Transfer.IdempotencyId` is documented as identifying “`Transfers`, `Authorizations`, or refund requests”, but no refund body member declares it — wire acceptance is `UNVERIFIED`; the app claim is authoritative.
- **`Authorization.Transfer` is the capture signal.** `CaptureAuthorization`’s `<remarks>`: “If captured successfully, the `transfer` field of the `Authorization` will contain the ID of the `Transfer` resource that moves funds.” The `Transfer` property’s own doc says it is created “when the `Authorization` moves to **SUCCEEDED**”, which conflicts with an authorization that is merely held — treat `state == SUCCEEDED` alone as **not** proof of capture (`UNVERIFIED`); require `Transfer` non-null.
- **“Can no longer be captured” is derived, not a single flag.** Defensive rule: block capture when `Transfer` is non-null (already captured), `IsVoid == true`, `VoidState == VoidState.Succeeded`, `State` is `Canceled`/`Failed`/`Unknown`, or `ExpiresAt <= TimeProvider.GetUtcNow()`. On a capture error, surface `FailureCode` + `FailureMessage` from the re-read authorization to the operator. Exact provider meaning of `PENDING` and of `ExpiresAt` timing is `UNVERIFIED`.
- **Fee and net.** `Transfer.Amount` is the Finix-reported captured amount and `Transfer.Fee` the Finix-reported fee; `Transfer` declares **no net field**, so `FinixPaymentService.FillCaptureDetailsAsync` computes `NetCents = Amount - Fee`. `Fee` is nullable; when it is null the report leaves `NetCents` null rather than fabricating zero.
- **Capture fee member is a floor, not the fee to charge.** `CaptureAuthorization.Fee` is documented as a *minimum* fee; leave it unset so the merchant's fee profile decides.
- **No delete operation exists for a payment instrument.** The only provider-side removal path in this SDK is `UpdatePaymentInstrument` with `.PaymentInstrumentDisableAPaymentInstrument { Enabled = false }`; `ListPaymentInstruments` has no `enabled` filter, so disabled cards must be filtered client-side.
- **Reconciliation range and scope.** `from`/`to` bind to `DateTimeOffset` and map to `ListTransfersRequest.CreatedAtGte`/`CreatedAtLte` and `ListAuthorizationsRequest.CreatedAtGte`/`CreatedAtLte` (wire `created_at.gte`/`created_at.lte`, serialized by the SDK's `ToIso8601()`); both are always sent so the server's “last 30 days” default never applies, and `Merchant = Finix:MerchantId` scopes both lists to this merchant.
- **Pagination envelope has no total/count/hasMore.** `Page` declares only `Limit (limit): int?` and `NextCursor (next_cursor): string?`; `Links33` declares `Self (self)` and `Next (next): Next` with `Href (href)`. Exhaustion is `Page.NextCursor == null` (or an empty `_embedded` collection); there is no total-count field to report.

## 9. Assumptions & Blockers

- **Resolved — no delete operation exists for a saved card.** The SDK has no `DeletePaymentInstrument`; `DELETE /api/payment-methods/{id}` removes the app's `SavedCard` row and calls `UpdatePaymentInstrument` with `PaymentInstrumentDisableAPaymentInstrument { Enabled = false }`. The card is no longer listed and cannot be used to pay; the provider retains a disabled instrument. This satisfies the task's required behaviour without inventing a provider capability.
- **Production sign-off note — PCI scope.** `CreatePaymentInstrument`'s own `<remarks>` say creating instruments directly via the API is for testing; production card handling should use hosted fields or the JavaScript client. The sandbox integration uses the direct card path the task requires. This is a compliance note, not a gap in the SDK.
- **Environment mapping — implemented.** `FINIX_ENVIRONMENT=sandbox` and `live` are both accepted. `FinixOptions.ResolveBaseUrl()` uses `Finix:BaseUrl` verbatim when set, otherwise the sandbox host for `sandbox` and the live host for `live`. `options.Environment = ServerEnvironment.Production` is used only as the SDK's carrier for that base URL.
- **Currency — implemented.** `Finix:Currency` must be `USD` or `CAD`; the open `Currency` enum has no public factory, so other codes fail startup rather than being built by reflection.
- **Order total — implemented.** `FinixPaymentService.ToCents` converts `Order.Total()` to cents with `MidpointRounding.AwayFromZero`; the same value is sent as `amount` and `capture_amount`.
- **Order placement — implemented.** `POST /api/orders` accepts catalog item ids + quantities plus the shipping address; each line snapshots the catalog price/name into `OrderItem`/`CatalogItemOrdered`.
- **Identity per shopper — implemented.** One `ShopperFinixIdentity` row per JWT `ClaimTypes.Name`; it is created lazily and never exposed.
- **Fee/net — implemented.** `Transfer.Amount` is the captured amount, `Transfer.Fee` the provider fee, and `NetCents = Amount - Fee` (or null when the provider has not reported a fee).
- **Refund idempotency — implemented.** `RefundRecord.RefundKey = orderId:idempotencyKey` is the primary key; `idempotency_id` is also sent through `RefundTransfer.AdditionalProperties` as defence in depth. Distinct keys remain distinct refunds; a failed attempt is removed so the same key can retry after a provider refusal.
- **Capture semantics — implemented.** `CaptureBlockReason` blocks when `Transfer` is non-null, `IsVoid`, `VoidState == Succeeded`, state is `CANCELED`/`FAILED`/`UNKNOWN`, or `ExpiresAt` has passed; the operator error includes `DescribeHoldState` (state, void, expiry, failure code/message).
- **Roles — implemented.** Fulfil, cancel and reconciliation require `ADMINISTRATORS`; every other endpoint is shopper-scoped. Refunds are shopper-scoped because the task explicitly lists only fufil, cancel and reconciliation as operator actions.
- **Payment idempotency — implemented.** Each new `OrderPayment` gets `IdempotencyId = eshop-order-{orderId}-{guid}`; a retry uses the stored value, while a fresh database/run cannot collide with a prior sandbox authorization. The `OrderPayment` primary key is the real duplicate guard.
- **Date filters — SDK wire-format workaround.** The generated SDK serialises `DateTimeOffset` query filters in a fractional-second/offset form that Finix rejects with `INVALID_FIELD: Must be in format 2018-01-26T11:21:23`. `FinixRequestHooks.NormalizeDateFilters` (an `SdkHook.OnRequest`) rewrites `created_at.*`, `updated_at.*` and `ready_to_settle_at.*` to UTC `yyyy-MM-ddTHH:mm:ss`. This corrects the wire format; it does not add a provider capability.
- **Test card — used.** The supplied Mastercard (`5200 8282 8282 8210`, `12/2029`, `022`) was used for the sandbox verification and is never logged or persisted.
