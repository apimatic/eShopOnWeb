# finix-api-reference-plan.md

Integration: Finix card payments + saved cards for eShopOnWeb `src/PublicApi` (ASP.NET Core 8 minimal APIs, JWT, in-memory DB).
SDK: `FinixApiReference` (generated, plugin-local) — SDK root `.opencode/sdk/dotnet/`; map `sdk-map.md`, operations `map/operations/`.
Project reference target: `.opencode/sdk/dotnet/src/FinixApiReference/FinixApiReference.csproj` (machine-local path; re-point on another install).

## 1. Scope & sequence

| # | Step | SDK operations used |
| --- | --- | --- |
| 0 | Prereq: add the SDK `<ProjectReference>` to `src/PublicApi/PublicApi.csproj`; bind `Finix:` settings (config keys, env-var fallback) + fail-fast; register `AddFinixApiReferenceClient`; register the payments store. Change `global.json` `rollForward` to `latestMajor` (or `major`) so the .NET 10-only machine can build. | none |
| 1 | Payments store (app-owned, in-memory EF): `OrderPayment` (1:1 with existing `Order.Id`) carrying `Status`, `TotalCents`, `Currency`, `PaymentAttemptKey`, `AuthorizationId`, `AuthorizationStatus` (`State1.Value`), `HoldExpiresAt`, `CaptureTransferId`, `TransferState` (`State11.Value`), `CapturedCents`, `FeeCents`, `AmountRefundedCents`; `SavedCard` (shopper → Finix instrument); `ShopperProfile` (shopper → Finix buyer `Identity`); `RefundRecord` (refund id/transfer id, amount, state); `PaymentOperationClaim` (PK claim table). Existing `Order`/`OrderItem` are reused unchanged. | none |
| 2 | One gateway class fronting the SDK: client construction, per-call total budget, error translation to typed results, `GenericError` extraction, identity ensure, claim helpers. No endpoint calls the SDK directly. | none |
| 3 | `POST /api/orders` — shopper; read catalog prices via `IRepository<CatalogItem>`, build `Order`+`OrderItem`, create `OrderPayment` in `AwaitingPayment`. | none |
| 4 | `POST /api/orders/{orderId}/pay` — AUTHORIZE (hold). Saved-card branch uses the stored instrument; one-off branch ensures the shopper's buyer `Identity`, creates a payment instrument, then authorizes. Amount = order total in cents, currency from config. | `Identities.CreateIdentity`, `PaymentInstrumentsApi.CreatePaymentInstrument`, `AuthorizationsApi.CreateAuthorization` |
| 5 | `POST /api/orders/{orderId}/fulfil` — operator (`Administrators`). Re-read the hold first; when it can no longer be taken return 409 with an operator-actionable reason, then capture; re-read the capture transfer for fee/net. Checks: no `AuthorizationId` → "order was never authorized"; `State != Succeeded` → include `failure_code` + `failure_message`; `IsVoid == true` or `VoidState == Succeeded` → "hold was released (voided) — ask the shopper to pay again"; `ExpiresAt <= now` → "hold expired at {ExpiresAt} — ask the shopper to pay again"; already captured → "captured at {time}". A 422 from capture is reported with the provider `code`/`message`/`logref`. | `AuthorizationsApi.GetAuthorization`, `AuthorizationsApi.CaptureAuthorization`, `TransfersApi.GetTransfer` |
| 6 | `POST /api/orders/{orderId}/cancel` — operator (`Administrators`), before fulfilment. Void the hold; no money moves. | `AuthorizationsApi.GetAuthorization`, `AuthorizationsApi.VoidAuthorization` |
| 7 | `POST /api/orders/{orderId}/refunds` — shopper, own order. Full or partial against the captured transfer; caller-supplied idempotency key; never beyond captured − already refunded. | `TransfersApi.GetTransfer`, `TransfersApi.CreateTransferReversal` |
| 8 | `GET /api/my-orders` — caller's orders + payment state from the store. | none |
| 9 | `GET /api/reconciliation?from&to` — operator. Page the whole range of Finix transfers and join to eShop orders; report `truncated`/`nextCursor`. | `TransfersApi.ListTransfers` |
| 10 | `POST /api/payment-methods` — save card; `GET /api/payment-methods`; `DELETE /api/payment-methods/{paymentMethodId}` — disable at Finix + mark deleted. | `PaymentInstrumentsApi.CreatePaymentInstrument`, `PaymentInstrumentsApi.UpdatePaymentInstrument` |
| 11 | Tests: `WebApplicationFactory` end-to-end with a stubbed SDK `HttpClient`; claim/unknown-outcome tests. | — |

Response identifiers (top level of each body, never nested): `orderId` from `POST /api/orders` (the existing `Order.Id`), `paymentMethodId` from `POST /api/payment-methods` (the app's `SavedCard.Id`, which is also what `DELETE /api/payment-methods/{paymentMethodId}` takes), `refundId` from `POST /api/orders/{orderId}/refunds` (the Finix reversal `Transfer.Id`). The Finix instrument id, authorization id and capture transfer id stay server-side on `OrderPayment`/`SavedCard`.

Route/auth conventions to imitate (read at edit time):- Endpoint shape: `src/PublicApi/CatalogItemEndpoints/CatalogItemGetByIdEndpoint.cs` (`IEndpoint<IResult, TRequest, …>`, `MapGet("api/…")`).
- Admin-only: `src/PublicApi/CatalogItemEndpoints/DeleteCatalogItemEndpoint.cs` — `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS, AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]` on the lambda. Shopper endpoints: same attribute without `Roles`.
- Caller identity: `HttpContext.User.Identity!.Name` — the token carries `ClaimTypes.Name` only (`src/Infrastructure/Identity/IdentityTokenClaimService.cs`); match it to `Order.BuyerId` and `SavedCard.ShopperId`.
- Store: existing EF in-memory toggle pattern (`src/Infrastructure/Dependencies.cs`), test config `tests/PublicApiIntegrationTests/appsettings.test.json`.

## 3. Trap notes

1. `PaymentInstrumentCard1.Number`, `SecurityCode`, `Name`, `Address` are card data; the SDK logs JSON request bodies **verbatim** when body logging is on, and `FINIX_API_REFERENCE_LOG=trace` turns it on with no code change — MUST load dotnet-configuration-resilience.
2. `PaymentInstrumentsRequest` and `AuthorizationsRequest` are multi-variant unions; building the body as a bare model or guessing the factory picks the wrong wire shape and fails at runtime — MUST load dotnet-models.
3. `Currency` is an open string enum with no public constructor or factory; a config string must be resolved, not cast — MUST load dotnet-models.
4. `GenericError` nests its messages under `_embedded.errors[]`; `TryGetGenericError` returning `true` does not mean a top-level message exists — MUST load dotnet-error-handling.
5. The SDK resends `PUT` (capture, void, disable) on transient failures but never `POST` (authorize, create instrument, refund) — the duplicate risk differs per write — MUST load dotnet-configuration-resilience.
6. Every non-GET call carries an `Idempotency-Key` header filled with a fresh `Guid.NewGuid()`; only a request-record member is a real key — MUST load dotnet-calling-endpoints.
7. These list operations are not `Pageable`; `Page.NextCursor` is the only continuation and a page loop with no bound can run forever — MUST load dotnet-configuration-resilience.
8. A transport failure after a write leaves the outcome unknown; reporting failure without re-reading provider state is a defect — MUST load dotnet-configuration-resilience.
9. `AddFinixApiReferenceClient` registers a singleton over the default unnamed `HttpClient` and captures options once at registration — MUST load dotnet-client-initialization.
10. A blank half of `BasicAuth` is treated as configured and sent as-is; nothing fails until the first call — MUST load dotnet-authentication.
11. A 2xx body that does not match its declared model, or a non-2xx that does not match its `{Operation}Error`, surfaces as `ResponseDeserializationException`, not `ApiException<TError>` — MUST load dotnet-error-handling.
12. Response models are nullable by default (`Id`, `State`, `Transfer`, `Fee`, `NextCursor`); null-forgiving hides a provider shape change — MUST load dotnet-models.
13. `ServerEnvironment.Production` is the sandbox host; selecting "live" is an app-level `BaseUrl` override, not an SDK environment — MUST load dotnet-configuration-resilience.
14. Stubbing the SDK for tests is done at the `HttpClient` seam, not by mocking `FinixApiReferenceClient` — MUST load dotnet-testing.

## 6. Assumptions & Blockers

**Assumptions**

1. **Buyer identity is required.** `PaymentInstrumentCard1.Identity` is `required`, so a card instrument cannot be created under the merchant alone. The plan creates one **buyer** `Identity` per shopper (`CreateIdentity` with `Buyer { Entity = new Entity5 { … } }`, all `Entity5` fields optional) on first need, stores it on `ShopperProfile`, and reuses it. This is a buyer identity, not a merchant identity — no merchant is created.
2. **One-off cards.** The SDK has no card-token source for an authorization (`AuthorizationAllFields.Source` is a payment-instrument id), so a one-off card is turned into a payment instrument under the shopper's identity, used, and then disabled best-effort after the authorization settles; only its id is recorded on the order. The number/CVV are never persisted.
3. **`POST /api/orders` body.** The existing `Order` constructor requires `buyerId`, an `Address shipToAddress`, and `List<OrderItem>`; the endpoint therefore accepts an optional shipping address and falls back to a fixed demo address when omitted. Item ids/quantities and catalog prices are the source of amounts; unknown item ids are a 400.
4. **Amounts.** `CatalogItem.Price` is a `decimal` in dollars; cents = `(long)Math.Round(price * 100m, MidpointRounding.AwayFromZero)`; the order total is the sum over items. `Finix:Currency` defaults to `USD` when blank (eShop prices are USD), and an unknown code fails startup.
5. **Caller identity.** The JWT carries `ClaimTypes.Name` only (no user id), so `Order.BuyerId` and `SavedCard.ShopperId` are the username. Admin = role `Administrators` (`BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS`).
6. **Card delete.** The SDK has **no delete-payment-instrument operation**; deletion is `UpdatePaymentInstrument` with `PaymentInstrumentDisableAPaymentInstrument { Enabled = false }` plus marking the app row deleted, which satisfies "not listed and not usable to pay".
7. **Net proceeds.** `Transfer` has no net field; the app reports `net = Amount − Fee`. `Fee` can be null before the transfer settles, so the response reports `fee: null` and `net: null` with a `feePending: true` flag rather than guessing.
8. **Refund idempotency is app-side.** `README.md` says `idempotency_id` is available on `/transfers/{id}/reversals`, but this SDK's three reversal body variants expose only `refund_amount` — no such member. The caller's key is therefore enforced by the app claim, not sent to Finix. Whether the provider dedupes reversals by anything else is UNVERIFIED.
9. **`idempotency_id` retention** on authorizations is not documented in the SDK; the app claim remains authoritative even when the provider key is sent.
10. **Duplicate order/card saves.** A double submit of `POST /api/orders` creates a second order; a double submit of `POST /api/payment-methods` without an `Idempotency-Key` header creates a second saved card. Neither moves money; refunds and the three payment operations are the idempotent ones the task requires.
11. **Build environment.** `global.json` pins `8.0.x` with `rollForward: latestFeature`, which does not reach a .NET 10-only SDK; it must become `latestMajor` (or `major`). If the `net8.0` targeting pack is unavailable, retarget `PublicApi` and the test project to `net10.0`.
12. **Store.** Payments data lives in a new in-memory EF context (`UseInMemoryDatabase`), independent of the SQL/in-memory switch used for catalog and identity; it is recreated per process, which is acceptable for this task.

**Blockers**

- **Live only (not sandbox):** the SDK's `CreatePaymentInstrument` remarks say direct instrument creation "should only be done for testing purposes" and that CVV submission is limited to PCI-compliant merchants. On a live merchant that is not PCI-enabled, the provider is expected to reject card creation (and CVV). The sandbox merchant is pre-approved, so the plan is executable there; going live needs hosted fields/tokenization, which this SDK does not expose.
- **Live only:** the live base URL `https://finix.live-payments-api.com` comes from the README, not the map; it is UNVERIFIED until the first live call. `Finix:BaseUrl` can override it without a code change.
